# 작업명세 05 테스트 계획: 환불 요청과 확인 기간 만료 자동 완료

- 작성일: 2026-10-13
- 작업기록: [작업기록](../작업기록.md)
- 관련 명세: [작업명세 01 테스트 계획: 공통](01_테스트계획_공통.md), [작업명세 07 공통 실행 참조](07_공통실행참조.md)

상황 S1-4의 조건, 요청, 절차, 예상 결과를 정한다. 테스트 목적, 테스트 방법, 실행 환경, 공통 결과 확인 기준은 [작업명세 01](01_테스트계획_공통.md)을 따른다.

## 1. 검증 목적과 정상 동작

구매자가 420,000원에 구매한 에어랩을 배송받은 뒤, 상품 확인 기한 직전에 구성품 누락을 발견하여 환불을 요청한다. 환불 요청이 처리되는 동안 같은 주문에 확인 기간 만료 자동 완료가 실행된다. 자동 완료는 배송 완료 후 48시간이 지난 주문을 정상 완료로 바꾸고 판매자에게 판매대금을 지급한다.

충돌하는 처리는 구매자의 환불 요청과 확인 기간 만료 자동 완료다. 확인 기간 만료 자동 완료는 주문을 조회한 뒤 그 주문에 환불 요청이 있는지 한 번 더 조회한다. 이 조회가 환불 요청의 커밋 뒤에 실행되면 그 주문을 완료하지 않는다.

**정상 동작:** 기한 안에 환불 요청이 먼저 접수되면 거래 상태는 보류가 되고 판매대금은 지급되지 않는다(요구사항 F-016-AC-02). 자동 완료가 먼저 성립하면 뒤이은 환불 요청은 409 `TRADE_ALREADY_FINALIZED`로 거절된다.

## 2. 사전조건과 테스트 데이터

### 2.1 시작 상태와 금액

| 항목 | 값 |
|---|---|
| 거래 상태 | 진행 중(`IN_PROGRESS`) |
| 배송 상태 | 배송 완료(`DELIVERED`). 준비 순서의 모의 배송 완료로 만든다 |
| 상품 | 에어랩, 가격 420,000원, 수량 1개. 등록 가격으로 결제 |
| 구매자 | 충전 450,000원, 결제 후 잔액 30,000원 |
| 판매자 | 충전 없음, 잔액 0원 |

### 2.2 기준 시각

아래 날짜는 모두 2026년이다. 요청 A와 요청 B의 시각은 서비스가 처리 조건을 검사할 때 쓰는 처리 기준 시각이며, JMeter가 HTTP 요청을 보내는 실제 시각과는 관계없다.

| 시점 | KST | API에 넣는 값(UTC) |
|---|---|---|
| 사전 준비(결제, 발송 등록) | 10-05(월) 10:00 | 서버 시계 `2026-10-05T01:00:00Z` |
| 모의 배송 완료 | 10-05(월) 10:02. 이 시각에서 48시간 뒤가 확인 기한이다 | 파라미터 `now=2026-10-05T01:02:00Z` |
| 확인 기한 | 10-07(수) 10:02 | 서버가 계산해 `PURCHASE_ORDER.INSPECTION_DEADLINE_AT`에 저장. 예상값 `2026-10-07T01:02:00Z` |
| 요청 A(환불 요청) | 10-07(수) 10:01:59.500. 확인 기한 0.5초 전 | 서버 시계 `2026-10-07T01:01:59.500Z` |
| 요청 B(확인 기간 만료 자동 완료) | 10-07(수) 10:02:05. 확인 기한 5초 뒤 | 파라미터 `now=2026-10-07T01:02:05Z` |

### 2.3 준비 순서

서버 시계를 `2026-10-05T01:00:00Z`로 설정한 뒤 다음 요청을 순서대로 보낸다.

1. 판매자와 구매자의 회원 가입과 로그인. 요청 형식은 [작업명세 07의 1절](07_공통실행참조.md#common-requests)을 따른다.
2. 판매자의 상품 등록 `POST /api/products`

   ```json
   {"name":"에어랩","description":"열 번 정도 사용했습니다. 구성품 전부 포함.","category":"ELECTRONICS","price":420000,"quantity":1}
   ```

3. 구매자의 충전 `POST /api/wallet/charges`

   ```json
   {"amount":450000,"requestId":"${__UUID()}"}
   ```

4. 구매자의 결제 `POST /api/orders`

   ```json
   {"productId":${productId},"quantity":1,"recipientName":"최유진","shippingAddress":"대전광역시 유성구 대학로 99","requestId":"${__UUID()}"}
   ```

5. 판매자의 발송 등록 `POST /api/orders/${orderId}/shipment`

   ```json
   {"carrierName":"한빛택배","trackingNumber":"6120-3345-9081","requestId":"${__UUID()}"}
   ```

6. 모의 배송 완료 `POST /test-support/jobs/delivery-complete?now=2026-10-05T01:02:00Z`. 주문의 배송 상태가 배송 완료로 바뀐다.

## 3. 요청 A와 요청 B

서버 시계를 `2026-10-07T01:01:59.500Z`(확인 기한 0.5초 전)로 설정한 뒤 두 요청을 보낸다. 요청 A는 서버 시계의 시각으로, 요청 B는 `now`로 넘긴 시각으로 처리된다.

**요청 A: 구매자의 환불 요청** `POST /api/orders/${orderId}/refund-request` (구매자 로그인 쿠키, `RefundService.requestRefund`)

```json
{"reasonCode":"DESCRIPTION_MISMATCH","detail":"구성품 전부 포함이라고 되어 있었는데 브러시 하나가 없습니다.","requestId":"${__UUID()}"}
```

**요청 B: 확인 기간 만료 자동 완료** `POST /test-support/jobs/inspection-complete?now=2026-10-07T01:02:05Z` (JMeter, `TradeCompletionService.completeExpiredInspections`)

본문은 없다. API 형식은 [작업명세 07의 2.2절](07_공통실행참조.md#test-support-api)을 따른다.

## 4. 겹침 재현 테스트

### 4.1 중지 위치

자동 완료는 환불 요청을 조회하기 전에 멈추므로, 재개 후의 환불 요청 조회가 환불 요청의 커밋 전인지 뒤인지에 따라 결과가 갈린다.

| 요청 | 중지 전에 끝난 조회 | 재개 후 조회 |
|---|---|---|
| A 환불 요청 | 주문 | 이미 접수된 환불 요청이 있는지 조회 |
| B 확인 기간 만료 자동 완료 | 주문 | 환불 요청이 있는지 조회. 없으면 완료를 진행하며 판매자 지갑을 조회 |

### 4.2 실행 절차

커밋 순서마다 별도의 주문으로 실행한다.

1. 2.3절의 준비 요청을 보낸다.
2. 서버의 요청 일시 중지를 켠다.
3. 서버 시계를 `2026-10-07T01:01:59.500Z`로 설정하고 요청 A와 요청 B를 보낸다.
4. 요청 A는 주문 조회 직후에, 요청 B는 주문 조회 뒤 환불 요청 조회 전에 멈췄는지 확인한다.
5. 먼저 커밋할 요청을 재개하고, 그 요청의 커밋이 끝났는지 확인한다.
6. 나머지 요청을 재개하고 응답을 받는다.
7. 6절의 값을 확인하고 기록한다.

### 4.3 예상 결과(가설)

아래 결과는 코드 분석에서 세운 가설이며 아직 실행하지 않았다.

| 커밋 순서 | 응답 | 테스트 직후의 주문 | 환불 요청(`REFUND_REQUEST`) | 판매대금 지급(`SALE_PAYOUT`) | 위반 기준 |
|---|---|---|---|---|---|
| 요청 A(환불 요청) → 요청 B(자동 완료) | A 201, B `{"processed": 0}` | 보류(`ON_HOLD`) | 응답 대기(`PENDING`) 1행 | 없음 | 없음 |
| 요청 B(자동 완료) → 요청 A(환불 요청) | A 201, B `{"processed": 1}` | 보류(`ON_HOLD`)로 되돌아감. 완료 기록(`COMPLETION_CAUSE`, `FINALIZED_AT`)이 NULL로 지워짐 | 응답 대기(`PENDING`) 1행 | +420,000원 1건 | 기준 1, 3 |

- **환불 요청이 먼저 커밋된 경우:** 자동 완료는 재개 후 환불 요청을 조회하므로, 접수된 환불 요청을 보고 완료를 건너뛸 것으로 예상한다. 정상 동작과 같은 결과다.
- **자동 완료가 먼저 커밋된 경우:** 환불 요청은 중지 전에 조회한 진행 중 주문으로 처리를 계속하여 주문을 보류로 되돌린다. 테스트 직후 판매자는 420,000원을 받았는데 주문은 보류이고 환불 요청은 응답 대기다. 이후 환불 요청 접수 48시간 뒤에 무응답 자동 환불이 실행되면 구매자에게도 420,000원이 반환될 수 있고, 판매자가 응답 기한 안에 환불을 거절하면 판매대금이 한 번 더 지급될 수 있다. 이후 처리는 이번 테스트 절차에 포함하지 않는다.

## 5. 정책 구성을 결정하기 위한 테스트 시나리오

지금까지의 테스트 계획은 각 동작에 대해 상태 값이 바로 직결되는 관계만 다룬다. 이 문서에서는 환불 요청과 확인 기간 만료 자동 완료다. 이 절에는 다음 두 가지를 고려한, 실제 요청 상황을 가정한 테스트 시나리오를 쓰고, 요청이 성공하든 실패하든 그 시나리오로 실제 테스트하여 정책 구성을 결정하는 데 쓴다.

- 요청에 대한 결과가 다른 상태들 혹은 비즈니스 맥락에 영향을 미칠 범위
- 실제 이 기능들을 사용하는 수많은 요청이 발생할 수 있다는 점과, 이를 비즈니스 정책에 반영할지

시나리오의 내용과 이 명세에 쓸 범위는 아직 정하지 않았다.

## 6. 결과 확인과 기록

적용할 기준은 [작업명세 01의 6절](01_테스트계획_공통.md#result-criteria)의 기준 1~3과 기준 5다. 요청 A는 HTTP 2xx 응답을, 요청 B는 처리 건수 1을 성공으로 본다. 기준 2·3·5는 [작업명세 07의 SQL 3.1, 3.2, 3.4](07_공통실행참조.md#result-sql)로 확인한다.

이 상황에서 확인할 값은 다음과 같다.

- 요청 A의 HTTP 응답 코드(201 또는 409 `TRADE_ALREADY_FINALIZED`)와 요청 B의 처리 건수
- `PURCHASE_ORDER`의 `TRADE_STATUS`, `COMPLETION_CAUSE`, `FINALIZED_AT`, `INSPECTION_DEADLINE_AT`
- `REFUND_REQUEST`의 행 수와 `DECISION`
- 판매자 `BALANCE_TRANSACTION`의 `SALE_PAYOUT` 건수

추가 증거로 서버 로그에서 자동 완료의 환불 요청 조회가 환불 요청의 커밋 전에 실행됐는지 뒤에 실행됐는지, 주문 UPDATE가 모든 컬럼을 포함하는지, 두 요청의 커밋 순서를 확인한다. 보관 자료와 민감 정보 처리는 [작업명세 01의 6.3절](01_테스트계획_공통.md#result-criteria)을 따른다.

## 8. 변경 기록

- 2026-10-13: 문서작성지침에 따라 본문 전반의 어휘와 문장을 수정하고, 조회·처리·커밋 시점과 결과 확인 기준을 구분했다. 중복 설명을 정리하고 테스트 조건, 입력값과 SQL은 유지했다.
- 2026-10-13: 문서작성지침에 따라 용어, 문장과 설명 순서를 정비했다. 처리 조건과 커밋 순서를 명확히 하고, 예상 결과가 실행 전 가설임을 명시했다.
- 2026-10-13: 사용자 지시로 구조를 「검증 목적과 정상 동작 / 사전조건과 테스트 데이터 / 요청 A와 요청 B / 겹침 재현 테스트 / 동시 전송 반복 테스트 / 결과 확인과 기록」으로 바꿨다. 기준 시각을 KST와 API 입력값을 함께 적은 표로 합치고, 요청과 예상 DB 값을 각 절로 옮겼다. 공통 기준·기록 항목·가정은 작업명세 01의 6절로, 공통 요청과 SQL은 작업명세 07로 옮겼다.
- 2026-10-13: 사용자 지시로 5절을 기초적인 명세만 남기도록 고쳤다. 반복 횟수와 결과 종류 표를 지우고, 테스트의 실행 시점과 목적, 기본 방법, 실행 전에 상황별로 정할 사항만 남겼다.
- 2026-10-13: 사용자 지시로 5절 첫 문단에 겹침 재현 테스트와의 차이, 보내는 요청과 서버가 정하는 처리 순서, 결과를 정책 결정 과정에 쓰는 방식을 더했다.
- 2026-10-13: 사용자 지시로 5절을 처음부터 다시 썼다. 제목을 「정책 구성을 결정하기 위한 테스트 시나리오」로 바꾸고, 사용자가 전달한 두 가지 고려 사항(요청 결과가 다른 상태와 비즈니스 맥락에 미치는 영향 범위, 수많은 요청이 발생하는 상황의 정책 반영)과 아직 범위를 정하지 않았다는 사실만 남겼다. 기본 방법 다섯 단계는 지웠다.
