# 작업명세 02 테스트 계획: 구매자 취소와 판매자 취소

- 작성일: 2026-10-13
- 작업기록: [작업기록](../작업기록.md)
- 관련 명세: [작업명세 01 테스트 계획: 공통](01_테스트계획_공통.md), [작업명세 07 공통 실행 참조](07_공통실행참조.md)

상황 S1-1의 조건, 요청, 절차, 예상 결과를 정한다. 테스트 목적, 테스트 방법, 실행 환경, 공통 결과 확인 기준은 [작업명세 01](01_테스트계획_공통.md)을 따른다.

## 1. 검증 목적과 정상 동작

구매자가 아이폰을 350,000원에 구매한 뒤 판매자와 채팅으로 주문 취소에 합의한다. 두 사람은 상대방의 취소 결과를 확인하기 전에 거의 동시에 취소 요청을 보낸다. 주문 화면은 상대방의 처리를 실시간으로 보여 주지 않으므로 이런 일이 생길 수 있다.

충돌하는 처리는 구매자의 주문 취소와 판매자의 주문 취소다. 두 처리 모두 주문을 취소 완료로 바꾸고 구매자에게 결제액을 돌려준다.

**정상 동작:** 두 취소 요청 가운데 하나만 성공한다. 다른 요청은 이미 끝난 거래에 대한 요청이므로 409 `TRADE_ALREADY_FINALIZED`로 거절된다. 결제액 350,000원은 한 번만 반환되어 구매자 잔액은 400,000원이 된다.

## 2. 사전조건과 테스트 데이터

### 2.1 시작 상태와 금액

두 요청을 보내기 직전의 상태는 다음과 같다.

| 항목 | 값 |
|---|---|
| 거래 상태 | 진행 중(`IN_PROGRESS`) |
| 배송 상태 | 발송 대기(`WAITING_SHIPMENT`) |
| 상품 | 아이폰, 가격 350,000원, 수량 1개. 등록 가격으로 결제 |
| 구매자 | 충전 400,000원, 결제 후 잔액 50,000원 |
| 판매자 | 충전 없음, 잔액 0원 |

### 2.2 기준 시각

| 시점 | KST | 서버 시계 설정값(UTC) |
|---|---|---|
| 사전 준비 | 2026-10-05(월) 10:00 | `2026-10-05T01:00:00Z` |
| 두 요청 전송 | 2026-10-05(월) 10:30 | `2026-10-05T01:30:00Z` |

이 상황의 두 요청에는 기한 검사가 없으므로 시각은 결과에 영향을 주지 않는다.

### 2.3 준비 순서

서버 시계를 `2026-10-05T01:00:00Z`로 설정한 뒤 다음 요청을 순서대로 보낸다.

1. 판매자와 구매자의 회원 가입과 로그인. 요청 형식은 [작업명세 07의 1절](07_공통실행참조.md#common-requests)을 따른다.
2. 판매자의 상품 등록 `POST /api/products`

   ```json
   {"name":"아이폰","description":"배터리 성능 86%, 흠집 없음. 박스와 케이블 포함.","category":"ELECTRONICS","price":350000,"quantity":1}
   ```

3. 구매자의 충전 `POST /api/wallet/charges`

   ```json
   {"amount":400000,"requestId":"${__UUID()}"}
   ```

4. 구매자의 결제 `POST /api/orders`

   ```json
   {"productId":${productId},"quantity":1,"recipientName":"김하늘","shippingAddress":"서울특별시 마포구 월드컵북로 400","requestId":"${__UUID()}"}
   ```

## 3. 요청 A와 요청 B

서버 시계를 `2026-10-05T01:30:00Z`로 설정한 뒤 두 요청을 보낸다. 두 요청 모두 `OrderCancellationService.cancelByParty`가 처리한다.

**요청 A: 구매자의 주문 취소** `POST /api/orders/${orderId}/cancel` (구매자 로그인 쿠키)

```json
{"reason":"판매자와 합의해 취소합니다."}
```

**요청 B: 판매자의 주문 취소** `POST /api/orders/${orderId}/cancel` (판매자 로그인 쿠키)

```json
{"reason":"구매자와 채팅으로 취소에 합의했습니다."}
```

## 4. 겹침 재현 테스트

### 4.1 중지 위치

두 요청은 주문을 조회한 직후에 멈추고, 구매자 지갑은 재개한 뒤에 조회한다. 그래서 나중에 재개한 요청은 먼저 커밋된 요청의 반환액이 반영된 잔액을 조회한다.

| 요청 | 중지 전에 끝난 조회 | 재개 후 조회 |
|---|---|---|
| A 구매자 취소 | 주문 | 구매자 지갑 |
| B 판매자 취소 | 주문 | 구매자 지갑 |

### 4.2 실행 절차

커밋 순서마다 별도의 주문으로 실행한다.

1. 2.3절의 준비 요청을 보낸다.
2. 서버의 요청 일시 중지를 켠다.
3. 서버 시계를 `2026-10-05T01:30:00Z`로 설정하고 요청 A와 요청 B를 보낸다.
4. 두 요청이 주문 조회 직후에 멈췄는지 확인한다.
5. 먼저 커밋할 요청을 재개하고, 그 요청의 커밋이 끝났는지 확인한다.
6. 나머지 요청을 재개하고 응답을 받는다.
7. 6절의 값을 확인하고 기록한다.

### 4.3 예상 결과(가설)

아래 결과는 코드 분석에서 세운 가설이며 아직 실행하지 않았다.

| 커밋 순서 | 응답 | 최종 주문 | 구매자 잔액 | 취소 반환 내역(`CANCEL_REFUND`) | 위반 기준 |
|---|---|---|---|---|---|
| 요청 A → 요청 B | A 200, B 200 | 취소 완료(`CANCELLED`). 취소 주체는 판매자(`SELLER`) | 750,000원 | +350,000원 2건. 변동 후 잔액 400,000원, 750,000원 | 기준 1, 3 |
| 요청 B → 요청 A | A 200, B 200 | 취소 완료(`CANCELLED`). 취소 주체는 구매자(`BUYER`) | 750,000원 | +350,000원 2건. 변동 후 잔액 400,000원, 750,000원 | 기준 1, 3 |

두 요청은 모두 바뀌기 전의 주문을 조회했으므로 재개 후 취소 조건을 통과할 것으로 예상한다. 먼저 커밋된 요청이 구매자 잔액을 400,000원으로 만들고, 나중 요청은 이 잔액을 조회하여 350,000원을 더 더하므로 최종 잔액은 750,000원이 된다. 주문의 취소 주체와 취소 사유는 나중에 커밋된 요청의 값으로 남는다.

반환 내역도 두 건 기록되므로 지갑 잔액과 변동 금액의 합계는 맞는다. 그래서 이 순서에서는 기준 2로 중복 반환이 드러나지 않으며, 요청 성공 수와 반환 내역 건수로 확인한다.

## 5. 정책 구성을 결정하기 위한 테스트 시나리오

지금까지의 테스트 계획은 각 동작에 대해 상태 값이 바로 직결되는 관계만 다룬다. 이 문서에서는 구매자 취소와 판매자 취소다. 이 절에는 다음 두 가지를 고려한, 실제 요청 상황을 가정한 테스트 시나리오를 쓰고, 요청이 성공하든 실패하든 그 시나리오로 실제 테스트하여 정책 구성을 결정하는 데 쓴다.

- 요청에 대한 결과가 다른 상태들 혹은 비즈니스 맥락에 영향을 미칠 범위
- 실제 이 기능들을 사용하는 수많은 요청이 발생할 수 있다는 점과, 이를 비즈니스 정책에 반영할지

시나리오의 내용과 이 명세에 쓸 범위는 아직 정하지 않았다.

## 6. 결과 확인과 기록

적용할 기준은 [작업명세 01의 6절](01_테스트계획_공통.md#result-criteria)의 기준 1~3이다. 기준 2와 기준 3은 [작업명세 07의 SQL 3.1](07_공통실행참조.md#sql-criterion-2)과 [SQL 3.2](07_공통실행참조.md#sql-criterion-3)로 확인한다. 이 상황에는 발송 정보와 환불 요청이 없으므로 기준 4·5의 SQL은 행이 나오지 않아야 한다.

이 상황에서 확인할 값은 다음과 같다.

- 두 요청의 HTTP 응답 코드(200 또는 409 `TRADE_ALREADY_FINALIZED`)
- `PURCHASE_ORDER`의 `TRADE_STATUS`, `CANCELLED_BY`, `CANCEL_REASON`
- 구매자 `WALLET.BALANCE`
- 구매자 `BALANCE_TRANSACTION`의 `CANCEL_REFUND` 건수와 각 행의 `BALANCE_AFTER`

추가 증거로 서버 로그에서 두 요청의 주문 UPDATE가 모든 컬럼을 포함하는지와 커밋 순서를 확인한다. 보관 자료와 민감 정보 처리는 [작업명세 01의 6.3절](01_테스트계획_공통.md#result-criteria)을 따른다.
