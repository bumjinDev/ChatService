### 2026-10-13 로컬 실행 환경 확인

DB와 Redis에 접속하지 않고, 실행 중인 서비스와 설치된 파일, 환경변수 이름만 확인했다. 환경변수의 값은 보지 않았다.

- 로컬 Oracle은 19c이며, README의 Docker 예시(21c XE)와 다르다. Docker 데몬은 실행 중이 아니다.
- 기존 Redis가 실행 중이다.
- JDK 21과 JMeter 5.6.3이 설치되어 있다. JMeter에는 Oracle 드라이버의 소스 묶음만 있고, 실행에 필요한 드라이버 파일은 없다.
- 통합 테스트용 환경변수(`MARKETPLACE_TEST_*`)는 설정되어 있지 않다.

세부 내용은 6절에 적었다.

### 2026-10-13 진행 방식 결정

사용자와 다음 내용을 정했다.

- 진행 과정: 문제 확인 과정 → 충돌 조건 확인 과정 → 정책 결정 과정 → 구현 과정 → 정책 검증 과정. [작업기록](../../작업기록.md)의 「계획 변경」에 적었다.
- 문제 확인 과정에서는 서버가 두 요청이 겹친 상태를 직접 만드는 겹침 재현 테스트와, JMeter로 두 요청을 같은 순간에 반복해 보내는 동시 전송 반복 테스트를 함께 한다.
- 자동 처리를 사람의 요청과 겹치게 만들기 위해 서버 시계 설정, 자동 처리 실행 API, 요청 일시 중지를 테스트 지원 기능으로 둔다.
- 테스트 환경은 미니PC 배포 서버다. 테스트 지원 기능은 운영 코드에 넣고 테스트 설정을 켰을 때만 동작하게 하며, 테스트하는 동안만 DB 계정을 `TOYCHAT_TEST`로 바꾼다. 결과 확인 SQL은 사용자가 SQL Developer로 실행한다.

사용자가 판단을 맡긴 네 가지는 다음과 같이 정했다.

| 사항 | 정한 내용 | 이유 |
|---|---|---|
| 겹침 재현 테스트도 JMeter로 할지 | 두 테스트 모두 같은 서버와 JMeter로 한다. 겹침 재현 테스트는 요청 일시 중지를 켜고, 동시 전송 반복 테스트는 끈다 | 도구를 하나로 맞추고, 두 테스트가 같은 요청과 데이터를 쓰게 한다 |
| 실제 스케줄러 확인 | 문제 확인 과정에서 하지 않는다 | 테스트 지원 API가 스케줄러와 같은 서비스 메서드를 실행한다. 스케줄러의 실행 시점이 주는 영향은 충돌 조건 확인 과정에서 본다 |
| 동시 전송 반복 테스트의 반복 횟수 | 처음에 상황마다 100회로 정했고, 이후 상황별로 다시 정하기로 했다 | 두 요청이 얼마나 자주 겹치는지 측정하는 횟수이며, 상황마다 겹칠 수 있는 구간이 다르다 |
| S1-5 범위 | 판매자 거절(5a)과 동의(5b)를 모두 넣는다 | 5a는 판매대금 지급과 환불 반환이 함께 남고, 5b는 반환이 두 번 반영되거나 잔액과 내역이 어긋나 결과가 다르다 |

### 2026-10-13 상황별 중지 위치와 예상 결과 설계

- 겹침 재현 테스트의 중지 위치를 상황마다 정했다. 기본은 두 요청이 주문을 조회한 직후이고, 미발송 자동 취소는 발송 정보 조회 전, 확인 기간 만료 자동 완료는 환불 요청 조회 전, 무응답 자동 환불은 환불 요청과 주문을 모두 조회한 뒤다.
- 중지 위치를 정하려고 각 처리가 주문 조회 뒤에 무엇을 더 조회하는지 코드로 확인했다.
  - 발송 등록은 발송 정보가 이미 있는지 조회한다.
  - 당사자 취소는 발송 정보를 따로 조회하지 않고 조회한 주문의 배송 상태로 판단한다.
  - 환불 요청은 기존 환불 요청이 있는지 조회한다.
  - 판매자 응답은 주문을 조회한 뒤 환불 요청을 조회한다.
  - 무응답 자동 환불은 환불 요청을 조회한 뒤 주문을 조회한다.
- 커밋 순서마다 예상 결과(가설)와 위반 기준을 정했다. 결과는 [작업명세 02~06](../../작업명세/02_테스트계획_구매자취소와_판매자취소.md)의 4절에 있다.
- 테스트 지원 기능이 코드에 있는지 확인했다. 시계 설정 API, 자동 처리 실행 API, 요청 일시 중지는 아직 없고, 스케줄러를 끄는 설정 `marketplace.scheduler.enabled`만 있다.

### 2026-10-13 정하지 않은 사항

테스트를 실행하기 전에 정해야 하는 사항은 다음과 같다.

- 겹침 재현 테스트에서 두 요청이 필요한 조회를 모두 마치고 저장하기 직전에 멈추는 순서와, 그 위치에서 두 요청을 동시에 진행시키는 순서를 더할지
- 두 요청을 겹치지 않게 차례로 보내는 실행을 더할지
- 사전 요청에 채팅(대화 생성과 메시지)을 넣을지
- 두 요청 뒤에 모의 배송 완료, 자동 완료, 무응답 자동 환불을 이어서 실행해 뒤따르는 결과를 확인할지
- 결과 확인 기준 2개(충전액 합계와 잔액·결제액 합계의 일치, 성공 응답의 상태와 최종 상태의 일치)를 더할지
- 동시 전송 반복 테스트의 상황별 반복 횟수, 회차마다 새 주문을 만드는 방법, 회원 ID 규칙, 회차 사이의 데이터 정리
- 테스트 지원 기능의 세부: 요청 일시 중지를 켜고 끄는 API의 경로와 형식, 요청 A·B를 구분하는 헤더 이름, 테스트 설정의 이름, 상대 요청을 기다리는 시간의 상한, 자동 처리의 건너뜀과 실패를 구분하는 방법
- 미니PC Oracle에 `TOYCHAT_TEST` 계정을 만드는 방법과 권한
