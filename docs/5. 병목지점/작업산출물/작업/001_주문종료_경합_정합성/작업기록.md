## 1. 작업 개요

### 1.1 목적과 범위

결제가 끝난 주문 하나를 구매자, 판매자, 자동 처리가 거의 동시에 끝내려 할 때, 한 주문은 취소 완료, 정상 완료, 환불 완료 가운데 하나로만 끝나야 한다는 규칙(요구사항 BR-005)이 지켜지는지 실제 요청과 Oracle 데이터로 확인한다. 1~3단계 보고서가 시나리오 S1(주문 종료 경로의 상호 배타성)로 정리하고 코드를 읽어 추정한 문제를 실행으로 확인하는 작업이다. 보고서가 추정한 결과는 가설로 다루고, 실행 결과가 가설과 다르면 그대로 기록한다.

범위와 지킬 조건은 다음과 같다.

- 대상: 보고서 3.1절의 다섯 상황 S1-1~S1-5. 다른 시나리오(S2~S8)는 다루지 않는다.
- 실행 환경: 미니PC에 배포된 서버(`http://wherehouse.it.kr:8186/ChatService/`)와 미니PC Oracle의 테스트 전용 계정 `TOYCHAT_TEST`. H2로 실행한 결과는 쓰지 않는다.
- 운영 코드(`src/main`)와 기존 문서(보고서, 요구사항, 설계 명세서, README)는 사용자의 지시 없이 고치지 않는다. 테스트 지원 기능은 사용자 지시로 운영 코드에 넣는다. 문서와 코드가 다른 점을 발견하면 사용자에게 알린다.
- 작업산출물 폴더는 커밋하고, 기타 폴더의 참고 자료는 커밋하지 않는다.

### 1.2 관련 작업

없음. 이 산출물 루트의 첫 작업이다.

## 2. 작업 계획

작업을 만들 때 세운 계획은 다음과 같다.

1. 세부 작업 01(설계): 기준 자료를 읽고, S1-1~S1-5의 요청과 시나리오를 설계하고, 실행 방법과 테스트 코드 추가 계획을 정한다. 사용자 확인을 받기 전에는 아무것도 실행하지 않는다.
2. 세부 작업 02(환경 구성): 테스트 전용 Oracle 계정과 테스트용 Redis를 준비하고, 기존 통합 테스트를 Oracle에서 실행한다.
3. 세부 작업 03(테스트): 실제 서버에 설계한 요청을 하나씩 차례로 보내고, 요청, 응답, DB 행, SQL, 로그를 기록한다.
4. 세부 작업 04(테스트): 통합 테스트 코드로 같은 요청을 겹치게 실행한다.
5. 세부 작업 03·04의 실행 결과를 분석한다.
6. 대안 비교, 기술결정, 코드 수정은 사용자가 방향을 정한 뒤에 한다.

### 계획 변경

- 2026-10-13: 사용자와 진행 과정을 다시 정했다. 위 계획의 3~5번을 아래 다섯 과정으로 바꾼다.

  | 과정 | 하는 일 |
  |---|---|
  | 문제 확인 과정 | 코드를 읽고 세운 가설이 실제로 일어나는지 확인한다. 테스트 계획은 [작업명세 01](작업명세/01_테스트계획_공통.md)~07이다 |
  | 충돌 조건 확인 과정 | 요청 간격, 기한까지 남은 시간 등을 바꿔 가며 실제 비즈니스 상황에 가까운 충돌을 구성한다 |
  | 정책 결정 과정 | 문제 확인 과정과 충돌 조건 확인 과정의 결과(실제 로직 동작과 데이터)로 정책을 정한다. 실제 정책 사례 조사는 후순위다 |
  | 구현 과정 | 정한 정책을 지키도록 구현한다 |
  | 정책 검증 과정 | 정한 정책으로 다시 테스트해 정책이 지켜지는지 확인한다 |

- 2026-10-13: 문제 확인 과정의 테스트 환경을 미니PC에 배포된 서버(`http://wherehouse.it.kr:8186/ChatService/`)로 정했다. 테스트 지원 기능(서버 시계 설정, 자동 처리 실행, 요청 일시 중지)은 운영 코드(`src/main`)에 넣고, 테스트 설정을 켰을 때만 동작하게 한다. 테스트하는 동안에만 이 설정을 켜고 DB 계정을 `TOYCHAT_TEST`로 바꿔 배포하며, 테스트가 끝나면 설정을 끄고 `TOYCHAT`으로 되돌려 다시 배포한다. 결과 확인 SQL은 사용자가 로컬 노트북의 SQL Developer로 직접 실행한다.
