# 거래 시나리오 구성안: 제안 수락 간 경합과 제안 수락·등록 가격 결제의 경합

## 목적과 범위

아직 예약과 주문이 없는 상품에 여러 구매자의 요청이 겹칠 때, 판매할 수 있는 수량을 초과하여 예약과 주문이 성립하지 않는지 확인한다.

확인할 흐름은 두 가지다.

- 서로 다른 구매자의 제안을 판매자가 수락하면서 예약을 생성하는 요청들이 겹치는 흐름
- 판매자의 제안 수락과 다른 구매자의 등록 가격 결제가 겹치는 흐름

예약이나 주문이 성립한 결과뿐 아니라, 예약받은 구매자가 실제로 결제할 수 있는지와 수량을 확보하지 못한 구매자가 어떤 안내를 받고 거래를 끝내는지도 살펴본다.

기존 시나리오가 예약 보유자의 결제·취소·예약 해제까지 이어지는 거래를 다룬다면, 이번에는 새로운 수량 확보가 성립하는 구간에 집중한다.

## 적용할 현재 정책

이번에는 현재 정책을 기준으로 구현의 동작을 확인한다.

- 가격 제안 등록만으로 수량을 확보하지 않는다.
- 판매자의 제안 수락이 성립하면 해당 수량을 구매자에게 예약한다.
- 유효한 예약은 다른 구매자의 거래로 침해되어서는 안 된다.
- 등록 가격 구매자는 결제창에서 수량을 선택하는 것만으로 수량을 확보하지 않는다.
- 새 예약과 등록 가격 결제에 요청 종류에 따른 특별한 우선권을 두지 않는다.
- 화면에서 먼저 누르거나 서버에 먼저 도착했다는 이유만으로 성공을 보장하지 않는다.
- 수량 부족으로 거절된 요청에는 주문·예약·금액 차감이 부분적으로 남아서는 안 된다.

이 정책이 사용자에게 가장 좋은 선택이라고 입증된 것은 아니다. 현재 구현을 평가하기 위한 기준이며, 정책 변경은 관찰 결과와 별도의 사용자 관점 검토를 바탕으로 판단한다.

## 참여자와 거래 조건

판매자는 같은 모델의 모니터 4개를 판매한다. 회의실 구매자는 3개, 작업실 구매자는 2개가 필요하다. 두 구매자는 필요한 수량 전체를 구매하려 하며, 부족하다고 일부만 구매하지는 않는다.

| 항목      | 조건                                                           |
| ------- | ------------------------------------------------------------ |
| 상품      | 모니터 4개, 등록 가격 개당 120,000원                                    |
| 회의실 구매자 | 3개를 개당 100,000원에 제안                                          |
| 작업실 구매자 | 첫 흐름에서는 2개를 개당 110,000원에 제안. 둘째 흐름에서는 가격 협의 없이 등록 가격으로 2개 구매 |
| 시작 잔액   | 구매자마다 600,000원, 판매자 0원                                       |
| 예약 기간   | 기존 설정인 20분. 후속 결제까지 예약 만료 전 유지                               |
| 실행 관계   | 두 흐름은 각각 예약·주문이 없는 새 상태에서 시작                                 |

수량 4개는 두 요청이 각각은 가능하지만 3개와 2개를 함께 확보할 수 없는 조건이다. 참여자의 구매 목적과 수량을 줄이지 않는 선택은 시나리오 가정이다.

## 첫 번째 흐름: 두 제안의 수락이 겹친다

1. 판매자가 상품을 등록하고 두 구매자가 각각 대화를 시작한다.
2. 회의실 구매자는 3개, 작업실 구매자는 2개를 제안한다. 두 제안은 응답 대기 상태다.
3. 판매자가 서로 다른 대화창에서 두 제안을 수락한다. 첫 요청의 결과가 확정되기 전에 다른 요청의 수량 판단과 예약 생성 처리가 겹치도록 구성한다.
4. 두 요청이 끝난 뒤 실제 제안·예약 상태를 확인한다.

정상 결과는 다음 두 가지다.

| 성립한 예약     | 다른 수락 요청          | 후속 거래                             |
| ---------- | ----------------- | --------------------------------- |
| 회의실 구매자 3개 | 작업실 구매자의 2개 수락 실패 | 회의실 구매자가 3개·300,000원 결제. 상품 1개 남음 |
| 작업실 구매자 2개 | 회의실 구매자의 3개 수락 실패 | 작업실 구매자가 2개·220,000원 결제. 상품 2개 남음 |

수락 실패 응답을 받는 사람은 판매자다. 판매자는 실제 수량을 확인하고 해당 구매자에게 안내한다. 구매자는 원하는 수량을 확보할 수 없음을 확인하고 이번 거래를 끝낸다. 판매자는 구매자의 의사를 확인한 뒤 남아 있는 응답 대기 제안을 명시적으로 거절한다.

수락된 구매자의 후속 결제는 두 수락 요청이 끝난 뒤 진행한다. 결제를 추가로 경합시키지 않는다.

## 두 번째 흐름: 제안 수락과 등록 가격 결제가 겹친다

1. 판매자가 새 상품을 등록하고 두 구매자가 구매를 준비한다.
2. 회의실 구매자는 3개를 제안한다. 작업실 구매자는 가격 협의 없이 등록 가격으로 2개를 구매하기로 한다.
3. 판매자가 회의실 구매자의 제안을 수락하는 동안 작업실 구매자가 2개 결제를 요청한다. 두 요청의 수량 판단과 확보 처리가 겹치도록 구성한다.
4. 두 요청이 끝난 뒤 실제 예약·주문·잔액을 확인한다.

정상 결과는 다음 두 가지다.

| 성립한 요청                 | 다른 요청                                | 후속 거래                                 |
| ---------------------- | ------------------------------------ | ------------------------------------- |
| 회의실 구매자 3개 예약          | 작업실 구매자의 2개 결제는 수량 부족으로 거절. 주문·차감 없음 | 회의실 구매자가 예약한 3개·300,000원 결제. 상품 1개 남음 |
| 작업실 구매자 2개·240,000원 결제 | 회의실 구매자의 3개 제안 수락 실패. 예약 없음          | 상품 2개가 남지만 회의실 구매자는 3개가 필요하므로 거래를 끝냄  |

일반 결제에 실패한 작업실 구매자는 최신 구매 가능 수량과 주문·잔액을 확인한다. 원하는 수량보다 적으면 동일 요청을 반복하지 않는다.

제안 수락이 실패했다면 판매자가 회의실 구매자에게 안내하고, 구매 의사를 확인한 뒤 응답 대기 제안을 거절하여 협의를 마친다.

## 잘못된 결과가 발생했을 때 확인할 후속 상황

두 요청이 모두 성공했다면 정상 분기로 받아들이지 않는다.

| 발생한 상태                      | 이어서 확인할 영향                                               |
| --------------------------- | -------------------------------------------------------- |
| 상품 4개에 예약 3개와 2개가 모두 생성됨    | 각 구매자가 자기 예약분을 결제하려 할 때 상대방 예약 때문에 결제하지 못하는지 확인          |
| 상품 4개에 예약 3개와 주문 2개가 함께 성립함 | 주문 수량을 차감한 뒤 남은 수량과 예약 수량이 어긋나는지, 예약 구매자의 후속 결제가 막히는지 확인 |

이는 현재 코드 구조를 바탕으로 확인하려는 가설이며 실제 재현 결과가 아니다.

수량 초과를 발견한 시점에 이미 실패로 기록한다. 후속 요청은 그 실패가 구매자에게 어떤 영향을 주는지 확인하기 위한 관찰이다. 성공한 것처럼 보이게 데이터를 고치거나, 한 구매자의 예약을 임의로 해제하여 정상 결말을 만들지 않는다.

구매자가 수락·예약 안내를 받았는데 결제하지 못한다면 최신 상태를 확인하고 판매자에게 문의하는 데까지 이어 간다. 잘못된 약속을 누구에게 어떤 방식으로 정정할지는 별도의 정책 검토 대상으로 남긴다.

## 이번 관찰의 종료 지점

정상 흐름은 성립한 예약의 결제와 수량을 확보하지 못한 구매자의 거래 종료까지 확인한다.

취소, 예약 해제·만료 경합, 발송, 배송 완료, 구매 확정, 정산은 추가하지 않는다. 자동 대기열이나 자동 재시도도 전제하지 않는다.

요청 두 개로 필요한 겹침을 재현하는 것부터 시작한다. 운영 환경을 대표하는 요청 수라고 주장하지 않으며, 요청 수와 상품 집중도를 늘리는 부하 실험은 이후 별도로 구성한다.

## 관찰 이후 검토할 사항

실험에서는 현재 정책을 위반한 데이터 오류와 정책에 따른 정상적인 수량 부족 거절을 구분한다.

이후 필요성이 드러나면 다음 정책을 검토한다.

- 등록 가격 구매자에게도 결제 준비 중 수량을 확보해 줄 것인가.
- 수량 선택·변경 중 어느 시점에 확보를 요청할 것인가.
- 결제창 이탈과 미결제 상태에서 확보를 언제 해제할 것인가.
- 확보 제한 시간을 어떻게 정할 것인가.

정책 검토는 데이터 오류가 발생했을 때만 가능한 것은 아니다. 구현이 현재 정책을 정확히 지켜도, 사용자가 결제 준비 후 구매하지 못하는 경험은 별도의 검토 대상이 될 수 있다.

기술 대안은 동일한 정책과 정상 결과를 보장하는 조건에서 비교한다. 정책 변경 효과와 동시성 오류 수정 효과를 구분하고, 실제 사용자 자료가 없는 구매 준비 시간·이탈 비율·요청량은 실험 가정으로 명시한다.
