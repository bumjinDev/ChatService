## 1. 개요

### 1.1 유형

테스트

### 1.2 목적과 범위

판매자가 등록한 모니터 7개를 세 구매자가 각각 3개, 2개, 3개 사려는 거래 시나리오의 1번부터 7번까지를 JMeter로 요청하고, 응답과 DB 데이터로 현재 구현의 결과를 확인한다. 같은 상품의 수량을 남은 수량보다 많이 배정하지 않는지, 주문 취소와 예약 해제 뒤 각 구매자에게 안내하는 구매 가능 수량이 업무 규칙과 맞는지를 본다. 구매 가능 수량은 남은 수량에서 다른 회원의 유효 예약(예약 중이고 만료 시각이 지나지 않은 예약) 수량을 뺀 값이다.

세 구매자는 주문 취소 구매자, 정가 구매자, 추가 제안 구매자다. 주문 취소 구매자는 3개를 합의 가격으로 예약해 결제한 뒤 주문을 취소하고, 정가 구매자는 등록 가격으로 2개를 결제하며, 추가 제안 구매자는 3개를 합의 가격으로 사려고 판매자에게 제안한다.

서버에 요청 순서를 제어하는 코드나 로그를 남기는 코드를 넣지 않고, 개선 기술이나 새 정책을 적용하지 않은 현재 구현으로 실행한다. 동일 주문의 중복 취소, 취소와 발송 등록의 경합, 미발송 자동 취소의 경합, 동일 지갑의 동시 변경은 범위에 넣지 않는다.

## 2. 계획

- 시나리오 테스트 명세서의 시나리오 1번부터 7번까지를 실행마다 JMeter 계획 하나로 요청한다. 계획은 회원 가입, 시나리오 1번의 준비, 시나리오 2번의 결제와 수락 경합, 시나리오 2번 실행 후 단계(구매자별 수량 조회와 이어갈 흐름 결정) 순서로 요청을 보낸다. 그다음 시나리오 2번의 응답 코드로 정가 결제 성공 흐름과 추가 제안 수락 성공 흐름 가운데 하나를 골라, 그 흐름의 시나리오 3번부터 7번까지 보낸다.
- 처리 기준 시각은 서버가 예약 만료와 거래 기한을 판단할 때 쓰는 시각이다. 계획은 시나리오 1번의 준비에서 이 시각을 고정하고, 시나리오 7번의 모의 배송 완료 전에 3분 뒤로 옮기며, 마지막에 고정을 푼다.
- 시나리오 2번은 주문 취소 구매자의 합의 가격 3개 결제, 정가 구매자의 등록 가격 2개 결제, 판매자의 추가 제안 3개 수락을 같은 순간에 보낸다.
- 계획의 각 그룹은 요청이 실패하거나 수량·예약·금액이 기대와 달라도 다음 요청을 보낸다. 결과는 성공과 실패를 가리지 않고 모든 단계에서 확인한다. 시나리오 3번부터 7번까지는 시나리오 2번의 결과에 따라 고른 흐름의 요청이므로, 시나리오 2번의 결과가 두 흐름 어느 쪽에도 해당하지 않으면 보내지 않는다.
- 실행마다 새 회원 네 명과 새 상품을 쓰고, 같은 조건으로 실행을 반복해 두 정상 흐름과 위반이 어떻게 나뉘는지 본다.
- 결과는 응답 파일, JMeter 실행 결과 파일, DB 조회 결과로 확인한다. 입력 파일은 테스트데이터의 실행별 폴더에, 결과 파일은 실행결과_원본의 실행별 폴더에 둔다.
- 테스트결과서는 실행마다 쓰지 않고, 여러 실행의 결과를 모은 뒤 한 번 쓴다.

모니터 상품의 최초 수량은 7이므로, 남은 수량 8은 명세의 관찰 항목인 「남은 수량은 0~7개」를 벗어난다. 남은 수량과 취소되지 않은 주문 수량(정가 구매자의 주문 2개)을 더하면 10으로, 최초 수량 7보다 3 많다.

**구매 목록 조회는 주문을 목록으로 돌려주지만, 판매자의 발송 등록은 주문 하나만 받는다.**

- 「ID 얻기: 정가 구매자의 구매 목록에서 진행 중 주문 ID」 요청은 정가 구매자의 주문 두 건을 목록으로 받았다.
- 로컬 소스에서 구매 목록은 결제할 때 기록한 시각이 늦은 주문부터, 그 시각이 같으면 주문 ID가 큰 주문부터 정렬한다. 처리 기준 시각을 고정했으므로 두 주문에 기록된 결제 시각이 모두 03:31:44였고, 나중에 생긴 정가 구매자의 두 번째 주문이 목록의 앞에 왔다.
- 계획은 목록에서 처음 나오는 진행 중 주문의 ID 하나만 얻도록 구성되어 있다. 그래서 정가 구매자의 두 번째 주문만 발송 등록 요청과 구매 확정 요청의 대상이 되었다.
- 판매자의 발송 등록 요청은 주문 ID 하나를 받아 그 주문만 배송 중으로 바꾼다. 주문이 두 건이면 주문마다 발송 등록 요청을 따로 보내야 한다.
- 계획은 정가 구매자의 주문이 한 건인 시나리오 명세대로 구성되어 있다. 명세에는 정가 구매자의 주문이 두 건일 때 보낼 요청이 없다.

**저장된 남은 수량은 추가 제안 수락 성공 흐름이 끝날 때까지 실제보다 3 많았다.** 시점마다 저장된 남은 수량과 취소되지 않은 주문 수량, 유효 예약 합계는 다음과 같다.

## 6. 시스템 명세

**JMeter 계획**

- 통합 계획: [실행01_계획_회원가입과_시나리오1번부터7번.jmx](테스트데이터/실행01_시나리오1번부터7번_20261102/실행01_계획_회원가입과_시나리오1번부터7번.jmx). 스레드 그룹은 다음 순서로 놓여 있다.
  1. 회원 가입 준비: 가입 결과 CSV 새로 만들기
  2. 회원 가입: 이 실행의 회원 네 명
  3. 시나리오 1번: 준비(처리 기준 시각 고정, 로그인, 충전, 상품 등록, 대화, 제안과 수락)
  4. 시나리오 2번: 결제와 수락 경합(세 요청을 같은 순간에 보냄)
  5. 시나리오 2번 실행 후 단계 : 사용자 입장에서 수량 등 조회
  6. 정가 결제 성공 흐름: 시나리오 3번부터 7번까지 차례로
  7. 추가 제안 수락 성공 흐름: 시나리오 3번부터 5번(주문 취소, 재조회, 새 예약 해제, 재조회)
  8. 추가 제안 수락 성공 흐름: 시나리오 6번 조회·결제 경합(두 스레드가 같은 순간에 출발)
  9. 추가 제안 수락 성공 흐름: 시나리오 6번 뒤 확인과 7번(발송, 모의 배송 완료, 구매 확정, 종료 조회)
  10. 종료 정리: 처리 기준 시각 고정 해제
- 로그인 토큰 갱신 계획: [실행01_계획_로그인토큰갱신.jmx](테스트데이터/실행01_시나리오1번부터7번_20261102/실행01_계획_로그인토큰갱신.jmx). 스레드 그룹은 「로그인 토큰 갱신: 네 회원 다시 로그인」 하나다.
- 회원 CSV: `테스트데이터/실행01_시나리오1번부터7번_20261102/실행01_회원.csv`(저장소에 올리지 않음)
- 「시나리오 2번: 결제와 수락 경합(세 요청을 같은 순간에 보냄)」 그룹의 동시 전송: 스레드 3개와 동기화 타이머. 세 스레드가 모두 준비되면 함께 보내며, 최대 10초 기다린다.
- 이어갈 흐름 결정: 「시나리오 2번: 결제와 수락 경합(세 요청을 같은 순간에 보냄)」 그룹의 응답 코드로 다음과 같이 정한다.
  - 정가 구매자의 결제가 201이고 추가 제안 수락이 200이 아니면: 정가 결제 성공 흐름
  - 추가 제안 수락이 200이고 정가 구매자의 결제가 201이 아니면: 추가 제안 수락 성공 흐름
  - 그 밖의 경우: 「해당없음」

  결정한 흐름은 JMeter 속성 `flow`에 넣고, 흐름 그룹은 이 값이 자기 흐름과 같을 때만 요청을 보낸다. 이 속성은 JMeter를 다시 시작하면 사라진다.
- 응답 본문은 요청마다 실행 폴더에 `{단계}_{역할}_{응답 종류}.json`으로 저장한다. 같은 그룹을 다시 실행하면 같은 이름의 파일을 덮어쓴다. 로그인, 충전, 대화 시작 요청의 응답 본문은 저장하지 않는다.

**요청**

경로는 모두 `/ChatService`로 시작한다.

- 처리 기준 시각 고정: `PUT /test-support/clock`, 본문 `{"instant":"2026-11-02T12:12:00Z"}`. 고정 해제: `DELETE /test-support/clock`
- 로그인: `POST /login`(폼 `userid`, `password`). 302 응답의 `Authorization` 쿠키를 로그인 토큰으로 쓴다
- 충전 `POST /api/wallet/charges`, 상품 등록 `POST /api/products`, 대화 시작 `POST /api/products/{상품 ID}/conversations`
- 가격 제안 `POST /api/conversations/{대화 ID}/offers`, 수락 `POST /api/offers/{제안 ID}/accept`
- 결제 `POST /api/orders`. 합의 가격 결제는 본문에 `offerId`를 넣는다
- 상품 상세 `GET /api/products/{상품 ID}`, 판매 목록 `GET /api/orders/sales`, 대화 상세 `GET /api/conversations/{대화 ID}`

**로그인 토큰의 유효 시간**

- 서버는 로그인할 때 토큰을 확인하는 정보를 Redis에 30분 동안 저장한다(`LoginFilter`). 토큰 자체의 만료 시간은 1시간이다(`JWTUtil`).

**DB 조회**

- SQL Developer에서 테이블마다 `SELECT * FROM {테이블}`로 조회했다.
- 「시나리오 1번: 준비(처리 기준 시각 고정, 로그인, 충전, 상품 등록, 대화, 제안과 수락)」 그룹을 실행한 뒤: `PRODUCT`, `CONVERSATION`, `PRICE_OFFER`, `RESERVATION`, `WALLET`, `BALANCE_TRANSACTION`, `PURCHASE_ORDER`, `SHIPMENT`
- 「시나리오 2번: 결제와 수락 경합(세 요청을 같은 순간에 보냄)」 그룹을 실행한 뒤: `PRODUCT`, `RESERVATION`, `PRICE_OFFER`, `PURCHASE_ORDER`와 `SELECT * FROM WALLET, BALANCE_TRANSACTION`. 마지막 문장은 두 테이블의 행이 모든 조합으로 짝지어진 15행을 보여 준다
