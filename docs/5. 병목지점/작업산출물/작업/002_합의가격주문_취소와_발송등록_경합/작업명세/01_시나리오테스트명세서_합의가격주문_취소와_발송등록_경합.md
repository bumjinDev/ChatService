## 1. 명세 내용

### 1.1 목적과 범위

같은 상품을 거래하는 여러 회원의 결제와 제안 수락이 겹칠 때 주문·예약이 판매할 수량을 초과하지 않는지 확인한다. 이어서 주문 취소와 다른 구매자의 결제를 겹쳐 수량 복구·차감·예약·반환이 서로 맞는지 확인한다. 예약 해제 후 남은 구매를 진행하고 판매대금 지급까지 마친다.

| 구분 | 내용 |
|---|---|
| 포함 | 등록 가격·합의 가격 결제, 제안 수락과 예약 생성, 취소와 다른 회원의 결제, 취소 후 새 예약, 직접 예약 해제와 추가 구매 |
| 정상 마무리 | 취소되지 않은 주문의 발송 등록·모의 배송 완료·구매 확정·판매대금 지급. 이 과정은 순차 처리 |
| 제외 | 동일 주문의 중복 취소, 취소와 발송 등록 경합, 미발송 자동 취소 경합, 환불 분쟁, 동일 지갑 동시 변경 |
| 제외 | 자동 대기열·자동 재시도·화면 자동 갱신의 검증, 취소 후 예약 정책 변경 |
| 기술 관찰 | 요청별 읽기·변경·커밋과 Oracle 잠금·격리 동작. 4.4의 비교는 후속 실험 조건이며 구현·실행 결과가 아님 |

### 1.2 테스트 배경

판매자가 모니터 7개를 판매하고, 흥정 구매자는 3개를 합의 가격으로 예약한다. 등록 가격 구매자는 2개를 바로 구매하려 하며, 대기 구매자는 3개를 제안한다. 이들의 거래를 예약·결제·취소·예약 해제·추가 구매·판매대금 지급까지 하나의 흐름으로 확인한다.

같은 이전 수량이나 서로 다른 시점의 상품·예약 정보로 요청을 처리하면 수량이 부족한 결제와 예약이 함께 성립하거나 취소·결제 중 한쪽의 수량 변경이 사라질 수 있다. 판매자는 공급할 수 없는 주문을 떠안고, 구매자는 승인받은 구매 기회를 보장받지 못할 수 있다.

1. 판매자가 상품을 등록하고 구매자들이 대화를 시작한다. 흥정 구매자의 3개 제안을 수락하여 예약하고 대기 구매자의 3개 제안은 응답 대기로 둔다.
2. 흥정 구매자 3개 결제, 등록 가격 구매자 2개 결제, 판매자의 대기 구매자 3개 제안 수락을 겹친다.
3. 흥정 구매자가 발송 전에 구매를 철회한다. 이 취소와 대기 구매자의 결제를 겹친다.
4. 아직 구매하지 못한 회원은 취소 후 새 예약 때문에 원하는 수량을 살 수 없음을 조회로 확인한다.
5. 흥정 구매자가 새 예약을 직접 해제한다. 판매자의 안내 후 남은 구매자가 최신 수량을 확인하고 구매한다.
6. 취소되지 않은 주문을 발송·배송 완료·구매 확정하여 거래를 마친다.

| 참여자 | 목적과 행동 | 테스트에서 보내는 요청 |
|---|---|---|
| 판매자 | 상품을 판매하고 가격을 협의한다. 구매 철회와 예약 해제 후 남은 구매자에게 수량을 확인하도록 안내하고 발송한다. | 상품 등록, 제안 수락, 상품·대화 조회, 발송 등록 |
| 흥정 구매자 | 3개를 합의 가격으로 구매하지만 사용 계획이 바뀌어 철회한다. 다시 구매하지 않으므로 남은 예약도 해제한다. | 제안, 합의 가격 결제, 주문 취소, 예약 조회·해제 |
| 등록 가격 구매자 | 2개를 등록 가격으로 확보한다. 구매하지 못하면 판매자의 안내 후 다시 확인한다. | 상품·대화 조회, 등록 가격 결제, 필요한 경우 결제 재시도, 구매 확정 |
| 대기 구매자 | 3개를 합의 가격으로 구매하려 한다. 수락되지 않으면 등록 가격으로 2개를 먼저 사고 1개를 추가 구매한다. | 제안, 상품·대화 조회, 합의 가격 또는 등록 가격 결제, 구매 확정 |

회원의 행동은 시나리오 가정이다. 대기 구매자는 시스템 대기열의 회원이 아니다. 판매자의 안내는 다시 조회하는 계기이며, 안내 전달과 UI 자동 갱신 자체는 검증하지 않는다. 부족한 수량을 확인하고도 이유 없이 결제·수락을 반복하는 요청은 넣지 않는다.

### 1.3 업무 규칙과 입력값

| 항목 | 적용 내용 |
|---|---|
| 상품 | 7개, 등록 가격 개당 120,000원. 상품명은 실행별 식별값을 붙인 「시나리오 모니터」, 설명은 「거래 시나리오용 모니터」, 분류는 ELECTRONICS |
| 흥정 구매자 | 3개를 개당 100,000원에 합의, 결제 300,000원 |
| 등록 가격 구매자 | 2개 결제, 240,000원 |
| 대기 구매자 | 제안은 3개·개당 110,000원. 수락되면 330,000원 결제. 수락되지 않으면 등록 가격 2개 240,000원과 1개 120,000원을 별도 주문으로 결제 |
| 시작 잔액 | 구매자마다 600,000원, 판매자 0원. 이후 충전·다른 거래 없음 |
| 수량의 의미 | 남은 수량에는 예약분이 포함된다. 회원별 구매 가능 수량은 남은 수량에서 다른 회원의 유효한 예약 수량을 뺀 값 |
| 예약 | 20분. 유효한 예약은 상태가 ACTIVE이고 관찰 시각이 만료 시각보다 이른 예약. 같은 상품·구매자에 유효한 예약은 하나 |
| 합의 가격 결제 | 본인의 수락된 제안과 유효한 예약이 필요하며, 제안한 3개 전체를 결제. 예약은 결제 종료 상태로 변경 |
| 수락 실패 | 예약할 수량이 부족하면 수락도 롤백. 제안은 응답 대기 유지, 자동 재시도 없음 |
| 취소·예약 해제 | 취소는 수량 복구·전액 반환·같은 수량의 새 예약 생성을 함께 처리. 기존 결제 종료 예약은 보존. 새 예약은 취소 시각부터 20분. 직접 예약 해제는 별도 요청 |
| 거래 종료 | 발송은 각 주문의 발송 기한 전. 모의 배송 완료는 배송 예정 시각 이상. 구매 확정은 배송 완료 후 상품 확인 기한 미만. 정상 완료 시 주문 금액 전액을 한 번 지급 |
| 기타 입력 | 수령인은 해당 구매자의 역할명, 주소는 「시나리오 테스트 주소」, 취소 사유는 「구매 철회」. 택배사는 「테스트택배」, 운송장 번호는 실행·주문별 고유값 |

7개를 사용하면 기존 예약 3개를 제외한 4개를 두고 2개 결제와 3개 예약이 경쟁한다. 첫 요청 묶음 이후에도 수량이 남아 취소와 다른 구매자의 결제를 겹칠 수 있다. 수량·금액은 계산을 위한 가정이며 측정 결과가 아니다.

원화 금액은 정수다. 주문 생성 시 단가와 결제 금액은 서버가 계산한다. 실패한 업무 요청에 주문·예약·금전 변경이 부분 반영되어서는 안 된다. 기술적 예외나 응답 유실은 정상적인 수량 부족 거절과 구분하여 실제 커밋·롤백을 확인한다.

### 1.4 테스트 시작 전 준비

각 실행은 아래 상태에서 시작하여 1.5의 전체 절차를 진행한다. 이전 실행에서 만든 주문·예약을 고쳐 다음 실행의 정상 상태로 사용하지 않는다.

| 대상 | 시작 상태·준비 | 확인 방법 |
|---|---|---|
| 회원 | 서로 다른 판매자·구매자 세 명. 유효한 인증 정보 확보 | 회원별 권한과 본인 조회 |
| 지갑 | 네 회원의 지갑을 미리 만들고 1.3의 잔액을 준비. 이 준비의 충전 내역은 거래 구간의 구매·반환·지급 합계에서 제외 | 시작 잔액과 관찰을 시작할 내역 위치 기록 |
| 상품·주문 | 새 실행에 사용할 상품은 단계 1에서 생성. 같은 회원에게 결과를 섞을 다른 거래나 자동 처리 대상이 없음 | 대상 데이터와 실행 식별값 확인 |
| 식별값 | 상품·대화·제안·예약·주문 ID는 응답과 조회에서 받아 연결. 이전 실행 ID를 재사용하지 않음 | 입력·응답 기록의 연결 관계 |
| 업무 시각 | 시작 시각을 기록하고 고정. 단계 7까지 예약 만료 전을 유지. 발송도 기한 전이며 단계 9에서만 배송 완료에 필요한 시각으로 이동 | 서버 시계 조회, 저장된 만료·기한 값 |
| 자동 처리·중지 | 스케줄러를 끄고 멈춘 요청이 없는 상태. 필요한 지원과 설정은 4장 기준 | 적용 설정, 중지 목록 |
| 재현 준비 | 중지 제어는 4.2의 새 중지 지점과 요청 제어가 구현된 뒤 적용 | 구현 버전과 중지 도달·재개 동작 확인 |

시계 고정은 서버의 모든 요청에 영향을 준다. 실제 로그 시각과 업무 시각을 구분하고 실행 종료 후 고정을 해제한다. 시간 조건을 유지하지 못한 실행은 수량 경합의 결과로 해석하지 않는다.

### 1.5 테스트 절차와 단계별 기대 결과

#### 1.5.1 테스트 전체 흐름

각 행의 요청과 후속 조회가 끝난 뒤 데이터를 확인하고 다음 단계로 간다. HTTP 경로와 응답 코드는 4.2를 따른다.

| 단계 | 수행 주체·요청·입력 | 정상 응답과 동작 | 단계 종료 후 데이터 |
|---|---|---|---|
| 1. 상품·대화 | 판매자가 1.3의 상품 등록. 세 구매자가 그 상품의 대화 시작 | 상품·대화 생성 성공 | 상품 7개·판매 중. 주문·제안·예약 없음 |
| 2. 제안·예약 | 흥정 구매자가 3개·100,000원 제안, 판매자가 수락. 대기 구매자가 3개·110,000원 제안 | 두 제안 등록, 흥정 구매자 제안 수락 성공 | 흥정 구매자 예약 3개. 대기 구매자 제안은 응답 대기. 상품 7개, 다른 구매자의 구매 가능 수량 4개 |
| 3. 결제·수락 | 흥정 구매자 합의 가격 3개 결제, 등록 가격 구매자 2개 결제, 판매자의 대기 구매자 3개 제안 수락 | 흥정 구매자 결제 성공. 등록 가격 결제와 대기 구매자 제안 수락 중 하나만 성공 | 등록 가격 결제 성공 흐름: 상품 2개·진행 주문 2건·유효 예약 없음. 제안 수락 성공 흐름: 상품 4개·진행 주문 1건·대기 구매자 예약 3개 |
| 4. 취소·결제 | 흥정 구매자 주문 취소와 대기 구매자 결제. 대기 구매자의 제안이 수락되지 않았으면 등록 가격 2개, 수락되었으면 합의 가격 3개 | 취소와 결제 모두 성공 | 흥정 구매자 주문 취소·300,000원 반환·새 예약 3개. 남은 상품은 등록 가격 결제 성공 흐름 3개, 제안 수락 성공 흐름 4개 |
| 5. 구매 가능 수량 | 아직 필요한 수량을 사지 못한 회원이 상품·대화 조회. 부족하면 결제를 보내지 않음 | 첫 흐름의 대기 구매자는 0개, 둘째 흐름의 등록 가격 구매자는 1개 확인 | 상품·예약·지갑 변경 없음 |
| 6. 예약 해제 | 흥정 구매자가 취소 뒤 생성된 새 예약 ID를 조회하여 직접 해제 | 해제 성공. 과거 결제 종료 예약에 해제 요청을 보내지 않음 | 유효 예약 없음. 남은 수량은 첫 흐름 3개, 둘째 흐름 4개. 잔액 변경 없음 |
| 7. 추가 구매 | 판매자의 안내 후 남은 구매자가 다시 조회. 첫 흐름에서는 대기 구매자 등록 가격 1개, 둘째 흐름에서는 등록 가격 구매자 2개 결제 | 필요한 수량을 확인한 뒤 결제 성공 | 상품 2개·판매 중. 유효 예약 없음. 흥정 구매자 취소 1건, 나머지 진행 중 주문 3건 또는 2건 |
| 8. 발송 | 판매자가 취소되지 않은 주문을 주문 ID 순서대로 발송 등록 | 주문별 발송 성공 | 각 주문은 IN_PROGRESS·SHIPPING, 발송 정보 각 1건. 취소 주문의 발송 정보 없음. 상품·잔액 변경 없음 |
| 9. 배송 완료 | 모든 발송 정보의 배송 완료 예정 시각 중 가장 늦은 값으로 업무 시계를 이동. 모의 배송 완료를 한 번 요청 | 처리 건수 첫 흐름 3건, 둘째 흐름 2건 | 대상 주문은 IN_PROGRESS·DELIVERED. 배송 완료 시각과 상품 확인 기한 생성. 지급 내역 없음 |
| 10. 구매 확정 | 구매자가 상품 확인 기한 전에 자기 주문을 주문 ID 순서대로 하나씩 확정 | 주문별 정상 완료와 판매대금 지급 | 모든 요청 종료 뒤 1.6과 대조 |

단계 4의 대기 구매자는 앞서 받은 제안 처리 결과와 구매 가능 수량을 보고 자신의 결제를 시작한다. 다른 회원의 취소를 감지하여 자동 재시도하는 행동이 아니다. 단계 7의 안내는 재조회 계기를 나타내며, JMeter에서는 안내가 전달되었다는 조건 뒤에 조회·조건부 결제를 둔다.

#### 1.5.2 관찰과 중단

각 단계의 요청이 모두 끝난 뒤 다음 업무 요청을 보내기 전에 데이터를 조회한다. 자동 작업과 다른 회원 거래가 없는 상태에서 같은 상품·주문·회원 범위로 비교한다. 다음 조건을 단계별로 함께 확인한다.

- 남은 수량과 취소되지 않은 주문 수량의 합은 최초 7개다. 남은 수량은 0~7개다.
- 유효한 예약 수량은 남은 수량 이하다. 같은 상품·구매자에게 유효한 예약은 하나를 넘지 않는다.
- 업무 거절된 요청의 주문·예약·차감 내역은 없다. 정상 결제·취소·구매 확정은 각 주문의 수량과 금액을 한 번만 반영한다.
- 회원 잔액은 시작 잔액과 해당 실행의 금전 내역에 맞는다. 누적 구매 차감은 보관 금액·누적 반환·누적 지급의 합과 같다.

수량·예약·금전 또는 응답과 기록에 위반이 있으면 실패를 기록하고 다음 업무 단계로 진행하지 않는다. 도달 실패·시간 초과·인증 만료 등으로 정한 순서를 만들지 못하면 경합 재현 여부는 판정 불가로 남긴다. 둘이 함께 발생하면 업무 위반과 제어 실패를 각각 기록한다.

중단 시 남아 있는 제어 대기를 해제하고, 이미 실행 중인 모든 요청의 실제 종료를 확인한다. 클라이언트 대기 종료를 서버 롤백으로 간주하지 않는다. 종료되지 않은 요청이 있으면 새 실행을 시작하지 않는다. 실패 상태와 로그를 보존한 뒤 다음 실행을 새로 준비한다.

### 1.6 테스트 종료 후 기대 결과

단계 10까지 마친 실행의 결과다. 아래 값은 계산한 정상 기대값이며 실행 결과가 아니다. 단계별 위반이 없고 다음 종료 결과도 모두 맞아야 통과한다.

| 최종 확인 대상 | 등록 가격 결제 성공 흐름 | 제안 수락 성공 흐름 |
|---|---|---|
| 상품 | 최초 7개, 남은 2개, ON_SALE | 동일 |
| 취소 주문 | 흥정 구매자 3개·300,000원 주문 1건. CANCELLED·WAITING_SHIPMENT, 발송 정보 없음 | 동일 |
| 정상 완료 주문 | 등록 가격 구매자 2개 주문 1건, 대기 구매자 2개·1개 주문 각 1건. 총 3건·5개 | 등록 가격 구매자 2개 주문 1건, 대기 구매자 3개 주문 1건. 총 2건·5개 |
| 배송·완료 | 정상 완료 주문마다 COMPLETED·DELIVERED, BUYER_CONFIRMED. 발송 정보 총 3건 | 같은 상태, 발송 정보 총 2건 |
| 예약 | 총 2행. 흥정 구매자의 최초 예약 FULFILLED, 취소 후 예약 RELEASED·해제 주체 BUYER. 유효 예약 없음 | 총 3행. 왼쪽의 2행과 대기 구매자의 FULFILLED 1행. 유효 예약 없음 |
| 제안 | 흥정 구매자 ACCEPTED, 대기 구매자 PENDING | 두 제안 모두 ACCEPTED |
| 흥정 구매자 잔액 | 600,000 − 300,000 + 300,000 = 600,000원 | 동일 |
| 등록 가격 구매자 잔액 | 600,000 − 240,000 = 360,000원 | 동일 |
| 대기 구매자 잔액 | 600,000 − 240,000 − 120,000 = 240,000원 | 600,000 − 330,000 = 270,000원 |
| 판매자 잔액 | 600,000원 | 570,000원 |
| PURCHASE | 4건, 출금 합계 900,000원 | 3건, 출금 합계 870,000원 |
| CANCEL_REFUND | 흥정 구매자 취소 주문에 1건, 300,000원 | 동일 |
| SALE_PAYOUT | 정상 완료 주문마다 1건, 총 3건·600,000원 | 총 2건·570,000원 |
| 진행 중·보류 주문과 보관 금액 | 없음, 0원 | 동일 |

누적 구매 차감은 첫 흐름에서 900,000 = 반환 300,000 + 지급 600,000원, 둘째 흐름에서 870,000 = 반환 300,000 + 지급 570,000원이다. 네 회원의 잔액 합은 시작과 끝 모두 1,800,000원이다. 내역의 주문 연결, 금액, 변동 후 잔액도 실제 회원 잔액과 대조한다.

최초 예약은 취소 주문에 연결된 결제 이력으로 남는다. 유효 예약이 없다는 것은 모든 예약 행을 삭제한다는 뜻이 아니다. 제안의 상태와 예약·합의 상태도 구분한다.

### 1.7 테스트 실행 결과

미실행. 재현, 잠금 대기, SQL 순서 또는 개선 효과를 확인한 결과는 없다. 실행 시 적용한 중지 지점·소스와 설정 버전·실제 순서·단계별 기대값과 실제값·판정·증거 위치를 실행별로 기록한다.

### 1.8 테스트에 사용한 파일

실행에 사용한 파일은 없다. 이 시나리오용 JMeter 계획과 단계별 결과 조회 쿼리는 준비 전이다. 작성·사용한 뒤 파일 위치와 버전, 사용한 실행을 기록한다.

### 1.9 테스트 결과 파일

미실행이므로 결과 파일은 없다. 실행 후 요청·응답, 서버·SQL·제어 로그, 데이터 조회 결과를 원본과 가공 자료로 구분하여 1.7의 해당 실행과 연결한다.

### 4.2 요청과 재현 제어

아래 경로는 애플리케이션의 context-path 뒤에 붙인다. 실제 배포의 기본 주소는 실행 설정으로 둔다. 회원 요청은 해당 회원으로 인증한다.

| 동작 | 요청 | 정상 응답 |
|---|---|---|
| 상품 등록·조회 | POST /api/products, GET /api/products/{productId} | 등록 201, 조회 200 |
| 대화 시작·조회 | POST /api/products/{productId}/conversations, GET /api/conversations/{conversationId} | 새 대화 201, 기존 대화·조회 200 |
| 제안·수락 | POST /api/conversations/{conversationId}/offers, POST /api/offers/{offerId}/accept | 제안 201, 수락 200 |
| 결제 | POST /api/orders | 201. productId·quantity·recipientName·shippingAddress 지정. 합의 가격은 해당 offerId, 등록 가격은 offerId 생략 |
| 취소·예약 해제 | POST /api/orders/{orderId}/cancel, DELETE /api/reservations/{reservationId} | 각각 200. 취소 본문 reason 지정 |
| 발송·확정 | POST /api/orders/{orderId}/shipment, POST /api/orders/{orderId}/confirm-receipt | 발송 201, 확정 200 |
| 상세·잔액·내역 | GET /api/orders/{orderId}, GET /api/wallet, GET /api/wallet/transactions | 200. 본인 권한으로 조회 |
| 시계 고정·조회·해제 | PUT·GET·DELETE /test-support/clock | 각각 200. 고정할 때 본문 instant 지정, 조회에서 fixed와 시각 확인 |
| 배송 완료 | POST /test-support/jobs/delivery-complete | 200. now 매개변수를 생략하여 고정한 업무 시각 사용. processed와 실제 주문 상태 확인 |
| 중지 조회·재개 | GET /test-support/pauses, POST /test-support/pauses/{name}/resume | 목록 200, 실제 재개 200. 재개할 이름이 없으면 409 |

상품·제안 입력은 1.3을 따르고 ID는 이전 응답에서 취득한다. 발송 본문은 carrierName·trackingNumber를 사용한다. requestId를 지원하는 요청에는 실행별 고유값을 넣되 중복 요청 방지 기능으로 간주하지 않는다.

중지 요청에는 X-Test-Request-Name과 X-Test-Pause-At을 사용한다. 요청 이름은 실행·회원·단계를 식별할 수 있는 고유값으로 둔다. 첫 요청 묶음은 업무 요청 스레드 3개와 제어 스레드 1개, 취소 구간은 업무 요청 2개와 제어 1개가 필요하다. 제어 스레드는 고정 시간 잠들기 대신 중지 목록에서 대상 이름의 도달을 확인한다.

| 제안하는 중지 지점 | 정확한 위치와 읽은 값 | 상태 |
|---|---|---|
| PAYMENT_CHECKED | OrderService 174행 잔액 검사 통과 후, 181행 주문 저장 전. 상품·예약 조건과 지갑을 읽은 상태 | 신설 필요 |
| RESERVATION_CHECKED | ReservationService 92행 수량 검사 통과 후, 96행 예약 저장 전. 수락의 기존 예약·구매 가능 수량 판단이 끝난 상태 | 신설 필요 |
| CANCEL_PRODUCT_READ | OrderCancellationService 237행 상품 조회 직후, 238행 수량 복구 전. 주문·지갑·상품을 읽은 상태 | 신설 필요 |

현재 [PausePoint](../../../../../../src/main/java/com/chatservice/marketplace/testsupport/PausePoint.java#L8)에는 ORDER_READ와 WALLET_READ만 있다. 기존 WALLET_READ는 취소의 상품 조회보다 앞이므로 취소와 결제가 같은 상품 수량을 읽었다고 보장할 수 없다. 새 이름을 헤더에 넣는 것만으로 중지되지 않는다. 이 문서는 구현 요구만 정하며 코드를 추가하지 않았다.

일반 서비스의 @Transactional은 기본 전파 설정을 사용하며 보조 서비스도 참여한다. readOnly 조회를 호출한다고 별도 트랜잭션이 생기는 것은 아니다. 객체 변경, SQL 발행, flush, commit은 구분한다. IDENTITY 행의 INSERT와 기존 객체의 변경 감지 UPDATE 시점도 같다고 가정하지 않는다. 이미 읽은 객체가 다른 요청의 커밋만으로 자동 갱신되는 것도 아니다. 실제 SQL 순서는 아직 관찰하지 않았다.

주문 변경 후 응답용 조회가 실패해도 앞선 커밋이 남을 수 있다. 반대로 서비스 안의 “성공” 로그만으로 커밋됐다고 판단할 수 없다. 모의 배송 완료는 응답 상태 외에 processed와 주문별 실패 로그·실제 상태를 확인한다.

단계 종료 시 PRODUCT, PRICE_OFFER, RESERVATION, PURCHASE_ORDER, SHIPMENT, WALLET, BALANCE_TRANSACTION을 실행의 상품·주문·회원 ID로 한정하여 조회한다. 관찰 도중 다른 변경이 없도록 하고, 여러 시점의 조회값을 합쳐 위반으로 판정하지 않는다. 거래 중인 구간을 조회한다면 일관된 관찰 기준과 각 조회 시점을 별도로 기록한다.

| 보존할 증거 | 확인 목적 |
|---|---|
| 요청·응답과 역할·요청 이름·생성 ID | 어느 회원의 어떤 행동인지 연결 |
| 중지 도달·재개·시간 초과 기록 | 지정한 겹침과 재개 순서를 실제로 만들었는지 확인 |
| SQL·바인드 값·커밋·롤백 및 오류 | 읽은 값과 반영한 값, 실제 트랜잭션 종료를 대조 |
| 단계별 데이터 조회 | 1.5와 1.6의 수량·상태·금전 결과 확인 |
| Oracle 세션·대기·차단 관계 | 잠금 대기를 관찰하는 후속 실험. 조회 권한과 수집 방법은 실행 전 확인 |

지갑을 조회할 때 없던 지갑이 생성될 수 있으므로 네 지갑을 준비 단계에서 만든다. 기술 로그와 업무 결과, 단일 요청의 응답과 전체 단계 종료 상태를 구분한다.

### 4.4 재현 가설과 Oracle 비교

다음은 코드 구조에 근거한 가설이며 정상 기대 결과가 아니다.

| 관찰 구간 | 재현할 가설 |
|---|---|
| 단계 3 | 두 결제가 모두 상품 7개를 읽고 각각 차감하면 한쪽 변경이 사라질 수 있다. 제안 수락까지 이전 구매 가능 수량으로 승인되면 총 8개의 주문·예약이 성립할 수 있다. |
| 단계 4의 등록 가격 결제 성공 흐름 | 취소와 결제가 모두 상품 2개를 읽으면 복구 결과 5개 또는 차감 결과 0개가 남아 정상 수량 3개와 달라질 수 있다. |
| 단계 4의 제안 수락 성공 흐름 | 두 요청이 상품 4개를 읽으면 복구 결과 7개 또는 차감 결과 1개가 남아 정상 수량 4개와 달라질 수 있다. |

실제 결과는 UPDATE 조건·갱신 열·flush 순서·제약조건·격리 수준으로 확인한다. 예약 합계가 저장된 남은 수량 이하인지뿐 아니라 최초 수량과 주문 수량의 관계도 봐야 변경 누락을 발견할 수 있다.

Oracle의 READ COMMITTED는 문장 단위 읽기 일관성을 제공하며, 변경 SQL은 행 잠금을 취득한다. 일반 조회와 같은 행의 변경 대기는 구분한다. SERIALIZABLE에서는 다른 트랜잭션이 변경한 행을 수정할 때 ORA-08177이 발생할 수 있다. 프로젝트의 실제 연결 설정은 확인하지 않았다.

| 후속 비교 | 같은 흐름에서 확인할 내용 |
|---|---|
| 실제 적용 격리 수준에서 재현 | 상품·예약을 읽은 시점과 변경 값, 커밋 순서를 확인 |
| SQL 이후·커밋 전 대기 | 같은 행의 변경이 실제로 대기하는지, 보유 요청의 커밋·롤백 후 어떻게 재개되는지 확인 |
| SERIALIZABLE | 충돌 오류·전체 롤백을 기록. 재시도는 자동으로 가정하지 않고 별도 실행 조건으로 결정 |
| 공통 상품 잠금·버전 검사 등 | 수량을 변경하는 결제·취소뿐 아니라 상품을 읽고 예약을 생성하는 수락까지 보호되는지 비교 |

수락은 상품 행을 변경하지 않으므로 상품의 변경 충돌 검사만으로 예약 합계가 보호된다고 미리 결론 내리지 않는다. 잠금을 추가한다면 참여 경로의 최초 읽기·재검사·잠금 순서를 함께 검토한다. 강제 flush 등 실행 순서를 바꾸는 계측은 원래 동작의 관찰과 구분하여 기록한다.
