## 1. 명세 내용

### 1.1 목적과 범위

이 테스트는 같은 상품에 여러 구매자의 거래가 이어질 때, 상품 수량의 배정과 구매 가능 수량의 안내가 업무 규칙에 맞는지 확인한다. 결제·예약이 끝난 뒤 저장된 결과와, 처리가 진행되는 동안 구매자가 받은 조회 응답을 각각 검증한다.

시나리오 2에서는 두 구매자의 결제와 판매자의 제안 수락을 겹친다. 기존 예약을 제외한 4개에 정가 구매자의 2개 결제와 추가 제안 구매자의 3개 예약을 모두 허용하는지 확인한다. 두 요청 중 하나만 성공하고 실패한 요청의 주문·예약·금액 차감이 남지 않아야 한다. 이 결과로 한정된 상품 수량을 중복 배정하지 않는지 판단한다.

시나리오 3–5에서는 합의 주문 취소, 수량 재조회, 새 예약 해제를 순서대로 확인한다. 주문 취소로 상품 3개가 복구되어도 같은 수량이 주문 취소 구매자에게 다시 예약되므로, 다른 구매자가 살 수 있는 수량은 늘지 않아야 한다. 새 예약을 직접 해제한 뒤에는 다른 구매자의 구매 가능 수량이 3개 늘고, 상품 수량과 잔액은 다시 바뀌지 않아야 한다.

시나리오 6은 2번에서 성립한 거래에 따라 나누어 수행한다. 정가 결제가 성공한 흐름에서는 추가 제안 구매자가 예약 없이 등록 가격으로 3개를 구매하는 과정을 순차 확인한다. 추가 제안이 수락된 흐름에서는 **추가 제안 구매자의 3개 예약 결제와 정가 구매자의 조회·2개 구매 요청**을 관찰한다. 정가 구매자의 결제 전 조회는 구매 가능 수량 4개를 안내하는지 확인한다. 조회가 결제 전 상품 7개와 결제 후 유효 예약 없음을 섞어 7개로 안내할 가능성을 살펴보려는 것이다. 조회 뒤 두 결제가 겹친다면 두 주문 합계 5개와 남은 상품 2개가 일치하는지도 확인한다.

2번에서는 남은 수량이 부족하므로 정가 결제와 추가 예약 중 하나만 성공하는 결과를 기대한다. 6번에서는 기존 예약 3개와 정가 구매자의 2개를 모두 판매할 수 있으므로 두 결제의 성공과 정확한 차감을 기대한다. 상품을 동시에 변경할 때의 문제는 2번과 일부 겹칠 수 있지만, 거래 조건과 기대 결과가 다르다. 여기에 구매자가 받은 조회 응답의 정확성도 별도로 판단한다. 최종 수량이 맞더라도 잘못된 조회를 통과시킬 수 없으며, 정가 구매자가 요청할 수량은 계속 2개다.

| 구분 | 적용 범위 |
|---|---|
| 경합 검증 | 2번의 결제·제안 수락, 6번 중 추가 제안 수락 성공 흐름의 예약 결제·상품 조회 및 조회 뒤 두 구매자의 결제 |
| 순차 검증 | 2번의 순차 기준, 3–5번의 주문 취소·재조회·예약 해제, 6.1의 등록 가격 구매와 6.2의 순차 비교, 7번의 발송·모의 배송·구매 확정·판매대금 지급 |
| 이번 범위에서 제외 | 동일 주문 중복 취소, 취소·발송 등록 경합, 미발송 자동 취소 경합, 환불 분쟁, 동일 지갑 동시 변경 |
| 변경하지 않는 정책 | 주문 취소와 예약 해제의 분리. 실패자 전용 알림·대기열과 자동 결제·수락 재시도는 추가하지 않음 |
| 확인하지 않은 내용 | 배포 버전, 실행 중 DB 설정·SQL, 실제 화면 동작, 실시간 전달의 신뢰성 |

요구사항 명세서 1.4는 동시 요청에 대한 정합성 보장을 후속 검증 대상으로 구분한다. 이 문서의 정상 기대값도 검증 목표이며, 현재 구현에서 이미 보장하거나 실행으로 입증한 결과가 아니다. 특히 6번의 조회 순서를 고정할 제어 기능은 추가 제안이며 현재 코드에 없다.

### 1.2 테스트 배경과 참여자

판매자가 등록한 모니터 7개를 세 구매자가 각각 3개, 2개, 3개씩 구매하려는 상황이다. 주문 취소 구매자의 3개 합의는 먼저 성립했고, 정가 구매자의 2개 결제와 판매자의 추가 제안 3개 수락이 남은 수량을 두고 겹친다. 정가 결제가 성공했는지 추가 제안이 수락되었는지에 따라 이후 구매를 진행할 사람이 달라진다.

주문 취소 구매자는 결제 뒤 사용 계획이 바뀌어 발송 전에 주문을 취소한다. 현재 구현은 결제에 사용한 옛 예약을 보존하고 같은 합의의 새 예약을 만들므로, 다른 구매자는 주문 취소만으로 원하는 수량을 살 수 있게 되지 않는다. 주문 취소 구매자가 재구매하지 않기로 하고 새 예약까지 해제하면, 수량이 부족했던 구매자는 상품을 다시 확인하고 후속 구매를 진행한다.

추가 제안이 수락된 흐름에서는 그 구매자의 기존 예약이 계속 남아 있다. 추가 제안 구매자가 구매 준비를 마쳐 예약한 수량을 결제하는 동안, 정가 구매자는 앞서 사지 못한 수량을 지금 살 수 있는지 다시 조회한다. 정가 구매자는 조회 결과로 2개를 살 수 있다고 판단하면 구매를 요청한다. 조회와 뒤따르는 결제를 6번에서 함께 관찰하고, 조회·결제 결과가 모두 정상이면 두 주문의 발송·거래 종료를 진행한다.

구매자 이름은 전체 시나리오에서 같은 사람을 가리킨다. ‘정가’는 상품에 등록된 가격을 뜻한다. ‘추가 제안’은 주문 취소 구매자와 먼저 성립한 합의 외에 다른 구매자가 제시한 3개 구매 제안이다.

| 참여자 | 목적과 행동 가정 |
|---|---|
| 판매자 | 7개를 판매한다. 추가 제안의 수락이 실패하면 다시 수락하지 않는다. 취소되지 않은 주문을 발송한다. |
| 주문 취소 구매자 | 3개를 합의 가격으로 결제한 뒤 발송 전에 구매를 철회한다. 주문 취소 후 본인의 새 예약도 직접 해제한다. |
| 정가 구매자 | 2개를 등록 가격으로 구매한다. 첫 결제가 거절되면 나중에 수량을 다시 확인하고 충분할 때 새로 결제를 요청한다. |
| 추가 제안 구매자 | 3개를 제안한다. 수락되면 예약 기간 내에 합의 가격으로 결제한다. 수락되지 않으면 3개를 한 번에 살 수 있을 때 등록 가격으로 구매한다. |

추가 제안 구매자가 수락 실패 후 등록 가격으로 3개를 한 번에 구매하는 것은 이 시나리오의 행동 가정이다. 모든 구매자가 그렇게 행동해야 하는 업무 규칙이 아니다. 수락된 흐름에서 6번까지 결제를 보류하는 것도 본인의 구매 준비 때문이라고 가정한다. 그동안 예약은 만료되지 않으며, 다른 사람의 주문 취소나 예약 해제가 이 구매자의 결제 자격을 새로 만드는 것은 아니다.

재조회 계기는 구매자가 상품을 다시 열거나 수동으로 새로고침하는 행동으로 정한다. 다른 사람의 취소·예약 내역을 통보받았다고 가정하지 않는다. 판매자의 대화 안내나 접속 중 상태 이벤트도 재조회 계기가 될 수 있지만, 수신을 필수 조건으로 두지 않는다. 구매 실패자 전용 알림·대기열은 별첨의 미확정 제안이다.

현재 로컬 응답·화면 코드에는 남은 상품 수량과 구매 가능 수량이 모두 있다. 이 시나리오에서는 구매자가 자신의 구매 가능 수량을 기준으로 판단한다. 남은 수량이 증가했다는 사실만으로 결제를 다시 요청하지 않는다. 실제 배포 화면과 차이가 있다면 향후 실행 기록에 남긴다.

### 1.3 업무 규칙과 입력값

| 항목 | 적용 내용 |
|---|---|
| 상품 | 7개, 개당 120,000원, ELECTRONICS. 상품명은 실행별 식별값을 붙인 「시나리오 모니터」, 설명은 「거래 시나리오용 모니터」 |
| 주문 취소 구매자 | 3개·개당 100,000원 합의, 결제·취소 반환 각각 300,000원 |
| 정가 구매자 | 등록 가격 2개, 240,000원 |
| 추가 제안 구매자 | 제안 3개·개당 110,000원. 수락 분기에서는 330,000원, 수락 실패 분기에서는 등록 가격 3개를 한 주문으로 360,000원 결제 |
| 시작 잔액 | 구매자마다 600,000원, 판매자 0원. 다른 거래·추가 충전 없음 |
| 수량 | 남은 수량에는 예약분 포함. 해당 회원의 구매 가능 수량 = 남은 수량 − 다른 회원의 유효 예약 수량 합계 |
| 유효 예약 | ACTIVE이면서 관찰 시각이 expiresAt보다 이른 예약. 기간 PT20M. 만료 시각에 도달하면 자동 해제 작업 전이라도 구매 가능 수량을 막지 않음 |
| 합의 가격 결제 | 본인의 수락 제안과 유효 예약이 있어야 함. 제안 수량 3개 전체를 결제하고 예약은 FULFILLED. 예약 중에는 offerId 없는 등록 가격 결제를 거절 |
| 수락 실패 | 예약할 수량 부족 시 수락도 롤백, 제안 PENDING 유지. 자동 재시도 없음 |
| 취소 | 발송 전 취소. 상품 +3, 같은 제안·수량의 새 ACTIVE 예약 +3, 전액 반환. 기존 FULFILLED 예약 보존. 새 만료 시각은 취소 시각 +20분 |
| 직접 해제 | 새 예약 ID로 별도 요청. RELEASED·releasedBy=BUYER. 상품 수량·주문·잔액을 다시 변경하지 않음 |
| 거래 종료 | 발송 기한 전 발송, 예정 시각 이상에서 모의 배송 완료, 상품 확인 기한 전 구매 확정, 주문 금액 전액을 한 번 지급 |
| 기타 입력 | 수령인은 역할명, 주소 「시나리오 테스트 주소」, 취소 사유 「구매 철회」. 택배사 「테스트택배」, 운송장은 실행·주문별 고유값 |

동일 상품·구매자의 유효 예약 하나, 수량·금전의 정합성은 검증할 불변식이다. 경합에서도 이미 보장된다고 단정하지 않는다. 금액은 원 단위 정수이며 단가·총액은 서버 계산값으로 확인한다.

### 1.4 시작 전 준비

새 상품과 서로 다른 판매자·구매자 세 명을 사용한다. 지갑을 미리 생성하고 위 잔액을 준비한다. 준비 충전은 거래 구간의 구매·반환·지급 집계에서 제외한다. 상품·대화·제안·예약·주문 ID는 응답과 본인 조회에서 취득하고 이전 실행 ID를 재사용하지 않는다.

업무 시계를 고정하고 스케줄러를 끈다. 시나리오 6까지 모든 예약이 만료 전이며 취소·발송도 기한 전이어야 한다. 배송 완료 때만 모든 배송 예정 시각 이상으로 이동한다. 종료 시 시계를 해제한다. TestClock은 서버 전체에 적용되므로 다른 테스트나 사용자 거래가 없는 환경을 전제로 한다.

시나리오 2가 불변식 위반으로 끝났다면 그 데이터를 고쳐 3–6으로 이어 가지 않는다. 6번의 조회와 후속 결제만 독립 검증할 때는 새 실행에서 정상 API를 순차 호출해 추가 제안 수락 성공 흐름을 준비할 수 있다: 주문 취소 구매자의 제안 수락·3개 결제 → 추가 제안 구매자의 3개 제안 수락 → 정가 구매자의 2개 결제 거절 확인. 이때 상품 4개·추가 제안 구매자 예약 3개가 된다. 이후 3–5를 그대로 수행한다. 이 준비는 2번 경합을 통과했다는 증거가 아니다.

### 1.5 테스트 절차와 단계별 기대 결과

#### 1.5.1 시나리오 번호와 전체 흐름

번호는 연결된 구성안의 시나리오 1–7과 통일한다. 종전 0.3 문서의 절차 단계 3은 시나리오 2에 해당했다. 정가 구매자의 최초 결제가 성공하면 ‘정가 결제 성공 흐름’, 판매자가 추가 제안을 수락하면 ‘추가 제안 수락 성공 흐름’으로 이어진다. 표는 각 요청의 트랜잭션 종료 후 기대값이며 실제 실행 결과가 아니다.

| 시나리오 | 수행 주체·요청 | 기대 결과 |
|---|---|---|

시나리오 2의 부족 거절은 정가 결제 성공 흐름의 수락 요청에는 409 `RESERVATION_QUANTITY_EXCEEDED`, 추가 제안 수락 성공 흐름의 정가 구매자 결제에는 409 `PRODUCT_RESERVED`를 순차 기준으로 기대한다. 경합 중 기술적 예외·응답 유실은 업무 거절과 구분하고 실제 커밋·롤백을 확인한다.

#### 1.5.2 시나리오 3–5: 취소, 구매 판단, 예약 해제를 분리

3번의 취소가 끝나고 5번의 해제를 하기 전까지는 새 예약이 유효하다. 이 구간에서 확인하는 사람과 수량을 2번의 결과별로 나누면 다음과 같다. 각 표는 별도의 실행 흐름이며, 모든 수량은 해당 단계의 요청이 종료된 뒤 관찰한다.

**정가 구매자의 2개 결제가 성공한 흐름**

2번에서 주문 취소 구매자의 3개 결제와 정가 구매자의 2개 결제가 성공한다. 남은 수량은 2개이므로 판매자의 추가 제안 3개 수락은 실패한다. 아직 구매하지 못한 사람은 추가 제안 구매자다. 이 사람의 결제 실패와 판매자의 수락 실패를 혼동하지 않는다.

| 관찰 시점 | 남은 상품 수량 | 주문 취소 구매자의 유효 예약 | 추가 제안 구매자의 구매 가능 수량 |
|---|---:|---:|---:|
| 주문 취소 전 | 2개 | 없음 | 2개 |
| 3번 주문 취소 완료 후 | 5개 | 3개 | 2개 |
| 5번 새 예약 해제 완료 후 | 5개 | 없음 | 5개 |

4번에서 추가 제안 구매자는 원하는 3개를 살 수 있는지 다시 조회한다. 구매 가능 수량은 2개다. 이 시나리오에서는 3개 일괄 구매를 선택했으므로 2개만 먼저 결제하지 않는다. 5번에서 예약이 해제된 뒤에는 구매 가능 수량이 5개가 되어 원하는 3개를 살 수 있다.

**추가 제안 구매자의 3개 제안이 수락된 흐름**

2번에서 주문 취소 구매자의 3개 결제와 추가 제안 구매자의 3개 예약이 성립한다. 남은 상품 4개 중 3개가 예약되어 정가 구매자가 살 수 있는 수량은 1개다. 따라서 정가 구매자의 2개 결제가 거절된다. 이 흐름에서 수량 부족으로 구매를 진행하지 못한 사람은 정가 구매자다.

| 관찰 시점 | 남은 상품 수량 | 주문 취소 구매자의 유효 예약 | 추가 제안 구매자의 유효 예약 | 정가 구매자의 구매 가능 수량 |
|---|---:|---:|---:|---:|
| 주문 취소 전 | 4개 | 없음 | 3개 | 1개 |
| 3번 주문 취소 완료 후 | 7개 | 3개 | 3개 | 1개 |
| 5번 새 예약 해제 완료 후 | 7개 | 없음 | 3개 | 4개 |

4번에서 정가 구매자는 앞서 사지 못한 2개를 살 수 있는지 다시 조회한다. 구매 가능 수량이 취소 전과 같은 1개이므로 2개 결제를 다시 요청하지 않는다. 5번에서 주문 취소 구매자의 새 예약이 해제되면 구매 가능 수량이 4개가 되어 2개를 살 수 있다. 추가 제안 구매자는 6번까지 결제하지 않으므로 그 예약 3개는 계속 유효하다.

두 흐름 모두 3번에서는 취소 주문에 연결된 반환 내역이 1건인지 확인한다. 새 예약은 결제로 FULFILLED가 된 기존 예약과 다른 행이어야 하며, 상품·구매자·대화·판매자·제안·수량은 같고 만료 시각만 취소 시각부터 새로 시작해야 한다.

5번에서는 해제한 새 예약이 RELEASED로 바뀌었는지 확인한다. 해제가 상품 수량이나 잔액을 다시 바꾸면 실패다.

#### 1.5.3 시나리오 6: 예약 해제 뒤 구매의 조회와 결제 검증

정가 구매자의 결제가 성공한 실행은 1.5.3.1로, 추가 제안이 수락된 실행은 1.5.3.2로 이어 간다. 두 흐름은 시작 상태가 다르므로 같은 데이터로 연속 수행하지 않는다. 기존 제안을 다시 수락하거나 새 예약을 만드는 절차는 어느 흐름에도 추가하지 않는다.

##### 1.5.3.1 정가 구매자의 2개 결제가 성공한 경우

5번 종료 시 상품은 5개이고 유효한 예약은 없다. 정가 구매자는 이미 2개를 결제했다. 추가 제안 구매자의 제안은 응답 대기 상태이며, 그 구매자의 예약과 주문은 없다. 이 흐름에서는 예약 해제 후 늘어난 구매 가능 수량으로 일반 구매가 가능한지 확인한다.

추가 제안 구매자는 원하는 3개를 살 수 있는지 상품을 다시 조회한다. 구매 가능 수량 5개를 확인한 뒤, 앞서 정한 행동 가정에 따라 등록 가격으로 3개를 결제한다. 조회와 결제는 순서대로 완료하며 다른 결제나 제안 수락을 겹치지 않는다.

결제 후에는 다음 결과를 확인한다.

- 수량 3개·개당 120,000원·총액 360,000원의 주문이 한 건 생긴다.
- 이 주문의 구매 차감 내역은 한 건이며 추가 제안 구매자의 잔액은 240,000원이 된다.
- 남은 상품은 2개이고 유효한 예약은 없다. 수락되지 않은 기존 제안은 응답 대기 상태로 유지된다.
- 정가 구매자의 기존 주문과 잔액은 바뀌지 않는다.

모두 일치하면 시나리오 7로 진행한다. 이 실행은 예약 해제 후의 순차 구매를 확인한 것이며, 다음 절의 예약 결제·조회 경합을 통과한 것으로 기록하지 않는다.

##### 1.5.3.2 추가 제안 구매자의 3개 제안이 수락된 경우

5번 종료 시 상품은 7개다. 주문 취소 구매자의 새 예약은 해제되었고, 추가 제안 구매자의 기존 예약 3개는 계속 유효하다. 정가 구매자는 앞서 2개 결제를 거절당했으며 주문이 없다. 두 구매자의 잔액은 각각 600,000원이고, 정가 구매자의 구매 가능 수량은 4개다.

추가 제안 구매자는 구매 준비를 마치고 예약한 3개를 합의 가격으로 결제 요청한다. 정가 구매자는 상품을 다시 조회하고, 필요한 2개를 살 수 있다고 판단하면 등록 가격으로 2개를 결제 요청한다. 정가 구매자의 조회와 구매 요청을 하나의 행동 흐름으로 이어서 관찰한다. 검증자가 조회의 정확성을 판정할 때까지 구매자가 기다리는 상황은 가정하지 않는다.

문제가 생길 가능성은 조회와 결제에서 나누어 살펴볼 수 있다. 조회 도중 추가 제안 구매자의 결제가 끝나면 상품과 예약을 서로 다른 시점에서 읽을 가능성이 있다. 조회가 먼저 끝나면 정가 구매자의 2개 결제가 진행 중인 3개 결제와 겹쳐, 상품 수량 차감이 어긋날 가능성도 있다. 아래 값은 두 요청이 정상적으로 처리되었을 때 기대하는 상태다.

| 결제 완료 상태 | 남은 상품 수량 | 추가 제안 구매자의 유효 예약 | 정가 구매자의 구매 가능 수량 |
|---|---:|---:|---:|
| 두 구매자 모두 결제 전 | 7개 | 3개 | 4개 |
| 추가 제안 구매자의 3개 결제만 완료 | 4개 | 없음 | 4개 |
| 정가 구매자의 2개 결제만 완료 | 5개 | 3개 | 2개 |
| 두 구매자의 결제 모두 완료 | 2개 | 없음 | 2개 |

가운데 두 행은 결제 완료 순서에 따른 서로 다른 경우다. 정가 구매자의 결제 전 조회는 4개를 반환하는 것이 기대값이고, 두 구매가 끝난 뒤 새로 조회하면 2개가 기대값이다. 추가 제안 구매자의 예약 결제만으로는 정가 구매자의 구매 가능 수량이 늘지 않지만, 정가 구매자 본인의 2개 결제가 완료되면 구매 가능 수량도 2개 줄어든다.

**조회 응답과 후속 구매 요청**

정가 구매자의 최초 조회 응답과 그 응답을 보고 보낸 수량 2개의 결제 요청을 연결해 기록한다. 조회가 결제 전 상품 7개와 결제 후 유효 예약 없음이라는 정보를 사용해 7개를 반환할 가능성을 확인하려는 것이다. 조회 응답이 성공이고 표시된 수량이 2개 이상이면, 시나리오의 구매자는 원래 원했던 2개를 요청하는 흐름을 따른다. 응답이 7개였더라도 요청 수량을 7개로 늘리거나 검증용 재조회로 원래 응답을 대체하지 않는다.

구매 가능 수량이 4개가 아닌 응답은 조회 검증의 실패로 남긴다. 다만 2개 구매 요청으로 이어질 수 있는 응답이라면 그 요청의 처리 결과까지 관찰한다. 조회 자체가 오류로 끝나거나 표시된 수량이 2개 미만이라면 구매자가 2개 결제를 보냈다고 가정하지 않고, 진행하지 못한 단계와 실제 응답을 기록한다.

**두 결제의 결과**

이 시점에는 예약된 3개와 예약되지 않은 수량 중 2개를 모두 판매할 수 있다. 2번처럼 한쪽의 수량 부족 거절을 정상 결과로 기대하는 조건이 아니다. 순차로 완료되든 두 요청이 겹치든 아래 결과와 일치하는지를 확인한다.

- 추가 제안 구매자에게 수량 3개·개당 110,000원·총액 330,000원의 주문 한 건과 구매 차감 한 건이 생기고, 잔액은 270,000원이 된다.
- 정가 구매자에게 수량 2개·개당 120,000원·총액 240,000원의 주문 한 건과 구매 차감 한 건이 생기고, 잔액은 360,000원이 된다.
- 남은 상품은 2개다. 추가 제안 구매자의 기존 예약은 결제 종료 상태가 되며 유효한 예약은 남지 않는다.
- 두 요청이 끝난 뒤 정가 구매자로 새로 조회하면 남은 상품 수량과 구매 가능 수량이 모두 2개다. 이 조회는 종료 상태 확인용이며 최초 조회의 정확성 판단을 대신하지 않는다.

두 결제가 같은 상품 수량을 읽고 각각 차감한 값을 저장하면 한쪽 차감이 반영되지 않을 가능성이 있다. 따라서 주문 두 건이 생겼다는 사실만으로 통과시키지 않고, 주문 수량 합계 5개와 남은 상품 2개를 함께 대조한다. 요청이 거절되거나 기술적 오류로 끝나면 실제 주문·차감·예약의 반영 여부를 확인하고, 두 구매가 완료된 실행으로 기록하지 않는다.

추가 제안 구매자의 결제가 조회 도중 끝나는 경우, 조회 뒤 두 결제가 겹치는 경우, 결제가 끝난 뒤 조회·구매하는 순차 경우를 각각 새 데이터로 비교할 수 있다. 조회와 결제 결과가 모두 기대값과 일치한 실행만 시나리오 7로 이어 간다.

#### 1.5.4 관찰과 중단

각 단계의 모든 요청이 종료된 뒤 같은 실행의 상품·주문·회원 범위로 확인한다. 시나리오 6의 중간 조회 응답은 별도 증거로 보존하고 최종 DB 값으로 덮어 해석하지 않는다.

- 남은 수량 + 취소되지 않은 주문 수량 = 최초 7개. 남은 수량은 0~7개.
- 유효 예약 합계는 남은 수량 이하, 동일 상품·구매자의 유효 예약은 하나 이하.
- 거절된 요청의 주문·예약·차감은 없고, 정상 결제·취소·확정은 수량과 금액을 각 주문에 한 번 반영.
- 누적 구매 차감 = 보관 금액 + 누적 반환 + 누적 지급. 회원 잔액은 시작 잔액과 내역에 일치.
- 취소만으로 타인의 구매 가능 수량이 늘지 않음. 해제만으로 남은 수량·잔액이 바뀌지 않음. 시나리오 6의 추가 제안 수락 성공 흐름에서는 정가 구매자 본인의 결제 전 조회가 구매 가능 수량 4개, 두 결제 후 새 조회가 2개를 반환.

위반이 있으면 실패를 기록하고 다음 업무 단계로 진행하지 않는다. 다만 6.2의 최초 조회에 잘못된 수량이 표시되었어도 구매자가 2개를 살 수 있다고 판단할 응답이라면, 그 응답에 따른 2개 결제까지 관찰한다. 조회 실패는 그대로 남기며 시나리오 7로 진행하지 않는다. 도달 실패·시간 초과·인증 만료 등은 정한 교차를 만들었는지 판정 불가로 기록한다. 중단 시 대기를 해제하고 이미 시작한 요청의 실제 커밋·롤백·종료를 확인한다. 클라이언트 타임아웃을 서버 롤백으로 간주하지 않는다. 실패 자료를 보존하고 다음 실행은 새로 준비한다.

### 1.6 테스트 종료 후 기대 결과

시나리오 7까지 정상 종료한 계산값이다. 추가 제안 구매자의 등록 가격 주문을 한 건으로 바꿨으므로 종전 정가 결제 성공 흐름의 주문·내역 건수도 함께 수정했다.

| 대상 | 정가 결제 성공 흐름 | 추가 제안 수락 성공 흐름 |
|---|---|---|
| 상품 | 최초 7, 판매 5, 남은 2, ON_SALE | 동일 |
| 취소 주문 | 주문 취소 구매자 3개·300,000원, 1건. CANCELLED·WAITING_SHIPMENT, 발송 없음 | 동일 |
| 정상 완료 주문 | 정가 구매자 2개·240,000원, 추가 제안 구매자 3개·360,000원. 2건·5개 | 정가 구매자 2개·240,000원, 추가 제안 구매자 합의 3개·330,000원. 2건·5개 |
| 배송·완료 | 주문별 COMPLETED·DELIVERED·BUYER_CONFIRMED, 발송 정보 2건 | 동일 |
| 예약 | 총 2행: 주문 취소 구매자 최초 FULFILLED, 취소 후 RELEASED·BUYER. 유효 예약 없음 | 총 3행: 왼쪽 2행 + 추가 제안 구매자 FULFILLED. 유효 예약 없음 |
| 제안 | 주문 취소 구매자 ACCEPTED, 추가 제안 구매자 PENDING | 두 구매자의 제안 모두 ACCEPTED |
| 주문 취소 구매자 잔액 | 600,000 − 300,000 + 300,000 = 600,000원 | 동일 |
| 정가 구매자 잔액 | 600,000 − 240,000 = 360,000원 | 동일 |
| 추가 제안 구매자 잔액 | 600,000 − 360,000 = 240,000원 | 600,000 − 330,000 = 270,000원 |
| 판매자 잔액 | 600,000원 | 570,000원 |
| PURCHASE | 3건·900,000원 | 3건·870,000원 |
| CANCEL_REFUND | 주문 취소 구매자 취소 주문에 1건·300,000원 | 동일 |
| SALE_PAYOUT | 2건·600,000원 | 2건·570,000원 |
| 진행 중·보류 주문과 보관 금액 | 없음, 0원 | 동일 |

정가 결제 성공 흐름은 900,000 = 반환 300,000 + 지급 600,000원, 추가 제안 수락 성공 흐름은 870,000 = 반환 300,000 + 지급 570,000원이다. 네 회원의 시작·최종 잔액 합계는 모두 1,800,000원이다. 예약 이력은 삭제하지 않는다. 제안 ACCEPTED와 현재 유효 예약 여부는 다른 상태다.

### 1.7 테스트 실행 결과

미실행. 이번 개정에서는 소스·문서를 읽고 문서의 수량·금액·연결 관계를 검토했다. API 요청, 애플리케이션 테스트, JMeter, DB 조회·변경은 실행하지 않았다. 향후 실행별 소스·설정 버전, 실제 순서, 기대값·실제값, 판정, 증거 위치를 기록한다.

### 1.8 테스트에 사용한 파일

이번 개정에서 실행에 사용한 파일은 없다. 0.12 흐름에 대응하는 실행 계획·조회 쿼리·계측은 준비 및 검증 전이다. 기존 실행 자료가 있더라도 이 개정의 실행 증거로 간주하지 않는다.

### 1.9 테스트 결과 파일

미실행이므로 이 개정의 결과 파일은 없다. 향후 요청·응답, 제어·SQL·트랜잭션 로그와 DB 결과를 실행별로 연결한다.
