## 1. 명세 내용

### 1.1 무엇을 확인하는 테스트인가

모니터 7개에 구매 요청이 3개·2개·3개 들어온다. 먼저 예약된 3개를 보호하면서, 나머지 4개를 두 사람에게 중복 배정하지 않는지 확인한다. 이어서 주문 취소와 예약 해제가 다른 구매자의 구매 가능 수량에 어떻게 반영되는지 확인한다.

핵심 판정은 세 가지다.

| 구간 | 확인할 문제 | 정상 결과 |
|---|---|---|
| 2번: 결제·제안 수락 경합 | 남은 4개에 결제 2개와 새 예약 3개를 모두 허용하는가? | 둘 중 하나만 성공. 먼저 예약된 3개의 결제는 성공 |
| 3–5번: 취소 후 예약 해제 | 주문만 취소했는데 다른 사람이 살 수 있는 수량도 늘어나는가? | 취소 직후에는 그대로. 새 예약까지 해제하면 3개 증가 |
| 6번: 후속 구매 | 예약 결제 중 조회가 틀리거나, 두 결제 중 한쪽 수량 차감이 누락되는가? | 아래 분기별 조회값과 일치. 총 5개 판매 후 상품 2개 남음 |

**주문 취소와 예약 해제는 별도 요청이다.** 현재 정책에서는 합의 주문을 취소하면 수량과 돈이 돌아오면서, 취소한 사람에게 같은 수량의 새 예약이 생긴다. 재구매하지 않으려면 그 예약도 해제해야 한다. 이 문서는 그 정책을 전제로 테스트한다.

파일명에는 ‘취소와 발송등록 경합’이 남아 있지만, 0.2부터 본문 범위가 바뀌었다. 이번 테스트에서 취소와 발송은 동시에 실행하지 않는다. 기존 링크를 유지하기 위해 파일명은 그대로 둔다.

동일 주문 중복 취소, 자동 취소 경합, 환불 분쟁, 같은 지갑의 동시 변경은 제외한다. 알림·대기열과 자동 재시도도 추가하지 않는다. 아래 값은 **테스트 기대값**이며 실제 동작을 확인한 결과가 아니다.

### 1.2 누가 무엇을 구매하는가

| 참여자 | 구매 계획 | 이후 행동 |
|---|---|---|
| 판매자 | 모니터 7개 판매 | 제안을 수락하고, 취소되지 않은 주문만 발송 |
| 주문 취소 구매자 | 먼저 3개를 합의 가격으로 예약 | 결제 → 발송 전 주문 취소 → 새 예약 해제 |
| 정가 구매자 | 등록 가격으로 2개 구매 | 첫 결제가 실패하면 나중에 상품을 다시 조회하고 구매 |
| 추가 제안 구매자 | 3개를 합의 가격으로 구매하고자 제안 | 수락되면 예약 결제. 수락 실패 시 나중에 등록 가격으로 3개 구매 |

‘정가’는 상품 등록 가격이다. ‘추가 제안’은 먼저 예약한 구매자 외에 다른 사람이 보낸 제안이다. 아래에서도 이 호칭을 같은 사람에게 사용한다.

추가 제안 구매자가 수락 실패 후 등록 가격으로 구매하는 것은 이 테스트의 행동 가정이다. 판매자는 실패한 수락을 재시도하지 않는다. 수락된 경우에는 6번까지 결제를 미루되 예약은 만료되지 않는다.

구매자는 상품을 다시 열거나 새로고침해서 **자신의 구매 가능 수량**을 확인한다. 다른 사람의 취소 내역을 알거나 별도 알림을 받았다고 가정하지 않는다.

### 1.3 업무 규칙과 입력값

| 항목 | 적용 내용 |
|---|---|
| 상품 | 7개, 개당 120,000원, ELECTRONICS. 상품명은 실행별 식별값을 붙인 「시나리오 모니터」, 설명은 「거래 시나리오용 모니터」 |
| 주문 취소 구매자 | 3개·개당 100,000원 합의, 결제·취소 반환 각각 300,000원 |
| 정가 구매자 | 등록 가격 2개, 240,000원 |
| 추가 제안 구매자 | 제안 3개·개당 110,000원. 수락 분기에서는 330,000원, 수락 실패 분기에서는 등록 가격 3개를 한 주문으로 360,000원 결제 |
| 시작 잔액 | 구매자마다 600,000원, 판매자 0원. 다른 거래·추가 충전 없음 |
| 수량 | 남은 수량에는 예약분 포함. 해당 회원의 구매 가능 수량 = 남은 수량 − 다른 회원의 유효 예약 수량 합계 |
| 유효 예약 | ACTIVE이면서 관찰 시각이 expiresAt보다 이른 예약. 기간 PT20M. 만료 시각에 도달하면 자동 해제 작업 전이라도 구매 가능 수량을 막지 않음 |
| 합의 가격 결제 | 본인의 수락 제안과 유효 예약이 있어야 함. 제안 수량 3개 전체를 결제하고 예약은 FULFILLED. 예약 중에는 offerId 없는 등록 가격 결제를 거절 |
| 수락 실패 | 예약할 수량 부족 시 수락도 롤백, 제안 PENDING 유지. 자동 재시도 없음 |
| 취소 | 발송 전 취소. 상품 +3, 같은 제안·수량의 새 ACTIVE 예약 +3, 전액 반환. 기존 FULFILLED 예약 보존. 새 만료 시각은 취소 시각 +20분 |
| 직접 해제 | 새 예약 ID로 별도 요청. RELEASED·releasedBy=BUYER. 상품 수량·주문·잔액을 다시 변경하지 않음 |
| 거래 종료 | 발송 기한 전 발송, 예정 시각 이상에서 모의 배송 완료, 상품 확인 기한 전 구매 확정, 주문 금액 전액을 한 번 지급 |
| 기타 입력 | 수령인은 역할명, 주소 「시나리오 테스트 주소」, 취소 사유 「구매 철회」. 택배사 「테스트택배」, 운송장은 실행·주문별 고유값 |

동일 상품·구매자의 유효 예약 하나, 수량·금전의 정합성은 검증할 불변식이다. 경합에서도 이미 보장된다고 단정하지 않는다. 금액은 원 단위 정수이며 단가·총액은 서버 계산값으로 확인한다.

### 1.4 시작 전 준비

새 상품과 판매자 1명·구매자 3명, 총 4개의 서로 다른 회원 계정을 사용한다. 지갑을 미리 생성하고 위 잔액을 준비한다. 준비 충전은 거래 구간의 구매·반환·지급 집계에서 제외한다. 상품·대화·제안·예약·주문 ID는 응답과 본인 조회에서 취득하고 이전 실행 ID를 재사용하지 않는다.

업무 시계를 고정하고 스케줄러를 끈다. 시나리오 6까지 모든 예약이 만료 전이며 취소·발송도 기한 전이어야 한다. 배송 완료 때만 모든 배송 예정 시각 이상으로 이동한다. 종료 시 시계를 해제한다. TestClock은 서버 전체에 적용되므로 다른 테스트나 사용자 거래가 없는 환경을 전제로 한다.

### 1.5 테스트 절차와 단계별 기대 결과

#### 1.5.1 시나리오 번호와 전체 흐름

정가 구매자의 최초 결제가 성공하면 ‘정가 결제 성공 흐름’, 판매자가 추가 제안을 수락하면 ‘추가 제안 수락 성공 흐름’으로 이어진다. 표는 각 요청의 트랜잭션 종료 후 기대값이다.

| 시나리오 | 수행 주체·요청 | 기대 결과 |
|---|---|---|
| 1. 준비 | 상품·세 대화 생성. 주문 취소 구매자의 3개 제안 수락, 추가 제안 구매자의 3개 제안은 PENDING | 상품 7, 주문 취소 구매자 예약 3. 정가 구매자·추가 제안 구매자 구매 가능 4 |
| 2. 결제·수락 경합 | 주문 취소 구매자의 합의 가격 3개 결제, 정가 구매자의 등록 가격 2개 결제, 판매자의 추가 제안 3개 수락을 겹침 | 주문 취소 구매자 결제 성공. 정가 결제와 추가 제안 수락은 하나만 성공해야 함. 정가 결제 성공 흐름: 상품 2·유효 예약 없음·결제 주문 2건. 추가 제안 수락 성공 흐름: 상품 4·추가 제안 구매자 예약 3·결제 주문 1건 |
| 3. 주문만 취소 | 주문 취소 구매자의 취소 요청을 끝낸 뒤 확인. 다른 구매자의 결제를 겹치지 않음 | 해당 주문 CANCELLED·300,000원 반환·새 예약 3. 정가 결제 성공 흐름: 상품 5·주문 취소 구매자 예약 3. 추가 제안 수락 성공 흐름: 상품 7·주문 취소 구매자와 추가 제안 구매자에게 각각 예약 3 |
| 4. 구매 가능 수량 확인 | 1.5.2의 두 흐름에 따라 수량 부족으로 구매를 진행하지 못한 사람이 상품을 재조회. 주문 취소 구매자는 본인 대화에서 새 예약 확인 | 해당 구매자의 구매 가능 수량은 취소 전과 같아 원하는 수량에 부족함. 결제 요청을 보내지 않고 다음에 다시 확인하기로 함 |
| 5. 새 예약 직접 해제 | 주문 취소 구매자가 취소 후 생성된 예약 ID로 DELETE 요청. 완료 후 앞서 수량이 부족했던 구매자가 재조회 | 새 예약 RELEASED. 남은 상품 수량·잔액 불변. 해당 구매자의 구매 가능 수량은 3개 늘어 원하는 수량을 살 수 있게 됨. 흐름별 수량은 1.5.2의 표와 대조 |
| 6. 후속 구매의 조회·결제 검증 | 정가 결제 성공 흐름은 추가 제안 구매자의 등록 가격 3개 구매. 추가 제안 수락 성공 흐름은 예약된 3개 결제와 정가 구매자의 조회·2개 구매. 분기별 절차는 1.5.3 참조 | 정가 결제 성공 흐름: 추가 제안 구매자 조회 5개. 추가 제안 수락 성공 흐름: 정가 구매자 결제 전 조회 4개. 두 흐름 모두 최종 판매 5개·상품 2개·유효 예약 없음 |
| 7. 정상 마무리 | 미취소 주문 2건을 순차 발송 → 모의 배송 완료 → 구매 확정 | 각 주문 COMPLETED·DELIVERED·BUYER_CONFIRMED. 지급 각 1회. 취소 주문 발송 없음. 1.6과 대조 |

시나리오 2의 부족 거절은 정가 결제 성공 흐름의 수락 요청에는 409 `RESERVATION_QUANTITY_EXCEEDED`, 추가 제안 수락 성공 흐름의 정가 구매자 결제에는 409 `PRODUCT_RESERVED`를 순차 기준으로 기대한다.

#### 1.5.2 시나리오 3–5: 취소, 구매 판단, 예약 해제를 분리

3번의 취소가 끝나고 5번의 해제를 하기 전까지는 새 예약이 유효하다. 이 구간에서 확인하는 사람과 수량을 2번의 결과별로 나누면 다음과 같다. 각 표는 별도의 실행 흐름이며, 모든 수량은 해당 단계의 요청이 종료된 뒤 관찰한다.

**정가 구매자의 2개 결제가 성공한 흐름**

2번에서 주문 취소 구매자의 3개 결제와 정가 구매자의 2개 결제가 성공한다. 남은 수량은 2개이므로 판매자의 추가 제안 3개 수락은 실패한다. 아직 구매하지 못한 사람은 추가 제안 구매자다.

| 관찰 시점 | 남은 상품 수량 | 주문 취소 구매자의 유효 예약 | 추가 제안 구매자의 구매 가능 수량 |
|---|---:|---:|---:|
| 주문 취소 전 | 2개 | 없음 | 2개 |
| 3번 주문 취소 완료 후 | 5개 | 3개 | 2개 |
| 5번 새 예약 해제 완료 후 | 5개 | 없음 | 5개 |

4번 조회값은 2개이므로 원하는 3개를 결제하지 않는다. 5번 조회값이 5개가 되면 6번 구매로 진행한다.

**추가 제안 구매자의 3개 제안이 수락된 흐름**

2번에서 주문 취소 구매자의 3개 결제와 추가 제안 구매자의 3개 예약이 성립한다. 남은 상품 4개 중 3개가 예약되어 정가 구매자가 살 수 있는 수량은 1개다. 따라서 정가 구매자의 2개 결제가 거절된다. 이 흐름에서 수량 부족으로 구매를 진행하지 못한 사람은 정가 구매자다.

| 관찰 시점 | 남은 상품 수량 | 주문 취소 구매자의 유효 예약 | 추가 제안 구매자의 유효 예약 | 정가 구매자의 구매 가능 수량 |
|---|---:|---:|---:|---:|
| 주문 취소 전 | 4개 | 없음 | 3개 | 1개 |
| 3번 주문 취소 완료 후 | 7개 | 3개 | 3개 | 1개 |
| 5번 새 예약 해제 완료 후 | 7개 | 없음 | 3개 | 4개 |

4번 조회값은 1개이므로 원하는 2개를 결제하지 않는다. 5번 조회값이 4개가 되면 6번 구매로 진행한다. 추가 제안 구매자의 예약 3개는 이때도 유효하다.

두 흐름에 공통으로 적용할 확인 사항은 다음과 같다.

- 취소: 주문에 연결된 300,000원 반환이 정확히 1건이다. 기존 예약은 FULFILLED로 남고, 같은 상품·당사자·제안·수량으로 새 ACTIVE 예약이 생긴다. 새 예약의 만료 시각은 취소 시각 +20분이다.
- 해제: 취소 후 생성된 **새 예약 ID**로 요청한다. 상태는 RELEASED, releasedBy는 BUYER다. 상품 수량과 잔액은 해제 전후 같아야 한다.

#### 1.5.3 시나리오 6: 예약 해제 뒤 구매의 조회와 결제 검증

정가 구매자의 결제가 성공한 실행은 1.5.3.1로, 추가 제안이 수락된 실행은 1.5.3.2로 이어 간다.

##### 1.5.3.1 정가 구매자의 2개 결제가 성공한 경우

5번 종료 시 상품은 5개이고 유효한 예약은 없다. 정가 구매자는 이미 2개를 결제했다. 추가 제안 구매자의 제안은 응답 대기 상태이며, 그 구매자의 예약과 주문은 없다.

추가 제안 구매자는 원하는 3개를 살 수 있는지 상품을 다시 조회한다. 구매 가능 수량 5개를 확인한 뒤 등록 가격으로 3개를 결제한다. 조회와 결제는 순서대로 완료하며 다른 결제나 제안 수락을 겹치지 않는다.

결제 후에는 다음 결과를 확인한다.

- 수량 3개·개당 120,000원·총액 360,000원의 주문이 한 건 생긴다.
- 이 주문의 구매 차감 내역은 한 건이며 추가 제안 구매자의 잔액은 240,000원이 된다.
- 남은 상품은 2개이고 유효한 예약은 없다. 수락되지 않은 기존 제안은 응답 대기 상태로 유지된다.
- 정가 구매자의 기존 주문과 잔액은 바뀌지 않는다.

##### 1.5.3.2 추가 제안 구매자의 3개 제안이 수락된 경우

5번 종료 시 상품은 7개다. 주문 취소 구매자의 새 예약은 해제되었고, 추가 제안 구매자의 기존 예약 3개는 계속 유효하다. 정가 구매자는 앞서 2개 결제를 거절당했으며 주문이 없다. 두 구매자의 잔액은 각각 600,000원이고, 정가 구매자의 구매 가능 수량은 4개다.

추가 제안 구매자는 예약한 3개를 합의 가격으로 결제 요청한다. 정가 구매자는 상품을 다시 조회하고, 필요한 2개를 살 수 있다고 판단하면 등록 가격으로 2개를 결제 요청한다. 정가 구매자의 조회와 구매 요청을 하나의 행동 흐름으로 이어서 관찰한다.

아래 값은 두 요청이 정상적으로 처리되었을 때 기대하는 상태다.

| 결제 완료 상태 | 남은 상품 수량 | 추가 제안 구매자의 유효 예약 | 정가 구매자의 구매 가능 수량 |
|---|---:|---:|---:|
| 두 구매자 모두 결제 전 | 7개 | 3개 | 4개 |
| 추가 제안 구매자의 3개 결제만 완료 | 4개 | 없음 | 4개 |
| 정가 구매자의 2개 결제만 완료 | 5개 | 3개 | 2개 |
| 두 구매자의 결제 모두 완료 | 2개 | 없음 | 2개 |

가운데 두 행은 결제 완료 순서에 따른 서로 다른 경우다. 정가 구매자의 결제 전 조회는 4개를 반환하는 것이 기대값이고, 두 구매가 끝난 뒤 새로 조회하면 2개가 기대값이다. 추가 제안 구매자의 예약 결제만으로는 정가 구매자의 구매 가능 수량이 늘지 않지만, 정가 구매자 본인의 2개 결제가 완료되면 구매 가능 수량도 2개 줄어든다.

**조회 응답과 후속 구매 요청**

조회 응답이 성공이고 표시된 수량이 2개 이상이면, 시나리오의 구매자는 원래 원했던 2개를 요청하는 흐름을 따른다.

**두 결제의 결과**

이 시점에는 예약된 3개와 예약되지 않은 수량 중 2개를 모두 판매할 수 있다. 순차로 완료되든 두 요청이 겹치든 아래 결과와 일치하는지를 확인한다.

- 추가 제안 구매자에게 수량 3개·개당 110,000원·총액 330,000원의 주문 한 건과 구매 차감 한 건이 생기고, 잔액은 270,000원이 된다.
- 정가 구매자에게 수량 2개·개당 120,000원·총액 240,000원의 주문 한 건과 구매 차감 한 건이 생기고, 잔액은 360,000원이 된다.
- 남은 상품은 2개다. 추가 제안 구매자의 기존 예약은 결제 종료 상태가 되며 유효한 예약은 남지 않는다.
- 두 요청이 끝난 뒤 정가 구매자로 새로 조회하면 남은 상품 수량과 구매 가능 수량이 모두 2개다.

#### 1.5.4 관찰

각 단계의 모든 요청이 종료된 뒤 같은 실행의 상품·주문·회원 범위로 확인한다.

- 남은 수량 + 취소되지 않은 주문 수량 = 최초 7개. 남은 수량은 0~7개.
- 유효 예약 합계는 남은 수량 이하, 동일 상품·구매자의 유효 예약은 하나 이하.
- 거절된 요청의 주문·예약·차감은 없다. 결제는 상품 수량 차감·구매 금액 차감, 취소는 상품 수량 복구·전액 반환, 구매 확정은 판매대금 지급을 각 주문에 한 번만 반영한다.
- 누적 구매 차감 = 보관 금액 + 누적 반환 + 누적 지급. 회원 잔액은 시작 잔액과 내역에 일치.
- 취소만으로 타인의 구매 가능 수량이 늘지 않음. 해제만으로 남은 수량·잔액이 바뀌지 않음. 시나리오 6의 추가 제안 수락 성공 흐름에서는 정가 구매자 본인의 결제 전 조회가 구매 가능 수량 4개, 두 결제 후 새 조회가 2개를 반환.

### 1.6 테스트 종료 후 기대 결과

시나리오 7까지 정상 종료했을 때의 기대값이다. 두 열은 서로 다른 실행의 결과다.

| 대상 | 정가 결제 성공 흐름 | 추가 제안 수락 성공 흐름 |
|---|---|---|
| 상품 | 최초 7, 판매 5, 남은 2, ON_SALE | 동일 |
| 취소 주문 | 주문 취소 구매자 3개·300,000원, 1건. CANCELLED·WAITING_SHIPMENT, 발송 없음 | 동일 |
| 정상 완료 주문 | 정가 구매자 2개·240,000원, 추가 제안 구매자 3개·360,000원. 2건·5개 | 정가 구매자 2개·240,000원, 추가 제안 구매자 합의 3개·330,000원. 2건·5개 |
| 배송·완료 | 주문별 COMPLETED·DELIVERED·BUYER_CONFIRMED, 발송 정보 2건 | 동일 |
| 예약 | 총 2행: 주문 취소 구매자 최초 FULFILLED, 취소 후 RELEASED·BUYER. 유효 예약 없음 | 총 3행: 왼쪽 2행 + 추가 제안 구매자 FULFILLED. 유효 예약 없음 |
| 제안 | 주문 취소 구매자 ACCEPTED, 추가 제안 구매자 PENDING | 두 구매자의 제안 모두 ACCEPTED |
| 주문 취소 구매자 잔액 | 600,000 − 300,000 + 300,000 = 600,000원 | 동일 |
| 정가 구매자 잔액 | 600,000 − 240,000 = 360,000원 | 동일 |
| 추가 제안 구매자 잔액 | 600,000 − 360,000 = 240,000원 | 600,000 − 330,000 = 270,000원 |
| 판매자 잔액 | 600,000원 | 570,000원 |
| PURCHASE | 3건·900,000원 | 3건·870,000원 |
| CANCEL_REFUND | 주문 취소 구매자 취소 주문에 1건·300,000원 | 동일 |
| SALE_PAYOUT | 2건·600,000원 | 2건·570,000원 |
| 진행 중·보류 주문과 보관 금액 | 없음, 0원 | 동일 |

정가 결제 성공 흐름은 900,000 = 반환 300,000 + 지급 600,000원, 추가 제안 수락 성공 흐름은 870,000 = 반환 300,000 + 지급 570,000원이다. 네 회원의 시작·최종 잔액 합계는 모두 1,800,000원이다. 예약 이력은 삭제하지 않는다. 제안 ACCEPTED와 현재 유효 예약 여부는 다른 상태다.

### 1.7 테스트 실행 결과

## 4. 시스템 명세

### 4.2 테스트 실행 분기점 기준

각 실행은 새 데이터로 시작한다. 2번에서 두 정상 분기 중 하나가 성립한 경우에만 해당 분기의 3–7번으로 이어 간다. 둘 다 성공하거나 예약된 구매자의 결제가 실패하면 해당 실행을 실패로 기록하고 증거를 보존한다. 데이터를 임의로 고쳐 정상 흐름에 끼워 넣지 않는다.

| 실행 | 요청 순서·겹침 | 판정 |
|---|---|---|
| 순차 기준 1 | 먼저 예약한 3개 결제 완료 → 정가 2개 결제 완료 → 추가 제안 수락 | 수락 거절. 정가 결제 성공 흐름의 3–7번 확인 |
| 순차 기준 2 | 먼저 예약한 3개 결제 완료 → 추가 제안 수락 완료 → 정가 2개 결제 | 정가 결제 거절. 추가 제안 수락 성공 흐름의 3–7번 확인 |
| 2번 경합 | 예약 3개 결제·정가 2개 결제·추가 제안 수락을 겹침 | 1.5.1의 두 정상 분기 중 하나. 수량 중복 배정·차감 누락·실패 요청의 잔여 데이터는 실패 |
| 6번 조회 경합 | 추가 제안 수락 성공 흐름에서 예약 3개 결제와 정가 구매자 조회를 겹침. 조회 응답 뒤 정가 2개 구매 | 결제 전 조회 4개. 이후 두 구매 완료 시 상품 2개 |
| 6번 결제 경합 | 같은 분기에서 정가 구매자 조회를 먼저 완료한 뒤, 예약 3개 결제와 정가 2개 결제를 겹침 | 조회 4개. 두 결제 성공·주문 합계 5개·상품 2개 |


동시에 요청을 전송했다는 사실만으로 내부 처리의 겹침이 입증되지는 않는다. 요청별 시작·종료, 중지 지점 도달·재개, 트랜잭션 종료 순서를 남긴다. 의도한 겹침을 확인하지 못한 실행은 ‘재현 미확인’으로 구분한다.

현재 `PausePoint`에는 `PAYMENT_CHECKED`, `PAYMENT_BEFORE_COMMIT`, `RESERVATION_CHECKED`가 있다. 상품 조회 중간을 멈추는 지점은 없다. 조회 경합의 정확한 재현 제어와 요청별 설정은 아직 작성·검증되지 않았으므로, 이 표를 곧바로 실행 가능한 스크립트로 취급하지 않는다.

### 4.3 실행 결과에 남길 항목

실행 ID, 소스 버전·설정, 상품·회원·제안·예약·주문 ID, 요청 순서와 실제 겹침, 요청·응답 원문, 종료 후 수량·상태·금액을 남긴다. 판정은 순차 동작·조회 정확성·결제 정합성을 구분한다. 예상과 다른 응답이나 시간 초과는 성공으로 간주하지 않고 원인과 실제 반영 여부를 확인한다.
