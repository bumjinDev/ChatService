# 작업명세 02 테스트 계획: 구매자 취소와 판매자 취소

- 작성일: 2026-10-13
- 작업기록: [작업기록](../작업기록.md)
- 관련 명세: [작업명세 01 테스트 계획: 공통](01_테스트계획_공통.md), [작업명세 07 공통 실행 참조](07_공통실행참조.md)

상황 S1-1의 조건, 요청, 절차, 예상 결과를 정한다. 테스트 목적, 테스트 방법, 실행 환경, 공통 결과 확인 기준은 [작업명세 01](01_테스트계획_공통.md)을 따른다.

## 1. 검증 목적과 정상 동작

구매자가 아이폰을 350,000원에 구매한 뒤 판매자와 채팅으로 주문 취소에 합의한다. 두 사람은 상대방의 취소 결과를 확인하기 전에 거의 동시에 취소 요청을 보낸다. 주문 화면은 상대방의 처리를 실시간으로 보여 주지 않으므로 이런 일이 생길 수 있다.

충돌하는 처리는 구매자의 주문 취소와 판매자의 주문 취소다. 두 처리 모두 주문을 취소 완료로 바꾸고 구매자에게 결제액을 돌려준다.

**정상 동작:** 두 취소 요청 가운데 하나만 성공한다. 다른 요청은 이미 끝난 거래에 대한 요청이므로 409 `TRADE_ALREADY_FINALIZED`로 거절된다. 결제액 350,000원은 한 번만 반환되어 구매자 잔액은 400,000원이 된다.

## 2. 사전조건과 테스트 데이터

### 2.1 시작 상태와 금액

두 요청을 보내기 직전의 상태는 다음과 같다.

| 항목 | 값 |
|---|---|
| 거래 상태 | 진행 중(`IN_PROGRESS`) |
| 배송 상태 | 발송 대기(`WAITING_SHIPMENT`) |
| 상품 | 아이폰, 가격 350,000원, 수량 1개. 등록 가격으로 결제 |
| 구매자 | 충전 400,000원, 결제 후 잔액 50,000원 |
| 판매자 | 충전 없음, 잔액 0원 |

### 2.3 준비 순서

다음 요청을 순서대로 보낸다.

1. 판매자와 구매자의 회원 가입과 로그인. 요청 형식은 [작업명세 07의 1절](07_공통실행참조.md#common-requests)을 따른다.
2. 판매자의 상품 등록 `POST /api/products`

   ```json
   {"name":"아이폰","description":"배터리 성능 86%, 흠집 없음. 박스와 케이블 포함.","category":"ELECTRONICS","price":350000,"quantity":1}
   ```

3. 구매자의 충전 `POST /api/wallet/charges`

   ```json
   {"amount":400000,"requestId":"${__UUID()}"}
   ```

4. 구매자의 결제 `POST /api/orders`

   ```json
   {"productId":${productId},"quantity":1,"recipientName":"김하늘","shippingAddress":"서울특별시 마포구 월드컵북로 400","requestId":"${__UUID()}"}
   ```

## 3. 요청 A와 요청 B

두 요청 모두 `OrderCancellationService.cancelByParty`가 처리한다.

**요청 A: 구매자의 주문 취소** `POST /api/orders/${orderId}/cancel` (구매자 로그인 쿠키)

```json
{"reason":"판매자와 합의해 취소합니다."}
```

**요청 B: 판매자의 주문 취소** `POST /api/orders/${orderId}/cancel` (판매자 로그인 쿠키)

```json
{"reason":"구매자와 채팅으로 취소에 합의했습니다."}
```

## 4. 겹침 재현 테스트

### 4.1 요청 처리를 일시 중지할 위치

**일시 중지하는 이유**

- **경합이 생기는 구조:** 취소 요청은 잠금 없이 주문을 조회하고, 조회한 주문 상태로 취소할 수 있는지 검사한다. 한 요청이 커밋하기 전에 다른 요청이 주문을 조회하면, 두 요청 모두 취소 전의 주문 상태를 보고 검사를 통과할 수 있다.
- **동시에 보내기만 할 때의 한계:** 두 요청이 이렇게 겹치려면 한 요청을 처리하는 짧은 시간 안에 다른 요청이 도착해야 한다. 그래서 겹칠지가 우연에 달려 있고, 어느 요청이 먼저 커밋될지도 정할 수 없다.
- **일시 중지로 확인하는 것:** 서버에서 두 요청을 일시 중지했다가 정한 순서로 재개해, 경합이 실제로 발생하는지를 매번 같은 조건으로 확인한다.

**일시 중지하는 위치**

- 두 취소 요청이 같은 주문 상태를 조회한 뒤 처리되도록, 조회가 끝난 지점에서 두 요청을 일시 중지한다.
- 구매자 지갑을 조회하는 시점에 따라서도 결과가 달라질 수 있으므로 중지 위치를 두 가지로 나누어 테스트한다.

취소 요청에서 주문과 잔액을 처리하는 순서는 다음과 같다.

1. 주문을 조회한다.
2. 요청자가 주문의 구매자 또는 판매자인지, 거래가 아직 종료되지 않았는지, 배송 상태가 발송 대기인지 검사한다. 거래·배송 상태는 1번에서 조회한 주문을 기준으로 검사한다.
3. 구매자 지갑을 조회하고, 결제액을 반환한 후의 잔액이 잔액 컬럼의 저장 범위를 초과하는지 검사한다.
4. 주문을 취소 완료로 변경하고, 요청자에 따라 취소 주체를 구매자 또는 판매자로 기록한다. 취소 사유에는 요청 본문의 값을 기록한다. 이어서 3번에서 조회한 잔액에 결제액을 더하고, 취소 반환 내역(`CANCEL_REFUND`) 한 건을 기록한다.
5. 트랜잭션을 커밋하여 변경을 확정한다.

각 테스트에서는 아래 두 위치 중 하나를 선택하여 두 요청을 모두 그 위치에서 일시 중지한다.

- **중지 위치 1: 주문 조회 직후, 취소 조건 검사 전.** 위 순서의 1번과 2번 사이에 해당한다. 두 요청 모두 주문만 조회한 상태이며, 구매자 지갑은 처리를 재개한 뒤 조회한다.
- **중지 위치 2: 구매자 지갑 조회와 잔액 범위 검사 후, 주문 변경 전.** 위 순서의 3번과 4번 사이에 해당한다. 두 요청 모두 주문과 구매자 지갑을 조회했으며, 주문 상태와 잔액은 아직 변경하지 않은 상태다.

테스트케이스마다 JMeter 스레드 세 개가 동시에 시작한다. 스레드 1은 요청 A를, 스레드 2는 요청 B를 보내고, 스레드 3은 위 4~6번 단계(멈춤 확인과 재개)를 맡는다. 아래에서는 스레드 3을 재개 제어라고 부른다.

나중에 재개되는 요청은 처음부터 다시 처리하지 않고, 멈추기 전에 조회해 둔 주문 상태로 이어서 처리한다. 그래서 먼저 재개된 요청이 주문을 취소하고 커밋한 뒤에도, 나중에 재개된 요청은 그 취소를 반영하지 않은 주문 상태로 처리를 계속한다. 테스트케이스별 처리 순서는 다음과 같다.

#### 4.2.1 테스트케이스1: 중지 위치 1(주문 조회 직후), 요청 A 먼저 재개

| 순서 | 요청 A(구매자 취소) | 요청 B(판매자 취소) | 재개 제어 |
|---|---|---|---|
| 1 | 구매 목록을 조회해 주문 ID를 얻고 취소 요청을 보낸다 | 판매 목록을 조회해 주문 ID를 얻고 취소 요청을 보낸다 | 두 요청이 멈출 때까지 기다린다 |
| 2 | 서버가 주문을 조회한 직후 멈춘다 | 서버가 주문을 조회한 직후 멈춘다 | 두 요청이 모두 멈춘 것을 확인한다 |
| 3 | 재개되어 취소 조건 검사, 구매자 지갑 조회, 주문 취소와 결제액 반환을 처리한 뒤 커밋한다. 응답을 받는다 | 멈춘 채 기다린다 | 요청 A를 재개하고 요청 A의 응답을 기다린다 |
| 4 | 끝난다 | 재개되어 2에서 조회한 주문 상태로 취소 조건을 검사한다. 이어서 구매자 지갑 조회, 주문 취소와 결제액 반환을 처리한 뒤 커밋한다. 응답을 받는다 | 요청 A의 응답을 확인하고 요청 B를 재개한다. 요청 B의 응답을 기다린다 |

#### 4.2.2 테스트케이스2: 중지 위치 1(주문 조회 직후), 요청 B 먼저 재개

| 순서 | 요청 A(구매자 취소) | 요청 B(판매자 취소) | 재개 제어 |
|---|---|---|---|

### 4.3 예상 결과와 확인 방법

다음은 코드 분석에 따른 가설이며, 아직 테스트로 확인하지 않았다. 아래의 첫 번째 요청과 두 번째 요청은 전송 순서가 아니라 4.2절에서 정한 재개 순서를 뜻한다.

테스트케이스1~테스트케이스4 모두 두 요청이 200 응답을 받고, 최종 거래 상태는 취소 완료(`CANCELLED`)가 될 것으로 예상한다. 두 요청 모두 취소 전의 주문 상태로 조건을 검사하며, 첫 번째 요청이 커밋해도 두 번째 요청에서 이미 조회한 주문 상태는 바뀌지 않기 때문이다.

| 중지 위치 | 커밋 순서 | 최종 구매자 잔액 | 취소 반환 내역(`CANCEL_REFUND`) | 최종 주문의 취소 주체 | 첫 번째 요청의 응답에 담긴 취소 주체 |
|---|---|---|---|---|---|
| 1(주문 조회 후) | 요청 A → 요청 B | 750,000원 | +350,000원 2건. 변동 후 잔액은 각각 400,000원, 750,000원 | 판매자(`SELLER`) | 구매자(`BUYER`) |
| 1(주문 조회 후) | 요청 B → 요청 A | 750,000원 | +350,000원 2건. 변동 후 잔액은 각각 400,000원, 750,000원 | 구매자(`BUYER`) | 판매자(`SELLER`) |
| 2(지갑 조회·잔액 범위 검사 후) | 요청 A → 요청 B | 400,000원 | +350,000원 2건. 변동 후 잔액은 모두 400,000원 | 판매자(`SELLER`) | 구매자(`BUYER`) |
| 2(지갑 조회·잔액 범위 검사 후) | 요청 B → 요청 A | 400,000원 | +350,000원 2건. 변동 후 잔액은 모두 400,000원 | 구매자(`BUYER`) | 판매자(`SELLER`) |

**중지 위치 1: 결제액 중복 반환**

첫 번째 요청이 구매자 잔액을 50,000원에서 400,000원으로 변경하고 커밋한다. 이후 두 번째 요청이 재개되면, 구매자 지갑에서 조회한 잔액 400,000원에 결제액 350,000원을 다시 더한다. 따라서 최종 잔액은 750,000원이고, 취소 반환 내역은 두 건일 것으로 예상한다.

이 경우 충전·결제·취소 반환 금액을 합산한 잔액 변동 내역의 합계도 750,000원이므로, 지갑 잔액과 내역 합계를 비교하는 것만으로는 중복 반환을 발견할 수 없다. 해당 주문의 취소 반환 내역이 한 건인지, 구매자 잔액이 정상 금액인 400,000원인지 확인한다.

**중지 위치 2: 지갑 잔액과 취소 반환 내역의 불일치**

두 요청 모두 반환 전 잔액인 50,000원을 조회한 상태에서 중지된다. 재개 후에는 각자 조회해 둔 잔액에 결제액 350,000원을 더하므로, 두 요청 모두 잔액을 400,000원으로 저장할 것으로 예상한다. 두 번째 요청이 같은 금액으로 덮어쓰면서 최종 잔액에는 반환 한 번만 반영되지만, 취소 반환 내역은 두 건 남는다는 가설이다.

잔액 변동 내역을 합산하면 충전 400,000원에서 결제 350,000원을 빼고 취소 반환 350,000원을 두 번 더한 750,000원이다. 이는 예상 최종 잔액 400,000원보다 350,000원 많다. 지갑 잔액만 확인하면 정상 금액과 같으므로, 취소 반환 내역의 건수와 잔액 변동 내역 합계를 함께 확인한다.

**두 중지 위치 공통: 응답과 최종 주문의 취소 정보 불일치**

두 요청이 모두 취소 주체와 취소 사유를 기록하므로, 최종 주문에는 두 번째 요청의 취소 정보가 남을 것으로 예상한다. 반면 첫 번째 요청의 응답은 두 번째 요청을 재개하기 전에 생성되므로, 첫 번째 요청으로 기록한 취소 정보를 포함한다.

따라서 앞서 설명한 금액·내역 문제와 함께 취소 정보의 불일치도 발생할 것으로 예상한다. 첫 번째 요청의 응답 본문에 담긴 취소 주체·취소 사유를 최종 주문에 저장된 값과 비교하여 확인한다.

## 5. 정책 구성을 결정하기 위한 테스트 시나리오

지금까지의 테스트 계획은 각 동작에 대해 상태 값이 바로 직결되는 관계만 다룬다. 이 문서에서는 구매자 취소와 판매자 취소다. 이 절에는 다음 두 가지를 고려한, 실제 요청 상황을 가정한 테스트 시나리오를 쓰고, 요청이 성공하든 실패하든 그 시나리오로 실제 테스트하여 정책 구성을 결정하는 데 쓴다.

- 요청에 대한 결과가 다른 상태들 혹은 비즈니스 맥락에 영향을 미칠 범위
- 실제 이 기능들을 사용하는 수많은 요청이 발생할 수 있다는 점과, 이를 비즈니스 정책에 반영할지

시나리오의 내용과 이 명세에 쓸 범위는 아직 정하지 않았다.

## 6. 결과 확인과 기록

적용할 기준은 [작업명세 07의 3절](07_공통실행참조.md#result-sql)의 기준 1~3이다. 기준 2와 기준 3은 [작업명세 07의 SQL 3.1](07_공통실행참조.md#sql-criterion-2)과 [SQL 3.2](07_공통실행참조.md#sql-criterion-3)로 확인한다. 이 상황에는 발송 정보와 환불 요청이 없으므로 기준 4·5의 SQL은 행이 나오지 않아야 한다.

이 상황에서 확인할 값은 다음과 같다.

- 두 요청의 HTTP 응답 코드(200 또는 409 `TRADE_ALREADY_FINALIZED`)
- `PURCHASE_ORDER`의 `TRADE_STATUS`, `CANCELLED_BY`, `CANCEL_REASON`
- 구매자 `WALLET.BALANCE`
- 구매자 `BALANCE_TRANSACTION`의 `CANCEL_REFUND` 건수와 각 행의 `BALANCE_AFTER`

추가 증거로 서버 로그에서 두 요청의 주문 UPDATE가 모든 컬럼을 포함하는지와 커밋 순서를 확인한다. 보관 자료와 민감 정보 처리는 [작업명세 01의 6.3절](01_테스트계획_공통.md#result-criteria)을 따른다.
