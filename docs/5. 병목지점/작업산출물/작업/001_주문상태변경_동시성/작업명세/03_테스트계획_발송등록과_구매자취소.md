# 작업명세 03 테스트 계획: 발송 등록과 구매자 취소

- 작성일: 2026-10-13
- 작업기록: [작업기록](../작업기록.md)
- 관련 명세: [작업명세 01 테스트 계획: 공통](01_테스트계획_공통.md), [작업명세 07 공통 실행 참조](07_공통실행참조.md)

상황 S1-2의 조건, 요청, 절차, 예상 결과를 정한다. 테스트 목적, 테스트 방법, 실행 환경, 공통 결과 확인 기준은 [작업명세 01](01_테스트계획_공통.md)을 따른다.

## 1. 검증 목적과 정상 동작

구매자가 캠핑 의자를 75,000원에 구매한 뒤, 같은 상품을 선물받아 주문 취소를 요청한다. 같은 시점에 판매자는 편의점 택배 접수를 마치고 운송장 번호를 등록한다.

충돌하는 처리는 판매자의 발송 등록과 구매자의 주문 취소다. 발송 등록은 주문을 배송 중으로 바꾸고 발송 정보를 남기며, 주문 취소는 주문을 취소 완료로 바꾸고 구매자에게 결제액을 돌려준다.

**정상 동작:** 발송 등록과 주문 취소 가운데 하나만 성공한다. 발송 등록이 먼저 처리되면 주문 취소는 409 `ORDER_ALREADY_SHIPPED`로, 주문 취소가 먼저 처리되면 발송 등록은 409 `ORDER_NOT_IN_PROGRESS`로 거절된다.

## 2. 사전조건과 테스트 데이터

### 2.1 시작 상태와 금액

| 항목 | 값 |
|---|---|
| 거래 상태 | 진행 중(`IN_PROGRESS`) |
| 배송 상태 | 발송 대기(`WAITING_SHIPMENT`) |
| 상품 | 캠핑 의자, 가격 75,000원, 수량 1개. 등록 가격으로 결제 |
| 구매자 | 충전 100,000원, 결제 후 잔액 25,000원 |
| 판매자 | 충전 없음, 잔액 0원 |

### 2.2 기준 시각

| 시점 | KST | 서버 시계 설정값(UTC) |
|---|---|---|
| 사전 준비 | 2026-10-05(월) 10:00 | `2026-10-05T01:00:00Z` |
| 두 요청 전송 | 2026-10-05(월) 14:00 | `2026-10-05T05:00:00Z` |

두 요청 시각은 발송 기한(10-13 00:00 KST)보다 충분히 이르므로 기한 검사는 결과에 영향을 주지 않는다.

### 2.3 준비 순서

서버 시계를 `2026-10-05T01:00:00Z`로 설정한 뒤 다음 요청을 순서대로 보낸다.

1. 판매자와 구매자의 회원 가입과 로그인. 요청 형식은 [작업명세 07의 1절](07_공통실행참조.md#common-requests)을 따른다.
2. 판매자의 상품 등록 `POST /api/products`

   ```json
   {"name":"캠핑 의자","description":"두 번 사용했습니다. 수납 가방 포함.","category":"LIVING","price":75000,"quantity":1}
   ```

3. 구매자의 충전 `POST /api/wallet/charges`

   ```json
   {"amount":100000,"requestId":"${__UUID()}"}
   ```

4. 구매자의 결제 `POST /api/orders`

   ```json
   {"productId":${productId},"quantity":1,"recipientName":"박서준","shippingAddress":"경기도 성남시 분당구 판교역로 235","requestId":"${__UUID()}"}
   ```

## 3. 요청 A와 요청 B

서버 시계를 `2026-10-05T05:00:00Z`로 설정한 뒤 두 요청을 보낸다.

**요청 A: 판매자의 발송 등록** `POST /api/orders/${orderId}/shipment` (판매자 로그인 쿠키, `ShipmentService.register`)

```json
{"carrierName":"편의점 택배","trackingNumber":"3621-0984-4170","requestId":"${__UUID()}"}
```

**요청 B: 구매자의 주문 취소** `POST /api/orders/${orderId}/cancel` (구매자 로그인 쿠키, `OrderCancellationService.cancelByParty`)

```json
{"reason":"같은 의자를 선물받아 취소합니다."}
```

## 4. 겹침 재현 테스트

### 4.1 중지 위치

두 요청은 주문을 조회한 직후에 멈춘다. 두 요청 모두 발송 대기 상태의 주문을 조회한 뒤 멈추므로, 재개 후에는 상대 요청이 바꾼 주문 상태를 다시 보지 않는다.

| 요청 | 중지 전에 끝난 조회 | 재개 후 조회 |
|---|---|---|
| A 발송 등록 | 주문 | 발송 정보가 이미 등록되었는지 조회한다. 취소는 발송 정보를 만들지 않으므로 이 조회는 통과한다 |
| B 구매자 취소 | 주문 | 구매자 지갑. 발송 정보는 따로 조회하지 않고, 중지 전에 조회한 배송 상태로 판단한다 |

### 4.2 실행 절차

커밋 순서마다 별도의 주문으로 실행한다.

1. 2.3절의 준비 요청을 보낸다.
2. 서버의 요청 일시 중지를 켠다.
3. 서버 시계를 `2026-10-05T05:00:00Z`로 설정하고 요청 A와 요청 B를 보낸다.
4. 두 요청이 주문 조회 직후에 멈췄는지 확인한다.
5. 먼저 커밋할 요청을 재개하고, 그 요청의 커밋이 끝났는지 확인한다.
6. 나머지 요청을 재개하고 응답을 받는다.
7. 6절의 값을 확인하고 기록한다.

### 4.3 예상 결과(가설)

아래 결과는 코드 분석에서 세운 가설이며 아직 실행하지 않았다. 두 순서 모두 두 요청이 성공하고, 최종 주문 상태는 나중에 커밋된 요청이 정한다.

| 커밋 순서 | 응답 | 테스트 직후의 주문 | 발송 정보(`SHIPMENT`) | 구매자 반환(`CANCEL_REFUND`) | 위반 기준 |
|---|---|---|---|---|---|
| 요청 A(발송 등록) → 요청 B(취소) | A 201, B 200 | 취소 완료(`CANCELLED`), 배송 상태 발송 대기(`WAITING_SHIPMENT`), 취소 주체 구매자(`BUYER`) | 1행 남음 | +75,000원 1건 | 기준 1, 4 |
| 요청 B(취소) → 요청 A(발송 등록) | A 201, B 200 | 진행 중(`IN_PROGRESS`), 배송 중(`SHIPPING`). 취소 기록(`CANCELLED_BY`, `CANCEL_REASON`, `FINALIZED_AT`)이 NULL로 지워짐 | 1행 남음 | +75,000원 1건 | 기준 1, 3 |

테스트 직후의 상태와, 이후 자동 처리까지 진행했을 때 예상되는 영향은 다음과 같다. 이후 자동 처리는 이번 테스트 절차에 포함하지 않는다.

- **발송 등록이 먼저 커밋된 경우:** 테스트 직후 취소 완료된 주문에 발송 정보가 남고, 구매자는 75,000원을 돌려받는다. 이 주문은 배송 중이 아니므로 이후 모의 배송 완료와 확인 기간 만료 자동 완료의 대상이 되지 않는다. 판매자는 상품을 보냈지만 판매대금을 받지 못한다.
- **구매자 취소가 먼저 커밋된 경우:** 테스트 직후 주문은 진행 중·배송 중으로 되돌아가고 취소 기록은 지워지지만, 구매자에게 돌려준 75,000원은 남는다. 이후 발송 2분 뒤의 모의 배송 완료와, 배송 완료 48시간 뒤의 확인 기간 만료 자동 완료를 실행하면 판매자에게도 75,000원이 지급될 수 있다. 한 주문에서 구매자 반환과 판매자 지급이 함께 일어나는 경우다.

## 5. 비즈니스 정책을 결정하기 위한 테스트 시나리오

4절에서는 발송 등록과 구매자 취소가 겹칠 때 처리 순서에 따라 주문 상태와 발송 정보, 구매자 반환 내역이 어떻게 달라지는지 확인한다. 이 절에서는 실제 서비스 이용 중 발생할 수 있는 요청 상황을 가정하고, 다음 사항을 고려해 테스트 시나리오를 정한다.

- 발송 등록과 구매자 취소의 처리 결과가 다른 상태와 이후 거래 과정에 어디까지 영향을 미치는가.
- 여러 사용자가 발송 등록과 구매자 취소를 요청하는 상황에서 어떤 일이 발생할 수 있으며, 이를 비즈니스 정책에 반영할 필요가 있는가.

정한 시나리오에 따라 테스트를 실행하고, 요청의 성공 여부와 관계없이 그 결과를 비즈니스 정책을 결정하는 근거로 사용한다. 구체적인 시나리오와 이 명세에서 다룰 범위는 아직 정하지 않았다.

## 6. 결과 확인과 기록

적용할 기준은 [작업명세 01의 6절](01_테스트계획_공통.md#result-criteria)의 기준 1~4다. 기준 2~4는 [작업명세 07의 SQL 3.1~3.3](07_공통실행참조.md#result-sql)으로 확인한다. 이 상황에는 환불 요청이 없으므로 기준 5의 SQL은 행이 나오지 않아야 한다.

이 상황에서 확인할 값은 다음과 같다.

- 두 요청의 HTTP 응답 코드(발송 등록 201 또는 409 `ORDER_NOT_IN_PROGRESS`, 취소 200 또는 409 `ORDER_ALREADY_SHIPPED`)
- `PURCHASE_ORDER`의 `TRADE_STATUS`, `SHIPPING_STATUS`, `CANCELLED_BY`, `CANCEL_REASON`, `FINALIZED_AT`
- `SHIPMENT` 행의 유무
- 구매자 `BALANCE_TRANSACTION`의 `CANCEL_REFUND` 건수

추가 증거로 서버 로그에서 두 요청의 주문 UPDATE가 모든 컬럼을 포함하는지와 커밋 순서를 확인한다. 보관 자료와 민감 정보 처리는 [작업명세 01의 6.3절](01_테스트계획_공통.md#result-criteria)을 따른다.
