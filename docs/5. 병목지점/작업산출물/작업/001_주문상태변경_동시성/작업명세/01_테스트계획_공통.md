## 1. 검증 목적과 범위

이번 테스트의 목적은 코드 분석에서 도출한 정합성 문제를 재현하고, 요청의 처리 순서에 따라 어떤 결과가 나오는지 확인하는 것이다. 이 문서와 작업명세 02~06에 적은 문제 상황과 예상 결과는 테스트로 검증할 가설이며, 실제 요청과 데이터로 확인한 결과가 아니다.

S1 검증 작업은 다음 다섯 과정으로 진행한다. 이번 테스트는 첫 번째인 문제 확인 과정이다.

1. **문제 확인:** 코드 분석에서 예상한 문제가 실제로 발생하는지 확인하고, 처리 순서별 결과를 기록한다.
2. **충돌 조건 확인:** 요청 간격과 기한까지 남은 시간을 바꾸어 실제 비즈니스 상황에 가까운 조건을 구성한다. 두 요청이 모두 성공하는 요청 간격의 범위와 각 요청의 처리 시간을 측정한다.
3. **정책 결정:** 앞선 테스트 결과를 바탕으로 비즈니스 요구사항을 지킬 처리 기준을 정한다.
4. **구현:** 정한 정책을 적용할 구현 방식을 고르고 코드를 수정한다.
5. **정책 검증:** 앞선 테스트와 같은 조건으로 다시 실행하여 두 요청이 모두 성공하지 않고, 정한 정책대로 처리되는지 확인한다.

한 주문이 하나의 결과로만 끝나야 한다는 요구사항(BR-005)은 이미 정해져 있다. 정책 결정 과정에서 정하는 것은 요구사항에 정해져 있지 않은 경합 처리 기준이다.

- 먼저 성립한 요청을 인정할지, 발송 등록처럼 특정 처리를 우선할지
- 기한을 지켰는지를 요청 시작 시각으로 판단할지, 저장 시각으로 판단할지, 자동 처리에 유예 시간을 둘지

이 선택에 따라 거절되는 요청 수와 판매대금 지급·환불 확정까지 걸리는 시간이 달라진다. 문제 확인과 충돌 조건 확인의 결과로 영향을 비교하되, F-011과 F-013의 ‘먼저 성립한 처리 인정’처럼 요구사항에서 정한 기준은 그대로 따른다.

이번 테스트에서는 정책을 고르거나 코드를 수정하지 않고, 정책 결정의 근거가 될 재현 결과를 확보한다. 요청 간격, 기한까지 남은 시간, 스케줄러 실행 시점에 따른 차이는 충돌 조건 확인 과정에서 다룬다.

## 2. 주문 종료 규칙과 경합 발생 원리

### 2.1 주문의 종료 상태와 결제액 처리

결제된 주문은 배송 상태와 거래 상태를 따로 관리한다. 배송 상태는 발송 대기, 배송 중, 배송 완료 순서로 바뀐다. 결제 직후의 거래 상태는 진행 중이며, 환불 요청이 접수되면 보류로 바뀐다. 최종 거래 상태는 정상 완료, 환불 완료, 취소 완료 가운데 하나여야 한다(요구사항 BR-005).

| 최종 거래 상태 | 처리하는 경우 | 결제액 처리 |
|---|---|---|
| 취소 완료 | 구매자·판매자의 발송 전 취소, 발송 기한이 지난 미발송 주문의 자동 취소 | 구매자에게 전액 반환 |
| 정상 완료 | 구매자의 수령 확인, 배송 완료 후 48시간이 지난 주문의 자동 완료, 판매자의 환불 거절 | 판매자에게 판매대금 지급 |
| 환불 완료 | 판매자의 환불 동의, 환불 요청 접수 후 48시간 동안 응답이 없는 요청의 자동 환불 | 구매자에게 전액 반환 |

한 주문에서 결제액을 두 번 반환하거나 반환과 판매대금 지급을 모두 처리하면, 내준 금액의 합이 받은 결제액을 넘는다.

### 2.2 경합이 발생하는 처리 구조

사용자 요청과 자동 처리는 다음 순서로 주문을 처리한다.

1. 잠금 없이 주문을 조회한다.
2. 조회한 상태로 처리 조건을 검사한다. 예를 들어 주문 취소는 거래가 끝나지 않았고 배송 상태가 발송 대기인지 확인한다.
3. 조건을 충족하면 주문 상태를 바꾼다. 결제액 반환이나 판매대금 지급이 필요하면 지갑 잔액을 갱신하고 잔액 변동 내역을 기록한다.
4. 변경 내용을 DB에 반영하고 트랜잭션을 커밋한다. 주문 갱신에는 그 요청이 바꾸지 않은 항목의 값도 포함될 수 있다. 지갑에는 조회한 잔액에 반환액 또는 지급액을 더한 값을 저장한다.

주문을 조회한 뒤 다른 요청이 같은 주문을 바꿔도, 이미 조회한 주문 상태는 바뀌지 않는다. 그래서 두 요청이 바뀌기 전의 상태를 각각 조회하면 둘 다 처리 조건을 통과할 수 있다. 검증할 가설은 두 요청이 모두 성공하고, 나중에 커밋된 요청이 앞선 요청의 주문 상태를 덮어쓰는 동안 반환·지급 내역은 두 건 모두 남는다는 것이다.

일부 처리는 주문 조회 뒤 발송 정보나 환불 요청을 한 번 더 조회한다. 이 추가 조회가 상대 요청의 커밋 뒤에 실행되면, 반영된 내용을 보고 사용자 요청을 거절하거나 자동 처리를 건너뛸 수 있다. 작업명세 04~06에서는 이 조회 시점과 커밋 순서를 함께 확인한다.

### 2.3 예상되는 영향

두 요청이 모두 성공하면 다음 세 가지 문제가 생길 것으로 예상한다.

**1. 결제액이 두 번 나간다**

한 주문의 결제액을 구매자에게 두 번 돌려주거나, 구매자에게 돌려주고 판매자에게도 지급한다.

| 겹치는 처리 | 결과 |
|---|---|
| 구매자 취소와 판매자 취소 | 결제액을 두 번 돌려준다. 350,000원 주문이면 구매자 잔액이 400,000원이 아니라 750,000원이 된다 |
| 판매자의 환불 동의와 무응답 자동 환불 | 결제액을 두 번 돌려준다 |
| 판매자의 환불 거절과 무응답 자동 환불 | 판매자에게 판매대금을 지급하고, 구매자에게도 결제액을 돌려준다 |
| 취소(구매자 취소 또는 미발송 자동 취소)가 먼저 저장되고 발송 등록이 뒤에 저장됨 | 주문이 배송 중으로 되돌아가 거래가 계속된다. 이미 돌려준 결제액은 그대로 남고, 거래가 끝나면 판매자에게도 판매대금이 지급된다 |
| 확인 기간 만료 자동 완료가 먼저 저장되고 환불 요청이 뒤에 저장됨 | 판매대금을 지급한 주문이 보류로 되돌아간다. 이후 무응답 자동 환불이 실행되면 구매자에게도 결제액을 돌려준다 |

**2. 판매자가 대금을 받지 못하거나, 환불 요청이 처리되지 않는다**

결제액이 더 나가지는 않지만, 한쪽이 받아야 할 처리를 받지 못한 채 주문이 끝난다.

| 겹치는 처리 | 결과 |
|---|---|
| 발송 등록이 먼저 저장되고 취소가 뒤에 저장됨 | 주문이 취소 완료가 되어 구매자는 결제액을 돌려받는다. 판매자는 이미 상품을 보냈지만 판매대금을 받지 못한다 |
| 환불 요청이 먼저 저장되고 확인 기간 만료 자동 완료가 뒤에 저장됨 | 주문이 정상 완료되어 판매자는 판매대금을 받는다. 환불 요청은 응답 대기로 남지만, 판매자 응답과 무응답 자동 환불은 보류 중인 주문만 처리하므로 끝까지 처리되지 않는다 |

**3. 지갑 잔액과 잔액 변동 내역이 맞지 않는다**

두 요청이 같은 구매자 잔액을 조회한 뒤 각자 결제액을 더해 저장하면, 잔액에는 한 번만 반영되고 반환 내역은 두 건 남는다. 예를 들어 잔액이 50,000원인 구매자에게 두 요청이 각각 350,000원을 돌려주면, 두 요청 모두 잔액을 400,000원으로 저장한다. 구매자 취소와 판매자 취소가 겹치거나, 판매자의 환불 동의와 무응답 자동 환불이 겹칠 때 생길 수 있다.

세 경우 모두 두 사용자는 성공 응답을 받지만, 최종 주문 상태에는 나중에 저장된 처리의 결과만 남는다. 또 환불 요청이 처리되지 않는 경우처럼 잔액과 변동 내역은 맞아 잔액만으로는 드러나지 않는 문제도 있다. 그래서 잔액뿐 아니라 발송 정보, 환불 요청과 주문 상태가 서로 맞는지도 함께 확인한다.

실제로 얼마나 자주 겹치는지는 아직 측정하지 않았다. 사용자 요청끼리 겹치는 상황은 두 요청의 처리 시간이 겹쳐야 하고, 기한 직전 상황은 사용자 요청이 처리되는 짧은 순간에 30초 간격의 자동 처리가 실행되어야 한다. 이 빈도는 테스트로 측정한다.

## 4. 테스트 방법과 전체 실행 순서

### 4.1 두 가지 테스트

두 테스트는 같은 서버에 JMeter로 같은 요청을 보낸다. 차이는 서버가 두 요청의 처리를 중간에 멈추는지 여부다.

두 테스트를 함께 하는 이유는 다음과 같다. 두 요청이 겹칠 수 있는 구간은 한 요청이 처리되는 짧은 시간뿐이다. 그래서 요청을 동시에 보내기만 해서는 문제가 실제로 있는지를 확인하기 어렵다. 서버가 겹친 상태를 직접 만들어 문제가 실제로 있는지 확인하는 테스트와, 멈춤 없이 보냈을 때 얼마나 자주 겹치는지 측정하는 테스트를 함께 하여, 두 결과를 정책 결정 과정에서 비즈니스 정책을 정할 근거로 쓴다.

**겹침 재현 테스트**

두 요청이 각각 필요한 데이터를 조회했지만 아직 커밋하지 않은 지점에서 처리를 멈춘다. 한 요청을 재개하여 커밋이 끝나면 나머지 요청을 재개한다. 요청 A가 먼저 커밋되는 경우와 요청 B가 먼저 커밋되는 경우를 각각 실행한다. 상황별 중지 위치는 작업명세 02~06의 4절에 있다.

**동시 전송 반복 테스트**

JMeter에서 두 요청의 전송 시작 시점을 맞추고, 서버는 멈추지 않고 처리한다. 두 요청을 어떤 순서로 처리하고 커밋할지는 서버가 정하므로, 결과는 서버의 실제 처리 조건을 따른다. 겹침 재현 테스트를 실행하고 결과를 확인한 뒤에 하며, 실제 비즈니스 요청에 가까운 조건에서 두 요청이 모두 성공하는지 측정하여 정책 결정 과정에서 경합 처리 기준을 정할 근거로 쓴다. 반복 횟수, 요청 조건, 측정 항목, 결과를 확인하는 방법은 겹침 재현 테스트의 결과를 확인한 뒤 상황별로 정한다. S1-5는 판매자의 환불 거절과 환불 동의를 따로 실행한다.

| 항목 | 겹침 재현 테스트 | 동시 전송 반복 테스트 |
|---|---|---|
| 요청 일시 중지 | 사용 | 사용하지 않음 |
| 실행 순서 | 조회 이후의 진행과 커밋 순서를 지정 | 서버의 실제 처리 순서를 따름 |
| 실행 횟수 | 상황마다 요청 A 먼저 커밋, 요청 B 먼저 커밋을 각 1회. S1-5는 환불 거절·동의를 나누어 실행 | 겹침 재현 테스트의 결과를 확인한 뒤 상황별로 정함. S1-5는 환불 거절·동의를 따로 실행 |
| 확인 대상 | 지정한 처리 순서에서 예상한 결과가 나오는지 | 멈춤 없이 두 요청이 모두 성공하는지 |

### 4.2 테스트 위한 설정 내용

평소 서버만으로는 위 테스트를 실행할 수 없어서, 다음 기능을 테스트 기간에만 켜서 쓴다. API와 설정의 상세는 [작업명세 07의 2절](07_공통실행참조.md#test-support-api)에 있다.

- **처리 기준 시각 설정:** S1-3~S1-5의 자동 처리는 기한이 지난 주문만 처리한다. 발송 기한은 결제 다음 영업일부터 세어 다섯 번째 영업일이 끝나는 자정이고, 상품 확인 기간과 환불 응답 기간은 각각 48시간이다. 실제 기한까지 기다리지 않도록 서비스가 쓸 현재 시각을 지정한다.
- **자동 처리 수동 실행:** 평소에는 스케줄러가 30초마다 자동 처리를 실행하므로, JMeter가 사용자 요청과 같은 순간에 자동 처리를 실행시킬 수 없다. 스케줄러와 같은 서비스 메서드를 부르는 테스트 전용 API로 실행 시점을 정한다.
- **요청 일시 중지와 재개:** 겹침 재현 테스트에서 두 요청을 정한 조회 지점 뒤에 멈추고, 지정한 순서로 재개한다. 요청 A와 요청 B는 JMeter가 보내는 요청 헤더로 구분한다.

테스트 기간에는 스케줄러를 끈다. 서버 시계를 기한 뒤로 설정했을 때 정기 실행이 끼어드는 것을 막고, 자동 처리의 실행 시점을 테스트 요청으로만 정하기 위해서다.

처리 기준 시각과 HTTP 전송 시각은 다르다. 서버 시계는 서비스가 처리 조건을 검사할 때 쓰는 시각이고, JMeter가 요청을 보내는 실제 시각과는 관계없다. 서버 시계는 하나뿐이므로 사용자 요청은 서버 시계의 시각(예: 기한 0.5초 전)을 쓰고, 자동 처리는 요청 파라미터 `now`로 넘긴 시각(예: 기한 5초 뒤)을 쓴다.

### 4.3 전체 실행 순서

1. [5절](#environment)에 따라 테스트 환경을 준비한다.
2. 상황마다 겹침 재현 테스트를 실행한다.
3. 상황마다 동시 전송 반복 테스트를 실행한다.
4. 테스트가 끝나면 [5절](#environment)에 따라 서버 설정을 되돌린다.

서버 시계는 모든 요청이 함께 쓰므로 상황은 하나씩 실행한다. 서로 다른 시각을 쓰는 상황을 함께 실행하면 시각 설정이 서로 간섭한다.

## 5. 실행 환경과 준비·복구

미니PC에 배포한 서버를 대상으로 테스트한다. 서버 주소는 `http://wherehouse.it.kr:8186/ChatService/`다.

| 항목 | 실행 환경 |
|---|---|
| 테스트 서버 | 미니PC에 배포해 실행하는 ChatService 서버. 테스트 지원 기능을 포함한 빌드를 배포한다 |
| DB | 미니PC Oracle의 테스트 전용 계정 `TOYCHAT_TEST`. 테스트 기간에만 배포 서버의 DB 계정을 이 계정으로 바꿈 |
| 요청 전송 | 로컬 노트북의 JMeter |
| 결과 확인 | 사용자가 로컬 노트북의 SQL Developer에서 결과 확인 SQL을 직접 실행 |

테스트 지원 기능은 운영 코드(`src/main`)에 추가하되 테스트 설정을 켰을 때만 동작하게 한다. 외부에서 접근할 수 있는 서버에 배포하므로 테스트 기간에만 켜고, 끝나면 끈 빌드로 다시 배포한다. 컨트롤러, 서비스, 저장소, 트랜잭션과 Oracle DB는 기존 애플리케이션의 실제 구현을 쓰며, 모의 객체(`@Mock`)는 쓰지 않는다.

검증에는 Oracle 실행 결과만 쓰고, H2 실행 결과는 쓰지 않는다. DB 접속 정보와 비밀번호는 환경변수로 전달한다.

준비와 복구는 다음 순서로 한다.

1. 미니PC Oracle에 `TOYCHAT_TEST` 계정을 만들고 기존 서비스와 C2C Marketplace의 DDL을 적용한다.
2. 기존 통합 테스트를 `TOYCHAT_TEST` 계정으로 실행하여 Oracle에서 통과하는지 확인한다.
3. 테스트 지원 기능을 포함한 빌드를 미니PC에 배포한다. 테스트 설정을 켜고 DB 계정을 `TOYCHAT_TEST`로 지정하여 서버를 실행한다.
4. 테스트를 실행한다.
5. 테스트 설정을 끄고 DB 계정을 `TOYCHAT`으로 되돌린 뒤 다시 배포한다.

로그인 토큰의 만료는 서버 시계가 아니라 실제 시각을 기준으로 한다. 서버 시계를 며칠 뒤로 바꿔도 토큰 만료에는 영향이 없으며, 토큰은 실제 시간으로 1시간이 지나면 만료된다.
