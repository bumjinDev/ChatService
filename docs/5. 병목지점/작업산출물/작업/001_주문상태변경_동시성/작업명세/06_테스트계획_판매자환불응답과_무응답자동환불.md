# 작업명세 06 테스트 계획: 판매자 환불 응답과 무응답 자동 환불

- 작성일: 2026-10-13
- 작업기록: [작업기록](../작업기록.md)
- 관련 명세: [작업명세 01 테스트 계획: 공통](01_테스트계획_공통.md), [작업명세 07 공통 실행 참조](07_공통실행참조.md)

상황 S1-5의 조건, 요청, 절차, 예상 결과를 정한다. 테스트 목적, 테스트 방법, 실행 환경, 공통 결과 확인 기준은 [작업명세 01](01_테스트계획_공통.md)을 따른다.

## 1. 검증 목적과 정상 동작

구매자가 85,000원에 구매한 키보드의 환불을 요청한 상황이다. 판매자가 응답 기한 직전에 환불 거절 또는 동의를 보내고, 그 요청이 처리되는 동안 무응답 자동 환불이 실행된다. 무응답 자동 환불은 환불 요청 접수 후 48시간 동안 판매자가 응답하지 않은 요청을 자동 승인하고 결제액 전액을 구매자에게 돌려준다.

충돌하는 처리는 판매자의 환불 응답과 무응답 자동 환불이다. 판매자 응답은 두 가지로 나누어 따로 실행한다.

- **환불 거절:** 주문을 정상 완료로 바꾸고 판매자에게 판매대금을 지급한다.
- **환불 동의:** 주문을 환불 완료로 바꾸고 구매자에게 결제액 전액을 돌려준다.

두 처리는 조회 순서가 다르다. 판매자 응답은 주문을 먼저 조회한 뒤 환불 요청을 조회하여 응답 대기인지 확인한다. 무응답 자동 환불은 환불 요청을 먼저 조회한 뒤 주문을 조회한다. 판매자 응답은 주문 행을 먼저, 자동 환불은 환불 요청 행을 먼저 갱신할 것으로 예상한다. 두 요청의 갱신이 겹치면 서로 상대가 잠근 행을 기다리는 교착 상태가 생겨, Oracle이 한 요청을 실패시킬 수 있다(갱신 순서는 실행 로그로 확인한다).

**정상 동작:** 판매자 응답과 무응답 자동 환불 가운데 하나만 성공한다. 자동 환불이 먼저 처리되면 판매자 응답은 409 `REFUND_ALREADY_DECIDED`로 거절되고, 판매자 응답이 먼저 처리되면 자동 환불은 이 환불 요청을 처리 대상에서 제외한다.

## 2. 사전조건과 테스트 데이터

### 2.1 시작 상태와 금액

환불 거절과 환불 동의는 각각 별도의 회원, 상품, 주문을 만들어 실행한다.

| 항목 | 값 |
|---|---|
| 거래 상태 | 보류(`ON_HOLD`). 준비 순서의 환불 요청으로 만든다 |
| 배송 상태 | 배송 완료(`DELIVERED`) |
| 환불 요청 | 응답 대기(`PENDING`) |
| 상품 | 키보드, 가격 85,000원, 수량 1개. 등록 가격으로 결제 |
| 구매자 | 충전 100,000원, 결제 후 잔액 15,000원 |
| 판매자 | 충전 없음, 잔액 0원 |

### 2.2 기준 시각

아래 날짜는 모두 2026년이다. 요청 A와 요청 B의 시각은 서비스가 처리 조건을 검사할 때 쓰는 처리 기준 시각이며, JMeter가 HTTP 요청을 보내는 실제 시각과는 관계없다.

| 시점 | KST | API에 넣는 값(UTC) |
|---|---|---|
| 사전 준비(결제, 발송 등록) | 10-05(월) 10:00 | 서버 시계 `2026-10-05T01:00:00Z` |
| 모의 배송 완료 | 10-05(월) 10:02. 확인 기한은 10-07(수) 10:02 | 파라미터 `now=2026-10-05T01:02:00Z` |
| 환불 요청 | 10-06(화) 10:00 | 서버 시계 `2026-10-06T01:00:00Z` |
| 판매자 응답 기한 | 10-08(목) 10:00. 접수 시각에 48시간을 더한 값 | 서버가 `REFUND_REQUEST.RESPONSE_DEADLINE_AT`에 저장. 예상값 `2026-10-08T01:00:00Z` |
| 요청 A(판매자 응답) | 10-08(목) 09:59:59.500. 판매자 응답 기한 0.5초 전 | 서버 시계 `2026-10-08T00:59:59.500Z` |
| 요청 B(무응답 자동 환불) | 10-08(목) 10:00:05. 판매자 응답 기한 5초 뒤 | 파라미터 `now=2026-10-08T01:00:05Z` |

### 2.3 준비 순서

서버 시계를 `2026-10-05T01:00:00Z`로 설정한 뒤 다음 요청을 순서대로 보낸다.

1. 판매자와 구매자의 회원 가입과 로그인. 요청 형식은 [작업명세 07의 1절](07_공통실행참조.md#common-requests)을 따른다.
2. 판매자의 상품 등록 `POST /api/products`

   ```json
   {"name":"키보드","description":"6개월 사용했습니다. 충전 케이블 포함.","category":"ELECTRONICS","price":85000,"quantity":1}
   ```

3. 구매자의 충전 `POST /api/wallet/charges`

   ```json
   {"amount":100000,"requestId":"${__UUID()}"}
   ```

4. 구매자의 결제 `POST /api/orders`

   ```json
   {"productId":${productId},"quantity":1,"recipientName":"정민재","shippingAddress":"인천광역시 연수구 컨벤시아대로 165","requestId":"${__UUID()}"}
   ```

5. 판매자의 발송 등록 `POST /api/orders/${orderId}/shipment`

   ```json
   {"carrierName":"한빛택배","trackingNumber":"7741-0026-5530","requestId":"${__UUID()}"}
   ```

6. 모의 배송 완료 `POST /test-support/jobs/delivery-complete?now=2026-10-05T01:02:00Z`
7. 서버 시계를 `2026-10-06T01:00:00Z`로 설정한 뒤 구매자의 환불 요청 `POST /api/orders/${orderId}/refund-request`

   ```json
   {"reasonCode":"DESCRIPTION_MISMATCH","detail":"키가 들떠 있고 스페이스바가 잘 눌리지 않습니다.","requestId":"${__UUID()}"}
   ```

## 3. 요청 A와 요청 B

서버 시계를 `2026-10-08T00:59:59.500Z`(판매자 응답 기한 0.5초 전)로 설정한 뒤 두 요청을 보낸다. 요청 A는 서버 시계의 시각으로, 요청 B는 `now`로 넘긴 시각으로 처리된다.

**요청 A: 판매자의 환불 응답** (판매자 로그인 쿠키, 본문 없음)

| 판매자 응답 | 메서드·경로 | 서비스 메서드 |
|---|---|---|
| 환불 거절 | `POST /api/orders/${orderId}/refund-request/reject` | `RefundService.respond`(`approve=false`) |
| 환불 동의 | `POST /api/orders/${orderId}/refund-request/approve` | `RefundService.respond`(`approve=true`) |

**요청 B: 무응답 자동 환불** `POST /test-support/jobs/refund-auto-approve?now=2026-10-08T01:00:05Z` (JMeter, `RefundService.autoApproveExpired`)

본문은 없다. API 형식은 [작업명세 07의 2.2절](07_공통실행참조.md#test-support-api)을 따른다.

## 4. 겹침 재현 테스트

### 4.1 중지 위치

두 요청은 중지 전에 끝낸 조회가 다르다. 판매자 응답은 주문만 조회한 상태에서 멈추고, 무응답 자동 환불은 환불 요청과 주문을 모두 조회한 뒤 멈춘다. 이 차이로 커밋 순서에 따라 결과가 달라질 것으로 예상한다.

| 요청 | 중지 전에 끝난 조회 | 재개 후 조회 |
|---|---|---|
| A 판매자 응답 | 주문 | 환불 요청이 응답 대기인지 조회. 조건을 충족하면 거절은 판매자 지갑, 동의는 구매자 지갑을 조회 |
| B 무응답 자동 환불 | 환불 요청(응답 대기), 주문(보류) | 구매자 지갑 |

### 4.2 실행 절차

판매자 응답(거절, 동의)과 커밋 순서마다 별도의 주문으로 실행한다.

1. 2.3절의 준비 요청을 보낸다.
2. 서버의 요청 일시 중지를 켠다.
3. 서버 시계를 `2026-10-08T00:59:59.500Z`로 설정하고 요청 A(거절 또는 동의)와 요청 B를 보낸다.
4. 요청 A는 주문 조회 뒤 환불 요청 조회 전에, 요청 B는 환불 요청과 주문을 모두 조회한 뒤에 멈췄는지 확인한다.
5. 먼저 커밋할 요청을 재개하고, 그 요청의 커밋이 끝났는지 확인한다.
6. 나머지 요청을 재개하고 응답을 받는다.
7. 6절의 값을 확인하고 기록한다.

### 4.3 예상 결과(가설)

아래 결과는 코드 분석에서 세운 가설이며 아직 실행하지 않았다.

| 커밋 순서 | 판매자 응답 | 응답 | 최종 주문 / 환불 요청 | 반환·지급 내역 | 위반 기준 |
|---|---|---|---|---|---|
| 요청 A → 요청 B | 환불 거절 | A 200, B `{"processed": 1}` | 환불 완료(`REFUNDED`), 완료 사유 NULL / 자동 승인(`AUTO_APPROVED`) | 판매자 `SALE_PAYOUT` +85,000원 1건, 구매자 `REFUND` +85,000원 1건 | 기준 1, 3 |
| 요청 A → 요청 B | 환불 동의 | A 200, B `{"processed": 1}` | 환불 완료(`REFUNDED`) / 자동 승인(`AUTO_APPROVED`) | 구매자 `REFUND` +85,000원 2건. 변동 후 잔액 100,000원, 185,000원 | 기준 1, 3 |
| 요청 B → 요청 A | 거절·동의 | A 409 `REFUND_ALREADY_DECIDED`, B `{"processed": 1}` | 환불 완료(`REFUNDED`) / 자동 승인(`AUTO_APPROVED`) | 구매자 `REFUND` +85,000원 1건 | 없음 |

판매자 응답이 먼저 커밋되어도, 자동 환불은 중지 전에 조회한 응답 대기 환불 요청과 보류 주문을 기준으로 처리를 계속할 것으로 예상한다. 판매자 응답의 종류에 따라 결과가 다르다.

- **환불 거절:** 판매자 지갑에는 판매대금이 지급되고 구매자 지갑에는 결제액이 반환된다. 판매자는 거절이 처리됐다는 성공 응답을 받지만, 자동 환불이 나중에 커밋되므로 최종 거래 상태는 환불 완료가 된다.
- **환불 동의:** 자동 환불이 판매자 동의의 커밋 뒤에 구매자 지갑을 조회한다. 이미 반환액이 반영된 100,000원에 85,000원을 더하므로 최종 잔액은 185,000원이 된다.

자동 환불이 먼저 커밋되면, 판매자 응답은 재개 후 자동 승인된 환불 요청을 조회하므로 거절과 동의 모두 거절될 것으로 예상한다. 정상 동작과 같은 결과다.

## 6. 결과 확인과 기록

적용할 기준은 [작업명세 01의 6절](01_테스트계획_공통.md#result-criteria)의 기준 1~3과 기준 5다. 요청 A는 HTTP 2xx 응답을, 요청 B는 처리 건수 1을 성공으로 본다. 기준 2·3·5는 [작업명세 07의 SQL 3.1, 3.2, 3.4](07_공통실행참조.md#result-sql)로 확인한다.

이 상황에서 확인할 값은 다음과 같다.

- 요청 A의 HTTP 응답 코드(200, 409 `REFUND_ALREADY_DECIDED` 또는 500)와 요청 B의 처리 건수
- `PURCHASE_ORDER`의 `TRADE_STATUS`, `COMPLETION_CAUSE`
- `REFUND_REQUEST`의 `DECISION`, `RESPONSE_DEADLINE_AT`
- 판매자 `BALANCE_TRANSACTION`의 `SALE_PAYOUT` 건수, 구매자 `BALANCE_TRANSACTION`의 `REFUND` 건수와 각 행의 `BALANCE_AFTER`
- 구매자 `WALLET.BALANCE`

추가 증거로 서버 로그에서 두 요청이 주문과 환불 요청을 갱신한 순서, 교착 상태(ORA-00060) 발생 여부, 두 요청의 커밋 순서를 확인한다. 보관 자료와 민감 정보 처리는 [작업명세 01의 6.3절](01_테스트계획_공통.md#result-criteria)을 따른다.
