# 작업명세 04 테스트 계획: 발송 등록과 미발송 자동 취소

- 작성일: 2026-10-13
- 작업기록: [작업기록](../작업기록.md)
- 관련 명세: [작업명세 01 테스트 계획: 공통](01_테스트계획_공통.md), [작업명세 07 공통 실행 참조](07_공통실행참조.md)

상황 S1-3의 조건, 요청, 절차, 예상 결과를 정한다. 테스트 목적, 테스트 방법, 실행 환경, 공통 결과 확인 기준은 [작업명세 01](01_테스트계획_공통.md)을 따른다.

## 1. 검증 목적과 정상 동작

월요일에 결제한 주문의 발송 기한은 다음 주 화요일 00:00이다. 판매자가 기한 직전에 발송 등록을 시작하고, 그 요청이 끝나기 전에 자정이 지난 뒤의 미발송 자동 취소가 같은 주문을 처리하는 상황을 재현한다.

충돌하는 처리는 판매자의 발송 등록과 미발송 자동 취소다. 이 상황을 이해하려면 두 처리의 시점을 알아야 한다.

- **발송 등록의 기한 검사:** 서비스 메서드가 시작될 때 조회한 시각을 쓴다. 예를 들어 기준 시각이 23:59:59라면 커밋이 00:00:00.05에 끝나도 기한 검사를 통과한다. 기한 검사에 쓰는 시각과 변경 내용이 확정되는 커밋 시점은 다르다.
- **미발송 자동 취소의 추가 조회:** 주문을 조회한 뒤 그 주문의 발송 정보가 있는지 한 번 더 조회한다. 이 조회가 발송 등록의 커밋 뒤에 실행되면 발송 정보를 보고 취소를 건너뛴다.

**정상 동작:** 두 처리 가운데 하나만 성공한다. 자동 취소가 먼저 처리되면 발송 등록은 409 `ORDER_NOT_IN_PROGRESS`로 거절되고, 발송 등록이 먼저 처리되면 자동 취소는 이 주문을 처리 대상에서 제외한다.

## 2. 사전조건과 테스트 데이터

### 2.1 시작 상태와 금액

| 항목 | 값 |
|---|---|
| 거래 상태 | 진행 중(`IN_PROGRESS`) |
| 배송 상태 | 발송 대기(`WAITING_SHIPMENT`) |
| 상품 | 닌텐도 스위치, 가격 290,000원, 수량 1개. 등록 가격으로 결제 |
| 구매자 | 충전 300,000원, 결제 후 잔액 10,000원 |
| 판매자 | 충전 없음, 잔액 0원 |

### 2.2 기준 시각

아래 날짜는 모두 2026년이다. 요청 A와 요청 B의 시각은 서비스가 처리 조건을 검사할 때 쓰는 처리 기준 시각이며, JMeter가 HTTP 요청을 보내는 실제 시각과는 관계없다.

| 시점 | KST | API에 넣는 값(UTC) |
|---|---|---|
| 사전 준비 | 10-05(월) 10:00 | 서버 시계 `2026-10-05T01:00:00Z` |
| 발송 기한 | 10-13(화) 00:00 | 서버가 결제 시각으로 계산해 `PURCHASE_ORDER.SHIP_DEADLINE_AT`에 저장. 예상값 `2026-10-12T15:00:00Z` |
| 요청 A(발송 등록) | 10-12(월) 23:59:59.500. 발송 기한 0.5초 전 | 서버 시계 `2026-10-12T14:59:59.500Z` |
| 요청 B(미발송 자동 취소) | 10-13(화) 00:00:05. 발송 기한 5초 뒤 | 파라미터 `now=2026-10-12T15:00:05Z` |

### 2.3 준비 순서

서버 시계를 `2026-10-05T01:00:00Z`로 설정한 뒤 다음 요청을 순서대로 보낸다.

1. 판매자와 구매자의 회원 가입과 로그인. 요청 형식은 [작업명세 07의 1절](07_공통실행참조.md#common-requests)을 따른다.
2. 판매자의 상품 등록 `POST /api/products`

   ```json
   {"name":"닌텐도 스위치","description":"작년 봄 구매. 독과 조이콘 포함.","category":"ELECTRONICS","price":290000,"quantity":1}
   ```

3. 구매자의 충전 `POST /api/wallet/charges`

   ```json
   {"amount":300000,"requestId":"${__UUID()}"}
   ```

4. 구매자의 결제 `POST /api/orders`

   ```json
   {"productId":${productId},"quantity":1,"recipientName":"이도윤","shippingAddress":"부산광역시 해운대구 센텀중앙로 79","requestId":"${__UUID()}"}
   ```

## 3. 요청 A와 요청 B

서버 시계를 `2026-10-12T14:59:59.500Z`(발송 기한 0.5초 전)로 설정한 뒤 두 요청을 보낸다. 요청 A는 서버 시계의 시각으로, 요청 B는 `now`로 넘긴 시각으로 처리된다.

**요청 A: 판매자의 발송 등록** `POST /api/orders/${orderId}/shipment` (판매자 로그인 쿠키, `ShipmentService.register`)

```json
{"carrierName":"편의점 택배","trackingNumber":"3621-0984-4171","requestId":"${__UUID()}"}
```

**요청 B: 미발송 자동 취소** `POST /test-support/jobs/unshipped-cancel?now=2026-10-12T15:00:05Z` (JMeter, `OrderCancellationService.cancelExpiredUnshipped`)

본문은 없다. API 형식은 [작업명세 07의 2.2절](07_공통실행참조.md#test-support-api)을 따른다.

## 4. 겹침 재현 테스트

### 4.1 중지 위치

두 요청의 중지 위치가 다르다. 자동 취소는 발송 정보를 조회하기 전에 멈추므로, 재개 후의 발송 정보 조회가 발송 등록의 커밋 전인지 뒤인지에 따라 결과가 갈린다.

| 요청 | 중지 전에 끝난 조회 | 재개 후 조회 |
|---|---|---|
| A 발송 등록 | 주문 | 발송 정보가 이미 등록되었는지 조회 |
| B 미발송 자동 취소 | 주문 | 발송 정보가 있는지 조회. 없으면 취소를 진행하며 구매자 지갑을 조회 |

### 4.2 실행 절차

커밋 순서마다 별도의 주문으로 실행한다.

1. 2.3절의 준비 요청을 보낸다.
2. 서버의 요청 일시 중지를 켠다.
3. 서버 시계를 `2026-10-12T14:59:59.500Z`로 설정하고 요청 A와 요청 B를 보낸다.
4. 요청 A는 주문 조회 직후에, 요청 B는 주문 조회 뒤 발송 정보 조회 전에 멈췄는지 확인한다.
5. 먼저 커밋할 요청을 재개하고, 그 요청의 커밋이 끝났는지 확인한다.
6. 나머지 요청을 재개하고 응답을 받는다.
7. 6절의 값을 확인하고 기록한다.

### 4.3 예상 결과(가설)

아래 결과는 코드 분석에서 세운 가설이며 아직 실행하지 않았다.

| 커밋 순서 | 응답 | 테스트 직후의 주문 | 발송 정보(`SHIPMENT`) | 구매자 반환(`CANCEL_REFUND`) | 위반 기준 |
|---|---|---|---|---|---|
| 요청 A(발송 등록) → 요청 B(자동 취소) | A 201, B `{"processed": 0}` | 진행 중(`IN_PROGRESS`), 배송 중(`SHIPPING`) | 1행 | 없음 | 없음 |
| 요청 B(자동 취소) → 요청 A(발송 등록) | A 201, B `{"processed": 1}` | 진행 중(`IN_PROGRESS`), 배송 중(`SHIPPING`). 자동 취소 기록(`CANCELLED_BY`, `CANCEL_REASON`, `FINALIZED_AT`)이 NULL로 지워짐 | 1행 | +290,000원 1건 | 기준 1, 3 |

- **발송 등록이 먼저 커밋된 경우:** 자동 취소는 재개 후 발송 정보를 조회하므로, 이미 등록된 발송 정보를 보고 취소를 건너뛸 것으로 예상한다. 정상 동작과 같은 결과다.
- **자동 취소가 먼저 커밋된 경우:** 발송 등록은 중지 전에 조회한 진행 중 주문으로 처리를 계속하여, 주문을 진행 중·배송 중으로 되돌린다. 테스트 직후 구매자에게 돌려준 290,000원은 남아 있다. 이후 모의 배송 완료와 확인 기간 만료 자동 완료를 실행하면 판매자에게도 290,000원이 지급될 수 있다. 이후 자동 처리는 이번 테스트 절차에 포함하지 않으며, [작업명세 03](03_테스트계획_발송등록과_구매자취소.md)에서 구매자 취소가 먼저 커밋된 경우와 같은 문제다.

## 6. 결과 확인과 기록

적용할 기준은 [작업명세 01의 6절](01_테스트계획_공통.md#result-criteria)의 기준 1~4다. 요청 A는 HTTP 2xx 응답을, 요청 B는 처리 건수 1을 성공으로 본다. 기준 2~4는 [작업명세 07의 SQL 3.1~3.3](07_공통실행참조.md#result-sql)으로 확인한다. 이 상황에는 환불 요청이 없으므로 기준 5의 SQL은 행이 나오지 않아야 한다.

이 상황에서 확인할 값은 다음과 같다.

- 요청 A의 HTTP 응답 코드(201 또는 409 `ORDER_NOT_IN_PROGRESS`)와 요청 B의 처리 건수
- `PURCHASE_ORDER`의 `TRADE_STATUS`, `SHIPPING_STATUS`, `CANCELLED_BY`, `CANCEL_REASON`, `FINALIZED_AT`, `SHIP_DEADLINE_AT`
- `SHIPMENT` 행의 유무
- 구매자 `BALANCE_TRANSACTION`의 `CANCEL_REFUND` 건수

추가 증거로 서버 로그에서 자동 취소의 발송 정보 조회가 발송 등록의 커밋 전에 실행됐는지 뒤에 실행됐는지, 주문 UPDATE가 모든 컬럼을 포함하는지, 두 요청의 커밋 순서를 확인한다. 보관 자료와 민감 정보 처리는 [작업명세 01의 6.3절](01_테스트계획_공통.md#result-criteria)을 따른다.
