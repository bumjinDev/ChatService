# 작업명세 04 테스트 계획: 발송 등록과 미발송 자동 취소

- 작성일: 2026-10-13
- 작업기록: [작업기록](../작업기록.md)
- 관련 명세: [작업명세 01 테스트 계획: 공통](01_테스트계획_공통.md), [작업명세 07 공통 실행 참조](07_공통실행참조.md)

상황 S1-3의 조건, 요청, 절차, 예상 결과를 정한다. 테스트 목적, 테스트 방법, 실행 환경, 공통 결과 확인 기준은 [작업명세 01](01_테스트계획_공통.md)을 따른다.

## 1. 검증 목적과 정상 동작

월요일에 결제한 주문의 발송 기한은 다음 주 화요일 00:00이다. 판매자가 기한 직전에 발송 등록을 시작하고, 그 요청이 끝나기 전에 발송 기한이 지난 뒤 실행된 미발송 자동 취소가 같은 주문을 처리하는 상황을 재현한다.

충돌하는 처리는 판매자의 발송 등록과 미발송 자동 취소다. 두 처리의 결과는 다음 두 가지에 따라 달라진다.

- **발송 등록의 기한 검사:** 발송 등록은 서비스 메서드가 시작될 때 구한 현재 시각으로 발송 기한을 검사한다. 예를 들어 이 시각이 23:59:59라면 커밋이 00:00:00.05에 끝나도 기한 검사를 통과한다. 기한 검사에 쓰는 시각과 변경 내용이 확정되는 커밋 시점은 다르다.
- **미발송 자동 취소의 추가 조회:** 미발송 자동 취소는 주문을 조회한 뒤 그 주문의 발송 정보가 있는지 한 번 더 조회한다. 이 조회가 발송 등록의 커밋 뒤에 실행되면 발송 등록이 저장한 발송 정보가 조회되어 주문을 취소하지 않는다. 커밋 전에 실행되면 발송 정보가 조회되지 않으므로 취소를 진행한다.

**정상 동작:** 두 처리 가운데 하나만 성공한다. 미발송 자동 취소가 먼저 처리되면 발송 등록은 409 `ORDER_NOT_IN_PROGRESS`로 거절되고, 발송 등록이 먼저 처리되면 미발송 자동 취소는 이 주문을 처리 대상에서 제외한다.

## 2. 사전조건과 테스트 데이터

### 2.1 시작 상태와 금액

| 항목 | 값 |
|---|---|
| 거래 상태 | 진행 중(`IN_PROGRESS`) |
| 배송 상태 | 발송 대기(`WAITING_SHIPMENT`) |
| 상품 | 닌텐도 스위치, 가격 290,000원, 수량 1개. 등록 가격으로 결제 |
| 구매자 | 충전 300,000원, 결제 후 잔액 10,000원 |
| 판매자 | 충전 없음, 잔액 0원 |

### 2.2 기준 시각

아래 날짜는 모두 2026년이다. 요청 A와 요청 B의 시각은 서비스가 처리 조건을 검사할 때 쓰는 처리 기준 시각이며, JMeter가 HTTP 요청을 보내는 실제 시각과는 관계없다.

| 시점 | KST | API에 넣는 값(UTC) |
|---|---|---|
| 사전 준비 | 10-05(월) 10:00 | 서버 시계 `2026-10-05T01:00:00Z` |
| 발송 기한 | 10-13(화) 00:00 | 서버가 결제 시각으로 계산해 `PURCHASE_ORDER.SHIP_DEADLINE_AT`에 저장. 예상값 `2026-10-12T15:00:00Z` |
| 요청 A(발송 등록) | 10-12(월) 23:59:59.500. 발송 기한 0.5초 전 | 서버 시계 `2026-10-12T14:59:59.500Z` |
| 요청 B(미발송 자동 취소) | 10-13(화) 00:00:05. 발송 기한 5초 뒤 | 파라미터 `now=2026-10-12T15:00:05Z` |

### 2.3 준비 순서

서버 시계를 `2026-10-05T01:00:00Z`로 설정한 뒤(`PUT /test-support/clock`) 다음 요청을 순서대로 보낸다.

1. 판매자와 구매자가 회원 가입하고 로그인한다. 요청 형식은 [작업명세 07의 「1. 공통 요청 형식」](07_공통실행참조.md#common-requests)을 따른다.
2. 판매자가 상품을 등록한다(`POST /api/products`).

   ```json
   {"name":"닌텐도 스위치","description":"작년 봄 구매. 독과 조이콘 포함.","category":"ELECTRONICS","price":290000,"quantity":1}
   ```

3. 구매자가 300,000원을 충전한다(`POST /api/wallet/charges`).

   ```json
   {"amount":300000,"requestId":"${__UUID()}"}
   ```

4. 구매자가 등록 가격으로 결제한다(`POST /api/orders`).

   ```json
   {"productId":${productId},"quantity":1,"recipientName":"이도윤","shippingAddress":"부산광역시 해운대구 센텀중앙로 79","requestId":"${__UUID()}"}
   ```

## 3. 요청 A와 요청 B

서버 시계를 `2026-10-12T14:59:59.500Z`(발송 기한 0.5초 전)로 설정한 뒤 두 요청을 보낸다. 요청 A는 서버 시계의 시각으로, 요청 B는 `now`에 넣은 시각으로 처리된다.

**요청 A: 판매자의 발송 등록** `POST /api/orders/${orderId}/shipment` (판매자 로그인 쿠키, `ShipmentService.register`)

```json
{"carrierName":"편의점 택배","trackingNumber":"3621-0984-4171","requestId":"${__UUID()}"}
```

**요청 B: 미발송 자동 취소** `POST /test-support/jobs/unshipped-cancel?now=2026-10-12T15:00:05Z` (로그인 쿠키 없음, `OrderCancellationService.cancelExpiredUnshipped`)

본문은 없다. API 형식은 [작업명세 07의 「2.2 자동 처리 실행 API와 처리 기준 시각 설정 API」](07_공통실행참조.md#test-support-api)를 따른다.

## 4. 겹침 재현 테스트

### 4.1 중지 위치

요청 A는 주문을 조회한 직후에 멈춘다. 요청 B가 멈출 수 있는 위치는 두 곳이며, 어느 위치에서 멈추느냐에 따라 요청 B의 발송 정보 조회가 멈추기 전에 끝나는지 재개된 뒤에 실행되는지가 정해진다. 중지 위치는 요청 헤더 `X-Test-Pause-At`으로 지정한다([작업명세 07의 「2.3 요청 일시 중지」](07_공통실행참조.md#request-pause)).

| 요청 | 중지 위치 | 멈추기 전에 끝나는 조회 | 재개된 뒤의 처리 |
|---|---|---|---|
| A 발송 등록 | 주문 조회 직후(`ORDER_READ`) | 주문 | 판매자인지와 거래가 끝나지 않았는지 검사하고, 발송 정보를 조회하고, 발송 기한 전인지 검사한 뒤 발송 정보를 저장하고 주문을 배송 중으로 바꾼다 |
| B 미발송 자동 취소 | 주문 조회 직후, 발송 정보 조회 전 | 대상 주문의 ID 목록, 주문 | 거래 상태·배송 상태·발송 기한을 검사하고 발송 정보를 조회한 뒤, 발송 정보가 없으면 주문을 취소한다 |
| B 미발송 자동 취소 | 구매자 지갑 조회 직후(`WALLET_READ`) | 대상 주문의 ID 목록, 주문, 발송 정보, 구매자 지갑 | 발송 정보를 다시 조회하지 않고 주문을 취소한다 |

요청 B의 「주문 조회 직후, 발송 정보 조회 전」 위치는 지금 코드에 없다.

### 4.2 실행 절차

테스트케이스는 요청 B의 중지 위치와 먼저 재개할 요청을 바꾸어 세 개로 정한다. 요청 A는 모든 테스트케이스에서 주문을 조회한 직후에 멈춘다.

| 테스트케이스 | 요청 B의 중지 위치 | 먼저 재개할 요청 | 실행 여부 |
|---|---|---|---|
| 테스트케이스1 | 주문 조회 직후, 발송 정보 조회 전 | 요청 A(발송 등록) | 실행하지 않는다 |
| 테스트케이스2 | 구매자 지갑 조회 직후(`WALLET_READ`) | 요청 B(미발송 자동 취소) | 실행한다 |
| 테스트케이스3 | 구매자 지갑 조회 직후(`WALLET_READ`) | 요청 A(발송 등록) | 실행한다 |

테스트케이스1과 3은 모두 요청 A를 먼저 재개하며, 요청 B의 중지 위치만 다르다. 테스트케이스1에서는 요청 B가 요청 A의 커밋 뒤에 발송 정보를 조회하고, 테스트케이스3에서는 요청 A가 발송 정보를 저장하기 전에 조회한다. 테스트케이스2는 요청 B를 먼저 재개하는데, 이때 요청 A는 발송 정보를 저장하기 전에 멈춰 있다. 그래서 요청 B가 두 위치 가운데 어디에서 멈춰도 발송 정보는 조회되지 않는다. 테스트케이스2가 이미 코드에 있는 `WALLET_READ` 위치를 쓰는 것은 이 때문이다.

테스트케이스1을 실행하지 않는 이유는, 코드 분석으로 예상한 결과(「4.3」)가 정상 동작과 같아 문제 확인 과정에서 재현할 문제가 없기 때문이다. 그래서 요청 B의 발송 정보 조회가 요청 A의 커밋 뒤에 실행될 때 요청 B가 주문을 취소하지 않는다는 것은 코드로만 확인한다. 테스트케이스1에서 쓰는 요청 B의 중지 위치(「4.1」)도 코드에 두지 않는다.

테스트케이스2와 3은 각각 별도의 주문으로 다음 순서에 따라 실행한다. 먼저 재개한 요청의 응답을 받은 뒤 나머지 요청을 재개하여 커밋 순서를 정한다. 테스트케이스2는 9번 단계 뒤에 이후 자동 처리를 이어서 실행한다(「4.2.3」).

1. 「2.3 준비 순서」에 따라 테스트 데이터를 준비한다.
2. 요청 B의 대상이 될 다른 주문이 없는지 확인한다. 미발송 자동 취소는 진행 중·발송 대기이고 발송 기한이 `now` 이하인 주문을 모두 처리하므로, 대상은 이번 테스트케이스의 주문 하나여야 한다.
3. 서버 시계를 `2026-10-12T14:59:59.500Z`로 설정한다(`PUT /test-support/clock`).
4. 요청 A와 요청 B를 보낸다.
5. 두 요청이 정한 위치에서 모두 멈췄는지 확인한다.
6. 먼저 재개할 요청을 재개하고 응답을 기다린다. 요청 A의 응답은 서버가 트랜잭션을 커밋한 뒤 주문을 다시 조회해 만들고, 요청 B의 응답은 서버가 주문마다 연 트랜잭션을 커밋한 뒤 처리 건수를 담아 보낸다. 그래서 응답을 받으면 그 요청의 커밋이 끝난 것이다.
7. 나머지 요청을 재개하고 응답을 기다린다.
8. 서버 시계를 시스템 시각으로 되돌린다(`DELETE /test-support/clock`). 서버 시계에 설정한 시각은 그 서버가 처리하는 모든 요청에 적용되기 때문이다.
9. 요청 A의 HTTP 응답 코드와 요청 B의 처리 건수를 기록하고, 「6. 결과 확인과 기록」의 값을 확인해 기록한다.

테스트케이스마다 JMeter 스레드 세 개가 동시에 시작한다. 스레드 1은 요청 A를, 스레드 2는 요청 B를 보내고, 스레드 3은 위 5~7번 단계(멈춤 확인과 재개)를 맡는다. 아래에서는 스레드 3을 재개 제어라고 부른다.

나중에 재개되는 요청은 처음부터 다시 처리하지 않고, 멈추기 전에 조회해 둔 주문으로 이어서 처리한다. 그래서 먼저 재개된 요청이 주문을 바꾸고 커밋한 뒤에도, 나중에 재개된 요청은 그 변경이 반영되지 않은 주문으로 처리를 계속한다. 반면 발송 정보는 조회할 때마다 DB에서 새로 읽는다. 테스트케이스별 처리 순서는 다음과 같다.

#### 4.2.3 테스트케이스2의 이후 자동 처리

테스트케이스2를 마친 주문은 진행 중·배송 중이고, 미발송 자동 취소가 구매자에게 반환한 결제액이 남아 있다(「4.3」). 이 주문에 모의 배송 완료와 확인 기간 만료 자동 완료를 이어서 실행해, 판매자에게도 판매대금이 지급되는지 확인한다.

두 자동 처리는 조건에 맞는 주문을 모두 처리한다. 그래서 대상이 테스트케이스2의 주문 하나일 때, 곧 「4.2」의 9번 단계를 마친 뒤 테스트케이스3을 실행하기 전에 실행한다. 모의 배송 완료의 `now`에는 요청 A가 저장하는 모의 배송 완료 예정 시각보다 뒤의 시각을 넣어야 한다. 이 예정 시각은 발송 시각 `2026-10-12T14:59:59.500Z`의 2분 뒤인 `2026-10-12T15:01:59.500Z`이다. API 형식은 [작업명세 07의 「2.2 자동 처리 실행 API와 처리 기준 시각 설정 API」](07_공통실행참조.md#test-support-api)를 따른다.

1. `now`에 `2026-10-12T15:02:00Z`를 넣어 모의 배송 완료를 실행한다(`POST /test-support/jobs/delivery-complete`).
2. 판매자 계정으로 주문을 조회해 상품 확인 기한을 얻는다(`GET /api/orders/{orderId}`).
3. 2에서 얻은 상품 확인 기한을 `now`에 넣어 확인 기간 만료 자동 완료를 실행한다(`POST /test-support/jobs/inspection-complete`).
4. 두 자동 처리의 처리 건수를 기록하고, 「6. 결과 확인과 기록」의 값을 다시 확인해 기록한다.

### 4.3 예상 결과(가설)

아래 결과는 코드 분석에서 세운 가설이며 아직 실행하지 않았다. 테스트케이스1은 실행하지 않으며, 그 이유는 「4.2」에 있다.

| 테스트케이스 | 커밋 순서 | 요청 B의 발송 정보 조회 시점 | 응답 | 테스트 직후의 주문 | 발송 정보(`SHIPMENT`) | 구매자 반환(`CANCEL_REFUND`) | 위반 기준 |
|---|---|---|---|---|---|---|---|
| 테스트케이스1(실행하지 않음) | 요청 A(발송 등록) → 요청 B(미발송 자동 취소) | 요청 A의 커밋 뒤 | A 201, B `{"processed": 0}` | 진행 중(`IN_PROGRESS`), 배송 중(`SHIPPING`) | 1행 | 없음 | 없음 |
| 테스트케이스2 | 요청 B(미발송 자동 취소) → 요청 A(발송 등록) | 요청 A의 발송 정보 저장 전 | A 201, B `{"processed": 1}` | 진행 중(`IN_PROGRESS`), 배송 중(`SHIPPING`). 요청 B가 주문에 기록한 취소 주체(`CANCELLED_BY`)·취소 사유(`CANCEL_REASON`)·종료 시각(`FINALIZED_AT`)이 NULL로 지워짐 | 1행 | +290,000원 1건 | 기준 1, 3 |
| 테스트케이스3 | 요청 A(발송 등록) → 요청 B(미발송 자동 취소) | 요청 A의 발송 정보 저장 전 | A 201, B `{"processed": 1}` | 취소 완료(`CANCELLED`), 발송 대기(`WAITING_SHIPMENT`). 취소 주체 `SYSTEM`, 취소 사유 `SHIPMENT_DEADLINE_EXPIRED` | 1행 | +290,000원 1건 | 기준 1, 4 |

- **테스트케이스1:** 미발송 자동 취소는 발송 등록이 커밋한 뒤 발송 정보를 조회하므로, 발송 등록이 저장한 발송 정보가 조회되어 주문을 취소하지 않는다. 정상 동작과 같은 결과다.
- **테스트케이스2:** 발송 등록은 멈추기 전에 조회한 진행 중 주문으로 검사를 통과한다. 이어서 주문 UPDATE가 주문 ID를 뺀 모든 열을 다시 쓰므로, 미발송 자동 취소가 취소 완료로 바꾼 주문이 진행 중·배송 중으로 되돌아간다. 미발송 자동 취소가 구매자에게 반환한 290,000원은 남는다. [작업명세 03](03_테스트계획_발송등록과_구매자취소.md)에서 구매자 취소가 먼저 커밋된 경우와 같은 문제다.
- **테스트케이스3:** 미발송 자동 취소는 멈추기 전에 발송 정보가 없음을 확인했으므로, 재개된 뒤 발송 정보를 다시 조회하지 않고 취소를 진행한다. 이어서 주문 UPDATE가 주문 ID를 뺀 모든 열을 다시 쓰므로, 발송 등록이 배송 중으로 바꾼 배송 상태가 발송 대기로 되돌아가고, 발송 등록이 저장한 발송 정보 1행이 취소 완료 주문에 남는다. [작업명세 03](03_테스트계획_발송등록과_구매자취소.md)에서 발송 등록이 먼저 커밋된 경우와 같은 형태다.

**테스트케이스2의 이후 자동 처리(「4.2.3」)**

| 자동 처리 | 처리 건수 | 처리 뒤의 주문 | 판매자의 판매대금 지급(`SALE_PAYOUT`) |
|---|---|---|---|
| 모의 배송 완료 | 1 | 진행 중(`IN_PROGRESS`), 배송 완료(`DELIVERED`). 배송 완료 시각 `2026-10-12T15:02:00Z`, 상품 확인 기한 `2026-10-14T15:02:00Z` | 없음 |
| 확인 기간 만료 자동 완료 | 1 | 정상 완료(`COMPLETED`), 배송 완료(`DELIVERED`). 완료 사유 `AUTO_EXPIRED` | 판매자 지갑을 만든 뒤 +290,000원 1건 |

두 자동 처리는 주문의 상태와 기한, 발송 정보와 환불 요청의 유무만 확인하므로, 구매자에게 이미 결제액을 반환한 이 주문도 처리한다. 그 결과 결제액 290,000원인 주문에서 구매자 반환 290,000원과 판매자 지급 290,000원, 합계 580,000원이 나간다. 정상 완료인 주문에 취소 반환과 판매대금 지급이 함께 있으므로 기준 3을 위반하고, 기준 2·4·5에는 행이 나오지 않는다.

## 6. 결과 확인과 기록

적용할 기준은 [작업명세 01의 6절](01_테스트계획_공통.md#result-criteria)의 기준 1~4다. 요청 A는 HTTP 2xx 응답을, 요청 B는 처리 건수 1을 성공으로 본다. 기준 2~4는 [작업명세 07의 SQL 3.1~3.3](07_공통실행참조.md#result-sql)으로 확인한다. 이 상황에는 환불 요청이 없으므로 기준 5의 SQL은 행이 나오지 않아야 한다.

이 상황에서 확인할 값은 다음과 같다.

- 요청 A의 HTTP 응답 코드(201 또는 409 `ORDER_NOT_IN_PROGRESS`)와 요청 B의 처리 건수
- `PURCHASE_ORDER`의 `TRADE_STATUS`, `SHIPPING_STATUS`, `CANCELLED_BY`, `CANCEL_REASON`, `FINALIZED_AT`, `SHIP_DEADLINE_AT`
- `SHIPMENT` 행의 유무
- 구매자 `BALANCE_TRANSACTION`의 `CANCEL_REFUND` 건수

테스트케이스2의 이후 자동 처리(「4.2.3」) 뒤에는 위 값과 함께 다음 값을 확인한다.

- 모의 배송 완료와 확인 기간 만료 자동 완료의 처리 건수
- `PURCHASE_ORDER`의 `COMPLETION_CAUSE`, `DELIVERED_AT`, `INSPECTION_DEADLINE_AT`
- 판매자 `WALLET`의 잔액과 판매자 `BALANCE_TRANSACTION`의 `SALE_PAYOUT` 건수

서버 로그에서는 요청 B의 발송 정보 조회가 요청 A의 커밋보다 먼저 실행되었는지, 주문 UPDATE가 주문 ID를 뺀 모든 열을 다시 쓰는지, 두 요청의 커밋 순서를 함께 확인한다. 보관 자료와 민감 정보 처리는 [작업명세 01의 6.3절](01_테스트계획_공통.md#result-criteria)을 따른다.
