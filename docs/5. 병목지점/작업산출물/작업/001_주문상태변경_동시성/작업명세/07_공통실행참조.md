<a id="common-requests"></a>
## 1. 공통 요청 형식

기본 URL은 `http://wherehouse.it.kr:8186/ChatService`다. 사전 준비에서 판매자와 구매자는 다음 요청으로 가입하고 로그인한다.

**회원 가입** `POST /members/join`

```json
{"id":"{회원 ID}","pw":"{비밀번호}","nickName":"{회원 ID}","tel":"010-0000-0000","email":"{회원 ID}@example.com"}
```

**로그인** `POST /login`

폼 파라미터 `userid`, `password`로 보낸다. 응답으로 로그인 쿠키(`Authorization`)를 받고, 이후 그 회원의 요청에 붙인다.

상품 등록, 충전, 결제는 다음 형식을 쓴다. `...` 자리의 값은 상황별 명세의 「2. 사전조건과 테스트 데이터」에 있다.

| 요청 | 메서드·경로 | 본문 형식 |
|---|---|---|
| 상품 등록 | `POST /api/products` | `{"name":...,"description":...,"category":...,"price":...,"quantity":1}` |
| 충전 | `POST /api/wallet/charges` | `{"amount":...,"requestId":"${__UUID()}"}` |
| 결제 | `POST /api/orders` | `{"productId":${productId},"quantity":1,"recipientName":...,"shippingAddress":...,"requestId":"${__UUID()}"}` |

`${__UUID()}`와 `${productId}`, `${orderId}`는 JMeter 변수다. 상황 설명의 시각은 KST로 쓰고, API에는 같은 시각을 UTC로 넣는다. KST는 UTC보다 9시간 빠르다.

<a id="test-support-api"></a>
## 2. 테스트 지원 API와 설정

이 절의 기능은 운영 코드(`src/main`)에 넣고, 테스트 설정을 켰을 때만 동작하게 한다(작업명세 01의 [5절](01_테스트계획_공통.md#environment)). `/test-support/**` 경로는 테스트 설정을 켰을 때만 동작하며 인증 없이 호출된다.

지금 구현한 것은 2.3절의 요청 일시 중지다. 2.2절의 서버 시계 설정과 자동 처리 실행 API는 S1-1에 필요하지 않아 아직 구현하지 않았고, S1-3~S1-5를 테스트할 때 만든다. 스케줄러를 끄는 설정 `marketplace.scheduler.enabled`는 원래 코드에 있다.

### 2.1 테스트 기간의 서버 설정

| 항목 | 값 |
|---|---|
| 테스트 서버 주소 | `http://wherehouse.it.kr:8186/ChatService/` |
| 테스트 기간의 DB 계정 | `TOYCHAT_TEST`(미니PC Oracle) |
| 테스트 종료 후 DB 계정 | `TOYCHAT` |
| 스케줄러 | `marketplace.scheduler.enabled: false` |
| 테스트 지원 기능 | `marketplace.test-support.enabled: true`. 기본값은 `false`이며, 환경변수 `MARKETPLACE_TEST_SUPPORT_ENABLED=true`로도 켤 수 있다 |
| 멈춘 요청의 최대 대기 시간 | `marketplace.test-support.pause-timeout: PT30S`(30초) |

### 2.2 서버 시계 설정과 자동 처리 실행 API(아직 구현하지 않음)

| 메서드·경로 | 입력 | 하는 일 |
|---|---|---|
| `PUT /test-support/clock` | 본문 `{"instant": "2026-10-12T14:59:59.500Z"}` | 서비스가 현재 시각으로 쓸 값을 설정한다 |
| `POST /test-support/jobs/unshipped-cancel` | 파라미터 `now` | 미발송 자동 취소 `OrderCancellationService.cancelExpiredUnshipped(now)`를 실행한다 |
| `POST /test-support/jobs/delivery-complete` | 파라미터 `now` | 모의 배송 완료 `ShipmentService.completeDueDeliveries(now)`를 실행한다 |
| `POST /test-support/jobs/inspection-complete` | 파라미터 `now` | 확인 기간 만료 자동 완료 `TradeCompletionService.completeExpiredInspections(now)`를 실행한다 |
| `POST /test-support/jobs/refund-auto-approve` | 파라미터 `now` | 무응답 자동 환불 `RefundService.autoApproveExpired(now)`를 실행한다 |

자동 처리 API는 `{"processed": 1}` 형식으로 처리 건수를 돌려준다. `now`를 생략하면 서버 시계에 설정한 시각을 쓴다.

서비스는 `TimeRules.now()`로 현재 시각을 얻고, `TimeRules`는 주입된 `Clock` 빈에서 시각을 읽는다. 테스트 설정에서 이 `Clock` 빈을 지정한 시각을 돌려주는 시계로 바꾸면, 서비스 코드를 고치지 않고 처리 기준 시각을 바꿀 수 있다.

<a id="request-pause"></a>
### 2.3 요청 일시 중지

겹침 재현 테스트에서 요청 A와 요청 B를 정한 위치에서 멈추고, 정한 순서로 하나씩 재개하는 기능이다. 중지 위치는 주문 취소 처리 코드의 두 곳이다(작업명세 02의 4.1절). 테스트 설정이 꺼져 있으면 어떤 요청도 멈추지 않는다.

**요청 헤더.** JMeter가 요청 A와 요청 B에 붙인다. 두 헤더가 모두 있고 `X-Test-Pause-At`의 값이 지금 처리 중인 위치와 같은 요청만 멈춘다. 헤더가 없는 일반 요청은 멈추지 않는다.

| 헤더 | 값 |
|---|---|
| `X-Test-Request-Name` | 요청 이름. `A` 또는 `B` |
| `X-Test-Pause-At` | 중지 위치. `ORDER_READ`(중지 위치 1: 주문 조회 직후) 또는 `WALLET_READ`(중지 위치 2: 구매자 지갑 조회 직후) |

**API.** 멈춘 요청을 확인하고 재개할 때 쓴다.

| 메서드·경로 | 응답 | 하는 일 |
|---|---|---|
| `GET /test-support/pauses` | 예: `["A","B"]` | 지금 멈춰 있는 요청의 이름 목록을 돌려준다 |
| `POST /test-support/pauses/{name}/resume` | 재개하면 200, 그 이름으로 멈춰 있는 요청이 없으면 409 | 그 이름으로 멈춰 있는 요청을 재개한다 |

멈춘 요청은 트랜잭션과 DB 연결을 잡은 채로 기다린다. 그래서 최대 대기 시간(30초) 안에 재개되지 않으면 그 요청은 오류로 끝나고 트랜잭션은 롤백된다.

S1-1의 JMeter 계획 `01_테스트_구매자취소와_판매자취소_겹침재현테스트.jmx`에서는 「재개 제어」 스레드가 이 API를 쓴다. 이 스레드는 요청 A와 요청 B가 모두 멈췄는지 확인하고, 먼저 재개할 요청을 재개한다. 그 요청의 응답을 받은 뒤에 나머지 요청을 재개한다.

<a id="result-sql"></a>
## 3. 결과 확인 SQL

기준 1은 HTTP 응답 코드와 자동 처리 응답의 처리 건수로 확인한다(작업명세 01의 [6절](01_테스트계획_공통.md#result-criteria)). 기준 2~5는 아래 SQL로 확인하며, 조회 결과에 행이 있으면 그 기준을 위반한 것이다. 사용자가 로컬 노트북의 SQL Developer에서 `TOYCHAT_TEST` 계정으로 실행한다. `:orderId`, `:sellerId`, `:buyerId`에는 확인할 주문의 ID와 판매자·구매자의 회원 ID를 넣는다.

<a id="sql-criterion-2"></a>
### 3.1 기준 2: 지갑 잔액과 잔액 변동 내역 합계가 다른 회원

```sql
SELECT w.MEMBER_ID, w.BALANCE, NVL(SUM(t.AMOUNT), 0) AS LEDGER_SUM
  FROM WALLET w
  LEFT JOIN BALANCE_TRANSACTION t ON t.MEMBER_ID = w.MEMBER_ID
 WHERE w.MEMBER_ID IN (:sellerId, :buyerId)
 GROUP BY w.MEMBER_ID, w.BALANCE
HAVING w.BALANCE <> NVL(SUM(t.AMOUNT), 0);
```

<a id="sql-criterion-3"></a>
### 3.2 기준 3: 반환·지급 내역의 건수와 종류가 거래 상태와 맞지 않는 주문

```sql
SELECT o.ORDER_ID, o.TRADE_STATUS,
       SUM(CASE WHEN t.TYPE = 'CANCEL_REFUND' THEN 1 ELSE 0 END) AS CANCEL_REFUND_CNT,
       SUM(CASE WHEN t.TYPE = 'REFUND'        THEN 1 ELSE 0 END) AS REFUND_CNT,
       SUM(CASE WHEN t.TYPE = 'SALE_PAYOUT'   THEN 1 ELSE 0 END) AS SALE_PAYOUT_CNT
  FROM PURCHASE_ORDER o
  LEFT JOIN BALANCE_TRANSACTION t
         ON t.ORDER_ID = o.ORDER_ID
        AND t.TYPE IN ('CANCEL_REFUND', 'REFUND', 'SALE_PAYOUT')
 WHERE o.ORDER_ID = :orderId
 GROUP BY o.ORDER_ID, o.TRADE_STATUS
HAVING NOT (
        (o.TRADE_STATUS IN ('IN_PROGRESS', 'ON_HOLD') AND COUNT(t.TRANSACTION_ID) = 0)
     OR (o.TRADE_STATUS = 'CANCELLED' AND COUNT(t.TRANSACTION_ID) = 1
         AND SUM(CASE WHEN t.TYPE = 'CANCEL_REFUND' THEN 1 ELSE 0 END) = 1)
     OR (o.TRADE_STATUS = 'REFUNDED' AND COUNT(t.TRANSACTION_ID) = 1
         AND SUM(CASE WHEN t.TYPE = 'REFUND' THEN 1 ELSE 0 END) = 1)
     OR (o.TRADE_STATUS = 'COMPLETED' AND COUNT(t.TRANSACTION_ID) = 1
         AND SUM(CASE WHEN t.TYPE = 'SALE_PAYOUT' THEN 1 ELSE 0 END) = 1));
```

<a id="sql-criterion-4"></a>
### 3.3 기준 4: 거래 상태·배송 상태와 발송 정보 유무가 맞지 않는 주문

```sql
SELECT o.ORDER_ID, o.TRADE_STATUS, o.SHIPPING_STATUS, COUNT(s.SHIPMENT_ID) AS SHIPMENT_CNT
  FROM PURCHASE_ORDER o
  LEFT JOIN SHIPMENT s ON s.ORDER_ID = o.ORDER_ID
 WHERE o.ORDER_ID = :orderId
 GROUP BY o.ORDER_ID, o.TRADE_STATUS, o.SHIPPING_STATUS
HAVING (o.TRADE_STATUS = 'CANCELLED' AND COUNT(s.SHIPMENT_ID) > 0)
    OR (o.SHIPPING_STATUS IN ('SHIPPING', 'DELIVERED') AND COUNT(s.SHIPMENT_ID) = 0)
    OR (o.SHIPPING_STATUS = 'WAITING_SHIPMENT' AND COUNT(s.SHIPMENT_ID) > 0);
```

<a id="sql-criterion-5"></a>
### 3.4 기준 5: 환불 요청의 처리 결과와 거래 상태가 맞지 않는 주문

```sql
SELECT o.ORDER_ID, o.TRADE_STATUS, o.COMPLETION_CAUSE, r.DECISION
  FROM PURCHASE_ORDER o
  JOIN REFUND_REQUEST r ON r.ORDER_ID = o.ORDER_ID
 WHERE o.ORDER_ID = :orderId
   AND NOT ((r.DECISION = 'PENDING' AND o.TRADE_STATUS = 'ON_HOLD')
         OR (r.DECISION IN ('APPROVED', 'AUTO_APPROVED') AND o.TRADE_STATUS = 'REFUNDED')
         OR (r.DECISION = 'REJECTED' AND o.TRADE_STATUS = 'COMPLETED'
             AND o.COMPLETION_CAUSE = 'REFUND_REJECTED'));
```
