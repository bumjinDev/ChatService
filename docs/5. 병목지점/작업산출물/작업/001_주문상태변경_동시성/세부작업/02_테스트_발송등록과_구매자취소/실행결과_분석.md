### 분석 내용

**요청 B가 409로 거절되지 않은 이유**

두 요청은 17:46:38.123에 주문 43을 조회했다. 이 시각은 요청 A의 커밋(17:46:38.737)보다 앞서므로, 두 요청이 조회한 주문은 진행 중·발송 대기인 주문이다. 두 요청은 주문을 조회한 직후에 멈추므로, 조회한 주문으로 하는 상태 검사는 모두 재개된 뒤에 실행된다.

요청 B는 요청 A가 커밋한 뒤인 17:46:38.940에 재개되었지만, 주문 ID로 주문 43을 다시 조회하지 않았다. 재개 뒤 요청 B가 처음 실행한 SQL은 구매자 지갑 조회(17:46:38.944)다. 재개된 요청은 처음부터 다시 처리하지 않고 멈추기 전에 조회한 주문으로 이어서 처리하므로([작업명세 03](../../작업명세/03_테스트계획_발송등록과_구매자취소.md)의 「4.2 실행 절차」), 요청 B는 발송 대기인 주문으로 배송 상태를 검사했다. 그래서 요청 A가 주문을 배송 중으로 커밋한 뒤에도 검사를 통과했고, 409 `ORDER_ALREADY_SHIPPED`로 거절되지 않았다.

**최종 주문이 취소 완료·발송 대기가 된 이유**

요청 A는 17:46:38.735에 주문을 거래 상태 진행 중, 배송 상태 배송 중으로 UPDATE하고 17:46:38.737에 커밋했다. 요청 B는 17:46:38.963에 주문을 UPDATE했다. 두 요청의 주문 UPDATE는 주문 ID를 뺀 모든 열을 다시 쓰는 문장이고, 조건은 주문 ID 하나다.

요청 B의 UPDATE는 거래 상태를 취소 완료로, 취소 주체를 구매자로 바꾸면서 배송 상태 열에도 값을 썼다. SELECT로 읽은 값은 로그에 남지 않지만, 요청 B는 재개 뒤 주문 ID로 주문을 다시 조회하지 않았으므로 이때 쓴 값 `WAITING_SHIPMENT`는 17:46:38.123에 조회한 주문의 배송 상태로 판단했다. 그래서 요청 A가 커밋한 배송 중이 발송 대기로 되돌아갔다. 요청 B가 UPDATE할 때 요청 A의 트랜잭션은 이미 커밋되어 있었고, p6spy가 기록한 요청 B의 주문 UPDATE 실행 시간은 4 ms였다. 잠금 상태는 직접 조회하지 않았지만, 이 주문을 바꾼 요청 A가 이미 커밋한 뒤였으므로 이 UPDATE는 행 잠금을 기다리지 않았을 것으로 보인다.

**발송 정보가 남은 이유**

요청 A가 17:46:38.728에 추가한 발송 정보 행은 요청 B가 바꾸지 않았다. 요청 B의 취소 처리는 발송 정보를 조회하거나 지우지 않고 주문 행과 지갑, 취소 반환 내역만 바꾼다. 그래서 취소 완료·발송 대기인 주문 43에 발송 정보 1행이 남았다. 거래 상태·배송 상태와 발송 정보 유무를 비교하는 기준 4에서 주문 43이 나온 것은 이 때문이다.

**결제액 반환이 한 번만 기록된 이유**

이 테스트케이스에서 결제액을 반환한 요청은 요청 B 하나다. 요청 B는 재개 뒤 구매자 지갑을 조회해(17:46:38.944) 결제 후 잔액 25,000원에 75,000원을 더한 100,000원을 지갑 잔액과 취소 반환 내역의 변동 후 잔액으로 저장했다. 잔액 변동 내역의 합계(100,000원 − 75,000원 + 75,000원)도 100,000원이어서 지갑 잔액과 같고, 주문 43의 취소 반환 내역은 1건이다. 그래서 기준 2와 기준 3에는 행이 나오지 않았다.

**두 요청의 응답이 서로 다른 거래 결과를 담은 이유**

요청 A의 응답은 요청 A가 커밋한 뒤, 요청 B가 재개되기 전에 별도 트랜잭션(커넥션 27, 17:46:38.739~17:46:38.751)에서 주문을 다시 조회해 만들었다. 그래서 판매자는 진행 중·배송 중인 주문을 응답으로 받았다. 요청 B의 응답은 요청 B가 커밋한 뒤 별도 트랜잭션(커넥션 28, 17:46:38.972~17:46:38.982)에서 만들었으므로, 구매자는 취소 완료·발송 대기인 주문과 함께 요청 A가 추가한 발송 정보를 응답으로 받았다.

**저장된 두 시각의 순서와 차이**

발송 정보의 발송 시각은 17:46:38.121769이고, 요청 A가 대기를 시작한 시각(17:46:38.124)보다 앞선다. 발송 등록은 주문을 조회하기 전에 현재 시각을 구하므로, 멈추기 전의 시각이 발송 시각으로 저장되었다. 주문의 종료 시각과 취소 반환 내역의 기록 시각은 17:46:38.945143으로, 요청 B가 재개된(17:46:38.940) 뒤에 구한 시각이다.

두 요청이 시각을 구한 위치가 다르므로, 저장된 두 시각의 차이(약 0.82초)에는 요청을 멈춰 둔 시간이 들어 있다. 이 차이는 일시 중지로 생긴 값이며 두 요청의 실제 처리 간격이 아니다. 이 실행에서는 저장된 시각의 순서(발송 시각이 먼저)와 커밋 순서(요청 A가 먼저)가 같았다. 처리 순서와 커밋 순서는 저장된 시각이 아니라 서버 로그와 p6spy 기록으로 판단했다.

### 분석 결과

테스트케이스1의 결과는 [작업명세 03](../../작업명세/03_테스트계획_발송등록과_구매자취소.md)의 「4.3 예상 결과(가설)」에서 요청 A(발송 등록)가 먼저 커밋되는 행과 같았다. 두 요청이 요청 A의 커밋 전에 조회한 주문으로 처리 조건을 검사해 둘 다 성공했다. 나중에 커밋한 요청 B는 주문의 모든 열을 다시 쓰면서 배송 상태를 발송 대기로 되돌렸다.

그 결과 취소 완료·발송 대기인 주문에 발송 정보 1행이 남아 기준 4를 위반했다. 결제액 반환은 한 번만 기록되어 지갑 잔액과 잔액 변동 내역은 맞았다. 판매자는 배송 중, 구매자는 취소 완료인 주문을 응답으로 받아, 같은 주문에 대해 두 당사자가 서로 다른 거래 결과를 받았다.

### 시스템 명세

- 발송 등록: `ShipmentService.register`가 현재 시각을 구하고 주문을 조회한 뒤 중지 위치(`ORDER_READ`)를 지난다. 이어서 판매자인지와 거래가 끝났는지 검사하고, 발송 정보가 있는지 조회(`ShipmentRepository.existsByOrderId`)하고, 발송 기한을 검사한 뒤 `SHIPMENT`를 INSERT하고 `PurchaseOrder.markShipped`로 배송 상태를 바꾼다. 주문 UPDATE는 커밋 전 flush 때 실행된다
- 당사자 취소: `OrderCancellationService.cancelByParty`가 주문을 조회한 뒤 중지 위치(`ORDER_READ`)를 지나고, 당사자·거래 상태·배송 상태를 검사한 뒤 `cancel`을 부른다. `cancel`은 `WalletService.ensureCreditable`, `PurchaseOrder.cancel`, `WalletService.credit` 순서로 처리한다
- 응답 생성: `OrderController`가 서비스 트랜잭션을 커밋한 뒤 주문을 다시 조회해 응답 본문을 만든다
- 커넥션 번호: 요청 A 26(데이터를 바꾼 트랜잭션)·27(응답 조회), 요청 B 25·28
- 주문 UPDATE(바인딩 전):

  ```sql
  update PURCHASE_ORDER set BUYER_ID=?,CANCEL_REASON=?,CANCELLED_BY=?,COMPLETION_CAUSE=?,CONFIRMED_AT=?,DELIVERED_AT=?,FINALIZED_AT=?,INSPECTION_DEADLINE_AT=?,OFFER_ID=?,PAID_AMOUNT=?,PRICE_SOURCE=?,PRODUCT_ID=?,QUANTITY=?,RECIPIENT_NAME=?,REQUEST_ID=?,SELLER_ID=?,SHIP_DEADLINE_AT=?,SHIPPING_ADDRESS=?,SHIPPING_STATUS=?,TRADE_STATUS=?,UNIT_PRICE=? where ORDER_ID=?
  ```
