## 1. 개요

실행02는 판매자의 발송 등록과 구매자의 주문 취소를 모두 주문 조회 직후에 멈춘 뒤 구매자 취소부터 재개하여, 같은 주문에서 한 요청만 성공하는지 확인한 테스트케이스2다. 구매자 취소가 먼저 커밋되었지만 두 요청이 모두 성공했고, 최종 주문은 진행 중·배송 중으로 되돌아가 취소 기록이 지워진 반면 구매자에게 반환한 75,000원은 남았다. 실행03은 [세부작업기록](세부작업기록.md)의 「2. 계획」 아래 「계획 변경」(2026-10-20)에 따라 같은 주문을 모의 배송 완료와 확인 기간 만료 자동 완료까지 진행했다. 그 결과 판매자에게도 75,000원이 지급되어, 결제액 75,000원인 주문에서 구매자 반환과 판매자 지급으로 합계 150,000원이 나갔다. 실행02의 결과는 [작업명세 03](../../작업명세/03_테스트계획_발송등록과_구매자취소.md)의 「4.3 예상 결과(가설)」 표에서 요청 B(취소) → 요청 A(발송 등록) 행의 예상과 같았고, 실행03의 결과는 같은 표 아래 「구매자 취소가 먼저 커밋된 경우」에 적은 영향과 같았다. 실행02는 결과 확인 기준 1과 3을, 실행03은 기준 3을 만족하지 못했다.

## 2. 테스트 대상

두 실행의 대상은 미니PC에 배포해 실행 중인 ChatService 서버다. 실행03의 서버는 실행02의 빌드에 모의 배송 완료와 확인 기간 만료 자동 완료를 실행하는 API 두 개(자동 처리 실행 API)를 더한 빌드다.

**실행02**

요청 A(발송 등록)는 판매자가 주문의 발송 정보를 등록하는 기능이다. 한 트랜잭션에서 현재 시각을 구하고 주문을 조회한 뒤, 요청자가 판매자인지와 거래가 끝나지 않았는지를 검사한다. 이어서 발송 정보가 이미 있는지 조회하고 발송 기한 전인지 검사한다. 검사를 통과하면 발송 정보를 저장하고 주문의 배송 상태를 배송 중으로 바꾼다.

요청 B(구매자 취소)는 구매자가 주문을 취소하는 기능이다. 한 트랜잭션에서 주문을 조회한 뒤, 요청자가 거래 당사자인지, 거래가 끝나지 않았는지, 배송 상태가 발송 대기인지 검사한다. 이어서 구매자 지갑을 조회하고 결제액 반환 후의 잔액이 저장 범위를 넘지 않는지 검사한다. 검사를 통과하면 주문을 취소 완료로 바꾸고 취소 주체·사유·시각을 기록하며, 구매자 잔액에 결제액을 더하고 취소 반환 내역을 추가한다. 두 기능 모두 변경 내용을 커밋한 뒤 별도 트랜잭션에서 주문을 조회해 응답을 만든다([작업명세 03](../../작업명세/03_테스트계획_발송등록과_구매자취소.md)의 「4.1 중지 위치」와 「4.2 실행 절차」).

발송 등록과 구매자 취소에는 주문을 조회한 직후, 상태를 검사하기 전에 요청을 멈출 수 있는 테스트 지원 기능(요청 일시 중지)이 들어 있다. 이 기능은 테스트 설정이 켜져 있고 요청 헤더에 지정한 중지 위치에 도달했을 때 동작하며, 대기 중에도 트랜잭션과 DB 연결을 유지한다([작업명세 07](../../작업명세/07_공통실행참조.md#request-pause)의 「2.3 요청 일시 중지」). 재개된 요청은 처음부터 다시 처리하지 않고, 멈추기 전에 조회해 둔 주문으로 멈춘 위치부터 처리를 계속한다([작업명세 03](../../작업명세/03_테스트계획_발송등록과_구매자취소.md)의 「4.2 실행 절차」).

테스트가 운영 코드의 동작을 그대로 확인하도록, 두 기능이 현재 시각을 구하는 위치는 바꾸지 않았다. 그래서 발송 등록은 멈추기 전에 구한 시각을 발송 시각으로 저장하고, 구매자 취소는 재개된 뒤에 구한 시각을 취소 시각으로 저장한다([세부작업기록](세부작업기록.md)의 「2026-10-19 테스트케이스와 테스트 지원 코드 변경」).

**실행03**

실행03에서는 스케줄러를 끈 상태에서 이 자동 처리 실행 API를 호출해, 스케줄러가 부르는 자동 처리 메서드를 한 번씩 실행했다. 요청에 파라미터 `now`가 있으면 그 시각을 처리 기준 시각으로 쓰고, 없으면 서버의 현재 시각을 쓴다. 자동 처리 서비스와 스케줄러의 코드는 바꾸지 않았다([세부작업기록](세부작업기록.md)의 「2026-10-20 자동 처리 실행 API 추가」, [작업명세 07](../../작업명세/07_공통실행참조.md)의 「2.2 자동 처리 실행 API와 처리 기준 시각 설정 API」).

모의 배송 완료는 트랜잭션 밖에서 진행 중·배송 중이고 배송 완료 시각이 없으며, 발송 정보의 모의 배송 완료 예정 시각이 처리 기준 시각 이하인 주문을 조회한다. 이어서 주문마다 새 트랜잭션에서 주문과 발송 정보를 다시 조회해 같은 조건을 확인하고, 배송 상태를 배송 완료로 바꾸면서 처리 기준 시각을 배송 완료 시각으로, 그 48시간 뒤를 상품 확인 기한으로 저장한다.

확인 기간 만료 자동 완료는 트랜잭션 밖에서 진행 중·배송 완료이고 상품 확인 기한이 처리 기준 시각 이하인 주문을 조회한다. 이어서 주문마다 새 트랜잭션에서 주문을 다시 조회해 같은 조건을 확인하고, 환불 요청이 없는지 조회한다. 조건을 통과하면 주문을 정상 완료로 바꾸고, 판매자 잔액에 결제 금액 전액을 더하고 판매대금 지급 내역을 추가한다. 판매자 지갑이 없으면 지갑을 만든 뒤 더한다. 두 자동 처리는 주문의 상태와 기한, 발송 정보와 환불 요청의 유무만 확인하고 잔액 변동 내역은 확인하지 않는다.

**시각 기준**

이 결과서에는 노트북과 미니PC 서버의 시계로 기록한 시각이 함께 나온다. 따로 밝히지 않은 시각은 서버 시각이다.

| 시계 | 그 시계로 기록한 자료 |
|---|---|
| 노트북 | JMeter의 `결과.jtl`, 실행02의 `재개제어_기록.txt` |
| 미니PC 서버 | 웹 애플리케이션 로그, 일시 중지·재개 로그, p6spy 기록, DB와 응답 본문에 저장된 시각 |

재개 제어는 서버에서 멈춘 두 요청을 차례로 재개하는 JMeter 스레드다.

| 재개한 요청 | 재개 제어의 응답 코드 200 기록 시각(노트북) | 요청 재개 시각(서버) | 서버 시각 − 노트북 시각 |
|---|---|---|---|
| 요청 B | 20:51:28.623 | 20:51:28.832 | 208.7 ms |
| 요청 A | 20:51:28.858 | 20:51:29.188 | 329.9 ms |

비교한 두 기록 사이에는 재개 요청의 응답이 노트북에 도착하는 시간이 들어 있으므로, 측정값은 두 시계의 실제 차이와 다를 수 있다. 따라서 이 차이는 노트북 쪽 기록과 서버 쪽 기록을 맞추어 보는 데에만 사용했고, 처리 순서와 걸린 시간은 같은 시계의 기록끼리만 비교했다.

실행03에는 재개 제어가 없어 두 시계의 차이를 측정하지 않았고, 실행03의 `결과.jtl` 시각은 서버 시각과 비교하지 않았다.

p6spy의 SQL·커밋 기록 시각은 해당 동작이 끝난 뒤의 시각이며, SQL에 바인딩된 저장 시각과 구분한다.

## 4. 테스트 데이터와 시작 상태

**실행02**

판매자와 구매자의 회원 가입·로그인을 마친 뒤 상품 등록, 구매자 충전, 결제 순서로 준비했다. 준비 순서와 금액은 [작업명세 03](../../작업명세/03_테스트계획_발송등록과_구매자취소.md)의 「2.1 시작 상태와 금액」과 「2.2 준비 순서」에 따른다. 상품 등록·충전·결제는 JMeter의 「4. 테스트케이스2 주문 만들기」로 실행했다. 표의 시각은 서버 로그에 해당 동작이 기록된 시각이다.

| 대상 | 데이터 | 데이터 출처 |
|---|---|---|
| 판매자 | `s1-2c2seller01`, 가입일 2026-10-19 | 회원 가입 후 로그인했다(회원 가입 요청 처리 시작 16:56:51.438, 로그인 인증 성공 20:47:14.559) |
| 구매자 | `s1-2c2buyer01`, 가입일 2026-10-19 | 회원 가입 후 로그인했다(회원 가입 요청 처리 시작 16:56:51.551, 로그인 인증 성공 20:47:14.701) |
| 상품 | 상품 44, 캠핑 의자, 75,000원, 1개 | 판매자 계정으로 등록했다(20:47:36.892) |

| 요청 A의 발송 정보 | 택배사 편의점 택배, 운송장 번호 3621-0984-4170 | 테스트케이스2 테스트 데이터 CSV의 값을 사용했다 |

## 8. 정리 및 결론

**실행02**

**요청 A가 거절되지 않은 이유:** 요청 A는 요청 B가 커밋하기 전에 주문 44를 조회하고 멈췄고, 재개된 뒤에도 주문을 다시 조회하지 않았다. 그래서 멈추기 전에 조회한 진행 중인 주문으로 거래 상태를 검사해 409로 거절되지 않았다(요청 A의 주문 조회 20:51:28.580, 요청 B 커밋 20:51:28.856).

**최종 주문이 진행 중·배송 중으로 되돌아간 이유:** 요청 A의 주문 UPDATE가 주문 ID를 뺀 모든 열을 다시 쓰면서 거래 상태에 진행 중을, 취소 기록에 NULL을 써, 요청 B가 커밋한 취소 완료를 덮었다(요청 B 커밋 20:51:28.856, 요청 A의 주문 UPDATE 20:51:29.202). 이 UPDATE는 요청 B가 커밋한 뒤에 실행되었고 p6spy가 기록한 실행 시간이 0 ms였으므로, 행 잠금을 기다리지 않았을 것으로 보인다(잠금 상태는 직접 조회하지 않았다).

**반환한 75,000원이 남은 이유:** 결제액 반환은 요청 B만 처리했고, 요청 A의 발송 등록은 구매자 지갑과 잔액 변동 내역을 바꾸지 않는다. 그래서 요청 A가 주문을 진행 중으로 되돌린 뒤에도 취소 반환 내역과 구매자 잔액 100,000원이 그대로 남았다(취소 반환 내역 추가 20:51:28.840, 요청 A 커밋 20:51:29.207).

**두 응답이 다른 이유:** 두 요청은 각자 커밋한 뒤 별도 트랜잭션에서 주문을 다시 조회해 응답을 만들었다. 요청 B는 요청 A가 재개되기 전에 조회했으므로 구매자는 취소 완료인 주문을 받았고, 요청 A는 자신의 커밋 뒤에 조회했으므로 판매자는 진행 중·배송 중인 주문을 받았다(요청 B의 응답 조회 20:51:28.858~20:51:28.869, 요청 A 재개 20:51:29.188). 그래서 구매자가 받은 취소 완료는 DB에 남은 최종 주문과 다르다.

**실행03**

**두 자동 처리의 대상이 된 이유:** 실행02를 마친 뒤 주문 44는 취소 기록이 지워진 진행 중·배송 중 주문이어서, 주문 행만 보면 발송 등록을 마친 정상 주문과 같았다. 두 자동 처리는 주문의 상태와 기한, 발송 정보와 환불 요청의 유무만 확인하고 잔액 변동 내역은 확인하지 않으므로, 구매자에게 이미 결제액을 반환한 주문 44도 두 자동 처리의 대상이 되었다(모의 배송 완료와 확인 기간 만료 자동 완료의 처리 건수 각 1).

**판매자에게도 지급되어 150,000원이 나간 이유:** 확인 기간 만료 자동 완료는 주문을 정상 완료로 바꾸면서 판매자에게 결제 금액 전액을 지급한다. 실행02의 취소 반환 75,000원이 남아 있는 상태에서 판매대금 75,000원도 지급되어, 결제액 75,000원인 주문 44에서 합계 150,000원이 나갔다(취소 반환 내역 70, 판매대금 지급 내역 71).

**기준 3에서만 드러난 이유:** 기준 2는 회원별로, 기준 3은 주문별로 내역을 비교한다. 구매자는 100,000원, 판매자는 75,000원으로 각자 지갑 잔액과 잔액 변동 내역 합계가 맞아 기준 2에는 행이 없었지만, 정상 완료인 주문 44에는 판매대금 지급 외에 취소 반환 1건이 더 있어 기준 3에 행이 나왔다.

발송 등록의 처리 순서는 `ShipmentService.register`에서 `timeRules.now()`, `purchaseOrderRepository.findById`, `testPause.reach(PausePoint.ORDER_READ)`, 상태 검사, 발송 정보 저장, `markShipped` 순이다. 구매자 취소는 `OrderCancellationService.cancelByParty`에서 주문 조회와 같은 중지 위치를 거친다. 취소 시각은 `cancel` 안에서 구매자 지갑 조회와 `WALLET_READ` 위치 뒤의 `nowSupplier.get()`으로 구한다. 이번 실행은 `ORDER_READ`만 지정했다.

요청 A의 데이터 변경 커넥션은 18, 응답 조회 커넥션은 20이며, 요청 B는 각각 17과 19다. 다음은 주문 UPDATE의 바인딩된 값 가운데 결과와 관련된 부분만 발췌한 것이다. 전체 문장은 주문 ID를 뺀 모든 열을 갱신한다.

```sql
-- 요청 B의 SET 절과 WHERE 조건 중 발췌
CANCEL_REASON='같은 의자를 선물받아 취소합니다.', CANCELLED_BY='BUYER',
FINALIZED_AT='2026-10-19T20:51:28.836+0900',
SHIPPING_STATUS='WAITING_SHIPMENT', TRADE_STATUS='CANCELLED'
where ORDER_ID=44

-- 요청 A의 SET 절과 WHERE 조건 중 발췌
CANCEL_REASON=NULL, CANCELLED_BY=NULL, FINALIZED_AT=NULL,
SHIPPING_STATUS='SHIPPING', TRADE_STATUS='IN_PROGRESS'
where ORDER_ID=44
```

**실행03**

| 용도 | 메서드·경로 또는 값 |
|---|---|
| C-1 | `GET /test-support/pauses` |
| C-2 | `GET /api/orders/sales`, 첫 주문의 `orderId` 사용 |
| C-3 | `POST /test-support/jobs/delivery-complete`, `now` 생략 |
| C-4·C-6·C-7 | `GET /api/orders/44` |
| C-5 | `POST /test-support/jobs/inspection-complete`, `now=2026-10-22T02:20:03.701172Z` |
| C-5의 입력 출처 | C-4 응답의 `inspectionDeadlineAt` |
| 자동 처리 응답 | `{"processed":1}` |

`TestSupportJobController`는 모의 배송 완료에 `ShipmentService.completeDueDeliveries(now)`를, 확인 기간 만료 자동 완료에 `TradeCompletionService.completeExpiredInspections(now)`를 호출한다. 모의 배송 완료의 대상 조회는 `PurchaseOrderRepository.findIdsByDeliveryDue`이고, 주문별 새 트랜잭션의 `deliverIfDue`에서 `PurchaseOrder.markDelivered`가 배송 완료 시각과 상품 확인 기한을 저장한다. 확인 기간 만료 자동 완료의 대상 조회는 `PurchaseOrderRepository.findIdsByInspectionExpired`이고, 주문별 새 트랜잭션의 `completeIfExpired`에서 `complete`를 통해 `WalletService.ensureCreditable`, `PurchaseOrder.complete`, `WalletService.credit`(`SALE_PAYOUT`) 순으로 처리한다.

모의 배송 완료는 대상 조회에 커넥션 10, 주문 처리에 11을 사용했고, 확인 기간 만료 자동 완료는 각각 13과 14를 사용했다. 다음은 p6spy의 바인딩된 조건과 갱신 값 발췌다. 모의 배송 완료의 대상 조회는 별칭을 테이블 이름으로 바꾸었다.

```sql
-- 모의 배송 완료 대상 조회의 WHERE 조건
SHIPMENT.ORDER_ID=PURCHASE_ORDER.ORDER_ID
and PURCHASE_ORDER.SHIPPING_STATUS='SHIPPING'
and PURCHASE_ORDER.TRADE_STATUS='IN_PROGRESS'
and PURCHASE_ORDER.DELIVERED_AT is null
and SHIPMENT.DELIVERY_DUE_AT<='2026-10-20T11:20:03.701+0900'

-- 확인 기간 만료 자동 완료 대상 조회의 WHERE 조건
TRADE_STATUS='IN_PROGRESS' and SHIPPING_STATUS='DELIVERED'
and INSPECTION_DEADLINE_AT<='2026-10-22T11:20:03.701+0900'

-- 확인 기간 만료 자동 완료 UPDATE의 SET 절과 WHERE 조건 중 발췌
COMPLETION_CAUSE='AUTO_EXPIRED',
FINALIZED_AT='2026-10-22T11:20:03.701+0900',
TRADE_STATUS='COMPLETED'
where ORDER_ID=44
```
