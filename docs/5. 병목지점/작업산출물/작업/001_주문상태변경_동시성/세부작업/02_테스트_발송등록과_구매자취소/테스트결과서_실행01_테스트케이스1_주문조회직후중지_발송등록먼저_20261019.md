## 1. 개요

판매자의 발송 등록과 구매자의 주문 취소가 같은 주문에서 겹칠 때 한 요청만 성공하는지 확인했다. 두 요청을 주문 조회 직후, 상태를 검사하기 전에 멈추고 요청 A(발송 등록)의 응답을 받은 뒤 요청 B(구매자 취소)를 재개했다. 요청 A는 201, 요청 B는 200으로 모두 성공했으며, 최종 주문 43은 취소 완료·발송 대기인데 발송 정보가 1행 남았다. 구매자에게 결제액 75,000원이 한 번 반환되었고, 최종 잔액과 잔액 변동 내역 합계는 모두 100,000원이었다. 이 결과는 [작업명세 03](../../작업명세/03_테스트계획_발송등록과_구매자취소.md)의 「4.3 예상 결과(가설)」에 적은 요청 A → 요청 B 순서의 예상과 같지만, 한 요청만 성공해야 하는 정상 동작을 충족하지 못해 결과 확인 기준 1과 4를 위반했다.

## 2. 테스트 대상

미니PC에 배포해 실행 중인 ChatService 서버의 판매자 발송 등록과 구매자 주문 취소 기능을 테스트했다. 발송 등록과 구매자 취소를 모두 주문 조회 직후에 멈출 수 있도록 테스트 지원 코드를 변경한 서버다.

발송 등록은 한 트랜잭션에서 현재 시각을 구하고 주문을 조회한 뒤, 요청자가 판매자인지와 거래가 끝나지 않았는지를 검사한다. 이어서 발송 정보가 이미 있는지 조회하고 발송 기한 전인지 검사한다. 검사를 통과하면 발송 정보를 저장하고 주문의 배송 상태를 배송 중으로 바꾼다.

주문 취소는 한 트랜잭션에서 주문을 조회한 뒤, 요청자가 거래 당사자인지, 거래가 끝나지 않았는지, 배송 상태가 발송 대기인지 검사한다. 이어서 구매자 지갑을 조회하고 결제액 반환 후의 잔액이 저장 범위를 넘지 않는지 검사한다. 검사를 통과하면 주문을 취소 완료로 바꾸고 취소 주체·사유·시각을 기록하며, 구매자 잔액에 결제액을 더하고 취소 반환 내역을 추가한다. 두 기능 모두 변경 내용을 커밋한 뒤 별도 트랜잭션에서 주문을 조회해 응답을 만든다([작업명세 03](../../작업명세/03_테스트계획_발송등록과_구매자취소.md)의 「4.1 중지 위치」와 「4.2 실행 절차」).

이번 실행의 중지 위치는 두 요청 모두 주문 조회 직후, 상태 검사 전이다. 요청 일시 중지는 테스트 설정이 켜져 있고 요청 헤더에 지정한 중지 위치에 도달했을 때 동작하며, 대기 중에도 트랜잭션과 DB 연결을 유지한다([작업명세 07](../../작업명세/07_공통실행참조.md#request-pause)의 「2.3 요청 일시 중지」). 재개된 요청은 처음부터 다시 처리하지 않고, 멈추기 전에 조회해 둔 주문으로 멈춘 위치부터 처리를 계속한다([작업명세 03](../../작업명세/03_테스트계획_발송등록과_구매자취소.md)의 「4.2 실행 절차」).

발송 등록은 주문 조회 전에 구한 시각을 발송 시각으로 저장하고, 구매자 취소는 재개된 뒤에 구한 시각을 취소 시각으로 저장한다([세부작업기록](세부작업기록.md)의 「2026-10-19 테스트케이스와 테스트 지원 코드 변경」).

**시각 기준**

요청을 보낸 노트북과 요청을 처리한 미니PC 서버는 각각 자기 시계로 시각을 기록했다. 재개 제어는 서버에서 멈춘 두 요청을 차례로 재개하는 JMeter 스레드이며, 이 기록도 노트북 시계를 따른다.

| 시계 | 그 시계로 기록한 자료 |
|---|---|
| 노트북 시계 | JMeter 결과 파일의 요청을 보낸 시각, 재개 제어 기록의 단계별 시각 |
| 서버 시계 | 서버 로그의 시각, DB의 기록 시각, 응답 본문에 담긴 시각 |

이 결과서에서 따로 밝히지 않은 시각은 서버 시각이다. 두 장비의 기록을 맞추어 보기 위해 같은 재개 동작에 대해 재개 제어가 응답 코드 200을 기록한 노트북 시각과 서버가 요청을 재개한 시각을 비교했다. 표의 시각은 밀리초까지 반올림했으며, 차이는 반올림 전 값으로 계산했다.

| 재개한 요청 | 재개 제어의 응답 코드 200 기록 시각(노트북 시각) | 요청 재개 시각(서버 시각) | 서버 시각 − 노트북 시각 |
|---|---|---|---|
| 요청 A | 17:46:38.548 | 17:46:38.695 | 146.6 ms |
| 요청 B | 17:46:38.907 | 17:46:38.940 | 33.3 ms |

비교한 두 기록 사이에는 재개 요청의 응답이 노트북에 도착하는 시간이 들어 있으므로, 측정값은 두 시계의 실제 차이와 다를 수 있다. 따라서 이 차이는 노트북 쪽 기록과 서버 쪽 기록을 맞추어 보는 데에만 사용했고, 처리 순서와 걸린 시간은 같은 시계의 기록끼리만 비교했다. DB 조회 화면과 응답 본문의 시각은 UTC이므로, 결과서에는 9시간을 더한 시각으로 밀리초까지 반올림해 적었다.

## 5. 수행 절차

JMeter의 「3. 테스트케이스1 테스트」를 실행했다. 요청 A, 요청 B, 재개 제어를 맡은 스레드 세 개를 동시에 시작했다. 두 요청에는 요청 이름과 주문 조회 직후의 중지 위치를 헤더로 지정했다. 실행 순서는 [작업명세 03](../../작업명세/03_테스트계획_발송등록과_구매자취소.md)의 「4.2.1 테스트케이스1: 주문 조회 직후 중지, 요청 A(발송 등록) 먼저 재개」와 같다.

| 순서 | 스레드 1: 요청 A(발송 등록) | 스레드 2: 요청 B(구매자 취소) | 스레드 3: 재개 제어 |
|---|---|---|---|
| 1 | 판매 목록에서 주문 ID를 조회한다 | 구매 목록에서 주문 ID를 조회한다 | 멈춘 요청 목록을 조회한다 |
| 2 | 발송 등록 요청을 보낸다 | 주문 취소 요청을 보낸다 | 멈춘 요청 목록을 조회한다 |
| 3 | 응답을 기다린다 | 응답을 기다린다 | 두 요청이 모두 멈춘 것을 확인한다 |
| 4 | 응답을 기다린다 | 응답을 기다린다 | 요청 A를 재개한다 |
| 5 | 응답을 받는다 | 응답을 기다린다 | 요청 A의 응답을 확인한다 |
| 6 | 처리를 마친다 | 응답을 기다린다 | 요청 B를 재개한다 |
| 7 | | 응답을 받는다 | 요청 B의 응답을 확인한다 |

두 요청이 끝난 뒤 SQL Developer에서 회원·상품·주문·발송 정보·지갑·잔액 변동 내역을 조회하고, 결과 확인 기준 2~5의 SQL을 실행했다. 조회 대상은 주문 43과 두 회원이며, 각 결과를 화면 사진으로 저장했다.

## 8. 해석

요청 B가 409로 거절되지 않은 것은 요청 A가 주문을 바꾸기 전에 조회한 주문으로 취소 조건을 검사했기 때문으로 판단했다. 두 요청은 요청 A가 커밋하기 전에 주문 43을 조회했고, 조회 직후 상태 검사 전에 멈췄다(주문 조회 17:46:38.123, 요청 A 커밋 17:46:38.737). 요청 A는 먼저 재개되어 발송 정보와 배송 상태를 저장하고 커밋했으며, 요청 B는 그 뒤에 재개되었다(요청 B 재개 17:46:38.940). 재개된 요청은 처음부터 다시 처리하지 않고 멈추기 전에 조회해 둔 주문으로 상태를 검사한다. 요청 B의 변경 트랜잭션에도 재개 뒤 주문 ID로 주문 43을 다시 조회한 SQL은 없었고, 재개 뒤 첫 SQL은 구매자 지갑 조회였다(17:46:38.944).

요청 B가 재개된 뒤 주문을 전혀 조회하지 않은 것은 아니다. 요청 B는 대화와 상품을 조회했고, 자신의 주문 UPDATE 뒤에 상품·구매자·판매자 조건으로 주문을 조회했다(대화 조회 17:46:38.953, 상품 조회 17:46:38.956, 주문 UPDATE 17:46:38.963, 주문 조회 17:46:38.965).

최종 주문의 배송 상태가 발송 대기로 되돌아간 것은 요청 B의 주문 UPDATE가 배송 상태 열까지 다시 썼기 때문이다. 두 UPDATE의 조건은 주문 ID 하나였고, 요청 B의 바인딩 후 SQL에는 거래 상태 취소 완료와 함께 배송 상태 `WAITING_SHIPMENT`를 쓴 것이 남아 있다. SELECT로 읽은 배송 상태 자체는 로그에 없지만, 요청 B가 재개 뒤 주문 ID로 주문을 다시 조회하지 않았으므로 이 값은 멈추기 전에 조회한 주문의 배송 상태로 판단했다(주문 조회 17:46:38.123). 요청 B는 커밋하면서 요청 A가 저장한 배송 중을 발송 대기로 덮어썼다(요청 B 커밋 17:46:38.970).

요청 B가 주문을 UPDATE할 때 요청 A는 이미 커밋한 상태였고, p6spy가 기록한 이 UPDATE의 실행 시간은 4 ms였다(요청 A 커밋 17:46:38.737, 요청 B 주문 UPDATE 17:46:38.963). 잠금 상태는 직접 조회하지 않았지만, 이 주문을 바꾼 요청 A가 이미 커밋한 뒤였으므로 이 UPDATE는 행 잠금을 기다리지 않았을 것으로 보인다.

발송 정보가 남은 것은 요청 B의 취소 처리가 요청 A가 추가한 발송 정보 행을 바꾸지 않았기 때문이다. 요청 A는 재개된 뒤 발송 정보를 추가했고, 요청 B의 변경 트랜잭션은 발송 정보를 조회하거나 지우지 않고 주문과 지갑을 갱신하고 취소 반환 내역을 추가했다(요청 A의 발송 정보 추가 17:46:38.728). 따라서 DB에는 취소 완료·발송 대기인 주문 43과 발송 정보 1행이 함께 남았고, 거래 상태·배송 상태와 발송 정보 유무를 비교하는 기준 4에서 주문 43이 나왔다.

결제액 반환은 요청 B만 처리했으므로 한 번 기록되었다. 요청 B는 구매자 지갑을 조회한 뒤 +75,000원, 변동 후 잔액 100,000원인 취소 반환 내역을 추가하고, 지갑 잔액을 100,000원으로 저장했다(지갑 조회 17:46:38.944, 취소 반환 내역 추가 17:46:38.950, 지갑 UPDATE 17:46:38.964). SELECT로 읽은 잔액 자체는 로그에 없지만, 결제 내역 66의 변동 후 잔액과 이후 저장한 반환액·잔액을 근거로 조회 당시 잔액은 25,000원이었을 것으로 판단했다. 구매자의 잔액 변동 내역 합계도 100,000원으로 지갑 잔액과 같고, 취소 완료인 주문 43의 취소 반환 내역이 1건이므로 기준 2와 3에는 행이 나오지 않았다.

두 요청의 응답이 서로 다른 거래 결과를 담은 것은 응답에 쓸 주문을 조회한 시점이 다르기 때문이다. 요청 A는 자신의 커밋 뒤, 요청 B가 재개되기 전에 별도 트랜잭션에서 응답에 쓸 주문을 조회했으므로, 판매자는 진행 중·배송 중인 주문을 받았다(요청 A의 응답 조회 17:46:38.739~17:46:38.751, 요청 B 재개 17:46:38.940). 요청 B도 자신의 커밋 뒤 별도 트랜잭션에서 주문을 조회했으므로, 구매자는 취소 완료·발송 대기인 주문과 함께 요청 A가 추가한 발송 정보를 받았다(요청 B 커밋 17:46:38.970, 요청 B의 응답 조회 17:46:38.972~17:46:38.982).

저장된 발송 시각과 취소 시각의 차이는 두 요청의 실제 처리 간격을 뜻하지 않는다. 발송 등록은 주문을 조회하기 전에 현재 시각을 구하므로, 요청 A가 멈추기 전의 시각이 발송 시각으로 저장되었다(발송 시각 17:46:38.122, 요청 A 대기 시작 17:46:38.124). 반면 취소 시각은 요청 B가 재개된 뒤에 구한 시각이다(요청 B 재개 17:46:38.940, 취소 시각 17:46:38.945). 그래서 두 시각의 차이인 약 0.82초에는 요청을 멈춰 둔 시간이 들어 있다. 이 실행에서는 저장된 발송 시각이 취소 시각보다 앞서고 요청 A가 먼저 커밋되었지만, 처리 순서와 커밋 순서는 저장된 시각이 아니라 서버 로그와 p6spy 기록으로 판단했다([실행결과 분석](실행결과_분석.md)의 「분석01 2026-10-19」 중 「저장된 두 시각의 순서와 차이」).

## 10. 시스템 명세

**요청**

- 요청 A: `POST /ChatService/api/orders/43/shipment`, 판매자 로그인 쿠키, 본문 `{"carrierName":"편의점 택배","trackingNumber":"3621-0984-4170","requestId":"{UUID}"}`
- 요청 B: `POST /ChatService/api/orders/43/cancel`, 구매자 로그인 쿠키, 본문 `{"reason":"같은 의자를 선물받아 취소합니다."}`
- 두 요청의 헤더: `X-Test-Request-Name`(`A` 또는 `B`), `X-Test-Pause-At: ORDER_READ`.
- 주문 ID 조회: 판매자 `GET /ChatService/api/orders/sales`, 구매자 `GET /ChatService/api/orders/purchases`.
- 멈춘 요청 목록과 재개: `GET /ChatService/test-support/pauses`, `POST /ChatService/test-support/pauses/{요청 이름}/resume`([작업명세 07](../../작업명세/07_공통실행참조.md#request-pause)의 「2.3 요청 일시 중지」).

**코드**

- 발송 등록: `ShipmentService.register`에서 `timeRules.now()`로 시각을 구하고 `purchaseOrderRepository.findById`로 주문을 조회한 직후 `testPause.reach(PausePoint.ORDER_READ)`를 호출한다. 재개 후 조건을 검사하고 `shipmentRepository.save`와 `PurchaseOrder.markShipped`로 발송 정보와 배송 상태를 변경한다.
- 구매자 취소: 당사자 취소를 처리하는 `OrderCancellationService.cancelByParty`에서 `purchaseOrderRepository.findById` 직후 `testPause.reach(PausePoint.ORDER_READ)`를 호출한다. 재개 후 당사자·거래 상태·배송 상태를 검사하고 `cancel`을 호출한다.
- 취소 처리 순서: `WalletService.ensureCreditable` → `testPause.reach(PausePoint.WALLET_READ)` → `nowSupplier.get()` → `PurchaseOrder.cancel` → `WalletService.credit`. 이번 요청 헤더는 `ORDER_READ`이므로 지갑 조회 직후에는 멈추지 않는다.
- 요청 일시 중지: `TestPause`, `PausePoint`, `TestSupportController`(패키지 `com.chatservice.marketplace.testsupport`).
- 커넥션 번호: 요청 A는 변경 트랜잭션 26·응답 조회 27, 요청 B는 변경 트랜잭션 25·응답 조회 28.

**서버 설정**

- 테스트 지원 기능: `marketplace.test-support.enabled: true`. 환경변수로는 `MARKETPLACE_TEST_SUPPORT_ENABLED=true`.
- 스케줄러: `marketplace.scheduler.enabled: false`.
- 멈춘 요청의 최대 대기 시간: `marketplace.test-support.pause-timeout: PT30S`.
- DB 계정: `TOYCHAT_TEST`.
