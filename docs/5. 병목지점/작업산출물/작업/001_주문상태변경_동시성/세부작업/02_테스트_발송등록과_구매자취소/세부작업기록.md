## 2. 계획

[작업명세 03](../../작업명세/03_테스트계획_발송등록과_구매자취소.md)에 따라 다음 순서로 진행한다.

1. 테스트케이스를 정한다.
2. 발송 등록과 구매자 취소를 주문 조회 직후에 멈출 수 있도록 테스트 지원 코드를 바꾼다.
3. 테스트 데이터와 JMeter 계획을 만든다.
4. 테스트케이스마다 실행하고, 서버 로그를 정리해 결과를 기록한다.
5. 결과를 작업명세 03의 「4.3 예상 결과(가설)」와 비교해 분석한다.

### 계획 변경

- 2026-10-20: 테스트케이스2(실행02)의 주문을 이후 자동 처리(모의 배송 완료와 확인 기간 만료 자동 완료)까지 진행해, [작업명세 03](../../작업명세/03_테스트계획_발송등록과_구매자취소.md)의 「4.3 예상 결과(가설)」 표 아래에 적은 「구매자 취소가 먼저 커밋된 경우」의 영향, 곧 판매자에게도 판매대금이 지급되는지를 확인하기로 했다. 「4.3」은 이후 자동 처리를 테스트 절차에 넣지 않았으므로 이 확인은 실행03으로 따로 실행한다. 자동 처리는 스케줄러를 끈 채 테스트 지원 API로 실행한다([작업명세 07](../../작업명세/07_공통실행참조.md)의 「2.2 자동 처리 실행 API와 처리 기준 시각 설정 API」).

## 3. 진행 기록

### 2026-10-19 테스트케이스와 테스트 지원 코드 변경

- 테스트케이스를 두 개로 정했다. 두 요청을 모두 주문 조회 직후에 멈추고, 테스트케이스1은 요청 A(판매자의 발송 등록)를, 테스트케이스2는 요청 B(구매자의 주문 취소)를 먼저 재개한다. [작업명세 03](../../작업명세/03_테스트계획_발송등록과_구매자취소.md)의 「4.3 예상 결과(가설)」가 두 커밋 순서의 결과를 서로 다르게 예상하기 때문이다. 실행 절차는 같은 문서의 「4.2 실행 절차」에 있다.
- 두 요청을 모두 주문 조회 직후에 멈출 수 있도록 테스트 지원 코드를 고쳤다. 두 위치는 같은 중지 위치 이름 `ORDER_READ`를 쓰고, 어느 요청인지는 요청 이름(A, B)으로 구분한다.
  - `src/main/java/com/chatservice/marketplace/order/service/ShipmentService.java`: 발송 등록이 주문을 조회한 직후, 판매자인지와 거래가 끝났는지를 검사하기 전에 멈추도록 했다.
  - `src/main/java/com/chatservice/marketplace/order/service/OrderCancellationService.java`: 2026-10-16에 주석 처리했던 당사자 취소의 주문 조회 직후 일시 중지 호출을 다시 켰다.
  - `src/main/java/com/chatservice/marketplace/testsupport/PausePoint.java`, `TestPause.java`: `ORDER_READ`의 설명과 일시 중지 코드의 주석이 발송 등록까지 가리키도록 고쳤다.
- 발송 등록과 당사자 취소가 현재 시각을 구하는 위치는 바꾸지 않았다. 테스트가 운영 코드의 동작을 그대로 확인하도록 하기 위해서다. 그래서 발송 등록은 주문을 조회하기 전, 곧 멈추기 전에 구한 시각을 발송 시각으로 저장하고, 당사자 취소는 재개된 뒤에 구한 시각을 취소 시각으로 저장한다.
- 「4. 실행 기록」의 「실행01 2026-10-19」는 이 변경을 적용한 서버로 실행했다.

  - `src/main/java/com/chatservice/marketplace/testsupport/TestSupportJobController.java`를 추가했다. 모의 배송 완료와 확인 기간 만료 자동 완료를 파라미터 `now`의 시각으로 한 번 실행하고 처리한 주문 수를 돌려준다. `now`를 생략하면 서버의 현재 시각을 쓴다. 테스트 설정이 켜져 있을 때만 등록된다.
  - 스케줄러와 서비스 코드는 고치지 않았다. 두 API는 스케줄러가 부르는 자동 처리 메서드를 그대로 부른다.
