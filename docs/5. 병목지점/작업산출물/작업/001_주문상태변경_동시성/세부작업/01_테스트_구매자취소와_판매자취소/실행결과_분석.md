### 분석 내용

**두 요청이 모두 200을 받은 이유**

두 실행 모두 두 요청이 요청 A의 커밋보다 먼저 주문을 조회했다. 실행01에서는 요청 B가 15:20:44.819, 요청 A가 15:20:44.865에 주문 4를 조회했고, 요청 A는 15:20:45.228에 커밋했다. 실행02에서는 요청 B가 17:17:46.821, 요청 A가 17:17:46.825에 주문 26을 조회했고, 요청 A는 17:17:47.085에 커밋했다.

취소 요청은 잠금 없이 주문을 조회하고, 같은 트랜잭션에서 조회한 주문으로 거래가 끝났는지 검사한다. 재개된 요청은 처음부터 다시 처리하지 않고 멈추기 전에 조회한 주문으로 이어서 처리한다([작업명세 02](../../작업명세/02_테스트계획_구매자취소와_판매자취소.md)의 「4.2 실행 절차」). 그래서 요청 B는 요청 A가 커밋한 취소 완료 상태를 보지 못하고, 진행 중인 주문으로 검사를 통과했다.

두 실행은 요청 B가 이 검사를 한 시점이 다르다. 실행01은 주문 조회 직후에 멈추므로, 요청 B의 검사는 요청 A의 커밋 뒤인 재개(15:20:45.432) 이후에 실행되었다. 실행02는 검사를 마친 뒤 지갑 조회 직후에 멈추므로, 요청 B는 요청 A가 재개되기 전에 이미 검사를 통과했다. 어느 경우든 요청 B가 검사에 쓴 주문은 요청 A가 커밋하기 전에 조회한 주문이다.

**구매자 잔액이 두 실행에서 다르게 나온 이유**

두 실행의 구매자 잔액이 다른 이유는 요청 B가 구매자 지갑을 조회한 시점이 다르기 때문이다.

실행01에서 요청 B는 재개된 뒤 15:20:45.434에 구매자 지갑을 조회했다. 이 조회는 요청 A의 커밋(15:20:45.228) 뒤이므로, 요청 A가 반환한 뒤의 잔액을 읽었다. 요청 B는 이어서 지갑 잔액과 취소 반환 내역의 변동 후 잔액을 750,000원으로 저장했다. 750,000원은 요청 A가 저장한 400,000원에 결제액 350,000원을 더한 값이다. 결제액이 구매자에게 두 번 반환되었고, 잔액과 잔액 변동 내역은 서로 맞는다.

실행02에서는 두 요청 모두 요청 A의 커밋(17:17:47.085) 전에 구매자 지갑을 조회한 뒤 멈췄다(요청 B 17:17:46.825, 요청 A 17:17:46.827). 요청 B는 재개된 뒤 지갑을 다시 조회하지 않았고, 재개 뒤 첫 SQL은 취소 반환 내역 추가(17:17:47.290)였다. 반환액을 더하는 처리는 같은 트랜잭션에서 잔액 범위 검사 때 조회한 지갑 객체를 다시 쓴다([작업명세 02](../../작업명세/02_테스트계획_구매자취소와_판매자취소.md)의 「7. 참조 자료」의 `WalletService.credit`). 그래서 두 요청은 각자 멈추기 전에 조회한 50,000원에 350,000원을 더해, 지갑 잔액과 변동 후 잔액을 모두 400,000원으로 저장했다. 요청 B가 같은 값으로 잔액을 덮어써 잔액에는 반환이 한 번만 반영되었고, 취소 반환 내역은 두 건 남았다.

p6spy는 SELECT로 읽은 값을 기록하지 않는다. 그래서 두 실행에서 요청 B가 읽은 잔액은 이어서 저장한 값으로 확인했다.

**최종 주문의 취소 정보가 요청 A의 응답과 다른 이유**

두 실행 모두 두 요청의 주문 UPDATE는 주문 ID를 뺀 모든 열을 다시 쓰는 문장이었고, 조건은 주문 ID 하나였다. 그래서 나중에 커밋한 요청 B의 UPDATE가, 요청 A가 저장한 취소 주체와 취소 사유를 판매자와 요청 B의 사유로 덮어썼다.

요청 A의 응답은 요청 A가 커밋한 뒤, 요청 B가 재개되기 전에 별도 트랜잭션에서 주문을 다시 조회해 만들었다(실행01 15:20:45.229~15:20:45.236, 실행02 17:17:47.087~17:17:47.097). 그래서 요청 A의 응답에는 구매자가 취소 주체로 담겼고, 최종 주문의 취소 주체와 달랐다.

**결과 확인 기준에 드러난 방식**

실행01에서는 구매자 지갑 잔액과 잔액 변동 내역 합계가 모두 750,000원으로 같아, 지갑 잔액과 내역 합계를 비교하는 기준 2에는 행이 나오지 않았다. 실행02에서는 지갑 잔액 400,000원과 내역 합계 750,000원이 달라 기준 2에 행이 나왔다. 실행02의 지갑 잔액은 정상 동작의 잔액인 400,000원과 같으므로, 잔액만 보면 이상을 알 수 없다.

두 실행 모두 주문별 반환 내역의 건수를 보는 기준 3에서 취소 반환 2건이 드러났다. 이 차이는 작업명세 02의 「4.3 예상 결과와 확인 방법」이 중지 위치마다 설명한 확인 방법과 같다.

### 분석 결과

두 실행 모두 작업명세 02의 「4.3 예상 결과와 확인 방법」에 적은 가설과 같은 결과가 나왔다. 두 요청이 요청 A의 커밋 전에 조회한 주문으로 취소 조건을 검사해 둘 다 성공했고, 두 실행에서 다른 점은 요청 B가 구매자 지갑을 조회한 시점이었다.

요청 B가 요청 A의 커밋 뒤에 지갑을 조회한 실행01에서는 결제액이 두 번 반환되어 구매자 잔액이 정상 금액보다 350,000원 많았다. 두 요청이 모두 커밋 전에 지갑을 조회한 실행02에서는 잔액에 반환이 한 번만 반영되어, 잔액과 잔액 변동 내역 합계가 350,000원 어긋났다. 두 실행 모두 최종 주문에는 나중에 커밋한 요청 B의 취소 정보가 남아, 먼저 성공한 요청 A의 응답과 달랐다.

### 시스템 명세

- 주문 취소: `OrderCancellationService.cancelByParty`가 주문 조회, 당사자·거래 상태·배송 상태 검사를 한 뒤 공통 처리 `cancel`을 부른다. `cancel`은 `WalletService.ensureCreditable`(지갑 조회와 잔액 범위 검사), `PurchaseOrder.cancel`, `WalletService.credit`(잔액 증가와 `CANCEL_REFUND` 기록) 순서로 처리한다
- 응답 생성: `OrderController`가 취소 트랜잭션을 커밋한 뒤 주문을 다시 조회해 응답 본문을 만든다
- 커넥션 번호: 실행01은 요청 A 379(데이터를 바꾼 트랜잭션)·380(응답 조회), 요청 B 378·381이다. 실행02는 요청 A 35·36, 요청 B 34·37이다
- 주문 UPDATE(바인딩 전):

  ```sql
  update PURCHASE_ORDER set BUYER_ID=?,CANCEL_REASON=?,CANCELLED_BY=?,COMPLETION_CAUSE=?,CONFIRMED_AT=?,DELIVERED_AT=?,FINALIZED_AT=?,INSPECTION_DEADLINE_AT=?,OFFER_ID=?,PAID_AMOUNT=?,PRICE_SOURCE=?,PRODUCT_ID=?,QUANTITY=?,RECIPIENT_NAME=?,REQUEST_ID=?,SELLER_ID=?,SHIP_DEADLINE_AT=?,SHIPPING_ADDRESS=?,SHIPPING_STATUS=?,TRADE_STATUS=?,UNIT_PRICE=? where ORDER_ID=?
  ```
