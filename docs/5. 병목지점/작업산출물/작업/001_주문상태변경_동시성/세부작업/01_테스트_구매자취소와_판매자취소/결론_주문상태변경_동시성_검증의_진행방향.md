# 결론: 주문 상태 변경 동시성 검증의 진행 방향

- 작성일: 2026-10-18
- 세부작업기록: [세부작업기록](세부작업기록.md)
- 작업기록: [작업기록](../../작업기록.md)

## 1. 결정 대상

2026-10-16에 구매자 취소와 판매자 취소의 문제 확인 테스트를 마친 뒤, 나머지 네 상황의 경합 지점도 확인한 뒤 다섯 상황에 적용할 정책과 보호 방식을 함께 정하기로 했다. 정책은 겹친 요청 가운데 어느 처리를 인정하고 기한 준수 여부를 어떤 시각으로 판단할지를 뜻한다. 보호 방식은 그 정책에 따라 주문과 지갑 등이 변경되도록 하는 구현 방법이다. 이번에 정한 것은 이를 결정할 범위와 진행 순서이며, 구체적인 구현 방법은 아직 선택하지 않았다.

작업 「001 주문상태변경_동시성」에서는 결제가 끝난 주문 하나에 구매자·판매자의 요청과 자동 처리가 겹칠 때, 주문이 취소 완료·정상 완료·환불 완료 가운데 하나로만 끝나는지 확인한다. 요구사항 BR-005가 정한 이 규칙을 실제 요청과 Oracle 데이터로 검증한다. 작업은 문제 확인, 충돌 조건 확인, 정책 결정, 구현, 정책 검증의 다섯 과정으로 진행한다. 각 과정의 목적은 [작업기록](../../작업기록.md)의 「2. 작업 계획」과 [작업명세 01 테스트계획_공통](../../작업명세/01_테스트계획_공통.md)의 「1. 검증 목적과 범위」에 있다.

주문 상태 변경 동시성 검증은 다음 다섯 상황을 대상으로 한다. 지금까지 실행한 것은 구매자 취소와 판매자 취소가 겹치는 테스트이며, 나머지 네 상황은 작업명세 03~06에 계획만 있고 실행하지 않았다.

## 3. 검토한 대안

### 대안: 당사자 취소에 낙관적 락을 적용하고 검증을 마무리한다

주문을 조회했을 때의 버전을 갱신 시점에 다시 검사하는 방식이다. 요청 A가 먼저 주문을 바꾸고 커밋하면 요청 B의 주문 UPDATE는 버전 조건을 만족하지 못해 실패한다. 이때 같은 트랜잭션에서 수행한 지갑 갱신과 반환 내역 추가도 함께 롤백된다. 따라서 테스트케이스1의 중복 반환과 테스트케이스2의 잔액·내역 불일치를 막을 수 있다고 검토했지만, 실제 적용과 재검증은 하지 않았다. 당사자 취소에 바로 적용하는 대안으로는 채택하지 않았으며, 이유는 「6. 채택하지 않은 대안과 이유」에 적었다.

### 대안: 당사자 취소의 주문 조회에만 비관적 락을 적용한다

주문을 조회할 때 행을 잠그고 트랜잭션이 끝날 때까지 잠금을 유지하는 방식이다. 구매자 취소와 판매자 취소가 모두 이 방식으로 주문을 조회하면, 나중 요청은 앞선 요청이 끝난 뒤 변경된 주문 상태로 취소 조건을 검사한다. 두 취소가 모두 성공하는 문제를 막을 수 있다고 검토했지만, 취소 처리에만 적용하는 대안으로는 채택하지 않았다.

### 대안: 격리 수준을 SERIALIZABLE로 바꾼다

트랜잭션이 시작된 뒤 다른 트랜잭션이 변경하고 커밋한 행을 갱신하려 하면 오류가 발생하는 격리 수준이다. 2026-10-16의 별도 실험에서 이 동작을 확인했다. 실험 조건과 결과는 「9.3 격리 수준에 관해 확인한 범위」에 적었다. 주문 상태 변경에 적용할 방식으로 확정하지 않고, 이후 다른 보호 방식과 비교할 후보로 남겼다.

### 대안: 주문 상태를 변경하는 모든 처리의 경합 지점을 확인한 뒤 정책과 보호 방식을 함께 정한다

나머지 네 상황의 문제 확인 테스트에서 각 요청이 주문·지갑·발송 정보·환불 요청을 조회하고 변경하는 순서를 확인한다. 어떤 처리가 겹칠 때 문제가 생기는지 정리한 뒤 다섯 상황에 적용할 정책을 정하고, 그 정책을 지킬 수 있는 구현 방법을 비교한다. 이 대안을 채택했다.

## 4. 결정 내용

### 4.1 정책과 보호 방식을 정할 범위

당사자 취소에는 지금 경합을 막는 코드를 추가하지 않는다. 나머지 네 상황의 문제 확인 테스트를 마치고 기능별 경합 지점을 정리한 뒤, 다섯 상황의 결과를 바탕으로 정책과 보호 방식을 함께 정한다. 작업의 다섯 과정은 유지한다. 다만 상황 하나마다 정책 결정·구현·정책 검증을 끝내지 않고, 이 세 과정은 다섯 상황을 대상으로 진행한다.

두 취소 요청의 테스트 결과는 잠금 없이 주문을 읽고 취소 조건을 검사한 뒤 변경하는 구조에서 두 취소가 모두 성공했다는 증거로 사용한다. 실행02에서는 두 요청이 이전에 읽은 잔액으로 각각 계산한 값을 저장해, 반환 내역은 두 건인데 잔액에는 한 건만 반영되는 갱신 손실도 확인했다. 이 결과를 근거로 지갑 행의 보호 방식은 취소뿐 아니라 같은 지갑을 바꾸는 결제·충전·다른 주문의 반환과 지급을 함께 검토해 정한다. 이번 두 취소 요청의 테스트에서는 결제·충전·다른 주문의 처리와 취소가 겹치는 상황까지 실행하지 않았다.

### 4.2 정책 결정 과정에서 정할 것

요구사항이 이미 정한 결과와 처리 기준은 그대로 따른다. BR-005에 따르면 한 거래는 정상 완료·환불 완료·취소 완료 가운데 하나로만 끝나야 하며, 판매대금 지급과 구매자 반환이 함께 이루어져서는 안 된다. F-012는 반복 취소나 자동 취소와 겹쳐도 반환은 한 번이어야 하고, 실패하면 취소·잔액·기록이 일부만 반영되어서는 안 된다고 정했다. 따라서 구매자 취소와 판매자 취소가 겹쳐도 반환을 한 번만 처리해야 한다는 결과가 이미 정해져 있다.

구매자 취소와 발송 등록 가운데 어느 쪽을 인정할지는 정책 결정 과정에서 정한다. F-011과 F-012는 둘이 동시에 성립할 수 없다고 정하지만 어느 쪽을 인정할지는 명시하지 않았다. 미발송 자동 취소와 발송 등록의 경합에는 F-013의 기준을 따른다. 유효 발송이 먼저 성립하면 자동 취소하지 않고, 자동 취소가 먼저 성립하면 발송을 거절한다. 구매자 취소와 자동 취소는 같은 공통 메서드를 호출하므로, 구매자 취소와 발송 등록의 경합에 다른 기준을 적용하려면 두 취소를 구분해 처리해야 한다.

발송 기한·확인 기한·응답 기한이 있는 세 상황에서는 기한을 지켰는지를 처리 시작 시각으로 판단할지, 커밋 시각으로 판단할지, 유예 시간을 둘지를 정한다. 주문 행의 보호 방식은 정한 시간 기준과 취소·발송 등록의 처리 우선순위를 지킬 수 있어야 한다. 선택한 방식은 주문 행을 바꾸는 모든 처리에 적용한다. 이러한 정책과 구현 방법은 아직 정하지 않았다.

비교할 보호 방식은 조건부 UPDATE, 비관적 락, 낙관적 락, SERIALIZABLE이다. 지갑에는 DB에서 최신 잔액에 금액을 더하는 원자적 갱신도 후보로 둔다. 이 방식은 다른 요청이 변경하기 전의 잔액으로 계산한 값을 덮어쓰는 갱신 손실을 막지만, 반환 처리가 두 번 실행되면 두 금액을 모두 더한다. 따라서 중복 반환은 주문을 변경하는 단계에서 막아야 한다.

### 4.3 진행 순서

1. 구매자 취소와 판매자 취소의 문제 확인 결과를 세부작업기록, 실행결과 분석, 테스트결과서 두 개로 기록해 마무리한다.
2. 나머지 네 상황의 문제 확인 테스트를 실행하고 기능별 경합 지점을 정리한다. 발송 등록·환불·완료 처리에 요청 일시 중지 위치를 두고, 기한이 있는 세 상황에는 서버 시계 설정과 자동 처리 실행 API를 만든다. 코드 변경은 수정안을 먼저 검토한 뒤 진행한다.
3. 각 기능에서 확인한 경합 지점을 바탕으로 「4.2 정책 결정 과정에서 정할 것」에 적은 처리 우선순위와 시간 기준을 정한다. 지갑은 같은 회원의 결제·충전·다른 주문의 반환과 지급까지 함께 검토한다.
4. 보호 방식 후보를 같은 테스트로 비교한다. 거절된 요청이 받는 응답, 대기 시간, 관계없는 요청에 미치는 영향을 측정한다.
5. 고른 방식으로 구현하고, 같은 테스트를 다시 실행해 정한 정책대로 처리되는지 확인한다.

작업 계획의 두 번째 과정인 충돌 조건 확인은 유지하며, 위 진행 순서에서 언제 수행할지는 이번에 정하지 않았다.

### 4.4 결정 시점만 정한 사항

동시 전송 반복 테스트를 계속 수행할지는 이후 작업 순서를 정할 때 결정한다. 같은 지갑이나 재고를 여러 요청이 바꾸는 상황(결제, 충전, 다른 주문의 반환과 지급)과, 응답을 받지 못한 결제 요청을 같은 요청 ID로 다시 보내는 상황을 주문 상태 변경 동시성 검증과 함께 진행할지는 각 테스트를 마치고 결과를 종합해 검토할 때 정한다.

## 5. 결정 이유

### 5.1 지갑을 조회한 시점에 따라 반환 결과가 달랐다

구매자 취소와 판매자 취소의 테스트는 미니PC에 배포한 ChatService 서버와 미니PC Oracle의 테스트 전용 계정으로 실행했다. 요청 A는 구매자의 주문 취소이고, 요청 B는 판매자의 주문 취소다. 서버가 두 요청을 지정한 위치에서 멈추면 JMeter의 재개 제어 스레드가 요청 A를 먼저 재개했다. 취소 응답은 커밋 이후에 생성되므로, 요청 A의 응답을 받은 뒤 요청 B를 재개해 커밋 순서를 정했다.

[실행결과 분석](실행결과_분석.md)의 「분석01 2026-10-16」에 따르면 두 실행 모두 두 요청이 요청 A의 커밋 전에 주문을 조회했다. 실행01의 요청 B는 요청 A가 커밋한 뒤에 재개되어 취소 조건을 검사했지만, 검사에는 멈추기 전에 읽은 주문 상태를 사용했다. 실행02의 요청 B는 멈추기 전에 이미 취소 조건 검사를 통과했다. 검사 시점은 달랐지만, 두 실행 모두 요청 B가 취소 전 주문 상태로 검사를 통과해 처리를 계속했다.

구매자 지갑을 조회한 시점은 두 실행에서 달랐다. 실행01의 요청 B는 요청 A의 커밋 뒤에 지갑을 조회하고 잔액을 750,000원으로 저장했다. 실행02에서는 두 요청 모두 요청 A의 커밋 전에 지갑을 조회했으며, 요청 B는 재개 후 지갑을 다시 조회하지 않고 잔액을 400,000원으로 저장했다.

p6spy 로그에는 SELECT 결과값이 없어 조회한 잔액을 직접 확인할 수 없다. 저장한 잔액과 반환액을 더하는 코드를 대조하면, 실행01의 요청 B는 400,000원에 350,000원을 더했고 실행02의 요청 B는 50,000원에 350,000원을 더한 것으로 해석된다.

실행01에서는 결제액이 두 번 반환되었지만 잔액과 내역 합계가 같아 기준 2의 조회 결과가 없었다. 실행02에서는 잔액이 정상 금액과 같았지만 반환 내역이 두 건 남아, 내역 합계와 잔액이 다른 회원을 조회하는 기준 2에서 문제가 확인되었다. 주문별 반환 내역 건수를 확인하는 기준 3에서는 두 실행 모두 조회 결과가 나왔다. 잔액만으로는 실행02의 문제를, 잔액과 내역 합계의 비교만으로는 실행01의 문제를 발견할 수 없었다.

두 실행의 주문 UPDATE는 주문 ID를 뺀 모든 열을 다시 썼고, 조건은 주문 ID 하나였다. 나중에 커밋한 요청 B가 요청 A의 취소 주체와 사유를 덮어썼다. 요청 A의 응답은 요청 B가 재개되기 전에 별도 트랜잭션에서 조회한 주문으로 만들었으므로, 취소 주체가 구매자로 표시되었다.

### 5.2 주문과 지갑의 변경을 한 트랜잭션으로 처리해도 갱신 손실이 발생했다

당사자 취소의 주문 갱신, 지갑 갱신, 취소 반환 내역 추가는 요청마다 한 트랜잭션으로 처리한다. 실행02의 요청 A도 세 SQL 문장을 같은 커넥션에서 실행하고 한 번의 커밋으로 확정했다. 그런데 요청 B는 요청 A가 커밋한 뒤에도 이전에 조회한 주문 상태와 잔액으로 처리를 계속했다. 변경을 한꺼번에 확정하는 트랜잭션만으로는, 조회 이후 다른 요청이 바꾼 값을 반영해 검사하거나 계산하도록 할 수 없었다.

회원 한 명의 지갑 행은 여러 기능에서 변경한다. 같은 회원의 다른 주문 결제·취소 반환·환불·충전과, 그 회원이 판매자일 때의 판매대금 지급이 모두 같은 행을 바꾼다. 주문 행에서 중복 종료를 막더라도 다른 주문의 처리나 충전이 같은 지갑을 변경할 때 생기는 갱신 손실은 막지 못한다. 따라서 지갑 행의 보호 방식은 이러한 처리들을 함께 검토해 정하기로 했다.

### 5.3 같은 주문을 바꾸는 처리들은 함께 검토해야 한다

다섯 상황 각각에서는 두 처리가 같은 주문 행을 변경한다. 특히 당사자 취소와 미발송 자동 취소는 같은 취소 메서드를 사용한다. 행 잠금이나 조건부 UPDATE를 사용하려면 겹치는 두 처리에 모두 적용해야 한다. 주문 엔티티에 낙관적 락을 적용하면 주문을 변경하는 모든 처리에서 버전을 검사한다. 따라서 구매자 취소와 판매자 취소의 결과만 보고 방법을 고르면 다른 상황의 정책을 정하기 전에 구현이 처리 결과를 결정하거나, 일부 처리에는 필요한 잠금과 조건 검사가 빠질 수 있다.

일부 처리는 주문 외의 행도 조회한다. 발송 등록은 기존 발송 정보가 있는지, 환불 요청은 기존 환불 요청이 있는지 확인한다. 판매자 응답은 주문 다음에 환불 요청을 조회하지만, 무응답 자동 환불은 환불 요청 다음에 주문을 조회한다. 이 조회 순서는 [세부작업기록](세부작업기록.md)의 「2026-10-13 상황별 중지 위치와 예상 결과 설계」에 기록되어 있다. 발송 정보와 환불 요청의 조회·추가도 확인해야 하므로 주문 취소의 두 실행만으로 전체 보호 방식을 정하지 않는다.

구매자 취소와 미발송 자동 취소는 각각 발송 등록과 겹칠 수 있다. 구매자 취소와 발송 등록 중 어느 처리를 인정할지 정할 때는 미발송 자동 취소에 이미 정해진 기준과 공통 취소 메서드를 함께 고려해야 한다. 기한이 있는 세 상황에는 기한 직전의 당사자 요청과 기한 직후의 자동 처리가 겹친다는 공통점도 있어, 시간 기준을 함께 검토해야 한다. 구매자 취소와 판매자 취소가 겹치는 테스트만으로는 이 기준들을 정할 수 없다. 지금 당사자 취소에 경합을 막는 코드를 추가하면 이후 정책에 맞춰 다시 고쳐야 할 수 있으므로, 다섯 상황의 경합 지점을 먼저 확인하기로 했다.

## 6. 채택하지 않은 대안과 이유

낙관적 락을 지금 적용하려면 두 DB 계정의 주문 테이블에 버전 열을 추가하고, 버전 충돌 예외가 발생했을 때 409 응답을 반환하도록 해야 한다. 현재 SQL 실행 순서에서는 반환 내역을 추가한 뒤, 커밋 직전의 주문 UPDATE에서 충돌을 확인하고 트랜잭션을 롤백하게 된다. 또한 주문을 변경하는 모든 처리에서 먼저 커밋한 쪽이 성공하므로, 구매자 취소와 발송 등록 중 어느 쪽을 인정할지 정하기 전에 처리 결과가 이 규칙으로 결정된다. 주문 버전만으로는 다른 주문이나 충전이 같은 지갑을 바꿀 때의 갱신 손실도 막지 못한다. 이 때문에 당사자 취소에 바로 적용하지 않았다.

취소 요청의 주문 조회에만 비관적 락을 적용하면 두 취소가 동시에 진행되는 것은 막을 수 있다. 그러나 발송 등록·환불·완료 처리는 여전히 잠금 없이 주문을 읽으므로, 취소와 이 처리들이 겹치는 문제는 남는다. 주문 행의 잠금은 지갑 행에 적용되지 않으며, 두 행을 모두 잠그려면 잠금 순서도 정해야 한다. 요청 B가 주문 조회에서 기다리게 되므로, 두 요청을 모두 멈춘 뒤 재개하는 현재 테스트 절차도 정책 검증 때 바꿔야 한다. 이 때문에 당사자 취소의 조회만 바꾸는 대안은 채택하지 않았다.

SERIALIZABLE을 적용한 별도 실험에서는 다른 트랜잭션이 변경하고 커밋한 행을 갱신하려 할 때 오류가 발생했다. 실패한 처리를 다시 시도하려면 새 트랜잭션에서 조회부터 실행하도록 해야 한다. 또한 조회 후 서로 다른 행을 INSERT하는 중복은 이 격리 수준만으로 막지 못한다는 점을 검토했으나, 이 동작은 직접 확인하지 않았다. 따라서 격리 수준 변경을 해결 방식으로 확정하지 않고 다른 후보와 함께 비교하기로 했다.

### 9.1 실행 환경과 테스트용 변경

테스트한 애플리케이션은 미니PC에서 실행한 ChatService 서버이며 주소는 `http://wherehouse.it.kr:8186/ChatService/`다. DB는 미니PC Oracle의 `TOYCHAT_TEST` 계정이다. 요청은 노트북의 JMeter로 보냈다.

중지 위치 1은 `OrderCancellationService.cancelByParty`의 주문 조회 직후이며, 중지 위치 2는 공통 취소 메서드 `cancel`에서 `walletService.ensureCreditable`을 호출한 직후다. 2026-10-16에 중지 위치 1의 일시 중지 호출을 주석 처리했다. 당사자 취소의 시각도 중지 전에 구하던 것을 중지 위치 2에서 재개된 뒤에 구하도록 바꿨다. 실행02는 이 변경을 적용한 서버로 실행했다. 테스트를 위한 변경이므로 두 요청의 경합을 막지는 않는다. 근거는 [세부작업기록](세부작업기록.md)의 「2026-10-16 테스트케이스2를 위한 중지 위치와 취소 시각 변경」이다.

현재는 주문 취소 처리의 중지 위치 2에서만 요청을 멈출 수 있다. 서버 시계 설정과 자동 처리 실행 API는 아직 구현하지 않았다.

### 9.2 주문과 지갑을 바꾸는 처리

주문 하나는 `PURCHASE_ORDER`의 행 하나이고, 회원의 지갑은 `WALLET`의 행 하나다. 다음은 각 처리에서 주문과 지갑을 바꾸는 메서드다.

| 처리 | 메서드 | 주문 행 변경 | 지갑 행 변경 |

| 미발송 자동 취소 | `OrderCancellationService.cancelIfStillExpired` → `cancel` | 취소 완료 | 구매자에게 결제액 반환 |

| 환불 요청 | `RefundService.requestRefund` | 보류로 변경(`hold`) | 없음 |
| 수령 확인·확인 기간 만료 자동 완료 | `TradeCompletionService` → `complete` | 정상 완료 | `credit`으로 판매대금 지급 |
| 판매자 환불 동의·무응답 자동 환불 | `RefundService` → `refund` | 환불 완료 | `credit`으로 구매자에게 환불 |
| 판매자 환불 거절 | `RefundService` → `TradeCompletionService.complete` | 정상 완료 | 판매대금 지급 |
| 결제 | `OrderService.placeOrder` | 주문 생성 | `debitForPurchase`로 구매자 잔액에서 결제액 차감 |
| 충전 | `WalletService.charge` | 없음 | 충전 |

발송 등록은 `SHIPMENT`를 조회하고 발송 정보를 추가하며, 환불 요청은 `REFUND_REQUEST`를 조회하고 환불 요청을 추가한다. 당사자 취소의 반환 내역은 `BALANCE_TRANSACTION`에 `CANCEL_REFUND`로 기록한다.

JPA는 조회한 지갑 엔티티를 영속성 컨텍스트에 보관한다. 현재 코드에서는 같은 트랜잭션에서 `ensureCreditable`이 조회한 지갑 객체를 `credit`에서도 사용한다. Java에서 그 객체의 잔액에 금액을 더하고, flush 때 계산한 잔액을 저장하는 UPDATE를 실행한다. 주문 UPDATE는 `ORDER_ID`만 조건으로 사용하며 ID를 제외한 모든 열을 다시 쓴다.

지갑 UPDATE에는 계산이 끝난 잔액만 전달되므로, DB에서 계산에 사용한 잔액의 조회 시점을 확인할 수 없다. JPA를 사용하지 않고 SQL로 직접 처리하더라도, 먼저 조회한 잔액으로 계산한 뒤 그 값을 저장하면 같은 갱신 손실이 생길 수 있다.

낙관적 락은 주문 엔티티에 `@Version`을 두는 방법을 검토했다. 이를 적용하려면 `TOYCHAT`과 `TOYCHAT_TEST`의 주문 테이블에 버전 열을 추가하는 DDL을 실행해야 한다. 비관적 락은 주문 조회에 `SELECT ... FOR UPDATE`를 사용하는 방법이다. 조건부 UPDATE는 검사 조건을 UPDATE의 WHERE 절에 넣고 변경된 행이 0개이면 요청을 거절하는 방법이다. 지갑의 원자적 갱신은 `BALANCE = BALANCE + 금액`처럼 DB에서 최신 잔액에 금액을 더하는 방법이다. 이 구현 방법들은 아직 적용하지 않았다.

### 9.3 격리 수준에 관해 확인한 범위

현재 격리 수준은 READ COMMITTED다. Oracle 문서에 근거해 검토한 내용에 따르면, UPDATE는 문장 시작 시점에 커밋된 내용으로 대상 행을 찾는다. 다른 트랜잭션이 그 행을 잠그고 있으면 해당 트랜잭션이 끝날 때까지 기다린다. 앞선 트랜잭션이 커밋하면 WHERE 조건에 사용한 열이 바뀌었는지 확인한다. 바뀌지 않았으면 최신 행에 UPDATE를 실행하고, 바뀌었으면 문장을 처음부터 다시 실행한다. 이 잠금 대기와 조건 재확인 과정은 구매자 취소와 판매자 취소의 두 실행에서 직접 확인하지 않았다.

UPDATE에서 다시 확인하는 조건에 Java에서 앞서 검사한 거래 상태는 포함되지 않는다. 주문 UPDATE의 조건은 주문 ID 하나이므로, 앞선 취소가 커밋된 뒤에도 같은 주문 행을 변경할 수 있다.

SERIALIZABLE에서는 트랜잭션 시작 시점의 데이터를 읽는다. 그 뒤 다른 트랜잭션이 변경하고 커밋한 행을 갱신하려 하면 `ORA-08177`로 실패한다. 문서에 근거해 검토한 내용에 따르면 같은 트랜잭션에서 다시 실행해도 조회 기준 시점은 같으므로, 재시도하려면 새 트랜잭션에서 조회부터 실행해야 한다. 조회 결과에 행이 없어 두 트랜잭션이 각각 새 행을 INSERT하는 중복은 이 격리 수준만으로 막지 못한다는 점도 검토했으나, 직접 실험하지는 않았다.

2026-10-16에는 `TOYCHAT_TEST`에 ID·상태·잔액 열이 있는 실험용 테이블을 만들고 행 하나를 넣었다. SQL Developer의 두 세션에서 이 행을 조회하고 변경했다. 구매자 취소와 판매자 취소의 테스트 데이터는 사용하지 않았으며 결과 화면은 파일로 저장하지 않았다.

실험 1에서는 SERIALIZABLE로 세션 1의 트랜잭션을 시작해 행을 조회한 뒤, 세션 2가 같은 행을 바꾸고 커밋했다. 세션 1은 다시 조회해도 처음 값을 읽었고, 같은 행의 UPDATE는 `ORA-08177`로 실패했다. 세션 1의 트랜잭션을 롤백하고 새 트랜잭션에서 실행하자 같은 UPDATE가 성공했다.

실험 2에서는 READ COMMITTED로 같은 순서를 실행했다. 세션 1의 UPDATE는 오류 없이 실행되어 세션 2가 커밋한 값을 덮어썼다. 두 실험에서 확인한 것은 실험용 행의 조회와 갱신 결과이며, 주문 상태 변경 처리에 격리 수준을 적용해 검증한 결과는 아니다.
