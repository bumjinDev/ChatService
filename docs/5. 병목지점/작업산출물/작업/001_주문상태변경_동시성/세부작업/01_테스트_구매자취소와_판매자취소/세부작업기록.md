# 01 테스트 구매자취소와_판매자취소

## 1. 개요

### 1.1 유형

테스트

### 1.2 목적과 범위

S1의 다섯 상황의 테스트 계획(작업명세 01~07)을 세우고, 작업명세 02(S1-1, 구매자 취소와 판매자 취소)의 겹침 재현 테스트를 실행해 결과를 기록한다.

## 2. 계획

세부 작업을 시작할 때 세운 계획은 다음과 같다.

1. 기준 자료를 처음부터 끝까지 읽는다.
2. 보고서의 코드 근거 가운데 S1에 쓰이는 항목을 원본 코드로 다시 확인한다.
3. S1-1~S1-5마다 회원, 상품, 주문 전에 보내는 요청, 겹치는 두 요청의 형태를 정한다.
4. 두 요청의 처리 순서별 예상 결과와, 결과를 확인할 기준과 SQL을 실행 전에 정한다.
5. 실행 방법과 테스트 코드 추가 계획을 정한다.
6. 사용자에게 확인을 받는다.

### 계획 변경

- 2026-10-13: 이 세부 작업의 결과를 문제 확인 과정의 테스트 계획(작업명세 01~07)으로 정했다. 실행 방법은 테스트 지원 기능을 넣은 미니PC 배포 서버와 JMeter다.

## 3. 진행 기록

### 2026-10-13 진행 방식 결정

- 작업 과정을 문제 확인 과정, 충돌 조건 확인 과정, 정책 결정 과정, 구현 과정, 정책 검증 과정 순서로 정했다.
- 문제 확인 과정에서 겹침 재현 테스트와 동시 전송 반복 테스트를 함께 하기로 했다. 겹침 재현 테스트는 서버가 두 요청이 겹친 상태를 직접 만들고, 동시 전송 반복 테스트는 JMeter로 두 요청을 같은 순간에 반복해 보낸다. 두 테스트 모두 같은 서버와 JMeter로 하고, 요청 일시 중지는 겹침 재현 테스트에서만 켠다.
- 테스트 지원 기능으로 서버 시계 설정, 자동 처리 실행 API, 요청 일시 중지를 두기로 했다.
- 테스트 환경을 미니PC 배포 서버로 정했다. 테스트 지원 기능은 운영 코드에 넣고 테스트 설정을 켰을 때만 동작하게 하며, 테스트하는 동안만 DB 계정을 `TOYCHAT_TEST`로 바꾼다. 결과 확인 SQL은 SQL Developer로 실행한다.
- 실제 스케줄러의 동작은 문제 확인 과정에서 확인하지 않기로 했다.
- 동시 전송 반복 테스트의 반복 횟수는 처음에 상황마다 100회로 정했다가, 상황마다 따로 정하기로 했다.
- S1-5는 판매자의 환불 거절(5a)과 환불 동의(5b)를 모두 테스트하기로 했다.

### 2026-10-13 상황별 중지 위치와 예상 결과 설계

- 겹침 재현 테스트의 중지 위치를 상황마다 정했다. 기본은 두 요청이 주문을 조회한 직후이고, 미발송 자동 취소는 발송 정보 조회 전, 확인 기간 만료 자동 완료는 환불 요청 조회 전, 무응답 자동 환불은 환불 요청과 주문을 모두 조회한 뒤다.
- 중지 위치를 정하려고 각 처리가 주문 조회 뒤에 무엇을 더 조회하는지 코드로 확인했다.
  - 발송 등록은 발송 정보가 이미 있는지 조회한다.
  - 당사자 취소는 발송 정보를 따로 조회하지 않고 조회한 주문의 배송 상태로 판단한다.
  - 환불 요청은 기존 환불 요청이 있는지 조회한다.
  - 판매자 응답은 주문을 조회한 뒤 환불 요청을 조회한다.
  - 무응답 자동 환불은 환불 요청을 조회한 뒤 주문을 조회한다.
- 커밋 순서마다 예상 결과(가설)와 위반 기준을 정했다. 결과는 [작업명세 02~06](../../작업명세/02_테스트계획_구매자취소와_판매자취소.md)의 4절에 있다.
- 테스트 지원 기능이 코드에 있는지 확인했다. 시계 설정 API, 자동 처리 실행 API, 요청 일시 중지는 아직 없고, 스케줄러를 끄는 설정 `marketplace.scheduler.enabled`만 있다.
