## 1. 개요

구매자와 판매자가 같은 주문을 거의 동시에 취소할 때 한 요청만 성공하는지 확인했다. 서버에서 두 취소 요청을 주문 조회 직후에 멈춘 뒤, 요청 A(구매자 취소)를 먼저 재개해 커밋하고 그 응답을 받은 다음 요청 B(판매자 취소)를 재개했다. 정상 동작이라면 요청 B는 409 `TRADE_ALREADY_FINALIZED`로 거절되어야 하지만, 두 요청이 모두 200을 받았다. 결제액 350,000원이 두 번 반환되어 구매자 잔액은 정상 금액 400,000원보다 350,000원 많은 750,000원이 되었고, 최종 주문에는 요청 A의 응답에 담긴 취소 주체(구매자)가 아니라 요청 B의 취소 주체(판매자)가 남았다. 이 결과는 작업명세 02의 「4.3 예상 결과와 확인 방법」에 적은 가설과 모두 같다.

## 2. 테스트 대상

- **기능:** 거래 당사자의 주문 취소. 구매자와 판매자 모두 요청할 수 있다. 서버는 한 트랜잭션에서 주문을 조회하고, 요청자가 거래 당사자인지와 거래가 끝나지 않았는지, 배송 상태가 발송 대기인지 검사한다. 이어서 구매자 지갑을 조회해 반환 후 잔액이 저장 범위를 넘지 않는지 검사하고, 주문을 취소 완료로 바꾸면서 취소 주체와 취소 사유를 기록한 뒤, 결제액을 구매자 잔액에 더하고 커밋한다. 성공 응답은 커밋한 뒤 별도 트랜잭션에서 주문을 다시 조회해 만든다.
- **테스트한 서버:** 미니PC에 배포해 실행 중인 ChatService 서버.
- **테스트를 위해 추가한 코드:** 요청 일시 중지. 테스트 설정이 켜져 있고 요청 헤더에 요청 이름과 중지 위치가 있으면, 서버는 그 요청을 중지 위치에서 멈추고 재개 요청이 올 때까지 기다리게 한다. 멈춘 요청은 트랜잭션과 이미 조회한 주문을 그대로 가진 채 기다리고, 재개되면 처음부터 다시 처리하지 않고 멈춘 자리부터 이어서 처리한다. 이번 실행의 중지 위치는 주문 조회 직후다.

**시각 기준**

이 결과서에는 노트북과 미니PC 서버, 두 장비의 시계로 기록한 시각이 함께 나온다. 재개 제어는 서버에서 멈춘 두 요청을 차례로 재개하는 JMeter 스레드다.

| 시계 | 그 시계로 기록한 자료 |
|---|---|
| 노트북 시계 | JMeter 결과 파일에 기록된 요청을 보낸 시각, 재개 제어 기록에 남은 단계별 시각 |
| 서버 시계 | 서버 로그의 시각, DB에 저장된 기록 시각, 응답 본문에 담긴 시각 |


- **시계 차이:** 서버 시계가 노트북 시계보다 약 5.08초 빠르다.
- **측정 방법:** 멈춘 요청을 재개하는 동작은 노트북과 서버 양쪽에 기록된다. 재개 제어는 재개 요청을 보내고 그 응답을 받은 직후의 노트북 시각을 재개 제어 기록에 남기고, 서버는 멈춘 요청이 재개되는 순간의 서버 시각을 서버 로그에 남긴다. 요청 A와 요청 B의 재개마다 이 두 시각의 차이를 계산했다.

  | 재개한 요청 | 재개 제어 기록의 시각(노트북 시각) | 서버 로그의 시각(서버 시각) | 서버 시각 − 노트북 시각 |
  |---|---|---|---|
  | 요청 A | 15:20:40.133 | 15:20:45.211 | 5,078.1 ms |
  | 요청 B | 15:20:40.352 | 15:20:45.432 | 5,080.5 ms |

- **측정값의 한계:** 서버가 재개를 기록한 뒤 재개 요청의 응답이 노트북에 도착하기까지 걸린 시간이 두 기록 사이에 들어 있다. 그래서 실제 시계 차이는 측정값보다 그 시간만큼 클 수 있다.
- **시계 차이를 쓴 곳:** 서버 로그에서 이 실행의 기록 구간을 찾고, 노트북 쪽 기록과 서버 쪽 기록을 서로 짝짓는 데에만 썼다. 처리 순서와 걸린 시간은 같은 시계의 기록끼리만 비교하고 계산했다.
- **UTC로 저장된 시각:** DB의 기록 시각과 응답 본문의 시각은 서버가 UTC로 바꿔 저장한 값이다. 그래서 SQL Developer의 조회 화면과 응답 본문에는 한국 시각보다 9시간 이른 UTC로 보인다. 이 결과서에는 9시간을 더한 한국 시각으로 적었다.

## 5. 수행 절차

준비가 끝난 뒤 겹침 재현 계획의 「3. 테스트케이스1 테스트」 항목을 실행했다. 이 항목의 JMeter 스레드 세 개가 동시에 시작해, 작업명세 02의 「4.2.1 테스트케이스1」 절차대로 진행했다.

| 순서 | 스레드 1: 요청 A(구매자 취소) | 스레드 2: 요청 B(판매자 취소) | 스레드 3: 재개 제어 |
|---|---|---|---|
| 1 | 구매 목록을 조회해 주문 ID를 얻는다 | 판매 목록을 조회해 주문 ID를 얻는다 | 멈춘 요청 목록을 조회한다 |
| 2 | 취소 요청을 보낸다 | 취소 요청을 보낸다 | 멈춘 요청 목록을 조회한다 |
| 3 | 응답을 기다린다 | 응답을 기다린다 | 두 요청이 모두 멈춘 것을 확인한다 |
| 4 | 응답을 기다린다 | 응답을 기다린다 | 요청 A를 재개한다 |
| 5 | 응답을 받는다 | 응답을 기다린다 | 요청 A의 응답을 확인한다 |
| 6 | 끝난다 | 응답을 기다린다 | 요청 B를 재개한다 |
| 7 | | 응답을 받는다 | 요청 B의 응답을 확인한다 |

두 취소 요청에는 요청 이름(A, B)과 중지 위치(주문 조회 직후)를 헤더로 넣었다. 순서 3에서 두 요청은 서버에서 주문을 조회한 직후 멈춰 있었고, 요청 A는 순서 4에서, 요청 B는 순서 6에서 재개되었다.

테스트 뒤 SQL Developer에서 [작업명세 07](../../작업명세/07_공통실행참조.md#result-sql)의 「3. 결과 확인 SQL」을 주문 4와 두 회원으로 실행했다.

## 6. 실행 결과

### 6.1 입력과 출력

응답 코드는 JMeter 결과 파일에서, 나머지 값은 응답 본문에서 확인했다.

| 입력 | 응답 코드 | 거래 상태 | 취소 주체 | 취소 사유 | 잔액 변동 내역 |
|---|---|---|---|---|---|
| 요청 A: 구매자의 주문 4 취소 | 200 | 취소 완료 | 구매자 | 판매자와 합의해 취소합니다. | 결제 −350,000원(변동 후 50,000원), 취소 반환 +350,000원(변동 후 400,000원) |

| 구매자 잔액 변동 내역의 합계 | 내역 9~12의 금액 합 | 400,000 − 350,000 + 350,000 + 350,000 | 750,000원 |
| 정상 금액과의 차이 | 최종 구매자 잔액 − 정상 동작의 구매자 잔액 | 750,000, 400,000 | 350,000원 |

## 8. 해석

**두 요청이 같은 주문 상태로 처리된 조건:** 요청 B는 44.819에, 요청 A는 44.865에 주문 4를 조회했다. 조회한 값은 로그에 남지 않지만, 두 조회 모두 주문을 바꾼 첫 커밋인 요청 A의 커밋(45.228)보다 앞서므로 두 요청이 조회한 주문은 취소되기 전의 주문이다. 요청 A의 첫 SQL(44.865)부터 요청 A의 커밋(45.228)까지 363 ms 동안 두 요청은 모두 커밋하기 전 상태로 함께 진행되었다.

**요청 B가 409로 거절되지 않은 이유:** 요청 B는 45.432에 재개된 뒤 주문을 다시 조회하지 않았다. 재개 뒤 요청 B가 처음 실행한 SQL은 구매자 지갑 조회(45.434)다. 재개된 요청은 멈추기 전에 조회한 주문으로 이어서 처리하므로(작업명세 02의 「4.2 실행 절차」), 요청 B는 44.819에 조회한 진행 중 상태의 주문으로 거래가 끝났는지 검사했다. 그래서 요청 A가 45.228에 주문을 취소 완료로 커밋했는데도 검사를 통과했다.

**결제액이 두 번 반환된 이유:** 요청 B의 구매자 지갑 조회(45.434)는 요청 A의 커밋(45.228) 뒤에 실행되었다. 요청 B는 그 뒤 취소 반환 내역의 변동 후 잔액과 지갑 잔액을 750,000원으로 저장했다. 750,000원은 요청 A가 저장한 400,000원에 결제액 350,000원을 더한 값이다. 요청 B가 지갑에서 읽은 값은 로그에 남지 않아, 이어서 저장한 값으로 확인했다.

**최종 주문의 취소 주체가 요청 A의 응답과 다른 이유:** 두 요청의 주문 UPDATE는 모든 열을 다시 쓰고 조건은 주문 ID 하나다. 그래서 요청 B의 UPDATE(45.443)가 요청 A가 저장한 취소 주체와 취소 사유를 판매자와 요청 B의 사유로 덮어썼다. 요청 A의 응답은 요청 B가 재개되기 전(45.229~45.236)에 별도 트랜잭션에서 조회한 주문으로 만들어졌으므로 구매자를 담았다.

**기준 2로 중복 반환이 드러나지 않은 이유:** 요청 B는 지갑 잔액에 350,000원을 더하면서 같은 금액의 취소 반환 내역도 추가했다. 그래서 구매자 지갑 잔액과 잔액 변동 내역 합계가 모두 750,000원으로 같다. 작업명세 02의 「4.3 예상 결과와 확인 방법」이 예상한 대로, 지갑 잔액과 내역 합계를 비교하는 기준 2로는 중복 반환이 드러나지 않았고, 주문별 반환 내역 건수를 보는 기준 3에서 드러났다.
