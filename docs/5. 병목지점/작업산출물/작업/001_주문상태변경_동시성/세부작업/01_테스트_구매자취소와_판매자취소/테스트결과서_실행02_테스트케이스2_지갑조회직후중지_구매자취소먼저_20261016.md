## 1. 개요

구매자와 판매자가 같은 주문을 거의 동시에 취소할 때 한 요청만 성공하는지 확인했다. 두 요청을 구매자 지갑 조회와 잔액 범위 검사 직후에 멈추고, 요청 A(구매자 취소)의 처리가 끝난 뒤 요청 B(판매자 취소)를 재개했다. 두 요청 모두 200을 받았으며, 최종 주문에는 요청 B의 취소 주체와 사유가 저장되었다. 구매자 잔액은 정상 금액인 400,000원이었지만 취소 반환 내역이 두 건 남아, 잔액 변동 내역 합계 750,000원과 일치하지 않았다. 이 결과는 [작업명세 02](../../작업명세/02_테스트계획_구매자취소와_판매자취소.md)의 「4.3 예상 결과와 확인 방법」에 적은 중지 위치 2의 예상과 같으며, 한 요청만 성공해야 하는 정상 동작은 충족하지 못했다.

## 2. 테스트 대상

미니PC에서 실행 중인 ChatService 서버의 거래 당사자 주문 취소 기능을 테스트했다. 실행01에 사용한 빌드에서 중지 위치와 취소 시각을 구하는 시점을 변경한 서버다.

주문 취소는 한 트랜잭션에서 처리한다. 주문을 조회한 뒤 요청자가 거래 당사자인지, 거래가 끝나지 않았는지, 배송 상태가 발송 대기인지 검사한다. 이어서 구매자 지갑을 조회하고 결제액 반환 후의 잔액이 저장 범위를 넘지 않는지 검사한다. 검사를 통과하면 주문을 취소 완료로 변경하고 취소 주체·사유·시각을 기록한다. 구매자 잔액에는 결제액을 더하고 취소 반환 내역을 추가한다. 취소 트랜잭션의 커밋이 끝나면 별도 트랜잭션에서 주문을 조회해 응답을 만든다([작업명세 02](../../작업명세/02_테스트계획_구매자취소와_판매자취소.md)의 「4.1 요청 처리를 일시 중지할 위치」와 「4.2 실행 절차」).

이번 실행에서는 구매자 지갑 조회와 잔액 범위 검사 직후인 중지 위치 2에서 두 요청을 멈췄다. 요청 일시 중지 기능은 테스트 설정이 켜져 있고 요청 헤더에 지정한 중지 위치에 도달했을 때 동작한다. 대기 중에도 트랜잭션과 조회한 주문·지갑을 유지하며, 재개하면 멈춘 위치부터 처리를 계속한다. 주문 조회 직후인 중지 위치 1의 호출은 주석 처리했다.

당사자 취소의 시각은 중지 위치 2를 지난 뒤, 주문 상태를 바꾸기 직전에 구하도록 변경했다. 변경 전 코드에서는 공통 취소 처리를 호출하기 전에 시각을 구해, 중지 위치 2에서 대기하기 전의 시각을 주문 종료 시각과 취소 반환 내역의 기록 시각으로 사용했다. 변경 내용은 [세부작업기록](세부작업기록.md)의 「2026-10-16 테스트케이스2를 위한 중지 위치와 취소 시각 변경」에 있다. 미발송 자동 취소에는 기존과 같이 전달받은 시각을 사용한다.

**시각 기준**

JMeter는 노트북 시계로 요청 전송과 재개 제어의 시각을 기록하고, ChatService는 미니PC 서버 시계로 처리 시각을 기록했다. 재개 제어는 서버에서 멈춘 두 요청을 차례로 재개하는 JMeter 스레드다.

| 시계 | 그 시계로 기록한 자료 |
|---|---|
| 노트북 시계 | JMeter 결과 파일의 요청을 보낸 시각, 재개 제어 기록의 단계별 시각 |
| 서버 시계 | 서버 로그의 시각, DB의 기록 시각, 응답 본문에 담긴 시각 |

두 장비의 시각을 맞추어 보기 위해 같은 재개 동작의 기록을 비교했다. 요청 A에서는 서버 기록의 시각이 노트북 기록보다 약 5.39초 앞섰다. 표의 시각은 밀리초까지 반올림했으며, 시각 차이는 반올림 전 값으로 계산했다.

| 재개한 요청 | 재개 제어 기록의 시각(노트북 시각) | 서버 로그의 시각(서버 시각) | 서버 시각 − 노트북 시각 |
|---|---|---|---|
| 요청 A | 17:17:41.671 | 17:17:47.060 | 5,389.5 ms |
| 요청 B | 17:17:41.873 | 17:17:47.286 | 5,412.9 ms |

측정한 시각 차이는 두 장비에서 같은 동작을 기록한 부분을 찾는 데에만 사용했다. 처리 순서와 걸린 시간은 같은 장비의 시각끼리 비교했다. DB 조회 화면과 응답 본문의 시각은 UTC이므로, 9시간을 더한 한국 시각으로 표시했다.

## 4. 테스트 데이터와 시작 상태

판매자와 구매자의 회원 가입·로그인을 마친 뒤 상품 등록, 구매자 충전, 결제 순서로 준비했다. 준비 순서와 금액은 [작업명세 02](../../작업명세/02_테스트계획_구매자취소와_판매자취소.md)의 「2.1 시작 상태와 금액」과 「2.3 준비 순서」에 따른다. 상품 등록·충전·결제는 JMeter의 「4. 테스트케이스2 주문 만들기」로 실행했다. 표의 시각은 서버 로그에 해당 동작이 기록된 시각이다.

| 데이터 | 값 | 만든 방법 |
|---|---|---|
| 판매자 | `s1-1c3seller02`. 가입일 2026-10-16 | 회원 가입 요청 처리 시작 17:16:13.271, 로그인 성공 17:16:41.131 |
| 구매자 | `s1-1c3buyer02`. 가입일 2026-10-16 | 회원 가입 요청 처리 시작 17:16:13.571, 로그인 성공 17:16:41.263 |

결제 과정에서 상품 수량이 1에서 0으로 줄고 판매 완료로 바뀌었다. 재고 차감 로그의 시각은 17:16:49.580이다. 충전·결제 서비스 로그의 시각은 DB에 저장된 잔액 변동 내역의 기록 시각과 다르다. DB 기록 시각은 [6.2 저장된 상태](#62-저장된-상태)의 잔액 변동 내역 표에 있다.

## 5. 수행 절차

JMeter의 「5. 테스트케이스2 테스트」를 실행했다. 구매자 취소, 판매자 취소, 재개 제어를 맡은 스레드 세 개를 동시에 시작했다. 두 취소 요청에는 요청 이름과 중지 위치 2를 헤더로 지정했다. 실행 순서는 [작업명세 02](../../작업명세/02_테스트계획_구매자취소와_판매자취소.md)의 「4.2.2 테스트케이스2: 중지 위치 2(구매자 지갑 조회 직후), 요청 A 먼저 재개」와 같다.

| 순서 | 스레드 1: 요청 A(구매자 취소) | 스레드 2: 요청 B(판매자 취소) | 스레드 3: 재개 제어 |
|---|---|---|---|
| 1 | 구매 목록에서 주문 ID를 조회한다 | 판매 목록에서 주문 ID를 조회한다 | 멈춘 요청 목록을 조회한다 |
| 2 | 취소 요청을 보낸다 | 취소 요청을 보낸다 | 멈춘 요청 목록을 조회한다 |
| 3 | 응답을 기다린다 | 응답을 기다린다 | 두 요청이 모두 멈춘 것을 확인한다 |
| 4 | 응답을 기다린다 | 응답을 기다린다 | 요청 A를 재개한다 |
| 5 | 응답을 받는다 | 응답을 기다린다 | 요청 A의 응답을 확인한다 |
| 6 | 끝난다 | 응답을 기다린다 | 요청 B를 재개한다 |
| 7 | | 응답을 받는다 | 요청 B의 응답을 확인한다 |

중지 위치 2에서는 두 요청 모두 취소 조건 검사와 지갑 조회를 마쳤고, 주문과 잔액은 아직 변경하지 않았다. 재개 제어는 요청 A의 취소 응답을 확인한 뒤 요청 B를 재개했다. 따라서 요청 A의 취소 트랜잭션이 먼저 커밋된 뒤 요청 B의 처리가 이어졌다.

재개 제어의 단계별 기록은 다음과 같다. 시각은 노트북 시각이며, 「응답 받음」은 재개 제어에서 각 취소 응답의 수신을 확인한 시점이다.

| 노트북 시각 | 재개 제어 기록 |
|---|---|
| 17:17:41.634894200 | 요청 A와 요청 B가 모두 멈춤(중지 위치 `WALLET_READ`) |
| 17:17:41.670507800 | 요청 A 재개 요청, 응답 코드 200 |
| 17:17:41.873113 | 요청 A 응답 받음 |
| 17:17:41.873113 | 요청 B 재개 요청, 응답 코드 200 |
| 17:17:42.088491500 | 요청 B 응답 받음 |

두 요청이 끝난 뒤 SQL Developer에서 회원·상품·주문·지갑·잔액 변동 내역을 조회하고, 결과 확인 기준 2~5의 SQL을 실행했다. 조회 대상은 주문 26과 두 회원이며, 각 결과를 화면 사진으로 저장했다.

## 8. 해석

두 취소 요청은 취소 전 주문으로 조건 검사를 마친 뒤 중지되었다. 주문 조회는 요청 B가 17:17:46.821, 요청 A가 17:17:46.825에 실행했고, 요청 A의 커밋은 17:17:47.085였다. 두 조회 모두 첫 커밋보다 앞섰으며, 중지 위치 2에 도달하기 전에 거래 상태와 배송 상태 검사를 통과했다. 재개 후에는 이미 조회한 주문으로 취소 처리를 계속했으므로, 요청 B도 409로 거절되지 않고 성공했다([작업명세 02](../../작업명세/02_테스트계획_구매자취소와_판매자취소.md)의 「4.1 요청 처리를 일시 중지할 위치」와 「4.2 실행 절차」).

요청 B의 재개 시각은 17:17:47.286으로 요청 A의 커밋 뒤였다. 재개 후 첫 SQL은 취소 반환 내역 추가(17:17:47.290)였으며, 그 전에 구매자 지갑이나 주문 ID를 조건으로 한 주문 26의 재조회는 없었다. 자신의 주문 UPDATE(17:17:47.298) 뒤에는 상품·구매자·판매자를 조건으로 주문을 조회했다(17:17:47.301). 요청 A도 주문 UPDATE 뒤인 17:17:47.083에 같은 조건으로 조회했다. 상품·구매자·판매자를 조건으로 한 조회는 두 요청 모두 주문 변경 뒤에 실행되었다.

지갑 잔액은 두 요청이 같은 금액을 저장하면서 400,000원으로 남았다. 구매자 지갑 조회는 요청 B가 17:17:46.825, 요청 A가 17:17:46.827에 실행했고, 모두 요청 A의 커밋보다 앞섰다. 이후 지갑 UPDATE에서 요청 A는 17:17:47.082에 400,000원을 저장했고, 요청 B도 17:17:47.299에 400,000원을 저장했다. 반면 취소 반환 내역은 각 요청이 별도로 추가했으므로 +350,000원 내역 두 건이 남았고, 두 내역의 변동 후 잔액도 모두 400,000원이었다. SELECT로 읽은 잔액 자체는 로그에 없으므로, 여기서는 지갑 UPDATE와 취소 반환 내역에 저장한 값을 비교했다.

최종 주문의 취소 주체와 사유는 요청 B의 UPDATE로 바뀌었다. 요청 A는 17:17:47.081에 구매자와 자신의 사유를 저장하고 17:17:47.085에 커밋했다. 요청 A의 응답은 그 뒤 별도 트랜잭션에서 주문을 조회해 만들었으므로(17:17:47.087~17:17:47.097), 구매자의 취소 정보를 담았다. 이후 요청 B가 17:17:47.298에 판매자와 자신의 사유로 주문을 갱신하고 17:17:47.305에 커밋했다. 두 UPDATE의 조건은 주문 ID 하나였으며, 나중 UPDATE가 앞서 저장한 취소 정보를 덮어썼다.

최종 구매자 잔액은 정상 금액인 400,000원과 같지만, 잔액 변동 내역 합계는 750,000원으로 350,000원 더 많다. 따라서 잔액만 비교하면 이상이 드러나지 않는다. 실제 조회에서는 지갑 잔액과 내역 합계를 비교하는 기준 2에 구매자 행이 나왔고, 반환 내역 건수를 확인하는 기준 3에도 취소 반환이 두 건인 주문 26이 나왔다. [작업명세 02](../../작업명세/02_테스트계획_구매자취소와_판매자취소.md)의 「4.3 예상 결과와 확인 방법」 중 「중지 위치 2: 지갑 잔액과 취소 반환 내역의 불일치」에서 예상한 문제를 두 기준으로 확인했다.

## 10. 시스템 명세

**요청**

- 요청 A: `POST /ChatService/api/orders/26/cancel`, 구매자 로그인 쿠키, 본문 `{"reason":"판매자와 합의해 취소합니다."}`
- 요청 B: `POST /ChatService/api/orders/26/cancel`, 판매자 로그인 쿠키, 본문 `{"reason":"구매자와 채팅으로 취소에 합의했습니다."}`
- 두 요청의 헤더: `X-Test-Request-Name`(`A` 또는 `B`), `X-Test-Pause-At: WALLET_READ`
- 주문 ID 조회: 구매자 `GET /ChatService/api/orders/purchases`, 판매자 `GET /ChatService/api/orders/sales`
- 멈춘 요청 목록과 재개: `GET /ChatService/test-support/pauses`, `POST /ChatService/test-support/pauses/{요청 이름}/resume`([작업명세 07](../../작업명세/07_공통실행참조.md#request-pause)의 「2.3 요청 일시 중지」)

**코드**

- 주문 취소: `OrderCancellationService.cancelByParty`가 주문 조회와 취소 조건 검사를 수행한 뒤 `cancel`을 호출한다.
- 중지 위치 1: `purchaseOrderRepository.findById` 직후의 `testPause.reach(PausePoint.ORDER_READ)` 호출은 주석 처리했다.
- 중지 위치 2: `cancel`에서 `walletService.ensureCreditable` 직후 `testPause.reach(PausePoint.WALLET_READ)`를 호출한다.
- 취소 시각: `cancel(PurchaseOrder, CancelledBy, String, Supplier<Instant> nowSupplier)`이 중지 위치 2를 지난 뒤 `nowSupplier.get()`으로 시각을 구한다. `cancelByParty`는 `timeRules::now`, `cancelIfStillExpired`는 `() -> now`를 전달한다.
- 요청 일시 중지: `TestPause`, `PausePoint`, `TestSupportController`(패키지 `com.chatservice.marketplace.testsupport`).
- 코드 위치: 저장소 루트 기준 `src/main/java/com/chatservice/marketplace/order/service/OrderCancellationService.java`.

**서버 설정**

- 환경변수: `MARKETPLACE_TEST_SUPPORT_ENABLED=true`, `MARKETPLACE_SCHEDULER_ENABLED=false`, DB 계정 `TOYCHAT_TEST`.
- 설정 키: `marketplace.test-support.enabled: true`, `marketplace.scheduler.enabled: false`, `marketplace.test-support.pause-timeout: PT30S`.
- 로그 파일: `logging.file.name: /var/log/chatservice/chatservice.log`. SQL 기록: `p6spy-spring-boot-starter`.
- 시각 저장: `spring.jpa.properties.hibernate.jdbc.time_zone: UTC`.
