### 분석 내용

**요청 A가 409로 거절되지 않은 이유**

요청 A는 17:52:47.117에 주문 65를 조회했다. 이 시각은 요청 B의 커밋(17:52:47.380)보다 앞서므로, 요청 A가 조회한 주문은 진행 중·발송 대기인 주문이다. 요청 A는 주문을 조회한 직후에 멈추므로, 조회한 주문으로 하는 상태 검사는 재개된 뒤에 실행된다.

요청 A는 요청 B가 커밋한 뒤인 17:52:47.576에 재개되었지만, 주문 ID로 주문 65를 다시 조회하지 않았다. 재개 뒤 요청 A가 처음 실행한 SQL은 발송 정보가 있는지 조회한 것이다(17:52:47.582). 재개된 요청은 처음부터 다시 처리하지 않고 멈추기 전에 조회한 주문으로 이어서 처리하므로([작업명세 04](../../작업명세/04_테스트계획_발송등록과_미발송자동취소.md)의 「4.2 실행 절차」), 요청 A는 진행 중인 주문으로 거래가 끝났는지 검사했다. 그래서 요청 B가 주문을 취소 완료로 커밋한 뒤에도 검사를 통과했고, 409 진행 중인 주문이 아님(`ORDER_NOT_IN_PROGRESS`)으로 거절되지 않았다. 발송 정보가 있는지 확인하는 조회는 재개 뒤 DB를 새로 조회했지만, 요청 B의 취소 처리는 발송 정보를 만들지 않으므로 이 조회에서도 거절되지 않았다. 발송 기한 검사에는 주문을 조회하기 전에 구한 현재 시각을 썼다. 이 시각은 고정한 처리 기준 시각 `2026-10-12T14:59:59.500Z`이고 발송 기한 `2026-10-12T15:00:00Z`보다 앞서므로, 이 검사도 통과했다.

**요청 B의 발송 정보 조회가 취소를 막지 못한 이유**

요청 B는 주문마다 새 트랜잭션을 열어 주문을 다시 조회하고, 거래 상태·배송 상태·발송 기한을 검사한 뒤 발송 정보가 있는지 DB에서 새로 조회한다. 이 조회는 17:52:47.055에 실행되었고, 이때 요청 A는 아직 주문을 조회하기 전이었다(요청 A의 주문 조회 17:52:47.117). 요청 A가 발송 정보를 저장한 것은 요청 B가 커밋한(17:52:47.380) 뒤인 17:52:47.585다. 그래서 요청 B는 발송 정보가 없는 주문으로 보고 취소를 진행했다. 요청 B의 발송 정보 조회에는 그 조회가 실행되기 전에 커밋된 발송 정보만 나오므로, 요청 B가 커밋한 뒤에 저장된 요청 A의 발송 정보는 이 조회로 확인할 수 없었다.

**최종 주문이 진행 중·배송 중이 되고 취소 기록이 지워진 이유**

요청 B는 17:52:47.373에 주문을 거래 상태 취소 완료, 취소 주체 시스템(`SYSTEM`), 취소 사유 발송 기한 만료(`SHIPMENT_DEADLINE_EXPIRED`)로 UPDATE하면서 요청 B에서 지정한 처리 기준 시각을 종료 시각으로 함께 썼고, 17:52:47.380에 커밋했다. 요청 A는 17:52:47.588에 주문을 UPDATE했다. 두 요청의 주문 UPDATE는 주문 ID를 뺀 모든 열을 다시 쓰는 문장이고, 조건은 주문 ID 하나다.

요청 A의 UPDATE는 배송 상태를 배송 중으로 바꾸면서 거래 상태 열에 진행 중(`IN_PROGRESS`)을, 취소 주체·취소 사유·종료 시각 열에 NULL을 썼다. SELECT로 읽은 값은 로그에 남지 않지만, 요청 A는 재개 뒤 주문 ID로 주문을 다시 조회하지 않았으므로 이때 쓴 거래 상태와 취소 기록은 17:52:47.117에 조회한 주문의 값으로 판단했다. 그래서 요청 B가 커밋한 취소 완료가 진행 중으로 되돌아가고, 취소 주체·취소 사유·종료 시각이 지워졌다. 요청 A가 UPDATE할 때 요청 B의 트랜잭션은 이미 커밋되어 있었고, p6spy가 기록한 요청 A의 주문 UPDATE 실행 시간은 1 ms였다. 잠금 상태는 직접 조회하지 않았지만, 이 주문을 바꾼 요청 B가 이미 커밋한 뒤였으므로 이 UPDATE는 행 잠금을 기다리지 않았을 것으로 보인다.

**결제액 반환 내역이 남은 이유**

이 테스트케이스에서 결제액을 반환한 요청은 요청 B 하나다. 요청 B는 멈추기 전에 구매자 지갑을 조회했고(17:52:47.057), 재개 뒤 결제 후 잔액 10,000원에 290,000원을 더한 300,000원을 취소 반환 내역의 변동 후 잔액(17:52:47.362)과 지갑 잔액(17:52:47.374)으로 저장했다. 요청 A의 발송 등록은 지갑과 잔액 변동 내역을 바꾸지 않는다. 그래서 요청 A가 주문을 진행 중으로 되돌린 뒤에도 취소 반환 내역 1건과 구매자 잔액 300,000원이 그대로 남았다.

진행 중인 주문 65에 취소 반환 내역이 1건 있으므로, 거래 상태와 반환·지급 내역을 비교하는 기준 3에서 주문 65가 나왔다. 잔액 변동 내역의 합계(300,000원 − 290,000원 + 290,000원)는 300,000원으로 지갑 잔액과 같아 기준 2에는 행이 나오지 않았다. 배송 중인 주문 65에는 요청 A가 17:52:47.585에 추가한 발송 정보가 있으므로 기준 4에도 행이 나오지 않았다.

**저장된 시각**

발송 정보의 발송 시각은 `2026-10-12T14:59:59.500Z`로, A-1이 고정한 처리 기준 시각과 같다. 발송 등록은 주문을 조회하기 전에 현재 시각을 구하고, 이때 처리 기준 시각이 고정되어 있었기 때문이다(고정 17:52:47.041, 요청 A의 처리 시작 17:52:47.101).

취소 반환 내역의 기록 시각과 구매자 지갑의 갱신 시각은 `2026-10-12T15:00:05Z`로, 요청 B에서 지정한 처리 기준 시각과 같다. 미발송 자동 취소는 지정한 처리 기준 시각을 취소 시각으로 쓰기 때문이다. 요청 B는 같은 시각을 주문의 종료 시각에도 썼지만, 요청 A의 UPDATE가 종료 시각을 NULL로 썼으므로 DB에서 이 시각은 잔액 변동 내역과 지갑에만 남았다.

요청 A는 고정한 처리 기준 시각으로, 요청 B는 요청에서 지정한 처리 기준 시각으로 실행했으므로, 저장된 시각은 실제 처리 순서를 나타내지 않는다. 이 실행에서 저장된 시각의 순서(발송 시각이 먼저)와 커밋 순서(요청 B가 먼저)는 반대였다. 처리 순서와 커밋 순서는 저장된 시각이 아니라 서버 로그와 p6spy 기록으로 판단했다.

### 분석 결과

테스트케이스2의 결과는 [작업명세 04](../../작업명세/04_테스트계획_발송등록과_미발송자동취소.md)의 「4.3 예상 결과(가설)」에서 테스트케이스2의 행과 같았다. 요청 B는 요청 A가 발송 정보를 저장하기 전에 발송 정보가 없음을 확인하고 주문을 취소했다. 요청 A는 요청 B의 커밋 전에 조회한 주문으로 처리 조건을 검사해, 두 요청이 모두 성공했다. 나중에 커밋한 요청 A는 주문의 모든 열을 다시 쓰면서 거래 상태를 진행 중으로 되돌리고 취소 기록을 지웠다.

그 결과 진행 중·배송 중인 주문에 구매자 취소 반환 내역 1건이 남아 기준 3을 위반했다. 지갑 잔액과 잔액 변동 내역은 맞았고, 배송 상태와 발송 정보 유무도 맞았다. 이 결과는 [02 테스트 발송등록과_구매자취소](../02_테스트_발송등록과_구매자취소/세부작업기록.md)의 「실행02 2026-10-19」에서 구매자 취소가 먼저 커밋되었을 때와 같은 형태다.

### 시스템 명세

- 발송 등록: `ShipmentService.register`가 현재 시각을 구하고 주문을 조회한 뒤 중지 위치(`ORDER_READ`)를 지난다. 이어서 판매자인지와 거래가 끝났는지 검사하고, 발송 정보가 있는지 조회(`ShipmentRepository.existsByOrderId`)하고, 발송 기한을 검사한 뒤 `SHIPMENT`를 INSERT하고 `PurchaseOrder.markShipped`로 배송 상태를 바꾼다. 주문 UPDATE는 커밋 전 flush 때 실행된다
- 미발송 자동 취소: `TestSupportUnshippedCancelController`가 `OrderCancellationService.cancelExpiredUnshipped(now)`를 부른다. 대상 조회는 `PurchaseOrderRepository.findIdsByDeadlinePassed`(트랜잭션 밖)이고, 주문마다 `TransactionTemplate`이 연 새 트랜잭션에서 `cancelIfStillExpired`가 주문을 조회하고 발송 정보 유무를 `ShipmentRepository.existsByOrderId`로 조회한다. 발송 정보가 없으면 `cancel`이 `WalletService.ensureCreditable`, 중지 위치(`WALLET_READ`), `PurchaseOrder.cancel`, `WalletService.credit`(`CANCEL_REFUND`) 순서로 처리한다
- 커넥션 번호: 요청 A 18(데이터를 바꾼 트랜잭션)·19(응답 조회), 요청 B 15(대상 주문 조회, 커밋 기록 없음)·16(데이터를 바꾼 트랜잭션)
- 주문 UPDATE(바인딩 전)는 [02 테스트 발송등록과_구매자취소의 실행결과 분석](../02_테스트_발송등록과_구매자취소/실행결과_분석.md)의 「분석01 2026-10-19」 시스템 명세와 같다
- 요청 B의 주문 UPDATE(바인딩 후, 발췌): `CANCEL_REASON='SHIPMENT_DEADLINE_EXPIRED',CANCELLED_BY='SYSTEM'`, `FINALIZED_AT='2026-10-13T00:00:05.000+0900'`, `SHIPPING_STATUS='WAITING_SHIPMENT',TRADE_STATUS='CANCELLED'`, `where ORDER_ID=65`
- 요청 A의 주문 UPDATE(바인딩 후, 발췌): `CANCEL_REASON=NULL,CANCELLED_BY=NULL`, `FINALIZED_AT=NULL`, `SHIPPING_STATUS='SHIPPING',TRADE_STATUS='IN_PROGRESS'`, `where ORDER_ID=65`

**주문 65가 두 자동 처리의 대상이 된 이유**

실행01이 끝난 뒤 주문 65는 진행 중·배송 중이었고, 취소 주체·취소 사유·종료 시각은 NULL로 지워져 있었으며, 발송 정보가 1행 있었다. 구매자의 취소 반환 내역은 남아 있었지만, 주문과 발송 정보만 보면 발송 등록을 마친 정상 주문과 같은 상태였다.

모의 배송 완료는 트랜잭션 밖에서 진행 중·배송 중이고 배송 완료 시각이 없으며, 발송 정보의 모의 배송 완료 예정 시각이 지정한 처리 기준 시각 이하인 주문을 조회했다(19:26:24.418). 주문 65의 모의 배송 완료 예정 시각은 `2026-10-12T15:01:59.500Z`이고 지정한 처리 기준 시각은 `2026-10-12T15:02:00Z`이므로, 주문 65가 대상이 되었다. 이어서 새 트랜잭션에서 주문 65와 발송 정보를 다시 조회한 뒤 주문을 배송 완료로 바꾸고, 처리 기준 시각을 배송 완료 시각으로, 그 48시간 뒤를 상품 확인 기한으로 저장했다(UPDATE 24.427, 커밋 24.429).

확인 기간 만료 자동 완료는 트랜잭션 밖에서 진행 중·배송 완료이고 상품 확인 기한이 지정한 처리 기준 시각 이하인 주문을 조회했다(24.488). 지정한 처리 기준 시각은 C-4에서 얻은 주문 65의 상품 확인 기한 `2026-10-14T15:02:00Z`와 같으므로, 주문 65가 대상이 되었다. 이어서 새 트랜잭션에서 주문 65를 다시 조회하고 환불 요청이 있는지 조회한 뒤(24.491, 24.496) 정상 완료로 처리했다. 두 자동 처리는 주문의 거래 상태·배송 상태와 기한, 발송 정보나 환불 요청의 유무만 검사하고, 잔액 변동 내역은 검사하지 않는다. 그래서 구매자에게 이미 결제액을 돌려준 주문 65도 거래가 정상적으로 진행 중인 주문과 같이 처리되었다.

**판매자에게 판매대금이 지급된 이유**

확인 기간 만료 자동 완료는 주문을 정상 완료로 바꾸면서 판매자에게 결제 금액 전액을 지급한다. 판매자 지갑이 없었으므로 지갑을 잔액 0원으로 추가하고(24.501), 판매대금 지급 내역 +290,000원을 추가한 뒤(24.502), 주문을 정상 완료로 UPDATE하고(24.514) 판매자 지갑 잔액을 290,000원으로 UPDATE했다(24.515). 커밋은 24.518이다.

그 결과 결제액 290,000원인 주문 65에서 구매자 취소 반환 290,000원(내역 94, 실행01)과 판매자 판매대금 지급 290,000원(내역 95)이 모두 나가, 합계 580,000원이 나갔다.

**결과 확인 기준에 드러난 방식**

기준 3에 따르면 정상 완료인 주문에는 판매대금 지급 내역 1건만 있어야 한다. 주문 65에는 판매대금 지급 1건 외에 취소 반환 1건이 더 있으므로 기준 3에 행이 나왔다. 실행01에서는 진행 중인 주문에 취소 반환 내역이 있어 기준 3에 행이 나왔고, 실행02에서는 주문이 정상 완료로 끝나면서 반환과 지급이 함께 있어 다시 행이 나왔다.

기준 2에는 행이 나오지 않았다. 구매자는 지갑 잔액과 잔액 변동 내역 합계가 모두 300,000원, 판매자는 모두 290,000원으로 회원마다 맞기 때문이다. 결제액보다 많은 금액이 나간 것은 회원별 잔액으로는 드러나지 않고, 주문별 반환·지급 내역을 보는 기준 3에서만 드러났다. 기준 4는 배송 완료인 주문 65에 발송 정보가 1행 있어서, 기준 5는 환불 요청이 없어서 행이 나오지 않았다.

**저장된 시각**

배송 완료 시각은 C-3에서 지정한 처리 기준 시각(`2026-10-12T15:02:00Z`)이고, 상품 확인 기한은 그 48시간 뒤인 `2026-10-14T15:02:00Z`다. 주문의 종료 시각, 판매대금 지급 내역의 기록 시각, 판매자 지갑의 갱신 시각은 모두 C-5에서 지정한 처리 기준 시각(`2026-10-14T15:02:00Z`)이다. 자동 처리는 지정한 처리 기준 시각을 현재 시각으로 쓰기 때문이다. 실제로 두 처리가 커밋된 시각은 2026-10-22 19:26:24.429와 19:26:24.518이다. 그래서 저장된 시각은 실제 처리 순서와 간격을 나타내지 않으며, 실행02의 처리 순서는 서버 로그와 p6spy 기록으로 판단했다.

**요청 A가 성공한 이유**

요청 A는 14:35:26.521에 주문 66을 조회했다. 주문 만들기(14:31:55) 뒤로 이 조회 전까지 주문 66을 바꾼 UPDATE는 없었으므로, 요청 A가 조회한 주문은 결제 직후의 진행 중·발송 대기였다. 이때 요청 B는 주문 66을 조회만 한 채 멈춰 있었다(요청 B의 대기 시작 14:35:26.453).

요청 A는 14:35:26.836에 재개되어 발송 정보가 있는지 조회했고(26.839), 발송 정보가 없어 이 검사를 통과했다. 발송 기한 검사에는 주문을 조회하기 전에 구한 현재 시각을 썼다. 이 시각은 고정한 처리 기준 시각 `2026-10-12T14:59:59.500Z`이고 발송 기한 `2026-10-12T15:00:00Z`보다 앞서므로, 이 검사도 통과했다. 그래서 요청 A는 발송 정보를 추가하고(26.843), 주문을 진행 중·배송 중으로 UPDATE한 뒤(26.859) 26.864에 커밋했다. 요청 A가 처리하는 동안 요청 B는 데이터를 바꾸지 않았으므로, 요청 A는 다른 요청과 겹치지 않았을 때와 같은 순서로 처리되었다. 요청 A가 주문을 UPDATE할 때 요청 B는 주문 66을 조회만 하고 바꾸지 않은 상태였고, p6spy가 기록한 이 UPDATE의 실행 시간은 14 ms였다.

**요청 B의 발송 정보 조회가 취소를 막지 못한 이유**

요청 B는 주문마다 새 트랜잭션을 열어 주문을 다시 조회하고(26.449), 거래 상태·배송 상태·발송 기한을 검사한 뒤 발송 정보가 있는지 DB에서 새로 조회한다. 이 조회는 14:35:26.451에 실행되었고, 이때 요청 A는 아직 주문도 조회하기 전이었다(요청 A의 주문 조회 26.521). 요청 A가 발송 정보를 추가하고 커밋한 것은 그 뒤인 26.843과 26.864다. 그래서 이 조회에는 발송 정보가 나오지 않았고, 요청 B는 취소를 진행해 구매자 지갑을 조회한 직후(26.452) 멈췄다.

요청 B는 요청 A가 커밋한 뒤인 14:35:27.071에 재개되었지만, 발송 정보를 다시 조회하지 않았다. 재개 뒤 요청 B가 실행한 SQL은 취소 반환 내역 추가(27.075), 대화 조회(27.078), 상품 조회(27.079), 주문 UPDATE(27.088), 지갑 UPDATE(27.090), 주문 조회(27.091)와 커밋(27.096)이다. 미발송 자동 취소의 발송 정보 조회는 구매자 지갑을 조회하기 전에 한 번만 있으므로, 재개된 요청 B는 요청 A가 커밋한 발송 정보를 확인하지 않았다. 이어지는 취소 처리의 상태 검사도 멈추기 전에 조회한 주문(진행 중·발송 대기)으로 했으므로 통과했다.

**최종 주문이 취소 완료·발송 대기가 된 이유**

요청 B는 14:35:27.088에 주문을 거래 상태 취소 완료, 취소 주체 시스템(`SYSTEM`), 취소 사유 발송 기한 만료(`SHIPMENT_DEADLINE_EXPIRED`)로 UPDATE하면서 요청 B에서 지정한 처리 기준 시각을 종료 시각으로 함께 썼고, 27.096에 커밋했다. 요청 A의 주문 UPDATE(26.859)와 커밋(26.864)은 그보다 앞서 있었다. 두 요청의 주문 UPDATE는 주문 ID를 뺀 모든 열을 다시 쓰는 문장이고, 조건은 주문 ID 하나다.

요청 B의 UPDATE는 거래 상태를 취소 완료로 바꾸면서 배송 상태 열에 발송 대기(`WAITING_SHIPMENT`)를 썼다. SELECT로 읽은 값은 로그에 남지 않지만, 요청 B는 재개 뒤 주문 ID로 주문을 다시 조회하지 않았으므로 이때 쓴 배송 상태는 14:35:26.449에 조회한 주문의 값으로 판단했다. 그래서 요청 A가 커밋한 배송 중이 발송 대기로 되돌아갔다. 요청 B가 UPDATE할 때 요청 A의 트랜잭션은 이미 커밋되어 있었고, p6spy가 기록한 요청 B의 주문 UPDATE 실행 시간은 5 ms였다. 잠금 상태는 직접 조회하지 않았지만, 이 주문을 바꾼 요청 A가 이미 커밋한 뒤였으므로 이 UPDATE는 행 잠금을 기다리지 않았을 것으로 보인다.

**발송 정보가 취소 완료 주문에 남은 이유**

요청 B는 재개된 뒤 주문과 지갑을 바꾸고 취소 반환 내역을 추가했을 뿐, 발송 정보를 조회하거나 지우지 않았다. 그래서 요청 A가 14:35:26.843에 추가한 발송 정보 24가 취소 완료·발송 대기인 주문 66에 그대로 남았고, 거래 상태·배송 상태와 발송 정보 유무를 비교하는 기준 4에서 주문 66이 나왔다.

**결제액 반환 내역**

이 테스트케이스에서 결제액을 반환한 요청은 요청 B 하나다. 요청 B는 멈추기 전에 구매자 지갑을 조회했고(14:35:26.452), 재개 뒤 결제 후 잔액 10,000원에 290,000원을 더한 300,000원을 취소 반환 내역의 변동 후 잔액(27.075)과 지갑 잔액(27.090)으로 저장했다. 요청 A의 발송 등록은 지갑과 잔액 변동 내역을 바꾸지 않는다.

그래서 잔액 변동 내역의 합계(300,000원 − 290,000원 + 290,000원)는 300,000원으로 지갑 잔액과 같아 기준 2에는 행이 나오지 않았다. 취소 완료인 주문 66에는 취소 반환 내역이 1건만 있으므로 기준 3에도 행이 나오지 않았다.

**두 요청의 응답과 최종 주문**

요청 A는 커밋한 뒤 별도 트랜잭션(커넥션 48)에서 응답에 쓸 주문을 조회했다(14:35:26.866~26.876). 이 조회는 요청 B가 재개된 27.071보다 앞서므로, 판매자는 진행 중·배송 중인 주문과 발송 정보를 응답으로 받았다. DB의 최종 주문은 요청 B가 27.096에 커밋한 취소 완료·발송 대기다. 요청 B는 자동 처리이므로 응답에는 처리 건수만 담긴다. 그 결과 판매자는 발송 등록이 성공한 응답을 받았지만, 주문은 취소 완료가 되고 결제액은 구매자에게 반환되었다.

**저장된 시각**

발송 정보의 발송 시각은 `2026-10-12T14:59:59.500Z`로, A-1이 고정한 처리 기준 시각과 같다. 발송 등록은 주문을 조회하기 전에 현재 시각을 구하고, 이때 처리 기준 시각이 고정되어 있었기 때문이다(고정 14:35:26.440, 요청 A의 처리 시작 14:35:26.511).

주문의 종료 시각, 취소 반환 내역의 기록 시각, 구매자 지갑의 갱신 시각은 `2026-10-12T15:00:05Z`로, 요청 B에서 지정한 처리 기준 시각과 같다. 미발송 자동 취소는 지정한 처리 기준 시각을 취소 시각으로 쓰기 때문이다.

요청 A는 고정한 처리 기준 시각으로, 요청 B는 요청에서 지정한 처리 기준 시각으로 실행했으므로, 저장된 시각은 실제 처리 순서를 나타내지 않는다. 이 실행에서는 저장된 시각의 순서(발송 시각이 먼저)와 커밋 순서(요청 A가 먼저)가 같았지만, 처리 순서와 커밋 순서는 저장된 시각이 아니라 서버 로그와 p6spy 기록으로 판단했다.

### 분석 결과

테스트케이스3의 결과는 [작업명세 04](../../작업명세/04_테스트계획_발송등록과_미발송자동취소.md)의 「4.3 예상 결과(가설)」에서 테스트케이스3의 행과 같았다. 요청 B는 요청 A가 발송 정보를 저장하기 전에 발송 정보가 없음을 확인했고, 재개된 뒤 발송 정보를 다시 조회하지 않고 주문을 취소했다. 요청 A는 요청 B가 데이터를 바꾸기 전에 조회한 주문으로 처리해, 두 요청이 모두 성공했다. 나중에 커밋한 요청 B는 주문의 모든 열을 다시 쓰면서 배송 상태를 발송 대기로 되돌렸다.

그 결과 취소 완료·발송 대기인 주문에 발송 정보 1행이 남아 기준 4를 위반했다. 결제액 반환은 1건이고 지갑 잔액과 잔액 변동 내역도 맞아 기준 2·3에는 행이 나오지 않았다. 판매자는 발송 등록이 성공한 응답을 받았지만, 최종 주문은 취소 완료다. 이 결과는 [02 테스트 발송등록과_구매자취소](../02_테스트_발송등록과_구매자취소/세부작업기록.md)의 「실행01 2026-10-19」에서 발송 등록이 먼저 커밋되었을 때와 같은 형태다. 미발송 자동 취소에는 구매자 취소에 없는 발송 정보 조회가 한 번 더 있지만, 이 조회가 요청 A의 발송 정보 저장보다 먼저 실행되어 결과는 같았다.

### 시스템 명세

- 미발송 자동 취소: `cancelIfStillExpired`가 주문을 조회하고(`PurchaseOrderRepository.findById`) 발송 정보 유무를 `ShipmentRepository.existsByOrderId`로 한 번 조회한 뒤 `cancel`을 부른다. `cancel`은 `WalletService.ensureCreditable`, 중지 위치(`WALLET_READ`), `PurchaseOrder.cancel`, `WalletService.credit`(`CANCEL_REFUND`), `ConversationService.publishStateToTradeConversation` 순서로 처리하며, 중지 위치 뒤에는 발송 정보를 조회하지 않는다. `PurchaseOrder.cancel`의 상태 검사(`requireState`)는 영속성 컨텍스트에 있는 주문 엔티티의 값으로 한다

- 커넥션 번호: 요청 A 47(데이터를 바꾼 트랜잭션)·48(응답 조회), 요청 B 44(대상 주문 조회, 커밋 기록 없음)·45(데이터를 바꾼 트랜잭션), A-2 46
