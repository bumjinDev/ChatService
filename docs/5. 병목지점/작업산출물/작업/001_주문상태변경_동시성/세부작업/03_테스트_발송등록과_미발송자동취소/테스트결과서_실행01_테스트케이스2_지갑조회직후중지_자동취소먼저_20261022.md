## 1. 개요

실행01에서는 테스트케이스2를 실행했다. 판매자의 발송 등록(요청 A)과 미발송 자동 취소(요청 B)가 같은 주문을 처리하는 도중에 겹치게 하여, 두 처리 가운데 하나만 성공하는지 확인했다. 서버는 요청 A를 발송 기한 0.5초 전의 처리 기준 시각으로, 요청 B를 요청에서 지정한 발송 기한 5초 뒤의 처리 기준 시각으로 처리했다. 중지 위치는 요청 A가 주문 조회 직후, 요청 B가 구매자 지갑 조회 직후였고, 두 요청이 모두 멈춘 뒤 요청 B를 먼저 재개했다.

요청 B가 먼저 커밋해 주문을 취소하고 결제액 290,000원을 구매자에게 반환했지만, 요청 A도 201로 성공했다. 최종 주문은 진행 중·배송 중이 되어 취소 기록이 지워졌고, 반환한 290,000원은 남았다.

실행02에서는 [작업명세 04](../../작업명세/04_테스트계획_발송등록과_미발송자동취소.md)의 「4.2.3 테스트케이스2의 이후 자동 처리」에 따라 같은 주문을 모의 배송 완료와 확인 기간 만료 자동 완료까지 진행했다. 판매자에게도 290,000원이 지급되어, 결제액 290,000원인 주문에서 합계 580,000원이 나갔다.

실행01의 결과는 같은 문서의 「4.3 예상 결과(가설)」에 있는 테스트케이스2 행의 예상과 같았고, 결과 확인 기준 1과 3을 만족하지 못했다. 실행02의 결과는 같은 항목의 「테스트케이스2의 이후 자동 처리」 표의 예상과 같았고, 기준 3을 만족하지 못했다.

## 2. 테스트 대상

두 실행의 대상은 미니PC에 배포해 실행 중인 ChatService 서버다. 실행01과 실행02의 요청을 처리한 서버는 같은 빌드이며, 두 실행의 서버 로그에 기록된 프로세스 번호가 같아 두 실행 사이에 서버가 다시 시작되지 않았다.

### 실행01

요청 A(발송 등록)는 판매자가 주문의 발송 정보를 등록하는 기능이다. 한 트랜잭션에서 현재 시각을 구하고 주문을 조회한 뒤, 요청자가 판매자인지와 거래가 끝나지 않았는지를 검사한다. 이어서 발송 정보가 이미 있는지 조회하고, 처음에 구한 현재 시각이 발송 기한 전인지 검사한다. 검사를 통과하면 발송 정보를 저장하고 주문의 배송 상태를 배송 중으로 바꾼다. 커밋한 뒤에는 별도 트랜잭션에서 주문을 조회해 응답을 만든다.

요청 B(미발송 자동 취소)는 주문을 취소하고 결제액을 구매자에게 반환하는 자동 처리다. 대상은 진행 중·발송 대기이고 발송 기한이 처리 기준 시각 이하인 주문이다. 트랜잭션 밖에서 대상 주문의 ID 목록을 조회한 뒤, 주문마다 새 트랜잭션에서 주문을 다시 조회해 거래 상태·배송 상태·발송 기한을 검사하고 그 주문의 발송 정보가 있는지 조회한다. 발송 정보가 없으면 구매자 지갑을 조회한 뒤 주문을 취소 완료로 바꾸고 취소 주체 시스템, 취소 사유 발송 기한 만료, 종료 시각을 기록하며, 구매자 잔액에 결제액을 더하고 취소 반환 내역을 추가한다. 주문마다 커밋하고, 처리한 주문 수를 응답으로 돌려준다([작업명세 04](../../작업명세/04_테스트계획_발송등록과_미발송자동취소.md)의 「1. 검증 목적과 정상 동작」, 「4.1 중지 위치」, 「4.2 실행 절차」).

발송 등록에는 주문을 조회한 직후에, 미발송 자동 취소에는 구매자 지갑을 조회한 직후에 요청을 멈출 수 있는 테스트 지원 기능(요청 일시 중지)이 들어 있다. 이 기능은 테스트 설정이 켜져 있고 요청 헤더에 지정한 중지 위치에 도달했을 때 동작하며, 대기 중에도 트랜잭션과 DB 연결을 유지한다([작업명세 07](../../작업명세/07_공통실행참조.md#request-pause)의 「2.3 요청 일시 중지」). 서버는 재개된 요청을 처음부터 다시 처리하지 않고, 멈추기 전에 조회해 둔 주문으로 멈춘 위치부터 이어서 처리한다([작업명세 04](../../작업명세/04_테스트계획_발송등록과_미발송자동취소.md)의 「4.2 실행 절차」).

미발송 자동 취소는 이 테스트를 위해 더한 미발송 자동 취소 실행 API로 실행했다. 이 API는 미발송 자동 취소를 요청에서 지정한 처리 기준 시각으로 한 번 실행하고 처리한 주문 수를 돌려준다. 테스트 지원 API 요청의 처리 시작과 처리 끝을 서버 로그에 남기는 테스트 지원 요청 로그도 이 테스트를 위해 더했다. 서비스 코드와 스케줄러는 바꾸지 않았다([세부작업기록](세부작업기록.md)의 「2026-10-21 테스트케이스와 테스트 지원 코드 변경」, 「2026-10-22 테스트 지원 요청 로그 추가」).

### 실행02

실행02에서는 스케줄러를 끈 상태에서 자동 처리 실행 API로 모의 배송 완료와 확인 기간 만료 자동 완료를 한 번씩 실행했다. 두 API는 [02 테스트 발송등록과_구매자취소](../02_테스트_발송등록과_구매자취소/세부작업기록.md)의 「2026-10-20 자동 처리 실행 API 추가」에서 추가한 API이며, 스케줄러가 부르는 자동 처리를 요청에서 지정한 처리 기준 시각으로 실행한다([작업명세 07](../../작업명세/07_공통실행참조.md#test-support-api)의 「2.2 자동 처리 실행 API와 처리 기준 시각 설정 API」).

모의 배송 완료는 트랜잭션 밖에서 대상 주문을 조회한다. 대상은 진행 중·배송 중이고 배송 완료 시각이 없으며, 발송 정보의 모의 배송 완료 예정 시각이 처리 기준 시각 이하인 주문이다. 이어서 주문마다 새 트랜잭션에서 주문과 발송 정보를 다시 조회해 같은 조건을 확인하고, 배송 상태를 배송 완료로 바꾸면서 처리 기준 시각을 배송 완료 시각으로, 그 48시간 뒤를 상품 확인 기한으로 저장한다.

확인 기간 만료 자동 완료는 트랜잭션 밖에서 대상 주문을 조회한다. 대상은 진행 중·배송 완료이고 상품 확인 기한이 처리 기준 시각 이하인 주문이다. 이어서 주문마다 새 트랜잭션에서 주문을 다시 조회해 같은 조건을 확인하고, 환불 요청이 없는지 조회한다. 조건을 통과하면 주문을 정상 완료로 바꾸고, 판매자 잔액에 결제 금액 전액을 더하고 판매대금 지급 내역을 추가한다. 판매자 지갑이 없으면 지갑을 만든 뒤 더한다.

두 자동 처리는 주문의 상태와 기한, 발송 정보와 환불 요청의 유무만 확인하고 잔액 변동 내역은 확인하지 않는다.

## 4. 테스트 데이터와 시작 상태

### 실행01

판매자와 구매자의 회원 가입·로그인을 마친 뒤 상품 등록, 구매자 충전, 결제 순서로 준비했다. 준비 순서와 금액은 [작업명세 04](../../작업명세/04_테스트계획_발송등록과_미발송자동취소.md)의 「2.1 시작 상태와 금액」, 「2.2 기준 시각」, 「2.3 준비 순서」에 따른다.

회원 가입은 JMeter의 회원 가입 계획으로, 로그인은 겹침 재현 계획의 「1. 로그인」으로, 상품 등록부터 결제까지는 「2. 테스트케이스2 주문 만들기」로 실행했다. 표의 시각은 서버 로그에 해당 동작이 기록된 시각이다.

## 8. 정리 및 결론

이 항목의 시각은 모두 2026-10-22의 서버 시각이다.

### 실행01

#### 요청 A가 409로 거절되지 않은 이유

요청 A는 요청 B가 커밋하기 전에 주문 65를 조회하고 멈췄고, 재개된 뒤에도 주문을 다시 조회하지 않았다(요청 A의 주문 조회 17:52:47.117, 요청 B 커밋 17:52:47.380, 요청 A 재개 17:52:47.576, 재개 뒤 첫 SQL인 발송 정보 조회 17:52:47.582). 그래서 서버는 멈추기 전에 조회한 진행 중인 주문으로 거래가 끝났는지 검사했고, 요청 A는 409(진행 중인 주문이 아님)로 거절되지 않았다. SELECT로 읽은 값은 로그에 남지 않아, 요청 A가 조회한 주문이 진행 중이었다는 것은 로그로 직접 확인하지 못했다. 이 조회가 요청 B의 커밋보다 앞섰고 요청 A의 주문 UPDATE가 거래 상태에 진행 중을 썼으므로, 조회한 주문이 진행 중이었다고 판단했다.

발송 기한 검사에는 주문을 조회하기 전에 구한 처리 기준 시각 `2026-10-12T14:59:59.500Z`를 썼다. 저장된 발송 시각도 이 시각과 같다. 이 시각이 발송 기한 `2026-10-12T15:00:00Z`보다 앞서므로 이 검사도 통과했다.

#### 요청 B의 발송 정보 조회가 취소를 막지 못한 이유

요청 B는 17:52:47.055에 주문 65의 발송 정보가 있는지 조회했고, 이때 요청 A는 아직 주문도 조회하기 전이었다(요청 A의 주문 조회 17:52:47.117). 요청 A가 발송 정보를 추가한 것은 요청 B가 커밋한 뒤인 17:52:47.585다. 요청 B는 구매자 지갑을 조회한 직후에 멈췄으므로, 서버는 요청 B를 재개한 뒤 발송 정보를 다시 조회하지 않고 취소를 진행했다.

#### 최종 주문이 진행 중·배송 중이 되고 취소 기록이 지워진 이유

요청 A의 주문 UPDATE가 주문 ID를 뺀 모든 열을 다시 쓰면서 거래 상태에 진행 중을, 취소 주체·취소 사유·종료 시각에 NULL을 써, 요청 B가 커밋한 취소 완료를 덮었다(요청 B 커밋 17:52:47.380, 요청 A의 주문 UPDATE 17:52:47.588). 이 UPDATE는 요청 B가 커밋한 뒤에 실행되었고 p6spy가 기록한 실행 시간이 1 ms였으므로, 행 잠금을 기다리지 않았을 것으로 보인다(잠금 상태는 직접 조회하지 않았다).

#### 반환한 290,000원이 남은 이유

서버는 요청 B를 처리할 때만 결제액을 반환했고, 요청 A의 발송 등록은 구매자 지갑과 잔액 변동 내역을 바꾸지 않는다. 그래서 요청 A가 주문을 진행 중으로 바꾼 뒤에도 취소 반환 내역 94와 구매자 잔액 300,000원이 그대로 남았다(취소 반환 내역 추가 17:52:47.362, 요청 A 커밋 17:52:47.590). 진행 중인 주문 65에 취소 반환 내역이 남았으므로 기준 3을 만족하지 못했다.

### 실행02

#### 두 자동 처리의 대상이 된 이유

실행01을 마친 뒤 주문 65는 취소 기록이 지워진 진행 중·배송 중 주문이고 발송 정보도 1행 있어서, 주문과 발송 정보만 보면 발송 등록을 마친 정상 주문과 같았다. 두 자동 처리는 주문의 상태와 기한, 발송 정보와 환불 요청의 유무만 확인하고 잔액 변동 내역은 확인하지 않으므로, 구매자에게 이미 결제액을 반환한 주문 65도 두 자동 처리의 대상이 되었다(모의 배송 완료와 확인 기간 만료 자동 완료의 처리 건수 각 1).

#### 판매자에게도 지급되어 580,000원이 나간 이유

확인 기간 만료 자동 완료는 주문을 정상 완료로 바꾸면서 판매자에게 결제 금액 전액을 지급한다. 실행01의 취소 반환 290,000원이 남아 있는 상태에서 판매대금 290,000원도 지급되어, 결제액 290,000원인 주문 65에서 합계 580,000원이 나갔다(취소 반환 내역 94, 판매대금 지급 내역 95).

#### 기준 3에서만 드러난 이유

기준 2의 SQL은 회원별로, 기준 3의 SQL은 주문별로 내역을 비교한다. 구매자는 300,000원, 판매자는 290,000원으로 각자 지갑 잔액과 잔액 변동 내역 합계가 맞아 기준 2에는 행이 없었지만, 정상 완료인 주문 65에는 판매대금 지급 외에 취소 반환 1건이 더 있어 기준 3에 행이 나왔다.

발송 등록의 처리 순서는 `ShipmentService.register`에서 `timeRules.now()`, `purchaseOrderRepository.findById`, `testPause.reach(PausePoint.ORDER_READ)`, 상태 검사, 발송 정보 유무 조회, 발송 기한 검사, 발송 정보 저장, `markShipped` 순이다.

미발송 자동 취소는 `TestSupportUnshippedCancelController`가 `OrderCancellationService.cancelExpiredUnshipped(now)`를 부르며, 대상 조회는 `PurchaseOrderRepository.findIdsByDeadlinePassed`(트랜잭션 밖)다. 주문마다 `TransactionTemplate`이 연 새 트랜잭션에서 `cancelIfStillExpired`가 주문을 조회하고 발송 정보 유무를 조회한 뒤, `cancel`이 `WalletService.ensureCreditable`, `testPause.reach(PausePoint.WALLET_READ)`, `PurchaseOrder.cancel`, `WalletService.credit`(`CANCEL_REFUND`) 순으로 처리한다.

요청 A의 데이터 변경 커넥션은 18, 응답 조회 커넥션은 19이며, 요청 B는 대상 조회에 15, 주문 처리에 16을 사용했다. 판매 목록 조회(A-2)는 커넥션 17을 사용했다.

```sql
-- 요청 B 대상 조회의 WHERE 조건
TRADE_STATUS='IN_PROGRESS' and SHIPPING_STATUS='WAITING_SHIPMENT'
and SHIP_DEADLINE_AT<='2026-10-13T00:00:05.000+0900'

-- 요청 B의 주문 UPDATE SET 절과 WHERE 조건 중 발췌
CANCEL_REASON='SHIPMENT_DEADLINE_EXPIRED', CANCELLED_BY='SYSTEM',
FINALIZED_AT='2026-10-13T00:00:05.000+0900',

-- 요청 A의 주문 UPDATE SET 절과 WHERE 조건 중 발췌
CANCEL_REASON=NULL, CANCELLED_BY=NULL, FINALIZED_AT=NULL,

where ORDER_ID=65
```

### 구현 위치

구현은 저장소 루트 기준 `src/main/java/com/chatservice/marketplace/` 아래에 있다. 발송 등록과 모의 배송 완료는 `order/service/ShipmentService.java`, 미발송 자동 취소는 `order/service/OrderCancellationService.java`, 확인 기간 만료 자동 완료는 `order/service/TradeCompletionService.java`에 있다. 테스트 지원 코드는 `testsupport/` 아래에 있다. 미발송 자동 취소 실행 API는 `TestSupportUnshippedCancelController.java`, 모의 배송 완료와 확인 기간 만료 자동 완료의 실행 API는 `TestSupportJobController.java`, 테스트 지원 요청 로그는 `TestSupportRequestLogFilter.java`다. 요청 일시 중지는 `TestPause.java`와 `PausePoint.java`이고, 멈춘 요청 조회와 재개 API는 `TestSupportController.java`다.
