## 2. 계획

[작업명세 04](../../작업명세/04_테스트계획_발송등록과_미발송자동취소.md)에 따라 다음 순서로 진행한다.

1. 테스트케이스를 정한다.
2. 처리 기준 시각을 고정하고 미발송 자동 취소를 지정한 시각으로 실행할 수 있도록 테스트 지원 코드를 더한다.
3. 테스트 데이터와 JMeter 계획을 만든다.
4. 테스트케이스2, 테스트케이스2의 이후 자동 처리, 테스트케이스3의 순서로 실행하고, 서버 로그를 정리해 결과를 기록한다.
5. 결과를 작업명세 04의 「4.3 예상 결과(가설)」와 비교해 분석한다.

## 3. 진행 기록

### 2026-10-21 테스트케이스와 테스트 지원 코드 변경

- 테스트케이스를 세 개로 정했다. 요청 A(판매자의 발송 등록)는 세 테스트케이스 모두 주문을 조회한 직후에 멈추고, 요청 B(미발송 자동 취소)의 중지 위치와 먼저 재개할 요청은 테스트케이스마다 다르다. 실행 절차는 [작업명세 04](../../작업명세/04_테스트계획_발송등록과_미발송자동취소.md)의 「4.2 실행 절차」에 있다.
  - 테스트케이스1: 요청 B를 주문 조회 직후, 발송 정보 조회 전에 멈추고 요청 A를 먼저 재개한다.
  - 테스트케이스2: 요청 B를 구매자 지갑 조회 직후에 멈추고 요청 B를 먼저 재개한다.
  - 테스트케이스3: 요청 B를 구매자 지갑 조회 직후에 멈추고 요청 A를 먼저 재개한다.
- 테스트케이스1은 실행하지 않기로 했다. 코드 분석으로 예상한 결과가 정상 동작과 같아, 문제 확인 과정에서 재현할 문제가 없기 때문이다. 테스트케이스1에서 쓰는 요청 B의 중지 위치도 코드에 두지 않았다.
- 테스트케이스2에서 요청 A는 요청 B가 커밋한 뒤에 재개되므로, 요청 B가 위의 두 중지 위치 가운데 어디에서 멈춰도 요청 B가 발송 정보를 조회하는 시점에 요청 A는 발송 정보를 저장하기 전이다. 그래서 테스트케이스2는 이미 코드에 있는 구매자 지갑 조회 직후의 중지 위치를 쓰기로 했다.
- 테스트케이스2와 3은 각각 별도의 주문으로 실행하기로 했다. 테스트케이스2를 마친 주문은 테스트케이스3을 실행하기 전에 모의 배송 완료와 확인 기간 만료 자동 완료까지 이어서 진행해, 판매자에게도 판매대금이 지급되는지 확인하기로 했다([작업명세 04](../../작업명세/04_테스트계획_발송등록과_미발송자동취소.md)의 「4.2.3 테스트케이스2의 이후 자동 처리」).
- 발송 등록은 발송 기한 직전의 처리 기준 시각으로, 미발송 자동 취소는 발송 기한이 지난 뒤의 시각으로 같은 순간에 처리할 수 있도록 테스트 지원 코드를 더했다.
  - `src/main/java/com/chatservice/marketplace/testsupport/TestClock.java`를 추가했다. 테스트 설정이 켜져 있을 때만, 서비스가 현재 시각을 구할 때 쓰는 `Clock` 빈 대신 등록된다. 고정하지 않았으면 시스템 시각을, 고정했으면 고정을 풀 때까지 고정한 시각을 돌려준다.
  - `src/main/java/com/chatservice/marketplace/testsupport/TestSupportClockController.java`를 추가했다. 처리 기준 시각을 지정한 시각으로 고정하고, 고정을 풀고, 지금의 처리 기준 시각과 고정 여부를 조회하는 테스트 지원 API다. 고정과 해제는 서버 로그에 남긴다.
  - `src/main/java/com/chatservice/marketplace/testsupport/TestSupportUnshippedCancelController.java`를 추가했다. 미발송 자동 취소를 요청에서 지정한 처리 기준 시각으로 한 번 실행하고 처리한 주문 수를 돌려주는 테스트 지원 API다. 처리 기준 시각을 지정하지 않으면 서버의 현재 시각을 쓰고, 지정한 시각과 처리 건수를 서버 로그에 남긴다. 미발송 자동 취소는 이 요청을 처리하는 서버 스레드에서 실행되므로, 요청 헤더로 지정하면 구매자 지갑 조회 직후에 멈출 수 있다.
  - `src/main/java/com/chatservice/marketplace/testsupport/PausePoint.java`: 구매자 지갑 조회 직후 중지 위치의 설명에 미발송 자동 취소도 이 위치를 지난다는 내용을 더했다.
- 모의 배송 완료와 확인 기간 만료 자동 완료를 실행하는 기존 `TestSupportJobController.java`는 고치지 않고, 미발송 자동 취소 실행 API를 새 클래스로 더했다. [02 테스트 발송등록과_구매자취소](../02_테스트_발송등록과_구매자취소/세부작업기록.md)의 실행03에서 쓴 코드를 그대로 두기 위해서다. 서비스 코드, 스케줄러, `ClockConfig`는 고치지 않았다.

### 2026-10-22 테스트 지원 요청 로그 추가

- 처음 실행한 테스트케이스2의 서버 로그에서 요청 B의 기록을 요청별로 나눌 수 없어, 테스트 지원 API 요청의 처리 시작과 처리 끝을 서버 로그에 남기는 테스트 지원 코드를 더한 뒤 같은 절차로 다시 실행했다.
  - 테스트 지원 API의 요청은 어느 보안 필터 체인에도 속하지 않아 서버 로그에 「요청 처리 시작」 기록이 남지 않는다. 서버는 스레드를 여러 요청에 다시 쓰므로, 이 기록이 없으면 요청 B의 로그와 SQL을 같은 스레드가 앞서 처리한 요청과 구분할 수 없다.
  - `src/main/java/com/chatservice/marketplace/testsupport/TestSupportRequestLogFilter.java`를 추가했다. 테스트 설정이 켜져 있을 때만 등록되는 서블릿 필터이며, `/test-support/`로 시작하는 요청이 시작될 때 요청 메서드·경로·쿼리 문자열·요청 이름을, 끝날 때 응답 코드를 서버 로그에 한 줄씩 남긴다.
- 기존 테스트 지원 클래스와 서비스 코드는 고치지 않았다.
- 「4. 실행 기록」의 「실행01 2026-10-22」는 이 변경을 적용한 서버로 실행했다.

## 5. 결과

### 5.1 결과 요약

[작업명세 04](../../작업명세/04_테스트계획_발송등록과_미발송자동취소.md)(S1-3, 판매자의 발송 등록과 미발송 자동 취소)의 겹침 재현 테스트를 테스트케이스2(실행01)와 테스트케이스3(실행03)으로 실행하고, 테스트케이스2의 주문을 이후 자동 처리까지 진행했다(실행02). 세 실행 모두 같은 문서의 「4.3 예상 결과(가설)」와 같은 결과가 나왔다.

두 테스트케이스 모두 발송 등록은 201을, 미발송 자동 취소는 처리 건수 1을 받아 두 요청이 모두 성공했고, 최종 주문 상태는 나중에 커밋한 요청이 정했다. 테스트케이스2에서는 나중에 커밋한 발송 등록이 주문을 진행 중·배송 중으로 되돌리고 취소 기록을 지워, 진행 중인 주문에 구매자 취소 반환 내역이 남았다(기준 1·3 위반). 이 주문을 이후 자동 처리까지 진행하자 확인 기간 만료 자동 완료가 판매자에게도 판매대금 290,000원을 지급해, 결제액 290,000원인 주문에서 구매자 반환과 판매자 지급으로 580,000원이 나갔다(기준 3 위반). 테스트케이스3에서는 나중에 커밋한 미발송 자동 취소가 배송 상태를 발송 대기로 되돌려, 취소 완료된 주문에 발송 정보가 남았다(기준 1·4 위반). 판매자는 발송 등록이 성공한 응답을 받았지만, 최종 주문은 취소 완료였다.

미발송 자동 취소는 주문을 취소하기 전에 발송 정보가 있는지 한 번 더 조회한다. 그러나 두 테스트케이스 모두 이 조회가 발송 등록이 발송 정보를 저장하기 전에 실행되어, 취소를 막지 못했다.

결과의 해석은 [실행결과 분석](실행결과_분석.md)의 「분석01 2026-10-22」, 「분석02 2026-10-22」, 「분석03 2026-10-23」에 있다.

- 처리 기준 시각의 고정과 해제 요청은 응답 코드 200과 응답 본문의 `"fixed":true`(고정한 시각 포함) 또는 `"fixed":false`를 검사한다. A-1의 고정에 실패하면 스레드 1은 요청 A를 보내지 않고 멈춘다
- 실행02는 이후 자동 처리 계획의 「1. 로그인」과 「2. 이후 자동 처리」를 실행했다. 「2. 이후 자동 처리」는 한 스레드가 C-1~C-7을 차례로 보낸다. C-2의 응답에서 첫 주문의 주문 ID를, C-4의 응답에서 상품 확인 기한을 꺼내 다음 요청에 넣는다. C-3의 `now`는 테스트케이스2 테스트 데이터 CSV의 `delivery_complete_now` 값이다. C-3과 C-5는 응답 코드 200과 응답 본문의 처리 건수 1을 검사한다
