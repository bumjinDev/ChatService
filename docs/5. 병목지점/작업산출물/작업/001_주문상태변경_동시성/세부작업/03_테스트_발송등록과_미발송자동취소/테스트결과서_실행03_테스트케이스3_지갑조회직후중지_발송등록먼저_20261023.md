## 1. 개요

판매자의 발송 등록(요청 A)과 미발송 자동 취소(요청 B)가 같은 주문을 처리하는 도중에 겹치게 하여, 두 처리 가운데 하나만 성공하는지 확인했다. 서버는 요청 A를 발송 기한 0.5초 전의 처리 기준 시각으로, 요청 B를 요청에서 지정한 발송 기한 5초 뒤의 처리 기준 시각으로 처리했다. 요청 A는 주문 조회 직후에, 요청 B는 구매자 지갑 조회 직후에 멈추고, 요청 A를 먼저 재개했다.

요청 A가 먼저 커밋해 발송 정보를 저장하고 주문을 배송 중으로 바꿨지만, 요청 B도 처리 건수 1로 주문을 취소하고 결제액 290,000원을 구매자에게 반환했다. 최종 주문은 취소 완료·발송 대기이고, 발송 정보 1행이 남았다. 판매자는 발송 등록이 성공한 응답(201)을 받았다.

이 결과는 [작업명세 04](../../작업명세/04_테스트계획_발송등록과_미발송자동취소.md)의 「4.3 예상 결과(가설)」에 있는 테스트케이스3 행의 예상과 같았고, 결과 확인 기준 1과 4를 만족하지 못했다.

## 2. 테스트 대상

테스트 대상은 미니PC에 배포해 실행 중인 ChatService 서버이며, 실행01·02와 같은 서버 프로세스다.

발송 등록에서는 현재 시각을 구한 뒤 주문을 조회한다. 이후 판매자인지, 거래가 끝나지 않았는지, 발송 정보가 없는지, 발송 기한 전인지를 검사한다. 검사를 통과하면 발송 정보를 저장하고 주문을 배송 중으로 바꾼다. 데이터를 바꾼 트랜잭션이 커밋된 뒤에는 별도 트랜잭션에서 응답에 필요한 주문과 발송 정보 등을 조회한다.

미발송 자동 취소에서는 진행 중·발송 대기이면서 발송 기한이 지난 주문의 ID 목록을 조회한다. 각 주문은 새 트랜잭션에서 다시 조회하고, 거래 상태·배송 상태·발송 기한과 발송 정보 유무를 검사한다. 취소할 수 있으면 구매자 지갑을 조회한 뒤 주문을 취소 완료로 바꾸고 결제액을 구매자에게 반환한다. 주문별 처리가 커밋되면 처리 건수에 반영한다.

테스트를 위해 추가한 요청 일시 중지 기능은 요청 헤더에 지정한 중지 위치에서 처리를 멈추고, 재개 요청이 오면 이어서 처리한다. 멈춘 동안에도 트랜잭션과 DB 연결은 유지되며, 재개된 요청은 처음부터 다시 처리하지 않고 멈추기 전에 조회해 둔 주문으로 멈춘 위치부터 처리를 이어 간다([작업명세 04](../../작업명세/04_테스트계획_발송등록과_미발송자동취소.md)의 「4.2 실행 절차」). 이번 테스트의 중지 위치는 요청 A의 주문 조회 직후와 요청 B의 구매자 지갑 조회 직후다. 미발송 자동 취소 실행 API는 요청에서 지정한 처리 기준 시각으로 자동 처리를 실행하고 처리 건수를 반환한다. 테스트 지원 요청 로그는 자동 처리와 일시 중지 제어 요청의 시작·종료 및 응답 코드를 남긴다.

## 5. 수행 절차

JMeter 계획의 「1. 로그인」, 「4. 테스트케이스3 주문 만들기」, 「5. 테스트케이스3 테스트」를 실행했다. 로그인과 주문 만들기를 마친 뒤 테스트 항목의 스레드 세 개를 동시에 시작했다. 재개 제어는 서버에서 멈춘 두 요청을 차례로 재개하는 JMeter 스레드다.

## 8. 정리 및 결론

### 요청 A가 성공한 이유

서버는 요청 A에서 주문을 조회하기 전에 요청 B를 구매자 지갑 조회 직후에 멈췄다. 결제 뒤 요청 A의 주문 조회 전까지 주문 66을 바꾼 UPDATE는 없었다. SELECT로 읽은 값 자체는 로그에 남지 않지만, 결제 결과와 이후 저장한 값으로 보아 요청 A는 결제 직후의 진행 중·발송 대기 주문을 조회한 것으로 판단된다(서버 시각: 결제 처리 14:31:55, 요청 B 중지 14:35:26.453, 요청 A 주문 조회 14:35:26.521).

요청 A의 처리를 재개한 뒤 발송 정보 유무를 조회했고, 발송 정보가 없어 검사를 통과했다. 발송 기한 검사에는 주문 조회 전에 구한 처리 기준 시각인 2026-10-12T14:59:59.500Z를 사용했다. 발송 기한인 2026-10-12T15:00:00Z보다 앞서므로 이 검사도 통과했다. 서버는 발송 정보를 추가하고 주문을 진행 중·배송 중으로 바꾼 뒤 커밋했다(서버 시각: 재개 14:35:26.836, 발송 정보 조회 14:35:26.839, 추가 14:35:26.843, 주문 UPDATE 14:35:26.859, 커밋 14:35:26.864).

요청 A를 처리하는 동안 요청 B는 데이터를 바꾸지 않은 채 멈춰 있었다(서버 시각: 요청 B 중지 14:35:26.453, 요청 A 커밋 14:35:26.864, 요청 B 재개 14:35:27.071). 따라서 요청 A는 다른 요청과 겹치지 않았을 때와 같은 순서로 처리되었다. p6spy가 기록한 요청 A의 주문 UPDATE 실행 시간은 14 ms였다.

### 요청 B의 발송 정보 조회가 취소를 막지 못한 이유

미발송 자동 취소에서는 주문마다 새 트랜잭션을 열어 주문을 다시 조회하고, 거래 상태·배송 상태·발송 기한을 검사한 뒤 발송 정보가 있는지 조회한다. 이번 실행에서 요청 B의 발송 정보 조회는 요청 A의 주문 조회보다 먼저 이루어졌다. 발송 정보가 추가되기 전이어서 이 조회에는 발송 정보가 나오지 않았고, 서버는 구매자 지갑을 조회한 직후 요청 B의 처리를 멈췄다(서버 시각: 요청 B 주문 조회 14:35:26.449, 발송 정보 조회 14:35:26.451, 지갑 조회 14:35:26.452, 중지 14:35:26.453, 요청 A 주문 조회 14:35:26.521).

요청 B의 처리는 요청 A의 커밋 뒤에 재개되었지만 발송 정보는 다시 조회하지 않았다. 재개 뒤에는 취소 반환 내역 추가, 대화 조회, 상품 조회, 주문 UPDATE, 지갑 UPDATE, 상품·구매자·판매자 조건의 주문 조회와 커밋이 이어졌다. 미발송 자동 취소의 발송 정보 검사는 구매자 지갑 조회 전에 한 번만 있으므로, 요청 A가 저장한 발송 정보가 취소 처리에 반영되지 않았다. 취소 처리의 상태 검사도 중지 전에 조회한 진행 중·발송 대기 주문으로 이루어져 통과했다(서버 시각: 요청 A 발송 정보 추가 14:35:26.843, 커밋 14:35:26.864, 요청 B 재개 14:35:27.071, 재개 뒤 SQL과 커밋 14:35:27.075~14:35:27.096).

### 최종 주문이 취소 완료·발송 대기가 된 이유

서버는 요청 B에서 주문을 취소 완료로 바꾸면서 취소 주체를 시스템, 취소 사유를 발송 기한 만료로 저장하고, 요청 B의 처리 기준 시각을 종료 시각으로 썼다. 이 UPDATE와 커밋은 요청 A가 주문을 진행 중·배송 중으로 바꾸고 커밋한 뒤에 이루어졌다. 두 요청의 주문 UPDATE는 주문 ID를 뺀 모든 열을 다시 쓰며, 갱신 조건은 주문 ID 하나다(서버 시각: 요청 A UPDATE 14:35:26.859, 커밋 14:35:26.864, 요청 B UPDATE 14:35:27.088, 커밋 14:35:27.096).

요청 B의 UPDATE에는 배송 상태가 발송 대기로 들어 있었다. SELECT로 읽은 값은 로그에 남지 않지만, 재개 뒤 주문 ID로 주문을 다시 조회하지 않은 점과 UPDATE에 들어간 값으로 보아 중지 전에 조회한 주문의 배송 상태를 쓴 것으로 판단된다. 그 결과 요청 A가 커밋한 배송 중이 발송 대기로 되돌아갔다(서버 시각: 요청 B 주문 조회 14:35:26.449, 재개 14:35:27.071, UPDATE 14:35:27.088).

p6spy가 기록한 요청 B의 주문 UPDATE 실행 시간은 5 ms였다. 잠금 상태는 직접 조회하지 않았지만, 같은 주문을 바꾼 요청 A가 이미 커밋한 뒤였으므로 이 UPDATE는 행 잠금을 기다리지 않았을 것으로 보인다.

### 발송 정보가 취소 완료 주문에 남은 이유

요청 B의 재개 뒤에는 주문과 지갑이 바뀌고 취소 반환 내역이 추가되었으며, 발송 정보를 조회하거나 삭제하는 SQL은 없었다. 따라서 요청 A가 추가한 발송 정보 24가 취소 완료·발송 대기인 주문 66에 남았다. 이 때문에 거래 상태·배송 상태와 발송 정보 유무를 확인하는 기준 4에서 주문 66이 조회되었다(서버 시각: 발송 정보 추가 14:35:26.843, 요청 B 재개 14:35:27.071, 커밋 14:35:27.096).

### 취소 반환이 한 번 이루어지고 기준 2·3을 위반하지 않은 이유

이 테스트에서 결제액을 반환한 처리는 요청 B 하나다. 서버는 요청 B를 멈추기 전에 구매자 지갑을 조회했고, 재개 뒤 결제 후 잔액 10,000원에 결제액 290,000원을 더한 300,000원을 취소 반환 내역의 변동 후 잔액과 지갑 잔액으로 저장했다. 요청 A의 발송 등록에서는 지갑과 잔액 변동 내역을 바꾸지 않는다(서버 시각: 지갑 조회 14:35:26.452, 취소 반환 내역 추가 14:35:27.075, 지갑 UPDATE 14:35:27.090).

따라서 구매자의 잔액 변동 내역 합계는 지갑 잔액과 같아 기준 2에 행이 나오지 않았다. 최종 거래 상태도 취소 완료이고 취소 반환 내역은 1건이어서 기준 3에 행이 나오지 않았다.

### 요청 A의 응답과 최종 주문 상태가 다른 이유

발송 등록에서는 데이터를 바꾼 트랜잭션을 커밋한 뒤 별도 트랜잭션에서 응답에 쓸 주문을 조회한다. 이 조회가 요청 B의 재개 전에 이루어졌으므로 판매자는 진행 중·배송 중인 주문과 발송 정보를 응답으로 받았다. 이후 요청 B의 처리가 커밋되면서 DB의 최종 주문은 취소 완료·발송 대기가 되었다(서버 시각: 요청 A 응답 조회와 커밋 14:35:26.866~14:35:26.876, 요청 B 재개 14:35:27.071, 커밋 14:35:27.096).

요청 B는 자동 처리 요청이므로 응답에는 처리 건수만 담긴다. 판매자는 발송 등록 성공 응답을 받았지만, 최종 주문은 취소 완료가 되었고 결제액은 구매자에게 반환되었다.

### 저장된 시각이 처리 기준 시각과 같은 이유

발송 등록에서는 주문 조회 전에 현재 시각을 구하고 이를 발송 시각으로 저장한다. 이번 실행에서 그 값은 요청 A의 처리 기준 시각이었으므로, 발송 정보의 발송 시각은 2026-10-12T14:59:59.500Z다. 미발송 자동 취소에서는 요청에서 지정한 처리 기준 시각을 취소 시각으로 사용하므로, 주문 종료 시각·취소 반환 내역 기록 시각·구매자 지갑 갱신 시각은 모두 2026-10-12T15:00:05Z다(서버 시각: 요청 A 처리 시작 14:35:26.511, 발송 정보 추가 14:35:26.843, 요청 B 취소 반환 내역 추가 14:35:27.075, 주문 UPDATE 14:35:27.088, 지갑 UPDATE 14:35:27.090).

저장된 시각은 각각의 처리 기준 시각을 나타내므로 실제 처리 순서를 나타내는 값은 아니다. 실제 커밋 순서는 서버 로그와 p6spy 기록에서 요청 A 다음 요청 B로 확인된다(서버 시각: 요청 A 커밋 14:35:26.864, 요청 B 커밋 14:35:27.096).

### 결론

테스트케이스3의 결과는 계획서의 예상 결과와 같았다. 요청 B에서 발송 정보가 없음을 확인한 뒤 요청 A가 발송 정보를 저장했지만, 요청 B의 처리를 재개한 뒤에는 발송 정보를 다시 확인하지 않고 주문을 취소했다. 요청 A는 요청 B가 데이터를 바꾸기 전에 조회한 주문으로 처리되어 두 요청 모두 성공했다. 나중에 커밋한 요청 B에서 주문의 모든 열을 다시 쓰면서 배송 상태가 발송 대기로 되돌아갔다.

그 결과 취소 완료·발송 대기 주문에 발송 정보 1행이 남아 기준 4를 위반했다. 취소 반환은 1건이고 지갑 잔액과 잔액 변동 내역이 맞아 기준 2·3에는 행이 나오지 않았다. 판매자가 받은 발송 등록 성공 응답과 달리 최종 주문은 취소 완료다.
