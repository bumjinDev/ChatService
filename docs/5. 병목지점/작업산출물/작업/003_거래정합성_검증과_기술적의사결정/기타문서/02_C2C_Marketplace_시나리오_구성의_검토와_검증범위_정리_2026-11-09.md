## 1. 작업 목적

포트폴리오에서 요청 처리량이나 응답 시간만 제시하는 대신, 구체적인 거래 상황과 비즈니스 규칙을 근거로 정합성 문제를 설명하고 기술적 의사결정으로 연결한다.

이를 위한 작업 흐름은 다음과 같다.

**거래 상황 구성 → 요청 실행과 결과 관찰 → 문제 판단 → 정책 확정·보완 → 기술적 해결책 선택 → 수정 후 검증**

이 과정은 실행 결과를 보기 전까지 아무 규칙도 정하지 않는다는 뜻이 아니다. 정합성을 판단하려면 수량 초과 금지, 유효 예약 보호 등 최소한의 판단 기준이 먼저 필요하다. 실행 결과는 그 기준의 위반 여부를 확인하고, 아직 정하지 못한 정책이나 불편한 구매 경험을 구체화하는 근거로 사용한다.

| 관찰 결과 | 판단 및 후속 작업 |
|---|---|
| 이미 정한 규칙을 위반 | 구현 문제와 발생 원인을 조사하고 기술적 해결책 검토 |
| 규칙은 지켰지만 구매 경험이 불편 | 정책 보완 필요성과 그에 따른 비용·영향 검토 |
| 허용 여부를 판단할 규칙이 없음 | 정책부터 결정하고 구현·검증 기준 정리 |
| 처리 결과를 확인하지 못함 | 저장된 결과를 확인하기 전까지 성공·실패 및 정합성 판단 보류 |

예를 들어 구매 준비 중 다른 거래가 수량을 확보하여 결제하지 못하는 경험은, 준비 중 수량 보호를 제공하지 않는 정책에서는 허용될 수 있다. 반면 유효 예약 수량을 다른 구매가 가져가는 결과는 예약 보호 규칙의 위반이다. 두 현상을 같은 실패로 묶어 해결책을 선택하지 않는다.

측정 결과만으로 정책이나 기술적 해결책이 자동 결정되지는 않는다. 관찰한 사실, 적용할 규칙, 선택한 해결책의 이유를 연결하여 설명한다.

## 2. 기존 거래 구성에서 확보한 근거

기존 구성은 동일 조건의 중고 모니터 4대, 판매자 1명, 구매자 A·B·C·D·E를 대상으로 한다.

| 참여자 | 구매 방식과 수량 |
|---|---|
| A | 가격을 협의하여 2대를 함께 구매 |
| B·E | 등록 가격으로 각각 1대 구매 |
| C | 2대를 함께 구매하는 가격 제안 |
| D | 1대의 가격 제안 |

상품 등록부터 제안·수락·예약·구매 준비·결제까지 연결하는 과정에서 다음 기준을 구체화했다.

- 가격 제안 등록은 수량 확보가 아니다.
- 상품 조회, 수량 선택, 주문 정보 입력만으로 수량을 확보하지 않는다.
- 제안 수락과 예약 생성은 하나의 업무 처리로 연결된다.
- 유효한 예약 수량은 다른 구매와 새로운 예약으로부터 보호한다.
- A·C의 2대 구매 조건을 수량 부족에 따라 자동으로 1대로 변경하지 않는다.
- 기존 예약을 주문으로 전환해도 다른 구매자의 새 확보 가능 수량은 늘어나지 않는다.
- 구매자는 자신의 수락·예약을 확인한 뒤 합의 가격 결제를 진행한다.
- 구매 성공 후 불필요한 추가 구매를 하지 않으며, 수량 부족을 확인하면 이번 시도를 멈춘다.
- 결과 미확인 시에는 기존 처리 결과부터 확인한다.
- 구매 철회와 명시적인 재구매 목적 취소는 다른 정책으로 처리한다.

이 기준들은 이후 검증에 필요한 업무상 근거다. 거래 시나리오의 구성 방식을 조정하더라도 폐기하지 않는다.

## 3. 하나의 통합 거래에 모든 검증을 맡길 때의 한계

### 3.1 서로 다른 목적의 중첩

하나의 거래 구성에 다음 목적을 함께 부여하면 완료 기준이 불명확해질 수 있다.

1. 참여자의 구매 목적과 행동을 자연스럽게 설명한다.
2. 구매–구매, 예약–구매, 예약–예약 경합을 모두 발생시킨다.
3. 각 경합의 결과와 원인을 구분한다.
4. 실행 결과를 정책과 기술적 의사결정의 근거로 사용한다.
5. 이후 요청 규모를 늘려 정합성과 성능을 비교한다.

자연스러운 거래 과정은 모든 경합의 발생을 보장하지 않는다. 앞선 거래의 결과가 다음에 관찰하려던 상황을 없애기도 한다.

예를 들어 C의 2대 예약이 먼저 성립하면 B·E에게 새 구매 가능 수량이 남지 않는다. 이후 B·E가 수량 부족을 확인하더라도, 두 구매가 같은 남은 수량을 두고 경합하는 상황을 충분히 검증했다고 볼 수 없다.

또한 판매자가 앞선 수락 결과를 확인한 뒤 다음 제안을 검토하는 행동을 유지하면, 그 흐름으로 두 수락 처리의 동시 발생을 구성할 수 없다.

### 3.2 요청 순서를 고정할 때와 무작위화할 때의 어려움

원하는 경합을 반드시 만들기 위해 요청 순서를 세밀하게 고정하면, 거래의 자연스러운 흐름보다 기능별 경합 테스트를 위한 배치가 중심이 된다. 반대로 모든 요청을 무작위로 호출하면 수락·예약 확인 후 결제와 같은 필수 행동 관계가 깨지고, 앞서 구성한 거래 흐름과 실행이 분리된다.

| 접근 | 발생할 수 있는 한계 |
|---|---|
| 모든 경합을 만들도록 행동과 순서를 고정 | 결과에 따라 달라져야 할 행동까지 미리 정하거나, 경합만을 위한 부자연스러운 행동을 추가할 수 있음 |
| 모든 요청을 무작위로 호출 | 예약 없는 합의 가격 결제, 결과 미확인 상태의 추가 요청 등 거래 조건에 맞지 않는 행동이 섞일 수 있음 |
| 자연스러운 거래 진행만 유지 | 특정 경합이 발생하지 않거나, 다른 거래 결과 때문에 검증 기회가 사라질 수 있음 |

따라서 문제는 시나리오를 사용한 것 자체가 아니라, 거래 설명과 특정 경합의 확실한 관찰을 하나의 실행 구성으로 모두 해결하려 했던 범위 설정에 있다.

## 4. 역할을 구분한 구성 방향

| 구분 | 답할 질문 | 주요 내용 |
|---|---|---|
| 거래 시나리오 | 누가 왜 요청하며 결과에 따라 어떻게 행동하는가? | 구매 목적, 참여자의 정보, 행동 관계, 정책 |
| 경합 검증 시나리오 | 특정 요청들이 겹쳐도 규칙이 지켜지는가? | 출발 상태, 대상 요청, 허용 결과, 위반 결과 |
| 규모·성능 검증 | 요청이 많아졌을 때 정합성과 처리 특성이 어떻게 달라지는가? | 요청 구성과 규모, 비교 조건, 관찰·측정 항목 |

세 범위는 서로 근거를 제공하지만 동일한 이야기나 한 번의 실행으로 구성할 필요는 없다.

거래 시나리오는 경합 검증에 출발 상태, 요청의 업무상 의미, 결과 이후의 행동을 제공한다. 경합 검증은 그중 확인할 질문을 좁힌다. 규모 검증은 목적과 요청 구성이 정해진 뒤 수행한다.

### 4.1 필수 행동 관계와 실행 시점의 구분

수락·예약을 확인한 뒤 합의 가격으로 결제하는 순서는 유지한다. 반면 서로 다른 구매자의 등록 가격 구매 사이에는 업무상 고정 순서가 없다. 경합 검증에서는 이러한 독립적인 요청의 실행 시점을 조절할 수 있다.

즉, 모든 요청의 순서를 고정하거나 모든 요청을 무작위화할 필요는 없다. 거래상 필요한 행동 관계는 유지하고, 검증 대상인 독립 요청들의 겹침을 별도로 다룬다. 구체적인 동기화 방식과 요청 간격은 후속 설계 사항이다.

통제한 경합 검증을 실제 이용 패턴의 재현으로 설명하지 않는다. 실제 이용 데이터에 따른 발생 빈도나 대표성은 확인되지 않았다.

### 4.2 결과의 변동성과 판단 기준의 구분

누가 수량을 확보하는지는 실행마다 달라질 수 있다. 그렇더라도 수량 초과 금지와 예약 보호 기준은 고정할 수 있다.

예를 들어 마지막 1대에 두 구매 요청이 진행될 때 성공자가 B인지 E인지는 달라질 수 있지만, 두 주문을 모두 성립시켜 같은 수량을 중복 판매하면 안 된다는 기준은 명확하다.

요청 전송 순서와 거래 성립 순서는 구분한다. 독립적으로 진행할 수 있다는 사실만으로 서버 처리가 실제로 겹쳤다고 판단하지 않는다.

## 5. 단계별 검증 범위

### 5.1 기존 예약·주문이 없는 기본 경합

여기서 예약 요청은 구매자의 가격 제안 등록이 아니라 판매자의 수락에 따른 예약 생성 처리를 뜻한다.

| 요청 조합 | 핵심 질문 |
|---|---|
| 예약–예약 | 여러 수락이 같은 수량에 예약을 생성할 때 확보 가능한 수량을 초과하지 않는가? |
| 예약–등록 가격 구매 | 새로운 예약과 새로운 주문이 같은 수량을 중복 확보하지 않는가? |
| 등록 가격 구매–등록 가격 구매 | 여러 주문이 같은 수량을 중복 구매하지 않는가? |

먼저 각 항목의 출발 상태, 대상 요청, 결과 확인 방식, 허용·위반 결과를 각각 구성한다. 이 문서에서는 상세 테스트 명세나 실행값을 확정하지 않는다.

예약–예약은 기술적 동시성 검증으로 구분한다. 기존의 단일 판매자 순차 검토 흐름만으로 두 수락의 겹침을 설명하지 않는다. 일반적인 이용 과정에서 실제로 발생하는 경로는 별도로 확인해야 한다. 기능의 동시 요청 안전성을 검증하는 목적과 실제 발생 가능성을 설명하는 목적을 혼동하지 않는다.

### 5.2 기존 예약 또는 기존 주문이 있는 상태

기본 요청 조합에 다음 출발 상태를 적용한다.

| 기존 상태 | 추가로 확인할 내용 |
|---|---|
| 유효 예약이 이미 존재 | 새로운 요청들이 기존 예약 수량을 침해하지 않는지 |
| 주문이 이미 성립하여 수량 차감 | 이미 판매한 수량을 다시 확보 가능한 것으로 계산하지 않는지 |

예약으로 보호하는 수량과 주문 성립으로 차감한 수량은 구분한다. 기존 주문을 단순히 예약과 같은 점유 상태로 취급하지 않는다.

이 단계에서는 기존 상태를 고정하여 새 요청의 처리에 정확히 반영되는지 확인한다. 기존 예약자의 결제까지 동시에 움직이는 문제는 다음 범위로 분리한다.

### 5.3 기존 예약의 주문 전환

기존 예약자가 결제하는 동안 다른 구매자의 새 예약 또는 등록 가격 구매가 진행되는 상황을 다룬다.

이는 새로운 수량 확보끼리의 경쟁과 구분된다. 기존 예약자는 이미 보호된 수량을 주문으로 전환한다. 전환 과정에서 해당 수량이 다른 거래에 열리거나, 예약과 주문 양쪽에 중복 계산되어서는 안 된다.

### 5.4 요청 규모 증가의 위치

요청이 많아지면 실행 도중 예약·주문이 누적될 수 있다. 하지만 원하는 상태에서 원하는 요청들이 실제로 겹쳤다는 보장은 없다. 수량이 일찍 소진되어 대부분의 요청이 수량 부족으로 끝날 수도 있다.

따라서 규모 확대는 특정 출발 상태를 지정한 검증을 대신하지 않는다. 개별 검증 질문을 정한 뒤 요청 규모와 구성을 확대한다.

성공·수량 부족·기타 실패의 비율이 달라지면 전체 평균 응답 시간의 의미도 달라질 수 있다. 향후 측정에서는 요청 종류와 결과 구성을 구분하여 해석할 수 있어야 한다. 구체적인 지표와 도구는 아직 정하지 않는다.

## 6. 취소 기능 수정과 후속 검증

취소는 첫 구매의 기본 경합과 구분하되, 기능 수정 후 검증할 항목에 포함한다. 실제 성립한 취소 가능한 주문을 대상으로 시작한다. 주문이 없는 구매자에게 취소를 붙이지 않는다.

### 6.1 의도별 취소 처리

| 취소 의도 | 채택한 처리 | 확인할 사항 |
|---|---|---|
| 구매 철회 | 주문 취소·수량 복구와 해당 구매 기회의 보호 종료. 새 예약을 만들지 않음 | 복구된 수량이 다른 거래에 열리는지, 별도 예약 해제를 요구하지 않는지 |
| 주소 수정 등 명시적인 재구매 | 주문 취소·수량 복구와 같은 합의 가격·수량의 한시적 보호 | 보호 수량이 다른 거래에 넘어가지 않는지, 조건과 기한 안에서 재결제할 수 있는지 |

구매 철회와 재구매 목적 취소를 구분하도록 기능을 수정해야 한다. 정책 채택은 구현 완료를 뜻하지 않는다. 구체적인 화면·API·저장 구조는 이 문서에서 확정하지 않는다.

### 6.2 보호 기한과 반복 취소

- 같은 합의의 첫 재구매 목적 취소가 성립할 때 보호 기한을 정한다.
- 재결제 후 다시 재구매 목적 취소를 해도 최초 보호 기한을 연장하지 않는다. 시간이 흐른 만큼 재구매에 사용할 수 있는 시간이 줄어든다.
- 최초 제안 수락 당시 예약의 남은 시간만 계속 사용하는 정책과는 다르다.
- 보호 유지는 업무상 수량 보호의 연속성을 뜻한다. 기존 예약 기록의 재사용 또는 새 기록 생성 중 하나를 강제하지 않는다.
- 반복 취소는 처음 취소한 주문이 아니라 재결제로 성립한 현재 살아 있는 주문을 대상으로 한다.
- 미결제 상태로 기한이 끝나거나 보호 중 구매를 철회하면 보호를 종료한다. 주문 취소 시 이미 수량을 복구했으므로 다시 복구하지 않는다.
- 기한 전에 성립한 재주문은 기한이 지났다는 이유로 취소하지 않는다.

### 6.3 취소와 다른 거래의 연결

구매 철회로 복구된 수량과 재구매 목적으로 보호되는 수량이 다른 구매자의 조회·예약·구매에 올바르게 반영되는지 확인한다. 취소와 보호가 함께 성립해야 하는 경우에 다른 거래가 그 수량을 가져가는 공백을 허용하지 않는다.

다른 구매자가 취소 사실을 자동으로 안다고 구성하지 않는다. 재방문·상품 조회·판매자의 안내 등 실제로 상태를 확인한 계기가 있어야 새로운 구매 판단으로 이어진다. 특정 결말을 만들기 위해 재방문이나 재시도를 강제하지 않는다.

### 6.4 미정 또는 범위 밖인 사항

- 보호를 제공할 수 없는 재구매 목적 취소의 구체적 처리 방식은 미정이다. 구매 철회로 자동 전환하여 주문만 취소하지 않는다.
- 구체적인 보호 기간은 미정이다. 기존 20분은 잠정 설명값이다.
- 등록 가격 주문에 새로운 재구매 예약 기능을 추가하는 정책은 채택하지 않았다.
- 취소·환불에 따른 잔액 정책은 별도 범위다.
- 판매자 취소·미발송 자동 취소, 결제 준비 중 임시 점유, 제안 유효기간·철회는 이번 정리에서 추가 채택하지 않는다.

## 7. 문서 및 실행 구성의 역할

| 자료 | 역할 |
|---|---|
| 기본 비즈니스 시나리오 구성과 논의 근거 종합 정리 | 구매 목적, 기존 확인 기록, 정책과 그 근거 보존 |
| A~E 첫 구매 대표 거래 시나리오 | 전체 거래의 행동과 결과 연결 설명 |
| 이 문서 | 통합 구성의 한계와 검증 범위 분리의 이유 정리 |
| 후속 경합 검증 시나리오 | 항목별 출발 상태·요청·결과 확인·판단 기준 구체화 |

기존 자료를 폐기하거나 모든 거래 설명을 다시 작성하지 않는다. 첫 구매 대표 시나리오에는 모든 경합을 반드시 재현해야 하는 역할을 부여하지 않는다.

향후 기본 거래와 취소 후속 거래를 포함한 하나의 통합 실행 파일을 사용한다는 방향은 유지한다. 하나의 파일 안에서 검증 항목을 구분하는 것과 모든 요청을 한꺼번에 섞는 것은 다른 구성이다.

## 8. 후속 진행과 현재 상태

후속 논의는 다음 순서로 진행한다.

1. 기존 예약·주문이 없는 세 가지 기본 경합을 각각 구체화한다.
2. 기존 예약 또는 기존 주문이 있는 출발 상태를 적용한다.
3. 기존 예약의 주문 전환과 새 확보 요청의 관계를 구성한다.
4. 취소 의도별 후속 시나리오를 구체화하고, 해당 정책에 맞는 기능 수정 후 검증한다.
5. 확인할 문제와 판단 기준이 정해진 뒤 요청 규모·실행 방법·측정 항목을 구체화한다.

현재 정리한 것은 검증 방향과 업무상 기준이다. 상세 테스트 명세 작성, 실행 파일 작성, 새 테스트 실행, 코드·설정 변경을 완료한 상태가 아니다. 기술적 해결책도 아직 선택하지 않았다.

이후 구현을 확인할 때에는 관련 기준 문서의 참조 위치부터 필요한 범위를 조사한다. 문서에 남은 과거 구현 기록을 현재 코드 또는 배포 상태의 보장으로 사용하지 않는다.
