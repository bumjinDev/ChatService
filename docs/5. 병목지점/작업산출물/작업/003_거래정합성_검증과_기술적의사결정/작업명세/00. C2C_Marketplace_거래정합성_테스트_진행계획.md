## 1. 테스트를 진행하려는 목적

거래 상황에 맞는 요청을 구성하고 실행 결과를 관찰하여 정합성이 지켜지는지 확인한다. 관찰 결과를 바탕으로 비즈니스 규칙을 확정하거나 보완하고, 문제를 해결하기 위한 기술적 의사결정과 수정 후 검증으로 이어 간다.

정합성이 틀어졌는지 판단하려면 수량 초과 금지와 유효 예약 보호처럼 실행 전에 정할 기준이 필요하다. 실행 후에는 이미 정한 규칙을 위반한 결과, 규칙은 지켰지만 불편한 구매 경험, 아직 정책이 없어 판단하기 어려운 결과를 구분한다.

## 2. 시나리오 구성 방향

기존 A~E 거래 구성은 구매 목적과 정책, 행동의 연결을 설명하는 자료로 유지한다. 하나의 자연스러운 거래에서 모든 기능 간 경합을 반드시 발생시키려 하지는 않는다.

원하는 경합을 만들려고 모든 요청 순서를 고정하면 거래 결과에 따라 달라져야 할 행동까지 미리 정하게 된다. 반대로 모든 요청을 무작위로 호출하면 수락·예약 확인 후 결제와 같은 필수 행동 관계가 깨진다.

따라서 거래에 필요한 선후 관계는 유지하고, 서로 독립적으로 진행할 수 있는 요청을 대상으로 경합을 구성한다. 기능 간 경합을 각각 살펴본 뒤 기존 상태와 복합 상황을 추가한다. 요청을 함께 보냈다는 사실만으로 실제 서버 처리가 겹쳤다고 판단하지 않는다.

## 3. 기본적인 세 가지 경합부터 구성

기존 예약이나 주문이 없는 상태에서 다음 세 가지를 각각의 시나리오로 구성한다.

| 구분 | 확인할 내용 |
|---|---|
| 예약–예약 | 여러 수락이 같은 수량에 예약을 중복 생성하지 않는가 |
| 예약–등록 가격 구매 | 새로운 예약과 주문이 확보 가능한 수량을 초과하지 않는가 |
| 등록 가격 구매–등록 가격 구매 | 여러 주문이 같은 수량을 중복 구매하지 않는가 |

여기서 예약은 가격 제안 등록이 아니라 판매자의 수락에 따라 수량 보호가 성립하는 처리를 뜻한다. 수락과 예약 생성은 하나의 업무 처리로 연결된다.

각 시나리오를 구성할 때에는 요청 전 상태, 요청 주체와 내용, 필요한 선행 행동, 결과 확인 방법, 허용 결과와 규칙 위반 결과를 정한다. 결과에 따라 다음 행동이 어떻게 달라지는지도 포함한다.

판매자가 앞선 수락 결과를 확인하고 다음 제안을 검토하는 흐름에서는 두 수락 처리가 겹치지 않는다. 따라서 예약–예약은 우선 기술적 동시성 검증으로 구분하고, 실제 이용 과정에서 발생하는 경로는 별도로 확인한다.

## 4. 기존 거래가 있는 상황과 주문 전환으로 확장

기본 경합을 구성한 뒤, 이미 예약이나 주문이 있는 상태에서 같은 요청들이 진행되는 상황을 추가한다.

- 기존 예약이 있는 상태에서 새로운 예약 또는 구매가 진행될 때 보호 수량을 침해하지 않는지 확인한다.
- 기존 주문으로 수량이 차감된 상태에서 새로운 예약 또는 구매가 진행될 때 이미 판매한 수량을 다시 사용할 수 있는 것으로 계산하지 않는지 확인한다.
- 기존 예약을 결제하여 주문으로 전환하는 동안 새로운 예약 또는 구매가 진행될 때 보호 공백이나 수량 중복 계산이 생기지 않는지 확인한다.

기존 상태를 고정한 경우와 그 상태가 바뀌는 도중의 경우를 구분한다. 등록 가격 구매로 주문이 성립한 상태는 수량이 차감된 상태이며, 예약으로 보호 중인 상태와 동일하게 취급하지 않는다.

요청 규모를 늘리면 이러한 상태가 실행 도중 생길 수는 있다. 하지만 필요한 상태에서 원하는 요청들이 실제로 경합했다는 보장은 없으므로, 규모 증가로 각 상황의 검증을 대신하지 않는다.

## 5. 취소 후속 시나리오와 기능 수정

취소는 취소 대상, 취소 의도, 수량 변화와 보호 여부를 먼저 정리하고 다른 예약·구매와 맞물리는 상황을 구성한다. 실제 성립한 취소 가능한 주문에서 시작하며, 주문이 없는 사람에게 주문 취소를 붙이지 않는다.

| 구분 | 적용할 처리 | 다른 거래와의 관계 |
|---|---|---|
| 합의 가격 주문의 구매 철회 | 주문 취소·수량 복구·해당 구매 기회의 보호 종료. 새 예약 없음 | 복구 수량을 새로운 예약·구매가 확보할 수 있음 |
| 합의 가격 주문의 명시적 재구매 목적 취소 | 주문 취소·수량 복구와 같은 합의 가격·수량의 한시적 보호 | 보호 수량을 다른 예약·구매가 확보하면 안 됨 |
| 등록 가격 주문의 구매 철회 | 주문 취소와 수량 복구 | 복구 수량을 새로운 예약·구매가 확보할 수 있음 |
| 재구매 후 반복 취소 | 현재 살아 있는 주문 취소, 최초 재구매 보호 기한 유지 | 반복 취소로 보호 기간이 연장되면 안 됨 |
| 미결제 상태의 보호 종료 | 기한 종료 또는 보호 중 철회로 보호 종료 | 수량을 다시 복구하지 않고 새 확보가 가능해짐 |

취소가 끝난 뒤 다른 거래가 진행되는 경우와 취소 처리 중 새로운 확보 요청이 들어오는 경우를 나누어 검토한다. 모든 조합을 기계적으로 늘리지 않고, 확인할 규칙과 상태 변화가 다른 경우를 구분한다.

구매 철회와 재구매 목적 취소를 구분하도록 기능을 수정한 뒤 해당 시나리오를 테스트한다. 정책을 채택한 상태와 구현을 완료한 상태는 구분한다.

미결제 예약 자체의 해제는 주문 취소와 구분하며, 별도 항목의 필요성을 후속 검토한다. 다른 구매자의 새 시도에는 재방문·조회 등 현재 상태를 확인한 계기가 필요하다. 취소 사실을 저절로 알거나 특정 결말을 위해 반드시 재방문하는 것으로 구성하지 않는다.

취소·환불의 잔액 정책, 판매자 취소·미발송 자동 취소, 결제 준비 중 임시 점유, 제안 유효기간·철회는 이번 계획에서 추가 채택하지 않는다.

## 6. 취소가 여러 지점에서 복합적으로 발생하는 상황

앞의 다섯 가지 취소·보호 항목을 각각 구성하고 검증한 뒤, 이 항목들이 여러 거래 지점에서 복합적으로 발생하는 시나리오도 구성한다.

개별 기능의 결과뿐 아니라 여러 취소, 보호 유지와 종료, 재구매, 새로운 예약·구매가 이어지는 과정에서 전체 수량과 각 구매자의 보호가 유지되는지 살펴본다.

현재는 이 복합 상황을 후속 작업에 포함한다는 방향까지 정한다. 구체적인 조합, 요청 순서와 규모는 개별 항목의 검증을 마친 뒤 정한다.

## 7. 시나리오별 규모와 결과 분석

각 시나리오에는 먼저 정합성을 확인할 수 있는 최소 규모를 정한다. 예를 들어 상품 1대에 두 요청이 각각 1대를 확보하려는 상황으로 시작할 수 있다. 필요한 경우에는 두 요청을 모두 수용할 수 있는 수량에서도 정상 거래가 불필요하게 제한되지 않는지 확인한다. 구체적인 수치는 개별 시나리오를 작성하면서 정한다.

규모를 늘리는 목적은 요청이 많아지거나 경합이 심해지는 조건에서도 비즈니스 규칙(정책)을 지키기 위해 어떤 기술적 의사결정이 필요한지 판단할 근거를 얻는 데 있다. 테스트에서 정합성 위반 여부와 발생 조건, 처리 특성을 관찰하고, 그 결과를 기술적 해결책의 선택과 적용 후 검증으로 연결한다. 이를 기준으로 규모를 늘려 확인할 항목을 선택하며, 상품 수량, 요청당 수량, 전체 요청 수와 동시에 진행할 요청 수를 함께 정한다. 모든 시나리오에 별도의 대규모 테스트를 붙이는 것이 아니라, 기술적 의사결정에 필요한 조건을 확인할 수 있도록 규모를 정한다.

같은 수량에 요청이 집중되는 상황을 볼 것인지, 성공하는 거래가 계속 이어지는 상황을 볼 것인지에 따라 구성을 달리한다. 성공·수량 부족·기타 실패의 구성을 구분하고 전체 평균 응답 시간만으로 개선 효과를 판단하지 않는다.

실행 결과에서 정한 규칙의 위반이 확인되면 처리 과정과 원인을 조사하고 기술적 해결책을 검토한다. 규칙을 지켰지만 구매 경험이 불편하다면 정책 보완 필요성을 검토한다. 처리 결과가 불명확하면 저장된 기존 결과부터 확인한다. 수정한 내용은 필요한 범위에서 다시 검증한다.

## 8. 앞으로의 진행

이 계획을 기준으로 테스트 항목을 하나씩 구체화하여 테스트 구성 파일로 작성한다. 먼저 세 가지 기본 경합의 출발 상태, 요청, 최소 규모와 허용 결과를 정리한다. 이후 기존 거래 상태, 주문 전환, 취소 개별 항목, 취소가 복합적으로 발생하는 상황으로 이어 간다.

실행 도구, 요청 간격과 동기화 방식, 확대 규모는 각 시나리오에서 무엇을 확인할지 정한 뒤 구체화한다. 지금 모든 테스트의 세부 구성을 확정하지 않는다.

향후 기본 거래와 취소 후속 거래를 포함하는 하나의 통합 실행 파일을 사용한다는 방향은 유지한다. 하나의 파일을 사용하더라도 검증 항목과 결과는 구분하며, 모든 요청을 한꺼번에 섞는다는 뜻은 아니다.

이 문서는 논의한 계획을 정리한 자료다. 개별 테스트 구성이나 실행, 코드·설정 수정의 완료를 뜻하지 않는다.
