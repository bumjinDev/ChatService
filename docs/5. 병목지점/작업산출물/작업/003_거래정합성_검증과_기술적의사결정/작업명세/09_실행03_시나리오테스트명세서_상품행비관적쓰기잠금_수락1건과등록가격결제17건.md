## 1. 명세 내용

### 1.1 목적과 범위

판매자가 가격 제안을 수락할 때와 구매자가 등록 가격으로 결제할 때 **같은 상품 행의 비관적 쓰기 잠금**을 얻도록 한 뒤, 실행02의 수량 부족 조건을 다시 적용한다. 선행 거래가 확정한 예약과 주문을 후행 거래가 반영하는지, 성공한 주문 수량만큼 상품 수량과 잔액이 정확히 차감되는지 확인한다.

| 구분 | 실행03에서 다루는 내용 |
|---|---|
| 검증 대상 | 같은 상품의 새 수락 1건과 등록 가격 결제 17건. 결제끼리 겹치는 구간과 수락·결제가 함께 출발하는 구간을 각각 관찰한다. |
| 준비·조회 | 기존 주문·예약과 수락 전 가격 제안은 시작 상태를 만들기 위해 준비한다. 상품·대화·지갑 조회는 거래 결과 확인에 사용한다. |
| 측정 범위 | 다섯 시점으로 분산한 요청별 응답 시간을 기록한다. 동시 출발 18건의 응답 시간 목표, 기술별 우열과 반복 횟수는 후속 평가 사항이다. |
| 별도 거래 | 합의 가격 결제, 예약 만료·취소·배송, 결제 준비 중 수량 점유, 선착순 배정은 실행03의 검증 대상에서 제외한다. |

### 1.2 테스트 배경

판매 수량 16개인 상품에 이미 주문 3개와 유효 예약 4개가 있다. 판매자는 새 흥정 구매자의 가격 제안 2개를 수락하려 하고, 다른 구매자 17명은 같은 상품을 각각 1개씩 구매한다.

실행02에서는 같은 시점에 출발한 두 결제가 남은 수량 13개를 읽고 각각 12개를 저장했다. 종료 시 전체 주문 20개와 유효 예약 6개가 판매 수량을 10개 초과했는데도 상품에는 남은 수량이 8개로 저장됐다. 실행03에서는 먼저 끝난 거래를 반영해, 정상적으로 확보할 수 있는 9개 안에서 거래가 성립하는지 확인한다.

| 참여자 | 행동 |
|---|---|
| 판매자 | 준비 단계에서 기존 예약을 성립시킨 뒤, 검증 구간의 90초에 새 가격 제안 2개를 한 번 수락한다. |
| 기존 주문 구매자·기존 예약 구매자 | 각각 주문 3개와 유효 예약 4개를 보유한다. 검증 구간에 추가 거래 없이 기존 거래가 보존되는지 확인한다. |
| 새 흥정 구매자 | 준비 단계에서 2개를 제안한다. 검증 구간에는 판매자가 수락 요청을 보내며, 흥정 구매자는 결제하지 않는다. |
| 새 등록 가격 구매자 17명 | 각자 지정된 시점에 1개씩 한 번 결제한다. 종료 후 자신의 주문과 잔액에 결제 결과가 반영됐는지 확인한다. |

### 1.3 업무 규칙과 입력값

| 항목 | 입력과 결과 확인 기준 |
|---|---|
| 상품과 가격 | 최초 판매 수량 16개, 등록 가격 개당 10,000원. 기존·새 가격 제안의 단가는 9,000원이다. |
| 초기 수량 | 기존 주문 1건·3개이므로 상품의 남은 수량은 13개다. 기존 유효 예약 4개를 빼면 예약이 없는 구매자가 새로 확보할 수 있는 수량은 9개다. |
| 새 요청 | 새 수락은 2개 전부를 예약하거나 거절한다. 결제는 구매자별 1건·1개·10,000원이다. 새로 요구하는 수량은 총 19개다. |
| 수량과 금액 반영 | 수락 성공은 유효 예약만 2개 늘린다. 결제 성공은 주문 1개, 잔액 차감 10,000원, 상품 수량 차감 1개가 함께 확정돼야 한다. 수량 부족으로 거절되면 세 변경 모두 없어야 한다. |
| 거절 사유 | 결제는 다른 구매자의 유효 예약을 뺀 구매 가능 수량이 주문 수량보다 적으면 거절한다. 수락은 예약할 수 있는 수량이 제안 수량보다 적으면 거절한다. 이 시나리오에서 상품의 남은 수량은 끝까지 4개 이상이므로, 남은 수량 자체가 주문 수량보다 적다는 사유의 결제 거절은 기대 결과가 아니다. |
| 순서와 기한 | 같은 시점에 출발한 요청의 성공 순서는 고정하지 않는다. 기존·새 예약은 종료 확인까지 유효해야 하며 기존 주문의 자동 상태 변경도 이 구간에 개입하지 않아야 한다. |

### 1.4 테스트 시작 전 준비

데이터를 준비하기 전에 코드를 아래 순서로 준비한다.

1. 비관적 쓰기 잠금을 반영하기 전의 코드 파일을 백업한다. 백업 대상은 잠금을 반영하면서 수정할 파일이고, 백업한 파일의 원본 경로와 백업 위치를 기록한다.
2. 가격 제안 수락과 등록 가격 결제의 첫 상품 조회에 같은 상품 행의 비관적 쓰기 잠금을 반영한다.

로깅은 수정하지 않는다.

새 상품과 이번 실행의 참여자·요청 식별값으로 준비한다. 실행02의 상품·주문·예약·결제 요청 ID나 종료 상태를 재사용하지 않는다. 준비 완료 직후, 첫 검증 요청 전에 아래 값을 기록한다.

| 대상 | 준비와 확인 |
|---|---|
| 상품·기존 주문 | 상품을 16개 등록한다. 기존 주문 구매자에게 30,000원을 충전하고 3개를 결제한다. 주문 1건·30,000원, 잔액 0원, 상품의 남은 수량 13개를 대조한다. |
| 기존 예약 | 다른 구매자가 4개를 제안하고 판매자가 수락한다. 해당 예약 1건의 수량·소유자·만료 시각을 확인한다. 상품의 남은 수량은 13개다. |
| 새 제안 | 새 흥정 구매자가 2개를 제안한다. 판매자 응답 대기 상태이고 이 제안에 연결된 예약이 없어야 한다. 기존 예약 구매자와 새 흥정 구매자의 잔액은 각각 0원이다. |
| 새 결제 | 새 구매자 17명에게 각 10,000원을 충전한다. 각 구매자에게 해당 상품의 기존 주문·유효 예약이 없고, 구매 가능 수량이 9개인지 확인한다. |
| 실행 식별·환경 | 실행03의 상품·제안·대화·회원·요청 ID와 서버 버전을 연결한다. 다른 실행의 요청이나 예약 만료가 같은 상품에 들어오지 않도록 확인한다. |

| 실행 전 확인할 사항 | 기록할 내용 |
|---|---|
| 잠금 적용 버전 | 두 기능의 첫 상품 조회가 같은 상품 행의 쓰기 잠금을 얻는지, 해당 거래의 커밋 또는 롤백까지 유지되는지 적용 코드와 실제 실행 SQL로 확인한다. |
| 도구·시간 조건 | 서버·DB·JMeter 버전, DB 연결 수, 실제 적용한 잠금·연결·응답 제한시간, 예약 만료 여유, 시각 기준을 기록한다. 제한시간이나 재시도 정책의 값을 이 명세에서 새로 정하지 않는다. |
| 입력과 출력 위치 | 실행02 계획의 상품·회원·요청 ID 연결 및 출발 배정을 검토한다. 실행03의 계획 파일과 입력 파일은 세부 작업 04의 `테스트데이터`에 새로 만드는 실행03 폴더에 둔다. 결과는 `실행결과_원본`에서 그 폴더 이름에 실행 날짜를 붙인 폴더에 저장한다. |

### 1.5 테스트 절차와 단계별 기대 결과

#### 1.5.1 테스트 전체 흐름

시간은 검증 구간 시작을 기준으로 한 **예정 출발 시점**이다. 총 18건, 한 시점의 최대 출발은 7건이다. 아래 중간값은 앞 시점의 거래가 다음 시점 전에 종료됐을 때의 기대값이다. 실제 출발·종료 시간이 겹치면 원래 일정을 변경하지 않고 요청별 확정 순서로 해석한다. 아래 표의 「수량 부족으로 거절」과 수락 거절은 「1.3 업무 규칙과 입력값」의 거절 사유에 해당하는 응답이어야 하며, 응답 값은 「4.2 요청과 실행 제어」에 있다.

| 출발 시점 | 요청 | 정상 응답과 해당 시점의 요청이 끝난 뒤 기대값 |
|---|---|---|
| 30초 | 새 구매자 2명이 각각 1개 결제 | 2건 성공. 전체 주문 수량 5개, 남은 수량 11개, 유효 예약 4개, 새로 확보 가능한 수량 7개. |
| 60초 | 다음 구매자 4명이 각각 1개 결제 | 4건 성공. 전체 주문 수량 9개, 남은 수량 7개, 유효 예약 4개, 새로 확보 가능한 수량 3개. |
| 90초 | 판매자 수락 1건·2개와 다음 구매자 결제 6건·각 1개 | **수락 성공 시** 예약 2개와 결제 1건이 성립하고 결제 5건은 수량 부족으로 거절된다. **수락 시 2개를 확보할 수 없으면** 수락은 거절되고 결제 3건이 성립하며 나머지 결제 3건은 거절된다. 두 결과 모두 일반 구매자가 새로 확보할 수 있는 수량은 0개다. |
| 120초 | 다음 구매자 3명이 각각 1개 결제 | 모두 수량 부족으로 거절된다. 주문·상품 수량·잔액에 변경이 없다. |
| 180초 | 마지막 구매자 2명이 각각 1개 결제 | 모두 수량 부족으로 거절된다. 18건의 처리 종료 후 「1.6 테스트 종료 후 기대 결과」와 대조한다. |

#### 1.5.2 관찰과 중단

- 실행 ID와 요청 ID로 JMeter의 출발·응답, 서버의 요청 수신·수량 판단·커밋 또는 롤백을 연결한다. 같은 시점의 출발만으로 두 거래의 잠금 대기가 실제 발생했다고 판단하지 않는다.
- 수락은 예약 가능 수량, 결제는 구매 가능 수량과 주문 후 남은 수량을 확인한다. 동시에 진행 중인 거래의 서로 다른 시점 값을 합산하지 않는다. 중간에 DB를 직접 조회하지 않은 수량은 요청별 확정 기록에서 재구성한 값으로 표시한다.
- 시작 상태가 다르거나 예약이 중간에 만료되면 해당 실행을 비교에서 분리한다. 주문 초과·예약 침해·차감 누락은 규칙 위반으로 기록한다. 시간 초과와 기술적 오류는 수량 부족 거절로 집계하지 않는다.
- 응답 누락·중단 시 이미 출발한 요청의 종료 및 실제 저장 결과를 확인한다. 확인하지 못한 요청은 결과 미확인으로 남기고 원본을 보존한다. 다음 실행은 독립된 데이터로 시작한다.

### 1.6 테스트 종료 후 기대 결과

마지막 요청을 포함한 서버 거래가 모두 끝난 뒤, 예약이 유효한 동안 동일 상품과 참여자를 조회한다. 아래 금액과 수량은 실행 전 계산값이다.

| 확인 대상 | 새 수락 성공 | 새 수락 수량 부족 거절 |
|---|---:|---:|
| 새 결제 성공 / 수량 부족 거절 | 7건 / 10건 | 9건 / 8건 |
| 기존 포함 주문 건수 / 주문 수량 | 8건 / 10개 | 10건 / 12개 |
| 상품의 남은 수량 / 판매 상태 | 6개 / 판매 중 | 4개 / 판매 중 |
| 유효 예약 건수 / 수량 | 2건 / 6개 | 1건 / 4개 |
| 새 가격 제안과 예약 | 수락 상태, 2개 예약 1건 | 수락 전 상태 유지, 새 예약 0건 |
| 새 결제에 따른 차감 총액 | 70,000원 | 90,000원 |
| 상세 조회의 구매 가능 수량 — 기존 예약 구매자 / 새 흥정 구매자 / 예약 없는 구매자 | 4개 / 2개 / 0개 | 4개 / 0개 / 0개 |

기존 주문 1건·3개와 기존 예약 1건·4개의 식별값, 소유자, 거래 상태가 유지돼야 한다. 새 결제 성공자마다 발송 대기 주문 1건과 그 주문에 연결된 −10,000원 차감 1건이 있고 잔액은 0원이어야 한다. 거절된 구매자는 새 주문·차감 없이 10,000원을 유지해야 한다. 기존 주문 구매자·기존 예약 구매자·새 흥정 구매자의 잔액은 각각 0원이다.

**전체 통과 조건.** 실제 출발 조건, 요청별 업무 결과, 단계별 수량, 최종 주문·예약·잔액·조회 결과가 서로 일치하고 요청 누락이나 기술적 실패가 없어야 한다. 두 분기 중 실제로 발생한 분기를 기록한다. 한 번의 실행으로 다른 분기도 검증했다고 표시하지 않는다. 의도한 겹침을 확인할 근거가 부족하면 데이터 결과와 경합 검증 여부를 따로 기록한다.

### 4.2 요청과 실행 제어

| 동작 | 입력 및 정상 종료 확인 |
|---|---|
| 판매자 수락 | 판매자 인증으로 `POST /ChatService/api/offers/{제안ID}/accept`를 한 번 보낸다. 본문은 없다. 성공은 HTTP 200과 새 예약으로 확인한다. 거절은 HTTP 409, 오류 코드 `RESERVATION_QUANTITY_EXCEEDED`(예약할 수 있는 수량보다 많이 예약할 수 없습니다)와 예약 미생성, 가격 제안의 수락 전 상태 유지로 확인한다. |
| 등록 가격 결제 | 각 구매자 인증으로 `POST /ChatService/api/orders`에 같은 상품 ID, 수량 1개, 수령인·배송지, 고유 요청 ID를 보낸다. 가격 제안 ID는 생략한다. 성공은 HTTP 201과 새 주문으로 확인한다. 거절은 HTTP 409, 오류 코드 `PRODUCT_RESERVED`(다른 회원에게 예약된 수량은 구매할 수 없습니다)와 주문·잔액 차감·상품 수량 차감이 없는 저장 상태로 확인한다. 같은 HTTP 409라도 오류 코드가 `INSUFFICIENT_STOCK`(남은 수량보다 많이 구매할 수 없습니다)이면 이 시나리오의 기대 결과가 아니므로 원인을 조사한다. |
| 종료 조회 | 상품 상세, 판매자 대화 상세, 구매자 지갑·잔액 변동 API와 해당 상품의 DB 조회를 대조한다. 최근 예약 한 건만 반환하는 대화 응답은 전체 예약 합계 검증에 단독으로 사용하지 않는다. |
| 동시 출발 제어 | 실행02의 출발시점 배정을 사용한다. 클라이언트 재전송 없이 요청별 1회 전송하며 서버의 수량 판단 뒤에 인위적으로 멈추지 않는다. 먼저 잠금을 획득한 요청을 멈춘 채 다른 요청도 같은 내부 지점에 도달하기를 기다리면 그 요청의 잠금이 풀리지 않을 수 있다. |
