## 1. 명세 내용

### 1.1 목적과 이번 검증 범위

사용자가 요청한 거래가 규칙에 맞게 처리되고 충분히 빠르게 응답하는지 기능별로 확인한다. 사용자가 어떤 상태에서 무엇을 하려는지로 거래를 구성하고, 그 거래에서 지켜야 할 규칙과 검증 질문을 정한다. 하나의 복합 거래에 모든 기능과 경합을 넣으려 하지는 않는다.

우선 가격 제안 수락, 등록 가격 결제, 상품 상세 조회를 대상으로 한다. 기존 예약을 주문으로 전환하는 시나리오에는 그 전환에 필요한 합의 가격 결제를 포함한다. 합의 가격 결제 전체의 검증으로 범위를 넓히는 것은 아니다.

기존 예약·주문이 없는 세 가지 경합의 실행 자료를 활용하고, 기존 거래 보호와 예약의 주문 전환, 조회 후 구매 기회 상실, 부하 증가에 따른 정확성과 응답 시간을 확인한다. 기존 실행에서 확인하지 못한 항목이 있다는 이유만으로 기본 동작 전체를 다시 테스트하는 단계를 먼저 두지 않는다. 준비 상태와 결과 해석에 필요한 기본 동작 확인은 각 시나리오에 포함한다.

작업명세 01의 「5. 취소 후속 시나리오와 기능 수정」과 「6. 취소가 여러 지점에서 복합적으로 발생하는 상황」은 별도 범위다. 결제 준비 중 수량 점유 기능의 구현과 비교 실험도 이번에 추가 채택하지 않는다.

### 1.2 결과를 판단하는 기준

구현 정확성과 구매 경험의 적절성을 구분한다. 구현 정확성은 요청별 결과와 전체 거래 상태를 함께 확인한다. 각 요청의 응답과 저장 결과가 일치해도, 전체 예약과 주문이 판매 수량을 넘으면 규칙 위반이다.

| 구분 | 확인할 내용 | 후속 판단 |
|---|---|---|
| 정한 규칙을 위반한 결과 | 수량 초과, 기존 예약 침해, 주문·잔액·남은 수량 불일치 등 | 처리 과정과 원인을 조사하고 기술적 대안을 검토한다 |
| 규칙은 지켰지만 불편한 구매 경험 | 조회할 때 구매 가능했으나 다른 거래 뒤 결제에서 거절되는 경험 등 | 정책 보완의 필요성과 비용을 검토한다 |
| 적용할 정책이 없는 결과 | 허용할 동작을 정하지 않아 정확성을 판단하기 어려운 결과 | 정책과 결과 확인 기준부터 정한다 |
| 처리 결과 미확인 | 응답을 받지 못했거나 저장 상태를 확인하지 못한 요청 | 기존 저장 결과를 확인하기 전까지 성공·실패 판단을 보류한다 |

응답을 받지 못했다는 사실 자체로 저장 실패나 구현 결함을 확정하지 않는다. 수량 부족 거절은 해당 조건에서 기대한 결과라면 정상 동작이다. 성공·수량 부족·기타 오류·결과 미확인을 나누고, 전체 성공률이나 평균 응답 시간 하나로 판단하지 않는다.

### 1.3 대상 기능과 지켜야 할 규칙

| 기능 | 요청별 결과 확인 | 전체 거래 상태 확인 |
|---|---|---|
| 가격 제안 수락 | 성공한 수락은 제안 수량 전부를 예약하고 수락 상태와 일치한다. 거절된 수락에는 새 예약이나 수락 상태가 남지 않는다 | 확보 가능한 수량 안에서 예약하고, 기존 유효 예약을 침해하지 않는다. 예약 자체는 상품의 남은 수량을 줄이지 않는다 |
| 등록 가격 결제 | 성공한 주문의 수량·금액과 잔액 차감이 일치한다. 거절된 결제에는 주문이나 잔액·수량 차감이 남지 않는다 | 기존 예약을 침해하지 않고, 남은 수량은 이미 성립한 주문을 반영한다 |
| 상품 상세 조회 | 조회한 구매자와 예약의 유효 여부에 맞는 구매 가능 수량을 보여 준다 | 상태가 안정된 시점의 주문·예약·남은 수량과 조회 결과를 대조한다 |
| 예약의 주문 전환 | 기존 예약자의 합의 가격 주문과 잔액 차감이 일치하고, 전환한 예약은 유효 예약 합계에서 빠진다 | 전환 중인 수량을 다른 거래가 중복 확보하지 않고, 예약과 주문으로 이중 계산해 가능한 거래를 거절하지 않는다 |

상품 조회가 정확하다는 것은 조회한 수량이 결제 때까지 보장된다는 뜻이 아니다. 조회 뒤 다른 거래가 수량을 확보할 수 있다. 거래 처리와 조회가 겹칠 때 허용할 조회 결과와 비교 시점은 상세 설계에서 정한다.

상품 목록 조회와 상품 상세 조회의 응답 시간은 합치지 않는다. 이번 초기 목표의 대상은 상품 상세 조회다. 다른 기능을 준비 단계에서 호출하더라도 해당 기능의 목표를 정한 것으로 보지 않는다.

### 1.4 시나리오별 검증 질문과 구성 초안

아래 수량은 논의에서 사용한 구성 초안이며 실행 결과가 아니다. 상세 조건을 정할 때 요청별 준비와 확인 방법을 함께 확정한다. 모든 구매자는 필요한 잔액과 정상 주문 정보를 갖추고, 수락 요청자는 해당 판매자다. 예약 보호를 확인하는 테스트에서는 처리와 결과 확인이 끝날 때까지 기존 예약이 유효하도록 준비한다.

#### 1.4.1 기존 예약·주문이 없는 세 가지 경합

예약–예약, 등록 가격 구매–등록 가격 구매, 예약–등록 가격 구매는 기존 세부 작업의 실행 자료를 활용한다. 새 계획에 맞추려고 기존 실행을 처음부터 반복하지 않는다. 기존 자료로 확인되는 내용과 추가 확인이 필요한 내용을 구분하고, 수정 후에는 필요한 동일 조건으로 재검증한다.

수량이 부족해 일부 요청만 성공해야 하는 조건과, 모든 요청을 수용할 수 있는 조건을 구분한다. 수량이 충분할 때도 정상 거래가 불필요하게 거절되지 않는지 확인한다. 준비 조건과 동시 실행 방법은 각 테스트케이스에 명시한다.

#### 1.4.2 기존 거래가 있는 상품의 새 예약과 구매

판매 수량 10개인 상품에 기존 주문 3개와 기존 흥정 구매자의 유효 예약 4개가 있는 상태를 만든다. 상품의 남은 수량은 7개이고, 다른 구매자가 새로 확보할 수 있는 수량은 3개다. 이 상태에서 서로 다른 새 구매자 두 명이 각각 2개를 확보하려고 한다.

| 테스트케이스 | 함께 진행할 요청 | 기대 결과 |
|---|---|---|
| 기존 거래가 있는 상품의 예약–예약 | 서로 다른 흥정 구매자의 가격 제안 2개씩을 판매자가 수락 | 하나만 성공하고 다른 하나는 수량 부족으로 거절 |
| 기존 거래가 있는 상품의 등록 가격 구매–등록 가격 구매 | 서로 다른 등록 가격 구매자가 2개씩 결제 | 하나만 성공하고 다른 하나는 수량 부족으로 거절 |
| 기존 거래가 있는 상품의 예약–등록 가격 구매 | 새 가격 제안 2개 수락과 다른 구매자의 등록 가격 결제 2개 | 둘 중 하나만 성공하고 다른 하나는 수량 부족으로 거절 |

누가 성공할지는 고정하지 않는다. 성공한 요청은 2개 전부를 확보하고, 기존 주문 3개와 기존 예약 4개는 유지되어야 한다. 새 예약이 성공했다면 남은 수량은 7개, 새 결제가 성공했다면 5개다. 거래가 끝난 뒤 예약이 없는 다른 구매자의 구매 가능 수량은 두 결과 모두 1개다. 거절된 요청에는 허용하지 않은 상태 변경이 남지 않아야 한다.

기존 예약과 기존 주문을 함께 둔 결과에서 원인을 구분하기 어렵다면, 기존 예약만 있는 조건과 기존 주문만 있는 조건을 나눠 추가 확인한다. 모든 조합을 처음부터 늘리는 대신 로그와 결과로 구분할 수 있는지 먼저 판단한다.

#### 1.4.3 예약의 주문 전환과 새 거래의 경합

출발 상태는 「1.4.2 기존 거래가 있는 상품의 새 예약과 구매」와 같다. 기존 흥정 구매자가 예약한 4개를 합의 가격으로 결제하는 동안, 다른 구매자의 새 예약 또는 등록 가격 구매를 진행한다. 예약이 주문으로 바뀌어도 다른 구매자가 새로 확보할 수 있는 수량은 3개로 유지되어야 한다.

| 테스트케이스 | 겹치게 할 요청 | 기대 결과 |
|---|---|---|
| 예약의 주문 전환–새 예약, 확보 가능한 수량 이내 | 기존 예약 4개 결제와 새 가격 제안 3개 수락 | 두 요청 모두 성공 |
| 예약의 주문 전환–등록 가격 구매, 확보 가능한 수량 이내 | 기존 예약 4개 결제와 다른 구매자의 등록 가격 결제 3개 | 두 요청 모두 성공 |
| 예약의 주문 전환–새 예약, 확보 가능한 수량 초과 | 기존 예약 4개 결제와 새 가격 제안 4개 수락 | 기존 예약자의 결제는 성공하고 새 수락은 수량 부족으로 거절 |
| 예약의 주문 전환–등록 가격 구매, 확보 가능한 수량 초과 | 기존 예약 4개 결제와 다른 구매자의 등록 가격 결제 4개 | 기존 예약자의 결제는 성공하고 새 결제는 수량 부족으로 거절 |

새 수락에 사용할 가격 제안은 기존 예약을 만들기 전에 등록한다. 그래야 4개 제안도 등록 단계에서 수량 부족으로 거절되지 않고 수락 단계까지 도달할 수 있다.

3개 요청은 예약과 주문을 이중 계산해 가능한 거래를 거절하는지 확인한다. 4개 요청은 예약이 주문으로 전환되는 도중 기존 예약자의 수량을 다른 거래가 확보하는지 확인한다.

| 새 거래 결과 | 종료 후 전체 주문 수량 | 종료 후 유효 예약 수량 | 상품의 남은 수량 |
|---|---:|---:|---:|
| 새 예약 3개 성공 | 7개 | 3개 | 3개 |
| 새 등록 가격 구매 3개 성공 | 10개 | 0개 | 0개 |
| 새 거래 4개 거절 | 7개 | 0개 | 3개 |

기존 주문 3개는 유지되고, 결제한 기존 예약 4개는 유효 예약 합계에서 빠져야 한다. 주문·잔액·응답도 대조한다. 판매 종료된 상품의 확인 경로는 상품 상세 조회가 아닌 종료 후 저장 상태 확인 방법으로 정한다.

요청을 동시에 보냈다는 사실만으로 전환 도중의 경합을 확인했다고 판단하지 않는다. 수량 조회와 예약·주문 변경의 순서를 로그 등으로 확인한다. 필요한 겹침이 없었다면 해당 실행은 그 경합의 검증 근거로 사용하지 않고, 실행 시점 조절 방법을 보완한다.

#### 1.4.4 조회 후 다른 거래가 먼저 성립하는 구매 경험

상품 조회나 수량 선택만으로 수량을 확보하지 않는 현재 정책에서, 구매 가능 수량을 확인한 사람이 결제 단계에서 거절되는 과정을 확인한다. 두 구매자에게는 필요한 잔액과 정상 주문 정보를 준비한다.

| 순서 | 결제 준비 구매자 | 먼저 결제하는 구매자 |
|---|---|---|
| 1 | 남은 수량 1개인 상품에서 구매 가능 수량 1개를 확인한다 | |
| 2 | 정보 입력 시간을 가정해 대기한다 | |
| 3 | | 상품 1개를 결제하고 성공 응답을 받는다 |
| 4 | 상품 1개의 결제를 요청한다 | |
| 5 | 수량 부족 또는 판매 종료에 따른 거절을 받는다 | |

주문은 하나만 성립하고 거절된 구매자의 잔액은 줄지 않아야 한다. 이 거래는 순차 처리만으로도 경험을 확인할 수 있으므로, 두 결제의 동시 처리를 강제하지 않는다.

처음에는 순서를 통제해 응답과 저장 결과를 확인한다. 발생 비율의 측정이 필요해지면 조회 시점과 정보 입력 시간을 달리해 반복한다. 입력 시간과 요청 빈도가 가정 값이면 결과도 그 조건에서의 발생 비율로 설명하며, 실제 서비스의 구매 실패율이나 이탈률로 표현하지 않는다.

이 결과만으로 수량 점유 도입을 결정하지 않는다. 점유는 결제 준비 구매자를 보호하지만 결제하지 않는 사람 때문에 다른 구매가 제한될 수 있다. 도입 여부와 기간, 결제 포기·만료 처리는 후속 정책 논의로 남긴다. 다른 서비스의 방식과 이용자 근거는 그 판단에 필요해질 때 조사하며, 서비스의 선택·통계와 이용자가 원한다는 직접 근거를 구분한다.

### 1.5 응답 시간 목표와 부하 구성

#### 1.5.1 확정한 초기 목표와 측정 구간

응답 시간은 요청을 보내기 시작한 때부터 응답 본문을 모두 받은 때까지로 정한다. 서버 처리와 통신 시간을 포함하며, 화면 표시까지의 시간으로 설명하지 않는다.

첫 평가 규모는 검증 대상 요청의 동시 실행 수 18건이다. 기존 실행과 연결하기 위한 실험 조건이며 실제 이용량의 추정이 아니다. 아래 목표는 실제 이용 기록이나 사용자 조사에서 얻은 값이 아닌, 논의에서 정한 가정 값이다.

| 기능 | 초기 응답 시간 목표 | 별도로 집계할 요청 결과 |
|---|---|---|
| 상품 상세 조회 | 요청의 95%가 500ms 이내 | 정상 조회 |
| 가격 제안 수락 | 요청의 95%가 1초 이내 | 성공과 수량 부족 거절 각각 |
| 등록 가격 결제 | 요청의 95%가 1초 이내 | 성공과 수량 부족 거절 각각 |

상품 상세 조회는 별도로 측정하고, 혼합 부하에서는 기능별 요청 구성을 명시한다. 수락 9건과 결제 9건을 보낸 실행이라면 두 기능을 하나의 분포로 합치지 않는다. 합의 가격 결제의 별도 응답 시간 목표는 아직 정하지 않았다.

한 번의 18건 실행으로 목표 달성을 판정하지 않는다. 동일 조건으로 반복하고, 기능·결과별 측정 건수와 실행별 변동을 표시한다. 가장 오래 걸린 요청, 기타 오류, 응답을 받지 못한 요청도 함께 보고한다. 측정 건수가 부족한 집계는 백분위 값만으로 결론 내리지 않는다.

목표를 충족해도 부하를 늘려 시간이 증가하는 조건을 살펴볼 수 있다. 목표를 넘으면 먼저 처리와 대기 원인을 확인하며, 목표 변경으로 초과 결과를 지우지 않는다.

#### 1.5.2 요청이 집중되는 상품의 범위

| 부하 조건 | 사용자 상황 | 확인할 질문 |
|---|---|---|
| 같은 상품 집중 | 여러 구매자가 같은 상품을 구매하고 판매자도 가격 제안을 수락한다 | 같은 수량을 확보하려는 요청이 늘어날 때 정확성과 시간이 어떻게 달라지는가 |
| 여러 상품 분산 | 여러 판매자의 상품에서 각각 수락과 결제가 진행된다 | 같은 상품을 두고 경쟁하지 않아도 전체 요청 증가로 느려지는가 |
| 인기 상품과 다른 상품의 요청을 함께 실행 | 인기 상품에 요청이 몰리는 동안 다른 상품도 조회하거나 구매한다 | 인기 상품의 부하가 다른 상품 이용자의 응답 시간에 영향을 주는가 |

집중과 분산을 비교할 때는 전체 요청 수, 기능별 비율, 수량 조건, 상품별 대화 수 등 비교 목적 이외의 조건을 맞춘다. 예를 들어 상품 하나에 결제 18건을 보내는 조건과 상품 18개에 결제 1건씩 보내는 조건을 비교할 수 있다. 정확한 상품 수와 비율은 상세 설계에서 정한다.

집중 조건에서만 느려지면 같은 상품 처리의 대기와 경합을 우선 조사한다. 분산 조건에서도 느려지면 DB 연결이나 서버 처리 능력, 요청마다 수행하는 조회 비용 등 공통 원인을 조사한다. 이 비교만으로 원인을 확정하지 않고 내부 측정과 대조한다.

#### 1.5.3 수량 조건과 단계적 확대

| 수량 조건 | 측정 목적 | 준비 원칙 |
|---|---|---|
| 요청을 수용할 수 있는 충분한 수량 | 성공 거래가 이어질 때 처리 비용을 확인한다 | 실행별 새 상품과 출발 상태를 구성하거나, 정한 측정 동안 충분한 상품과 수량을 미리 준비한다 |
| 일부 요청만 성공할 수 있는 부족한 수량 | 수량 초과 방지와 거절 응답 시간을 확인한다 | 성공·수량 부족·기타 오류·미확인을 분리한다 |

수량 소진 뒤 대부분 거절된 실행을 성공 거래의 처리 성능으로 설명하지 않는다. 수정 전후에도 결과 구성이 달라질 수 있으므로 전체 평균만 비교하지 않는다.

동시 요청 수를 1 → 6 → 12 → 18 → 24건으로 늘리는 구성을 초안으로 둔다. 혼합 요청의 비율, 낮은 단계에서 보낼 기능, 각 단계의 반복 횟수와 중단 조건은 미정이다. 로컬 설정의 DB 연결 최대 수가 12개인 점은 그 전후를 살펴볼 이유이며, 실제 서버 설정과 연결 사용 상태는 실행 전에 확인한다. 12개라는 숫자만으로 병목이나 대기 발생을 단정하지 않는다.

같은 장비와 설정의 결과를 비교하되 절대 수치를 실제 서비스의 처리 능력으로 일반화하지 않는다. 부하 발생 장비나 네트워크의 한계도 구분할 수 있도록 관측 방법을 상세 설계에서 정한다.

#### 1.5.4 데이터 증가와 내부 시간의 관측

동시 요청 수가 같아도 요청이 처리하는 데이터 양에 따라 시간이 달라질 수 있다. 상품에 연결된 대화 수를 18 → 50 → 100건으로 늘리는 예시를 논의했으나, 구체적인 데이터 증가 실험은 후순위로 둔다. 대화 수는 한 대화 안의 메시지 수와 다르다. 예약·주문 등 다른 데이터와 사용자 경험을 저해하는 여러 원인으로 관점을 넓히되, 지금 상세 테스트를 확정하지 않는다.

DB 연결 대기, SQL 실행, 잠금 대기 등 응답 시간이 늘어난 구간을 구분할 수 있도록 측정 항목을 정한다. 로그 시각의 차이로 추정한 DB 연결 대기와 직접 측정한 대기 시간을 구분한다. 현재 자료로 구분할 수 없으면 필요한 관측을 추가하는 계획을 먼저 정한다.

### 1.6 테스트 파일과 반복 실행 원칙

하나의 통합 실행 파일 안에서 검증 목적별 실행 부분을 나누고, 필요한 시나리오를 선택해 실행하는 방향으로 구성한다. 기존 실행 파일의 실제 재사용 범위와 선택 방법은 파일 구조를 확인한 뒤 정한다.

| 실행 부분 | 역할 |
|---|---|
| 준비 | 회원·상품·가격 제안·잔액과 필요한 기존 예약·주문을 만든다 |
| 요청 전 확인 | 남은 수량·유효 예약·기존 주문·구매자 잔액이 출발 조건과 맞는지 확인한다 |
| 검증 대상 요청 | 해당 테스트케이스의 수락·결제·조회와 필요한 동시 실행을 수행한다 |
| 종료 후 확인 | 응답과 예약·주문·잔액·남은 수량을 대조한다 |
| 결과 집계 | 기능별·응답 결과별 건수와 시간, 위반과 미확인 사항을 정리한다 |

준비와 종료 후 확인 요청의 시간은 검증 대상 요청의 응답 시간에 합치지 않는다. 상품 조회 자체가 검증 대상이면 그 요청은 별도로 표시한다. 파일에서 선택하는 단위는 기술 이름이 아니라 시나리오로 둔다.

요청별 결과를 추적하는 테스트는 반복마다 새 상품과 필요한 상태를 준비한다. 이전 실행의 주문·예약·수량 변화를 그대로 둔 채 같은 조건의 반복이라고 설명하지 않는다. 지속 부하는 충분한 상품과 수량을 준비하고 정한 시간 동안 요청을 보내는 별도 조건으로 구성한다. 요청 묶음의 반복과 지속 부하 결과는 구분한다.

준비 운동과 본 측정을 나누고, 비교 조건에는 동일한 반복 횟수나 측정 시간을 적용한다. 빠른 실행만 선택하지 않고 실행별 결과와 변동을 남긴다. 반복 횟수·측정 시간·요청 간격·충분한 표본의 기준은 실행 전에 정한다.

### 1.7 완료 기준과 기술적 의사결정으로 이어지는 순서

테스트를 계획대로 수행한 것과 기능이 규칙을 지킨 것은 구분한다. 현재 구현을 조사하는 단계에서는 규칙 위반을 명확히 확인한 테스트도 그 문제를 확인하려는 목적을 달성할 수 있다.

| 테스트 결과 | 판단 조건 | 다음 행동 |
|---|---|---|
| 규칙을 지킴 | 필요한 상황이 발생했고 응답과 저장 상태가 기준을 만족한다 | 확인한 조건과 범위를 기록한다 |
| 규칙 위반 확인 | 수량 초과, 예약 침해, 주문·잔액 불일치 등을 확인한다 | 관련 요청과 처리 과정을 분석한다 |
| 검증 미완료 | 준비 상태가 틀리거나 필요한 경합이 없거나 저장 결과를 확인하지 못했다 | 부족한 조건을 보완해 다시 실행한다 |

순차 처리만 확인한 실행을 동시 처리의 검증으로 표시하지 않는다. 한 번의 명확한 위반도 결함 존재의 근거가 될 수 있지만, 발생 조건과 빈도를 설명하려면 반복이 필요하다. 여러 번 위반이 없었다는 결과도 확인한 조건과 횟수의 범위에서 설명한다.

성능은 정확성 준수와 응답 시간 목표 충족을 함께 확인한다. 정확성은 지켰지만 목표를 넘었다면 처리와 대기를 조사한다. 응답이 빨라도 규칙을 위반했다면 정상 동작으로 평가하지 않는다. 표본이 부족하거나 비교 조건이 다르면 측정 불충분으로 남긴다.

이번 단계는 정한 시나리오별로 정확성과 응답 시간을 확인하고, 위반·목표 초과·미확인을 구분해 정리하는 데까지다. 확인된 문제마다 원인 근거와 추가 조사할 내용을 정리한 뒤 기술적 대안을 검토한다. 실행 결과와 그 해석은 기존 기록 양식에 따라 구분한다.

진행 순서는 현재 구현의 테스트 구성과 실행, 문제와 원인 확인, 기술적 대안의 적용·비교, 선택 및 수정 후 재검증이다. 정확성과 응답 시간은 수정 전부터 함께 측정하고, 정확성을 통과한 방법끼리 성능을 비교한다. 정확성을 위반한 기존 구현도 변화의 크기를 설명할 비교 자료로 보존한다.

상품 행 잠금과 버전 방식 등을 비교 대상으로 미리 확정하지 않는다. 실제 문제에 맞는 대안을 그때 검토하며, 정확성·응답 시간·구현 및 관리 부담을 비교한다. 서버 하나와 DB 하나의 구성에서는 DB 안에서 해결하는 방법을 먼저 검토하고, 분산 잠금이나 메시지 대기열은 측정으로 필요가 확인될 때 검토한다.

### 1.8 실행 전에 정할 상세 조건과 보류 사항

| 항목 | 남은 내용 |
|---|---|
| 시나리오 상세 | 초안 수량의 확정, 준비 순서, 요청별 입력, 예약 유효 시간, 종료 후 확인 경로 |
| 경합 확인 | 겹치게 할 처리 구간, 실행 시점 조절 방법, 로그의 시점과 순서를 해석하는 방법 |
| 조회 정확성 | 거래와 조회가 겹칠 때 허용할 결과와 비교 시점 |
| 부하 상세 | 기능 비율, 상품 수, 요청 간격, 지속 시간, 단계 확대·중단 조건 |
| 반복 측정 | 준비 운동과 본 측정 횟수, 기능·응답 결과별 표본, 백분위 계산 방법 |
| 내부 관측 | 연결 대기·잠금 대기·SQL 시간의 구분, 서버와 부하 발생 장비의 관측, 계측 비용 |
