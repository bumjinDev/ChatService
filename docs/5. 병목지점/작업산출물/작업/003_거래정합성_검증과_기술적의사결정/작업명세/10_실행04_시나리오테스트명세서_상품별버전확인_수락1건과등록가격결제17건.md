## 1. 명세 내용

### 1.1 목적과 범위

가격 제안 수락과 등록 가격 결제에 상품별 버전 확인을 적용한 서버에 실행03과 같은 요청 18건을 보낸다. 판매 수량 16개인 상품에 기존 주문 3개와 기존 예약 4개가 있을 때, 판매자의 새 가격 제안 수락 1건(2개)과 새 등록 가격 구매자 17명의 등록 가격 결제 17건(각 1개)이 새로 확보할 수 있는 9개 안에서만 성립하는지 확인한다. 성공한 결제의 수량만큼 상품의 남은 수량과 구매자의 잔액이 줄어드는지도 함께 확인한다.

상품별 버전 확인은 상품 행에 버전 번호를 두는 방법이다. 작업명세 08에서 쓰는 이름이고, 낙관적 락이라고도 부른다. 서버는 수락이나 결제를 커밋하기 직전에, 그 요청이 상품을 조회한 뒤로 상품의 버전이 바뀌었는지 확인한다. 버전이 바뀌었으면 그 요청이 한 저장은 모두 롤백되고, 서버가 그 요청을 처음부터 다시 처리한다. 이 문서에서는 서버가 한 요청을 한 번 처리하는 것을 시도라고 부른다.

이 테스트의 결과는 작업명세 08에서 비교하기로 한 세 방법(DB 상품 행 잠금, 상품별 버전 확인, 애플리케이션의 상품별 잠금) 가운데 상품별 버전 확인의 결과로 쓴다.

### 1.2 테스트 배경

판매 수량 16개인 상품에 기존 주문 구매자의 주문 3개와 기존 예약 구매자의 예약 4개가 있는 상태에서 시작한다. 판매자는 새 흥정 구매자의 가격 제안 2개를 수락하고, 새 등록 가격 구매자 17명은 같은 상품을 등록 가격으로 1개씩 결제한다. 요청 18건은 모든 요청이 준비된 순간부터 30초, 60초, 90초, 120초, 180초의 다섯 출발 시점에 나누어 출발한다.

이 문서에서 새 수락은 판매자가 새 흥정 구매자의 가격 제안을 수락하는 요청이고, 새 결제는 새 등록 가격 구매자가 등록 가격으로 결제하는 요청이다. 새 수락 1건과 새 결제 17건을 합쳐 검증 요청이라고 부른다. 검증 요청은 JMeter 계획의 그룹 이름에서 온 말이다.

같은 출발 시점에 출발한 수락과 결제는 같은 남은 수량과 같은 예약을 조회해, 각자 수량이 충분하다고 판단할 수 있다. 먼저 확정된 주문이나 예약을 뒤에 확정되는 요청이 반영하지 못하면, 성공으로 응답한 주문과 예약의 합계가 판매 수량 16개를 넘고 판매자는 그 가운데 일부를 이행할 수 없다.

앞선 두 실행에서 같은 요청 18건을 보낸 결과는 다음과 같다.

- **실행02:** 서버가 상품을 잠금 없이 조회했다. 18건이 모두 성공했다. 주문 20개와 유효 예약 6개의 합계 26개가 판매 수량보다 10개 많았고, 상품에는 남은 수량이 8개로 저장됐다.
- **실행03:** 서버가 수락과 결제에서 상품을 처음 조회할 때 상품 행의 비관적 쓰기 잠금을 얻었다. 새 수락은 수량 부족으로 거절됐고, 새 결제는 9건이 성공하고 8건이 수량 부족으로 거절됐다. 주문 12개와 유효 예약 4개의 합계가 판매 수량 16개와 같았고, 상품에 저장된 남은 수량은 4개였다.

실행04의 서버는 수락과 결제가 상품을 조회할 때 잠금을 얻지 않는다. 같은 출발 시점의 요청은 기다리지 않고 같은 남은 수량과 같은 버전을 조회할 수 있다. 실행04에서 확인하는 것은 다음 세 가지다.

- 먼저 커밋한 요청이 상품의 버전을 올렸을 때, 같은 버전을 조회한 다른 요청이 커밋하지 못하고 롤백되는가.
- 롤백된 요청이 저장하려던 주문, 예약, 잔액 차감이 남지 않는가.
- 다시 처리된 요청이 앞 요청의 주문과 예약이 반영된 수량으로 다시 판단하는가.

시작부터 끝까지의 흐름은 다음과 같다.

1. 판매자와 구매자 20명이 가입하고 로그인한다.
2. 판매자가 판매 수량 16개, 등록 가격 개당 10,000원인 상품을 등록한다. 구매자 20명이 각각 이 상품으로 판매자와 대화를 시작한다.
3. 기존 주문 구매자가 30,000원을 충전하고 등록 가격으로 3개를 결제한다.
4. 새 등록 가격 구매자 17명이 각각 10,000원을 충전한다.
5. 기존 예약 구매자가 개당 9,000원에 4개를 제안하고, 판매자가 이 가격 제안을 수락한다. 기존 예약 구매자에게 4개가 예약된다.
6. 새 흥정 구매자가 개당 9,000원에 2개를 제안한다. 판매자는 아직 응답하지 않았다.
7. 검증 요청을 보내기 전의 상태를 조회해 출발 상태와 대조한다.
8. 모든 요청이 준비된 순간부터 30초에 새 등록 가격 구매자 2명이 결제하고, 60초에 4명이 결제한다.
9. 90초에 판매자가 새 흥정 구매자의 가격 제안을 수락하고, 같은 출발 시점에 새 등록 가격 구매자 6명이 결제한다.
10. 120초에 새 등록 가격 구매자 3명이 결제하고, 180초에 2명이 결제한다.
11. 검증 요청 18건이 모두 끝난 뒤 상품, 대화, 가격 제안, 예약, 주문, 잔액을 다시 조회해 기대 결과와 대조한다.

| 참여자 | 목적과 행동 | 테스트에서 보내는 요청 |
|---|---|---|
| 판매자 | 상품 16개를 등록해 판다. 기존 예약 구매자의 가격 제안을 수락했고, 새 흥정 구매자의 가격 제안도 수락하려 한다. | 준비에서 상품 등록 1건과 기존 예약 구매자의 가격 제안 수락 1건을 보낸다. 90초 출발 시점에 새 흥정 구매자의 가격 제안 수락 1건을 보낸다. |
| 기존 주문 구매자 | 등록 가격으로 3개를 이미 샀다. | 준비에서 대화 시작, 30,000원 충전, 등록 가격 결제 3개를 보낸다. 검증 요청은 보내지 않는다. |
| 기존 예약 구매자 | 개당 9,000원에 4개를 제안해 수락받았고, 4개가 예약되어 있다. | 준비에서 대화 시작과 가격 제안 4개를 보낸다. 검증 요청은 보내지 않는다. |
| 새 흥정 구매자 | 개당 9,000원에 2개를 사려고 제안하고, 판매자의 응답을 기다린다. | 준비에서 대화 시작과 가격 제안 2개를 보낸다. 검증 요청은 보내지 않는다. |
| 새 등록 가격 구매자 01부터 17까지 | 가격 제안 없이 등록 가격으로 1개를 사려 한다. | 준비에서 대화 시작과 10,000원 충전을 보낸다. 배정된 출발 시점에 등록 가격 결제 1개를 한 번 보낸다. |

### 1.4 테스트 시작 전 준비

- 시작 상태를 확인하는 시점: 준비 그룹을 모두 실행한 뒤, 검증 요청을 보내기 전에 「요청 전 확인: API 조회와 읽기 전용 DB 대조(9단계)」 그룹으로 확인한다.
- 실행 사이의 상태 관리: 새 회원 21명과 새 상품으로 시작한다. 실행03의 회원, 상품, 주문, 예약을 이어받지 않는다.
- 다른 실행이나 자동 처리의 영향: 대상 상품은 이 실행에서 새로 등록한 상품이고, 이 실행의 회원만 이 상품에 요청을 보낸다. 서버의 테스트 지원 기능이 켜져 있으면, 처리 기준 시각이 고정되어 있지 않은지와 일시 중지로 멈춘 요청이 없는지를 요청 전 확인과 종료 후 확인에서 조회한다.

#### 1.5.2 관찰과 중단

검증 요청 18건은 앞 출발 시점의 응답과 관계없이 배정된 출발 시점에 모두 보낸다. 기대 결과와 다른 응답이 나와도 종료 후 확인과 결과 집계까지 실행한다.

- 관찰 시점·대상:
  - 검증 요청을 보내기 전에는 요청 전 확인 그룹의 조회 결과를 관찰한다.
  - 검증 요청마다 출발한 시각, 전송을 시작한 시각, 응답을 모두 받은 시각, 걸린 시간, 응답을 관찰한다.
  - 검증 요청 18건이 모두 응답을 받았거나 응답을 기다리는 제한 시간이 지난 뒤에는 종료 후 확인 그룹의 조회 결과를 관찰한다.
  - 서버 로그에서는 요청마다 수량 판단에 쓴 남은 수량과 유효 예약, 커밋과 롤백을 관찰한다. 같은 출발 시점의 요청이 서버에서 겹쳐 처리되었는지는 서버 로그로 확인한다.
  - 서버 로그에서 버전이 달라져 롤백된 시도와 다시 처리한 횟수를 요청마다 관찰한다. 작업명세 08은 이 횟수를 응답 시간을 설명하는 근거로 둔다.
- 단계마다 함께 확인할 관계:
  - 주문 수량의 합계와 유효 예약 수량의 합계를 더한 수량이 판매 수량 16개 이하다.
  - 상품의 남은 수량이 판매 수량 16개에서 주문 수량의 합계를 뺀 수량과 같다.
  - 성공 응답을 받은 결제마다 주문 1건과 잔액 차감 10,000원이 있다.
  - 거절된 요청과 롤백된 시도가 저장하려던 주문, 예약, 잔액 차감이 남아 있지 않다.
  - 새 등록 가격 구매자 한 명에게 주문이 2건 이상 생기지 않는다.
- 필요한 증거: 검증 요청의 출발 기록과 응답, 요청 전 확인과 종료 후 확인의 API 응답과 DB 조회 결과, 결과 집계 그룹의 대조 결과, 서버 로그가 필요하다. 파일 이름은 「4.2 요청과 실행 제어」에 있다.

롤백된 시도도 주문 번호와 예약 번호를 쓴다. 그래서 저장된 주문 번호와 예약 번호가 이어지지 않을 수 있다(낙관적 락 논의 내용 총정리).

- **기존 예약 구매자의 가격 제안과 예약:** 요청 전에 저장한 행과 모든 열이 같다. 예약은 종료 후 DB 조회 시각에 유효하다.

- **새 흥정 구매자의 주문:** 주문이 없다.
- **대상 상품의 주문:** 기존 주문 구매자와 새 등록 가격 구매자가 아닌 회원의 주문이 없다. 새 등록 가격 구매자 한 명에게 주문이 2건 이상 있지 않다.

- **대상 상품의 가격 제안:** 가격 제안은 2건이다.

| 첫 상품 조회의 위치 | 수락은 `OfferService.respond`에서 `getProductWithOptimisticLock`으로 상품을 처음 조회한다. 결제는 `OrderService.placeOrder`에서 잠금 없이 조회하는 `getProduct`로 상품을 처음 조회한다. | 서버 코드에 반영했다. |
| 다시 처리 | Spring Retry의 `@Retryable`을 수락 메서드와 결제 메서드에 붙였고, 시작 클래스에 `@EnableRetry`를 붙였다. 다시 처리할 예외는 `OptimisticLockingFailureException`이다. `maxAttempts = 7`, `backoff = @Backoff(delay = 1)`이다. | 서버 코드에 반영했다. |
| 횟수를 다 쓴 요청의 응답 | 처리하지 않는 예외로 나가 HTTP 500으로 응답한다. JMeter 계획은 이 응답을 「기타오류」로 나눈다. | 낙관적 락 논의 내용 총정리의 코드 위치(`ApiExceptionHandler`), 실행04의 JMeter 계획 |
| 배포 서버의 DB | 서버를 배포하기 전에 `ALTER TABLE PRODUCT ADD (VERSION NUMBER(19) DEFAULT 0 NOT NULL);`을 실행한다. 이미 있는 상품 행의 버전은 0이 된다. | SQL 파일은 테스트데이터의 실행04 폴더에 있는 `실행04_상품테이블_버전열추가.sql`이다. 실행했는지는 확인하지 않았다. |
| 실행 도구 | JMeter 5.6.3으로 계획을 실행한다. 실행할 때의 JMeter 버전, Java 버전, 실행 PC의 운영체제는 계획이 `실행조건.csv`에 기록한다. | 실행04의 JMeter 계획 |
| 서버와 DB의 주소, DB 계정 | 실행 설정 `실행04_실행설정.csv`에 있고 이 문서에는 적지 않는다. DB 비밀번호는 「실행 시작」 그룹의 입력 창에서 받아 JMeter 메모리에만 둔다. | 실행04의 JMeter 계획 |
| DB 조회 | 읽기 전용 트랜잭션에서 SELECT만 실행한다. | 실행04의 JMeter 계획 |
| 제한 시간 | 서버 연결 대기는 5초, 응답 대기는 30초, 모든 검증 요청이 준비될 때까지의 대기는 10초다. | 실행 설정의 `connectTimeoutMs`, `responseTimeoutMs`, `gatherTimeoutMs` |
| 기한 여유 | 검증 요청이 출발할 때 기존 예약의 만료 시각과 기존 주문의 발송 기한까지 510초 이상 남아 있어야 한다. 510초는 기한 여유 5분, 가장 늦은 출발 시점 180초, 응답 대기 30초를 더한 시간이다. | 실행 설정의 `deadlineMarginMin`, 실행04의 JMeter 계획 |
| 로그인 유지 | 로그인한 때부터 25분 안에 가장 늦은 출발 시점과 응답 대기 30초가 끝나야 한다. | 실행 설정의 `loginMaxAgeMin`, 실행04의 JMeter 계획 |
| 서버의 테스트 지원 기능 | 요청 일시 중지와 처리 기준 시각 고정을 쓰지 않는다. 켜져 있는지는 `GET /ChatService/test-support/clock`, `GET /ChatService/test-support/pauses`의 응답으로 확인한다. | 실행04의 JMeter 계획 |
| 서버 로그용 헤더 | `X-Test-Log-Name`은 테스트 이름 「기존 거래가 있는 상품의 가격 제안 수락 1건과 등록 가격 결제 17건」이다. `X-Test-Log-Run-Id`는 「실행 시작」 그룹이 `mpay04-`에 날짜와 시각을 붙여 만드는 실행 ID다. `X-Test-Log-Request-Id`는 새 수락이 `accept-new`, 새 결제가 `pay-01`부터 `pay-17`까지, 기존 주문을 만드는 준비 결제가 `prep-order-existing`, 기존 예약을 만드는 준비 수락이 `prep-accept-existing`이다. | 실행04의 JMeter 계획 |
| 회원 ID | 판매자는 `run04_seller`, 기존 주문 구매자는 `run04_order_buyer`, 기존 예약 구매자는 `run04_reserve_buyer`, 새 흥정 구매자는 `run04_offer_buyer`, 새 등록 가격 구매자 01부터 17까지는 `run04_listed_buyer01`부터 `run04_listed_buyer17`까지다. | 실행04의 JMeter 계획 |

### 4.2 요청과 실행 제어

| 동작·적용 단계 | 요청·입력 또는 실행 방법 | 정상 응답·종료 확인 |
|---|---|---|
| 준비 요청 | 회원 가입은 `POST /ChatService/members/join`, 로그인은 `POST /ChatService/login`이다. 상품 등록은 `POST /ChatService/api/products`, 대화 시작은 `POST /ChatService/api/products/{상품 ID}/conversations`, 충전은 `POST /ChatService/api/wallet/charges`, 가격 제안은 `POST /ChatService/api/conversations/{대화 ID}/offers`다. 기존 주문 구매자의 결제와 판매자의 준비 수락은 새 결제, 새 수락과 같은 경로로 보낸다. | 준비 그룹마다 응답을 확인하고 `준비_단계별확인.csv`에 기록한다. |
| 새 수락 | 판매자의 로그인 쿠키로 `POST /ChatService/api/offers/{제안 ID}/accept`를 한 번 보낸다. 본문은 없다. | 성공은 HTTP 200과 새 예약이다. 수량 부족 거절은 HTTP 409와 오류 코드 `RESERVATION_QUANTITY_EXCEEDED`다. |
| 새 결제 | 새 등록 가격 구매자의 로그인 쿠키로 `POST /ChatService/api/orders`를 한 번 보낸다. 본문에는 `productId`, `quantity`(1), `recipientName`, `shippingAddress`, `requestId`를 넣고 `offerId`는 넣지 않는다. `requestId`는 실행 ID에 요청 ID를 붙인다. | 성공은 HTTP 201과 새 주문이다. 수량 부족 거절은 HTTP 409와 오류 코드 `PRODUCT_RESERVED`다. |
| 응답 분류 | 검증 요청 그룹의 「응답 분류(파일은 모든 요청이 끝난 뒤 씀)」가 응답을 「성공」, 「수량부족」, 「기타오류」, 「미확인」으로 나눈다. | HTTP 409와 `INSUFFICIENT_STOCK`, HTTP 409와 `PRODUCT_NOT_ON_SALE`은 「수량부족」으로 나누되 예상 상태와 다른 사유로 적는다. 그 밖의 HTTP 응답은 「기타오류」다. 숫자 HTTP 응답을 받지 못한 요청은 「미확인」이다. |
| 출발 맞추기 | 검증 요청 그룹의 스레드는 40개다. 스레드마다 `실행04_검증요청배정.csv`의 한 줄(맡을 요청, 로그인 쿠키의 역할, 출발 시점)을 읽고, 읽을 줄이 없는 스레드는 바로 끝난다. 「출발 조건 확인과 출발 맞추기(모든 요청이 준비되어야 출발, 출발 시점마다 함께 출발)」가 요청 전 확인에서 출발 상태와 다른 항목이 0개인지, 로그인 쿠키가 있는지, 기한 여유와 로그인 유지 시간이 남았는지 확인한다. 18건이 모두 준비되면 그 순간을 기준으로 출발 시점마다 같은 출발 시점의 요청끼리 함께 출발한다. | 출발한 순간은 `검증요청_전체출발시각.csv`에 남는다. 이 파일이 있는 결과 폴더에서는 검증 요청을 다시 보내지 않는다. 출발을 기다린 시간은 검증 요청의 응답 시간에 넣지 않는다. |
| 요청 전 확인과 종료 후 확인의 API 조회 | 상품 상세는 `GET /ChatService/api/products/{상품 ID}`를 기존 예약 구매자, 새 흥정 구매자, 새 등록 가격 구매자 01의 로그인 쿠키로 조회한다. 대화 상세는 `GET /ChatService/api/conversations/{대화 ID}`를 판매자의 로그인 쿠키로 구매자 20명의 대화마다 조회한다. 잔액은 `GET /ChatService/api/wallet`, 잔액 변동 내역은 `GET /ChatService/api/wallet/transactions`를 구매자 20명마다 조회한다. 기존 주문 상세는 `GET /ChatService/api/orders/{주문 ID}`를 조회한다. | 응답은 `요청전_API응답.json`, `요청전_API조회.csv`, `종료후_API응답.json`, `종료후_API조회.csv`에 저장한다. |
| 요청 전 확인과 종료 후 확인의 DB 조회 | `PRODUCT`, `CONVERSATION`, `PRICE_OFFER`, `RESERVATION`, `PURCHASE_ORDER`는 대상 상품의 `PRODUCT_ID`로 조회한다. `WALLET`, `BALANCE_TRANSACTION`은 구매자 20명의 `MEMBER_ID`로 조회한다. | 조회 결과는 `요청전_DB_*.csv`, `요청전_기준값.json`, `종료후_DB_*.csv`, `종료후_DB조회.json`에 저장한다. 요청 전 확인의 대조 결과는 `요청전_확인결과.csv`에 저장한다. |
| 결과 집계 | 「결과 집계(종료후_확인결과.csv, 검증요청_결과.csv, 검증요청_출발시점별결과.csv, 검증요청_응답시간요약.csv, 종료후확인.log, 실행_요약.csv)」가 `요청전_기준값.json`, `검증요청_응답.json`, 종료 후 확인의 API 응답과 DB 조회 결과를 읽어 대조한다. 대조 항목은 「규칙」, 「시간」, 「기대」로 나뉜다. | 「규칙」 항목이 다르면 규칙 위반으로 적는다. 출발하지 못한 요청, 「기타오류」나 「미확인」인 응답, 확인하지 못한 항목, 「시간」 항목이 다른 것은 검증 미완료 사유로 적는다. 「기대」 항목이 다르거나, 예상 상태와 다른 사유로 거절되었거나, 수량이 남았는데 거절된 요청이 있으면 조사할 사항으로 적는다. |
| 결과 집계의 계산 | 새 수락이 성공하면 1, 거절되면 0으로 두고, 새 결제가 성공한 건수를 구한다. 전체 주문은 기존 주문 1건 3개에 새 결제가 성공한 건수를 더한다. 유효 예약은 기존 예약 1건 4개에, 새 수락이 성공했으면 1건 2개를 더한다. 남은 수량은 판매 수량 16개에서 전체 주문 수량을 뺀다. | 계산한 수량을 종료 후 확인의 API 응답과 DB 조회 결과에 대조한다. |
| JMeter 그룹이 쓰는 CSV | 테스트데이터의 실행04 폴더에 `실행04_회원.csv`, `실행04_실행정보.csv`, `실행04_검증요청배정.csv`, `실행04_회원가입결과.csv`, `실행04_로그인결과.csv`, `실행04_상품과대화.csv`, `실행04_기존주문.csv`, `실행04_기존예약.csv`, `실행04_새흥정제안.csv`, `실행04_요청전확인.csv`를 쓴다. | 다음 그룹이 이 파일을 읽어 변수로 쓴다. 회원 파일에는 테스트 회원의 비밀번호가 들어 있고, 로그인 결과 파일에는 로그인 쿠키가 들어 있다. 두 파일은 저장소에 올리지 않는다. |
| 결과 폴더에 쓰는 파일 | `실행조건.csv`, `준비_단계별확인.csv`, `준비_`로 시작하는 응답 본문 JSON, `계획_결과.csv`, `검증요청_전체출발시각.csv`, `검증요청_출발.csv`, `검증요청_응답.json`, `검증요청_결과.csv`, `검증요청_출발시점별결과.csv`, `검증요청_응답시간요약.csv`, `종료후_확인결과.csv`, `종료후확인.log`, `실행_요약.csv`와 위의 요청 전 확인, 종료 후 확인 파일을 쓴다. | 결과 폴더는 「실행 시작: 실행 설정·회원·DB 계정 확인과 실행 조건 기록」 그룹이 만든다. |
