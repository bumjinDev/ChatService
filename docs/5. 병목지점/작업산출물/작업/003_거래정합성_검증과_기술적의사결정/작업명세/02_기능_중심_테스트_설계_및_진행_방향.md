# 기능 중심 시나리오 설계 및 단계적 테스트 진행 원칙

- 작업기록: [작업기록](../작업기록.md)

## 1. 기존 시나리오 중심 설계의 문제점

기존에는 실제 서비스에서 발생할 법한 복합적인 스토리형 시나리오를 먼저 구상하고, 그 안에 여러 기능과 기술적 검증 요소를 포함하려고 했다.

그러나 이러한 방식은 시나리오를 구성하는 과정에서 오히려 검증할 기능과 기술적 문제의 범위를 제한하는 결과를 가져왔다.

구체적으로 다음 조건을 동시에 만족시키기가 어려웠다.

1. 실제 서비스에서 발생할 가능성이 충분한 상황이어야 한다.
2. 여러 기능이 하나의 흐름 안에서 자연스럽게 연결되어야 한다.
3. 기능 간 상호작용을 통해 동시성 문제, 데이터 정합성 문제 또는 성능 병목 등 기술적으로 검증할 가치가 있는 상황이 발생해야 한다.
4. 테스트 결과가 비즈니스 규칙의 수립이나 기술적 의사결정의 근거로 활용될 수 있어야 한다.
5. 포트폴리오에서 보여주고자 하는 주요 기능과 검증 요소를 충분히 포함해야 한다.

이러한 조건을 충족하는 시나리오를 먼저 구상하다 보니, 현실적인 스토리를 유지하기 위해 기능의 조합이 제한되거나 특정 기능을 포함하기 위해 부자연스러운 상황을 만들어야 하는 문제가 발생했다.

결과적으로 시나리오를 설계하기 위한 고민 자체에 지나치게 많은 시간이 소모되었으며, 실제로 검증해야 할 기능과 기술적 문제에 집중하기 어려웠다.

따라서 **스토리형 시나리오를 설계의 출발점으로 삼는 기존 접근 방식을 변경한다.**

## 2. 기능 및 상호작용 중심의 설계

앞으로는 시나리오를 먼저 구상하지 않는다.

우선 프로젝트에 구현된 기능과 비즈니스 규칙을 정리하고, 검증할 가치가 있는 기능 간 상호작용을 선정한다.

이 과정에서는 다음 사항을 중심으로 검토한다.

1. 각 기능이 어떠한 데이터를 조회하거나 변경하는가?
2. 서로 다른 기능이 동일한 데이터 또는 비즈니스 상태에 영향을 미치는가?
3. 여러 요청이 동시에 실행되거나 처리 순서가 달라질 때 어떤 문제가 발생할 수 있는가?
4. 기존 비즈니스 규칙만으로 해당 상황을 처리할 수 있는가?
5. 추가적인 비즈니스 규칙이나 기술적 해결 방안이 필요한가?
6. 테스트를 통해 어떤 사실을 확인하고, 이를 어떠한 기술적 의사결정의 근거로 활용할 수 있는가?

이러한 검토를 바탕으로 기능들을 복합적으로 구성하고, 이후 실제 서비스에서 발생할 법한 사용자 행동과 업무 흐름을 적용하여 스토리형 시나리오로 구체화한다.

즉, 기존의 접근 방식이 다음과 같았다면,

**스토리형 시나리오 구상 → 기능 조합 → 기술적 검증 요소 도출**

앞으로는 다음 순서로 진행한다.

**기능 및 비즈니스 규칙 분석 → 기능 간 상호작용 구성 → 검증 목적 설정 → 실제 서비스 흐름에 맞는 시나리오 설계**

이를 통해 시나리오의 현실성을 유지하면서도, 스토리 구성에 의해 기술적 검증 범위가 불필요하게 제한되는 문제를 방지한다.

## 3. 기능별 검증과 복합적인 상호작용 검증의 구분

포트폴리오에서 검증하고자 하는 모든 기능을 하나의 복합 시나리오에 포함할 필요는 없다.

또한 모든 시나리오에서 반드시 새로운 기술적 문제를 발견하거나 기술적 의사결정을 도출해야 하는 것도 아니다.

테스트의 목적에 따라 다음 두 가지를 구분한다.

### 3.1. 기능 및 비즈니스 규칙 검증

개별 기능 또는 비교적 단순한 기능 조합을 대상으로 기존 비즈니스 규칙이 정상적으로 적용되는지 검증한다.

이 과정에서는 요청 처리 결과, 데이터 상태 변화, 기능의 정상 동작 여부 등을 확인한다.

별도의 기술적 문제가 발견되지 않더라도 기능의 정확성과 기존 비즈니스 규칙의 타당성을 확인했다는 점에서 검증의 의미가 있다.

### 3.2. 복합적인 상호작용 및 기술적 문제 검증

여러 기능이 동일한 데이터나 비즈니스 상태에 영향을 미치는 상황을 구성한다.

특히 요청의 동시 실행이나 처리 순서에 따라 데이터 정합성 문제, 비즈니스 규칙 간 충돌, 성능 병목 등이 발생할 가능성이 있는 조합을 우선적으로 검토한다.

이 과정에서 실제로 문제가 발생하는지 확인하고, 문제가 발견되면 발생 원인과 해결 방안을 분석하여 기술적 의사결정으로 연결한다.

단, 기술적 문제를 발견하기 위해 비현실적인 비즈니스 흐름을 억지로 구성하지 않는다. 실제 서비스에서 발생 가능한 상황을 바탕으로 검증하되, 문제의 발생 조건을 확인하기 위한 동시 요청과 부하 조건은 의도적으로 구성할 수 있다.

### 3.3. 전체 테스트 범위의 충족

개별 시나리오가 모든 기능을 포함해야 한다는 제약을 두지 않는다.

대신 여러 테스트를 종합했을 때 포트폴리오에서 보여주고자 하는 주요 기능, 비즈니스 규칙 및 기술적 검증 요소가 충분히 다루어졌는지 확인한다.

이를 통해 개별 시나리오의 현실성과 자연스러움을 유지하면서도 전체적인 기능 검증 범위를 확보한다.

## 4. 기술적 의사결정을 위한 트래픽 환경 구성

프로젝트가 대형 쇼핑몰 수준의 서비스가 아니더라도, 높은 트래픽이나 동시 요청이 발생하는 환경을 인위적으로 구성하여 테스트한다.

서비스의 현재 규모가 크지 않다는 이유만으로 동시성 문제나 성능 문제에 대한 검증을 제한할 필요는 없다.

다만 단순히 높은 트래픽을 발생시키는 것 자체를 목적으로 삼지는 않는다.

테스트를 통해 다음 사항을 확인하는 것이 중요하다.

1. 요청이 동시에 발생했을 때 기존 비즈니스 규칙이 정상적으로 유지되는가?
2. 요청 수나 동시성이 증가하면서 새로운 문제가 발생하는가?
3. 문제가 발생한다면 어떤 조건에서 재현되는가?
4. 해당 문제를 해결하기 위해 비즈니스 규칙이나 기술적 구현을 변경할 필요가 있는가?
5. 변경 전후 테스트 결과를 비교하여 기술적 의사결정의 타당성을 입증할 수 있는가?

특히 높은 트래픽을 구성하더라도 실제 서비스에서 발생 가능한 요청 흐름과 데이터 상태를 고려한다.

**높은 트래픽은 기술적 문제를 발견하고 검증하기 위한 수단이며, 최종 목적은 테스트 결과를 근거로 비즈니스 규칙과 기술적 의사결정의 타당성을 설명하는 것이다.**

## 5. 테스트 요청 규모의 단계적 확대

초기 테스트부터 무조건 많은 요청을 발생시키지 않는다.

우선 요청의 처리 과정과 결과를 직접 추적하고 분석할 수 있는 수준으로 요청 수를 설정한다.

초기 테스트에서는 다음 사항을 중점적으로 확인한다.

1. 각 요청이 어떠한 순서로 처리되는가?
2. 요청 간 상호작용이 실제로 발생하는가?
3. 데이터 상태가 어떠한 과정을 거쳐 변경되는가?
4. 비즈니스 규칙이 의도한 대로 적용되는가?
5. 예상하지 못한 결과가 발생했다면 그 원인을 추적할 수 있는가?

이 단계에서는 요청 수를 늘리는 것보다 **테스트 결과를 충분히 이해하고 문제의 발생 과정을 설명할 수 있는지**를 우선한다.

이후 초기 테스트 결과를 분석하여 추가 검증이 필요하다고 판단되면 요청 수와 동시성을 단계적으로 확대한다.

특히 낮은 부하에서는 확인하기 어려운 문제가 있거나, 기술적 의사결정의 근거를 확보하기 위해 더 높은 부하가 필요한 경우에는 요청 규모를 충분히 확대한다.

단, 요청 수를 늘리는 과정에서도 결과를 분석할 수 있도록 로그, 응답 결과 및 데이터 상태 등을 확보한다.

최종적으로는 단순히 많은 요청을 처리했다는 사실보다, **어떤 조건에서 어떠한 문제가 발생했으며 이를 어떻게 분석하고 해결했는지**를 설명할 수 있어야 한다.

## 6. 최종 진행 원칙

앞으로 테스트 설계 및 수행은 다음 순서에 따라 진행한다.

**1단계. 기능 및 비즈니스 규칙 분석**

프로젝트의 주요 기능과 기존 비즈니스 규칙을 정리하고, 각 기능이 영향을 미치는 데이터와 상태 변화를 파악한다.

**2단계. 기능 간 상호작용 구성**

서로 영향을 주고받는 기능들을 선정하여 복합적으로 구성한다. 이 과정에서 동시성 문제, 데이터 정합성 문제 및 비즈니스 규칙 간 충돌 가능성을 검토한다.

**3단계. 검증 목적 및 테스트 범위 설정**

각 기능 조합을 통해 무엇을 검증할 것인지 명확히 한다. 기능의 정상 동작을 검증할 것인지, 기술적 문제의 발생 여부를 확인할 것인지 구분한다.

**4단계. 실제 서비스 흐름에 맞는 시나리오 설계**

선정한 기능 조합과 검증 목적을 바탕으로 실제 서비스에서 발생할 법한 사용자 행동 및 업무 흐름을 구성한다.

이때 모든 기능이나 기술적 검증 요소를 하나의 시나리오에 억지로 포함하지 않는다.

**5단계. 추적 가능한 규모의 초기 테스트**

요청 처리 과정과 결과를 충분히 추적하고 분석할 수 있는 규모로 테스트를 수행한다.

**6단계. 테스트 결과 분석**

요청 처리 결과, 데이터 상태 변화, 비즈니스 규칙의 적용 여부 및 기술적 문제의 발생 여부를 분석한다.

**7단계. 필요에 따른 부하 확대 및 기술적 의사결정**

추가 검증이 필요하면 요청 수와 동시성을 단계적으로 확대한다.

문제가 확인되면 발생 원인과 해결 방안을 검토하고, 필요한 비즈니스 규칙 및 기술적 구현을 결정한다. 이후 변경 전후 결과를 비교하여 의사결정의 타당성을 검증한다.

## 7. 핵심 결론

**시나리오를 구성하기 위해 기능을 선택하는 것이 아니라, 검증할 기능과 기능 간 상호작용을 먼저 선정하고 이를 설명하기 위해 시나리오를 구성한다.**

시나리오는 기술적 검증을 위한 수단이지, 검증 범위를 결정하거나 제한하는 기준이 아니다.

또한 모든 기능과 기술적 의사결정을 하나의 시나리오에 담을 필요는 없다. 여러 테스트를 통해 전체적인 기능 검증 범위를 충족하고, 기술적으로 의미 있는 문제를 발견한 경우 이를 별도의 의사결정 사례로 발전시킨다.

테스트 역시 처음부터 대규모 요청을 발생시키기보다 결과를 추적하고 이해할 수 있는 규모로 시작한다. 이후 기술적 검증의 필요성에 따라 요청 규모를 확대한다.

궁극적인 목적은 복잡한 시나리오를 만드는 것이 아니라, **실제 서비스에서 발생 가능한 기능 간 상호작용을 검증하고, 그 결과를 근거로 비즈니스 규칙과 기술적 의사결정의 타당성을 입증하는 것이다.**
