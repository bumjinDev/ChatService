## 1. 시나리오 기준과 정책 후보의 구분

기본 시나리오에 채택한 기준, 현재 구현의 동작, 검토 중인 정책 후보를 구분한다.

| 구분 | 의미 | 대표 사례 |
|---|---|---|
| 기본 시나리오에 채택한 기준 | 이번 기본안을 설명하고 판단하는 데 사용하는 조건 | 모니터 4대, 구매자 A·B·C·D, 판매자의 순차적인 제안 검토 |
| 현재 명세·코드에서 확인한 동작 | 실제 소스와 기존 문서를 읽어 확인한 내용 | 제안 자체는 수량을 점유하지 않음, 수락하면 예약 생성, 합의 가격 주문 취소 후 재예약 |
| 지켜야 할 업무상 보장 | 실행 결과가 올바른지 판단할 기준. 구현이 동시 요청에서도 보장한다는 뜻은 아님 | 유효한 예약 보호, 수량 초과 금지, 결제 결과와 금액·수량의 일치 |
| 설명을 위한 가정 | 특정 구매 상황을 구체적으로 논의하기 위해 둔 조건 | A·C는 각각 2대를 함께 구매하려 함, C·D의 제안 가격은 판매자가 수락을 고려할 수 있음 |
| 채택한 변경 정책 | 구현 수정 후 시나리오에 적용할 기준. 구현 완료를 뜻하지 않음 | 구매 철회 시 보호 종료, 재구매 목적 취소 시 한시적 보호 |
| 미확인 사항 | 코드나 기록만으로 확정하지 못한 사실 | 일반적인 화면 사용에서 여러 수락의 서버 처리가 실제로 겹치는지, 배포 서버와 로컬 소스의 일치 여부 |

특히 다음 사항을 혼동하지 않는다.

1. 기본 시나리오가 완성되었다고 모든 제품 정책이 확정된 것은 아니다.
2. 여러 수락 행동을 같은 거래 흐름에 포함했다고 수락끼리의 동시 처리를 확인한 것은 아니다.
3. 현재 정책에 맞는 결과라도 구매 경험의 개선 대상일 수 있다.
4. 요구사항에 적힌 보장과 현재 구현이 실제로 달성한 보장은 구분한다.
5. 설명용 수량과 참여자 수는 실제 서비스의 대표 규모나 성능 목표가 아니다.

## 2. 출발 배경과 검토 목적

### 2.1 최초 문제: 작업 002와 작업 003의 구분

출발점은 결제·수락 등 기능별로 나눈 경합 범위가 구매자·판매자의 거래 흐름을 설명하는 데에도 적절한지 검토하는 것이다.

| 기존 작업 | 주된 관심 | 당시 진행 상태 |
|---|---|---|
| 작업 002 | 구매자의 결제와 판매자의 가격 제안 수락이 같은 상품 수량에 영향을 주는 상황 | 실행01·실행02 기록 존재 |
| 작업 003 | 같은 상품에 대한 여러 가격 제안 수락이 예약 가능한 수량에 영향을 주는 상황 | 실행하지 않은 상태 |

기존 작업은 서로 다른 기능 조합의 경합을 관찰하기 위해 구분했다. 새 시나리오에서는 이 기능별 구분이 구매자·판매자의 실제 거래 흐름에도 적절한지 재검토한다.

검토 기준은 다음 두 가지다.

- **비즈니스 시나리오의 범위:** 어떤 사람들이 어떤 목적으로 거래하고 서로의 행동에 어떤 영향을 받는가.
- **개별 경합의 관찰 범위:** 어떤 요청 조합이 충돌했으며, 결과와 원인을 구분하려면 무엇을 따로 확인해야 하는가.

하나의 상품 거래 흐름 안에 여러 경합 가능성이 존재할 수 있다. 그렇다고 모든 경합을 반드시 같은 순간에 발생시켜야 하는 것은 아니다.

### 2.2 판매자 행동과 수락 처리의 관계

구매 희망자는 상품별로 판매자와 1:1 대화를 시작하고 가격을 제안한다. 판매자는 각 구매 희망자의 대화 화면에서 수락 버튼을 누른다. 좌측 대화 목록에서 다른 방을 선택하면 해당 방의 화면을 새로 불러온다.

따라서 다음 두 조건을 구분한다.

1. 판매자가 서로 다른 구매자의 제안을 차례로 검토·수락할 수 있는가.
2. 앞선 수락이 서버에서 처리되는 동안 다른 수락도 서버에 도달하여 실제로 처리가 겹치는가.

대화방을 이동할 수 있다는 사실만으로 두 수락의 서버 처리가 겹친다고 판단할 수는 없다.

### 2.3 검토 범위

대화방 이동, 제안 수락, 예약, 결제, 수량 변경의 관계를 바탕으로 기본 거래 흐름과 판단 기준을 구성한다.

- 구매 목적, 수량 확보 시점, 행동의 선후 관계와 가능한 결과를 정리한다.
- 작업 002·003의 공통 거래 맥락과 개별 경합의 관찰 범위를 구분한다.
- 구매자 취소 의도별 분리는 채택한 변경 정책으로 관리한다. 임시 점유·제안 유효기간은 별도 정책 후보로 유지한다.
- 다수 구매자로의 확대, 테스트 명세·실행 계획과 구현 변경은 후속 범위로 둔다.

### 2.4 기존 작업의 활용 범위

기존 002는 여러 기능을 조합하여 구매자·판매자의 거래 흐름을 살펴보기 위한 구성이었다. 새 시나리오는 기존 구성을 그대로 이어받을 필요 없이 구매 목적과 서비스가 보장할 내용을 기준으로 독립적으로 구성한다.

기존 기록의 활용 원칙은 다음과 같다.

- 기존 002의 인물, 수량, 요청 순서, 취소·재구매 연결, 기대 결말을 새 구성에 유지할 의무가 없다.
- 기존 기록에서 확인된 관찰 사실은 필요할 때 참고할 수 있다.
- 과거 시나리오의 구성 품질과 그 실행에서 관찰한 사실의 가치는 구분한다.
- 새 시나리오는 구매자의 목적과 서비스의 약속을 기준으로 독립적으로 구성한다.
- 기존 기록과의 대조는 새 구성의 필수 선행 과정에서 제외한다.

기존 기록을 삭제하거나 내용을 수정하기로 한 것은 아니다.

## 3. 현재 거래 처리 구조

### 3.1 제안·예약·결제의 관계

가격 제안은 판매자가 검토할 가격과 수량을 등록하는 단계다. 제안이 수락되면 해당 구매자의 예약이 생성되고, 결제가 성립하면 주문 생성과 상품 수량 차감이 이루어진다. 합의 가격 주문을 취소하면 현재 구현에서는 수량 복구와 새 예약 생성이 이어진다.

이 연결 관계를 기준으로 각 행동이 언제 수량을 확보하고 다른 거래에 어떤 영향을 주는지 구분한다. 관련 구현 위치는 16번 항목에 정리한다.

### 3.2 판매자의 제안 검토와 수락

판매자는 구매자별 대화방에서 제안 가격과 수량을 확인하고 수락한다. 다른 대화방을 선택하면 해당 방의 화면과 거래 상태를 새로 불러온다.

- 수락 확인을 마치면 요청이 전송되고, 처리 중에는 누른 버튼이 비활성화된다.
- 수락 요청 중에도 다른 대화방으로 이동하는 것을 막는 처리는 없다.
- 거래 상태 변화는 대화 상세 재조회와 실시간 이벤트로 화면에 반영된다.

이 구조는 여러 구매자의 제안을 차례로 검토하는 흐름을 뒷받침한다. 다만 대화방 이동이 가능하다는 사실만으로 두 수락의 서버 처리가 실제로 겹친다고 볼 수는 없다.

### 3.3 가격 제안 수락과 예약 생성

주요 호출 관계는 다음과 같다.

`대화 화면의 수락 → OfferController.accept → OfferService.respond → ReservationService.reserve → 예약 저장`

확인한 업무 처리는 다음과 같다.

- 판매자 권한, 상품 판매 상태, 제안의 응답 대기 상태를 확인한다.
- 수락 처리 안에서 같은 제안 수량의 예약 생성을 호출한다.
- 예약 생성 시 해당 구매자의 기존 유효 예약과 상품의 예약 가능 수량을 확인한다.
- 수락과 예약은 같은 트랜잭션에서 처리하도록 구성되어 있다. 예약이 거절되면 수락도 반영되지 않는 구조다.
- 예약은 상품의 남은 수량을 직접 차감하지 않는다.
- 수락·예약이 반영되면 같은 상품의 대화들에 상태 이벤트를 보내도록 등록한다.

서로 다른 구매자의 예약을 상품 전체에서 하나만 허용하는 규칙은 아니다. 각 구매자와 수량 조건이 허용하면 같은 상품에 여러 구매자의 예약이 있을 수 있다.

### 3.4 결제에 따른 수량 변경

주요 호출 관계는 다음과 같다.

`구매 화면의 결제 → OrderController.placeOrder → OrderService.placeOrder → 주문 생성·잔액 차감·상품 수량 차감 → 해당 구매자의 유효 예약 결제 종료`

확인한 업무 처리는 다음과 같다.

- 남은 수량과 다른 구매자의 유효 예약을 고려한 구매 가능 수량을 검사한다.
- 등록 가격과 합의 가격을 구분한다.
- 합의 가격은 해당 구매자의 수락된 제안, 유효한 예약, 제안 수량과 같은 결제 수량 등을 확인한다.
- 합의가 예약 중인 구매자는 그 상품을 등록 가격으로 먼저 결제할 수 없도록 되어 있다.
- 결제 성공 시 주문 수량만큼 남은 수량을 차감한다.
- 결제한 구매자의 유효 예약은 결제 종료 상태로 전환한다.

예약된 수량을 결제로 전환하는 것은 그 수량을 다른 구매자에게 새로 풀어 주는 동작이 아니다.

### 3.5 공통 수량 계산

현재 조회 로직은 다음 관계를 사용한다.

**조회자 기준 구매 가능 수량 = 상품의 남은 수량 − 다른 구매자에게 걸린 유효한 예약 수량의 합계**

유효한 예약은 활성 상태이면서 만료 시각 전인 예약이다. 자동 만료 작업이 아직 상태를 바꾸지 않았더라도 만료 시각이 지나면 유효한 예약으로 계산하지 않는다.

- 판매자가 새 예약을 만들 때는 구매자들의 유효 예약 전체를 제외한 수량이 상한이 된다.
- 예약된 구매자가 결제할 때는 자신의 예약을 구매 가능 수량에서 제외하지 않는다.
- 그렇다고 예약 구매자가 합의한 수량보다 자유롭게 더 결제할 수 있다는 뜻은 아니다. 합의 가격 결제에는 제안 수량 일치 등 별도의 조건이 있다.

수량 계산 결과를 조회했다는 사실만으로 그 수량을 확보한 것은 아니다.

### 3.6 취소와 재예약의 현재 동작

확인한 현재 구현·명세에서는 발송 전 취소 시 주문 수량을 복구한다. 합의 가격 주문이면 그 결제로 끝난 예약을 바탕으로 같은 내용의 새 예약을 생성한다.

- 기존 결제 종료 예약을 다시 활성으로 되돌리는 방식이 아니라 새 행을 만든다.
- 기본 예약 기간은 문서상 20분이며, 새 예약은 취소 시점부터 새 기간을 적용한다.
- 같은 수량을 복구하고 다시 예약하므로 다른 구매자의 구매 가능 수량은 취소만으로 늘지 않을 수 있다.
- 주문 취소와 예약 해제는 별도 동작이다.
- 현재 명세에서는 판매자 취소와 미발송 자동 취소도 합의 가격 주문이면 재예약하는 흐름을 사용한다.

위 내용은 기존 확인 시점의 구현 기록이다. 구매 철회와 재구매 목적 취소를 분리하는 정책을 채택했으며, 시나리오 테스트 전에 11.1번 항목의 기준으로 수정한다. 이 문서 수정은 코드 수정 완료를 뜻하지 않는다.

## 4. 시나리오 구성의 변경 근거

### 4.1 주요 구성 결정

| 검토 항목 | 초기 구성·검토 내용 | 반영 내용과 근거 |
|---|---|---|
| 작업 번호를 기준으로 검토 시작 | 002와 003을 합칠지 나눌지 고민 | 거래 참여자의 행동에 따른 거래 범위와 개별 경합 확인 범위를 구분하기로 함 |
| 실제 코드 확인 | 대화방 이동, 수락, 예약, 결제가 연결되는 방식 확인 | 같은 수량을 다루는 공통 업무 맥락은 확인. 실제 수락 간 겹침은 미확인으로 유지 |
| 초기 설명용 구성 | 판매자 1명·구매자 5명·상품 7개 | 정책 차이를 설명하는 중간 구성으로 사용했지만 최종 기본안은 아님 |
| 취소 정책 논의 확장 | 구매 철회·재구매 목적·판매자 취소·자동 취소 검토 | 첫 구매 흐름에 모두 포함하지 않고 별도 정책 후보·후속 상황으로 구분 |
| 기존 002의 활용 범위 | 기존 기록과의 직접 대조 | 구매 목적부터 독립적으로 구성하기 위해 필수 선행 과정에서 제외 |
| 독립적인 거래 상황 구성 | 작업실 정리 판매자, 모니터 4대, 서로 다른 목적의 구매자 4명 | 수량과 행동에 이유를 붙인 현재 기본안으로 채택 |
| 기본안의 종료·판단 기준 정리 | 가능한 거래 결과, 진행 중·미확인 상태, 금액·수량의 일치 정리 | 기본 비즈니스 시나리오 구성 완료로 정리 |
| 규모 확장과의 구분 | 기본안 완성과 확장 설계의 관계 | 기본형은 완료 상태로 두고 규모 확장·실행 준비는 별도 단계로 구분 |

### 4.2 7개 구성의 정확한 위치

기존 002 기록에서 논의한 상품 수량은 7개였다. 그 기록에서는 3개가 이미 예약되어 있었고, 나머지 4개에 등록 가격 2개 결제와 추가 제안 3개 수락이 영향을 주었다.

초기 정책 검토에는 이를 확장한 다음의 설명용 구성을 사용했다.

| 중간 구성의 구매자 | 구매 희망 수량 | 당시 역할 |
|---|---:|---|
| A | 3개 | 이미 합의·예약된 구매자 |
| B | 2개 | 등록 가격 구매자 |
| C | 1개 | 등록 가격 구매자 |
| D | 3개 | 가격 제안 구매자 |
| E | 1개 | 가격 제안 구매자 |

이 중간 구성은 총 판매 수량 7개, 총 구매 희망 수량 10개였다. A의 취소 의도에 따라 다른 구매자의 기회가 달라지는 것을 설명하는 데 사용했다.

예를 들어 A가 3개, B가 2개를 결제한 뒤 A가 취소하면 남은 수량은 5개로 복구된다. 현재 정책대로 A에게 3개를 다시 예약하면 다른 구매자는 2개만 확보할 수 있다. A가 구매를 완전히 철회하여 새 예약을 만들지 않는 후보에서는 5개가 다른 거래에 열리고, C·D·E의 희망 수량 합계 5개를 수용할 수 있다.

이는 정책 차이를 설명하기 위한 가정 사례였으며, 새로 실행한 테스트 결과가 아니다. 이 문서의 최종 A·B·C·D와 중간 구성의 역할·수량을 혼용하지 않는다.

### 4.3 왜 4개로 변경했는가

기존 002를 필수 설계 기준에서 제외하고 구매 목적부터 독립적으로 구성하면서 상품 수량을 4개로, 구매자를 4명으로 정했다.

4개는 다음 관계를 명확하게 만들기 위한 설명용 선택이다.

- A에게 이미 예약된 2개: 기존 약속이 보호되는지 살펴볼 부분.
- 아직 확보되지 않은 2개: C의 2개 예약 또는 B의 1개 결제와 D의 1개 예약이 성립할 수 있는 부분.
- C와 D의 제안을 모두 수락하면 남은 2개에 합계 3개를 약속하게 되어 수량 한계를 넘는다.

7개가 잘못된 수량이어서 바꾼 것이 아니다. 4개는 초기 수량 관계와 가능한 결과를 단순하게 설명하기 위한 수량이며, 실제 서비스의 적정 재고·대표 요청 규모·성능 목표를 의미하지 않는다.

이후 수량이나 참여자 수를 변경할 때에도 어떤 거래 관계를 살펴보기 위한 변경인지 목적과 근거를 함께 기록한다.

## 5. 완료된 기본 비즈니스 시나리오

### 5.1 중심 상황과 목적

판매자는 작업실을 정리하면서 같은 모델·동등한 상태의 중고 모니터 4대를 판매한다. 구매자는 등록 가격으로 바로 구매하거나, 대화에서 가격과 수량을 제안할 수 있다.

여러 구매자가 각자의 조건으로 구매를 시도하는 동안 상품 수량이 줄어든다. 서비스는 이미 성립한 예약을 보호하면서 새로운 결제와 새로운 예약의 성립 여부를 결정해야 한다.

**현재 기본안의 목적은 첫 구매 과정에서 수량 확보가 성립하는 기준과 이미 약속한 예약 수량의 보호를 판단하는 것이다.** 모니터 4대·판매자 1명·구매자 A~D의 구성을 유지하며, 각 참여자가 확인한 결과에 따라 결제와 제안 응답을 이어 간다.

주문 취소에 따른 구매 기회의 반환·유지는 11.1번 항목의 채택 정책을 적용한 후속 흐름으로 포함한다. 첫 구매와 취소 후속 단계는 구분한다. 장시간 제안 대기 중의 구매 의사 변화는 별도 후속 검토로 유지한다. 기본안에는 구매 의사가 유지되는 동안 제안의 응답을 기다리는 행동이 포함되지만, 오래된 제안의 유효기간·철회 정책까지 확정하는 것을 완료 조건으로 삼지는 않는다. 결제 준비 중 임시 점유도 별도 정책 후보로 둔다.

이번 시나리오가 다루는 중심 질문은 다음과 같다.

1. 구매자는 어느 순간부터 자기 수량이 확보되었다고 믿을 수 있는가.
2. 남은 수량을 여러 사람이 원할 때 어떤 성공·실패 결과가 정당한가.
3. 각 참여자는 자신이 확인할 수 있는 정보를 바탕으로 어떻게 다음 행동을 하는가.

### 5.2 참여자와 구매 목적

| 참여자 | 목적·상황 | 필요한 수량과 행동 |
|---|---|---|
| 판매자 | 작업실을 정리하며 동일 조건의 모니터를 판매 | 총 4대를 등록하고 가격 제안을 대화방에서 하나씩 검토 |
| A | 자녀 두 명의 학습 환경을 마련하려 함 | 2대의 총비용을 협의하여 판매자의 수락을 먼저 받음 |
| B | 고장 난 모니터를 교체하려 함 | 등록 가격을 받아들이고 1대를 바로 구매하려 함 |
| C | 자신의 작업 환경을 듀얼 모니터로 구성하려 함 | 2대를 함께 구매하려고 가격 제안 |
| D | 보조 화면을 추가하려 하지만 급하지는 않음 | 제안 가격이 수락되면 1대 구매 |

총 구매 희망 수량은 6대이며 판매 수량은 4대다. 모든 구매자의 요구를 동시에 충족할 수 없다.

A와 C는 이 기본안에서 각각 2대를 함께 확보하려는 구매자로 둔다. 수량이 부족하다고 시스템이 자동으로 1대만 구매하게 바꾸지 않는다. 일부 수량만이라도 구매하려는 의사는 별도 행동 조건이다.

### 5.3 시나리오에서 정한 조건

- 하나의 상품 등록 건으로 취급할 수 있는 동일 모델·동등한 상태의 모니터 4대다.
- 물품 자체는 정상이며 다른 구매자에게 판매할 수 있다. 파손·실물 수량 부족에 따른 판매 중단은 이번 범위가 아니다.
- C·D의 제안 가격은 판매자가 수락을 고려할 수 있는 범위라고 둔다. 제안 가격은 실제 코드의 조건에 맞게 등록 가격보다 낮다고 둔다.
- 구체적인 등록 가격·제안 가격·계정·잔액·주소 등의 실행용 값은 정하지 않았다.
- 대표적인 정상 종료 상태는 수량 외의 결제 조건도 충족되고 구매 의사가 유지되는 경우를 다룬다.
- 구매자의 구매 의사가 유지되는 동안 제안이 검토되는 상황이다. 가격 제안 유효기간 기능이 이미 존재한다고 가정하지 않는다.
- A의 예약은 유효한 상태에서 시작하며, 첫 핵심 흐름에는 예약 해제·만료·주문 취소를 의도적으로 끼워 넣지 않는다.
- 이 가정들은 실제 이용자 데이터를 분석해 얻은 분포나 빈도가 아니다.

### 5.4 거래가 겹칠 수 있는 출발점

A의 2대 제안은 이미 수락되어 예약이 생성되어 있다. 상품의 남은 수량은 4대이고, 다른 구매자들이 새로 확보할 수 있는 수량은 2대다.

- A는 예약된 2대의 결제를 준비한다.
- B는 구매 화면에서 1대를 선택하고 주문 정보를 입력한다.
- C·D는 각각 2대와 1대의 유효하게 등록된 가격 제안을 보내 놓고 응답을 기다린다.
- 판매자는 C·D의 제안을 대화방에서 차례로 검토한다.

C·D의 제안 등록에는 당시 구매 가능 수량 조건이 적용된다. 두 제안은 각각 등록 가능한 상태에서 제출되었다고 둔다. 그렇다고 이후 수락 때에도 수량이 보장되는 것은 아니다. 구체적인 요청 출발 시각이나 기술적 실행 순서는 정하지 않았다.

### 5.5 수량 확보가 성립하는 시점

| 행동 | 수량 확보 여부 | 제공되는 의미 |
|---|---|---|
| 상품 조회·수량 선택·주문 정보 입력 | 확보되지 않음 | 조회 당시 구매 가능한 수량을 알 수 있음 |
| 가격 제안 전송 | 확보되지 않음 | 판매자가 검토할 가격·수량 제안이 등록됨 |
| 판매자의 수락과 예약이 함께 성립 | 해당 구매자에게 예약됨 | 예약이 유효한 동안 다른 거래가 그 수량을 가져가지 못해야 함 |
| 등록 가격 결제가 성립 | 주문 수량 확보 | 주문 생성·금액 차감·상품 수량 차감이 함께 반영되어야 함 |
| 예약된 구매자의 합의 가격 결제가 성립 | 기존 예약을 주문으로 전환 | 확보한 수량을 다른 구매자와 다시 경쟁하지 않아야 함 |

여기서 성립은 버튼을 누르거나 요청을 보낸 순간이 아니라 서버에서 해당 거래 결과가 확정된 상태를 의미한다. 성공 응답은 이를 요청한 당사자에게 알려 주는 수단이다. 응답을 받지 못해도 서버에서는 결과가 성립했을 수 있다.

### 5.6 기본 거래 흐름

1. A는 유효한 예약을 바탕으로 결제를 진행한다.
2. B는 등록 가격으로 1대를 구매하려고 조회·입력·결제를 진행한다.
3. 판매자는 C·D의 제안 가격과 수량을 검토하고 응답한다.
4. C 또는 D는 자신의 수락·예약이 성립한 것을 확인한 경우 합의 가격 결제로 진행한다.
5. 필요한 수량을 구매한 사람은 이번 구매 목적을 달성한 것으로 본다.
6. 수량을 확보하지 못한 사람은 상품 상태, 실패 안내 또는 판매자의 안내를 통해 이번 시도의 결과를 확인한다.

위 목록은 거래를 설명하는 순서다. A의 결제가 끝나야 B나 판매자가 행동할 수 있다는 전역 순서를 뜻하지 않는다. 반드시 앞서야 하는 행동과 독립적으로 가능한 행동은 아래 「6. 행동의 선후 관계와 독립 관계」에서 구분한다.

## 6. 행동의 선후 관계와 독립 관계

여기서는 A·B·C·D에 등록 가격 구매자 E를 추가한 구성과, 채택한 취소 정책을 적용한 후속 흐름의 공통 행동 관계를 정한다. 모든 요청을 하나의 고정 순서로 실행한다는 뜻은 아니다. 구체적인 대표 장면은 17번 항목과 별도 비즈니스 시나리오 문서에 둔다.

거래가 성립한 순서와 요청을 보낸 순서를 구분한다. 독립적인 행동이 가능하다는 사실만으로 실제 서버 처리의 겹침을 단정하지 않는다. 클릭·요청 도착 순서에 따른 엄격한 선착순을 추가하지 않는다. 실행용 간격·동기화·도구 설정은 여기서 다루지 않는다.

### 6.1 반드시 성립해야 하는 선행 조건

| 후속 행동 | 필요한 선행 조건 |
|---|---|
| A·C·D의 최초 합의 가격 결제 | 해당 구매자의 수락과 유효 예약 성립, 구매자가 자신의 합의·예약 상태 확인 |
| B·E의 등록 가격 구매 시도 | 각자의 구매 의사와 수량·주문 정보 확인. 조회·입력 자체는 수량 확보가 아님 |
| 판매자의 다음 제안 검토 | 앞선 응답 결과를 확인한 뒤 다음 대화로 이동 |
| 주문 취소 | 해당 주문이 성립하고 발송 전 취소 가능한 상태. 구매 철회 또는 재구매 목적을 구분 |
| 합의 가격 주문의 재구매 목적 취소 후 재결제 | 취소와 같은 합의의 수량 보호가 성립하고, 구매자가 결과·조건·기한을 확인. 보호가 유효한 동안 같은 가격·수량으로 재결제 |
| 구매 철회 취소 후 다른 구매자의 후속 시도 | 취소·수량 복구·해당 구매 기회의 보호 종료 성립. 다른 구매자가 재방문·상품 조회·판매자 안내 등으로 현재 구매 가능 상태를 확인하고 구매 의사를 유지 |
| 재구매 보호 만료 후 다른 구매자의 후속 시도 | 보호 종료와 구매 가능 상태 확인. 자동 알림·자동 재시도가 있다고 가정하지 않음 |
| 결과 미확인 요청 이후의 추가 거래 판단 | 기존 요청의 저장된 결과 확인. 확인 부족 시 미확인으로 유지 |

판매자의 순차 검토는 채택한 행동 조건이며 화면의 강제 여부와 구분한다. C·D 중 어느 제안을 먼저 검토할지는 고정하지 않는다. 취소 버튼을 누른 시점이나 요청을 보낸 시점만으로 복구 수량이 다른 거래에 열렸다고 간주하지 않는다.

### 6.2 독립적으로 진행될 수 있는 행동

| 행동 조합 | 업무상 살펴볼 관계 |
|---|---|
| A의 예약 2대 결제와 B 또는 E의 등록 가격 1대 결제 | 각 주문의 수량 차감이 정확히 반영되고 A의 기존 예약이 보호되어야 함 |
| B·E의 등록 가격 구매 각 1대 | 새 확보 가능 수량이 2대이면 둘 다 성립 가능. D의 1대 예약 등으로 1대만 남으면 한 명만 성립 가능 |
| B 또는 E의 1대 구매와 C의 2대 제안 수락 | 새로 확보 가능한 2대에 합계 3대를 허용하지 않음 |
| B 또는 E의 1대 구매와 D의 1대 제안 수락 | 수량이 허용하면 둘 다 성립 가능. 다른 등록 가격 주문이 이미 성립했다면 그 수량도 반영 |
| A의 예약 결제와 판매자의 새 제안 수락 | A의 예약을 주문으로 전환해도 다른 구매자의 새 확보 가능 수량은 변하지 않음 |
| D의 예약 후 결제 준비와 B·E의 구매 시도 | D의 결제 완료를 기다릴 필요는 없지만 D의 유효 예약은 보호 |
| 취소 당사자의 행동과 다른 구매자의 조회·구매 판단 | 독립적으로 행동할 수 있으나, 다른 구매자가 취소 결과를 알고 있다고 가정하지 않음. 성립한 수량 복구와 보호 상태를 적용 |

A의 주문 전환은 남은 수량과 유효 예약 합계를 각각 2대 줄인다. 전환 시점과 무관하게 보호 공백이나 중복 계산을 허용하지 않는다. 판매자의 C·D 응답은 앞선 결과 확인을 선행하므로 서로 독립적인 동시 수락으로 구성하지 않는다.

### 6.3 결과에 따라 달라지는 후속 행동

- 수락·예약 성립을 확인한 구매자만 합의 가격 결제로 진행한다. 수락 실패 뒤 합의 가격 결제를 붙이지 않는다.
- B·E가 원하는 1대를 구매하면 그 구매는 종료한다. 취소되지 않은 주문에 불필요한 재구매를 추가하지 않는다.
- 수량 부족을 확인하면 이번 시도를 멈춘다. 이후 새 시도에는 구매 의사와 재방문 등 인지 계기가 필요하다.
- 구매 철회 취소가 성립하면 해당 구매 기회의 보호를 끝낸다. 별도 예약 해제까지 해야 철회가 완성되는 흐름으로 대체하지 않는다.
- 재구매 목적 취소가 성립하면 보호 조건·기한을 확인한 뒤 주소 수정 등 목적에 맞는 후속 행동과 재결제를 진행한다. 취소된 주문을 대신하는 재결제와 불필요한 중복 구매를 구분한다.
- 재구매 보호를 약속한 취소는 취소·수량 복구·보호가 함께 성립해야 한다. 보호 불가를 구매 철회로 자동 전환하지 않는다.
- 보호 중 구매 철회 또는 미결제 상태의 기한 종료 시 보호를 끝낸다. 이미 취소된 주문을 다시 취소하는 것으로 설명하지 않는다.
- 같은 합의의 반복 재구매 목적 취소는 최초 보호 기한을 연장하지 않는다. 기한 전에 성립한 재주문은 기한 경과만으로 취소하지 않는다.
- 결과 미확인은 성공·실패와 구분한다. 기존 결과 확인 없이 새 결제나 취소를 이어 가지 않는다.

### 6.4 행동 관계와 상세 정책·시나리오의 구분

11.1번 항목은 취소 정책의 내용과 근거를 정하고, 여기서는 그 정책에 필요한 행동 관계를 정한다. 대표 장면은 17번 항목과 별도 시나리오 문서에서 구체화한다. 취소 기능 수정은 시나리오 테스트의 선행 작업이며, 비즈니스 행동 순서에 코드 수정 작업을 끼워 넣지 않는다. 보호 기간의 실행값, 임시 점유·제안 유효기간 후보, 취소·환불의 잔액 정책은 여기서 추가 확정하지 않는다.

## 7. 가능한 결과와 수량 보장 기준

### 7.1 먼저 성립할 수 있는 대표적인 거래

출발점에서 A의 2대 예약을 제외하면 새로 확보할 수 있는 수량은 2대다.

| 수량 확보가 성립한 흐름 | 이후 결과 |
|---|---|
| C의 2대 예약이 먼저 성립 | B의 1대 결제와 D의 1대 예약은 수량 부족으로 성립할 수 없음 |
| B의 1대 결제와 D의 1대 예약이 성립 | C의 2대 예약은 성립할 수 없음 |

후자의 경우 B와 D 사이의 순서는 어느 쪽이 먼저여도 수량상 둘 다 성립할 수 있다. 두 요청이 겹쳤다는 이유만으로 반드시 하나를 실패시켜야 하는 것은 아니다.

이미 성립한 A의 예약은 보호한다. 새 결제와 새 수락 중 어느 기능에도 무조건적인 우선권을 추가하지 않는다. 먼저 성립한 수량 확보를 후속 처리가 반영하는 기준을 사용한다.

엄격한 클릭 순서·요청 도착 순서에 따른 선착순을 보장하기로 한 것은 아니다. 그러한 우선순위가 필요하다면 별도 정책으로 정해야 한다.

### 7.2 대표적인 정상 종료 상태

수량을 확보한 구매자가 결제 조건을 충족하고 구매 의사를 유지하여 결제까지 마쳤다면 다음 두 결과가 대표적이다.

| 종료 상태 | A | B | C | D | 총 판매 수량 |
|---|---:|---:|---:|---:|---:|
| C의 2대 예약이 성립한 흐름 | 2대 구매 | 구매하지 못함 | 2대 구매 | 구매하지 못함 | 4대 |
| B의 결제와 D의 예약이 성립한 흐름 | 2대 구매 | 1대 구매 | 구매하지 못함 | 1대 구매 | 4대 |

성공한 사람이 2명인지 3명인지 자체가 옳고 그름의 기준은 아니다. 거래 수량과 약속이 맞아야 한다.

예약만 받은 사람, 결제를 진행하지 않은 사람, 결과를 확인하지 못한 요청이 있다면 위 결말에 억지로 맞추지 않는다. 별도 진행 중·미확인 상태로 남긴다.

### 7.3 상품 수량의 일치

이번 첫 흐름에는 취소·재입고가 없으므로 다음 관계가 성립해야 한다.

**남은 수량 = 최초 4대 − 성립한 주문 수량의 합계**

**유효한 예약 수량의 합계 ≤ 정확하게 계산된 남은 수량**

결제에 사용한 예약은 결제 종료로 전환되어 같은 수량을 결제와 유효 예약 양쪽에 중복 계산하지 않아야 한다.

확장된 취소 흐름을 논의할 때 사용한 관계는 다음과 같다.

**남은 수량 = 최초 판매 수량 − 성공한 결제 수량 + 발송 전 취소로 복구한 수량**

현재 프로젝트의 환불은 수량을 복구하지 않는 규칙이다. 이 취소·환불 차이를 첫 흐름에 임의로 섞지 않는다.

### 7.4 예약 보호와 요청 내용의 보존

- A의 예약이 유효한데 다른 구매자의 거래 때문에 해당 수량을 잃어서는 안 된다.
- 예약 보호는 잔액·입력 등 모든 결제 조건을 무조건 충족한다는 뜻은 아니다.
- C가 2대를 제안했는데 1대만 남았다면 시스템이 제안 수량을 임의로 줄여 수락하지 않는다.
- 합의 가격 결제는 합의한 수량과 가격 조건을 따른다.
- 수량 부족으로 수락이 실패했다면 수락과 예약을 성공한 것으로 남기거나 안내해서는 안 된다.

### 7.5 금액과 주문의 일치

- 성립한 주문에는 해당 주문 수량과 적용 단가에 따른 결제액이 반영되어야 한다.
- 수량 부족으로 명확히 거절된 결제 요청에는 그 요청의 주문과 차감이 남지 않아야 한다.
- 같은 구매 목적을 달성했는데 시나리오가 다시 결제를 보내 불필요한 주문을 만들지 않는다.
- 이번 범위는 결제 성립까지다. 발송·배송·정상 수령·판매대금 지급까지 완료되었다고 해석하지 않는다.
- 프로젝트는 실제 자금 이동이 없는 회원 테스트 잔액을 사용한다. 여기서 금액은 해당 서비스의 주문·잔액 기록을 뜻한다.

## 8. 참여자별 결과 확인과 종료 상태

### 8.1 상태를 네 가지로 구분

| 상태 | 의미 | 취급 |
|---|---|---|
| 결제 성립 | 주문·금액·수량 반영 결과가 확인됨 | 해당 구매 목적 달성 |
| 수량 부족으로 거래 불성립 | 필요한 수량을 확보하지 못함 | 해당 요청의 주문·차감·예약이 남지 않아야 함 |
| 예약 중이며 미결제 | 수량은 보호되지만 주문은 아직 없음 | 진행 중 상태로 구분 |
| 결과 미확인 | 응답만으로 처리 결과를 알 수 없음 | 저장된 결과를 확인하기 전까지 성공·실패로 단정하지 않음 |

시나리오의 종료 기준은 각 구매자의 이번 구매 시도 결과가 확인된 상태다. 예약 중이거나 미확인인 요청이 남으면 미종결 부분을 명시한다.

### 8.2 누가 어떤 결과를 직접 받는가

- 등록 가격 결제의 성공·실패 응답은 결제를 요청한 구매자가 받는다.
- 제안 수락의 성공·실패 응답은 수락을 요청한 판매자가 받는다.
- 판매자의 수락 요청이 실패했다고 제안한 구매자가 그 실패를 즉시 알고 행동한다고 가정하지 않는다.
- 제안한 구매자는 자신의 대화에 반영된 수락·예약 상태, 상품 상태 또는 판매자의 안내를 통해 다음 행동을 판단한다.
- 구매 화면의 수량 부족 오류 후 최신 수량 재조회와, 모든 구매자가 이후 재고 회복을 자동으로 아는 것은 다른 문제다.

구매자는 자신에게 보이는 정보로 행동한다. 전체 결과를 판단하는 분석자는 이후 모든 관련 주문·예약·수량을 대조할 수 있지만, 그 전체 정보를 구매자가 이미 알고 있었다고 구성하지 않는다.

### 8.3 실패 후 재시도에는 계기가 필요함

기본안에서는 수량 부족을 확인하면 이번 시도를 멈춘다. 나중에 다시 행동하려면 상품 재방문, 판매자의 안내, 대화에서 확인한 상태 변화 등 인지 계기가 있어야 한다.

취소나 해제가 발생했다는 내부 사실만으로 모든 구매자가 동시에 재시도하지 않는다. 최신 수량을 다시 조회했더라도 이후 다른 거래가 먼저 수량을 확보하면 다시 실패할 수 있다.

자동 대기열, 재고 회복 자동 알림, 자동 수락, 자동 결제 재시도가 구현되어 있다고 가정하지 않는다.

### 8.4 결과 미확인과 재전송

현재 화면 코드에는 연결 실패나 서버 오류처럼 결과를 알 수 없는 경우를 구분하는 처리가 있다. 결제 결과를 확인하지 못하면 구매 내역을 먼저 확인하도록 안내한다.

다음은 구분해야 한다.

- 응답을 못 받았다고 결제가 실패했다고 단정할 수 없다.
- 같은 요청 식별자를 다시 사용한다고 중복 주문 방지가 보장된다고 가정할 수 없다.
- 기록을 조회하는 동작과 새로운 결제를 요청하는 동작은 다르다.
- 확인이 부족하면 미확인으로 남겨야 하며, 기대한 결말을 만들기 위해 재결제를 보내지 않는다.

### 8.5 판매 종료 후에도 응답 대기 제안이 남는다는 의미

상품의 판매 상태와 제안의 응답 상태는 별도로 관리된다.

예를 들어 D가 1대의 가격 제안을 보낸 뒤, 판매자가 그 제안에 응답하기 전에 A와 C가 각각 2대를 구매하여 상품이 판매 종료될 수 있다.

현재 구현은 판매 종료만을 이유로 D의 제안을 자동으로 거절로 바꾸지 않는다. 따라서 다음 두 상태가 함께 존재할 수 있다.

- 상품: 판매 종료.
- D의 제안: 아직 수락·거절한 기록이 없는 응답 대기(`PENDING`).

이는 D에게 계속 기다리라고 안내한다는 뜻이 아니다. 화면은 상품 상태와 제안 상태를 함께 판단하여 **판매 종료로 응답 불가**를 표시하고 수락·거절 버튼을 보여주지 않는다.

사람의 구매 시도가 끝났다는 사실과 제안 데이터가 거절로 바뀌었다는 사실은 같은 의미가 아니다. 시나리오를 끝내려고 제안 상태를 임의로 거절 처리하지 않는다.

현재 명세에서는 상품이 다시 판매 중으로 돌아오면 대기 제안에 다시 응답할 수 있다. 이 성질 때문에 제안 유효기간 논의가 추가로 필요해졌다. 해당 내용은 별도 정책 후보로 정리한다.

## 9. 결과를 해석하는 세 가지 범주

### 9.1 허용하면 안 되는 결과

어떤 후속 정책을 선택하더라도 지켜야 할 수량·금액·상태 보장이 깨진 경우다.

예시:

- 새로 확보 가능한 2대에 C의 2대 예약과 D의 1대 예약을 모두 허용함.
- A·B의 결제가 성립했는데 주문 수량 합계와 남은 수량이 맞지 않음.
- 유효한 A의 예약 수량을 다른 거래가 사용함.
- 수량 부족으로 명확히 거절한 결제 요청의 주문·차감이 남음.

이러한 결과는 구매 경험의 취향이나 취소 정책 선택의 문제와 구분한다.

### 9.2 현재 정책에서는 허용되지만 개선을 검토할 경험

대표적인 사례는 B가 수량을 확인하고 주문 정보를 입력하는 동안 C의 예약이 성립하여 마지막 결제가 거절되는 경우다.

현재 정책에서는 조회·입력이 수량 확보를 뜻하지 않으므로 허용되는 결과다. 그러나 구매자에게 바람직한 경험인지는 별도로 판단할 수 있다. 결제 준비 중 임시 점유는 이 경험을 바꿀 후보다.

### 9.3 채택한 취소 정책에 따른 판정

구매 철회 취소 후 A를 위한 새 예약이 남아 다른 사람의 구매를 제한하는 결과는, 수정 후 적용할 정책에서는 허용하지 않는다.

기존 일괄 재예약 구현에서는 가능한 결과였으나, 채택한 정책은 구매 철회 시 보호를 종료한다. 반면 명시적인 재구매 목적 취소 후 유효한 보호 기간 동안 다른 구매자의 확보를 제한하는 것은 허용한다. 정책 위반 여부와 동시 처리 문제의 원인 판정은 구분한다.

결과 미확인 상태는 위 범주로 성급히 분류하지 않는다. 저장된 사실을 충분히 확인하지 못했으면 판단을 보류한다.

## 10. 작업 002·003의 현재 위치

### 10.1 공통 비즈니스 맥락

결제와 제안 수락은 같은 상품의 한정된 수량을 주문 또는 예약으로 확보하는 행동이다. 기능이 다르다는 사실만으로 반드시 별개의 비즈니스 시나리오여야 하는 것은 아니다.

현재 기본안은 다음 과정으로 정의한다.

**구매자들의 독립적인 결제와 판매자의 순차적인 제안 수락이 같은 상품 수량에 영향을 주는 과정.**

이 안에는 여러 구매자의 결제와 여러 제안의 검토·수락이 들어간다.

### 10.2 수락 행동이 여러 번 있다는 것과 수락 처리의 겹침은 다름

판매자는 기본 행동에서 앞선 응답 결과를 확인한 후 다음 제안을 검토한다. 따라서 기본안은 수락끼리 서버에서 겹치도록 구성하지 않는다.

다음은 아직 확인하지 않았다.

- 판매자에게 앞선 결과를 기다리지 않고 다른 방에서 수락할 이유가 있는지.
- 해당 화면 동작에서 두 수락이 서버에 도달하여 처리되는 시간이 실제로 겹치는지.
- 그러한 상황이 일반적인 흐름인지, 별도로 설명해야 하는 상황인지.

따라서 이번 기본안을 작성했다고 작업 003의 동시 수락 상황까지 재현·검증한 것으로 설명해서는 안 된다. 발생 가능성을 부정한 것도 아니다.

### 10.3 최종 분리·통합에 관한 현재 판단

- 거래 설명의 범위는 구매자·판매자의 행동과 공통 수량을 기준으로 잡는다.
- 개별 경합의 원인 확인이 필요하면 요청 조합을 구분할 수 있다.
- 여러 수락을 같은 거래 흐름에 포함하는 데에는 근거가 있다.
- 여러 수락의 동시 처리를 기본 조건으로 강제할 근거는 아직 없다.
- 기존 작업 번호·문서·테스트 파일을 병합하거나 삭제한 것은 아니다.

## 11. 채택한 취소 정책과 별도 정책 후보

구매자의 구매 철회와 재구매 목적 취소를 분리하는 정책을 채택한다. 취소 후속 시나리오는 수정 후의 정책을 기준으로 구성하며, 시나리오 테스트 전에 취소 기능을 수정한다. 기존 구현 기록과 채택 정책, 구현 완료 여부를 구분한다.

판매자 취소·미발송 자동 취소에 관한 11.2번 항목의 후보는 별도 검토로 남긴다. 결제 준비 중 임시 점유와 제안 유효기간 역시 이번 결정으로 채택하지 않는다. 취소·환불의 잔액 정책은 이번 변경 범위에서 제외한다.

### 11.1 구매 철회와 재구매 목적 취소 — 채택 정책

#### 기존 구현과 수정 후 적용 기준

기존에 확인한 구현은 합의 가격 주문의 발송 전 취소 시 수량을 복구하고 같은 내용의 새 예약을 생성한다. 이 일괄 재예약 동작을 구매 의도에 따라 분리한다.

| 취소 의도 | 수정 후 적용할 동작 | 다른 구매자에게 미치는 영향 |
|---|---|---|
| 구매 철회 | 주문 취소와 수량 복구 후 해당 구매 기회의 수량 보호를 종료한다. 새 예약을 만들지 않으며 별도의 예약 해제를 추가로 요구하지 않는다. | 복구된 수량을 다른 거래가 확보할 수 있다. |
| 주소 수정 등 같은 조건으로 재구매 | 주문을 취소하고 수량을 복구하되, 같은 합의 가격·수량을 정해진 보호 기한까지 예약으로 보호한다. | 보호가 유효한 동안 해당 수량은 다른 거래에 열리지 않는다. |

취소의 기본 의미는 구매 철회로 둔다. 재구매 보호는 명시적인 재구매 의사가 있는 경우에 적용한다. 화면의 선택 방식과 API 및 저장 방식은 구현 단계의 구체화 사항이다. 예약의 유지란 업무상 보호의 연속성을 뜻하며, 기존 예약 행의 재활성화나 새 행 생성 중 하나를 이 문서에서 강제하지 않는다.

재구매 보호는 이 문서에서 논의한 합의 가격 주문을 대상으로 구체화한다. 등록 가격 주문에 새로운 재구매 예약 기능을 추가하는 정책까지 자동으로 확장하지 않는다. 등록 가격 구매자의 구매 철회는 수량을 복구하고 다른 구매 기회를 연다.

#### 보호 기한과 반복 취소

- 같은 합의의 첫 재구매 목적 취소가 성립할 때 보호 기한을 한 번 정한다.
- 같은 합의로 재결제한 뒤 다시 재구매 목적 취소를 해도 최초 보호 기한을 연장하지 않는다.
- 기존 문서의 20분은 잠정 설명값이다. 확정 기간이나 이용 적절성이 검증된 값으로 취급하지 않는다. 실행 전에 적용할 기간값을 명시한다.
- 보호 기한 전에 재결제가 성립하면 예약을 주문으로 전환한다. 기한이 지났다는 이유로 성립한 주문을 취소하지 않는다.
- 미결제 상태로 보호 기한이 끝나면 수량 보호를 종료한다.
- 보호 기간 중 구매 철회로 의사가 바뀌면 남은 기간과 관계없이 보호를 종료한다. 주문이 이미 취소된 상태라면 주문을 다시 취소하는 행동으로 설명하지 않는다.
- 보호 기한이 끝난 뒤에는 같은 합의라는 이유만으로 보호를 자동 연장하지 않는다.

첫 제안 수락 당시의 기한만 사용하면 주소 수정 시점에 재구매 시간이 없을 수 있으므로 첫 재구매 목적 취소를 기준으로 보호 기한을 정한다. 반복 취소마다 기간을 새로 주면 다른 구매자의 기회가 계속 제한되므로 연장하지 않는다.

#### 취소 성립과 결과 확인

재구매 보호를 약속한 취소가 성립했다면 주문 취소·수량 복구와 안내한 조건의 수량 보호가 함께 성립해야 한다. 보호할 수 없을 때 구매 철회로 자동 전환하여 주문만 취소하지 않는다. 취소한 구매자는 취소 결과와 보호 여부·보호 기한을 확인한 뒤 다음 행동을 결정한다.

구매 철회 취소는 취소 뒤 예약 해제를 별도로 실행해야 완성되는 흐름으로 대체하지 않는다. 다른 구매자는 취소의 내부 사실을 자동으로 아는 것으로 구성하지 않으며, 상품 재조회나 판매자의 안내 등 실제 인지 계기를 통해 다음 행동을 선택한다. 결과를 확인하지 못한 취소는 성공이나 실패로 단정하지 않는다.

### 11.2 판매자 취소와 미발송 자동 취소

#### 제안한 방향

| 취소 주체·상황 | 권고한 후보 |
|---|---|
| 판매자 취소 | 자동 재예약 없이 종료하고, 합의 가격으로 재거래하려면 양측 의사를 다시 확인 |
| 미발송 자동 취소 | 자동 재예약 없이 종료·반환하고, 재거래 여부는 당사자가 다시 판단 |

판매자가 취소한 뒤에도 같은 조건으로 다시 거래할 의사가 있는지 불분명하고, 미발송 자동 취소 후 재결제하면 이번에는 발송할 수 있는지 확인된 것이 아니므로 자동 재예약을 기본으로 두지 않는 방향을 권고했다.

자동 재예약을 없애면 취소당한 구매자의 재구매 기회가 줄어들 수 있다. 정책 선택 시 함께 고려할 불이익이며, 현재는 검토 후보로 남긴다.

#### 판매자 취소 기능의 필요성

판매자 취소는 포트폴리오에서 다양한 거래 상황을 다루기 위해 추가한 기능이다. 첫 구매 흐름에는 필수적이지 않으므로 프로젝트에서의 유지 여부를 별도로 검토할 수 있다.

기능 범위는 다음과 같이 정리한다.

- 판매자 취소를 필수 기능으로 고정하지 않는다.
- 현재 첫 거래 흐름에서는 제외한다.
- 프로젝트에서 실제로 삭제할지는 후속 기능 범위 결정이다.
- 실제 서비스에서 판매자 취소가 얼마나 일반적인지는 실제 취소 기록과 판매자·구매자의 경험을 조사해야 판단할 수 있다.

#### 수량 복구와 재판매 가능 여부

판매자 취소 사유가 파손이나 실물 수량 부족이라면 주문 수량을 복구했다는 이유만으로 다른 사람에게 다시 판매할 수 있다고 보면 안 된다. 반대로 미발송이라는 사실만으로 물품이 없다고 단정할 수도 없다.

현재 프로젝트는 상품 수정·판매 중단을 구현 범위에서 제외하고 있다. 첫 기본안은 물품 자체가 정상이고 판매 가능한 상황으로 한정한다. 파손·실물 부족을 포함하면 상품 판매 가능 상태와 수량 정정 정책이 추가로 필요하다.

미발송 자동 취소는 발송 기한 이후의 후속 상황이다. 이를 결제 직후의 수량 경합과 같은 시간대에 억지로 넣지 않는다.

### 11.3 결제 준비 중 짧은 수량 확보

#### 결제 준비 중 품절되는 상황

구매자는 구매 화면에서 수량이 있음을 보고 수량을 선택하고 정보를 입력했는데, 마지막 결제에서 수량이 없다는 안내를 받으면 좋지 않은 경험을 할 수 있다. 수량을 선택한 시점부터 결제 준비에 맞는 짧은 시간 동안 수량을 확보하는 방안을 검토 후보로 둔다.

#### 현재 정책과 후보의 차이

현재는 조회·입력이 수량 확보를 뜻하지 않는다. 그동안 다른 거래가 수량을 확보하여 결제가 거절되는 것은 현재 정책에서 허용되는 결과다. 정상적인 처리라는 판단과 구매 경험이 바람직하다는 판단은 구분한다.

임시 점유 후보를 채택하면 구매자에게 제공되는 보장은 다음처럼 달라진다.

**시스템이 임시 확보 성공을 확인한 뒤에는, 정해진 조건과 시간 동안 다른 거래가 그 수량을 가져가지 못한다.**

다른 사람의 구매를 제한하므로 이것도 업무상 예약의 한 종류다. 가격 제안 수락에 따른 예약과 목적·시작 시점·유지 시간이 다른 수량 확보로 구분한다.

#### 논의한 검토 조건

- 화면에서 숫자를 선택한 것만으로 확보가 성립하지 않는다. 시스템이 확보 성공을 확인해야 한다.
- 경쟁이 사라지는 것이 아니라 수량 확보를 결정하는 시점이 결제보다 앞당겨진다.
- 입력 중 수량을 잃는 경험을 줄이는 대신, 결제하지 않는 사람의 임시 점유 때문에 다른 구매자가 기다릴 수 있다.
- 이미 예약된 A의 2대를 결제 화면 진입으로 다시 점유하여 같은 수량을 중복 확보하지 않아야 한다.
- 페이지가 열린 동안 계속 유지하는 방식과 상한 시간이 있는 방식을 비교 후보로 둔다.

페이지가 열린 동안 점유를 유지하는 방식과 상한 시간을 두는 방식은 후속 비교 대상이다. 종료 방식과 구체적인 시간은 미정이다.

탭을 방치하면 수량이 계속 묶일 수 있다는 성질은 현재도 설명할 수 있다. 그 효과를 서비스가 어디까지 허용할지와 적절한 제한 시간은 별도의 정책 선택이다.

#### 수량 확보 종료 안내

기능을 채택한다면 수량 확보가 끝났다는 사실을 화면에서 알 수 있어야 한다. 그러나 별도의 알림 시스템이 반드시 필요하다고 결정한 것은 아니다.

수량 선택 항목 초기화, 화면 안내, 알림창 등은 안내 방식의 후보이며 아직 확정하지 않았다. 구매자가 수량 확보의 종료 사실을 알고, 계속 확보되어 있다고 오해하지 않도록 한다는 요구 수준으로 남긴다.

### 11.4 응답 대기 가격 제안의 유효기간

#### 유효기간이 필요한 상황

판매 종료 후에도 D의 제안이 응답 대기로 남고, 판매가 재개되면 다시 수락 대상이 될 수 있다. 오래된 가격·수량 제안을 언제까지 유효하게 볼 것인지 검토가 필요하다.

이 기간은 수락 후 예약의 유효기간과 다르다.

| 구분 | 목적 | 수량 점유 |
|---|---|---|
| 응답 대기 제안의 유효기간 | 판매자가 그 가격·수량 조건을 언제까지 수락할 수 있는지 정함 | 아직 점유하지 않음 |
| 수락 후 예약의 유효기간 | 수락된 구매자에게 수량을 보호해 주는 기간 | 점유함 |
| 결제 준비 중 임시 점유 시간 | 결제 준비 중의 수량을 한시적으로 확보하는 후보 | 기능 채택 시 점유함 |

기존 예약 기본값 20분을 제안 유효기간에도 그대로 적용할 이유는 없다.

#### 현재 코드에서 확인한 동작

- 가격 제안에는 작성 시각과 응답 시각이 저장된다.
- 확인한 제안 처리 코드에는 작성 후 경과 시간에 따른 만료 검사가 없다.
- 상품이 판매 중이고 제안이 응답 대기이면 다른 조건을 검사하여 수락을 진행한다.
- 응답 대기 제안이 남아 있으면 같은 대화에서 새 제안을 보내는 것을 막는다.
- 상품이 판매 중으로 돌아오고 예약 가능한 수량도 생기면 오래된 대기 제안이 다시 수락 대상이 될 수 있다.

따라서 구매자가 이미 다른 물건을 샀는데 판매자가 옛 제안을 수락하여 새 예약을 만드는 상황, 구매자가 조건을 바꾸고 싶지만 이전 제안 때문에 새 제안을 보내지 못하는 상황을 검토할 필요가 있다.

#### 후보로 남긴 정책 의미

- 제안을 언제까지 수락할 수 있는지 검토한다.
- 만료된 제안으로 새 예약을 만들지 않는 방향을 검토한다.
- 만료된 제안이 새 제안을 계속 막지 않도록 해야 한다.
- 판매 종료로 현재 응답할 수 없는 상태와 제안 자체가 시간상 만료된 상태를 구분한다.
- 기한 전에 구매 의사가 바뀌는 경우의 제안 철회도 관련 후보로 남긴다.

유효기간이 남았다고 구매자가 반드시 여전히 사고 싶다는 뜻은 아니다. 유효기간은 서비스가 수락을 허용하는 범위이고, 실제 구매 의사의 변화는 별도 문제다.

첫 시나리오는 구매 의사가 유지되는 동안의 거래로 두므로 이 기능을 먼저 구현할 필요는 없다. 오래된 제안의 처리와 제안 만료는 현재 기본 시나리오와 별도의 정책 검토 항목으로 유지한다.

### 11.5 실제 서비스 이용 기록과 이용자 의견이 없을 때 초기 기간을 정하는 방법

실제 서비스에서 수집한 접속·요청 기록, 제안에 응답하기까지 걸린 시간, 구매를 준비하는 데 걸린 시간, 이용자의 후기·불편 신고·인터뷰가 없어도 초기 기간을 정할 수 있다. 다만 그 값은 서비스 운영이나 이용자 경험으로 검증한 값이 아니라, 예상한 거래 상황에 맞춰 정한 초기값이라고 밝혀야 한다.

- 실시간 대화 중 협의하는 상황인지, 판매자가 나중에 접속해 답하는 상황까지 포함하는지 구체적으로 설명한다.
- 판매자에게 응답할 시간을 얼마나 주려는지, 오래된 제안을 언제까지 유지하려는지 등 기간을 정한 이유를 남긴다.
- 실제로 응답이나 구매 준비에 얼마나 걸리는지, 기한 때문에 거래를 놓치는 일이 얼마나 생기는지, 구매자·판매자가 어떤 불편을 겪는지는 아직 확인하지 못한 내용으로 구분한다.
- 테스트로 설정한 기한에 맞게 기능이 동작하는지는 확인할 수 있다. 하지만 그 결과만으로 해당 기간이 실제 거래에 알맞다고 판단하지 않는다.
- 이후 실제 접속·요청 및 거래 기록과 이용자의 후기·불편 신고·인터뷰가 쌓이면, 응답·구매 소요 시간과 기한으로 인한 불편을 살펴보고 기간을 조정한다. 요청량만으로 이용자의 경험까지 판단하지 않는다.

현재 제안 유효기간과 결제 준비 중 점유 시간은 미정이다. 재구매 보호 설명에서 사용한 20분도 실제 거래 기록이나 이용자 의견으로 적합성을 확인한 값은 아니다.

### 11.6 정책을 정할 시점과 실행 결과의 역할

정책 판단 기준은 실행 전에 마련하고, 실제 영향과 미검증 가정은 실행 결과를 바탕으로 검토한다.

1. 실행 전에 무엇을 보장해야 하고 어떤 결과를 잘못된 것으로 볼지는 정해야 한다.
2. 현재 코드·명세만으로 알 수 있는 동작의 차이는 지금 논의할 수 있다.
3. 정책 후보를 제안하는 것과 최종 선택·구현하는 것은 구분한다.
4. 실제 결과는 구성한 행동에서 어떤 영향이 나타나는지 판단하는 자료가 된다.
5. 결과가 어떤 정책을 선택해야 하는지 자동으로 결정해 주지는 않는다.
6. 시나리오 실행만으로 실제 이용자의 불편 빈도나 적절한 시간값까지 입증할 수는 없다.
7. 현재 정책의 결과와 아직 구현하지 않은 변경 후보의 결과를 한 실행에 섞어 설명하지 않는다.

### 14.3 후속 진행 순서와 규모 확장의 검토 방향

첫 구매와 취소 후속 흐름의 출발 상태·행동·결과 확인·허용 결과·근거를 정리한다. 그다음 취소 기능을 채택 정책에 맞게 수정하고, 수정된 기능을 대상으로 시나리오 테스트를 진행한다. 장시간 제안 대기는 별도 후속 상황으로 유지한다. 이번 문서 수정에는 코드 수정·테스트 명세 작성·테스트 실행을 포함하지 않는다.

대표 흐름을 정리한 뒤 규모를 확대할 때에는 한 상품에 구매 희망자가 더 몰리는 상황을 먼저 고려한다. 구체적인 수치는 아직 없다.

- 인원을 늘려 어떤 추가 현상을 보려는지 먼저 정한다.
- 구매자 수만 늘리지 않고 상품 수량과 전체 구매 희망 수량의 관계를 함께 고려한다.
- 상품 4대에 구매자만 크게 늘리면 대부분 품절 거절로 끝날 수 있다.
- 같은 상품의 판매자는 한 명이라는 행동 맥락을 유지한다.
- 모든 참여자를 같은 순간에 행동시키거나 판매자를 여러 명처럼 복제하지 않는다.
- 실제 서버 처리가 겹쳤는지는 관찰 결과로 구분한다.

확장 규모와 실행 방법은 위 기준을 바탕으로 별도 설계한다.

## 15. 후속 설계 기준

1. 최초 기본안은 **모니터 4대·판매자 1명·구매자 A·B·C·D**이며, 현재 확장 구성에는 등록 가격 1대 구매자 E를 추가한다. 5~8번 항목의 최초 기본 관계를 유지하고 17번 항목의 추가 관계를 적용한다. 중간의 7대 구성과 혼용하지 않는다.
2. 기존 002는 참고 자료이며 새 구성의 필수 설계 기준이 아니다.
3. 기본안의 구매자·판매자 행동을 유지하면서 확장한다. 경합을 만들기 위한 목적만으로 실제 거래에 근거가 없는 행동이나 정보를 추가하지 않는다.
4. 거래가 성립한 구매자에게 불필요한 재결제를 보내거나, 수락 실패한 구매자에게 합의 결제를 이어 붙이지 않는다.
5. 변경 전 구현 기록, 채택한 수정 정책, 지켜야 할 규칙, 미채택 후보를 명시적으로 나눈다.
6. 수량 오류와 정책상 허용되지만 불편한 경험을 구분한다.
7. 실제 이용자 근거가 없는 기간·비율·빈도는 가정으로 표시한다.
8. 현재 소스와 배포 상태가 달라졌을 수 있으므로 추가 분석 시 필요한 부분의 최신 상태를 확인한다.
9. 테스트 명세·실행 계획과 구현 변경은 후속 작업의 범위와 조건을 별도로 정한다.
10. 다음 단계는 대표 행동 순서와 결과 분기의 구체화이며, 규모 확장·실행 준비는 그 이후다. 기본안의 거래 구조를 유지하며, 변경이 필요하면 새 근거와 변경 범위를 기록한다.

## 17. 확장한 대표 흐름과 수정 후 취소 시나리오

### 17.1 유지 조건과 등록 가격 구매자 E

모니터 4대와 판매자 1명, A의 유효 예약 2대, B의 등록 가격 1대 구매, C의 2대 제안, D의 1대 제안을 유지한다. E는 등록 가격으로 1대를 구매하려는 독립적인 구매자로 추가한다. 총 구매 희망 수량은 7대다. 이는 4.2번 항목의 과거 7개 상품 구성과 다르다.

5~8번 항목은 최초 기본안의 관계를 설명한다. 확장 구성에서는 다음 결과를 추가 적용한다. 수량 외의 결제 조건이 충족되고 확보한 구매자가 결제를 마치는 경우의 결과다.

| 먼저 성립한 확보 관계 | 허용되는 구매 결과 |
|---|---|
| C의 2대 예약 | A 2대·C 2대. B·D·E는 확보 불가 |
| B·E의 등록 가격 주문 각 1대 | A 2대·B 1대·E 1대. C·D는 확보 불가 |
| D의 1대 예약 후 B·E가 남은 1대를 구매하려 함 | A 2대·D 1대·B 또는 E 1대. C와 다른 등록 가격 구매자는 확보 불가 |

B·E가 새로 확보 가능한 2대를 각각 1대씩 구매하는 경우에는 모두 성립할 수 있다. D가 1대를 먼저 예약한 경우에는 B·E 중 한 명만 남은 1대를 확보할 수 있다. 두 이름만 바뀌는 결과는 같은 흐름으로 취급한다. 판매자는 앞선 응답을 확인한 뒤 다음 제안을 검토한다. 요청 순서와 성립 순서를 구분하고 실제 서버 처리의 겹침은 단정하지 않는다.

A의 예약이 주문으로 전환되는 시점이 달라도 다른 구매자의 새 확보 가능 수량은 변하지 않아야 한다. 남은 수량과 유효 예약 수량에서 각각 2대가 빠지며, 보호 공백이나 중복 계산이 생겨서는 안 된다.

### 17.2 합의 가격 구매 철회 — 수량을 다른 거래에 반환

출발 상태는 A·C가 각각 2대의 결제를 마친 상태다. 남은 수량과 유효 예약은 모두 0대다. A에게 구매가 더 이상 필요하지 않은 사정이 생겨 발송 전 구매 철회 취소를 선택한다.

1. A의 구매 철회 취소가 성립하면 2대를 복구하고 A를 위한 수량 보호를 종료한다. 새 확보 가능 수량은 2대다.
2. A는 주문 취소와 보호 종료를 확인하고 구매를 끝낸다. 추가 예약 해제나 재결제를 요구하지 않는다.
3. B·E는 각각 상품을 재방문하여 구매 가능한 수량을 확인하고, 구매 의사가 유지되는 경우 등록 가격으로 1대씩 새 구매를 시도한다. 자동 재고 알림이나 자동 재시도가 있다고 가정하지 않는다.
4. 이 대표 흐름에서는 판매자가 D를 새로 수락하지 않은 동안 B·E의 주문이 각각 성립한다. 최종 취소되지 않은 주문 수량은 C 2대·B 1대·E 1대다.

C의 성립한 주문에는 영향이 없어야 한다. A의 철회 후 예약이 남아 복구 수량을 막거나, B·E 중 한 주문의 수량 차감이 누락되는 것은 불허한다. 다른 거래가 먼저 확보하면 그 결과를 반영하며 위 결말을 강제하지 않는다.

### 17.3 주소 수정 후 재구매 — 같은 합의의 수량 보호

출발 상태는 17.2번 항목과 같다. A는 구매 의사를 유지하며 배송 주소를 고치기 위해 발송 전 재구매 목적 취소를 선택한다.

1. 취소가 성립하면 A의 주문 2대를 복구하면서 같은 합의의 2대를 보호 기한까지 예약한다. 남은 수량은 2대, 유효 예약은 A 2대, 다른 구매자의 새 확보 가능 수량은 0대다.
2. A는 주문 취소, 보호 수량, 합의 조건과 보호 기한을 확인한다. 주소를 수정하고 기한 안에 같은 합의 가격·수량으로 재결제한다.
3. B·E가 재방문하더라도 해당 2대를 새로 확보할 수 없다. 상품의 남은 수량 2대와 자신이 구매할 수 있는 수량 0대를 구분한다. 각자 확인한 수량 부족 안내에 따라 멈춘다.
4. A의 재결제가 성립하면 예약을 주문으로 전환한다. 최종 취소되지 않은 주문은 A 2대·C 2대다.

이 재결제는 주소 수정이라는 목적이 있는 후속 행동이다. 취소되지 않은 주문에 불필요한 중복 구매를 붙이는 경우와 구분한다. 취소와 보호 사이에 다른 거래가 2대를 가져가거나, A의 재결제를 신규 수량 경쟁으로 취급하는 결과는 불허한다.

### 17.4 재구매 보호가 끝나는 분기

17.3번 항목에서 재결제하지 않은 채 보호 기한이 끝나면 예약 보호를 종료하고 2대를 다른 거래에 연다. A도 기한이 끝난 뒤 계속 보호받는다고 판단하지 않으며, 새 구매 판단 전에 현재 거래 상태를 확인한다. B·E의 후속 구매에는 재방문·상태 확인 등 인지 계기가 필요하다.

보호 기간 중 A가 구매를 철회하면 남은 기간과 관계없이 보호를 종료한다. 주문은 이미 취소되었으므로 보호 종료가 후속 행동이다. 재결제 후 다시 주소 수정 목적 취소를 하더라도 최초 보호 기한을 연장하지 않는다. 이들은 새 정책을 비교하는 후보가 아니라 채택한 보호 한계의 결과 분기다.

### 17.5 등록 가격 구매 철회와 남은 1대 경쟁

D의 1대 예약 뒤 B·E가 남은 1대 구매를 시도하여 B의 주문이 성립하고 E는 수량 부족을 확인한 상태를 둔다. A·D도 각자의 예약을 주문으로 전환한다. 이후 B가 발송 전 구매를 철회하면 1대가 복구되어 다른 거래에 열린다.

E가 상품 재방문으로 복구된 수량을 확인하고 여전히 구매하려는 경우 새 주문을 시도할 수 있다. 성공하면 최종 취소되지 않은 주문은 A 2대·D 1대·E 1대다. C의 2대 조건은 복구된 1대만으로 충족되지 않는다. 등록 가격 주문의 주소 수정용 예약 기능은 이 흐름에 추가하지 않는다.

### 17.6 적용 순서와 미완료 사항

취소 시나리오의 허용 결과는 11.1번 항목의 채택 정책을 기준으로 한다. 기존 일괄 재예약은 변경 전 구현 기록이며 수정 후 시나리오의 기대 결과로 사용하지 않는다.

진행 순서는 비즈니스 흐름 구체화, 취소 기능 수정, 수정된 기능을 대상으로 한 시나리오 테스트다. 정책 채택과 문서 반영은 구현·검증 완료를 뜻하지 않는다. 구체적인 보호 기간값, 화면·API·저장 방식은 구현 단계에서 구체화한다. 이번 문서 개정에는 코드 수정, 테스트 명세·실행 계획 작성, 테스트 실행을 포함하지 않는다. 취소·환불의 잔액 정책도 별도 범위로 유지한다.
