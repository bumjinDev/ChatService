## 1. 명세 내용

### 1.1 목적과 범위

기존 주문과 유효 예약이 있는 같은 상품에서, 판매자가 새 가격 제안을 수락하는 동안 여러 구매자가 등록 가격으로 결제한다. 기존 거래를 보호하면서 새 요청을 확보 가능한 수량 안에서 처리하는지 확인한다. 후보 기술을 각각 적용한 뒤 동일한 조건에서 정확성과 응답 시간, 필요한 내부 처리 비용을 비교하여 기술 선택의 근거를 마련한다. 후보 기술의 종류와 최종 선택은 이 초안에서 정하지 않는다.

기존 실행01에서는 수락과 결제가 각각 2개를 요구했고, 확보 가능한 수량 3개에서 둘 다 성공하여 전체 주문 5개와 유효 예약 6개가 판매 수량 10개를 넘었다. 정합성 오류의 존재는 이미 확인했다. 추가 부하 실험을 오류의 존재를 다시 입증하기 위한 필수 단계로 두지 않는다.

| 구분 | 내용 | 근거 |
|---|---|---|
| 포함 | 기존 주문 3개·유효 예약 4개가 있는 상품의 새 수락 1건과 다수 등록 가격 결제 | 작업명세 07의 거래 구성, 이번 논의 |
| 포함 | 충분·부족 수량 조건, 거래별 결과와 전체 수량·잔액·조회 결과 대조 | 작업명세 06의 1.3·1.5.3 |
| 포함 | 경합 종료 직후까지의 기존 거래 보호 확인 | 세부 작업 04와 동일한 업무 범위를 유지한다는 결정 |
| 제외 | 기존 예약 4개의 후속 결제 | 향후 고려 사항으로만 남긴다. 이번 절차·통과 조건·동시 요청 수에 포함하지 않는다 |
| 제외 | 취소·발송·환불, 예약 만료 경합, 중복 요청, 여러 상품 분산 | 이번 같은 상품 집중 시나리오 밖의 범위 |
| 제외 | 수락 건수의 비례 확대 및 수락 2~4건 추가 | 판매자의 수락 1건에 결제가 몰리는 장면으로 범위를 정함 |

기존 오류의 개선 전후 재현은 작업명세 07의 수락 1건·2개와 결제 1건·2개 조건을 사용한다. 이 문서의 결제 요청당 1개 조건으로 기존 실행을 대체하거나 동일 조건 비교라고 기록하지 않는다.

### 1.2 테스트 배경

상품에는 이미 주문 3개와 예약 4개가 있다. 기존 주문 구매자는 결제를 마쳤고, 기존 예약 구매자는 예약한 수량을 보호받는 상태다. 판매자는 별도의 새 흥정 구매자가 낸 2개짜리 제안을 수락하려 하며, 다른 구매자들은 같은 상품을 등록 가격으로 각각 1개씩 구매하려 한다.

새 수락과 결제가 상대방의 수량 확보를 반영하지 않은 채 진행되면 판매 수량을 넘는 거래가 성립하거나 기존 예약 몫이 침해될 수 있다. 정합성을 보완하는 기술을 적용한 뒤에는 대기나 충돌 처리 때문에 응답 시간이 늘어나는지도 함께 살펴본다. (구체적인 검토 대상과 추가 분석 범위는 테스트 결과를 확인한 뒤, 실제 문제가 드러난 부분을 중심으로 정한다.)

1. 서로 다른 회원과 새 상품을 준비하고 기존 주문 3개와 유효 예약 4개를 만든다.
2. 새 흥정 구매자는 수량 2개의 가격 제안을 등록하고, 새 등록 가격 구매자들은 결제에 필요한 잔액과 입력을 준비한다.
3. 판매자의 새 제안 수락 1건과 새 구매자들의 등록 가격 결제를 함께 보낸다.
4. 모든 요청의 서버 처리 종료를 확인한 뒤 기존 거래와 새 거래, 전체 수량과 잔액, 조회 결과를 대조하고 관찰을 종료한다.

| 참여자 | 목적과 행동 | 테스트에서 보내는 요청 |
|---|---|---|
| 판매자 | 새 흥정 구매자의 제안 2개를 수락 | 새 수락 1건 |
| 기존 주문 구매자 | 이미 구매한 3개의 거래 유지 | 준비 단계에서만 주문 생성. 경합 중 변경 요청 없음 |
| 기존 예약 구매자 | 이미 예약한 4개 유지 | 준비 단계에서만 제안 등록. 후속 결제 없음 |
| 새 흥정 구매자 | 제안한 2개를 예약받음 | 준비 단계에서 제안 등록. 경합 중 본인 결제 없음 |
| 새 등록 가격 구매자들 | 각자 상품 1개 구매 | 서로 다른 구매자마다 등록 가격 결제 1건 |

### 1.3 업무 규칙과 입력값

| 항목 | 적용할 내용·값 | 근거·확인 상태 |
|---|---|---|
| 기존 거래 | 기존 주문 1건·3개, 유효 예약 1건·4개 유지 | 작업명세 07에서 유지 |
| 새 수락 | 요청 1건, 제안 수량 2개. 기존 예약을 다시 수락하는 요청이 아님 | 이번 논의에서 확정 |
| 새 결제 | 구매자별 1건, 요청당 1개 | 이번 논의에서 확정. 기존 실행의 요청당 2개에서 변경 |
| 수량 처리 | 수락 요청은 2개 전부를 예약하거나 거절한다. 결제는 구매자별 요청 1건·수량 1개를 각각 처리하며, 확보 가능한 수량에 따라 전체 결제 요청 중 일부는 성공하고 일부는 거절될 수 있다 | 작업명세 06의 1.3 |
| 가격·잔액 | 등록 가격 10,000원, 제안 단가 9,000원. 기존 주문은 30,000원. 새 결제 구매자별 직전 잔액 10,000원 | 작업명세 07의 등록 가격 10,000원을 유지하고, 새 결제 구매자마다 1개를 결제할 수 있도록 10,000원을 미리 충전한다 |
| 기타 잔액 | 기존 주문 구매자는 준비 결제 후 0원, 기존 예약·새 흥정 구매자는 각각 0원 | 작업명세 07 유지. 예약은 결제가 아님 |
| 거래 규칙 | 예약 자체는 남은 수량을 줄이지 않음. 남은 수량은 최초 판매 수량에서 전체 주문 수량을 뺀 값 | 작업명세 06·07 |
| 조회 규칙 | 구매 가능 수량은 남은 수량에서 조회자 본인이 아닌 구매자들의 유효 예약 수량을 뺀 값 | 작업명세 07의 1.6.2 |
| 시간 조건 | 기존·새 예약이 결과 확인 시점까지 유효해야 함. 기존 주문의 자동 상태 변경이 개입하지 않아야 함 | 작업명세 07 유지. 실제 저장 기한과 서버 기준 시각으로 확인 |

새 등록 가격 구매자들은 각각 결제 요청 1건으로 상품 1개를 구매하도록 통일한다. 이는 실제 구매 수량을 재현하기 위한 값이 아니라, 구매자별 요청 수량 차이의 영향을 줄이고 결제 성공 건수와 확보된 상품 수량을 일치시켜 경합 결과를 쉽게 확인하기 위한 실험 조건이다. 판매자의 새 수락 요청은 별도로 정한 수량 2개를 유지한다.

동시 요청 합계를 N, 새 결제 요청 수를 K=N−1, 최초 판매 수량을 S로 표시한다. N과 K는 요청 건수이고 S는 상품 개수다. 새 요청이 확보하려는 총수량은 K+2=N+1개이며, 기존 거래를 제외하고 새로 확보할 수 있는 수량은 S−7개다.

| 동시 요청 합계 | 새 수락 | 새 결제 | 새 요청이 확보하려는 총수량 | 수량 충분 조건의 상품 등록 수량 | 수량 부족 조건의 상품 등록 수량 | 규모의 위치 |
|---|---|---|---:|---:|---:|---|
| 2건 | 1건·2개 | 1건·1개 | 3개 | 10개 | 9개 | 최소 경합 비교 기준 |
| 6건 | 1건·2개 | 5건·각 1개 | 7개 | 14개 | 10개 | 추가 후보 |
| 12건 | 1건·2개 | 11건·각 1개 | 13개 | 20개 | 13개 | 추가 후보 |
| 18건 | 1건·2개 | 17건·각 1개 | 19개 | 26개 | 16개 | 응답 시간 목표 평가 규모 |
| 24건 | 1건·2개 | 23건·각 1개 | 25개 | 32개 | 19개 | 추가 후보 |

판매 수량은 모두 제안값이다. 충분 조건은 새 요구량 전부를 수용하고, 부족 조건은 일부만 수용하도록 잡았다. 다섯 규모 전부의 실행을 확정한 것은 아니다. 추가 규모와 판매 수량은 기술 비교 설계 때 확정한다. 부족 조건의 재고도 규모에 따라 달라지므로 고정 재고에서 요청만 늘린 실험으로 해석하지 않는다.

요청 수는 실제 이용량 추정치가 아니라 평가를 위한 실험 조건이다. 18건은 작업명세 06에서 정한 초기 목표이며, 실제 서비스에서 18건이 동시에 발생한다는 근거로 사용하지 않는다.

### 1.4 테스트 시작 전 준비

- 시작 상태 확인 시점: 준비 처리 완료 후, 검증 대상 요청을 전송하기 직전.
- 실행 사이의 상태 관리: 매 실행마다 새 회원·상품·대화·거래를 준비한다. 실패한 상태나 이전 실행 결과를 다음 실행의 출발점으로 사용하지 않는다.
- 다른 실행·자동 처리의 영향: 대상 상품과 회원을 다른 실행이 변경하지 않게 분리한다. 실제 예약 만료와 주문 기한을 확인하고, 기간을 벗어난 결과를 정상 조건의 결과로 합치지 않는다.

| 대상 | 필요한 시작 상태·값 | 준비 방법 | 확인 방법 |
|---|---|---|---|
| 회원·인증 | 판매자와 K+3명의 구매자가 서로 다른 회원. 총 K+4명 | 새 회원 준비·로그인 | 역할별 회원 ID와 인증 확인 |
| 상품·대화 | 상품 1개, 최초 S개·판매 중. 구매자별 대화 1개씩 기본 K+3개 | 상품 등록 후 대화 생성 | 상품·판매자·구매자 연결 및 대화 수 대조 |
| 기존 주문 | 주문 1건·3개, 등록 가격·30,000원, 진행 중·발송 대기 | 30,000원 충전 후 결제 | 주문·잔액·변동 내역, 남은 수량 S−3 |
| 기존 예약 | 제안 수락 및 연결된 유효 예약 1건·4개 | 단가 9,000원·4개 제안 후 수락 | 예약 ID·연결·수량·상태·예약 및 만료 시각 |
| 새 흥정 제안 | 단가 9,000원·2개, 응답 대기. 아직 예약·주문 없음 | 제안 등록 | 제안·예약·주문 조회 |
| 새 결제 구매자 | 각각 잔액 10,000원, 기존 예약·주문 없음 | 충전, 유효한 가상 배송정보 준비 | 잔액과 대상 상품 거래 대조 |
| 출발 수량 | 전체 주문 3개, 유효 예약 4개, 남은 수량 S−3개, 비예약자 구매 가능 S−7개 | 준비 완료 후 조회 | API와 대상 상품 전체 DB 결과 대조 |

기존 주문·예약의 개별 필드와 잔액을 요청 전 기준값으로 저장한다. 합계만 저장하지 않는다. 준비 실패·조회 미확인·출발 상태 불일치가 있으면 검증 요청을 보내지 않는다.

| 미정·미확인 사항 | 영향을 받는 단계 | 실행 전에 필요한 결정·확인 |
|---|---|---|
| 후보 기술과 대상 버전 | 기술별 비교 전체 | 각 기술의 적용 범위·설정·재시도 및 실패 응답 정책 기록 |
| 판매 수량과 추가 규모 | 준비·예상 결과 | 제안값 채택 여부, 실제 실행할 조건 확정 |
| 반복 횟수·측정 건수 | 응답 시간 평가 | 기능·성공·수량 부족 거절별 집계 및 필요한 표본 설계. 각 10회는 확정값이 아님 |
| 대화 수 등 데이터 조건 | 부하 비교 | 같은 규모의 기술 간 동일하게 맞춤. 규모 간 대화 수를 고정할지 함께 늘릴지 결정하고 기록 |
| 동시 전송과 내부 관측 | 경합 확인 | 도구의 출발 제어·실제 전송 시각·처리 겹침 및 대기 관측 방법 |
| 환경·제한시간 | 실행·판정 | 배포 버전, DB 연결 설정, 타임아웃, 기한 여유, 로그 수준과 워밍업 조건 확인 |
| 오류 응답 계약 | 결과 분류 | 후보 구현의 정상 업무 거절과 기술적 충돌·타임아웃을 구분 |

### 1.5 테스트 절차와 단계별 기대 결과

#### 1.5.1 테스트 전체 흐름

| 단계 | 수행 주체·요청·입력 | 정상 응답과 동작 | 단계 종료 후 데이터·다음 단계 조건 |
|---|---|---|---|
| 1. 출발 확인 | 준비한 상품과 모든 참여자의 거래·잔액·기한 조회 | 1.4의 출발 상태 확인 | 전 항목 확인 뒤에만 동시 요청 준비 |
| 2. 새 거래 동시 요청 | 판매자 수락 1건·2개와 서로 다른 K명 구매자의 결제 각 1건·1개 | 충분 조건은 전부 성공. 부족 조건은 일부 성공·일부 수량 부족 거절. 성공 순서는 고정하지 않음 | 성공 수락은 유효 예약 1건·2개, 성공 결제는 구매자별 주문 1건·1개. 거절 요청에는 예약·주문·잔액 및 수량 차감이 남지 않음 |
| 3. 처리 종료 확인 | 요청별 응답 및 서버 완료 여부 확인 | 수락 성공 200, 결제 성공 201. 거절은 사유와 저장 결과를 함께 확인 | 응답 미확인은 서버 결과 확인 전까지 미확인으로 유지. 모든 처리 종료가 확인되어야 최종 집계 |
| 4. 전체 대조 및 종료 | 판매자 대화 상세, 구매자별 잔액·내역, 조회자별 상품 상세 및 전체 DB 조회 | 1.6의 개별·전체 결과 일치 | 증거와 결과를 보존하고 종료. 기존 예약자의 후속 결제 없음 |

기술 적용으로 잠금 대기나 재시도가 생겨도 이를 수량 부족 거절과 같은 결과로 합치지 않는다. 구체적인 허용 정책은 비교 설계에서 정한다. 가용 수량이 있는데 기술적 충돌로 종료된 요청을 정상 수량 부족 거절로 통과시키지 않는다.

#### 1.5.2 관찰과 중단

- 관찰 시점·대상: 출발 직전의 상태, 요청별 실제 판단·저장·확정·응답, 모든 처리 종료 후의 안정된 상태를 구분한다. 중간 로그와 종료 후 조회값을 동일 시점의 값처럼 합산하지 않는다.
- 확인할 관계: 주문과 유효 예약 합계가 최초 판매 수량 이내인지, 남은 수량이 전체 주문을 반영하는지, 응답·주문·예약·잔액이 일치하는지 확인한다. 기존 주문·예약은 요청 전 개별 값과 대조한다.
- 필요한 증거: 요청·응답 원본, 요청별 시각과 결과, API·DB 조회 원본, 실제 판단값과 처리 순서를 연결할 서버 로그. 구체적 수집 방법은 4장 및 실행 설계에서 확정한다.
- 실패: 수량 초과, 기존 거래 변경·침해, 부분 예약, 주문·잔액·남은 수량 불일치 등 규칙 위반. 빠른 응답으로 정합성 실패를 상쇄하지 않는다.
- 판정 불가: 준비 불일치, 일부 요청 미전송, 종료 미확인, 조회 누락, 만료 등 조건 이탈. 이미 확보한 위반 증거는 별도로 유지한다.
- 경합 확인: 동시 전송만으로 내부 처리가 겹쳤다고 단정하지 않는다. 기술이 의도적으로 직렬화한 경우에는 대기 등으로 동시 유입을 확인하며, 내부 변경이 순차였다는 이유만으로 검증 실패로 보지 않는다.
- 중단 후 처리: 추가 묶음 전송을 멈추고 진행 중 요청의 종료와 저장 상태를 확인한다. 변경 요청을 임의로 재전송하거나 증거 확인 전에 데이터를 지우지 않는다.

### 1.6 테스트 종료 후 기대 결과

- 종료 시점: 이번 묶음의 모든 수락·결제 처리가 끝나고 종료 후 대조가 완료된 때. 기존 예약 결제·취소·발송 등은 실행하지 않는다.
- 최종 조회 범위: 대상 상품의 모든 주문·예약·제안과 참여자의 잔액·변동 내역. 성공 응답에 나온 ID만 조회하지 않는다. 대화 상세의 최근 예약 한 건만 합산하지 않고 DB 전체 예약을 중복 없이 대조한다.

새 수락 성공 여부를 A(성공 1, 수량 부족 거절 0), 새 결제 성공 건수를 B로 둔다. 아래 계산은 기술적 오류나 결과 미확인이 없고 모든 예약이 유효한 정상 종료를 전제로 한다.

| 최종 확인 대상 | 기대 결과 | 확인 방법·증거 |
|---|---|---|
| 기존 주문·예약 | 동일 ID·주체·연결·수량·상태·시각 유지. 주문 3개, 예약 4개 | 요청 전 기준값과 종료 후 API·DB 대조 |
| 새 수락 | A=1이면 수락 제안과 유효 예약 1건·2개 연결. A=0이면 제안 응답 대기·새 예약 없음. 새 흥정 구매자의 주문 없음 | 제안·전체 예약·주문 조회 |
| 새 결제 | 성공한 구매자마다 등록 가격 주문 정확히 1건·1개·10,000원·진행 중·발송 대기. 거절 구매자의 주문 없음 | 응답 주문과 전체 주문 대조 |
| 잔액·내역 | 성공 구매자 0원, 거절 구매자 10,000원. 성공 주문마다 결제 차감 10,000원 1회. 기타 구매자의 잔액은 직전 값 유지 | 잔액 및 주문 연결 변동 내역 |
| 전체 주문 | 1+B건, 수량 3+B개 | 전체 주문 합산 |
| 전체 유효 예약 | 1+A건, 수량 4+2A개 | 유효 조건·식별자 중복 제외 후 전체 예약 합산 |
| 전체 수량 | 7+B+2A ≤ S. 남은 수량 S−3−B개 | 상품과 전체 거래 대조 |
| 상품 상태 | 이번 제안 조건에서는 판매 중. 남은 수량에 기존 예약 몫이 포함되어 있음 | 상품 조회·DB |
| 비예약자 구매 가능 수량 | S−7−B−2A개 | 새 등록 가격 구매자 인증으로 조회 |
| 기존 예약 구매자 구매 가능 수량 | S−3−B−2A개 | 기존 예약 구매자 인증으로 조회 |
| 새 흥정 구매자 구매 가능 수량 | S−7−B개 | 새 흥정 구매자 인증으로 조회 |

### 4.2 요청과 실행 제어

아래 요청은 작업명세 07의 4장에 정리된 계약을 기반으로 수량을 조정한 초안이다. 후보 기술 적용 후 실제 응답 계약을 확인한다. 서버 접속 주소·문맥 경로·인증정보는 실행 설정으로 분리한다.

| 동작·적용 단계 | 요청·입력 또는 실행 방법 | 정상 응답·종료 확인 |

| 수량 부족 거절 | 수락 RESERVATION_QUANTITY_EXCEEDED, 결제 PRODUCT_RESERVED 및 HTTP 409를 기존 기준으로 참조 | 코드·사유·데이터 무변경 함께 대조. 모든 409를 같은 정상 거절로 분류하지 않음 |
| 출발 제어 | N개 요청의 입력·인증 준비 완료 후 한 묶음으로 출발 | 실제 전송 수·시각 기록. 구체적인 도구 설정 미정 |
| 종료 후 조회 | 상품 상세, 판매자의 대화 상세, 구매자별 잔액·내역 및 대상 상품 전체 DB 읽기 전용 조회 | 모든 요청 종료 뒤 동일한 유효 기간 안에서 1.6 대조 |

실행·요청 로그 식별자를 준비 요청과 검증 요청에 구분해 부여한다. 본문의 requestId만으로 중복 요청 방지가 보장된다고 가정하지 않는다. 인증 토큰·비밀번호·실제 개인정보는 공개 기록에 포함하지 않는다.

잠금·재시도 등을 적용한 뒤에는 모든 요청을 같은 내부 지점까지 도달시킨 후 풀어 주는 중지 방식이 가능한지 다시 확인한다. 선행 요청이 자원을 보유해 후행 요청이 도달하지 못할 수 있으므로 기존 중지 방식을 그대로 적용하지 않는다. 기본 성능 비교에서는 이러한 인위적 중지를 사용하지 않는다.
