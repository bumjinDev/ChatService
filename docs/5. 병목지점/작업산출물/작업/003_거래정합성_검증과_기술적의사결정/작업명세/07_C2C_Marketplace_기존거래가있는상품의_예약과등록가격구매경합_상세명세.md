## 1. 명세 내용

### 1.1 목적과 범위

이미 주문과 예약이 성립한 상품에서 판매자의 새 가격 제안 수락과 다른 구매자의 등록 가격 결제가 함께 진행될 때, 기존 거래를 보호하면서 확보 가능한 수량 안에서만 새 거래가 성립하는지 확인한다.

기존 주문 구매자는 구매를 마쳤고, 기존 예약 구매자는 합의 가격으로 구매할 수량을 보호받고 있다. 이 상태에서 판매자는 다른 흥정 구매자의 가격 제안을 수락하려 하고, 별도의 구매자는 등록 가격으로 구매하려 한다. 두 새 요청 사이에는 업무상 선후 관계가 없으므로 함께 보낼 수 있다. 요청 시점을 맞추는 것은 경합을 관찰하기 위한 실험 조건이며 실제 이용 빈도를 재현한다는 뜻은 아니다.

대상은 새 수락 1건과 새 등록 가격 결제 1건이다. 기존 예약자의 결제, 취소·발송·환불, 예약 만료와의 경합, 같은 구매자의 중복 요청은 포함하지 않는다. 예약–예약과 등록 가격 구매–등록 가격 구매로의 확장은 별도 테스트케이스로 구성한다.

서버 처리를 멈추지 않는 동시 요청을 기본으로 한다. 특정 일시 중지 기능의 사용을 전제로 하지 않는다. 필요한 처리 관계가 관찰되지 않으면 결과를 검증 미완료로 남기고 후속 관측이나 통제 실행을 설계한다. 기술적 해결책은 이 명세에서 선택하지 않는다.

### 1.2 입력값과 참여자

이 명세에서는 작업명세 06의 수량 예시를 아래 실행 조건으로 구체화한다. 가격과 잔액은 계산과 대조를 위한 실험용 값이며 실제 거래 데이터가 아니다.

| 항목 | 값 |
|---|---|
| 상품 | 실행마다 새 상품 하나, 판매 수량 10개 |
| 등록 가격 | 개당 10,000원 |
| 가격 제안 | 기존 예약 구매자와 새 흥정 구매자 모두 개당 9,000원 |
| 기존 주문 | 등록 가격으로 3개, 결제 금액 30,000원 |
| 기존 예약 | 기존 예약 구매자에게 4개 |
| 새 수락 요청 | 새 흥정 구매자의 가격 제안 2개 수락 |
| 새 결제 요청 | 새 등록 가격 구매자가 2개 결제, 결제 금액 20,000원 |
| 대화 | 구매자 네 명과 판매자 사이에 상품별 대화 하나씩, 총 4개 |

| 참여자 | 준비 행동 | 경합 직전 잔액 | 검증 대상 행동 |
|---|---|---:|---|
| 판매자 | 상품 등록, 기존 예약 구매자의 제안 수락 | 결제 판단 대상 아님 | 새 흥정 구매자의 제안 2개 수락 |
| 기존 주문 구매자 | 30,000원 충전 후 3개 결제 | 0원 | 없음 |
| 기존 예약 구매자 | 4개 가격 제안 후 수락받음. 충전하지 않음 | 0원 | 없음 |
| 새 흥정 구매자 | 2개 가격 제안. 충전하지 않음 | 0원 | 판매자의 수락 결과를 확인 |
| 새 등록 가격 구매자 | 20,000원 충전 | 20,000원 | 등록 가격으로 2개 결제 |

다섯 참여자는 모두 서로 다른 새 회원으로 준비한다. 실행마다 회원·상품·대화를 새로 만들고 이전 실행 데이터는 지우거나 다시 사용하지 않는다. 회원 정보, 상품명, 요청 식별 정보에는 실행을 구분할 수 있는 값을 넣는다. 수령인과 배송 주소는 유효한 형식의 가상 데이터만 사용한다.

### 1.3 실행 환경과 사전 조건

실행 전에 서버의 배포 코드 버전, 적용 설정, DB 종류·버전, DB 연결 최대 수, 테스트 도구 버전과 실행 장비를 기록한다. 로컬 설정값을 배포 서버의 적용값으로 간주하지 않는다.

처리 기준 시각은 고정하지 않는다. 기존 테스트 지원 설정이 켜져 있더라도 요청 일시 중지나 시각 고정이 이번 실행에 적용되지 않는지 확인한다. 이를 위해 서버 전체의 테스트 지원을 임의로 끄지는 않는다. 기존 일시 중지 지점의 위치에 맞춰 이번 시나리오를 바꾸지 않는다.

다른 실행에서 이번 회원과 상품을 변경하지 않도록 한다. 인증이 유효하고, 기존 예약의 실제 만료 시각과 기존 주문의 발송 기한을 확인할 수 있어야 한다. 로컬 예약 기간은 20분으로 설정되어 있지만, 실행에서는 저장된 예약의 실제 만료 시각을 기준으로 판단한다.

실행 파일의 기본 제한값은 다음과 같이 둔다. 성능 목표가 아니라 실행을 무한히 기다리지 않기 위한 제한이다. 적용값을 실행 기록에 남긴다.

| 항목 | 값과 처리 |
|---|---|
| 서버 연결 대기 제한 | 요청별 5초. 테스트 도구에서 서버로 연결하는 시간이며 DB 연결 대기와 구분 |
| 응답 대기 제한 | 요청별 30초. 초과하면 응답 미확인으로 기록하며 서버 실패로 단정하지 않음 |
| 검증 요청 준비 대기 | 두 요청이 모두 준비될 때까지 최대 10초. 모이지 않으면 준비 실패로 종료하고 준비된 요청만 보내지 않음 |
| 예약·주문 기한 여유 | 검증 요청 직전 기존 예약 만료와 기존 주문 발송 기한까지 각각 5분 이상 남아 있어야 함 |

기한 여유는 결과 확인 시간을 확보하기 위한 실험 운영 조건이다. 5분 안에 결과 확인이 보장된다는 뜻은 아니므로, 확인 시점에도 만료 여부를 다시 검사한다. 서버 처리 기준 시각과 결과 확인 시각의 출처를 기록한다. 시계 차이로 유효 여부를 판단할 수 없으면 추정으로 통과시키지 않는다.

### 1.4 준비 순서와 요청 전 확인

준비 요청은 순차 실행한다. 각 단계의 응답과 저장 상태가 확인된 뒤 다음 단계로 진행한다. 데이터 변경 요청은 자동 재시도하지 않는다.

| 순서 | 행동 | 다음 단계로 진행할 조건 |
|---|---|---|
| 1 | 다섯 회원 가입과 로그인 | 서로 다른 회원이며 모든 인증 결과를 확인함 |
| 2 | 판매자가 10개 상품 등록 | 최초·남은 수량 10개, 등록 가격 10,000원, 판매 중 |
| 3 | 구매자 네 명이 상품의 대화를 각각 시작 | 구매자별 대화 하나, 총 4개이며 상품·판매자와 연결됨 |
| 4 | 기존 주문 구매자에게 30,000원 충전 후 3개 결제 | 주문 한 건 3개, 등록 가격·30,000원 결제, 잔액 0원, 남은 수량 7개 |
| 5 | 새 등록 가격 구매자에게 20,000원 충전 | 잔액 20,000원, 이 구매자의 주문 없음 |
| 6 | 기존 예약 구매자가 개당 9,000원으로 4개 제안 | 응답 대기 제안 한 건, 아직 예약 없음 |
| 7 | 판매자가 기존 예약 구매자의 제안을 수락 | 제안 수락과 같은 구매자의 예약 4개가 연결됨. 남은 수량 7개 |
| 8 | 새 흥정 구매자가 개당 9,000원으로 2개 제안 | 응답 대기 제안 한 건, 새 예약과 주문 없음 |
| 9 | 네 구매자의 거래·잔액과 상품을 조회하고 전체 DB 상태 대조 | 아래 출발 상태가 모두 일치함 |

기존 예약을 만드는 단계는 준비 처리이고 검증 대상 수락이 아니다. 기존 주문을 만드는 결제도 검증 대상 결제와 구분한다. 준비 중 가격 제안 등록이나 수락이 실패하면, 단순히 해당 단계만 다시 보내지 말고 기존 처리 결과부터 확인한다.

| 출발 상태 | 기대값 |
|---|---|
| 상품 | 최초 수량 10개, 남은 수량 7개, 판매 중 |
| 전체 주문 | 기존 주문 구매자의 주문 한 건 3개, 결제 금액 30,000원, 진행 중·발송 대기 |
| 전체 예약 | 기존 예약 구매자의 유효 예약 한 건 4개 |
| 가격 제안 | 기존 예약 구매자의 4개 제안은 수락, 새 흥정 구매자의 2개 제안은 응답 대기 |
| 다른 구매자의 거래 | 새 흥정 구매자와 새 등록 가격 구매자에게 예약·주문 없음 |
| 기존 예약 구매자의 상품 상세 | 남은 수량 7개, 구매 가능 수량 7개 |
| 새 등록 가격 구매자의 상품 상세 | 남은 수량 7개, 구매 가능 수량 3개 |
| 잔액 | 기존 주문 구매자·기존 예약 구매자·새 흥정 구매자 각각 0원, 새 등록 가격 구매자 20,000원 |

기존 주문·예약·가격 제안의 식별 정보와 수량·상태·주체·연결 관계·시각, 각 구매자의 잔액을 요청 전 기준값으로 저장한다. 기존 예약의 만료 시각과 주문의 발송 기한도 저장한다. 합계만 저장하지 않는다.

준비 완료 표시는 이번 실행의 출발 상태를 모두 확인한 뒤에만 설정한다. 준비가 실패하거나 읽지 못한 항목이 있으면 검증 요청을 차단한다. 이전 실행의 준비 완료 표시와 결과값을 이어받지 않는다. 마지막 확인 이후 상태가 달라졌거나 기한 여유가 부족하면 새 실행으로 다시 준비한다.

### 1.5 검증 대상 요청

판매자의 새 제안 수락과 새 등록 가격 구매자의 결제를 하나의 동시 요청 묶음으로 구성한다. 두 요청이 필요한 입력과 인증을 갖추고 준비된 뒤 출발을 맞춘다. 준비가 끝나지 않은 상태에서 일부 요청만 출발시키지 않는다.

| 요청 | 요청자와 입력 | 횟수 |
|---|---|---:|
| 새 가격 제안 수락 | 판매자가 새 흥정 구매자의 응답 대기 제안 2개를 수락 | 1회 |
| 새 등록 가격 결제 | 새 등록 가격 구매자가 해당 상품 2개를 등록 가격으로 결제 | 1회 |

각 요청의 전송 시작과 응답 수신 완료 시각, 두 전송 시작 시각의 차이를 기록한다. 전송 시각이 가깝다는 사실만으로 서버 내부 처리가 겹쳤다고 판단하지 않는다. 이 실행에서는 로그인·충전·다른 조회를 의도적으로 경합 요청 사이에 추가하지 않는다.

응답은 성공·수량 부족·기타 오류·미확인으로 분류한다. 분류와 업무 규칙 충족은 별도로 판단한다. 이 출발 상태에서 허용되는 거절 사유는 새 수락의 예약 가능 수량 부족 또는 새 결제의 구매 가능 수량 부족이다. 판매 종료나 상품 자체의 남은 수량 부족 응답은 넓은 의미의 수량 부족으로 분류하더라도, 이번 예상 상태와 다른 사유로 별도 기록하고 원인을 조사한다.

두 요청을 모두 보낸 뒤 결과와 서버 처리를 확인한다. 시간 초과나 오류 응답을 받았다는 이유로 같은 변경 요청을 다시 보내지 않는다. 결제 저장이 끝난 뒤 응답 생성에서 오류가 발생할 수도 있으므로 오류 응답도 저장 상태와 대조한다.

### 1.6 종료 후 확인과 전체 상태 대조

정상 응답이 모두 끝나면 종료 후 조회를 시작한다. 결과가 미확인인 요청은 서버의 완료 여부를 로그와 DB로 확인하기 전까지 최종 상태로 판정하지 않는다. 조회 시각과 진행 중 여부를 남기고, 증거가 확보되지 않으면 해당 실행의 전체 판정은 미완료로 둔다.

판매자의 대화 상세 네 건과 구매자별 잔액을 조회한다. 기존 예약 구매자와 새 등록 가격 구매자의 인증으로 상품 상세를 각각 조회한다. 그 뒤 대상 상품의 전체 주문·예약·가격 제안과 해당 구매자의 잔액·잔액 변동 내역을 DB에서 읽기 전용으로 대조한다. 모든 조회의 시각을 남기고, 조회 중 만료나 다른 상태 변화가 발생하면 서로 다른 시점의 값을 하나의 상태로 합치지 않는다.

대화 상세 응답은 해당 구매자의 가장 최근 예약 한 건만 제공한다. 따라서 네 대화의 예약 합계만으로 중복 예약이 없다고 결론 내리지 않는다. DB에서는 대상 상품의 모든 예약을 확인하고, 동일 예약 식별 정보는 한 번만 합산한다. 전체 DB 대조를 하지 못했다면 API에서 확인된 결과는 남기되 전체 정합성 확인은 미완료로 둔다.

#### 1.6.1 허용되는 종료 상태

| 항목 | 새 수락 성공·새 결제 거절 | 새 수락 거절·새 결제 성공 |
|---|---:|---:|
| 전체 주문 건수와 수량 | 1건, 3개 | 2건, 5개 |
| 전체 유효 예약 건수와 수량 | 2건, 6개 | 1건, 4개 |
| 상품 남은 수량 | 7개 | 5개 |
| 상품 상태 | 판매 중 | 판매 중 |
| 새 등록 가격 구매자 잔액 | 20,000원 | 0원 |
| 기존 주문 구매자 잔액 | 0원 | 0원 |
| 기존 예약 구매자·새 흥정 구매자 잔액 | 각각 0원 | 각각 0원 |
| 기존 예약 구매자가 보는 구매 가능 수량 | 5개 | 5개 |
| 새 등록 가격 구매자가 보는 구매 가능 수량 | 1개 | 1개 |

위 표는 요청 전 조건이 유지되고 정상적으로 처리가 끝났을 때의 두 허용 결과다. 어느 요청이 성공해야 하는지는 고정하지 않는다. 새 수락과 새 결제가 모두 성공하면 기존 주문 3개·기존 예약 4개·새 예약 2개·새 주문 2개가 합계 11개이므로 수량 초과다. 다른 오류나 만료 없이 둘 다 수량 부족으로 거절됐다면, 새로 확보 가능한 3개를 사용하지 못한 판단을 조사한다.

#### 1.6.2 개별 거래의 결과 확인 기준

- 기존 주문은 요청 전과 같은 주문이며 구매자·판매자·상품·수량 3개·단가 10,000원·결제 금액 30,000원·진행 중·발송 대기 상태를 유지한다.
- 기존 예약은 같은 예약이며 구매자·상품·대화·가격 제안의 연결, 수량 4개, 예약 중 상태, 예약 시각과 만료 시각을 유지한다. 해제나 주문 전환이 없어야 한다.
- 새 수락이 성공하면 새 제안은 수락 상태이고, 새 흥정 구매자에게 그 제안과 연결된 예약 한 건 2개가 존재한다. 상품·대화·주체가 일치하고 확인 시점에도 유효해야 한다.
- 새 수락이 거절되면 새 제안은 응답 대기이고 새 흥정 구매자의 예약과 주문은 없다. 일부 수량만 예약하지 않는다.
- 새 결제가 성공하면 새 등록 가격 구매자의 주문이 정확히 한 건 생기며 수량 2개·등록 가격·단가 10,000원·결제 금액 20,000원·진행 중·발송 대기여야 한다. 응답의 주문과 저장된 주문이 일치해야 한다.
- 새 결제가 거절되면 해당 구매자의 주문은 없고 잔액은 요청 직전의 20,000원 그대로다. 실패한 요청의 수량 차감도 남지 않아야 한다.
- 결제에 따른 잔액 감소는 요청 직전 잔액에서 계산하고, 주문과 연결된 잔액 변동 내역이 금액·횟수와 맞는지 확인한다. 준비 단계의 충전·기존 결제 내역과 검증 대상 결제 내역을 구분한다.
- 전체 주문 수량과 유효 예약 수량의 합은 최초 10개를 넘지 않는다. 상품의 남은 수량은 10개에서 전체 주문 수량을 뺀 값이다. 유효 예약은 예약 중이면서 확인 기준 시각보다 만료 시각이 뒤인 예약이다.
- 구매 가능 수량은 상품의 남은 수량에서 조회자 본인이 아닌 구매자의 유효 예약 수량을 뺀 값이다. 조회 결과는 해당 조회자의 인증과 함께 대조한다.

조회에 실패한 것을 주문·예약이 없는 것으로 처리하지 않는다. 만료 시각이 지나 예약 합계가 줄었다면 이를 정상 수량으로 통과시키지 않고, 시간 조건을 벗어난 확인으로 표시한다. 이미 확보한 규칙 위반 증거는 별도로 보존한다.

### 1.7 경합 여부와 원인 확인

두 요청 각각에 대해 수량 판단에 실제 사용한 남은 수량·유효 예약 합계·구매 또는 예약 가능 수량·판단 기준 시각·판단 결과를 확인한다. 로그를 위해 다시 조회한 값을 당시 판단값으로 대체하지 않는다.

관찰하려는 관계는 두 요청이 상대 요청의 새 확보 결과를 반영하기 전에 각각 2개를 확보할 수 있다고 판단하고, 그 뒤 저장을 진행하는지다. 수량 조회·저장 처리·DB 확정·응답을 구분해 요청별 흐름을 연결한다. 저장 처리 로그 하나로 거래 성립을 확정하지 않는다.

애플리케이션의 완료 로그는 DB 확정 이후에 남으므로, 서로 다른 요청의 완료 로그 출력 순서만으로 DB의 정확한 확정 순서를 단정하지 않는다. 원인 설명에 필요한 선후 관계는 DB 기록 등과 대조하고, 판단할 수 없는 부분은 미확인으로 남긴다.

| 관찰 결과 | 처리 |
|---|---|
| 규칙 위반을 확인했고 로그로 발생 과정도 설명 가능 | 위반과 근거를 기록한다. 기존 일시 중지 기능을 추가 사용하기 위해 다시 실행하지 않는다 |
| 결과는 허용 범위이고 필요한 처리 겹침도 확인 | 해당 조건에서 규칙을 지킨 실행으로 기록한다 |
| 결과는 허용 범위이나 실제 처리는 순차 진행 | 순차 결과는 기록하되 경합 검증은 미완료로 둔다 |
| 내부 처리 순서를 확인할 자료가 부족 | 필요한 관측부터 정하고, 처리 순서 통제가 필요하면 후속 실행을 별도로 설계한다 |

후속 통제 실행에서는 확인할 처리 관계에 맞는 방법을 선택한다. 기존 중지 지점은 적합할 때만 사용하고, 적합하지 않으면 요청 순서 조절이나 다른 관측·중지 방법을 설계한다. 인위적으로 중지한 실행은 성능 목표 평가에서 제외하며 중지 시간만 빼서 정상 응답 시간으로 보정하지 않는다.

### 1.8 반복과 응답 시간 기록

첫 실행 한 회로 준비·요청·결과 확인이 명세대로 동작하는지 확인한다. 자료를 제대로 확보했고 추가 관찰이 필요한 경우 동일 조건으로 최대 두 회를 더 수행하는 초기 3회 구성을 사용한다. 각 회는 새 회원과 상품으로 독립 실행한다. 이 횟수는 실행 구성을 확인하기 위한 값이며 결함 발생률이나 성능 백분위를 평가하기 위한 표본 수가 아니다.

준비 실패나 조회·관측 부족이 있으면 동일 실행을 무작정 반복하지 않고 그 문제부터 보완한다. 명확한 위반과 충분한 근거를 얻었다면 남은 회차를 반드시 채우지 않아도 된다. 3회에서 필요한 겹침을 확인하지 못하면 반복 횟수만 늘리지 않고 후속 관측 방법을 정한다. 위반이 없는 반복 결과도 모든 실행의 안전성을 증명하지 않는다.

수락과 결제의 요청 전송 시작부터 응답 본문 수신 완료까지를 각각 기록한다. 준비·로그인·종료 후 조회·동시 출발 대기 시간은 검증 대상 요청의 응답 시간에 합치지 않는다. 서버 내부 대기와 통신 시간은 포함한다. 전송 전 대기까지 섞이지 않도록 도구의 실제 측정 구간을 확인한다.

이번 요청 두 건으로 작업명세 06의 동시 요청 18건 응답 시간 목표 달성을 판정하지 않는다. 기능별 개별 시간을 결과와 함께 보존하고, 부하 측정은 별도 실행 명세에서 다룬다.

### 1.9 실패·미확인·중단의 처리

| 상황 | 기록과 행동 |
|---|---|
| 준비 요청 실패, 조회 실패, 출발 상태 불일치 | 검증 요청을 보내지 않는다. 준비 실패와 마지막 확인 상태를 남긴다 |
| 두 요청이 제한 시간 안에 모두 준비되지 않음 | 두 요청 모두 보내지 않고 실행 준비 실패로 종료한다 |
| 부분 전송이나 예상하지 않은 도구 중단 | 실제 전송 건수를 남기고 저장 결과를 확인한다. 계획한 경합의 완료로 보지 않는다 |
| 응답 미확인·서버 처리 진행 여부 미확인 | 변경 요청을 재전송하지 않는다. 읽기 전용 조회와 로그로 확인하고 전체 판정은 보류한다 |
| 종료 후 조회 실패 | 해당 항목을 미확인으로 둔다. 조회하지 못한 대상을 없음으로 계산하지 않는다 |
| 만료·다른 요청 개입 등 출발 조건 변경 | 변경 시각과 이미 얻은 증거를 남기고 원래 조건의 검증은 미완료로 둔다 |
| 수량 초과 등 명확한 규칙 위반 | 확인한 위반과 증거를 남긴다. 기술 적용이나 데이터 복구를 자동 수행하지 않는다 |

결과는 준비 상태, 전송 건수, 응답 분류, 저장 결과, 경합 확인 여부를 각각 남긴다. 규칙 위반 확인과 다른 항목의 미확인이 동시에 존재할 수 있으므로 하나의 성공·실패 표시로 모두 덮지 않는다.

### 1.10 기록과 구현 완료 확인

| 기록 | 필수 내용 |
|---|---|
| 실행 조건 | 명세 버전, 코드·설정·도구·장비, 실행 시각, 제한값, 시각 고정·중지 적용 여부 |
| 요청 전 상태 | 역할별 회원·대화·상품·제안·예약·주문 식별 정보와 실제 조회값, 기한, 잔액, 준비 통과 여부 |
| 요청별 결과 | 실행·요청 구분, 요청 종류와 수량, 전송·응답 시각, 응답 분류와 사유, 응답 본문 |
| 기존 거래 전후 대조 | 기존 주문과 예약의 개별 값, 변경 여부, 확인 시각 |
| 종료 후 상태 | 새 거래·잔액·전체 수량·조회자별 구매 가능 수량, DB 대조 결과 |
| 경합 근거 | 실제 판단값, 처리 순서, 확인한 사실과 미확인 사항 |
| 판정 | 규칙 준수 또는 위반 항목, 검증 미완료 사유, 다음 확인 필요 사항 |

공통 로그의 실행·요청 식별 방식은 유지하되 준비 처리와 검증 대상 요청을 구분한다. 저장 응답과 조회 원본을 보존하고 계산 결과만 남기지 않는다. 파일에는 인증 토큰·비밀번호·실제 개인정보를 저장하지 않는다. 공개할 원본 사본의 민감정보 제거와 보관 위치는 작업물 관리 명세를 따른다.

실행 파일은 준비, 요청 전 확인, 검증 요청, 종료 후 확인, 집계를 구분한다. 준비 성공 여부를 실제 요청 전송 조건으로 사용한다. 준비·확인·집계만 다시 수행할 수 있더라도 변경 요청이 자동 재실행되지 않아야 한다. 기존 파일을 통째로 복제한 뒤 인원수만 바꾸지 않고, 이번 역할·기존 거래·결과 확인 기준으로 구성한다.

실제 서버 실행에 앞선 실행 파일 검토에서는 정상 준비, 준비 불일치, 상태 조회 실패, 한 요청의 준비 지연, 응답 미확인, 두 허용 결과, 두 요청 모두 성공한 위반 결과를 올바르게 구분하는지 확인한다. 대역 응답을 사용한 검토는 파일 동작 확인이며 실제 DB 정합성의 검증으로 기록하지 않는다.

새 세부 작업과 실행 결과의 저장 위치는 작업물 관리 명세에 따라 실행 파일을 구성할 때 지정한다. 기존 실행 원본을 덮어쓰지 않는다. 실행 기록에는 관찰한 결과를, 분석에는 근거와 해석을 구분해 적는다.

## 3. 변경 기록

이 명세를 따르는 실행은 시작하지 않았다. 실행 시작 뒤 본문을 바꾸면 날짜, 변경 내용과 변경 전 명세를 적용한 실행을 추가한다.

## 4. 시스템 명세

### 4.1 요청과 응답의 연결

서버 주소·포트·문맥 경로는 실행 환경에서 입력하며 문서에 실제 접속 정보를 고정하지 않는다. 아래 경로 앞에 실제 문맥 경로를 붙인다. 회원 가입과 로그인은 프로젝트의 현재 인증 계약을 확인해 구성하며, 기존 테스트의 인증정보 자체는 복사하지 않는다.

| 행동 | 요청 | 확인할 응답 |
|---|---|---|
| 상품 등록 | `POST /api/products`, `name`, `description`, 유효한 `category`, `price=10000`, `quantity=10` | 201, `productId`, `initialQuantity`, `remainingQuantity`, `status` |
| 대화 시작 | 구매자 인증으로 `POST /api/products/{productId}/conversations` | 새 대화 201, `conversationId`. 이미 존재한 대화가 반환되면 새 실행 준비 조건 확인 |
| 충전 | 구매자 인증으로 `POST /api/wallet/charges`, `amount`, `requestId` | 201 후 잔액 조회로 실제 금액 확인 |
| 가격 제안 | `POST /api/conversations/{conversationId}/offers`, `amount=9000`, `quantity=4` 또는 `2`, `requestId` | 201, `offerId`, 상태·수량 확인 |
| 수락 | 판매자 인증으로 `POST /api/offers/{offerId}/accept`, 요청 본문 없음 | 200, 해당 제안과 `reservation` 연결 |
| 등록 가격 결제 | `POST /api/orders`, `productId`, `quantity=3` 또는 `2`, `recipientName`, `shippingAddress`, `requestId`. `offerId` 생략 | 201, 주문 상세. 준비 결제와 검증 결제의 식별 정보 구분 |
| 상품 상세 | 해당 조회자 인증으로 `GET /api/products/{productId}` | 200, `remainingQuantity`, `availableQuantity`, `status` |
| 대화 상세 | 판매자 인증으로 `GET /api/conversations/{conversationId}` | 200, `product`, `offers`, `orders`, `reservation` |
| 잔액과 내역 | 각 구매자 인증으로 `GET /api/wallet`, `GET /api/wallet/transactions` | 200, 실제 잔액과 주문에 대응하는 변동 내역 |

요청 본문의 `requestId`는 서로 다른 변경 요청마다 구분하고 64자 이내로 만든다. 이 값이 있다는 이유만으로 중복 요청 방지가 보장된다고 간주하지 않는다. 서버 로그용 헤더 `X-Test-Log-Name`, `X-Test-Log-Run-Id`, `X-Test-Log-Request-Id`와 요청 본문의 식별자는 목적을 구분한다. 헤더의 인코딩은 기존 로그 수신 코드와 맞춘다.

수락의 정상 응답은 200, 결제의 정상 응답은 201이다. 수량 부족 분류에는 수락의 `RESERVATION_QUANTITY_EXCEEDED`, `PRODUCT_NOT_ON_SALE`, 결제의 `PRODUCT_RESERVED`, `INSUFFICIENT_STOCK`, `PRODUCT_NOT_ON_SALE`을 HTTP 409와 함께 확인한다. 이 테스트의 정상 거절 사유는 수락의 `RESERVATION_QUANTITY_EXCEEDED` 또는 결제의 `PRODUCT_RESERVED`다. 기타 409를 모두 수량 부족으로 처리하지 않는다. 숫자 HTTP 응답을 받지 못한 요청은 미확인이다.

### 4.2 전체 DB 대조에 필요한 조회 범위

SQL은 구현 시 실제 스키마와 대조해 작성하고 읽기 전용으로 실행한다. 성공한 응답의 식별자 목록만 조회하지 않고 대상 상품 전체를 조회하여 예상하지 않은 행도 검출한다.

| 조회 대상 | 필수 범위와 값 |
|---|---|
| 상품 | 대상 상품 식별 정보, 최초·남은 수량, 상태 |
| 가격 제안 | 대상 상품의 전체 제안, 구매자·판매자·대화·수량·금액·상태 |
| 예약 | 대상 상품의 전체 예약, 구매자·상품·대화·제안·수량·상태·예약 시각·만료 시각·종료 정보 |
| 주문 | 대상 상품의 전체 주문, 구매자·판매자·수량·단가·결제 금액·가격 출처·제안·거래·발송 상태 |
| 잔액과 변동 | 구매자 네 명의 잔액, 이번 실행에서 생긴 충전·결제 내역과 주문 연결 |

### 4.3 로컬 코드에서 확인한 근거

프로젝트는 `E:/devSpace/SpringBootProjects/ChatService`이며, 아래 경로는 프로젝트 기준이다. 현재 배포 상태는 실행 전에 별도로 확인한다.

| 경로와 처리 | 근거 |
|---|---|
| `src/main/java/com/chatservice/marketplace/offer/OfferController.java` | 제안과 수락의 요청 형식 |
| `src/main/java/com/chatservice/marketplace/order/OrderController.java` — `placeOrder` | 주문 저장 처리 뒤 별도 상세 조회로 응답을 구성하므로 응답 오류만으로 저장 실패를 단정할 수 없음 |
| `src/main/java/com/chatservice/marketplace/order/dto/PlaceOrderRequest.java` | 등록 가격 결제 입력과 선택 제안 식별자 |
| `src/main/java/com/chatservice/marketplace/conversation/dto/ConversationDetailResponse.java` | 대화의 주문 목록과 가장 최근 예약 한 건을 제공하는 응답 범위 |
| `src/main/java/com/chatservice/marketplace/reservation/dto/ReservationResponse.java` | 예약의 식별자·연결·수량·상태·만료·종료 정보 |
| `src/main/java/com/chatservice/marketplace/product/dto/ProductDetailResponse.java` | 조회자 기준 구매 가능 수량 |
| `src/main/java/com/chatservice/marketplace/wallet/WalletController.java` | 인증된 본인의 잔액·변동 내역 조회 |
| `src/main/java/com/chatservice/marketplace/testsupport/TradeTestLog.java` — `registerTransactionEnd` | DB 확정 이후 남기는 완료 로그 |
| `src/main/resources/application.yml` — `marketplace.reservation.duration` | 로컬 예약 기간 `PT20M`. 실행에서는 실제 예약의 만료 시각 확인 |

기존 JMeter 파일의 단계 분리와 응답 처리 방식은 참고할 수 있다. 인원 18명, 기존 예약·주문 없음, 충전 금액 기준 잔액 비교, 조회 실패 시의 위반 집계, 준비 실패 뒤 계속 실행하는 조건은 그대로 가져오지 않는다.
