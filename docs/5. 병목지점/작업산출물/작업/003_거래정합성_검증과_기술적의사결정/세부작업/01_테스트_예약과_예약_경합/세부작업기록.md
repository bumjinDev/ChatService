## 1. 개요

### 1.1 유형

테스트

### 1.2 목적과 범위

기존 예약과 주문이 없는 상품 하나에서, 같은 판매자가 서로 다른 흥정 구매자 18명의 가격 제안을 같은 순간에 수락할 때 예약이 판매 수량을 넘어 생기지 않는지 확인한다. 여기서 예약은 판매자가 가격 제안을 수락하면서 만들어지는 예약이며, 수락과 예약 생성은 요청 하나로 처리된다. 유효 예약은 예약 중이고 만료 시각이 지나지 않은 예약이다.

이 세부 작업에서는 수락 처리에 로그를 넣고, JMeter로 수락 요청 18건을 보낸 뒤, 응답, DB 데이터, 서버 로그로 문제가 생긴 지점과 생긴 방식을 확인하는 데까지 한다. 확인한 정합성 문제의 기술적 개선은 하지 않는다. 결제, 예약의 주문 전환, 취소, 기존 예약·주문이 있는 상황, 다른 기능과의 복합 경합은 범위에 넣지 않는다.

판매 수량 50개와 수락 요청 18건은 이 검증을 위해 정한 조건이며, 개인 중고 거래의 대표적인 수량이나 실제 트래픽이 아니다. 판매자가 앞선 수락 결과를 확인하고 다음 제안을 검토하는 실제 이용 흐름에서는 두 수락의 서버 처리가 겹치지 않으므로, 이 테스트는 기술적 동시성 검증으로 구분한다.

## 2. 계획

- [작업명세 04 C2C_Marketplace_예약과예약경합_로깅_설계](../../작업명세/04_C2C_Marketplace_예약과예약경합_로깅_설계.md)에 정한 로그를 수락 처리 코드에 넣고, 그 코드를 미니PC 서버에 배포한 뒤 JMeter로 테스트를 실행한다.
- 테스트의 기본 구성은 다음과 같다.

  | 항목 | 구성 |
  |---|---|
  | 상품 | 상품 하나, 판매 수량 50개 |
  | 참여자 | 판매자 1명, 서로 다른 흥정 구매자 18명 |
  | 사전 가격 제안 | 2개·3개·5개 제안 각 6건, 제안 수량 합계 60개 |
  | 요청 전 상태 | 가격 제안 18건 모두 응답 대기, 예약·주문 없음 |
  | 경합 요청 | 판매자가 가격 제안 18건을 각각 한 번씩 같은 순간에 수락 |
  | 처리 단위 | 수락과 그 제안 수량만큼의 예약 생성 |

- 가격 제안 등록은 사전 준비로 마치고, 수락 요청과 경합시키지 않는다. 테스트용 중지 위치와 처리 기준 시각 고정은 쓰지 않는다.
- JMeter 계획 하나에 다음 그룹을 차례로 둔다.
  1. 회원 가입 준비: 가입 결과 CSV 새로 만들기
  2. 회원 가입: 판매자 1명과 흥정 구매자 18명
  3. 준비: 로그인, 상품 등록, 대화 시작, 가격 제안 18건 등록, 요청 전 상태 확인
  4. 수락 경합: 판매자의 가격 제안 수락 18건을 같은 순간에 보냄
  5. 수락 경합 뒤 저장 상태 확인: 판매자의 상품 상세와 대화 상세 18건 조회
- 수락 응답은 성공, 수량부족, 기타오류, 미확인으로 나누고, 어느 요청도 다시 보내지 않는다.
- 실행마다 새 상품과 새 가격 제안을 만들고, 이전 실행의 데이터는 지우지 않는다.
- 결과 확인 기준은 다음과 같다.
  - 유효 예약 합계가 판매 수량 50개를 넘지 않는다.
  - 성공한 수락에는 제안 수량 전부가 예약된다. 남은 수량에 맞춰 일부만 예약하지 않는다.
  - 수락 상태와 예약의 상품·구매자·제안·수량이 일치한다.
  - 예약만 만들므로 상품의 저장된 남은 수량은 50개이고 주문은 없다.
  - 성공하는 흥정 구매자의 조합은 달라질 수 있으며, 정확히 50개를 예약하는 것을 성공 조건으로 두지 않는다.
  - 수량 부족으로 거절된 요청에 수락이나 예약이 남지 않는다.
  - 수량 부족으로 거절된 요청은 다시 보내지 않는다.
  - 응답을 받지 못한 요청은 저장된 처리 결과부터 확인하고, 확인하기 전에 다시 수락하지 않는다.
  - 기타 오류와 수량 부족을 구분하고, 실패하거나 응답을 받지 못한 요청을 정상 처리로 합산하지 않는다.
- 결과는 응답 파일, JMeter 결과 파일, DB 조회 결과, 서버 로그(애플리케이션 로그와 p6spy 기록)로 확인한다. 서버 로그는 스크립트로 엑셀 파일에 정리한다.
- 결과를 확인한 뒤 테스트 결과서를 쓴다.

### 계획 변경

- 2026-11-11: 이 단계에서는 테스트 결과서를 쓰지 않는다. 애플리케이션 로그와 p6spy 기록을 대조해 요청 구간별로 수치 변화를 따라가는 분석은, 작업명세 01에 있는 테스트를 이번처럼 실행해 결과를 낸 다음 단계에서 한다.

## 3. 진행 기록

### 2026-11-10 수락 요청이 거쳐 가는 코드에 동작 설명 주석 추가

- 판매자의 가격 제안 수락 요청이 거쳐 가는 소스 19개에 처리 동작을 설명하는 주석을 넣었다. 가격 제안 수락, 예약 생성, 구매 가능 수량 계산, 대화 상태 이벤트 처리가 해당한다. 코드의 동작은 바꾸지 않았다.
- 주석을 넣은 파일 목록은 「7. 시스템 명세」에 있다.

### 2026-11-10 예약–예약 경합의 로그 지점과 항목 결정

- 수락 요청 하나에서 로그를 남길 지점, 지점별로 남길 항목, 지점별 코드 위치를 [작업명세 04 C2C_Marketplace_예약과예약경합_로깅_설계](../../작업명세/04_C2C_Marketplace_예약과예약경합_로깅_설계.md)에 정했다. 로그 줄은 [작업명세 03 C2C_Marketplace_공통로그포맷_설계](../../작업명세/03_C2C_Marketplace_공통로그포맷_설계.md)의 공통 형식을 따른다.
- 정한 내용은 다음과 같다.
  - 서버가 DB에 보낸 SQL과 커밋·롤백은 p6spy 기록으로 확인하고, p6spy 기록에 남지 않는 값만 애플리케이션 로그로 남긴다. 수량 판단에 쓴 남은 수량·유효 예약 합계·판단 결과, 저장한 예약의 ID, 롤백된 이유, 응답에 담긴 오류 코드가 해당한다.
  - 서버는 수락 요청 하나에 요청수신, 수락시작, 수량판단, 예약저장처리완료, 커밋전, 커밋완료(또는 롤백완료, 확정여부미확인), 요청응답의 일곱 단계 로그를 남긴다. 예약을 저장한 직후에는 예약저장처리완료를 남기고, 수락과 예약이 DB에 확정된 뒤에만 커밋완료를 남긴다.
  - 수락 요청 18건이 모두 끝난 뒤 JMeter가 요청별사후확인과 전체사후확인을 서버 로그와 같은 형식으로 실행 폴더의 파일에 쓴다.
  - 요청과 p6spy 기록은 요청수신 로그에 남긴 서버 스레드 이름으로 연결한다.
  - 실행 ID 헤더와 요청 ID 헤더가 없는 요청은 기록하지 않는다.

### 2026-11-11 로그를 수락 처리 코드에 반영

- 작업명세 04의 「3. 지점별 코드 위치」대로 가격 제안 수락 처리, 예약 생성 처리, 구매 가능 수량 계산, 업무 오류 응답 처리에 로그를 넣었다.
- 공통 형식의 로그를 남기는 파일 두 개를 테스트 지원 코드에 만들었다. 한 파일은 요청을 처리하는 동안 실행 ID와 요청 ID를 보관하고 로그 줄을 만든다. 다른 파일은 요청을 받을 때와 응답할 때 로그를 남긴다.
- 테스트 설정이 꺼져 있거나 테스트 헤더가 없는 요청은 기록하지 않는다. 업무 규칙, 수량 계산, 트랜잭션 범위는 바꾸지 않았다.
- 컴파일과 단위 테스트를 통과했다. 바꾼 파일은 「6.2 변경한 코드와 파일」에 있다.

### 2026-11-11 JMeter 계획 작성

- 테스트데이터의 실행01 폴더에 회원 CSV와 JMeter 계획을 만들었다. 회원 CSV에는 판매자 1명과 흥정 구매자 18명이 있고, 흥정 구매자의 제안 수량은 01~06번이 2개, 07~12번이 3개, 13~18번이 5개다.
- JMeter 계획의 그룹은 「2. 계획」의 다섯 그룹이다. 서버 로그용 헤더(테스트명, 실행 ID, 요청 ID)는 수락 요청 18건에만 붙인다.
- 「수락 경합 뒤 저장 상태 확인」 그룹은 요청별사후확인 18줄과 전체사후확인 1줄을 실행 폴더의 `사후확인.log`에 쓴다. 전체사후확인은 결과 확인 기준에 따라 다음 여섯 가지 위반을 확인한다.
  - 유효 예약 합계가 판매 수량 50개를 넘음
  - 성공한 수락에 제안 수량 전부가 예약되지 않음
  - 수락 상태와 예약이 맞지 않음
  - 상품의 남은 수량이 50개가 아님
  - 주문이 있음
  - 수량 부족으로 거절된 요청에 수락이나 예약이 남음
- 로그인 토큰은 파일에 쓰지 않고 JMeter 속성으로만 다음 그룹에 넘긴다. 그래서 그룹은 같은 JMeter 창에서 이어서 실행해야 한다.
- 실제 서버에는 요청하지 않고, API 응답 형식만 흉내 낸 로컬 대역 서버에 요청을 보내 계획을 확인했다.
  - 대역 서버가 수량을 잠금 없이 읽고 저장하게 했을 때 예약 합계 57개가 위반으로 기록되었다.
  - 수량 확인과 저장을 한 번에 하나씩 처리하게 했을 때 수량 부족 두 건이 수량부족으로 나뉘고 위반은 없었다.
  - 일부러 넣은 서버 오류는 기타오류로, 저장한 뒤 연결을 끊은 요청은 미확인으로 나뉘고 저장 상태가 함께 기록되었다.

## 7. 시스템 명세

**JMeter 계획**

- 파일: [실행01_계획_회원가입과_가격제안수락18건동시요청.jmx](테스트데이터/실행01_가격제안수락18건동시요청_20261111/실행01_계획_회원가입과_가격제안수락18건동시요청.jmx). 스레드 그룹은 다음 순서로 놓여 있다.
  1. 회원 가입 준비: 가입 결과 CSV 새로 만들기
  2. 회원 가입: 판매자 1명과 흥정 구매자 18명
  3. 로그인: 판매자 1명과 흥정 구매자 18명
  4. 준비: 상품 등록, 대화 시작, 가격 제안 18건 등록, 요청 전 상태 확인
  5. 수락 경합: 판매자의 가격 제안 수락 18건을 같은 순간에 보냄
  6. 수락 경합 뒤 저장 상태 확인: 판매자의 상품 상세와 대화 상세 18건 조회
- 회원 CSV: `테스트데이터/실행01_가격제안수락18건동시요청_20261111/실행01_회원.csv`(저장소에 올리지 않음)
- 「수락 경합」 그룹의 동시 전송: 스레드 18개와 동기화 타이머. 18개 스레드가 모두 준비되면 함께 보내며, 최대 10초 기다린다.
- 서버 로그용 헤더: `X-Test-Log-Name`(테스트명), `X-Test-Log-Run-Id`(실행 ID), `X-Test-Log-Request-Id`(요청 ID). 실행 ID는 준비 그룹이 시작할 때 `run{실행 번호}-{yyyyMMdd}-{HHmmss}` 형식으로 만들고, 요청 ID는 흥정 구매자 번호에 맞춘 `accept-01`~`accept-18`이다. 15:38 수락 경합의 실행 ID는 `run01-20261111-153709`다.
- 응답 본문은 그룹마다 실행 폴더에 `{단계}_{역할}_{응답 종류}.json`으로 저장한다. 같은 그룹을 다시 실행하면 같은 이름의 파일을 덮어쓴다.
- `사후확인.log`의 파일명 칸에는 JMeter 파일 이름을, 메소드명 칸에는 「수락 경합 뒤 저장 상태 확인」을 넣는다. 응답을 받지 못한 요청의 응답상태는 「응답없음(예외 이름)」으로 쓴다.

**요청**

경로는 모두 `/ChatService`로 시작한다.

- 로그인: `POST /login`. 302 응답의 `Authorization` 쿠키를 로그인 토큰으로 쓴다
- 가격 제안 수락: `POST /api/offers/{제안 ID}/accept`
- 상품 상세: `GET /api/products/{상품 ID}`, 대화 상세: `GET /api/conversations/{대화 ID}`
- 15:35의 수락 요청 18건은 `POST /api/offers/NOT_FOUND/accept`로 보내졌고, 응답의 오류 코드는 `VALIDATION_ERROR`였다.
