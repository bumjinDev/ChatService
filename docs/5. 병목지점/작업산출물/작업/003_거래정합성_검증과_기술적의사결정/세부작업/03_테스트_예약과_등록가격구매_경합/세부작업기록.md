# 03 테스트 예약과_등록가격구매_경합

## 1. 개요

### 1.1 유형

테스트

### 1.2 목적과 범위

기존 예약과 주문이 없는 상품 하나에, 판매자의 가격 제안 수락 요청과 등록 가격 구매 요청을 같은 순간에 보낼 때, 새로 생긴 예약과 주문이 확보 가능한 수량을 넘지 않는지 확인한다. 여기서 예약은 판매자가 흥정 구매자의 가격 제안을 수락하면서 만들어지는 예약이며, 수락과 예약 생성은 요청 하나로 처리된다. 등록 가격 구매는 가격 제안 없이 상품의 등록 가격으로 결제하는 요청이며, 주문 저장, 잔액 차감, 남은 수량 차감이 요청 하나로 처리된다.

이 세부 작업에서는 코드에 들어가 있는 수락 처리 로그와 결제 처리 로그를 그대로 쓰고, JMeter로 수락 요청과 결제 요청을 보낸 뒤, 응답, DB 데이터, 서버 로그로 확인하는 데까지 한다. 확인한 정합성 문제의 기술적 개선은 하지 않는다.

## 2. 계획

- 가격 제안 수락 요청과 등록 가격 결제 요청이 같은 상품의 남은 수량, 유효 예약 합계, 예약 가능 수량, 구매 가능 수량을 읽고 바꾸는 처리를 코드에서 따라간 뒤, 테스트의 기본 구성과 결과 확인 기준을 정한다.
- 로그는 [작업명세 04 C2C_Marketplace_예약과예약경합_로깅_설계](../../작업명세/04_C2C_Marketplace_예약과예약경합_로깅_설계.md)와 [작업명세 05 C2C_Marketplace_등록가격구매와등록가격구매경합_로깅_설계](../../작업명세/05_C2C_Marketplace_등록가격구매와등록가격구매경합_로깅_설계.md)에 따라 이미 코드에 들어간 것을 그대로 쓰고, 새로 넣지 않는다.
- JMeter 계획의 구성을 정한 뒤, 세부 작업 02의 JMeter 계획 생성 스크립트(준비 그룹을 네 그룹으로 나눈 판)를 복사해 그 구성대로 고친다. 가격 제안 등록과 수락 요청은 세부 작업 01의 생성 스크립트에서 가져온다. 실제 서버에 요청하지 않는 로컬 대역 서버로 응답 분류와 종료 후 확인 기록을 확인한다.
- JMeter로 테스트를 실행하고 응답, DB 조회 결과, 서버 로그를 실행 폴더에 저장한다.
- 세부 작업 02의 서버 로그 정리 스크립트를 실행 폴더에 복사하고, 한 실행에 함께 있는 수락 요청과 결제 요청의 로그를 한 엑셀에 정리하도록 고쳐, 웹 애플리케이션 로그 엑셀과 DB 로그 엑셀을 만든다.
- 실행 기록을 쓴다. 이 단계에서는 테스트 결과서를 쓰지 않는다. 애플리케이션 로그와 p6spy 기록을 대조해 요청 구간별로 수치 변화를 따라가는 분석은, 작업명세 01에 있는 테스트를 결과까지 낸 다음 단계에서 한다.
- 테스트의 기본 구성은 다음과 같다.

  | 항목 | 구성 |
  |---|---|
  | 상품 | 상품 하나, 판매 수량 50개, 등록 가격 개당 10,000원 |
  | 참여자 | 판매자 1명, 흥정 구매자 9명, 등록 가격 구매자 9명. 구매자 18명은 모두 다른 회원이다 |
  | 가격 제안 | 흥정 구매자마다 1건. 01~03번은 2개, 04~06번은 3개, 07~09번은 5개를 제안해 합계 30개. 제안 금액은 개당 9,000원 |
  | 등록 가격 구매 | 등록 가격 구매자마다 1건. 01~03번은 2개, 04~06번은 3개, 07~09번은 5개를 사서 합계 30개 |
  | 같은 순간에 보낼 요청 | 판매자의 수락 요청 9건과 등록 가격 구매자의 결제 요청 9건, 합계 18건 |
  | 요청 전 상태 | 상품이 판매 중이고 남은 수량과 구매 가능 수량이 50개다. 구매자마다 판매자와의 대화가 하나씩 있다(18건). 가격 제안 9건은 모두 응답 대기다. 예약과 주문은 없다. 등록 가격 구매자의 잔액은 결제 금액과 같고, 흥정 구매자는 충전하지 않는다 |
  | 준비 | 상품 등록, 대화 시작 18건, 가격 제안 등록 9건, 등록 가격 구매자의 충전 9건, 요청 전 상태 확인 |
  | 제외 행동 | 판매자의 가격 제안 거절, 합의 가격 결제(예약을 주문으로 바꾸는 결제), 예약 해제, 같은 구매자가 여러 번 수락받거나 결제하는 것, 흥정 구매자의 등록 가격 결제, 등록 가격 구매자의 가격 제안, 준비 요청(가격 제안 등록, 충전)과 경합 요청의 경합, 주문 취소와 발송 같은 주문 뒤 처리, 기존 예약·주문이 있는 상황, 다른 기능과의 복합 경합 |

- 판매 수량, 요청 수, 구매 수량의 조합, 대화 수는 세부 작업 01·02와 같게 두고, 요청 18건만 수락 9건과 결제 9건으로 나눈다.
  - 수락만 모으면 30개, 결제만 모아도 30개다. 그래서 같은 종류의 요청끼리만 경합해서는 예약 합계도 주문 합계도 50개를 넘지 않는다. 두 합계를 더한 값이 50개를 넘었다면, 수락과 결제가 같은 수량을 함께 확보한 것이다. 다만 결제끼리 남은 수량을 덮어쓰는 문제는 세부 작업 02처럼 이번에도 생길 수 있다.
  - 요청 18건, 2개·3개·5개 구성, 요청 수량 합계 60개, 대화 18건이 세부 작업 01·02와 같다. 대화 수가 같으므로 대화 상태 이벤트를 만드는 반복 조회도 요청마다 예약 조회 18건으로 같다. 18건 가운데 DB 연결 12개를 넘는 6건이 연결을 기다리는 조건도 같다.
  - 커밋 순서대로 한 건씩 처리했다면, 확보한 수량 합계가 50개에 이를 때까지만 성공한다. 따라서 수락이나 결제 가운데 몇 건은 수량 부족으로 거절되어야 한다.
  - 결제 합계가 30개이므로 남은 수량은 20개 아래로 내려가지 않는다. 따라서 남은 수량 부족이나 판매 종료로 거절되는 요청은 나오지 않는다. 결제가 거절된다면 다른 회원의 예약을 뺀 구매 가능 수량이 모자라서이고, 수락이 거절된다면 예약 가능 수량이 모자라서이다.
- 테스트용 중지 위치와 처리 기준 시각 고정은 쓰지 않는다.
- 실행마다 새 회원과 새 상품을 만들고, 이전 실행의 데이터는 지우지 않는다.
- 응답은 성공, 수량부족, 기타오류, 미확인으로 나누고, 어느 요청도 다시 보내지 않는다.
  - 수락 요청: 200이면 성공이다. 409이면서 예약 가능 수량이 부족하거나 상품이 판매 종료여서 거절되었으면 수량부족이다.
  - 결제 요청: 201이면 성공이다. 409이면서 남은 수량 부족, 구매 가능 수량 부족, 판매 종료 가운데 하나로 거절되었으면 수량부족이다.
  - 그 밖의 HTTP 응답은 기타오류, 응답을 받지 못한 요청은 미확인이다.
- 결과 확인 기준은 다음과 같다.
  - 유효 예약 합계와 주문 수량 합계를 더한 값이 판매 수량 50개를 넘지 않는다.
  - 성공한 수락과 결제는 커밋 순서대로 한 건씩 처리했을 때의 수량 안에서만 예약되고 주문된다.
    - 수락: 제안 수량이 「판매 수량 − 앞서 커밋한 주문의 수량 합계 − 앞서 커밋한 유효 예약 합계」를 넘지 않는다.
    - 결제: 구매 수량이 같은 방식으로 구한 수량, 즉 다른 회원의 유효 예약을 뺀 구매 가능 수량을 넘지 않는다.
    - 이 기준은 응답과 DB만으로는 확인할 수 없다. 커밋완료 로그의 순서로 계산한 기대 값과 비교해 확인하고, 그 비교는 웹 애플리케이션 로그 엑셀의 시트 2에 둔다.
  - 성공한 수락에는 제안 수량 전부가 예약되고, 성공한 결제는 구매 수량 전부를 주문한다. 남은 수량에 맞춰 일부만 처리하지 않는다.
  - 수락 상태와 예약의 상품·구매자·제안·수량이 일치한다.
  - 상품에 저장된 남은 수량은 판매 수량 50개에서 주문 수량 합계를 뺀 값이다. 예약은 남은 수량을 줄이지 않는다.
  - 상품 상태는 남은 수량과 맞는다. 남은 수량이 0이면 판매 종료이고, 0보다 크면 판매 중이다.
  - 주문이 있는 등록 가격 구매자는 잔액이 0원이고, 주문이 없는 등록 가격 구매자는 잔액이 충전 금액 그대로다.
  - 실패한 수락에는 수락과 예약이 남지 않고, 가격 제안은 응답 대기로 남는다. 실패한 결제에는 주문, 잔액 차감, 남은 수량 차감이 남지 않는다.
  - 성공하는 구매자의 조합은 달라질 수 있으며, 정확히 50개를 확보하는 것을 성공 조건으로 두지 않는다.
  - 수량 부족으로 거절된 요청은 다시 보내지 않는다. 응답을 받지 못한 요청은 저장된 상태부터 확인하고, 확인하기 전에는 다시 보내지 않는다.
  - 기타 오류와 수량 부족을 구분하고, 실패하거나 응답을 받지 못한 요청을 정상 처리로 합산하지 않는다.
- 유효 예약 합계는 예약 중이면서 만료 전인 예약의 수량을 더한 값이다. 예약 기간이 20분이므로, 저장 상태 확인과 DB 조회는 수락 경합 뒤 20분 안에 한다. 세부 작업 01에서는 대화 상세 조회가 만료 시각 뒤에 실행되어, 예약 중 상태인 예약을 더하는 방식으로 확인했다.
- JMeter 계획 하나에 다음 그룹을 차례로 둔다. 준비는 세부 작업 02처럼 단계마다 그룹을 나눠, 한 그룹만 다시 실행해도 다른 단계의 데이터가 다시 만들어지지 않게 한다. 세부 작업 02보다 가격 제안 등록 그룹이 하나 늘고, 충전은 등록 가격 구매자 9명만 한다.

  2. 회원 가입: 판매자 1명, 흥정 구매자 9명, 등록 가격 구매자 9명
  3. 로그인: 판매자 1명, 흥정 구매자 9명, 등록 가격 구매자 9명

  5. 준비: 대화 시작 18건
  6. 준비: 가격 제안 등록 9건
  7. 준비: 충전 9건
  8. 준비: 요청 전 상태 확인
  9. 수락·결제 경합: 가격 제안 수락 9건과 등록 가격 결제 9건을 같은 순간에 보냄
