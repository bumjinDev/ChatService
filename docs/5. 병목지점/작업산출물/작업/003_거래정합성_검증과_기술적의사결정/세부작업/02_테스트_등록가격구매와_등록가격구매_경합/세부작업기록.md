# 02 테스트 등록가격구매와_등록가격구매_경합

## 1. 개요

### 1.1 유형

테스트

### 1.2 목적과 범위

기존 예약과 주문이 없는 상품 하나에 등록 가격 구매 요청 여러 건을 같은 순간에 보낼 때, 여러 주문이 같은 수량을 중복 구매하지 않는지 확인한다. 등록 가격 구매는 가격 제안 없이 상품의 등록 가격으로 결제하는 요청이며, 주문 저장, 잔액 차감, 남은 수량 차감이 요청 하나로 처리된다.

이 세부 작업에서는 결제 처리에 로그를 넣고, JMeter로 등록 가격 구매 요청을 보낸 뒤, 응답, DB 데이터, 서버 로그로 확인하는 데까지 한다. 확인한 정합성 문제의 기술적 개선은 하지 않는다.

## 2. 계획

- 등록 가격 구매 요청이 거쳐 가는 코드에서 로그를 남길 지점을 정하고, 지점별 단계 이름과 항목, 지점별 코드 위치를 [작업명세 05 C2C_Marketplace_등록가격구매와등록가격구매경합_로깅_설계](../../작업명세/05_C2C_Marketplace_등록가격구매와등록가격구매경합_로깅_설계.md)에 정한다. 등록 가격 구매 요청이 모두 끝난 뒤 JMeter가 쓰는 요청별종료후확인과 전체종료후확인의 항목과 형식도 이 명세에서 정한다.
- 로그를 넣을 코드 파일을 로그를 넣기 전 상태로 수집자료에 백업한 뒤, 작업명세 05대로 로그를 넣는다. 컴파일과 단위 테스트를 통과한 코드를 미니PC 서버에 배포한다.
- 세부 작업 01의 JMeter 계획 생성 스크립트에서 준비, 경합, 경합 뒤 저장 상태 확인 부분만 바꿔 JMeter 계획을 만든다. 실제 서버에 요청하지 않는 로컬 대역 서버로 응답 분류와 종료 후 확인 기록을 확인한다.
- JMeter로 테스트를 실행하고 응답, DB 조회 결과, 서버 로그를 실행 폴더에 저장한다.
- 세부 작업 01의 서버 로그 정리 스크립트를 실행 폴더에 복사해, 서버 로그를 웹 애플리케이션 로그 엑셀과 DB 로그 엑셀로 정리한다.
- 실행 기록을 쓴다. 이 단계에서는 테스트 결과서를 쓰지 않는다. 애플리케이션 로그와 p6spy 기록을 대조해 요청 구간별로 수치 변화를 따라가는 분석은, 작업명세 01에 있는 테스트를 결과까지 낸 다음 단계에서 한다.
- 테스트의 기본 구성은 다음과 같다.

  | 항목 | 구성 |
  |---|---|
  | 상품 | 상품 하나, 판매 수량 50개, 등록 가격 개당 10,000원 |
  | 참여자 | 판매자 1명, 서로 다른 등록 가격 구매자 18명 |
  | 구매 수량 | 2개·3개·5개 각 6명, 요청 수량 합계 60개 |
  | 동시에 보낼 구매 요청 | 18건. 등록 가격 구매자마다 한 번씩 같은 순간에 보낸다 |
  | 요청 전 상태 | 상품은 판매 중이고 남은 수량과 구매 가능 수량이 50개. 등록 가격 구매자마다 판매자와의 대화가 하나씩 있다(18건). 가격 제안, 예약, 주문은 없다. 등록 가격 구매자마다 잔액이 결제 금액과 같다 |
  | 준비 | 상품 등록, 등록 가격 구매자의 대화 시작 18건, 충전 18건, 요청 전 상태 확인 |
  | 제외 행동 | 가격 제안과 예약, 합의 가격 결제, 같은 구매자가 여러 번 결제하는 것, 충전과 결제의 경합, 주문 취소와 발송 같은 주문 뒤 처리, 기존 예약·주문이 있는 상황, 다른 기능과의 복합 경합 |

- 충전 금액은 결제 금액과 같다. 2개 구매자는 20,000원, 3개 구매자는 30,000원, 5개 구매자는 50,000원을 충전한다. 성공한 구매자의 잔액은 0원이 되고, 거절된 구매자의 잔액은 충전 금액 그대로 남는다.
- 요청 전에 등록 가격 구매자마다 판매자와의 대화를 시작해 둔다.
  - 판매 종료 상품은 상품 상세 조회가 404를 돌려주므로, 종료 후 확인에서는 판매자의 대화 상세로 상품의 남은 수량, 판매 상태, 구매자별 주문을 읽는다.
  - 대화 상태 이벤트를 만드는 반복 조회가 요청마다 같은 횟수(대화 조회 1건, 예약 조회 18건)가 된다.
  - 세부 작업 01의 JMeter 계획에서 준비와 저장 상태 확인 구성을 이어 쓸 수 있다.
  - 그래서 대화가 없는 구매자에게 결제 처리가 대화를 만드는 동작은 이 테스트에서 실행되지 않는다.
- 준비 요청은 구매 요청과 경합시키지 않는다. 테스트용 중지 위치와 처리 기준 시각 고정은 쓰지 않는다.
- 구매 응답은 성공, 수량부족, 기타오류, 미확인으로 나누고, 어느 요청도 다시 보내지 않는다. 남은 수량 부족, 구매 가능 수량 부족, 판매 종료로 거절된 409 응답을 수량부족으로 본다.
- 실행마다 새 회원과 새 상품을 만들고, 이전 실행의 데이터는 지우지 않는다.
- 결과 확인 기준은 다음과 같다.
  - 성공한 주문의 수량 합계가 판매 수량 50개를 넘지 않는다.
  - 성공한 구매는 요청 수량 전부를 주문한다. 남은 수량에 맞춰 일부만 주문하지 않는다.
  - 상품에 저장된 남은 수량은 판매 수량 50개에서 주문 수량 합계를 뺀 값이다.
  - 상품 상태는 남은 수량과 맞는다. 남은 수량이 0이면 판매 종료이고, 0보다 크면 판매 중이다.
  - 주문이 있는 구매자는 잔액이 결제 금액만큼 줄어 0원이고, 주문이 없는 구매자는 잔액이 충전 금액 그대로다.
  - 성공하는 구매자의 조합은 달라질 수 있으며, 정확히 50개를 파는 것을 성공 조건으로 두지 않는다.
  - 수량 부족으로 거절된 요청에는 주문이 남지 않고 잔액도 줄지 않는다. 이 요청은 다시 보내지 않는다.
  - 응답을 받지 못한 요청은 저장된 주문과 잔액부터 확인하고, 확인하기 전에 다시 보내지 않는다.
  - 기타 오류와 수량 부족을 구분하고, 실패하거나 응답을 받지 못한 요청을 정상 처리로 합산하지 않는다.

## 3. 진행 기록

### 2026-11-12 등록 가격 구매 경합의 로그 지점과 항목, 테스트 기본 구성 결정

- 등록 가격 구매 요청 하나에서 로그를 남길 지점, 지점별로 남길 항목, 지점별 코드 위치를 [작업명세 05 C2C_Marketplace_등록가격구매와등록가격구매경합_로깅_설계](../../작업명세/05_C2C_Marketplace_등록가격구매와등록가격구매경합_로깅_설계.md)에 정했다. 로그 줄은 [작업명세 03 C2C_Marketplace_공통로그포맷_설계](../../작업명세/03_C2C_Marketplace_공통로그포맷_설계.md)의 공통 형식을 따른다.
- 정한 내용은 다음과 같다.
  - 애플리케이션 로그는 지점마다 한 줄씩 남기고, 같은 스레드에서 두 지점 사이에 남은 p6spy 기록을 그 구간의 DB 기록으로 본다. 애플리케이션 로그에는 p6spy 기록에 남지 않는 값만 남긴다. 확인에 쓴 남은 수량·유효 예약 합계·구매 가능 수량·잔액과 판단 결과, 저장한 주문의 ID, 커밋할 때 쓸 차감 후 남은 수량과 상품 상태, 롤백된 이유, 응답에 담긴 오류 코드가 해당한다.
  - 서버는 등록 가격 구매 요청 하나에 요청수신, 결제시작, 남은수량판단, 구매가능수량판단, 잔액판단, 주문저장처리완료, 차감처리완료, 커밋전, 커밋완료(또는 롤백완료, 확정여부미확인), 요청응답의 열 단계 로그를 남긴다.
  - 로그를 새로 넣는 파일은 결제 처리 하나다. 요청수신, 요청응답, 커밋·롤백 결과 기록, 오류 코드 보관, 구매 가능 수량 계산의 값 보관은 세부 작업 01에서 넣은 코드를 그대로 쓴다.
  - 구매 요청 18건이 모두 끝난 뒤 JMeter가 요청별종료후확인과 전체종료후확인을 서버 로그와 같은 형식으로 실행 폴더의 `종료후확인.log`에 쓴다.
- 테스트의 기본 구성과 결과 확인 기준을 정했다. 내용은 「2. 계획」에 있다.

### 2026-11-12 로그를 넣을 코드 백업

- 로그를 넣을 기존 코드 파일 1개(결제 처리)를 로그를 넣기 전 상태로 수집자료에 백업했다. 백업 파일과 원본 경로의 대응은 [20261112_로깅추가전_코드백업_원본경로.md](수집자료/20261112_로깅추가전_코드백업_원본경로.md)에 있다.

### 2026-11-12 로그를 결제 처리 코드에 반영

- 작업명세 05의 「3. 지점별 코드 위치」대로 결제 처리에 결제시작, 남은수량판단, 구매가능수량판단, 잔액판단, 주문저장처리완료, 차감처리완료, 커밋전 로그와 커밋·롤백 결과 기록을 넣었다.
- 결제 처리 본문을 예외 처리 블록으로 감싸, 예외가 메서드 밖으로 나가기 직전에 실패 사유를 보관하고 같은 예외를 다시 던지게 했다. 구매 가능 수량과 잔액은 비교하기 전에 변수에 받도록만 바꿨다.
- 요청수신, 요청응답, 커밋·롤백 결과 기록, 오류 코드 보관, 구매 가능 수량 계산의 값 보관은 세부 작업 01에서 넣은 코드를 그대로 썼다.
- 테스트 설정이 꺼져 있거나 테스트 헤더가 없는 요청은 기록하지 않는다. 업무 규칙, 검사 순서, 수량과 금액의 계산, 트랜잭션 범위는 바꾸지 않았다.
- 컴파일과 단위 테스트를 통과했다. 바꾼 파일의 위치는 「7. 시스템 명세」에 있다.

### 2026-11-12 JMeter 계획 작성과 실행 번호 기준 결정

- 테스트데이터의 실행01 폴더에 회원 CSV와 JMeter 계획을 만들었다. 회원 CSV에는 판매자 1명과 등록 가격 구매자 18명이 있고, 등록 가격 구매자의 구매 수량은 01~06번이 2개, 07~12번이 3개, 13~18번이 5개다.
- JMeter 계획의 그룹은 다음 순서로 놓았다.
  1. 회원 가입 준비: 가입 결과 CSV 새로 만들기
  2. 회원 가입: 판매자 1명과 등록 가격 구매자 18명
  3. 로그인: 판매자 1명과 등록 가격 구매자 18명
  4. 준비: 상품 등록, 대화 시작 18건, 충전 18건, 요청 전 상태 확인
  5. 구매 경합: 등록 가격 구매 18건을 같은 순간에 보냄
  6. 구매 경합 뒤 저장 상태 확인: 판매자의 대화 상세 18건과 등록 가격 구매자의 잔액 18건 조회
- 서버 로그용 헤더(테스트명, 실행 ID, 요청 ID)는 결제 요청 18건에만 붙인다.

  6. 준비: 충전 18건

  8. 구매 경합: 등록 가격 구매 18건을 같은 순간에 보냄
  9. 구매 경합 뒤 저장 상태 확인: 판매자의 대화 상세 18건과 등록 가격 구매자의 잔액 18건 조회

- 서버 로그용 헤더: `X-Test-Log-Name`(테스트명), `X-Test-Log-Run-Id`(실행 ID), `X-Test-Log-Request-Id`(요청 ID). 실행 ID는 「준비: 상품 등록」 그룹(준비 그룹을 나누기 전에는 준비 그룹)이 시작할 때 `run{실행 번호}-{yyyyMMdd}-{HHmmss}` 형식으로 만들고, 요청 ID는 등록 가격 구매자 번호에 맞춘 `buy-01`~`buy-18`이다. 14:04 구매 경합의 실행 ID는 `run01-20261112-135853`이다.

**요청**

경로는 모두 `/ChatService`로 시작한다.

- 로그인: `POST /login`. 302 응답의 `Authorization` 쿠키를 로그인 토큰으로 쓴다
- 상품 등록: `POST /api/products`, 대화 시작: `POST /api/products/{상품 ID}/conversations`, 충전: `POST /api/wallet/charges`

- 상품 상세: `GET /api/products/{상품 ID}`, 대화 상세: `GET /api/conversations/{대화 ID}`, 잔액: `GET /api/wallet`
