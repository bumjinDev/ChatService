## 1. 개요

### 1.1 유형

테스트

### 1.2 목적과 범위

판매 수량 10개인 상품에 기존 주문 3개와 기존 예약 구매자의 유효 예약 4개가 있는 상태에서, 판매자의 새 가격 제안 수락(2개)과 다른 구매자의 등록 가격 결제(2개)를 함께 보낼 때, 기존 주문과 예약을 지키면서 새로 확보할 수 있는 3개 안에서 새 거래 하나만 성립하는지 확인한다. 새 수락은 판매자가 새 흥정 구매자의 가격 제안을 수락하면서 그 구매자에게 예약을 거는 요청이고, 새 결제는 새 등록 가격 구매자가 가격 제안 없이 등록 가격으로 결제하는 요청이다.

이 세부 작업에서는 코드에 들어가 있는 수락 처리 로그와 결제 처리 로그를 그대로 쓴다. 서버 처리를 멈추지 않고 두 요청을 보낸 뒤 응답, DB 데이터, 서버 로그로 확인하는 데까지 하고, 확인한 문제의 기술적 해결은 하지 않는다.

## 2. 계획

- 입력값, 준비 순서, 출발 상태, 두 허용 결과, 결과 확인 기준은 [작업명세 07](../../작업명세/07_C2C_Marketplace_기존거래가있는상품의_예약과등록가격구매경합_상세명세.md)을 따른다. 요지는 다음과 같다.

  | 항목 | 구성 |
  |---|---|
  | 상품 | 실행마다 새 상품 하나, 판매 수량 10개, 등록 가격 개당 10,000원 |
  | 참여자 | 판매자, 기존 주문 구매자, 기존 예약 구매자, 새 흥정 구매자, 새 등록 가격 구매자. 다섯 명 모두 실행마다 새로 가입한다 |
  | 기존 거래 | 기존 주문 구매자의 등록 가격 주문 3개(30,000원), 기존 예약 구매자의 개당 9,000원 가격 제안 4개를 판매자가 수락해 만든 예약 4개 |
  | 함께 보낼 요청 | 판매자가 새 흥정 구매자의 개당 9,000원 가격 제안 2개를 수락하는 요청 1건, 새 등록 가격 구매자가 등록 가격으로 2개(20,000원)를 결제하는 요청 1건 |
  | 출발 상태 | 남은 수량 7개, 유효 예약 4개. 새 등록 가격 구매자가 보는 구매 가능 수량 3개. 새 등록 가격 구매자의 잔액 20,000원, 나머지 구매자 세 명의 잔액 0원 |
  | 허용 결과 | 새 수락만 성공(주문 1건 3개, 유효 예약 2건 6개, 남은 수량 7개) 또는 새 결제만 성공(주문 2건 5개, 유효 예약 1건 4개, 남은 수량 5개). 두 결과 모두 기존 예약 구매자가 보는 구매 가능 수량은 5개, 새 등록 가격 구매자가 보는 구매 가능 수량은 1개 |

- 두 요청이 모두 성공하면 주문 수량과 유효 예약 수량의 합계가 11개가 되어 판매 수량 10개를 넘으므로 규칙 위반이다.
- 테스트용 중지 위치와 처리 기준 시각 고정은 쓰지 않는다.
- 실행마다 새 회원과 새 상품을 만들고, 이전 실행의 데이터는 지우지 않는다. 첫 실행 한 회로 준비·요청·결과 확인이 명세대로 동작하는지 확인하고, 반복 여부는 작업명세 07 「1.8 반복과 응답 시간 기록」에 따라 정한다.
- JMeter 계획 하나에 다음 그룹을 차례로 둔다. 그룹 이름의 단계 번호는 작업명세 07 「1.4 준비 순서와 요청 전 확인」의 순서다.
  1. 실행 시작: 실행 번호·회원 CSV·DB 계정 확인과 실행 조건 기록
  2. 회원 가입: 판매자와 구매자 네 명
  3. 로그인: 판매자와 구매자 네 명
  4. 준비: 상품 등록과 대화 4건 시작(2·3단계)
  5. 준비: 기존 주문 구매자의 30,000원 충전과 3개 결제(4단계)
  6. 준비: 새 등록 가격 구매자의 20,000원 충전(5단계)
  7. 준비: 기존 예약 구매자의 4개 제안과 판매자의 수락(6·7단계)
  8. 준비: 새 흥정 구매자의 2개 제안(8단계)
  9. 요청 전 확인: API 조회와 읽기 전용 DB 대조, 준비 완료 표시(9단계)
  10. 검증 요청: 새 가격 제안 수락과 새 등록 가격 결제를 함께 보냄
  11. 종료 후 확인: API 조회와 읽기 전용 DB 조회
  12. 결과 집계: 응답 분류, 기존 거래 전후 대조, 두 허용 결과와 대조
- 그룹은 앞 그룹이 끝난 상태에서만 요청을 보낸다. 준비나 요청 전 확인에서 하나라도 실패하면 실행 전체를 멈추고 검증 요청을 보내지 않는다.
- 「실행 시작」 그룹은 다음을 확인한다. 이 그룹에서 멈추면 데이터를 바꾸는 요청은 보내지 않고, 실행 폴더에는 JMeter 결과 파일에 남는 그 그룹의 기록 말고는 아무 파일도 쓰지 않는다. 같은 실행 번호로 다시 시작할 수 있다.
  - 이 실행 번호로 회원 가입 요청을 이미 보냈는지. 보냈으면 시작하지 않는다
  - 회원 CSV에 다섯 역할의 서로 다른 회원이 있는지
  - DB 계정과 비밀번호를 받은 뒤, 서버의 공개 상품 목록에 있는 최근 상품 5개가 같은 ID와 이름으로 DB에 있는지. 없으면 서버가 쓰는 스키마가 아니므로 멈춘다
- DB는 읽기 전용 트랜잭션 안에서 SELECT만 실행한다. DB 비밀번호는 「실행 시작」 그룹이 띄우는 입력 창에서 받아 JMeter 메모리에만 두고 파일에 쓰지 않는다.
- 「요청 전 확인」 그룹은 API 조회 17건과 DB 조회로 출발 상태를 대조한다.
  - API 조회: 서버 처리 기준 시각과 고정 여부, 일시 중지로 멈춘 요청, 기존 예약 구매자와 새 등록 가격 구매자의 상품 상세, 판매자의 대화 상세 4건, 구매자 네 명의 잔액과 잔액 변동 내역, 기존 주문 구매자의 기존 주문 상세
  - DB 조회: 대상 상품의 상품·대화·가격 제안·예약·주문 전체, 구매자 네 명의 잔액과 잔액 변동 내역
  - 조회에 실패한 항목은 「확인 못함」으로 두고 없는 것으로 계산하지 않는다. 모든 항목이 출발 상태와 맞을 때만 준비 완료를 표시하고, 기존 주문과 예약의 행 전체를 요청 전 기준값으로 저장한다.
- 「검증 요청」 그룹은 스레드 두 개로 수락과 결제를 하나씩 맡는다.
  - 두 스레드는 준비 완료 표시, 로그인 토큰, 기존 예약 만료와 기존 주문 발송 기한까지 5분 이상 남았는지, 로그인한 지 25분이 지나지 않았는지를 각각 확인한다.
  - 두 스레드가 모두 확인을 통과해 모였을 때만 함께 출발한다. 10초 안에 모이지 않거나 한쪽이 확인을 통과하지 못하면 두 요청 모두 보내지 않는다.
  - 응답을 받지 못하거나 오류가 나도 다시 보내지 않는다.
- 응답은 성공, 수량부족, 기타오류, 미확인으로 나눈다.
  - 수락 요청: 200이면 성공이다. 409이면서 예약 가능 수량이 부족해 거절되었으면 수량부족이다. 409이면서 판매 종료로 거절되었으면 수량부족으로 나누되 예상 상태와 다른 사유로 따로 적는다.
  - 결제 요청: 201이면 성공이다. 409이면서 다른 회원의 예약을 뺀 구매 가능 수량이 부족해 거절되었으면 수량부족이다. 409이면서 남은 수량 부족이나 판매 종료로 거절되었으면 수량부족으로 나누되 예상 상태와 다른 사유로 따로 적는다.
  - 그 밖의 HTTP 응답은 기타오류, 숫자 HTTP 응답을 받지 못한 요청은 미확인이다.
- 「종료 후 확인」 그룹은 요청 전 확인과 같은 범위를 API와 DB로 다시 조회한다. 새 결제가 성공 응답을 받았으면 그 주문 상세도 조회한다.
- 「결과 집계」 그룹은 다음을 확인해 규칙 위반, 검증 미완료, 조사할 사항을 따로 적는다.
  - 기존 주문과 기존 예약의 행을 요청 전 기준값과 열마다 비교하고, 기존 예약이 종료 후 DB 조회 시각에도 유효한지 확인한다.
  - 전체 주문, 유효 예약, 남은 수량, 잔액, 조회자별 구매 가능 수량을 두 허용 결과와 대조한다.
  - 주문 수량과 유효 예약 수량의 합계가 10개 이하인지, 남은 수량이 10개에서 주문 수량을 뺀 값인지 확인한다.
  - 성공한 요청의 응답과 저장 결과가 맞는지, 거절된 요청에 상태 변경이 남지 않았는지 확인한다.
  - 기존 예약이 종료 후 확인 전에 만료되었으면 원래 조건의 검증 미완료로 적는다.
- 유효 예약은 예약 중 상태이면서 확인 시각보다 만료 시각이 뒤인 예약이다. 구매 가능 수량은 남은 수량에서 조회자 본인이 아닌 구매자의 유효 예약 수량을 뺀 값이다.
- 서버 로그용 헤더(테스트명, 실행 ID, 요청 ID)는 검증 요청 두 건과, 기존 주문을 만드는 준비 결제, 기존 예약을 만드는 준비 수락에 붙인다.
  - 테스트명: 「기존 거래 예약–등록 가격 구매」
  - 실행 ID: 「실행 시작」 그룹이 실행마다 하나 만든다.
  - 요청 ID: 검증 요청의 수락은 `accept-new`, 결제는 `buy-new`. 준비 결제는 `prep-order-existing`, 준비 수락은 `prep-accept-existing`
- 회원 CSV, 응답 파일 이름, DB 조회 범위는 「7. 시스템 명세」에 있다.

### 2026-11-13 JMeter 계획을 로컬 대역 서버로 확인

- 실제 서버와 DB에는 요청하지 않고, API 응답과 DB 조회 결과의 모양만 흉내 낸 로컬 대역 서버에 JMeter 계획의 그룹 전체를 실행했다. 대역 서버로 확인한 것은 실행 파일의 동작이며, 실제 DB 정합성의 검증이 아니다.

  | 대역 서버의 동작 | 대역 서버가 받은 검증 요청 | 실행 파일의 판정 |

- 규칙 위반: 수량 초과다. 주문 수량 5개와 유효 예약 수량 6개를 더한 11개가 판매 수량 10개를 넘었다. 새로 확보할 수 있는 수량은 3개였는데, 새 수락의 예약 2개와 새 결제의 주문 2개가 모두 저장되어 4개를 확보했다.
- 규칙을 지킨 항목은 다음과 같다.
  - 기존 주문과 기존 예약은 요청 전 기준값과 모든 열이 같고, 기존 예약은 확인 시각에도 유효했다. 새 요청이 기존 거래의 행을 바꾸지는 않았다.
  - 성공한 두 요청 모두 응답과 저장 결과가 일치했다. 새 수락은 제안 수량 2개 전부를 예약했고, 새 결제는 2개를 주문하고 요청 직전 잔액 20,000원에서 20,000원을 차감했다.
  - 상품의 남은 수량 5개는 판매 수량 10개에서 주문 수량 5개를 뺀 값과 같다. 예약은 남은 수량을 줄이지 않았다.
  - 상품 상세의 구매 가능 수량은 정의에 따라 계산한 값과 같았다.
- 수량 초과의 결과가 조회에도 드러났다. 새 등록 가격 구매자가 보는 구매 가능 수량은 남은 수량 5개에서 다른 구매자의 유효 예약 6개를 뺀 −1개이고, 기존 예약 구매자가 보는 구매 가능 수량은 5개에서 새 흥정 구매자의 예약 2개를 뺀 3개다. 두 허용 결과에서는 각각 1개와 5개다.
- 검증 미완료 사유는 없다. 두 요청이 모두 응답을 받았고, 준비 상태와 종료 후 저장 상태를 모두 조회했으며, 기존 예약이 만료되기 전에 확인했다.

**두 요청의 처리가 겹쳤는지**

두 요청은 상대 요청의 새 확보 결과를 반영하지 않은 값으로 각각 2개를 확보할 수 있다고 판단했고, 그 뒤 둘 다 저장과 커밋을 진행했다. 근거는 다음과 같다.

- 결제 요청이 판단에 쓴 값: 구매가능수량판단 로그에 남은수량 7개, 유효예약합계 4개가 적혀 있다. 유효예약합계에 새 흥정 구매자의 예약 2개가 들어 있지 않다. p6spy 기록에서 결제 요청이 예약을 조회한 시각(15:13:18.195)은 수락 요청이 예약을 INSERT한 시각(15:13:18.206)과 커밋한 시각(15:13:18.212)보다 앞이다.
- 수락 요청이 판단에 쓴 값: 수량판단 로그에 남은수량 7개, 유효예약합계 4개가 적혀 있다. 남은수량에 새 결제의 차감 2개가 반영되어 있지 않다. p6spy 기록에서 수락 요청이 상품을 조회한 시각(15:13:18.203)은 결제 요청이 상품의 남은 수량을 5개로 UPDATE한 시각(15:13:18.204)과 커밋한 시각(15:13:18.209)보다 앞이다.
- 이 값들은 로그를 남기려고 다시 조회한 값이 아니라, 각 요청이 수량을 판단할 때 계산에 쓴 값이다.
- 결제 요청의 첫 SQL 기록(15:13:18.194)부터 커밋 기록(15:13:18.209)까지와, 수락 요청의 첫 SQL 기록(15:13:18.202)부터 커밋 기록(15:13:18.212)까지는 15:13:18.202~15:13:18.209 동안 겹쳐 있다. 두 요청의 수량 판단에 쓴 조회는 모두 상대 요청의 커밋 기록보다 앞이다.

**원인 해석**

다음은 위 사실을 로컬 소스와 대조해 설명한 해석이다. 실행 서버의 코드와 로컬 소스가 같은지는 확인하지 않았다.

- 결제는 상품 행의 남은 수량과 예약 행을 잠금 없이 읽고 판단한 뒤 주문을 INSERT하고 상품 행을 UPDATE한다. 수락은 같은 상품 행과 예약 행을 잠금 없이 읽고 판단한 뒤 예약을 INSERT하고 가격 제안 행을 UPDATE한다.
- 두 요청이 변경한 행은 서로 달랐고, p6spy에 기록된 SQL 실행 시간은 모두 0ms였다. 행 잠금 대기 자체는 측정하지 않았으므로, 이 기록만으로 대기가 전혀 없었다고 확정할 수는 없다.
- 수락 요청이 읽은 남은 수량 7개는 결제 요청이 차감하기 전의 값이다. 결제 요청의 남은 수량 UPDATE는 수락 요청의 상품 조회보다 뒤(15:13:18.204)에 기록되었고, 커밋은 15:13:18.209에 기록되었다. 결제 요청이 예약을 조회한 15:13:18.195에는 새 흥정 구매자의 예약이 아직 INSERT되지 않았다.
- 그래서 두 요청 모두 「남은 수량 7개 − 유효 예약 4개 = 3개」로 2개를 확보할 수 있다고 판단했고, 서로 다른 행에 저장해 둘 다 커밋되었다.

**확인한 사실과 추론의 구분**

- 확인한 사실: 두 응답과 저장 상태, 기존 거래의 전후 값, 각 요청이 판단에 쓴 값, 서버 로그에 남은 SQL과 커밋의 기록 순서
- 추론: 두 요청이 상대 요청의 변경을 읽지 못한 이유에 대한 위 해석. p6spy 기록 시각은 1ms 단위이고 SQL을 실행한 뒤 남는 시각이므로, 수락 요청의 상품 조회(15:13:18.203)와 결제 요청의 UPDATE(15:13:18.204)의 선후는 기록 순서로 판단한 것이다. 커밋 기록 시각도 애플리케이션이 커밋 호출을 마친 뒤 남긴 시각이며, DB 안에서 확정된 순서를 직접 기록한 것은 아니다.
