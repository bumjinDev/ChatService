## 1. 개요

**테스트한 상황**

판매 수량 10개인 상품에 이미 두 거래가 있었다. 기존 주문 구매자가 3개를 샀고, 기존 예약 구매자에게 4개가 예약되어 있었다. 그래서 다른 구매자가 새로 확보할 수 있는 수량은 3개였다.

이 상태에서 다음 두 요청을 함께 보냈다. 두 요청은 2개씩 확보하려고 하므로, 하나가 먼저 확정되면 다른 하나는 남은 1개로 판단해 거절되어야 한다.

- 판매자가 새 흥정 구매자의 가격 제안 2개를 수락한다. 수락하면 새 흥정 구매자에게 2개가 예약된다.
- 새 등록 가격 구매자가 등록 가격으로 2개를 결제한다.

**확인한 것**

- 두 새 요청 가운데 하나만 성공하고, 다른 하나는 수량 부족으로 거절되는가
- 기존 주문과 기존 예약이 바뀌지 않고 유지되는가
- 전체 주문, 유효 예약, 상품의 남은 수량, 잔액, 조회자별 구매 가능 수량이 두 허용 결과 가운데 하나와 같은가
- 두 요청이 서버 안에서 상대 요청의 결과를 반영하지 않은 채 수량을 판단했는가

**결과**

- **두 새 요청:** 둘 다 성공했다. 새 흥정 구매자에게 예약 2개가 생겼고, 새 등록 가격 구매자의 주문 2개가 생겼다.
- **전체 수량:** 주문 5개와 유효 예약 6개를 더하면 11개로, 판매 수량 10개를 넘었다. 작업명세 07의 결과 확인 기준으로 규칙 위반이다.
- **기존 거래:** 기존 주문과 기존 예약은 요청 전과 모든 값이 같았고, 기존 예약은 종료 후 확인 시각에도 유효했다.
- **조회 결과:** 새 등록 가격 구매자가 상품 상세에서 본 구매 가능 수량은 −1개, 기존 예약 구매자가 본 구매 가능 수량은 3개였다. 두 허용 결과에서는 각각 1개와 5개다.
- **처리 순서:** 서버 로그에서 두 요청 모두 남은 수량 7개와 유효 예약 4개로 판단한 것을 확인했다. 두 요청의 판단은 모두 상대 요청이 커밋되기 전에 이루어졌다.

## 2. 테스트 대상

미니PC에 배포해 실행 중인 ChatService 서버를 테스트했다. 서버에는 가격 제안 수락과 결제의 처리 단계를 서버 로그에 남기는 테스트 로그가 들어 있다(작업명세 04와 05).

이 테스트의 참여자는 다음 다섯 명이다. 다섯 명 모두 이번 실행에서 새로 가입했다(작업명세 07 「1.2 입력값과 참여자」).

- **판매자:** 상품을 등록하고, 기존 예약 구매자의 가격 제안을 준비 단계에서 수락한다. 검증 요청에서는 새 흥정 구매자의 가격 제안을 수락한다.
- **기존 주문 구매자:** 준비 단계에서 3개를 등록 가격으로 산다.
- **기존 예약 구매자:** 준비 단계에서 4개를 개당 9,000원에 제안해 수락받는다. 수락으로 4개가 예약된다.
- **새 흥정 구매자:** 2개를 개당 9,000원에 제안하고, 판매자의 수락을 기다린다.
- **새 등록 가격 구매자:** 2개를 등록 가격으로 결제한다.

**이 결과서에서는 판매자가 새 흥정 구매자의 가격 제안을 수락하는 요청을 새 수락, 새 등록 가격 구매자의 등록 가격 결제 요청을 새 결제라고 부른다.**

결과를 이해하는 데에는 다음 규칙이 필요하다. 수량 규칙의 출처는 작업명세 07 「1.6.2 개별 거래의 결과 확인 기준」이다. 처리 순서와 저장 방식은 로컬 소스에서 확인했다.

- **남은 수량:** 상품에 남아 있다고 저장된 수량이다. 결제로 주문이 생기면 줄어들고, 예약으로는 줄어들지 않는다.
- **유효 예약:** 예약 중 상태이면서 만료 시각이 아직 지나지 않은 예약이다. 이번 실행의 예약 기간은 20분이었다.
- **구매 가능 수량:** 남은 수량에서 조회한 사람이 아닌 구매자의 유효 예약 수량을 뺀 수량이다. 조회한 사람마다 값이 다르다.
- **가격 제안 수락의 수량 판단:** 판매자가 가격 제안을 수락하면, 서버는 가격 제안 객체를 먼저 수락 상태로 바꾼 뒤, 남은 수량에서 모든 유효 예약 수량을 뺀 수량(예약 가능 수량)과 제안 수량을 비교한다. 제안 수량이 더 많으면 같은 트랜잭션을 롤백해 수락과 예약을 반영하지 않는다. 검사를 통과하면 예약을 저장한다.
- **등록 가격 결제의 수량 판단:** 서버는 남은 수량, 구매 가능 수량, 잔액을 차례로 확인한다. 모두 통과하면 주문을 저장하고, 잔액과 남은 수량을 줄인다.
- **판단에 쓰는 값:** 두 요청 모두 상품과 예약을 잠금 없이 조회한 값으로 판단한다.
- **DB에 쓰는 시점:** 저장하는 대상에 따라 DB에 SQL이 실행되는 시점이 다르다.
  - 주문, 잔액 변동, 예약은 저장하는 순간 INSERT가 DB에 실행된다. DB가 ID를 만드는 방식이라 저장할 때 ID를 받아야 하기 때문이다. INSERT를 실행한 뒤에도 커밋하기 전까지는 확정되지 않은 변경이다.
  - 상품의 남은 수량, 잔액, 가격 제안의 상태는 서버의 객체 값만 먼저 바뀐다. UPDATE는 커밋 직전에 DB에 실행된다.

**두 요청이 모두 통과한 이유**

- **새 결제:** 예약을 .195(2117)에 조회해, 유효 예약 4개로 판단했다(2120). 새 수락의 예약은 그보다 뒤인 .206에 INSERT되고 .212에 커밋되었으므로, 이 시점의 예약 합계에 들어갈 수 없었다.
- **새 수락:** 상품을 .203(2163)에 조회해, 남은 수량 7개로 판단했다(2187).
  - 새 결제의 남은 수량 차감은 그때 서버의 객체 값으로만 일어나 있었다.
  - DB UPDATE는 .204(2184)에, 커밋은 .209(2205)에 기록되었다.
  - 그래서 새 수락이 읽은 7개는 차감 전의 값이다.
- **두 요청이 바꾼 행이 서로 달랐다.** 새 결제는 상품·잔액 행을 바꾸고 주문·잔액 변동 행을 추가했다. 새 수락은 가격 제안 행을 바꾸고 예약 행을 추가했다. 두 요청의 SQL은 모두 실행에 걸린 시간이 0ms로 기록되었고, 두 요청 모두 커밋되었다.

확인한 사실과 추론, 확인하지 못한 범위는 다음과 같다.

- 확인한 사실: 판단에 쓴 값(애플리케이션 로그), SQL과 커밋의 기록 순서와 SQL 실행 시간(p6spy 기록)
- 추론: "커밋 전의 변경은 다른 요청에 보이지 않았다"는 해석
- 확인하지 못한 범위: 행 잠금 대기 자체는 측정하지 않았다. 두 요청이 서로 다른 행을 변경했고 SQL 실행 시간이 0ms로 기록되었다는 것만으로는 대기가 전혀 없었는지 알 수 없다.

## 9. 정리 및 결론

### 새 수락과 새 결제가 모두 성립한 과정

출발 상태에서 상품의 남은 수량은 7개, 유효 예약은 4개였다. 다른 구매자가 새로 확보할 수 있는 수량은 3개였다. 규칙에 따르면 먼저 확정된 요청이 2개를 가져가고, 다음 요청은 남은 1개로 판단해 거절된다. 두 요청을 커밋완료 로그가 남은 순서대로 한 건씩 처리하는 경우를 계산하면, 새 결제가 통과하고 새 수락이 거절된다(표 11).

실제로는 두 요청이 모두 남은 수량 7개, 유효 예약 4개로 판단했다.

- 새 결제는 새 수락이 예약을 저장하기 전에 예약을 조회했다.
- 새 수락은 새 결제가 남은 수량을 UPDATE하고 커밋하기 전에 상품을 조회했다.
- 두 요청이 바꾼 행은 서로 달랐고, 두 요청의 SQL은 모두 실행에 걸린 시간이 0ms로 기록되었다. 두 요청 모두 커밋되었다.

이 과정은 서버 로그의 수량 판단 기록에 적힌 남은 수량·유효 예약 수량과, SQL·커밋의 기록 순서로 확인했다(표 7, 표 10). 다음 두 가지는 이 기록만으로 확정하지 않았다.

- 새 수락이 읽은 남은 수량이 새 결제의 차감을 반영하지 않은 이유: 기록 순서에, 커밋 전의 변경은 다른 트랜잭션에 보이지 않는다는 해석을 더한 추론이다.
- 행 잠금 대기: 행 잠금 대기 자체를 측정하지 않아, 대기가 전혀 없었는지는 확인하지 못했다.

### 기존 거래와 조회 결과에 나타난 영향

기존 주문과 기존 예약의 행은 바뀌지 않았다. 두 새 요청이 기존 거래의 행을 고치거나 끝내지는 않았다.

수량이 넘친 결과는 조회 결과에 그대로 드러났다. 저장된 남은 수량은 주문된 수량과 맞는 5개였지만, 유효 예약 6개가 남은 수량보다 많아졌다. 그래서 새 등록 가격 구매자의 구매 가능 수량은 −1개로 계산되어 상품 상세에 나왔다. 기존 예약 구매자의 구매 가능 수량도 새 흥정 구매자의 예약 2개가 빠져 3개가 되었다. 기존 예약 구매자는 자신의 예약 4개를 결제하려는 사람인데, 상품 상세에는 그보다 적은 3개를 살 수 있다고 나온 것이다.

결제의 구매 가능 수량 판단도 같은 계산을 쓴다(로컬 소스). 따라서 기존 예약 구매자가 예약한 4개를 결제하면, 구매 가능 수량 3개를 넘게 된다. 이 결제는 이번 실행의 범위가 아니어서 보내지 않았고, 실제로 거절되는지는 확인하지 않았다. 기존 예약의 행은 그대로였지만, 그 예약 4개를 모두 결제할 수 있는지는 이 결과로 확인되지 않았다.

### 결론

- 기존 주문 3개와 유효 예약 4개가 있는 상품에서 새 수락과 새 결제를 함께 보내자, 두 요청이 모두 성공해 주문과 유효 예약의 합계가 판매 수량을 1개 넘었다. 작업명세 07의 결과 확인 기준에서 규칙 위반이다.
- 기존 주문과 기존 예약의 행은 유지되었다. 다만 기존 예약 구매자가 보는 구매 가능 수량이 3개로 줄어, 예약한 4개를 모두 결제할 수 있는지는 확인되지 않았다.
- 서버 처리를 멈추지 않은 실행에서, 두 요청이 서로의 확보 결과가 커밋되기 전에 각각 수량을 판단한 과정을 서버 로그로 확인했다.
- 한 번의 실행이므로, 두 요청의 도착 간격이 어느 정도일 때 이런 결과가 나오는지와 그 발생 비율은 이 결과로 알 수 없다.

## 10. 제한

- **실행 횟수:** 같은 조건으로 한 번 실행했다. 두 요청이 모두 성공하는 조건과 발생 비율은 판단할 수 없다.
- **처리 순서의 정밀도:** p6spy 기록은 1ms 단위이고 SQL을 실행한 뒤 남는다. 새 수락의 상품 조회(.203)와 새 결제의 상품 UPDATE(.204)처럼 1ms 차이의 선후는 기록 순서로 판단했다. 커밋 기록도 서버가 커밋을 마친 뒤 남긴 시각이며, DB 안에서 확정된 순서를 직접 기록한 것이 아니다.
- **서버 코드와 로컬 소스의 동일성:** 「2. 테스트 대상」의 처리 순서와 저장 방식은 로컬 소스에서 확인했다. 실행한 서버의 코드가 이 소스와 같은지는 따로 확인하지 않았다. 서버 로그의 처리 단계와 SQL 순서는 로컬 소스의 처리 순서와 같았다.
- **기존 예약 구매자의 결제:** 작업명세 07의 범위에 따라 기존 예약 구매자의 결제는 보내지 않았다. 종료 후 상태에서 기존 예약 구매자가 예약한 4개를 결제할 수 있는지는 확인하지 못했다.
- **응답 시간:** 요청 두 건의 시간이므로, 작업명세 06의 동시 요청 18건 응답 시간 목표는 이 결과로 판정할 수 없다.
