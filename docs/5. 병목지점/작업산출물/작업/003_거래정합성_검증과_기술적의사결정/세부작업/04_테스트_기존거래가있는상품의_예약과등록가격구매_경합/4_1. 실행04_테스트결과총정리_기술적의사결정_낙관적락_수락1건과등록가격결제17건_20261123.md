## 1. 요청 18건의 처리 순서

아래 표는 서버가 요청을 끝낸 순서다. 표의 열은 다음과 같다.

- **시도 횟수:** 서버가 그 요청의 결제나 수락을 처음부터 처리한 횟수다. 2번 이상인 요청은 앞 시도가 커밋하지 못하고 롤백되어 서버가 다시 처리한 요청이다.
- **마지막 시도가 판단에 쓴 남은 수량, 마지막 시도가 판단에 쓴 구매 가능 수량:** 그 요청의 마지막 시도가 수량을 판단할 때 쓴 값이다. 앞 시도가 쓴 값은 이 표에 없다. 구매 가능 수량은 남은 수량에서 유효 예약을 뺀 수량이다. 유효 예약은 수락이 커밋되기 전에는 4개(기존 예약), 수락이 커밋된 뒤에는 6개(기존 예약 4개와 새 예약 2개)였다.
- **결과:** 그 요청이 받은 응답이다. 마지막 시도가 커밋된 요청은 성공이고, 마지막 시도에서 구매 가능 수량이 부족했던 요청은 거절이다.
- **마지막 시도가 저장한 남은 수량:** 마지막 시도가 커밋하면서 상품에 저장한 남은 수량이다. 거절된 요청과 수락은 남은 수량을 저장하지 않았다.

**확인한 사실**

- **같은 출발 시점의 요청이 처리된 과정**
  - 30초, 60초, 90초에 함께 출발한 요청들은 첫 시도에서 상품의 남은 수량을 모두 같은 값으로 조회하였다. 요청들이 조회한 때는 그 가운데 어느 요청도 아직 커밋하기 전이었다.
    - 30초: 결제 2건이 모두 13개를 조회하였다.
    - 60초: 결제 4건이 모두 11개를 조회하였다.
    - 90초: 결제 6건과 수락 1건이 모두 7개를 조회하였다.
  - 요청들은 저마다 조회한 남은 수량으로 수량을 판단하였고, 첫 시도에서 모두 통과하였다. 60초를 예로 들면, 결제 4건이 저마다 남은 수량 11개에서 1개를 살 수 있다고 판단하였다.
  - 통과한 요청 가운데 출발 시점마다 한 건만 커밋되었다. 나머지 요청은 롤백되었고 서버가 다시 처리하였다. 다시 처리한 요청은 앞서 커밋된 주문과 예약이 반영된 수량으로 판단하였다.
  - 90초의 둘째 시도에서는 새로 확보할 수 있는 수량이 2개였는데, 결제 5건과 수락 1건(2개)이 모두 통과로 판단하였다. 수락만 커밋되었고, 결제 5건은 셋째 시도에서 구매 가능 수량 0개로 판단하여 거절되었다.
- **수량**
  - 새로 확보할 수 있는 9개가 모두 확보된 뒤의 요청은 모두 거절되었다. 30초에 2개, 60초에 4개, 90초에 결제 1개와 수락 2개가 확보되어 9개가 되었다. 90초의 나머지 결제 5건과 120초, 180초의 결제 5건은 거절되었고, 거절된 구매자에게 주문과 결제 차감은 없다.
  - 90초에 수락이 성공하였다. 90초의 요청이 출발하기 전에 새로 확보할 수 있는 수량은 3개였고, 이 3개를 새 등록 가격 구매자 12의 결제 1개와 수락 2개가 확보하였다. 새 등록 가격 구매자 12의 주문에 저장된 구매 확정 시각이 수락의 예약에 저장된 예약 시각보다 60ms 이르다.
  - 구매자 한 명에게 주문이 2건 이상 생기지 않았다. 결제가 성공한 7명에게 주문이 1건씩 있다.
- **롤백된 시도가 DB에 남긴 것이 없는지**

  - 롤백된 시도가 만든 주문과 예약은 DB에 남지 않았다.
    - 수량 판단을 통과한 시도는 주문이나 예약을 만든다. 그 시도가 롤백되면 만든 주문이나 예약도 함께 취소된다.
    - 수량 판단을 통과한 뒤 롤백된 시도 18번은 주문 17건과 예약 1건을 만들었다.
    - 이 18건은 종료 후 DB 조회 결과 반영되지 않았다.
    - 새 등록 가격 구매자 03의 결제를 예로 들면, 시도 4번에서 주문을 4번 만들었고 DB에는 커밋된 넷째 시도의 주문 1건만 있다.

  - DB에 남은 주문 ID와 예약 ID는 번호가 중간에 빠져 있다.
    - 롤백된 시도가 만든 주문과 예약도 번호를 하나씩 받았고, 롤백되면서 그 번호는 쓰이지 않은 채로 남았다.
    - 성공한 결제 7건의 주문 ID는 283, 284, 286, 289, 292, 294, 298이다.
    - 새 예약의 ID는 203이다.
    - 그 사이에 빠진 주문 ID 17개와 예약 ID 1개는 롤백된 시도의 로그에 적힌 번호와 같다.
    - 결제 차감의 잔액 변동 ID(460, 462, 463, 467, 470, 472, 475)도 번호가 중간에 빠져 있다.

  - 상품의 버전은 커밋된 요청의 건수만큼만 올랐다.
    - 상품의 버전은 결제나 수락이 커밋될 때마다 1씩 오르는 번호다.
    - 검증 요청을 보내기 전에는 2였다. 기존 주문 구매자의 결제 뒤에 1이 되었고, 판매자가 기존 예약 구매자의 가격 제안을 수락한 뒤에 2가 되었다.
    - 검증 요청이 끝난 뒤에는 10이었다.
    - 검증 요청 동안 오른 8은 성공한 결제 7건과 성공한 수락 1건을 더한 건수와 같다.
    - 수락은 상품의 남은 수량을 바꾸지 않지만 버전은 1 올렸다.

## 2. 응답 시간

JMeter에서 측정한 응답 시간은 JMeter가 전송을 시작한 때부터 응답을 모두 받은 때까지의 시간이다. 서버의 요청 처리 시간은 서버가 요청을 받은 때부터 응답을 보낼 때까지의 시간으로, 서버 로그에 남은 값이다.

| 기능 | 결과 | 건수 | 측정한 시간 | 최소 | 최대 | 평균 | 중앙값 |
|---|---|---:|---|---:|---:|---:|---:|
| 가격 제안 수락 | 성공 | 1건 | JMeter에서 측정한 응답 시간 | 118ms | 118ms | 118.0ms | 118ms |
| | | | 서버의 요청 처리 시간 | 100ms | 100ms | 100.0ms | 100ms |
| 등록 가격 결제 | 성공 | 7건 | JMeter에서 측정한 응답 시간 | 86ms | 270ms | 184.9ms | 207ms |
| | | | 서버의 요청 처리 시간 | 60ms | 213ms | 113.4ms | 108ms |
| 등록 가격 결제 | 거절 | 10건 | JMeter에서 측정한 응답 시간 | 131ms | 188ms | 150.3ms | 137.5ms |
| | | | 서버의 요청 처리 시간 | 11ms | 116ms | 62.8ms | 61ms |

- 18건 모두 1초 안에 응답하였다.
- JMeter에서 측정한 응답 시간은 서버의 요청 처리 시간보다 길다. JMeter가 서버에 연결하는 데 걸린 시간이 함께 들어 있기 때문이다. 연결하는 데 걸린 시간은 출발 시점마다 달랐다.
  - 30초: 67ms
  - 60초: 45ms
  - 90초: 7~9ms
  - 120초: 158ms
  - 180초: 118ms
- 120초와 180초에 거절된 결제 5건은 JMeter에서 측정한 응답 시간이 142~188ms였다. 이 가운데 118~158ms가 서버에 연결하는 데 걸린 시간이고, 서버의 요청 처리 시간은 11~12ms였다.
- 60초에 성공한 결제 4건은 주문에 저장된 구매 확정 시각이 56ms, 53ms, 45ms 간격으로 이어졌다. 구매 확정 시각은 서버가 주문을 만들 때 주문에 저장하는 시각이다. 이 4건의 JMeter에서 측정한 응답 시간도 133ms, 176ms, 215ms, 270ms로 차례로 길어졌다.
- 실행03의 JMeter 응답 시간은 성공한 결제 9건의 중앙값이 119ms, 거절된 결제 8건의 중앙값이 44ms였다. 실행04가 더 길게 나왔지만, 연결 시간이 섞여 있으므로 두 실행의 차이는 서버의 요청 처리 시간으로 비교해야 한다.

## 3. 아직 확인하지 않은 것

- **수량 판단을 통과한 시도 18번이 롤백된 사유:** 서버 로그로 확인한 것은 이 18번이 상품 UPDATE 문을 실행한 직후에 롤백되었고, 서버가 그 요청을 다시 처리하였다는 것까지다. 왜 롤백되었는지는 로그에 없다. 서버는 롤백한 뒤에 실패 사유를 로그로 남기는데, 이 18번의 실패 사유는 「미상(커밋 처리 중 오류 또는 사유를 적지 못한 예외)」으로 남았다. 서버가 커밋 처리 중에 난 오류의 사유는 기록하지 않기 때문이다.
- **새 수락이 거절되는 결과:** 작업명세 10 「1.6 테스트 종료 후 기대 결과」의 두 기대 결과 가운데 이 실행에서 나온 것은 새 수락이 성공하는 결과다. 한 번만 실행하였으므로 새 수락이 거절되는 결과는 확인하지 못하였다.
