DB로그_2_엑셀정리.py 실행 방법

[하는 일]
DB로그_1_p6spy기록_CSV추출.py가 만든 p6spy 기록 CSV와 웹애플리케이션로그_1_CSV추출.py가 만든 웹 애플리케이션 로그 CSV를 읽어, 기존 주문과 기존 예약이 있는 상품에 출발 시점을 나누어 보낸 수락·결제 검증 요청 18건이 DB에 보낸 SQL과 커밋·롤백을 확인할 수 있게 엑셀 파일 하나로 정리한다.
18건은 판매자가 새 흥정 구매자의 가격 제안을 수락하는 요청 1건(accept-new)과 새 등록 가격 구매자 17명이 등록 가격으로 1개씩 결제하는 요청 17건(pay-01부터 pay-17까지)이다.
출발 시점은 다섯 개(30초, 60초, 90초, 120초, 180초)이고, 같은 출발 시점에 배정된 요청끼리 함께 출발했다.
요청과 p6spy 기록은 로깅 설계 문서(작업명세 04·05) 「1.1 애플리케이션 로그와 p6spy 기록」에 적힌 방법으로 잇는다. 같은 서버 스레드에서 그 요청의 요청수신 로그부터 요청응답 로그 사이에 남은 p6spy 기록이 그 요청의 것이다.
대상은 실행 ID가 --run-id와 같은 요청 가운데, 검증 요청 결과 파일(검증요청_결과.csv)에 서버 로그 요청 ID가 적힌 검증 요청이다. 세 시트 모두 요청을 서버가 요청을 끝낸 순서(요청마다 커밋완료 로그나 롤백완료 로그가 서버 로그에 남은 시각이 이른 순서)로 둔다. 웹 애플리케이션 로그 정리 엑셀과 같은 순서다.
같은 실행 ID로 서버 로그에 남은 준비 요청 2건(기존 주문을 만든 준비 결제 prep-order-existing, 기존 예약을 만든 준비 수락 prep-accept-existing)은 엑셀에 넣지 않는다.
구간은 웹 애플리케이션 로그 엑셀의 시트 3과 같다(요청의 로깅 설계 문서 로그 하나와, 같은 요청에서 그 바로 앞에 남은 로그 사이).
p6spy 기록이 어느 구간에 드는지는 서버 로그 파일의 줄 순서로 정한다. p6spy 기록의 시각은 1/1,000초까지라 1/1,000,000초까지 있는 설계 로그 시각과 비교하면 같은 1/1,000초 안의 앞뒤를 가를 수 없기 때문이다.
입력 파일은 읽기만 한다. 출력 파일이 이미 있으면 덮어쓰지 않고 중단한다.

[시트 구성]
1_요청별SQL          요청마다, 구간마다 그 요청 자신의 p6spy 기록을 표 하나에 둔다.
                     표의 열은 chatservice.log 줄 번호, p6spy 기록 시각, SQL 실행에 걸린 시간, p6spy 기록 구분, DB 연결 번호, SQL 이름, 바인드 값을 넣은 SQL이다.
                     「SQL 이름」 칸에는 로깅 설계 문서 「2.1 요청 하나에서 로그가 남는 순서」의 SQL 이름을 적는다.
                     수락 요청은 작업명세 04의 「직전에 실행되는 SQL」 열의 이름(가격 제안 조회, 상품 조회, 대화 조회, 같은 구매자의 예약 조회, 상품의 예약 조회, 예약 INSERT,
                     대화 상태 이벤트를 만들기 위한 조회, 가격 제안 UPDATE)이다.
                     결제 요청은 작업명세 05의 「앞 로그부터 이 로그까지 p6spy에 남는 SQL」 열의 이름(상품 조회, 상품의 예약 조회, 주문 INSERT 등)이다.
                     수락 요청의 수량판단 구간과 결제 요청의 남은수량판단 구간에 있는 상품 조회는 SQL 끝에 for update가 붙은 잠금을 얻는 상품 조회다.
                     성공한 결제 요청의 요청응답 구간에 있는 상품 조회는 응답 본문을 만드는 조회이고 for update가 없다.
                     거절된 요청은 수량을 판단한 구간까지의 SQL과 롤백완료 구간의 ROLLBACK만 남는다.
2_요청별시간         요청 18건의 시간 값을 표 두 개에 요청마다 한 행씩 둔다. 두 표 모두 행은 서버가 요청을 끝낸 순서다.
                     표 1 「요청별 잠금 시간: 요청마다 상품 행의 잠금을 얻기까지 걸린 시간과 잠금을 가진 시간」은 열을 요청이 처리되는 순서로 둔다.
                     열은 JMeter 헤더 로그용 요청 ID, 구매자, 잠금을 얻는 상품 조회의 SQL 실행에 걸린 시간, 잠금을 얻는 상품 조회의 기록 시각, 커밋 기록 시각, 롤백 기록 시각,
                     잠금을 얻는 상품 조회 기록부터 커밋 기록까지의 시간, 잠금을 얻는 상품 조회 기록부터 롤백 기록까지의 시간이다.
                     출발 시점이 같은 요청을 「출발 시점 60초」 같은 구분 줄 아래에 묶는다.
                     잠금을 얻는 상품 조회는 바인드 값을 넣은 SQL이 상품 테이블 조회이고 끝에 for update가 붙은 기록이다. 수락 요청은 수량판단 구간에, 결제 요청은 남은수량판단 구간에 한 건씩 있다.
                     잠금을 얻는 상품 조회의 SQL 실행에 걸린 시간은 그 기록의 「took」 값이다. 조회 자체의 실행 시간과, 다른 요청이 같은 상품 행의 잠금을 가지고 있어 기다린 시간이 함께 들어 있고,
                     잠금을 기다린 시간만 따로 기록한 값은 없다.
                     커밋된 요청은 커밋완료 구간의 commit 기록을 「커밋 기록 시각」 열에, 거절되어 롤백된 요청은 롤백완료 구간의 rollback 기록을 「롤백 기록 시각」 열에 두고, 해당하지 않는 열의 칸은 「-」로 둔다.
                     결제 요청의 요청응답 구간에 남은 응답 조회 트랜잭션의 commit 기록은 쓰지 않는다.
                     잠금을 얻는 상품 조회 기록부터 커밋 기록까지의 시간은 커밋 기록 시각에서 잠금을 얻는 상품 조회의 기록 시각을 뺀 값이다.
                     롤백된 요청은 롤백 기록 시각에서 잠금을 얻는 상품 조회의 기록 시각을 뺀 값을 「잠금을 얻는 상품 조회 기록부터 롤백 기록까지의 시간」 열에 둔다.
                     표 2 「요청별 그 밖의 시간: 처리 전체 시간, DB 연결 대기, 반복하는 예약 조회, 상품 UPDATE」는 표 1에 두지 않은 값을 두고, 요청마다 출발 시점(초)을 함께 둔다.
                     첫 SQL 기록부터 커밋 기록까지의 시간(롤백된 요청은 롤백 기록까지의 시간), DB 연결 대기(추정), 대화 상태 이벤트를 만들려고 대화마다 반복하는 예약 조회의 건수와 시간을 계산해 둔다.
                     「첫 SQL 기록부터 커밋 기록까지의 시간」 열과 「첫 SQL 기록부터 롤백 기록까지의 시간」 열도 같은 방식으로 나누어 둔다.
                     반복하는 예약 조회는 커밋전 구간에 남은 예약 조회 가운데 상품 ID와 예약 상태로 조회한 기록이다. 거절된 요청은 커밋전 구간이 없어 건수가 0이고 시간 두 칸이 「-」다.
                     결제 요청의 행에는 상품 UPDATE 기록 시각, 상품 UPDATE의 SQL 실행에 걸린 시간, 상품 UPDATE에 적힌 남은 수량을 둔다.
                     상품 UPDATE는 결제 요청이 커밋할 때 상품의 남은 수량을 DB에 쓰는 SQL이고, 적힌 남은 수량은 그 SQL의 REMAINING_QUANTITY 값이다.
                     다른 요청이 같은 상품 행을 먼저 고치고 아직 커밋하지 않았으면, 그 커밋을 기다린 시간이 상품 UPDATE의 SQL 실행에 걸린 시간에 남는다고 추론한다
                     (작업명세 05 「2.1 요청 하나에서 로그가 남는 순서」). 수락 요청은 상품을 고치지 않고, 거절된 결제 요청은 상품 UPDATE 기록이 남지 않으므로 세 칸이 「-」다.
3_구간별다른요청SQL  기준 요청마다, 구간마다 그 사이에 남은 다른 요청(수락 요청과 결제 요청 모두)의 p6spy 기록을 서버 로그 파일의 줄 순서대로 표 하나에 둔다.
                     chatservice.log 줄 번호를 누르면 시트 1의 그 기록으로 이동한다. 건수를 세거나 영향을 판단하는 열은 두지 않는다.
각 시트 아래에는 열마다 무슨 데이터인지 적은 열 설명 표가 있다. 시트 1과 시트 3은 요청마다 엑셀의 행 그룹으로 묶었다.

[인자]
--p6spy             DB로그_1_p6spy기록_CSV추출.py가 만든 p6spy 기록 CSV. 스크립트는 CSV 칸 길이 한도를 늘려 읽는다. 실행02의 서버 로그에는 바인드 값을 넣은 SQL이 55만 자를 넘는 기록이 있었고, 실행03의 서버 로그에서 가장 긴 SQL은 593자다
--web-csv           웹애플리케이션로그_1_CSV추출.py가 만든 웹 애플리케이션 로그 CSV. 요청의 서버 스레드, 로깅 설계 문서 로그의 줄 번호와 시각, 인증 성공 시각을 읽는다
--run-id            정리할 수락·결제 경합의 실행 ID. 11:21 「실행 시작」 그룹이 만든 실행 ID다
--prepare-baseline  「요청 전 확인」 그룹이 실행 폴더에 남긴 요청 전 기준값 파일(요청전_기준값.json). 역할별 회원 ID, 대화 ID, 새 흥정 구매자의 제안 ID를 찾는다
--request-result    「결과 집계」 그룹이 실행 폴더에 남긴 검증 요청 결과 파일(검증요청_결과.csv). 검증 요청마다 요청 종류, 요청자, 회원 ID, 출발 시점, 서버 로그 요청 ID를 읽는다. 이 파일에 서버 로그 요청 ID가 있는 요청만 엑셀에 넣는다
--output            만들 엑셀 파일. 폴더가 없으면 만든다

[py -V:3.13]
이 노트북에 설치된 Python 3.13으로 실행하라는 뜻이다. 엑셀 파일을 만드는 openpyxl이 이 Python에 설치되어 있다.

실행하면 화면에 요청 건수, 같은 실행 ID로 남았지만 엑셀에 넣지 않은 준비 요청, 요청마다 구매자·서버 스레드·p6spy 기록 건수·구간별 기록 건수·반복하는 예약 조회 건수, 요청 18건의 p6spy 기록 합계,
잠금을 얻는 상품 조회 기록이 한 건인 요청의 수, 시트 3에 넣은 행 수, 저장한 파일 경로가 나온다.
SQL 이름을 정하지 못한 기록이 있으면 그 건수도 나오고, 잠금을 얻는 상품 조회 기록이 한 건이 아닌 요청이 있으면 그 요청 ID와 건수도 나온다.
