# Instawork형 — 단기 근무 매칭과 근무 책임 이전

> 상태: **우선 선택지 / 백업 후보로 보존**. 최종 주제·구현 착수·기술 스택을 확정하는 문서가 아니다. 다른 두 후보와 순위를 정하지 않는다. 작성·공개 자료 확인: 2026-09-25.

## 1. 문서의 전제와 근거 구분

- **[사실·공식]** 실제 제품의 공개 안내에서 확인한 내용이다. 내부 구현까지 확인한 것은 아니다.
- **[사실·첨부]** 제공된 기획 자료·포트폴리오에 기재된 내용이다. 구현 코드나 실험 결과를 독립 검증했다는 뜻은 아니다.
- **[설계 추론]** 업무 규칙에서 도출한 백엔드 문제와 해결 후보다. 실제 Instawork의 아키텍처나 사고 사례가 아니다.
- **[프로젝트 가정]** 개인 프로젝트에서 선택할 수 있는 정책·상태 모델·실험 수치다. 아직 채택하거나 실험하지 않았다.
- **[미확인]** 정책의 적용 조건, 자료 간 차이, 실제 운영 규모 등 확인하지 못한 내용이다.

검토 근거는 첨부된 「서비스 도메인 우선 실시간 백엔드 웹 프로젝트 조사 — 새 세션용 기획 프롬프트 v4.md」, 「프로젝트_기획의_실제_고민과_의도.txt」, 「1_새프로젝트기획_참고_커뮤니티글정리.txt」, 「ChatService_포트폴리오.pptx」와 대화 「조사 바로 시작」이다. 슬라이드는 1~5장의 텍스트를 확인했다. 커뮤니티 글은 판단 방식의 참고이며 채용 효과나 기술 정답의 증거로 사용하지 않는다.

최신 대화의 판단을 따른다. 주제의 희소성보다 업무 규칙에서 의사결정과 실험이 이어지는지가 중요하다. 공통적인 거래·배정 구조를 가진다는 이유만으로 탈락시키지 않되, 기술 실험을 위해 정책을 덧붙이는지도 검토한다.

## 2. 서비스 정체성과 사용자·사업 목적

**[사실·공식]** Instawork는 사업자의 근무 수요와 일할 사람을 연결한다. 근무자는 시간·장소·요건을 확인해 근무를 잡고, 출근 의사를 확인하고, 실제 근무 시간을 기록한다. [How to be successful on Instawork](https://help.instawork.com/en/articles/4375343-how-to-be-successful-on-instawork)

**[설계 추론]** 보존할 프로젝트 정체성은 **“사업자가 필요한 근무자를 확보하고, 근무자가 자신의 일정과 자격에 맞는 일을 맡아 완료하는 서비스”**다. 사람을 사고파는 서비스로 표현하지 않는다.

| 참여자 | 달성하려는 목적 | 시스템이 잘못되었을 때의 손해 |
|---|---|---|
| 사업자 | 필요한 시간대의 근무 책임자 확보 | 명단에는 충원됐지만 실제로 아무도 책임지지 않음 |
| 근무자 | 수행 가능한 일을 선택하고 책임·보수를 명확히 확인 | 넘긴 근무가 여전히 자신의 책임으로 남거나 이중 배정됨 |
| 운영자 | 취소·미확인·분쟁을 추적하고 정상 업무로 복구 | 잘못된 책임 기록 때문에 취소 귀책이나 근무 이력 판단이 왜곡됨 |

사업 관점의 프로젝트 목표는 충원 상태와 실제 배정 책임을 일치시키고, 빈자리를 제때 다시 모집하는 것이다. 매출·수수료 구조나 실제 충원율 개선은 이 문서에서 검증하지 않는다.

## 3. 공식 확인과 프로젝트 정책의 경계

**[사실·공식]** 양도는 자격을 갖춘 다른 근무자에게 근무를 넘기는 절차다. 성공 전에는 기존 근무자의 책임이 유지되고, 상대방이 수락하면 책임이 이전된다. 계정 상태·직무 자격·일정 충돌·사업자 제한 등이 조건이다. [How do shift transfers work?](https://help.instawork.com/en/articles/12675783-how-do-shift-transfers-work)

**[사실·공식]** 근무 재확인을 하지 않으면 자동 취소될 수 있고, 취소는 재충원 문제로 연결된다. [How to be successful on Instawork](https://help.instawork.com/en/articles/4375343-how-to-be-successful-on-instawork)

**[미확인]** 시간 조건은 단정하지 않는다. 공식 양도 문서에는 시작 전 12시간 제한과 같은 날의 90분 조건이 함께 등장한다. 확인 안내도 문서에 따라 32시간·36시간 표현이 다르다. 이를 하나의 일관된 정책으로 임의 합성하지 않는다. 양도받은 사람에게 재확인이 필요한지도 추가 확인 대상이다. [Understand your performance score](https://help.instawork.com/en/articles/6449818-understand-your-performance-score)

**[프로젝트 가정]** 첫 모델은 사업자 한 곳의 단일 근무를 한 자리 단위로 나눈다. 자격은 승인된 직무 여부로 단순화하고, 일정 충돌 검증을 포함한다. 양도는 확인 마감 D 이전에만 가능하며 수락 자체가 새 책임자의 확인을 겸한다. 기존 근무자의 취소가 먼저 확정되면 양도 요청은 무효다. 동일 시각 경계에서는 DB에서 현재 상태를 검사하는 시점을 기준으로 `now < D`일 때만 확인·양도를 허용한다. D 이후 미확인 배정은 취소한다. 이 정책은 실제 제품의 복제가 아닌 비교 가능한 초안이다.

## 4. 핵심 업무 흐름과 깊게 팔 백엔드 흐름

전체 연결 흐름은 다음과 같다.

1. 사업자가 직무·시간·인원·보수를 포함한 근무를 게시한다.
2. 근무자가 요건과 자신의 일정을 확인해 지원하고 배정을 받는다.
3. 배정된 근무자가 기한 안에 근무 의사를 확인한다.
4. 수행이 어려우면 취소하거나 다른 적격 근무자에게 양도를 요청한다.
5. 취소·미확인으로 비면 다시 모집한다. 양도가 성공하면 새 책임자로 명단을 바꾼다.
6. 근무 완료와 시간 확인을 거쳐 보수 확정 기록을 남긴다.

**[설계 추론]** 심층 대상은 **배정 책임 이전 ↔ 기존 책임자의 취소 ↔ 확인 마감 ↔ 재충원**이다. 이 흐름을 제거해도 근무 게시·자격 검증·배정·근무 완료라는 서비스 목적이 남는다. 다만 첫 MVP는 양도 수락·취소·마감의 한 경계에 집중하고, 급여 계산이나 평가 알고리즘까지 확장하지 않는다.

대표 질문은 “A가 B에게 양도를 요청한 뒤 A의 취소, B의 수락, 확인 마감 처리가 교차하면 현재 책임자는 누구인가?”이다. 답은 락 종류를 고르기 전에 업무 정책으로 정해야 한다.

## 5. Actor / Entity / State / Invariant

이 절은 전부 **[프로젝트 가정]**이며 실제 내부 모델이 아니다.

| 구분 | 모델과 책임 |
|---|---|
| Actor | Business는 근무 게시·취소·완료 확인, Worker는 자신의 배정 확인·양도·취소, Scheduler는 기한 처리, Operator는 사유를 남긴 복구 |
| Shift / ShiftPosition | 근무 시간·자격 조건과 한 자리의 현재 배정 참조 |
| WorkerQualification | 직무 승인 상태. 수락 시 다시 검증 |
| Assignment | 자리·책임자·확인 상태·마감·버전·종료 사유 |
| TransferRequest | 대상 배정 버전·보내는 사람·받는 사람·유효기간 |
| WorkRecord | 실제 완료·시간 승인·모의 보수 확정 기록 |

| 객체 | 상태 전이 | 조건 |
|---|---|---|
| 근무 자리 | OPEN → ASSIGNED → COMPLETED | 게시, 유효 배정, 근무 완료 |
| 배정 | PENDING_CONFIRMATION → CONFIRMED → COMPLETED | 책임자가 기한 내 확인, 완료 승인 |
| 배정 | PENDING_CONFIRMATION / CONFIRMED → CANCELLED | 정책상 허용된 취소. 미확인 만료는 reason=DEADLINE |
| 배정 | 기존 배정 → TRANSFERRED, 새 배정 → CONFIRMED | 한 트랜잭션에서 기존 책임 해제와 새 책임 부여 |
| 양도 요청 | PENDING → ACCEPTED / DECLINED / EXPIRED / INVALIDATED | 수락·거절·시간 초과·대상 배정 변경 |

지켜야 할 조건:

1. 한 자리의 활성 배정은 최대 하나다. 배정이 없으면 명시적으로 OPEN 또는 사업자 취소 상태여야 한다.
2. 양도 요청만으로 기존 책임이 사라지지 않는다. 성공 시 기존 배정 종료·새 배정 생성·자리 참조 변경은 함께 커밋된다.
3. 이미 이전된 배정을 대상으로 한 A의 늦은 취소는 B의 배정을 취소할 수 없다. 명령에는 assignmentId와 예상 버전을 사용한다.
4. 수락자의 자격과 일정은 수락 시점에 유효해야 한다. 서로 다른 자리에서 같은 사람을 동시에 배정하는 경쟁도 막는다.
5. 만료 워커는 이미 확인되거나 교체된 배정을 취소할 수 없다. 마감 시각만 보고 갱신하지 않는다.
6. 중복 요청·재시작에도 같은 양도 수락의 업무 효과는 한 번이다. 감사 이력에는 주체·대상·전후 버전·결과를 기록한다.

허용되지 않는 전이는 충돌 사유와 현재 상태를 반환한다. 운영자 복구도 원시 DB 수정이 아니라 검증된 명령과 감사 기록으로 수행한다.

## 6. 실시간성의 업무상 필요

**[설계 추론]** 책임 변경의 원본은 서버다. 양도가 성공했는데 사업자는 계속 A를 책임자로 보면 출근 확인과 재충원 판단이 틀어진다. 빈자리 복구가 늦으면 근무 시작까지 대체 인력을 구할 시간이 줄어든다.

| 단계 | 완료의 의미 | 초안의 보장 |
|---|---|---|
| 명령 접수 | 요청을 받음 | 아직 양도 성공이 아님 |
| DB 커밋 | 새 책임자와 기존 책임 해제를 확정 | 성공 응답 전에 완료 |
| 후속 알림 | 상대방·사업자에게 변경 전달 | 실패하면 재시도 가능 |
| 화면 갱신 | 사용자가 최신 명단 확인 | 지연 가능하지만 다음 명령에서 원본 재검증 |

**[프로젝트 가정]** 화면 갱신 목표는 2초 이내, 마감 처리 지연 목표는 5초 이내로 먼저 실험한다. 실제 서비스 SLA가 아니다. 초기에는 polling으로 충분한지 확인하고, 다수 명단 구독자에게 변경을 밀어줄 필요가 확인되면 SSE를 비교한다. 양방향 지속 연결이 필요한지 확인되지 않았으므로 WebSocket은 필수가 아니다. 알림 도착이 책임 이전의 성립 조건이 되지 않는다.

## 7. 경쟁·장애·복구 시나리오

모두 **[설계 추론 / 실험 시나리오]**이며 실제 장애 사례가 아니다.

### 7.1 양도 수락과 취소·마감 경쟁

A의 배정 v7과 B에게 보낸 요청이 존재한다. B의 수락과 A의 취소가 같은 상태를 읽고, 마감 워커도 v7을 대상으로 실행한다. 각각 별도 저장하면 자리만 풀리거나 B와 새 지원자가 동시에 배정될 수 있다. 배정·자리·양도 상태를 한 경계에서 검사하고 갱신해야 한다. 수락이 먼저 성공하면 과거 v7에 대한 취소·마감은 무효다. 취소가 먼저 성공하면 B에게 수락 실패를 명확히 돌려준다. 정확히 D부터는 신규 확인·수락을 거절한다.

### 7.2 B가 다른 근무도 동시에 수락

서로 다른 자리의 행만 잠그면 두 트랜잭션 모두 B의 빈 일정을 보고 성공할 수 있다. 근무자별 일정 직렬화나 DB의 시간 구간 제약을 비교한다. 자리 단위 락만으로 모든 불변조건을 보장했다고 주장하면 안 된다.

### 7.3 커밋 직후 프로세스 종료

책임 이전은 커밋됐지만 응답·알림 전에 종료된다. B가 다시 요청하면 동일 멱등키로 기존 결과를 반환한다. 후속 알림을 DB의 전송 대기 기록과 함께 저장했다면 워커가 재전송한다. 알림 실패 때문에 양도를 되돌리지 않는다.

### 7.4 재시작 후 만료 작업 재실행

메모리 타이머에만 의존하면 마감 작업을 잃는다. DB에 마감과 처리 상태를 두고 재조회한다. 중복 워커가 같은 대상을 집어도 조건부 전이로 한 번만 취소한다. 처리 실패는 감지, 격리, 재처리, 원본 상태 대조를 구분한다. 영구 대기 배정과 자리 참조 불일치는 운영자 확인 대상으로 남긴다.

## 8. 기술 탐구 경로

| 업무 제약 → 실패 경계 | 먼저 볼 지표 | 단순 대안 비교 | 추가 기술 검토 조건과 비용 |
|---|---|---|---|
| 책임자를 하나로 확정 → 읽기와 갱신 사이 경쟁 | 이중 배정·stale 명령 성공·락 대기 | RDB 행 잠금 vs 버전 조건부 갱신 | 낙관 재시도 폭증 시 정책 변경. 분산 락은 실패·만료 문제까지 추가 |
| 같은 사람의 시간 충돌 방지 → 여러 자리 교차 갱신 | 일정 중복·교착·거절률 | 근무자 행 직렬화 vs DB 시간 구간 제약 | 실제 선택 DB에서 지원·비용 확인 필요 |
| 마감 이후 빈자리 회복 → 워커 지연·중복 | deadline lag·미처리 수·복구시간 | DB 기한 스캔과 조건부 처리 | 작업 큐는 처리량·격리 필요가 관측될 때. 재전달·운영 비용 발생 |
| 확정 사실의 통지 → 커밋/전송 간 종료 | 누락 알림·재전송 수·최고 대기시간 | 같은 DB 전송 대기 테이블 | outbox 워커와 재시도 설계. 브로커까지 필수는 아님 |

Spring 계열 단일 애플리케이션과 RDB를 출발 후보로 둔다. JVM 탐구는 락 대기, DB 커넥션 대기, 실행 큐, GC·할당량을 관측한 뒤 연결한다. CPU가 낮고 응답이 느리다는 이유만으로 가상 스레드를 선택하지 않는다. 외부 알림의 I/O가 병목이면 제한된 실행 풀과 별도 실행 단위를 먼저 비교하며, 가상 스레드도 DB 용량이나 업무 경쟁을 해결하지는 않는다는 조건에서 실험한다.

## 9. 실험 방향

**[프로젝트 가정]** 상용 서비스 트래픽을 재현한다는 뜻이 아니다. 자신의 테스트 서버에만 부하를 보낸다.

- 기준: 근무자 100명, 근무 자리 50개, 동시 명령 10개, 조회/변경 요청 8:2.
- 경쟁: 같은 배정에 20개 명령 집중, 마감 전후 100ms에 수락·취소·확인 주입. 서로 다른 자리에서 동일 B에게도 동시 요청.
- 장애: API 2개 인스턴스, 중복 워커 2개, 동일 요청 10% 재전송, 커밋 직후 종료, 알림 응답 0.1초/2초/timeout.
- 시간 정책은 가상 시계로 결정적 순서를 검증하고, DB를 포함한 통합 시험에서는 실제 경계 경쟁을 별도로 확인한다.

가설 H1: 자리 단위 보호만으로는 근무자 시간 충돌이 남는다. H2: 조건부 갱신은 낮은 경합에서 단순하지만 높은 경합에서 재시도 비용이 커질 수 있다. H3: DB 기한 기록은 재시작 후 미처리 배정을 복구할 수 있다. 모두 결과가 반대로 나올 수 있는 가설이다.

판정 지표는 이중 책임자 수, 일정 중복, 잘못된 취소, 미충원 지속시간, p95/p99, 락·커넥션 대기, 재시도 수, 복구 후 상태 불일치다. 같은 데이터·정책·자원·부하 seed로 비교하고 예열 후 5회 반복하는 초안을 둔다. 업무 불변조건 위반 0건을 필수로 삼되 유한한 실험의 무위반을 모든 실행의 증명으로 표현하지 않는다. 아직 실험 결과나 성능 개선 수치는 없다.

## 10. 기존 ChatService와의 차이

**[사실·첨부]** 기존 PPT에는 HTTP→WebSocket 2단계 입장, 방별 Semaphore, sessionKey, TTL 회수, 200 동시 요청×10개 방 실험이 기재돼 있다. 이번 문서는 그 성과나 기술적 판단을 부정하지 않으며 PPT의 수치를 재측정한 것도 아니다.

**[설계 추론]** 겹치는 부분은 한정된 자리와 만료 처리다. 새롭게 보여줄 부분은 **현재 책임자가 누구인가, 누가 과거 명령을 행사할 수 있는가, 다른 근무와 동시에 책임질 수 있는가, 재시작 후에도 책임 기록이 유지되는가**다. 연결의 수명에서 업무 책임의 수명으로 중심이 이동한다. 단순 선착순 배정에서 끝나면 차별성이 약해진다. 기존 인증·관측 코드의 재사용은 가능하지만 인메모리 정원 모델에 도메인을 맞추지 않는다.

## 11. 장점·위험·미확인 사항

- **장점 [정성 평가]:** 자격·시간·취소·책임 이전이 연결되어 업무 질문에서 기술 선택이 나온다. 핵심은 서버와 DB만으로 재현 가능하다.
- **위험:** 단순 자리 예약으로 축소하거나 급여·노무·평판까지 확장하면 목적을 잃는다. 규칙을 많이 넣는 것 자체가 깊이는 아니다.
- **미확인:** 실제 확인·양도 시간 조건, 양도 후 재확인, 계정 정지와 기존 배정의 관계, 실제 이벤트 전달·트래픽·내부 저장 구조.
- **모의 환경의 한계:** 책임 기록과 복구는 검증할 수 있지만 실제 출근 여부·GPS 정확도·현장 노동 제공·실제 보수 지급은 검증하지 못한다.

## 12. 개인 프로젝트 축소 범위와 보존 판단

| 구분 | 범위 |
|---|---|
| 얇게 구현 | 사업자 근무 등록, 직무 승인, 근무 목록, 배정, 완료 확인, 모의 보수 기록 |
| 깊게 구현 | 양도 수락·취소·확인 마감, 현재 책임 검증, 재충원 상태 복구 |
| 후속 실험 | 다중 인스턴스, 알림 outbox, 자격 취소 경쟁, 다수 일정 충돌 |
| 제외 | GPS·경로, 실제 급여·세금·보험, 평판 알고리즘, 자동 추천, 채팅, 장기 근무 묶음 |

보존 이유는 업무 책임과 시간 조건의 연결이다. 다음 검토에서는 한 배정의 전이표와 3개 경쟁 재현만으로 충분한 의사결정이 나오는지 확인한다. 실제 시간 조건에서 양도와 확인 마감이 만날 수 없다면 억지 경합을 만들지 않고 **양도↔취소**, **확인↔마감**을 별도 시나리오로 나눈다. 현재 문서는 선택 가능성을 남기는 초안이며 최종 추천이나 구현 명령이 아니다.
