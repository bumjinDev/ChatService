# Vinted형 — C2C 거래의 배송·분쟁·판매대금 해제

> 상태: **우선 선택지 / 백업 후보로 보존**. 최종 주제·구현 착수·기술 스택을 확정하지 않는다. 세 후보의 순위를 뜻하지 않는다. 작성·공개 자료 확인: 2026-09-25.

## 1. 문서의 전제와 근거 구분

**[사실·공식]**은 공개된 제품 동작, **[사실·첨부]**는 제공 자료의 기재 내용, **[설계 추론]**은 업무에서 도출한 기술 문제, **[프로젝트 가정]**은 개인 구현용 정책·실험 조건이다. **[미확인]**은 현재 사실로 확정하지 못한 사항이다. 제안한 상태 이름·락·테이블·이벤트는 Vinted 내부 구현에 대한 주장이 아니다.

첨부된 「서비스 도메인 우선 실시간 백엔드 웹 프로젝트 조사 — 새 세션용 기획 프롬프트 v4.md」, 「프로젝트_기획의_실제_고민과_의도.txt」, 「1_새프로젝트기획_참고_커뮤니티글정리.txt」, 「ChatService_포트폴리오.pptx」 및 대화 「조사 바로 시작」을 토대로 한다. PPT 1~5장 텍스트를 확인했으며 코드·벤치마크를 재검증한 것은 아니다. 커뮤니티 사례에서는 원인 관측, 단순 대안 비교, 복구 검증이라는 검토 방식을 참고했다.

현재 방향은 특이한 업종을 계속 찾기보다 실제 업무가 기술적 의사결정을 공급하는지 확인하는 것이다. 흔한 커머스라는 첫인상은 위험으로 기록하되 탈락 조건으로 삼지 않는다.

## 2. 서비스 정체성과 사용자·사업 목적

**[사실·공식]** Vinted는 판매자가 상품을 올리고 구매자가 구매하는 마켓플레이스다. 가격 제안 수락만으로 상품이 판매되는 것은 아니며, 다른 사용자에게 계속 구매 가능할 수 있다. [Making an offer](https://www.vinted.com/help/258-wie-mache-ich-dem-kaufer-ein-angebot)

**[설계 추론]** 프로젝트 정체성은 **“개인 간 중고 물품 거래에서 구매·배송·문제 제기·대금 확정을 연결하는 서비스”**다. 사용자 목적은 판매자의 처분·대금 수령과 구매자의 물품 확보·문제 발생 시 구제다. 사업 목적은 거래 당사자들이 완료 상태를 신뢰하게 하는 것이다. 실제 수익 개선이나 사용자 만족 개선은 검증하지 않았다.

| Actor | 목적 | 잘못된 처리의 업무 결과 |
|---|---|---|
| Seller | 하나의 물품을 판매하고 대금 수령 | 다른 구매자에게 중복 판매, 지급 누락 |
| Buyer | 물품 수령과 문제 제기 기회 확보 | 제기한 분쟁보다 대금 해제가 먼저 확정됨 |
| Operator | 증거·처리 이력을 통해 분쟁 종결 | 환불·해제 양쪽이 실행되거나 처리 근거가 사라짐 |

## 3. 확인된 정책과 축소 가정

**[사실·공식]** 미국 영문 도움말은 배송 관련 통지 후 2일 안에 문제를 제기하는 흐름과, 문제없음 확인 또는 기한 경과 시 거래 완료·대금 해제를 안내한다. 문제 조사 중에는 대금이 보류될 수 있다. [Buying basics](https://www.vinted.com/help/5/25-buying-basics), [Package was damaged in transit](https://www.vinted.com/help/729)

**[미확인·버전 주의]** 국가별 조건을 하나로 합치지 않는다. 조회된 미국 약관 페이지는 적용일을 `08-10-2026`으로 표시한다. 날짜 표기 해석과 현재 효력 여부를 이번 문서에서 확정하지 않으므로 이를 현재 정책의 단독 근거로 삼지 않는다. 확인 기간의 정확한 기산점·달력일 계산·예외는 구현 전 선택 시장의 유효 약관으로 재확인해야 한다. [USER TERMS AND CONDITIONS](https://www.vinted.com/terms-and-conditions)

**[프로젝트 가정]** 개인 판매자·단일 상품·한 통화·한 배송을 대상으로 한다. 가격 제안은 비구속적이며 재고를 잡지 않는다. 배송 완료 이벤트 수용 시 서버가 구매자용 통지 레코드를 만들고 그 시점을 T0로 한다. D=T0+48시간으로 단순화하고, 실험에서는 60초로 압축 가능하게 한다. 이는 실제 달력일 정책을 정확히 재현한 것이 아니다. 이메일·푸시 열람 시점은 기산점으로 사용하지 않는다.

문제 제기는 주문 원본을 잠그고 검사하는 DB 시각이 D 이전일 때 수락한다. D 이후 미처리 요청은 늦은 요청으로 거절한다. 기한 전 HTTP 도착을 반드시 보장해야 한다면 별도 영속 접수와 순서 정책이 필요하므로 후속 대안으로 비교한다. 네트워크 도착과 DB 판정 시점이 같다고 가정하지 않는다.

대금 해제는 판매자에게 받을 금액을 확정하는 내부 업무로 모델링한다. 실제 은행 출금·청산·PG 정산 전체를 하나의 “payout 완료”로 표현하지 않는다.

## 4. 핵심 업무 흐름과 심층 대상

1. 판매자가 상태·설명·가격과 함께 상품을 게시한다.
2. 구매자가 조회하거나 가격을 제안한다. 제안 수락은 구매 확정과 구분한다.
3. 구매 명령이 단일 거래 권리를 확보하고 모의 결제를 진행한다.
4. 판매자가 발송하고 배송 어댑터가 배송 상태를 전달한다.
5. 구매자는 수령 상태를 확인하고 문제없음 또는 문제 제기를 선택한다.
6. 문제없음·기한 경과이면 거래를 완료하고 판매대금 해제를 기록한다. 분쟁이면 해제를 중단하고 운영자 판단에 따라 환불 또는 해제로 종결한다.

**[설계 추론]** 깊게 팔 흐름은 **배송 통지 → 문제 제기 가능 기간 → claim과 자동 완료의 경쟁 → 대금 해제·환불 → 장애 복구**다. 동시 구매는 필요한 시작 조건이지만 프로젝트 전체가 되지 않는다. 분쟁 심층 실험을 제거해도 등록·가격 협의·구매·발송·수령이라는 거래 서비스가 남는다.

## 5. Actor / Entity / State / Invariant

아래 모델은 **[프로젝트 가정]**이다.

| 구분 | 모델과 역할 |
|---|---|
| Actor | Buyer는 자기 주문 구매·확인·claim, Seller는 자기 상품·발송, CarrierAdapter는 검증된 배송 사건, Scheduler는 기한 처리, Operator는 분쟁 판정, PaymentAdapter는 모의 지급·환불 |
| Listing / Offer | 유일 물품의 게시 상태와 구매자별 제안 가격 |
| Order / PaymentAttempt | 거래 상태·대금·버전·결제 시도와 외부 결과 |
| Shipment / IncomingEvent | 배송 식별자·사건 원문·중복키·처리 결과 |
| Claim | 문제 유형·신청자·접수시각·판정·근거 |
| Release / Refund | 해제 또는 환불의 의도·멱등키·외부 처리 결과 |

| 객체 | 상태와 전이 |
|---|---|
| Listing | AVAILABLE → COMMITTED → SOLD. 결제 실패가 확정되면 COMMITTED → AVAILABLE |
| Order | PAYMENT_PENDING → PAID → SHIPPED → INSPECTION → COMPLETED |
| Order 분기 | INSPECTION → DISPUTED → COMPLETED 또는 REFUNDED. 발송 전 확정 취소는 CANCELLED |
| PaymentAttempt | REQUESTED → SUCCEEDED / FAILED / UNKNOWN. timeout은 UNKNOWN이며 실패와 다름 |
| Release / Refund | PENDING → SENT → CONFIRMED. 응답 불명은 UNKNOWN으로 조회·대사 |

불변조건:

1. 한 Listing에는 결제 대기·유효 판매 상태의 주문이 동시에 두 개 존재하지 않는다. 결제 대기를 풀 때도 외부 성공 여부가 불명확하면 재판매하지 않는다.
2. 미종결 claim이 있는 주문을 자동 완료하거나 새 해제 대상으로 만들지 않는다.
3. 한 주문의 최종 대금 처분은 환불 또는 판매자 해제 중 하나다. MVP는 부분 환불을 제외한다.
4. 같은 배송 사건은 claim 기간을 다시 시작하거나 이미 진행된 상태를 뒤로 돌리지 않는다.
5. 같은 업무 해제·환불의 외부 효과는 한 번이어야 한다. 이벤트 ID 중복 방지와 별개로 주문별 업무 멱등키를 둔다.
6. 과거 주문 취소가 새 거래를 AVAILABLE로 되돌릴 수 없다. 상품 갱신은 현재 연결 주문·버전을 검사한다.

잘못된 명령은 권한·상태·기한 오류로 거절한다. 정상적으로 중복된 요청은 기존 결과를 반환한다. 매핑되지 않은 배송 사건은 버리지 않고 격리해 재조회·재처리한다.

## 6. 실시간성의 업무상 필요

**[설계 추론]** 배송 목록은 잠시 늦어도 되지만, 수락된 claim을 해제 결정에서 늦게 반영하면 구매자 보호가 무너진다. 실시간성의 핵심은 알림 애니메이션보다 **업무 결정을 내릴 때의 최신 원본 상태**다.

| 경계 | 요구 |
|---|---|
| 구매 성공 응답 | 원본에서 유일 거래 확보를 확인한 뒤 응답 |
| claim 성공 응답 | 분쟁 상태와 자동 해제 차단을 같은 커밋에 반영 |
| 자동 완료 | D와 claim 부재를 원본에서 다시 검사하고 해제 의도까지 기록 |
| 외부 지급 처리 | 내부 의도와 외부 성공을 별도로 노출. 늦어져도 재조회·복구 가능 |
| 주문 화면 | 버전·갱신 시각 표시, 변경 명령에서는 서버 재검증 |

**[프로젝트 가정]** 내부 변경의 화면 반영 목표 2초, 정상 자동 완료 지연 목표 5초를 둔다. 실제 SLA가 아니다. polling을 시작점으로 하며 주문 상태의 단방향 갱신에는 SSE가 대안이다. WebSocket 채팅은 MVP 목적에 필요하지 않다. 상품 검색 캐시는 구매 가능 여부를 최종 판정하지 않는다.

## 7. 경쟁·장애·복구 시나리오

모두 **[설계 추론]**으로, Vinted에서 실제로 일어난 사고라는 뜻이 아니다.

### 7.1 claim과 자동 완료 경쟁

주문은 INSPECTION이고 D가 다가온다. 구매자의 claim과 워커가 같은 주문을 읽는다. 워커가 읽은 뒤 외부 해제를 바로 호출하면 그 사이 claim이 성공해도 돈이 해제될 수 있다. 두 경로가 같은 주문 경계를 직렬화하고 완료·분쟁 결정을 먼저 확정해야 한다. D 전 claim이 확정되면 자동 완료는 무효다. D 이후라면 claim은 실패 응답을 받아야 한다. “먼저 읽은 쪽”이나 알림 도착 순서로 결정하지 않는다.

### 7.2 외부 해제 성공 후 응답 유실

해제 의도를 저장하고 어댑터를 호출했으나 응답이 끊긴다. 로컬 상태만 보고 새 지급을 만들면 중복 효과가 생긴다. 같은 업무 멱등키로 조회·재시도한다. 모의 어댑터는 멱등 요청과 결과 조회 계약을 제공하도록 한다. 실제 제공자가 이를 보장하지 않는다면 자동 재시도만으로 정확히 한 번 지급을 주장할 수 없다.

### 7.3 배송 사건 중복·역전

DELIVERED 다음에 오래된 IN_TRANSIT가 도착하거나 같은 완료가 다른 전달 ID로 재전송된다. 수신 ID와 업무 전이를 모두 검증한다. 완료 상태를 되돌리거나 D를 연장하지 않는다. 오배송 정정은 일반 중복과 다르게 별도 운영자 검토 대상으로 둔다.

### 7.4 결제 결과 불명과 재판매

구매 A의 결제 timeout을 실패로 취급해 상품을 풀었는데 나중에 성공 콜백이 도착하고 B가 이미 구매했을 수 있다. UNKNOWN 동안 재판매를 막고 외부 결과를 조회한다. 실패 확정 후에만 원래 주문 참조를 조건으로 상품을 해제한다. 승인·취소의 외부 상태와 내부 상태를 대조해 미결 항목을 복구한다.

### 7.5 커밋 후 워커 종료

COMPLETED는 남았는데 외부 해제 작업이 사라지는 구간을 재현한다. 주문 변경과 해제 의도를 같은 DB에 기록하고 미처리 작업을 재스캔한다. 단순 오류 로그·DLT 보관만으로 복구 완료라 하지 않는다. 누락 탐지, 재실행, 외부 결과 대조, 최종 금액 확인을 각각 수행한다.

## 8. 기술 탐구 경로

| 업무 제약 → 실패 경계 | 관측 | 우선 비교 | 확장 조건·비용 |
|---|---|---|---|
| 유일 판매 → 동일 상품 구매 경합 | 이중 주문·락 대기·거절률 | 행 잠금 vs 조건부 갱신·유일 제약 | Redis 락은 원본 트랜잭션과의 간극을 추가하므로 필요가 입증돼야 함 |
| claim 우선 보호 → 기한 판정 경쟁 | claim 후 잘못된 해제·기한 판정 지연 | 주문 행 직렬화 vs 버전 갱신 | 영속 접수 순서 정책은 공정성을 보완하지만 처리 대기·복구가 복잡해짐 |
| 외부 재전송 → 중복 업무 효과 | 수신 수 대비 실제 효과 수·미처리 최고 경과시간 | RDB inbox·업무 유일키 | 큐는 수신 폭주·장애 격리가 관측될 때. 순서·재전달 운영 추가 |
| 외부 응답 불명 → 중복 해제 | UNKNOWN 건수·대사 불일치·복구시간 | 동기 호출+결과 조회 vs DB 작업 워커 | 실행 단위 분리부터 비교. DB 분리·Kafka는 별도 근거 필요 |

JVM에서는 배송·결제 어댑터 지연이 요청 스레드와 커넥션을 얼마나 점유하는지 측정한다. 외부 I/O를 DB 락 안에서 기다리는 구현과 락 밖의 영속 작업 방식의 차이가 우선 질문이다. bounded executor, timeout, 커넥션 풀을 먼저 관측하고 가상 스레드·비동기 방식은 이후 비교한다. 더 빠른 응답이 대금 처리 완료를 의미하지 않도록 지표를 분리한다.

## 9. 실험 방향

**[프로젝트 가정]** 실제 Vinted TPS·분쟁률을 아는 것이 아니다. 단일 상품에 구매가 몰리고 외부 사건이 재전달되는 상황을 자신의 서버에서 합성한다.

- 기준 데이터: 상품 1,000개, 사용자 200명, 동시 명령 20개, 조회/변경 8:2.
- 집중 부하: 구매 50개를 한 상품에 동시에 시도. 나머지 상품 부하와 섞어 국소 경합과 전체 처리량을 구분.
- 기한 경쟁: D 전후 100ms의 claim·자동 완료 조합. 동일 입력 순서를 고정해 반복하고 무작위 순서도 추가.
- 외부 사건: 중복 0/10/50%, 역전 10%, 지연 0/5/60초. 결제·해제 timeout과 성공 응답 유실을 따로 주입.
- 종료 지점: 외부 호출 전, 외부 성공 후, 로컬 결과 기록 전. API·워커 1개와 2개를 비교.

가설은 “락으로 주문을 보호해도 외부 중복 지급은 남는다”, “수신 ID만 중복 제거하면 다른 ID의 동일 업무 사건을 막지 못한다”, “DB 작업 기록으로 커밋 이후 유실을 복구할 수 있다”다. 반례와 미재현도 결과로 남긴다.

지표는 double-sale, 수락된 claim 이후 잘못된 release, 주문별 해제·환불 총액, 잘못된 relist, 외부 호출 중복 효과, UNKNOWN 지속시간, deadline lag, 복구 후 불일치, p95/p99다. 같은 하드웨어·DB·데이터·부하 seed·정책으로 예열 후 5회 반복하는 초안을 둔다. correctness 판정과 성능 판정을 분리하며 모든 실험은 아직 미수행이다.

## 10. 기존 ChatService와의 차이

**[사실·첨부]** ChatService PPT에는 정원 통제·HTTP와 WebSocket 경계·sessionKey·TTL 회수 및 2,000건 실험이 있다. 실제 성능이나 코드 정확성을 새로 인증하는 문서는 아니다.

**[설계 추론]** 유일 상품 동시 구매만 보면 기존 정원 문제와 겹친다. 새 중심은 **거래 당사자의 이의 제기 권리, 외부 배송의 지연·중복, 내부 완료와 외부 금전 효과의 차이, 미결 상태의 대사·복구**다. 인메모리 동시성 제어를 영속 데이터와 외부 시스템까지 연결하는 경험이 된다. 단순 쇼핑몰 CRUD에 락을 추가한 수준에서 멈추면 후보의 장점을 살리지 못한다.

## 11. 장점·위험·미확인 사항

- **장점 [정성 평가]:** 사용자 목적이 설명하기 쉽고 센서 없이 핵심을 재현할 수 있다. 하나의 주문을 따라 동시성·시간·외부 실패·복구가 연결된다.
- **위험:** 흔한 쇼핑몰로 보일 수 있다. 결제 승인·정산·판매대금 해제·은행 출금을 섞으면 현실과 다른 복잡성을 만들 수 있다. 운영자 판정의 적정성을 코드만으로 증명할 수 없다.
- **미확인:** 선택 국가의 현행 정책, 정확한 기한·통지 계약, 배송 정정·분실·반품 처리, 지급 API의 멱등·조회 보장, 실제 트래픽과 시스템 구조.
- **모의 환경의 한계:** 주문 상태와 어댑터 계약 아래 복구는 검증 가능하다. 실제 PG 결제·금융 규제·은행 지급·택배 사실의 정확성은 검증하지 않는다.

## 12. 개인 프로젝트 축소 범위와 보존 판단

| 구분 | 범위 |
|---|---|
| 얇게 구현 | 상품 게시·조회, 간단 가격 제안, 구매, 발송, 주문 내역, 모의 결제 |
| 깊게 구현 | 배송 사건 수신, 문제 제기 기간, claim/자동 완료, 해제·환불 의도와 복구 |
| 후속 실험 | 결제 UNKNOWN, 여러 워커, 배송 정정, 영속 claim 접수 순서 |
| 제외 | 실결제·실제 에스크로 운영, 국제배송·세금, 묶음구매, 부분 환불, 추천, 채팅, 전체 반품 물류 |

반품은 첫 범위에서 운영자 판정과 모의 환불로 축소한다. 물품 반환 여부까지 입증하는 구현이라고 주장하지 않는다. 보존 이유는 순수 웹 백엔드에서 거래의 전체 경계를 검증하기 쉽다는 점이다. 다음 검토의 종료 기준은 **claim과 자동 완료 경쟁, 외부 성공 후 응답 유실, 복구 후 금액 대조**를 작은 구현으로 설명할 수 있는지다. 최종 확정 없이 선택지로 남긴다.
