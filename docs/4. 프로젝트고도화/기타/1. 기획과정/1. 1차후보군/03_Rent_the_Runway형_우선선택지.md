## 2. 서비스 정체성과 사용자·사업 목적

**[사실·공식]** Rent the Runway는 구독자가 의류를 선택해 이용하고, 계속 보유하거나 다른 의류로 교환할 수 있는 서비스를 안내한다. 계속 보유한 의류는 현재 shipment의 한 spot을 차지한다. [How Rent the Runway Works](https://www.renttherunway.com/content-pages/how-it-works?ab_variant=control)

**[설계 추론]** 프로젝트 정체성은 **“구독자가 정해진 이용 한도 안에서 옷을 빌려 사용하고 반납·교환하는 서비스”**다. 날짜별 의류 예약이나 창고 운영 시스템으로 중심을 옮기지 않는다.

| 참여자 | 목적 | 잘못된 처리의 결과 |
|---|---|---|
| 구독자 | 구매 부담 없이 옷을 바꾸어 이용 | 반납했는데 다음 대여가 막히거나 권한이 잘못 소진됨 |
| 운영 사업자 | 구독 약속에 맞게 이용을 허용하고 물품 회수를 관리 | 중복 권한 지급으로 한도를 초과한 대여 발생 |
| 운영자 | 반납·구독·이용권 불일치 해결 | 수동 수정이 기존 이력과 충돌해 다음 달에도 오류 지속 |

사업상의 프로젝트 목표는 구독 계약에 따른 이용 가능 여부와 실제 대여 책임을 일치시키는 것이다. 의류 추천 품질, 물류 최적화, 구독 유지율 개선은 이 실험의 증명 대상이 아니다.

## 3. 이전 대화의 가정 보정과 공식 확인

**[사실·공식]** 공개 안내는 다음 shipment의 의류를 고르고 계속 보유할 의류를 선택한 뒤, 확인 후 다음 날 반납하도록 안내한다. 따라서 **“RTR는 창고가 수령한 뒤에만 다음 대여를 허용한다”는 이전 대화의 설명을 실제 정책으로 보존하면 안 된다.** [How Rent the Runway Works](https://www.renttherunway.com/content-pages/how-it-works?ab_variant=control)

**[사실·공식]** 반납 안내에는 Swap 선택·새 주문 후 스캔된 배송 라벨과 반납품을 연결하는 설명이 있다. 다른 계정의 라벨을 사용하면 drop-off가 반영되지 않고 RTR 도착 후 반납이 인식될 수 있다고 한다. [How to Return](https://www.renttherunway.com/returns)

**[설계 추론]** 여기서 남길 문제는 단일한 “수령 즉시 +1” 구현보다 넓다. **어떤 반납 증거를 믿고 언제 이용 권한을 열 것인가, 조기 교환을 허용하면 회수 전 책임을 어떻게 남길 것인가**가 핵심이다.

**[미확인]** 요금제별 spot·shipment·교환 제한, 미반납 시 제한, 조기 교환의 허용량, 월 경계와 carry-over의 세부 계약, 내부 이벤트·원장 구현은 확인하지 않았다. 보유 한도와 월 shipment 수를 같은 숫자로 간주하지 않는다. 공개 정책은 변경될 수 있고 일회성 날짜 렌탈과 구독 정책도 분리해야 한다.

## 4. 개인 프로젝트용 정책 선택지

아래 두 안은 **[프로젝트 가정]**이다. 초기 구현은 A를 작게 검증하는 후보로 두지만 최종 선택은 보류한다.

| 안 | 이용 권한 개방 시점 | 장점 | 비용·실제 제품과의 거리 |
|---|---|---|---|
| A. 수령 확인형 | 어댑터의 개별 대여품 수령 확인 | 효과의 원인과 멱등 범위가 명료 | 공개 RTR의 선교환 흐름보다 보수적. 이용 대기 증가 |
| B. 조건부 선교환형 | 회원의 swap 확정 등 정책상 인정한 시점 | 다음 의류 선택 대기 감소 | 반납 예정 책임·연체·추가 교환 제한을 별도 모델링해야 함 |

A는 “RTR와 동일한 정책”이 아닌 **RTR형 구독 렌탈을 단순화한 실험 모델**이라고 명시한다. B는 실제 시스템 복제라고 주장하지 않으며, 허용 조건이 확인되기 전에는 프로젝트 자체 정책으로 다룬다. 두 안은 동일한 보유 한도 공식을 그대로 적용할 수 없다. B에서는 잠시 집에 있는 실물 수가 계약 spot 수보다 클 수 있어 교환 중 의무를 따로 세야 한다.

이하 기본 설계는 A를 기준으로 한다. plan 변경·일시정지는 후속 범위이며, 최대 보유량 C=3, 월 신규 주문 한도 M=2를 예시로 둔다. 실서비스 요금제 수치가 아니다.

## 5. 핵심 업무 흐름과 깊게 팔 백엔드 흐름

1. 회원이 구독을 활성화하고 현재 이용 한도와 주기별 주문 한도를 확인한다.
2. 이용 가능한 의류를 선택하면 신규 대여 책임과 이용량이 원자적으로 기록된다.
3. 발송·사용 상태를 조회하고 계속 보유하거나 반납을 선택한다.
4. 반납 표시, 운송, 실제 수령 확인이 서로 다른 사건으로 들어온다.
5. 정책상 인정한 사건에 의해 기존 대여 책임을 종료하고 이용 가능량을 회복한다.
6. 회복된 권한으로 다음 의류를 선택한다. 월 주기는 별도로 갱신한다.

**[설계 추론]** 심층 대상은 **반납 사건의 중복·지연 ↔ 대여 책임 종료 ↔ 이용량 복구 ↔ 새 주문 ↔ 주기 갱신**이다. 반납 이벤트 실험을 제거해도 구독·선택·사용·교환이라는 제품 목적이 남는다. 물류 시뮬레이터가 제품 전체가 되지 않게 한다.

이 절은 **[프로젝트 가정 A]**다.

| 구분 | 모델과 권한 |

| Actor | Subscriber는 자기 구독·주문·반납 요청, WarehouseAdapter는 수령 확인, CarrierAdapter는 운송 정보, BillingScheduler는 주기 갱신, Operator는 근거 있는 정정 |

| Rental / PhysicalItem | 특정 회원의 개별 물품 대여와 책임. Rental과 상품 종류를 구분 |
| ReturnParcel / ReturnLine | 반납 봉투와 개별 Rental의 연결. 봉투 하나에 여러 물품 가능 |
| EntitlementEntry | 어떤 대여가 무엇 때문에 이용량을 점유·해제했는지 남기는 기록 |
| IncomingEvent | 제공자·이벤트 ID·Rental 매핑·수신시각·처리 결과 |

| 객체 | 상태 전이와 의미 |
|---|---|
| Rental | ALLOCATED → AT_HOME → RETURN_MARKED → IN_TRANSIT → RECEIVED |
| Rental 예외 | 발송 전 CANCELLED는 점유 해제. 배송 중의 취소는 별도 검토로 두며 자동 해제하지 않음 |
| 반납 | 회원의 RETURN_MARKED는 의사 표시이며 A에서는 권한을 돌려주지 않음 |
| 주기 | OPEN → CLOSED. 새 주기는 별도 행으로 생성하며 기존 대여를 삭제하지 않음 |
| 수신 사건 | RECEIVED → APPLIED / DUPLICATE / QUARANTINED. 통신 수신과 업무 수령을 구분 |

불변조건:

1. A에서 `U=아직 종료되지 않은 대여 점유 수`, `available=C-U`이며 `0 ≤ U ≤ C`다. 신규 주문과 U 변경을 같은 회원 경계에서 확정한다.
2. 한 Rental의 수령에 의한 점유 해제는 한 번이다. 이벤트 전달 ID가 달라도 같은 Rental을 다시 해제하지 않는다.
3. 한 반납 봉투의 스캔만으로 모든 물품을 수령했다고 단정하지 않는다. 확인된 ReturnLine만 종료한다.
4. 반납은 동시 보유 가능량을 복구하지만 해당 월의 주문 횟수를 되돌리지 않는다. 주기 갱신은 월 한도만 새로 만들며 미반납 대여를 초기화하지 않는다.
5. 이전 달 Rental의 늦은 반납도 그 Rental의 점유만 종료한다. 현재 월의 주문권을 덧셈으로 생성하지 않는다.
6. Membership이 비활성이어도 실제 반납은 처리한다. 반납 수용과 신규 대여 허용은 다른 판단이다.
7. 개별 실물은 동시에 두 활성 Rental에 배정되지 않는다. 반납 수령과 재대여 준비 완료도 동일 사건이라고 가정하지 않는다.

수령 정정이 필요하면 과거 원장을 삭제하지 않고 보정 이력·사유를 남긴다. 자동 역전이 새 대여 한도를 침범할 수 있으므로 MVP에서는 운영자 검토로 격리한다. 모델 B를 선택하면 위의 1번을 그대로 쓰지 않고 현재 계약 점유와 반납 예정 의무를 분리해야 한다.

## 7. 실시간성의 업무상 필요

**[설계 추론]** 반납 증거가 도착했는데 서버가 계속 이전 권한을 보여주면 회원은 다음 옷을 빌리지 못한다. 반대로 중복으로 권한을 열면 초과 대여를 허용한다. 필요한 것은 사건 이후 권한을 적시에 확정하고 새 주문이 원본 상태를 검사하는 것이다. 택배 이동 자체를 밀리초로 만드는 문제는 아니다.

| 경계 | 완료 의미 |
|---|---|
| 이벤트 수신 | 원문을 영속 보관. 아직 이용량 회복을 보장하지 않음 |
| 업무 커밋 | Rental 수령·점유 해제·처리 기록을 함께 확정 |
| 새 주문 | 구독 상태·주기 한도·현재 점유를 검사해 새 점유 확정 |
| 화면 통지 | 커밋된 이용 가능량을 전달. 전송 실패로 업무 커밋을 되돌리지 않음 |

**[프로젝트 가정]** 유효한 사건 수신부터 권한 반영까지 2초, 장애 회복 후 미처리 사건 정리 30초를 첫 실험 목표로 둔다. 실제 SLA가 아니다. false block duration은 **서버가 인정 가능한 증거를 받은 뒤** 부당하게 대여를 막은 시간으로 정의하고, 실제 택배 이동시간과 구분한다. 초기 polling과 단방향 SSE를 비교할 수 있으며 WebSocket은 기본 요구가 아니다.

## 8. 경쟁·장애·복구 시나리오

모두 **[설계 추론]**이며 실제 RTR 장애 사례가 아니다.

### 8.1 중복 반납 사이에 새 주문

U=3에서 Rental R1의 수령 사건이 도착한다. 첫 처리로 U=2가 되고 회원이 새 R4를 빌려 U=3이 된다. 같은 반납이 다시 와 무조건 `available+1`하면 초과 대여가 가능해진다. R1의 종료·원장 해제·이벤트 처리 완료를 함께 커밋하고, R1별 해제 유일성을 확인해야 한다. 단순 수신 ID 중복 제거로는 다른 ID의 의미상 중복까지 막지 못한다.

### 8.2 월 경계와 늦은 반납

이전 주기의 R1이 반납되는 동안 월 주기 갱신이 일어난다. 모든 한도를 plan 값으로 초기화한 뒤 반납에 +1하면 보유 한도를 초과한다. 월 주문 예산과 미종료 대여 점유를 분리하고 각 변경을 자신의 식별자에 연결한다. 주기 갱신 중복은 회원·주기 유일키로 막는다.

### 8.3 처리 중 프로세스 종료와 replay

이용량만 바꾸고 처리 기록 전에 종료하면 replay가 중복 해제를 만들 수 있다. 동일 트랜잭션으로 묶으면 둘 다 성공하거나 둘 다 실패한다. 성공 후 응답만 유실된 경우 재전달은 기존 처리 결과를 돌려준다. inbox를 먼저 저장하는 비동기 방식이면 처리 대기 상태를 재스캔한다.

### 8.4 매핑 불명·부분 반납·순서 역전

라벨만 있고 Rental 매핑이 없거나 3개 예정 중 2개만 도착한다. 봉투 상태를 전체 수령으로 바꾸어 이용량 3개를 돌려주면 안 된다. 불명 사건은 격리하고 확인된 line만 반영한다. RECEIVED 이후 늦은 IN_TRANSIT가 와도 상태를 되돌리지 않는다. 운영자가 매핑을 보완한 뒤 멱등 재처리하고 실제 종료된 Rental 집합을 대조한다.

### 8.5 모델 B로 확장했을 때의 추가 실패

swap 확정으로 먼저 권한을 열고도 반납이 오지 않을 수 있다. 해당 의무를 다음 주기 갱신이 지워서는 안 된다. 조건부 권한과 반납 의무·기한 초과 제한을 별도로 남겨야 한다. 이는 A의 수령 처리 테스트만으로 검증할 수 없는 추가 범위다.

| 업무 제약 → 실패 경계 | 관측 | 단순 대안 | 확장 조건·비용 |
|---|---|---|---|
| 한번만 점유 해제 → 중복 반납 | Rental별 해제 수·초과 권한 | RDB 트랜잭션+업무 유일키 | queue를 추가해도 업무 멱등은 여전히 필요 |
| 새 대여와 반납의 경쟁 → 동일 회원 이용량 | U와 활성 Rental 수 차이·락 대기 | 회원 행 잠금+카운터 vs 활성 Rental 집계 | 집계도 동시 주문은 직렬화해야 함. 원장 추가 시 대사·보정 비용 |
| 월 한도와 보유 한도 분리 → 늦은 사건 | cycle 중복·잘못 생성된 주문권 | 주기별 행과 Rental별 점유 관리 | 이벤트 소싱은 필수가 아니며 replay·스키마 관리 비용 존재 |
| 반납 burst → 수신 처리 포화 | 최고 대기시간·backlog·false block | 동기 DB 반영 vs DB inbox+별도 워커 | 처리 격리 필요가 관측되면 브로커 비교. 지연·재전달·운영 증가 |

Redis는 처음부터 권한 원본으로 사용하지 않는다. 조회량이 문제라면 조회 캐시와 갱신 지연을 비교하되 새 주문은 원본에서 판정한다. JVM 탐구는 이벤트 역직렬화·할당량, DB 대기, 워커 큐 적체, GC와 처리 지연의 관계를 관측한 뒤 시작한다. API와 반납 워커의 실행 자원 분리가 필요하다고 해서 DB 분리나 Kafka까지 필요하다고 결론내리지 않는다.

## 10. 실험 방향

**[프로젝트 가정]** 실제 RTR의 이벤트 규모·재전달 비율은 미확인이다. 아래는 자신이 구현한 환경의 합성 부하다.

- 기준: 회원 100명, 회원당 C=3, Rental 300개, 초당 반납 사건 5개, 동시 신규 주문 10개.
- 집중: 반납 100개를 1초 안에 주입. 일부 회원의 반납 직후 새 주문을 몰아 동일 회원 경쟁을 강화.
- 사건 오류: 중복 0/10/50%, 같은 의미·다른 ID 포함, 역전 10%, 지연 0/5/60초, 부분 반납 및 매핑 불명 포함.
- 시간: 월 갱신과 이전 주기 반납을 겹치게 하고 주기 워커를 두 개 실행.
- 종료: 수신 저장 후·권한 커밋 전·커밋 후 응답 전에 종료하고 같은 사건을 replay.

가설 H1은 단순 가용량 증감이 중복 사건과 새 주문 사이에서 깨진다는 것이다. H2는 Rental별 해제와 회원 단위 직렬화가 정확성을 지키되 특정 회원 집중에서 대기가 증가한다는 것이다. H3는 inbox가 수신 안정성을 높여도 처리 지연으로 false block이 늘 수 있다는 것이다.

지표는 duplicate release, over-entitlement, 활성 Rental과 U의 불일치, 주기별 주문 한도 위반, false block duration, inbox 최고 경과시간, 격리 수, replay 후 원장·조회 상태 차이, p95/p99와 복구시간이다. 상태만 확인하지 말고 새 주문 성공·거절의 적정성도 판정한다.

동일 DB·자원·데이터·정책·seed로 예열 후 5회 반복하는 초안을 둔다. 정상·집중·장애 결과를 분리하고, 집계 방식과 저장 카운터 방식의 비용을 비교한다. 이벤트 입력량보다 생성기 성능이 먼저 포화됐는지도 확인한다. 아직 실험을 수행하지 않았으며 성능 개선이나 무오류를 달성했다고 주장하지 않는다.

## 11. 기존 ChatService와의 차이

**[사실·첨부]** ChatService PPT는 HTTP 입장과 WebSocket 연결 사이의 상태, 방별 정원, sessionKey·TTL 회수와 동시성 실험을 다룬다. 이 문서는 기존 구현을 재검증하거나 그 가치를 부정하지 않는다.

**[설계 추론]** 한도와 회수라는 공통점은 있다. 차이는 **클라이언트 연결 상태가 아니라 외부 반납 증거가 권한을 바꾸고, 그 권한이 구독 주기와 개별 대여 책임에 연결된다**는 점이다. 중복 증거의 업무적 의미, 늦은 사건의 귀속, 재시작·replay·대사가 새로운 탐구 대상이다. 단순 카운터 증감이나 세마포어 데모로 끝나면 기존 프로젝트와 차이가 약해진다.

## 12. 장점·위험·미확인 사항

- **장점 [정성 평가]:** 구독·대여·반납·교환이라는 제품 목적이 명확하고, 외부 사건이 권한을 바꾸는 문제를 작게 깊게 다룰 수 있다.
- **위험:** A를 실제 RTR 정책으로 오인할 수 있다. B는 현실적인 선교환에 가까운 방향이지만 미반납 의무까지 넓어져 범위가 커진다. 창고·세탁·재고 시스템 전체를 만들면 원래 범위를 벗어난다.
- **미확인:** 적용 요금제·교환 인정 시점·월 한도·연체 규칙·물품 단위 수령 증거·실제 내부 원장·event ID 보장·운영 규모.
- **모의 환경의 한계:** 명시한 이벤트 계약 아래 권한·복구는 검증할 수 있다. 실제 스캔 정확도·택배 유실·옷 상태·세탁 완료·고객 행동은 검증할 수 없다. 실제 고객이 A의 대기를 받아들일지는 시스템 부하 시험으로 결정할 수 없다.

## 13. 개인 프로젝트 축소 범위와 보존 판단

| 구분 | 범위 |
|---|---|
| 얇게 구현 | 고정 plan 가입, 의류 목록, 대여 주문, 내 대여품, 반납 요청, 현재 이용 가능량 |
| 깊게 구현 | Rental별 수령, 중복·지연 사건, 권한 복구와 새 주문 경쟁, 주기 갱신·replay 대조 |
| 후속 실험 | 구독 정지, plan 변경, 모델 B의 선교환·미반납 의무, 여러 워커 |
| 제외 | 날짜별 예약, 창고/WMS, 세탁·검수 공정, 운송 경로, 실제 결제·연체료, 추천·사이즈 예측 |

어댑터는 사건 입력·지연·중복·실패를 만드는 작은 도구로 제한한다. 실물 재배정은 최소 유일성만 확인하고 창고 재고 최적화를 하지 않는다. 보존 이유는 반납이라는 외부 사실과 내부 이용 권한 사이의 경계다. 다음 검토에서는 **A의 단순화가 흥미로운 업무 질문을 충분히 남기는지**, 또는 **B의 최소 의무 모델이 필요한지**를 먼저 선택한다. 이 문서는 그 결정을 대신하지 않고 후보를 독립적으로 다시 검토할 수 있게 남긴 기록이다.
