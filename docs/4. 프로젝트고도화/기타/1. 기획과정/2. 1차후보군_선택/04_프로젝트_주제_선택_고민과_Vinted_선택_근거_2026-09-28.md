# 프로젝트 주제 선택 판단과 Vinted형 우선 선택 근거

작성일: 2026-09-28

## 1. 문서 목적

Instawork형, Vinted형, Rent the Runway형 세 후보를 실제 서비스 정책과 백엔드 문제 관점에서 조사했지만, 조사 결과만으로는 무엇을 선택해야 하는지 바로 결정되지 않았다.

세 후보 모두 구현 가능한 서비스 흐름과 기술적으로 탐구할 수 있는 문제가 존재한다. 따라서 지금부터의 판단은 “어느 서비스가 더 복잡한가”, “어느 서비스가 기술을 더 많이 넣을 수 있는가”가 아니라 다음 질문을 기준으로 내려야 한다.

> 새 프로젝트가 기존 포트폴리오에 어떤 백엔드 역량을 추가로 보여 줄 수 있는가.

또한 프로젝트 주제를 고르기 전에 실제 업무를 완벽하게 이해해야 한다는 방향으로 계속 조사만 이어가는 것도 적절하지 않다고 판단한다. 실제 업무 맥락을 조사한 목적은 기술적인 고민을 만들기 위해 요구사항을 임의로 추가하지 않기 위해서였다. 실제 서비스 정책에서 충분한 제약과 예외를 확보했다면, 그다음부터 프로젝트의 가치는 조사량보다 직접 구현하고 실패 조건을 재현하고 측정한 결과에서 만들어져야 한다.

현재 판단은 다음과 같다.

> 새 프로젝트는 Vinted형 C2C 거래 서비스를 우선 선택한다.

다만 Vinted의 모든 기능을 구현하는 프로젝트로 만들지 않는다. 상품 등록과 구매, 발송까지의 기본 서비스 흐름을 얇게 구현하고, 배송 이후 구매자 claim, 자동 완료, 판매대금 처리, 외부 처리 실패와 복구를 깊게 검증하는 구조로 제한한다.

---

## 2. 지금까지의 방향에서 유지해야 할 부분

처음 프로젝트 기획에서 해결하고 싶었던 문제는 단순히 어려운 기술을 많이 넣는 것이 아니었다.

기존 프로젝트에서는 직접 기능을 정하고 그 기능 안에서 기술적인 의사결정을 했다. 그러나 실제 업무 정책과 제약에서 시작한 기능이 아니었기 때문에, 첫 번째 문제를 해결한 뒤 다음 업무상의 질문을 계속 만들어 가는 데 한계를 느꼈다.

새 프로젝트에서는 다음 흐름을 만들고 싶었다.

```text
실제 서비스와 사용자 목적 이해
→ 공개 자료로 업무 정책과 예외 확인
→ 개인이 구현할 핵심 흐름 선택
→ 요구사항과 지켜야 할 조건 정의
→ 최소 구현
→ 실험용 workload 구성
→ 경쟁·지연·장애와 시스템 상태 관측
→ 단순한 대안을 포함한 해결책 비교
→ 필요한 범위에서 시스템과 JVM까지 탐구
→ 선택 근거와 남은 한계 설명
```

이 방향은 유지한다.

특히 다음 기준은 그대로 가져간다.

- 기술을 먼저 정하고 기술을 사용할 이유를 나중에 만드는 방식은 피한다.
- 실제 서비스의 업무 정책에서 지켜야 할 상태와 실패 결과를 먼저 찾는다.
- 공개되지 않은 실서비스 트래픽을 안다고 가정하지 않는다.
- 프로젝트에서 만든 workload는 프로젝트 가정이라고 명시한다.
- 특정 기술을 사용하지 않았다는 사실도 판단 결과가 될 수 있다.
- 실험에서 예상한 문제가 재현되지 않으면 그 결과를 그대로 남긴다.
- JVM과 시스템 구조는 실제 처리 경로에서 지연, 대기, 실행 자원 문제가 관측됐을 때 내려간다.

## 3. 지금까지의 방향에서 수정해야 할 부분

실제 비즈니스 도메인을 충분히 이해해야 한다는 문제의식 자체는 타당하다.

그러나 조사 과정이 길어지면서 다음과 같은 방향으로 조금씩 이동하고 있었다.

> 좋은 도메인을 찾으면 깊은 기술 문제가 계속 자동으로 발생해야 한다.

이 기대는 수정해야 한다.

좋은 도메인은 기술 문제를 자동으로 만들어 주는 장치가 아니다. 좋은 도메인은 어떤 상태가 잘못되면 실제 업무 결과가 왜 틀리는지 설명할 수 있게 해 주는 배경이다.

예를 들어 Vinted형 프로젝트에서 `claim과 자동 완료의 경쟁`을 구현했는데 version 조건부 update 하나로 문제가 충분히 해결될 수도 있다.

그 결과 자체는 프로젝트의 실패가 아니다.

그다음 실제 장애를 주입하고 외부 I/O 지연을 넣고 connection pool, thread, scheduler 상태를 관찰했는데도 목표 workload에서 병목이 재현되지 않을 수도 있다.

그 역시 실패가 아니다.

오히려 다음과 같이 설명할 수 있다.

> 처음에는 실행 구조 변경이 필요할 것으로 예상했지만, 설정한 workload에서 해당 병목은 재현되지 않았다. 따라서 현재 범위에서는 더 복잡한 구조를 도입하지 않았다.

이런 판단이 프로젝트에서 보여 주고 싶은 기술적 사고에 더 가깝다.

반대로 “문제가 더 있어야 좋은 프로젝트”라고 생각해서 Redis, Kafka, MSA, Virtual Thread 같은 기술을 추가하기 시작하면 이전 프로젝트에서 느꼈던 문제로 다시 돌아간다.

## 4. 취업과 연결할 때 프로젝트에서 보여 줘야 할 것

프로젝트 이름이나 서비스 종류 자체가 채용에서 직접적인 강점이 되는 것은 아니다.

`Vinted형 프로젝트`, `Instawork형 프로젝트`라는 이름만으로 취업 경쟁력이 생기지는 않는다.

프로젝트를 통해 다음 역량을 확인할 수 있어야 한다.

| 확인할 역량 | 프로젝트에서 보여 줄 내용 |
|---|---|
| 기본 백엔드 구현 | Spring API, RDB/JPA 모델링, transaction, 예외 처리, 테스트, 인증·인가, 배포 |
| 업무 이해 | 어떤 상태가 존재하고 왜 그 상태를 잘못 만들면 안 되는지 설명 |
| 정합성 판단 | 동시 요청, stale command, deadline에서 어떤 결과를 허용할지 정의 |
| 장애 처리 | timeout, 중복, 프로세스 종료 후에도 업무 상태를 복구하는 과정 |
| 성능 판단 | 느리다는 이유만으로 기술을 바꾸지 않고 병목 위치를 관측 |
| 기술 선택 | Redis, Kafka, Virtual Thread 등을 사용한 이유와 사용하지 않은 이유 |
| 범위 통제 | 구현하지 않아도 되는 기능과 기술을 제외한 판단 |
| 설명 가능성 | 요구사항부터 상태, 문제, 대안, 실험, 선택, 한계까지 연결해 설명 |

새 프로젝트의 목적은 위 항목을 모두 억지로 채우는 것이 아니다.

기본 구현 능력을 보여 주면서 기존 ChatService에 없었던 새로운 종류의 실패 경계와 시스템 문제를 추가하는 것이 더 중요하다.

## 5. SI와 서비스 회사를 완전히 다른 방향으로 준비할 필요는 없다

SI와 자체 서비스 회사가 완전히 같은 역량을 보는 것은 아니다.

그러나 신입 백엔드 프로젝트에서 요구되는 기반은 상당 부분 겹친다.

공통적으로 필요한 것은 다음과 같다.

- Java와 Spring 기반 API 구현
- RDB 설계와 SQL
- transaction과 데이터 정합성
- 외부 API 연동
- 테스트
- 예외 처리
- 배포와 운영 가능한 구조
- 문제 발생 시 원인 추적

SI나 기업 업무 시스템에서는 요구사항을 정확한 상태 모델로 옮기는 능력, transaction, 권한, 배치, 외부 연동과 유지보수 가능한 코드가 특히 중요하게 연결될 수 있다.

자체 서비스나 플랫폼에서는 여기에 동시성, latency, traffic, failure isolation, 외부 dependency 실패, 복구, 모니터링 같은 문제가 더 강하게 드러날 수 있다.

따라서 지금 단계에서 `SI용 프로젝트`와 `서비스 회사용 프로젝트`를 따로 만들 필요는 없다.

새 프로젝트에서는 다음 목표를 잡는 것이 적절하다.

> 어느 회사에서도 확인할 수 있는 기본 백엔드 역량을 갖추고, 기존 ChatService에 없었던 영속 transaction과 외부 시스템 실패 경계를 추가한다.

## 6. 기존 ChatService가 이미 보여 주는 것

현재 ChatService에서는 다음 문제를 다뤘다.

```text
HTTP 입장 요청
→ 좌석 선점
→ WebSocket 연결
→ 입장 확정
→ 연결되지 않은 좌석 자동 회수
```

또한 다음 기술 문제를 다뤘다.

- HTTP와 WebSocket 사이의 상태 정합성
- 동일 방에 여러 입장 요청이 동시에 들어올 때 정원 초과 방지
- Semaphore를 이용한 정원 경계 제어
- 서버가 관리하는 sessionKey
- 비명시 종료 이후 TTL 유예
- 유예 만료 후 세션과 좌석 회수

따라서 새 프로젝트에서 다시 다음 이야기만 반복할 필요는 없다.

```text
한정된 자원
→ 여러 요청의 동시 선점
→ lock 또는 semaphore
→ 일정 시간 후 자원 회수
```

Instawork나 Rent the Runway도 잘못 축소하면 이 구조와 비슷해질 수 있다.

새 프로젝트에서는 다른 종류의 문제를 추가하는 편이 포트폴리오 전체 구성이 더 좋아진다.

## 7. Instawork형 프로젝트에서 보여 줄 수 있는 것

Instawork형 프로젝트의 기술 중심은 “알바 자리 경쟁”이 아니라 근무 책임의 이동이다.

예를 들어 다음 흐름이 있다.

```text
A가 Shift의 현재 책임자
→ B에게 transfer 요청
→ B가 수락
→ 동시에 A가 취소를 요청
```

이 상황에서는 하나의 `Assignment`를 여러 명령이 동시에 변경한다.

여기서 다음 문제를 검토할 수 있다.

- row lock
- optimistic version
- stale command
- transaction 경계
- 동일 ShiftPosition의 현재 책임자 유일성

첫 번째 문제를 해결한 뒤에도 다른 문제가 남는다.

B가 동시에 서로 다른 두 Shift를 수락하면 각 ShiftPosition만 lock해서는 Worker의 일정 충돌을 막지 못할 수 있다.

따라서 다음 질문이 나온다.

> 한 자리의 책임자만 보호하면 되는가, 아니면 Worker의 전체 일정도 같은 transaction 규칙 아래 보호해야 하는가.

그다음 근무 확인 deadline과 scheduler가 들어오면 다음 문제로 이어진다.

- 메모리 timer와 재시작
- DB에 저장된 deadline
- 중복 scheduler
- 이미 다른 Assignment로 교체된 상태를 과거 deadline 작업이 취소하는 stale command

Instawork형 프로젝트에서 보여 줄 수 있는 기술 범위는 다음과 같다.

```text
RDB transaction
→ pessimistic / optimistic concurrency control
→ 여러 aggregate에 걸친 invariant
→ stale command
→ durable scheduler
→ idempotency
→ commit 이후 알림 작업
→ 필요하면 outbox
```

### 취업 연결성

Instawork형은 업무 상태와 transaction을 강하게 보여 줄 수 있다.

SI와 자체 서비스 회사 모두에 설명하기 좋다.

특히 복잡한 업무 규칙을 RDB 상태와 transaction으로 정확하게 옮기는 능력을 보여 주기 좋다.

### 위험

프로젝트를 다음 수준으로 축소하면 기존 ChatService와 차이가 약해진다.

```text
한 자리 남음
→ 여러 Worker가 동시에 신청
→ 한 명만 성공
```

따라서 Instawork를 선택한다면 `자리 경쟁`보다 `책임 이전`, `자격 재검증`, `일정 충돌`, `deadline`, `stale command`를 중심으로 잡아야 한다.

## 8. Vinted형 프로젝트에서 보여 줄 수 있는 것

Vinted형 프로젝트의 기술 중심은 상품 등록이나 중고거래 CRUD가 아니다.

다음 거래 생명주기가 중심이다.

```text
상품 구매
→ 결제 상태
→ 발송
→ 배송 완료
→ 구매자 확인 기간
→ claim
→ 거래 완료 또는 분쟁
→ 판매대금 release 또는 refund
→ 외부 처리 결과 확인
→ 실패 시 대사와 복구
```

### 8.1 claim과 자동 완료의 경쟁

Order가 `INSPECTION` 상태이고 claim 기한이 끝나기 직전이라고 가정한다.

같은 순간 다음 두 작업이 실행될 수 있다.

```text
Buyer claim
Scheduler auto-complete
```

잘못 처리하면 claim API는 성공했지만 Order는 COMPLETED가 되고 판매대금 release가 시작될 수 있다.

따라서 다음 조건을 지켜야 한다.

> 유효하게 접수된 claim이 있으면 같은 Order의 자동 완료와 판매대금 release가 성공해서는 안 된다.

여기서 transaction, row lock, optimistic version, deadline 판정 기준을 비교할 수 있다.

### 8.2 내부 transaction과 외부 처리의 경계

Order가 정상적으로 COMPLETED가 됐다고 가정한다.

그다음 판매대금 release를 PaymentAdapter에 요청한다.

외부에서는 실제 release가 성공했지만 HTTP 응답만 timeout될 수 있다.

이 경우 로컬 서버에서 `FAILED`로 단정하고 다시 요청하면 외부 효과가 중복될 수 있다.

따라서 다음 상태가 필요해질 수 있다.

```text
PENDING
→ SENT
→ CONFIRMED
또는
→ UNKNOWN
```

`UNKNOWN`은 실패가 아니다.

외부에서 실제로 성공했는지 아직 알 수 없는 상태다.

이 문제에서 다음 기술 주제로 이어질 수 있다.

- idempotency key
- retry
- 결과 조회
- reconciliation
- 외부 상태와 내부 상태 대조

### 8.3 commit 이후 작업 유실

DB transaction은 commit됐지만 외부 release 작업을 실행하기 전에 애플리케이션이 종료될 수 있다.

이 경우 Order는 완료됐지만 후속 작업 자체가 사라질 수 있다.

따라서 다음 질문이 생긴다.

> commit된 업무 상태에 필요한 후속 작업을 재시작 이후에도 어떻게 다시 찾을 것인가.

처음에는 같은 DB의 작업 테이블이나 outbox를 비교할 수 있다.

처리량과 장애 격리가 실제로 문제로 확인된 뒤에만 broker를 검토한다.

### 8.4 배송 이벤트의 중복과 순서 역전

CarrierAdapter가 다음처럼 이벤트를 전달할 수 있다.

```text
IN_TRANSIT
DELIVERED
DELIVERED
IN_TRANSIT
```

마지막 `IN_TRANSIT`가 늦게 도착한 과거 이벤트일 수 있다.

이 경우 event ID를 중복 제거하는 것만으로 충분하지 않을 수 있다.

다음 두 문제를 구분해야 한다.

- 통신 이벤트가 같은가.
- 업무 효과가 같은가.

여기서 inbox, business idempotency, stale external event, replay 문제를 검토할 수 있다.

### 8.5 JVM과 실행 구조까지 이어지는 경로

Vinted형 프로젝트는 외부 I/O를 자연스럽게 가진다.

PaymentAdapter가 느려졌다고 가정한다.

```text
요청 수신
→ DB 조회
→ transaction 처리
→ 외부 PaymentAdapter 호출
→ 응답 대기
→ 결과 저장
```

외부 응답이 2초 또는 5초씩 늦어지면 CPU 사용률이 높지 않아도 request thread나 worker가 오래 점유될 수 있다.

DB transaction 안에서 외부 요청을 기다리는 구조라면 lock과 DB connection도 더 오래 점유될 수 있다.

이 상태를 실제로 관측한 뒤 다음 대안을 비교할 수 있다.

- 기존 thread pool 조정
- 외부 호출을 transaction 밖으로 이동
- bounded executor
- 작업 처리 분리
- Virtual Thread

Virtual Thread를 먼저 넣고 효과를 찾는 방식이 아니라, 외부 I/O 대기 때문에 실제 실행 자원이 막히는 것이 관측됐을 때 비교하는 구조다.

## 9. Rent the Runway형 프로젝트에서 보여 줄 수 있는 것

Rent the Runway형 프로젝트에서는 다음 상태의 분리가 중요하다.

```text
새 Shipment 권리
+
기존 Rental 책임
+
ReturnObligation
+
외부 ReturnEvidence
+
다음 Swap 제한
+
BillingCycle
```

새 Shipment를 먼저 허용하더라도 기존 Rental의 반환 책임이 사라져서는 안 된다.

반환 이벤트가 중복되거나 늦게 도착할 수 있고, BillingCycle이 바뀌더라도 이전 Rental의 미반환 책임이 초기화되어서는 안 된다.

따라서 다음 문제를 다룰 수 있다.

- entitlement와 obligation 분리
- 외부 event idempotency
- stale event
- cycle boundary
- outstanding obligation
- event replay
- reconciliation

기술적으로 나쁜 후보는 아니다.

그러나 현재 기준에서는 우선순위를 낮춘다.

이 후보의 심층 문제를 설명하려면 Rent the Runway의 swap 정책과 반환 정책부터 충분히 설명해야 한다.

또한 Carrier/Warehouse 이벤트가 프로젝트 중심에 가까이 들어오기 때문에 실제 서비스에서 확인한 사실과 프로젝트 simulator에서 정한 계약의 경계를 계속 관리해야 한다.

같은 개발 시간을 투입했을 때 Vinted의 거래 상태와 외부 실패, Instawork의 업무 책임과 transaction보다 채용 관점의 기술 신호가 특별히 더 강하다고 판단하기 어렵다.

따라서 현재는 백업 후보로 남긴다.

## 10. 세 후보를 취업 관점에서 다시 비교

| 항목 | Instawork형 | Vinted형 | Rent the Runway형 |
|---|---|---|---|
| 기본 Spring/RDB 구현 | 충분함 | 충분함 | 충분함 |
| transaction 문제 | 강함 | 강함 | 강함 |
| 동시성 | 강함 | 강함 | 중간 |
| 시간 조건 | 강함 | 강함 | 중간 |
| stale command/event | 강함 | 강함 | 강함 |
| 외부 I/O 실패 | 낮음~중간 | 매우 강함 | 강함 |
| idempotency/retry | 중간 | 매우 강함 | 강함 |
| reconciliation | 중간 | 매우 강함 | 강함 |
| JVM I/O 탐구 연결 | 가능 | 가장 자연스러움 | 가능 |

기존 ChatService와 나란히 놓았을 때 다른 종류의 문제를 가장 명확하게 추가할 수 있다는 점이다.

## 11. Vinted형을 우선 선택하는 이유

현재 새 프로젝트는 Vinted형을 우선 선택한다.

이 판단의 이유는 다음과 같다.

### 11.1 기존 ChatService와 기술 축이 다르다

ChatService에서는 다음을 다뤘다.

```text
WebSocket
+ 인메모리 상태
+ Semaphore
+ HTTP/WebSocket 상태 경계
+ TTL lifecycle
```

Vinted형에서는 다음을 다룰 수 있다.

```text
영속 transaction
+ 시간에 따른 업무 권리
+ 외부 I/O
+ UNKNOWN 상태
+ idempotency
+ 후속 작업 유실 복구
+ reconciliation
```

두 프로젝트의 기술 이야기가 겹치지 않고 이어진다.

### 11.2 하나의 거래 안에서 문제의 연속성이 있다

별도의 기능을 계속 추가하지 않아도 다음 문제가 한 Order 생명주기 안에서 이어진다.

```text
유일 구매
→ 배송
→ claim
→ deadline
→ 거래 완료
→ 판매대금 처리
→ 외부 결과 불명
→ retry
→ reconciliation
```

### 11.3 JVM까지 내려갈 수 있는 실제 경로가 있다

외부 PaymentAdapter 또는 CarrierAdapter 지연은 request thread, executor, DB connection, lock duration과 연결될 수 있다.

실제 지표에서 이런 대기가 관측되면 JVM 실행 구조와 Virtual Thread까지 검토할 수 있다.

관측되지 않으면 도입하지 않는다.

### 11.4 SI와 서비스 회사 양쪽에 설명 가능하다

RDB 상태 모델과 transaction은 기업 업무 시스템에도 연결된다.

외부 I/O, timeout, retry, idempotency, failure recovery는 서비스와 플랫폼 백엔드에도 직접 연결된다.

따라서 한쪽 채용 방향에만 지나치게 특화되지 않는다.

---

## 12. Vinted형을 선택하더라도 전체 기능을 구현하지 않는다

Vinted형 후보 문서에 등장하는 모든 문제는 구현 목록이 아니다.

서비스 흐름은 얇게 만든다.

```text
Listing 등록
→ Listing 조회
→ 구매
→ 발송
→ 배송 완료
```

깊게 구현할 범위는 세 덩어리로 제한한다.

### 12.1 claim과 자동 완료

```text
배송 완료
→ INSPECTION
→ claim 가능 기간
→ claim과 Scheduler auto-complete 경쟁
```

검토:

- transaction
- lock
- optimistic version
- deadline 기준
- stale scheduler

### 12.2 거래 완료와 판매대금 release

```text
COMPLETED
→ release intent
→ PaymentAdapter
→ SUCCESS / FAILED / UNKNOWN
→ retry 또는 reconciliation
```

검토:

- external I/O
- idempotency
- timeout
- 작업 유실
- process crash
- local/external state mismatch

### 12.3 Carrier event

```text
IN_TRANSIT
→ DELIVERED
→ duplicate
→ out-of-order
→ replay
```

검토:

- event deduplication
- business idempotency
- stale event
- inbox 필요 여부

---

## 13. 처음부터 넣지 않을 기술

다음 기술은 현재 프로젝트 시작 조건에 포함하지 않는다.

- Redis
- Kafka
- MSA
- Virtual Thread
- event sourcing
- CQRS

필요한 문제가 관측되면 대안으로 검토한다.

예를 들어 release 작업을 동일 DB 작업 테이블로 충분히 복구할 수 있다면 Kafka를 넣지 않는다.

고정 thread pool에서도 목표 workload의 외부 I/O를 충분히 처리한다면 Virtual Thread를 넣지 않는다.

조회 성능이 RDB만으로 충분하다면 Redis를 넣지 않는다.

이 기술들을 사용하지 않았다는 사실은 부족함이 아니다.

현재 workload와 실패 조건에서 필요성을 입증하지 못했다는 판단이 된다.

---

## 14. 구현을 시작한 뒤 주제를 다시 바꿀 조건

Vinted형을 선택했다고 해서 어떤 상황에서도 끝까지 유지해야 하는 것은 아니다.

구현 과정에서 다음 상황이 확인되면 Instawork형으로 변경할 수 있다.

### 변경을 검토할 조건

- PaymentAdapter와 CarrierAdapter simulator를 만드는 작업이 서비스 구현보다 훨씬 커진다.
- 거래 상태보다 가짜 PG와 배송 시스템 설계가 프로젝트의 중심이 된다.
- 실제 Vinted 정책과 프로젝트 가정을 구분하기 어려워진다.
- claim과 거래 완료보다 결제 인프라 자체를 설명하는 시간이 대부분을 차지한다.
- 개인 프로젝트 범위에서 검증 가능한 질문보다 가정해야 하는 외부 시스템 동작이 더 많아진다.

이 경우 Instawork형으로 바꾸는 것은 실패가 아니다.

실제 구현을 통해 Vinted형의 external dependency가 현재 목적에 비해 과하다는 사실을 확인한 결과다.

## 15. 앞으로의 판단 기준

이제부터 프로젝트 진행 중 새로운 기능이나 기술을 넣을지 고민할 때는 다음 순서로 판단한다.

1. 실제 서비스 업무에서 어떤 상태나 권리를 지켜야 하는가.
2. 현재 구현에서 그 조건이 실제로 깨지는가.
3. 어떤 workload나 장애 조건에서 깨지는가.
4. 가장 단순한 방법으로 막을 수 있는가.
5. 그 방법의 비용이 실제로 관측되는가.
6. 더 복잡한 대안이 해결하는 문제가 실제로 존재하는가.
7. 바꾼 뒤 어떤 지표가 개선됐고 어떤 비용이 새로 생겼는가.
8. 실험으로 판단할 수 없는 부분은 어디인가.

기술 이름 자체는 판단 기준에 넣지 않는다.

## 16. 현재 결정

현재 단계에서는 추가 후보 조사를 중단한다.

세 후보 중 Vinted형을 우선 선택하고 실제 구현 범위를 구체화한다.

선택 이유는 Vinted가 가장 화려하거나 가장 어려운 서비스이기 때문이 아니다.

기존 ChatService가 이미 다룬 동시 접속, 인메모리 상태, Semaphore, TTL과 다른 방향으로 다음 역량을 추가할 수 있기 때문이다.

```text
영속된 거래 상태
→ 시간에 따른 권리
→ transaction 경계
→ 외부 I/O
→ 결과 불명
→ 멱등성
→ 작업 유실
→ 대사와 복구
```

이후 프로젝트의 성공 여부는 위 문제를 전부 구현했는지로 판단하지 않는다.

실제 구현과 실험에서 확인한 범위 안에서 어떤 문제가 발생했고, 어떤 대안을 비교했고, 왜 특정 설계를 선택하거나 선택하지 않았는지를 설명할 수 있는지가 더 중요하다.

다음 단계는 Vinted형 서비스 전체 기능을 확장하는 것이 아니라, **구현할 정확한 서비스 범위와 프로젝트가 소유할 업무 규칙을 고정하는 것**이다.
