# Vinted형 프로젝트 심층 검증 문서
작성일: 2026-09-28

## 1. 문서 목적과 현재 결론

이 문서는 Vinted형 C2C 중고거래 서비스를 신입 백엔드 포트폴리오의 새 프로젝트 후보로 검토하기 위해 작성한다. 실제 Vinted 내부 시스템을 재현하는 것이 아니라, 공개된 사용자 정책을 바탕으로 개인 프로젝트가 구현할 수 있는 거래 생명주기와 실패 경계를 정리한다.

현재 결론은 **세 후보 중 우선도가 가장 높은 후보**다.

이 후보의 장점은 “중고거래”라는 서비스 이름에 있지 않다. 하나의 거래가 시작해서 끝날 때 다음 업무가 연결된다.

> 상품 게시
> → 가격 협의
> → 구매 확정
> → 결제 상태
> → 발송
> → 배송 완료
> → 구매자 확인 기간
> → claim
> → 거래 완료 또는 분쟁
> → 판매대금 해제 또는 환불
> → 외부 처리 결과 대사와 복구

첫 번째 동시성 문제를 해결한 뒤에도 시간 조건, 외부 이벤트, 금전 효과, 재시도, 상태 대사 문제로 계속 이어지기 때문에 이번 프로젝트의 목표인 “업무 규칙에서 다음 기술 질문이 자연스럽게 나오는 구조”와 가장 잘 맞는다.

표기는 다음과 같다.

- **[공식 확인]**: Vinted의 공개 도움말이나 약관에서 확인한 동작
- **[설계 추론]**: 확인된 업무 규칙에서 도출한 백엔드 문제
- **[프로젝트 가정]**: 개인 프로젝트가 실험을 위해 직접 정하는 상태나 수치
- **[미확인]**: 공개 자료만으로 현재 정확한 내부 동작이나 시장별 세부 정책을 확정하지 못한 내용

## 2. 제품 정체성

### 2.1 사용자가 이 서비스를 쓰는 이유

[공식 확인] Vinted는 판매자가 개인 물품을 등록하고 다른 사용자가 구매하는 C2C marketplace다.

판매자는 물품을 처분하고 판매대금을 받으려 한다.

구매자는 물품의 설명과 가격을 확인하고 구매한 뒤, 배송된 물품이 실제 설명과 맞는지 확인하고 문제가 있으면 정해진 기간 안에 이의를 제기할 수 있다.

플랫폼은 단순 게시판이 아니라 구매, 배송, Buyer Protection, claim, refund, seller earnings를 연결한다.

따라서 프로젝트 정체성은 다음처럼 설명할 수 있다.

> 개인 판매자와 구매자 사이의 한 물품 거래에서 구매 권리, 배송 상태, 구매자 이의 제기 권리, 거래 완료와 판매대금 처분을 연결하는 C2C 거래 서비스

### 2.2 심층 기능을 제거해도 서비스 세계가 남는가

남는다.

claim과 자동 완료 실험을 제거해도 다음 서비스가 남는다.

- 상품 등록
- 상품 조회
- 가격 제안
- 구매
- 결제
- 발송
- 배송
- 주문 상태 조회

따라서 claim race 하나를 확대한 기능 데모가 아니라 독립적인 거래 서비스로 유지할 수 있다.

## 3. 실제 서비스에서 확인한 업무 규칙

### 3.1 가격 제안은 구매 확정이 아니다

[공식 확인] Vinted에서 구매자가 가격 제안을 하고 판매자가 수락해도 그 물품이 판매된 것은 아니다.

제안은 binding하지 않으며, 구매자가 `Buy now`를 눌러 실제 구매를 완료하기 전까지 다른 사용자도 같은 상품을 구매할 수 있다.

이 규칙은 프로젝트에서 `Offer`와 `Order`를 분리해야 하는 근거가 된다.

`Offer ACCEPTED`를 `Listing SOLD`와 같은 상태로 취급하면 실제 제품 동작과 다르다.

### 3.2 판매자의 발송 기한

[공식 확인] Vinted의 현재 도움말은 판매자가 구매 후 통상 5영업일 안에 상품을 발송해야 한다고 설명한다. 정해진 기간 안에 발송되지 않으면 주문이 자동 취소될 수 있다.

[설계 추론] 첫 프로젝트 범위에서는 이 마감 자체를 심층 주제로 삼지 않아도 된다. 다만 하나의 거래가 구매 성공 직후 바로 완료되는 것이 아니라 발송 책임과 시간 조건을 가진다는 서비스 맥락을 보여 준다.

### 3.3 배송 후 구매자 확인 기간

[공식 확인] Vinted가 상품이 배송되었다고 알린 뒤 구매자는 2일 안에 다음 중 하나를 선택할 수 있다.

- `Everything is OK`
- `I have an issue`

문제가 없다고 확인하면 판매자에게 대금이 해제되는 방향으로 주문이 완료된다.

정해진 기간 안에 issue를 제기하지 않아도 주문이 자동 완료될 수 있다.

[공식 확인] `I have an issue`가 접수되면 거래는 suspended 상태가 되고 판매자에게 지급될 금액은 문제가 해결될 때까지 보류된다.

이 정책이 이 후보의 시간 경계와 업무 권리를 만든다.

### 3.4 분쟁 이후에도 상태전이가 계속된다

[공식 확인] 상품이 설명과 크게 다른 경우 구매자는 문제를 제기할 수 있다.

판매자는 경우에 따라 다음 선택을 할 수 있다.

- 부분 환불을 제안한다.
- 전액 환불을 제안한다.
- 상품 반환을 요구한다.

반환이 필요한 경우 구매자는 판매자의 요청 이후 일정 기간 안에 상품을 다시 보내야 한다. 현재 미국 도움말은 5영업일을 안내한다.

판매자가 반환품을 받은 뒤에도 확인 기간이 존재하며, 현재 도움말은 2일을 안내한다.

따라서 claim은 단순한 boolean flag가 아니라 이후 환불, 반환, 판매자 확인과 연결되는 별도 생명주기를 가진다.

### 3.5 판매대금의 pending과 available

[공식 확인] 구매자가 결제한 금액은 즉시 판매자가 자유롭게 사용할 수 있는 상태가 아니다.

판매자 Vinted Wallet에서는 주문이 완료되기 전까지 금액이 `Pending balance`로 유지되고, 주문이 정상 완료된 뒤 `Available balance`로 이동한다.

이 규칙은 프로젝트에서 “구매 결제 성공”과 “판매자 대금 해제”를 같은 사건으로 처리하면 안 되는 근거가 된다.

## 4. 여러 업무 흐름의 연결

### 4.1 상품 게시와 가격 협의

1. Seller가 상품 사진, 설명, 상태, 가격을 입력한다.
2. Listing이 구매 가능한 상태가 된다.
3. Buyer는 정가로 구매하거나 가격을 제안할 수 있다.
4. Offer가 수락되어도 Listing은 즉시 판매 완료되지 않는다.
5. 실제 구매 명령이 별도로 실행되어야 한다.

### 4.2 구매와 결제

1. Buyer가 `Buy now`에 해당하는 구매 명령을 보낸다.
2. 서버는 Listing이 아직 구매 가능한지 확인한다.
3. Order를 생성하고 결제 시도를 시작한다.
4. 결제 결과가 확정되면 판매 상태를 연결한다.
5. 결제 결과가 불명확하면 재판매 여부를 즉시 결정하지 않는다.

### 4.3 발송과 배송

1. Seller가 상품을 발송한다.
2. Shipment가 생성된다.
3. CarrierAdapter가 외부 배송 상태를 전달한다.
4. 배송 완료로 인정할 수 있는 사건이 오면 구매자 확인 기간을 시작한다.

### 4.4 확인 기간과 claim

1. Order는 배송 후 검사 가능한 상태로 이동한다.
2. Buyer가 `Everything is OK`를 누르면 거래 완료로 진행한다.
3. Buyer가 `I have an issue`를 누르면 claim을 생성하고 거래를 보류한다.
4. 아무 명령도 없고 확인 기간이 끝나면 Scheduler가 자동 완료를 시도한다.

### 4.5 거래 완료와 대금 처분

정상 완료:

```text
INSPECTION
→ COMPLETED
→ seller release intent
→ external release
```

분쟁:

```text
INSPECTION
→ DISPUTED
→ seller/buyer resolution
→ COMPLETED + seller release
또는
→ REFUNDED
```

실제 은행 청산과 지급 전체를 개인 프로젝트가 구현했다고 주장하지 않는다. `PaymentAdapter`는 내부의 release/refund 의도와 외부 처리 결과 사이의 실패 경계를 재현하기 위한 simulator로 제한한다.

## 5. 개인 프로젝트에서 깊게 팔 흐름

심층 흐름은 다음으로 잡는다.

> 배송 완료 인정
> → 구매자 claim 가능 기간 시작
> → claim과 자동 완료 경쟁
> → 거래 완료 또는 분쟁 확정
> → 판매대금 release/refund 의도 생성
> → 외부 처리
> → timeout·중복·응답 유실
> → 대사와 복구

이 흐름의 장점은 첫 문제 이후 다음 문제를 만들기 위해 기술을 추가할 필요가 없다는 것이다.

## 6. 문제의 연속성

### 6.1 문제 1: claim과 자동 완료의 경쟁

Order가 `INSPECTION` 상태이고 마감 `D`가 가까워진다.

거의 같은 순간 다음 두 작업이 실행될 수 있다.

- Buyer의 claim 요청
- Scheduler의 자동 완료

잘못된 구현은 두 경로가 각각 `INSPECTION`을 읽은 뒤 서로 독립적으로 성공할 수 있다.

그 결과 다음 상태가 발생할 수 있다.

1. claim은 성공 응답을 반환한다.
2. 그 직후 자동 완료가 Order를 COMPLETED로 바꾼다.
3. 판매대금 release가 시작된다.
4. 구매자는 시스템상 claim을 제기했지만 보호 효과가 사라진다.

따라서 claim의 성공은 단순 Claim row 삽입이 아니다.

> claim 상태 반영과 자동 완료 차단이 같은 업무 경계에서 확정되어야 한다.

### 6.2 문제 2: 내부 완료와 외부 금전 효과 사이의 실패

문제 1을 DB transaction으로 해결했다고 가정한다.

Order가 정상적으로 COMPLETED가 되고 seller release intent가 생성된다.

그 뒤 PaymentAdapter에 release를 요청했는데 외부에서는 실제로 성공했지만 HTTP 응답이 timeout될 수 있다.

로컬 서버가 단순히 `FAILED`로 기록하고 새 release 요청을 만들면 외부 금전 효과가 중복될 수 있다.

따라서 다음 질문이 생긴다.

> 응답이 없다는 사실을 실패와 동일하게 볼 수 있는가.

여기서 `UNKNOWN` 상태와 외부 결과 조회, 멱등키, 대사가 필요해진다.

### 6.3 문제 3: 외부 배송 이벤트의 중복과 순서 역전

CarrierAdapter가 다음 사건을 보낼 수 있다.

```text
IN_TRANSIT
DELIVERED
DELIVERED 재전송
오래된 IN_TRANSIT 지연 도착
```

수신 event ID만 중복 제거해도 충분하지 않을 수 있다. 서로 다른 event ID가 같은 업무상 배송 완료를 의미할 수 있기 때문이다.

또 `DELIVERED` 이후 늦게 도착한 `IN_TRANSIT`가 상태를 뒤로 돌려서는 안 된다.

여기서 질문은 다음으로 바뀐다.

> 통신 이벤트 중복 제거와 업무 상태전이 멱등성을 어떻게 분리할 것인가.

### 6.4 문제 4: 결제 timeout과 재판매

구매 A의 결제 요청이 timeout됐다고 가정한다.

실패라고 단정하고 Listing을 다시 AVAILABLE로 만들면 Buyer B가 구매할 수 있다.

그 뒤 A의 결제가 실제로 성공했다는 결과가 늦게 도착하면 하나의 실물에 두 거래가 연결되는 문제가 생긴다.

따라서 `PaymentAttempt UNKNOWN` 동안 Listing을 어떻게 처리할지 정책을 정해야 한다.

이 문제는 claim과 다른 단계지만 하나의 Order 생명주기 안에서 자연스럽게 이어진다.

### 6.5 문제 5: commit 이후 후속 작업 유실

Order 변경 transaction은 commit됐지만 release/refund worker가 실행되기 전에 프로세스가 종료될 수 있다.

로그만 남기면 후속 업무가 사라질 수 있다.

따라서 다음 질문이 생긴다.

> 업무 상태 commit과 후속 외부 효과 사이의 작업 의도를 어디에 남겨야 재시작 후 다시 찾을 수 있는가.

이 지점에서 동일 DB 작업 테이블, outbox, inbox, reconciliation 같은 대안을 비교할 수 있다.

## 7. Actor / Entity / State

이 절은 [프로젝트 가정]이다.

### 7.1 Actor

- `Seller`: 상품 등록, 가격 제안 대응, 발송, 분쟁 대응
- `Buyer`: 구매, 수령 확인, claim
- `CarrierAdapter`: 배송 사건 전달
- `PaymentAdapter`: 모의 결제, release, refund
- `Scheduler`: 발송/확인 기간 마감 처리
- `Operator`: 분쟁 판정과 예외 복구

### 7.2 Entity

- `Listing`
- `Offer`
- `Order`
- `PaymentAttempt`
- `Shipment`
- `IncomingEvent`
- `Claim`
- `Release`
- `Refund`

### 7.3 상태 예시

`Listing`

```text
AVAILABLE
→ COMMITTED
→ SOLD
```

결제 실패가 확정된 경우:

```text
COMMITTED
→ AVAILABLE
```

`Order`

```text
PAYMENT_PENDING
→ PAID
→ SHIPPED
→ INSPECTION
→ COMPLETED
```

분쟁:

```text
INSPECTION
→ DISPUTED
→ COMPLETED
또는
→ REFUNDED
```

`PaymentAttempt`

```text
REQUESTED
→ SUCCEEDED
→ FAILED
→ UNKNOWN
```

`Release / Refund`

```text
PENDING
→ SENT
→ CONFIRMED
```

외부 결과를 알 수 없으면 `UNKNOWN`을 별도로 둘 수 있다.

## 8. 지켜야 할 불변조건

1. 한 Listing에 유효한 구매 권리가 동시에 둘 이상 확정되어서는 안 된다.
2. 미종결 Claim이 있는 Order를 자동 완료해서는 안 된다.
3. claim 성공 응답을 반환한 뒤 같은 Order의 seller release를 새로 시작해서는 안 된다.
4. 한 Order의 최종 대금 처분은 프로젝트 범위에서 `seller release` 또는 `full refund` 중 하나여야 한다.
5. 같은 배송 완료가 중복 전달돼도 claim 기간을 새로 시작해서는 안 된다.
6. 오래된 배송 이벤트가 이미 확정된 상위 상태를 뒤로 돌려서는 안 된다.
7. 외부 release/refund 요청이 재전송돼도 같은 업무 효과가 두 번 발생하지 않도록 멱등 범위를 정의해야 한다.
8. 과거 Order의 늦은 취소나 실패 callback이 현재 Listing의 새 거래를 AVAILABLE로 되돌려서는 안 된다.
9. `UNKNOWN` 외부 결과를 단순 실패로 간주해 재판매하거나 중복 지급하지 않는다.

## 9. 적시성이 필요한 이유

이 후보에서 적시성의 의미는 화면을 빠르게 바꾸는 것이 아니다.

가장 중요한 상태는 다음이다.

- Order가 현재 `INSPECTION`, `DISPUTED`, `COMPLETED` 중 무엇인지
- Buyer의 claim 권리가 아직 유효한지
- 자동 완료가 실행 가능한지
- 판매대금 release가 이미 시작되었는지
- refund와 release 중 어느 방향으로 최종 처분이 확정됐는지

Buyer의 claim이 정상 접수됐는데 서버가 이 사실을 늦게 반영해 자동 완료가 진행되면 실제 사용자 권리와 금전 결과가 달라진다.

이 점에서 Vinted형의 실시간성은 세 후보 중 가장 설명하기 쉽다.

반대로 상품 목록 화면의 갱신이 약간 늦는 것은 별개의 문제다. 최종 구매 명령에서 authoritative Listing 상태를 다시 확인하면 된다.

## 10. 기술 탐구 경로

### 10.1 동일 상품 구매 경쟁

업무 조건:

> 하나의 물품에는 하나의 유효 거래만 확정되어야 한다.

먼저 비교할 대안:

- Listing row lock
- version 조건부 update
- unique constraint와 상태 조건

측정:

- double-sale
- 거절률
- lock wait
- retry
- p95/p99

이 부분만 프로젝트의 중심으로 삼으면 기존 ChatService와 차이가 약하다. 동시 구매는 거래 생명주기의 시작 조건으로만 다룬다.

### 10.2 claim과 deadline

업무 조건:

> 유효하게 접수된 claim이 있으면 자동 완료가 성공해서는 안 된다.

대안:

- Order row lock
- version 기반 상태전이
- 영속 claim 접수 시점과 처리 시점을 분리하는 방식

추가 질문:

HTTP 요청이 마감 전에 서버에 도착했지만 DB lock 대기로 실제 transaction 판정은 마감 이후에 이루어졌다면 어느 시각을 기준으로 권리를 인정할 것인가.

이 정책은 기술이 아니라 프로젝트 업무 규칙으로 먼저 정의해야 한다.

### 10.3 외부 호출

초기에는 동기 PaymentAdapter 호출로도 구현할 수 있다.

그 뒤 다음을 측정한다.

- DB transaction 안에서 외부 I/O를 기다릴 때 lock duration
- connection pool 점유
- request thread 점유
- timeout 증가 시 전체 API latency
- 외부 성공 후 local 기록 실패

필요하면 다음 대안으로 이동한다.

1. transaction 안 동기 호출
2. release/refund 의도만 DB에 commit
3. 별도 worker가 외부 호출
4. 처리량과 격리 요구가 실제로 커질 때 broker 검토

### 10.4 inbox/outbox와 대사

queue를 추가하면 멱등 문제 자체가 사라지는 것이 아니다.

`IncomingEvent`를 저장하면 수신 유실 가능성을 줄일 수 있지만, 처리 backlog와 replay 책임이 생긴다.

`ReleaseJob`을 저장하면 commit 이후 작업 유실을 복구할 수 있지만, 외부에서 실제로 성공했는지 모르는 `UNKNOWN` 상태를 별도로 대사해야 한다.

DLT에 넣는 것과 복구 완료는 같은 뜻이 아니다.

### 10.5 JVM과 실행 구조

Vinted형은 외부 I/O가 자연스럽게 존재하기 때문에 JVM 실행 자원 탐구와 연결하기 쉽다.

관측할 순서:

1. PaymentAdapter 또는 CarrierAdapter 지연 증가
2. request thread 점유 시간
3. worker queue
4. DB connection wait
5. lock duration
6. CPU
7. thread 수와 메모리

그 뒤 다음을 비교할 수 있다.

- 기존 fixed thread pool 조정
- bounded executor
- timeout
- 작업 실행 단위 분리
- Virtual Thread

Virtual Thread는 외부 서비스 자체를 빠르게 하지 않는다. I/O 대기 중 실행 자원 사용 방식을 바꾸는 대안으로만 평가한다.

## 11. 실험 방향

아래 수치는 실제 Vinted 트래픽이 아니라 [프로젝트 가정]이다.

### 11.1 기본 workload

- Listing 1,000개
- 사용자 200명
- 동시 명령 20개
- 조회/변경 8:2

### 11.2 동일 상품 집중

한 Listing에 구매 요청 50개를 집중한다.

동시에 다른 Listing에도 정상 트래픽을 보내 국소 lock 경합과 전체 처리량 저하를 구분한다.

### 11.3 claim와 자동 완료

마감 `D` 기준:

- D - 100ms
- D
- D + 100ms

구간에 claim과 자동 완료를 교차 실행한다.

업무 지표:

- accepted claim 이후 잘못된 COMPLETED 건수
- accepted claim 이후 release 생성 건수
- deadline 처리 지연
- lock wait
- retry

### 11.4 배송 이벤트

- 중복 0%, 10%, 50%
- `DELIVERED → IN_TRANSIT` 역전
- 0초, 5초, 60초 지연
- 같은 의미지만 다른 event ID

측정:

- claim window 중복 생성
- 상태 역행
- quarantine 수
- replay 후 원본 불일치

### 11.5 외부 결제·대금 처리

PaymentAdapter에 다음 결과를 주입한다.

- 정상 성공
- 명시적 실패
- timeout
- 실제 성공 후 응답 유실
- 중복 요청
- 결과 조회 지연

측정:

- double-release
- double-refund
- `UNKNOWN` 지속시간
- 복구시간
- 내부 합계와 외부 simulator 합계 차이

### 11.6 프로세스 종료

종료 지점을 나눈다.

1. 외부 호출 전
2. 외부 성공 후
3. local 결과 기록 전
4. local commit 후 응답 전

이 실험을 통해 “재시도 가능”이라는 추상적인 주장 대신 어느 경계에서 어떤 상태가 남는지 직접 확인한다.

## 12. 기존 ChatService와의 차이

기존 ChatService는 방 정원, HTTP와 WebSocket 사이의 입장 상태, sessionKey, TTL 기반 세션 회수에 집중했다.

Vinted형에서 동일 상품 구매 경쟁만 구현하면 “한정 자원 하나를 여러 요청이 잡는다”는 점에서 기존 프로젝트와 비슷해질 수 있다.

그러나 이 후보의 주력 범위는 그 이후다.

> 사용자 claim 권리
> → 시간 경계
> → 자동 완료
> → 외부 배송 사건
> → 내부 거래 상태
> → 외부 금전 효과
> → UNKNOWN
> → 재시도
> → 대사와 복구

따라서 인메모리 연결 상태 중심 프로젝트에서 영속 업무 상태와 외부 시스템 실패를 다루는 프로젝트로 이동한다.

## 14. 장점과 위험

### 장점

1. 일반 사용자가 이해하기 쉬운 서비스다.
2. 하나의 Order만 따라가도 업무 규칙이 여러 단계 연결된다.
3. 적시성 실패가 구매자 권리와 판매자 대금이라는 구체적인 결과로 이어진다.
4. 동시성, 시간, 외부 event, idempotency, retry, UNKNOWN, reconciliation이 한 업무 이야기 안에서 나온다.
5. 외부 I/O가 자연스럽기 때문에 JVM 실행 자원 탐구까지 이어질 가능성이 높다.
6. 기존 ChatService와 기술 문제의 중심이 명확히 다르다.

### 위험

1. 제목만 보면 흔한 쇼핑몰 프로젝트처럼 보일 수 있다.
2. PaymentAdapter를 실제 금융 시스템처럼 과장하면 신뢰도가 떨어진다.
3. CarrierAdapter와 PaymentAdapter의 계약을 명확히 하지 않으면 simulator가 무엇을 검증하는지 모호해진다.
4. 결제, 정산, 지급, escrow를 하나의 `payment` 상태로 합치면 실제 업무를 오히려 왜곡할 수 있다.
5. 모든 예외를 넣으려 하면 범위가 매우 커진다.

## 15. 현재 평가

현재 Vinted형은 세 후보 중 **1순위**다.

이유는 기술 이름이 많이 붙기 때문이 아니다.

한 거래가 끝날 때까지의 실제 업무를 따라가면 다음 질문이 자연스럽게 이어진다.

```text
유일 구매
→ 결제 상태
→ 배송 상태
→ claim 권리
→ deadline
→ 거래 완료
→ 판매대금 처분
→ 외부 결과 불명
→ 재시도
→ 대사·복구
```

이 구조는 사용자가 원했던 “실제 업무 요구사항을 먼저 이해하고, 그 처리 과정의 경쟁·지연·장애를 관측한 뒤 단순 대안부터 비교하고 필요하면 JVM까지 내려가는 프로젝트”와 가장 직접적으로 연결된다.

선택 조건은 하나다.

> 실제 결제사나 택배사를 구현하는 것이 아니라, 명시적인 Adapter contract 아래 timeout·중복·UNKNOWN을 주입하는 simulator를 사용하는 것을 받아들일 수 있는가.

이 조건이 괜찮다면 현재 가장 강한 후보로 판단한다.
