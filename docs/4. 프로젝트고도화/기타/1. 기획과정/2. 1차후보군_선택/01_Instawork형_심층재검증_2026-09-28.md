# Instawork형 프로젝트 심층 검증 문서
작성일: 2026-09-28

## 1. 문서 목적과 현재 결론

이 문서는 Instawork형 단기 근무 매칭 서비스를 신입 백엔드 포트폴리오의 새 프로젝트 후보로 검토하기 위해 작성한다. 실제 Instawork의 내부 시스템을 복제하는 문서가 아니라, 공개된 제품 정책과 사용자 흐름을 확인한 뒤 개인 프로젝트로 축소했을 때 어떤 업무 상태와 기술적 의사결정이 남는지 검증하는 문서다.

현재 결론은 **우선 후보로 유지**다. 다만 프로젝트를 “근무 자리 선점”으로 축소하면 기존 ChatService의 정원 경쟁 문제와 비슷해질 위험이 크다. 이 후보를 선택한다면 중심은 **근무 책임의 이전, 자격 재검증, 일정 충돌, 확인 마감, 취소 이후 재충원, 재시작 후 상태 복구**가 되어야 한다.

이 문서의 표기는 다음 의미로 사용한다.

- **[공식 확인]**: Instawork의 공개 도움말에서 확인한 정책이나 사용자 흐름이다.
- **[설계 추론]**: 공식 정책에서 개인 프로젝트의 백엔드 문제로 도출한 내용이다. 실제 Instawork 내부 구현을 의미하지 않는다.
- **[프로젝트 가정]**: 개인 프로젝트에서 실험을 위해 직접 정해야 하는 규칙, 상태, 수치다.
- **[미확인]**: 공개 자료만으로 일관된 사실을 확정하기 어렵거나, 도움말 사이 표현 차이가 있는 내용이다.

## 2. 제품 정체성

### 2.1 사용자가 이 서비스를 쓰는 이유

[공식 확인] Instawork는 사업자의 단기 인력 수요와 일을 원하는 근무자를 연결한다. 사업자는 근무 시간, 위치, 역할, 인원과 같은 조건을 정해 shift를 게시하고, 근무자는 자신이 수행할 수 있는 shift를 선택한다.

근무자의 목적은 단순히 빈자리를 선점하는 것이 아니다. 근무를 맡은 뒤에는 실제로 출근하고, 근무 시간을 기록하고, 예정대로 수행하기 어려우면 취소하거나 조건을 충족하는 다른 근무자에게 책임을 넘기는 과정까지 이어진다.

사업자의 목적도 단순한 “예약 수 확보”가 아니다. 특정 시간에 실제로 일할 책임자가 존재해야 하고, 취소나 미확인으로 공백이 생기면 다시 충원할 수 있어야 한다.

따라서 프로젝트 정체성은 다음처럼 잡는 것이 적절하다.

> 사업자가 필요한 시간대의 근무 책임자를 확보하고, 근무자는 자신의 자격과 일정에 맞는 일을 맡아 완료하며, 책임 변경이나 공백이 발생해도 현재 책임 상태를 정확하게 유지하는 단기 근무 매칭 서비스

### 2.2 심층 기능을 제거해도 서비스 세계가 남는가

남는다.

양도 기능을 제거해도 다음 흐름이 남는다.

1. 사업자가 shift를 게시한다.
2. 근무자가 shift를 탐색한다.
3. 자격과 일정 조건을 만족하는 근무자가 shift를 맡는다.
4. 근무 전 확인 절차를 거친다.
5. 실제 근무를 수행한다.
6. 출퇴근 또는 근무시간 기록을 남긴다.

따라서 shift transfer 하나가 프로젝트 전체 정체성을 대신하는 기능 확대형 구조는 아니다.

## 3. 실제 서비스에서 확인한 업무 규칙

### 3.1 shift transfer의 책임 이전

[공식 확인] Instawork의 현재 도움말은 shift transfer를 기존 근무자가 다른 적격 근무자에게 자신의 shift를 넘기는 절차로 설명한다.

양도받는 근무자는 다음과 같은 조건을 만족해야 한다.

- Instawork 계정이 활성 상태여야 한다.
- 해당 position에 승인되어 있어야 한다.
- 해당 시간대에 이용 가능해야 한다.
- 다른 shift와 시간이 겹치면 안 된다.
- 다른 shift와 일정 간격 조건을 만족해야 한다.
- 사업자 또는 Partner에게 차단된 근무자가 아니어야 한다.
- 해당 shift가 requested Pros 전용, Top Pro 제한, 장기 shift 등 양도 제한 조건에 걸리지 않아야 한다.

[공식 확인] 양도 요청을 보냈다고 기존 근무자의 책임이 없어지는 것은 아니다. 상대방의 수락이 성공할 때까지 기존 근무자가 여전히 shift의 책임을 가진다.

이 규칙은 개인 프로젝트에서 매우 중요하다. `TransferRequest`의 생성과 `Assignment`의 책임 변경을 같은 사건으로 보면 안 된다.

### 3.2 취소

[공식 확인] 근무자는 자신이 맡은 shift를 취소할 수 있고, 늦은 취소나 no-show는 계정 상태와 향후 근무 접근에 불이익을 줄 수 있다.

[공식 확인] 현재 도움말은 늦은 취소를 근무 시작 24시간 이내의 취소로 설명한다. 양도가 가능한 경우 취소 대신 다른 근무자에게 shift를 넘기는 선택지가 제공된다.

[설계 추론] 개인 프로젝트에서 패널티 점수 자체를 구현할 필요는 없다. 이 규칙에서 중요한 것은 **취소 시점에 따라 업무 결과가 달라지고, 취소가 성공하면 현재 배정 책임과 빈자리 상태도 함께 변경되어야 한다는 점**이다.

### 3.3 근무 확인과 자동 취소

[공식 확인] Instawork는 근무 전에 근무자가 실제로 해당 shift를 수행할 의사가 있는지 다시 확인하는 절차를 제공한다. 확인하지 않으면 shift가 자동 취소될 수 있다.

[미확인] 확인 요청이 정확히 언제 발생하는지에 대해서는 현재 공개 도움말 사이 표현이 완전히 일치하지 않는다. 한 페이지는 시작 32시간 전에 확인 prompt가 발생한다고 설명하고, 다른 페이지는 48시간 전에 확인을 요청한다고 설명한다. 여러 페이지는 시작 전 특정 시점까지 확인하지 않으면 자동으로 제거된다고 설명한다.

따라서 개인 프로젝트에서 `32시간`, `48시간` 같은 값을 실제 Instawork의 고정 정책으로 복제하지 않는다. 프로젝트에서는 별도의 확인 마감 `D`를 정의하고, **실제 서비스에 확인 마감과 자동 취소가 존재한다는 사실만 근거로 사용한다.**

### 3.4 양도 시간 조건

[공식 확인] 현재 shift transfer 도움말에는 시작 12시간 이내의 shift는 transfer할 수 없다는 설명과, same-day shift의 경우 최소 90분이 남아야 한다는 설명이 함께 등장한다.

[미확인] 두 조건의 적용 관계는 공개 문서만으로 명확하지 않다. 따라서 개인 프로젝트에서는 실제 정책을 임의 합성하지 않는다.

## 4. 여러 업무 흐름의 연결

Instawork형 프로젝트를 서비스로 유지하려면 한 개의 경쟁 시나리오만 떼어내지 않고 전체 업무 흐름을 얇게라도 연결해야 한다.

### 4.1 근무 게시와 배정

1. Business가 직무, 시간, 보수, 필요 인원, 자격 조건을 입력해 Shift를 등록한다.
2. Shift는 여러 ShiftPosition을 가질 수 있다.
3. Worker는 조회 가능한 Shift를 확인한다.
4. Worker가 특정 자리를 맡으려 하면 현재 자격과 일정 충돌을 검사한다.
5. 조건을 만족하면 Assignment를 생성하고 ShiftPosition은 해당 Assignment를 현재 책임으로 가리킨다.

### 4.2 근무 확인

1. Assignment가 존재해도 근무 시작 전 확인이 필요할 수 있다.
2. Worker가 확인하면 Assignment는 확인 상태로 변경된다.
3. 마감까지 확인하지 않으면 Scheduler가 Assignment를 취소한다.
4. 취소된 자리는 다시 충원 가능한 상태로 돌아간다.

### 4.3 취소와 재충원

1. Worker가 근무를 수행할 수 없으면 취소를 요청한다.
2. 서버는 현재 Assignment가 아직 해당 Worker의 책임인지 확인한다.
3. 취소가 성공하면 기존 책임을 종료한다.
4. ShiftPosition은 다시 OPEN 상태가 된다.
5. 이후 다른 적격 Worker가 해당 자리를 맡을 수 있다.

### 4.4 근무 책임 이전

1. A가 자신의 Assignment를 B에게 넘기기 위한 TransferRequest를 생성한다.
2. 이 시점에도 A가 현재 책임자다.
3. B가 수락할 때 자격과 일정 조건을 다시 검사한다.
4. 수락이 성공하면 기존 Assignment를 종료하고 B의 새 Assignment를 생성한다.
5. ShiftPosition이 새 Assignment를 현재 책임으로 가리킨다.

### 4.5 근무 완료

1. 실제 근무가 끝나면 WorkRecord에 근무 결과를 남긴다.
2. 사업자 확인 또는 프로젝트에서 정의한 완료 절차를 거쳐 Assignment를 종료한다.
3. 실제 급여 지급, 세금, 보험은 프로젝트 범위에서 제외하고 모의 기록으로 제한한다.

## 5. 개인 프로젝트에서 깊게 팔 흐름

심층 대상은 다음 연결로 잡는다.

> Assignment 책임 확정
> → TransferRequest
> → 수락 시점의 자격·일정 재검증
> → 기존 책임자의 취소와 경쟁
> → 근무 확인 마감
> → 공백 발생 시 재충원
> → 재시작 후 미처리 마감 복구

여기서 첫 문제만 해결해도 다음 질문이 실제 업무 정책에서 계속 발생한다.

### 5.1 문제 1: 양도 수락과 기존 책임자의 취소

A가 B에게 transfer 요청을 보낸다.

그 뒤 A의 취소와 B의 수락이 거의 동시에 실행될 수 있다.

두 요청이 동일한 기존 Assignment를 읽고 각각 성공하면 다음과 같은 잘못된 결과가 가능하다.

- A의 취소로 ShiftPosition이 OPEN으로 돌아간다.
- 동시에 B의 수락으로 새 Assignment가 생성된다.
- 그 사이 다른 Worker C가 OPEN 상태를 보고 새로 배정될 수 있다.
- B와 C가 같은 자리를 동시에 책임지는 상태가 만들어질 수 있다.

따라서 수락과 취소는 단순 API 두 개가 아니라 같은 업무 상태를 두고 경쟁하는 명령이다.

### 5.2 문제 2: 자리 단위 보호만으로 Worker 일정 충돌을 막을 수 있는가

문제 1을 ShiftPosition row lock으로 해결했다고 가정한다.

그 뒤에도 B가 서로 다른 ShiftPosition 두 개를 거의 동시에 수락하면 문제가 남는다.

각 트랜잭션은 서로 다른 ShiftPosition만 보호하기 때문에 둘 다 B의 현재 일정을 조회하고 “충돌 없음”이라고 판단할 수 있다.

따라서 다음 질문은 자연스럽게 Worker 기준 불변조건으로 이동한다.

> 한 자리의 유일 책임자만 지키면 충분한가, 아니면 한 Worker가 동시에 책임질 수 있는 일정 자체도 직렬화해야 하는가.

이 질문은 새로운 기술을 보여주기 위해 만든 요구사항이 아니라 실제 transfer 자격 조건에서 나온다.

### 5.3 문제 3: 마감 작업의 내구성과 stale 작업

확인 마감 작업을 메모리 Timer로만 예약했다고 가정한다.

애플리케이션이 재시작하면 예약했던 작업을 잃을 수 있다.

반대로 DB에서 마감 대상을 주기적으로 다시 찾도록 바꾸면, 이미 확인됐거나 다른 Worker로 책임이 넘어간 Assignment를 과거 마감 작업이 취소하는 stale command 문제가 생긴다.

따라서 다음 질문은 다음과 같다.

> 시간만 보고 취소할 것이 아니라 현재 Assignment의 식별자와 상태까지 다시 확인해야 하지 않는가.

이 단계까지도 하나의 근무 책임 생명주기 안에서 이어진다.

## 6. Actor / Entity / State

이 절은 [프로젝트 가정]이다. 실제 Instawork 내부 모델을 의미하지 않는다.

### 6.1 Actor

- `Business`: Shift 등록, 취소, 완료 확인
- `Worker`: Shift 배정, 확인, 취소, 양도 요청과 수락
- `Scheduler`: 확인 마감 처리, 미처리 상태 재조회
- `Operator`: 정상 API만으로 해결되지 않는 상태 정정과 감사 기록

### 6.2 Entity

- `Shift`: 근무 시간, 장소, 직무, 보수, 자격 조건
- `ShiftPosition`: 한 근무에서 실제로 채워야 하는 한 자리
- `WorkerQualification`: Worker가 특정 직무를 맡을 자격
- `Assignment`: ShiftPosition의 특정 시점 책임자
- `TransferRequest`: 기존 Assignment를 다른 Worker에게 넘기기 위한 요청
- `WorkRecord`: 완료한 실제 근무 기록
- `DeadlineTask` 또는 deadline 컬럼: 확인 마감 및 처리 상태

### 6.3 상태 예시

`ShiftPosition`

```text
OPEN
→ ASSIGNED
→ OPEN        // 취소·미확인으로 다시 비어 있음
→ ASSIGNED
→ COMPLETED
```

`Assignment`

```text
PENDING_CONFIRMATION
→ CONFIRMED
→ COMPLETED
```

또는

```text
PENDING_CONFIRMATION / CONFIRMED
→ CANCELLED
```

양도 성공 시:

```text
기존 Assignment → TRANSFERRED
새 Assignment → CONFIRMED 또는 프로젝트에서 정한 초기 상태
```

`TransferRequest`

```text
PENDING
→ ACCEPTED
→ DECLINED
→ EXPIRED
→ INVALIDATED
```

## 7. 지켜야 할 불변조건

다음 조건은 [프로젝트 가정]이지만 실제 서비스 정책에서 도출한 검증 대상이다.

1. 한 ShiftPosition에는 활성 Assignment가 최대 하나만 존재한다.
2. TransferRequest가 생성됐다는 사실만으로 기존 Assignment의 책임을 제거하지 않는다.
3. 양도 성공 시 기존 책임 종료, 새 책임 생성, ShiftPosition의 현재 책임 참조가 서로 어긋나지 않아야 한다.
4. 이미 양도된 과거 Assignment를 대상으로 한 늦은 취소가 현재 Assignment를 취소해서는 안 된다.
5. 수락하는 Worker의 자격은 요청 생성 시점이 아니라 수락 시점에도 유효해야 한다.
6. 동일 Worker에게 시간상 충돌하는 두 활성 Assignment가 동시에 확정되어서는 안 된다.
7. 마감 Worker는 이미 확인되었거나 다른 Assignment로 교체된 책임을 취소해서는 안 된다.
8. 같은 transfer 수락 요청이 네트워크 재전송이나 재시작으로 반복돼도 책임 이전 효과는 한 번만 발생해야 한다.
9. 운영자 정정은 원시 DB 수정이 아니라 변경 이유와 전후 상태를 남기는 명령으로 처리한다.

## 8. 적시성이 필요한 이유

이 후보에서 “실시간”은 WebSocket 연결 여부가 아니다.

서버가 제때 확정해야 하는 상태는 다음과 같다.

- 현재 ShiftPosition을 실제로 책임지는 Worker
- Worker의 현재 자격과 일정
- Assignment 확인 여부
- 취소 또는 transfer 완료 여부
- 재충원이 필요한 OPEN 상태

양도가 성공했는데 사업자가 오래된 A를 책임자로 보고 있으면 실제 출근 대상 판단이 틀린다. 취소가 성공했는데 OPEN 상태가 늦게 반영되면 다른 근무자를 구할 수 있는 시간이 줄어든다.

반대로 화면이 잠시 오래된 정보를 보여 주는 것 자체는 반드시 치명적이지 않다. 쓰기 명령이 실행될 때 서버가 authoritative state를 다시 확인하면 된다.

따라서 프로젝트에서는 다음 완료 시점을 구분해야 한다.

1. HTTP 요청을 서버가 수신한 시점
2. DB transaction이 commit되어 책임 변경이 확정된 시점
3. 알림이 다른 사용자에게 전달된 시점
4. 화면이 갱신된 시점

책임 변경의 성립 조건은 2번이다. 3번과 4번이 실패했다고 이미 commit된 책임 변경을 되돌리는 구조로 만들 필요는 없다.

## 9. 기술 탐구 경로

기술은 문제 이후에 선택한다.

### 9.1 책임자 유일성

업무 조건:

> 한 ShiftPosition의 현재 책임자는 한 명이어야 한다.

먼저 비교할 수 있는 대안:

- RDB row lock
- version 기반 conditional update
- 현재 Assignment를 참조하는 unique constraint와 조건 검증

관측할 값:

- 이중 책임자 수
- stale 명령 성공 수
- lock wait
- retry 횟수
- p95/p99

Redis distributed lock은 처음부터 필요하지 않다. DB transaction과 별도의 분산 락을 함께 사용하면 오히려 두 원본 사이의 실패 경계가 추가된다.

### 9.2 Worker 일정 충돌

업무 조건:

> 서로 다른 ShiftPosition이라도 같은 Worker가 겹치는 근무를 맡아서는 안 된다.

비교 대상:

- Worker 기준 직렬화
- 일정 테이블에 대한 DB 제약 또는 조건부 삽입
- 충돌 검사와 Assignment 생성을 하나의 transaction으로 묶는 방식

### 9.3 마감 처리

업무 조건:

> 마감 이후 미확인 Assignment를 취소하되, 이미 상태가 바뀐 Assignment에는 영향을 주지 않는다.

작은 출발점:

- DB에 `confirmation_deadline` 저장
- Scheduler가 대상 조회
- 현재 Assignment ID와 상태를 조건으로 갱신

그 뒤 실제 backlog나 다중 worker 문제가 관측되면 작업 큐나 실행 단위 분리를 비교할 수 있다.

### 9.4 알림

책임 변경과 알림 전달을 같은 의미로 두지 않는다.

DB commit 직후 프로세스가 종료되면 책임 변경은 성공했지만 알림은 유실될 수 있다.

필요하면 다음 순서로 확장한다.

1. 동일 DB에 notification job 또는 outbox record 저장
2. 별도 worker가 전달
3. 실패 시 재시도
4. 처리량과 장애 격리 요구가 실제로 생기면 broker 검토

Kafka를 포트폴리오 기술 목록에 넣기 위해 먼저 도입하지 않는다.

### 9.5 JVM과 실행 자원

JVM 탐구는 업무 처리 경로에서 실제 병목을 관측한 뒤 연결한다.

관측 후보:

- DB lock 대기
- connection pool 대기
- scheduler worker queue
- 외부 알림 I/O 대기
- thread 수
- allocation과 GC

CPU 사용률이 낮다는 이유만으로 Virtual Thread를 도입하지 않는다. 외부 I/O 대기가 실행 슬롯을 오래 점유한다는 것이 관측되면 기존 thread pool 조정, bounded executor, timeout과 함께 비교한다.

## 10. 실험 방향

아래 수치는 실제 Instawork 트래픽이 아니라 [프로젝트 가정]이다.

### 10.1 정상 workload

- Worker 100명
- ShiftPosition 50개
- 동시 쓰기 요청 10개
- 조회/변경 요청 비율 8:2

목적은 기본 기능의 정상 상태전이와 응답 지연을 측정하는 것이다.

### 10.2 국소 경합 workload

같은 Assignment에 다음 명령을 집중시킨다.

- 기존 Worker 취소
- TransferRequest 수락
- 확인 처리
- 마감 Worker

목표는 처리량을 크게 만드는 것이 아니라 같은 업무 상태를 여러 명령이 동시에 바꾸는 조건을 재현하는 것이다.

### 10.3 Worker 일정 충돌 workload

서로 다른 두 ShiftPosition에서 동일한 Worker B에게 수락 요청을 동시에 실행한다.

확인할 값:

- 이중 일정 발생 여부
- 한 요청의 정상 거절 여부
- lock wait
- retry 횟수

### 10.4 장애 workload

- DB commit 직후 프로세스 종료
- 동일 API 재전송
- Scheduler 두 개 동시 실행
- 알림 어댑터 timeout
- 애플리케이션 재시작 후 과거 deadline 대상 재조회

### 10.5 가설

- H1: ShiftPosition 단위 보호만으로는 Worker 일정 충돌을 막지 못한다.
- H2: version 기반 조건부 갱신은 낮은 경합에서 단순하지만 경합이 집중되면 retry 비용이 커질 수 있다.
- H3: deadline을 DB에 영속화하면 재시작 후 미처리 Assignment를 다시 찾을 수 있지만 stale 작업 검증이 추가로 필요하다.
- H4: 책임 변경과 알림을 분리하면 알림 실패 때문에 업무 transaction을 rollback하지 않아도 되지만, 별도의 전달 복구 책임이 생긴다.

실험 결과는 아직 존재하지 않는다. 반대 결과가 나오면 그대로 기록한다.

## 11. 기존 ChatService와의 차이

기존 ChatService는 HTTP 입장과 WebSocket 연결 사이의 상태, 방 정원, Semaphore permit, sessionKey, TTL 기반 미접속 세션 회수를 다뤘다.

Instawork형에서도 “한정된 자리”와 “시간 기반 만료”가 등장하기 때문에 표면적으로 비슷해질 수 있다.

차이는 프로젝트 중심을 어디에 두느냐에서 발생한다.

ChatService의 질문:

> 남은 정원을 초과하지 않고 좌석을 선점·회수할 수 있는가.

Instawork형의 질문:

> 현재 책임자는 누구이며, 그 책임을 다른 사람에게 넘길 권한이 있는가. 새 책임자는 지금도 자격이 있는가. 같은 사람이 다른 근무도 동시에 책임질 수 있는가. 과거 명령과 마감 작업이 현재 책임을 잘못 취소하지 않는가.

따라서 Instawork형을 선택한다면 “자리 경쟁”은 시작 조건일 뿐 심층 주제가 되어서는 안 된다.

## 13. 장점과 위험

### 장점

1. 외부 시스템 의존성이 낮아 서버와 RDB만으로 핵심 문제 대부분을 직접 재현할 수 있다.
2. 책임, 자격, 일정, 시간 조건이 연결되어 하나의 문제를 해결한 뒤 다음 질문이 자연스럽게 이어진다.
3. 단순 동시성에서 끝나지 않고 stale command, scheduler durability, idempotency, 복구까지 확장할 수 있다.
4. 비즈니스 규칙에서 기술 선택이 나오는 구조를 만들기 쉽다.

### 위험

1. “근무 자리 예약”으로 축소하면 ChatService와 비슷한 선착순 자원 선점 프로젝트가 된다.
2. 실제 시간 정책을 공개 문서의 서로 다른 표현에서 임의로 합성하면 사실성이 떨어진다.
3. 급여, 노동법, 평판, GPS까지 확장하면 개인 프로젝트 범위를 벗어난다.
4. 양도 기능 하나만 강조하면 서비스 전체보다 특정 기능 데모처럼 보일 수 있다.

## 14. 현재 평가

현재 Instawork형은 프로젝트 후보로 **통과**로 본다.

선택 조건은 명확하다.

- 외부 결제·배송 simulator를 최소화하고 싶다.
- RDB transaction과 동시성, 시간 경계, scheduler 복구를 깊게 파고 싶다.
- “현재 책임자”와 “과거 명령의 무효화” 같은 업무 정합성을 중심으로 프로젝트를 구성하고 싶다.

이 조건이면 세 후보 중 구현 통제성이 가장 높다.

반대로 단순히 같은 shift를 여러 Worker가 동시에 잡는 경쟁만 구현할 생각이라면 이 후보를 선택할 이유가 약해진다.
