# C2C Marketplace 프로젝트 기획서

## 1. 프로젝트 개요

| 항목 | 내용 |
| --- | --- |
| 프로젝트명 | C2C Marketplace |
| 서비스 소개 | 개인 판매자가 중고 물품을 판매하고, 구매자가 상품을 구매한 뒤 배송과 거래 결과를 확인하는 서비스다. 구매한 상품에 문제가 있으면 환불을 요청하고 처리 결과를 확인할 수 있다. |
| 프로젝트 목표 | 상품 등록부터 거래 종료까지의 기본 기능과 실시간 1:1 채팅을 구현하고, 메시지와 합의 가격, 거래 상태를 일관되게 관리하는 백엔드를 개발한다. |
| 현재 단계 | 기존 ChatService를 중고거래 서비스로 확장·고도화하기 위해 주요 기능과 구현 범위를 구체화하는 기획 단계다. |

## 2. 기획 배경과 목적

### 2.1 기존 프로젝트를 개선하려는 이유

기존 ChatService에서는 HTTP와 WebSocket 사이의 입장 처리, 동시 입장 시 정원 제한, 세션의 유지와 회수를 설계하고 테스트했다. 다만 직접 정한 기능 안에서 실제 업무의 정책과 예외를 구체화하기 어려웠고, 기존 문제를 해결한 뒤 무엇을 더 검토하고 실험해야 할지 고민이 남았다.

이번 프로젝트는 기존 ChatService에 중고거래의 업무 기능을 추가하고, 이에 맞게 기존 기능과 구조를 개선하는 것을 목표로 한다. 중고거래는 구매 이후에도 배송, 상품 확인, 문제 해결과 대금 처리가 이어지므로, 한 거래의 진행 과정에서 여러 설계 문제를 검토할 수 있다고 판단했다.

기존 ChatService에서 다룬 실시간 연결 관리 경험을 실제 거래 과정에 적용하고자 한다. 구매자와 판매자가 상품을 문의하고 가격을 협의하는 1:1 채팅을 제공하여, 실시간 메시지 전달과 거래 조건의 변경을 함께 다룬다.

### 2.2 이번 프로젝트에서 달성할 목표

판매자와 구매자가 상품 등록부터 구매, 배송 확인, 거래 종료까지 이용할 수 있는 기본 서비스를 구현한다. 정상적으로 끝나는 거래뿐 아니라 상품에 문제가 생겨 처리를 보류하거나 환불하는 경우도 다룬다.

개발 과정에서는 DB에 저장된 거래 상태를 관리하고, 동시 요청과 장애 상황에서 업무 규칙이 지켜지는지 확인한다. 관측한 결과를 바탕으로 설계를 선택한 이유를 설명한다. 실행 자원이나 대기 시간이 문제로 나타나면 원인을 이해하는 데 필요한 시스템 구조와 JVM 동작도 학습한다.

## 3. 대상 사용자와 사용 목적

| 사용자 | 서비스를 사용하는 상황 | 이루려는 목적 |
| --- | --- | --- |
| 판매자 | 보유한 물품을 다른 사람에게 판매하려는 경우 | 상품을 소개하고 구매자에게 발송한 뒤 판매대금을 받는다. |
| 구매자 | 다른 사람이 판매하는 중고 물품을 구매하려는 경우 | 상품 정보를 확인해 구매하고, 수령한 상품에 문제가 있으면 해결을 요청한다. |

## 4. 서비스의 주요 이용 흐름

1. 판매자가 상품 정보와 가격을 등록하면 구매자가 상품을 조회할 수 있다.
   구매자는 필요하면 판매자와 1:1 채팅으로 상품을 문의하고 가격을 제안한다. 판매자가 수락한 가격은 저장되며, 구매자가 나중에 다시 접속해 결제할 때도 선택할 수 있다.
2. 구매자는 개인 페이지에서 테스트 잔액을 충전할 수 있다. 주문 정보를 입력하고 결제를 요청하면 상품의 구매 가능 여부와 잔액을 확인한 뒤, 잔액을 차감하고 구매를 확정한다.
3. 구매가 확정되면 판매자가 상품을 발송하고, 구매자는 주문 내역에서 배송 진행 상황을 확인한다.
4. 배송이 완료되면 구매자가 상품 상태를 확인한다.
5. 문제가 없으면 거래를 완료하고 판매자의 잔액에 판매대금을 지급한다.
6. 구매자가 상품 설명과 실제 상태가 다르다는 사유로 환불을 요청하면 거래를 보류한다. 판매자가 동의하면 반품 없이 전액 환불하며, 합의하지 못하면 보류 상태를 유지한다.

배송 완료 안내 후 2일 동안 상품을 확인하고 환불을 요청할 수 있다. 이 기간에 유효한 환불 요청이 없으면 거래를 자동으로 완료한다.

### 4.1 회원 잔액과 충전

회원은 개인 페이지에서 자신의 잔액과 사용 내역을 확인할 수 있다. 잔액은 상품 구매에 사용하는 테스트용 금액이며, 회원이 충전할 금액을 입력하면 해당 금액만큼 잔액을 늘린다. 실제 입금이나 외부 결제 수단은 연동하지 않는다.

### 4.2 잔액 결제와 구매 확정

#### 4.2.1 구매 가능 여부와 잔액 확인

상품 조회와 주문 정보 입력 중에는 상품을 예약하지 않는다. 구매자가 ‘결제하기’를 요청하면 상품의 구매 가능 여부와 구매자의 잔액을 확인한다. 잔액이 부족하거나 이미 판매된 상품이면 결제를 거절하고 잔액을 차감하지 않는다.

#### 4.2.2 잔액 차감과 구매 확정

상품을 구매할 수 있고 잔액이 충분하면 결제 금액만큼 잔액을 차감하고 구매를 확정한다. 구매자가 적용 가능한 합의 가격을 선택했다면 서버가 해당 제안을 확인하여 합의 가격을 적용하고, 선택하지 않았다면 등록 가격을 적용한다. 잔액 차감, 결제 내역 기록, 구매 확정은 모두 함께 반영되거나 모두 반영되지 않아야 한다.

#### 4.2.3 동시 구매·결제 요청 처리

- 여러 구매자가 같은 상품에 동시에 구매를 요청해도 한 명만 구매할 수 있어야 한다.
- 한 회원이 여러 상품을 동시에 결제해도 보유 잔액을 초과하여 사용할 수 없어야 한다.

#### 4.2.4 반복 결제 요청 처리

같은 결제 요청이 반복되어도 잔액을 중복으로 차감하지 않는다.

#### 4.2.5 응답을 받지 못한 경우의 결과 확인

결제 후 화면에서 응답을 받지 못한 경우에는 저장된 결제 내역을 조회하여 결과를 확인한다.

### 4.3 판매대금 지급과 환불

구매 시 차감한 금액은 거래가 완료되기 전까지 판매자가 사용할 수 있는 잔액에 반영하지 않는다. 거래가 정상적으로 완료되면 판매자의 잔액에 지급하고, 정해진 환불 조건에 따라 환불이 승인되면 구매자의 잔액으로 전액 반환한다. 같은 거래에서 판매대금 지급과 환불이 중복으로 이루어지지 않아야 한다.

### 4.4 구매 상품의 문제 접수 및 환불

#### 4.4.1 환불 요청 사유와 기간

구매자는 배송 완료 안내 후 2일 이내에 ‘상품 설명과 실제 상태가 다름’을 사유로 환불을 요청할 수 있다. 주말과 공휴일도 기간에 포함하며, 이번 프로젝트에서는 배송 완료 안내 시점부터 48시간으로 계산한다. 구매자가 정상 수령을 확인하여 거래를 완료했거나 요청 기한이 지난 경우에는 환불 요청을 받지 않는다.

#### 4.4.2 환불 요청 시 제출할 정보

요청 시 사유와 설명을 작성하며, 초기에는 사진 증빙을 받지 않는다.

#### 4.4.3 환불 요청 접수 후 거래 보류

유효한 환불 요청이 접수되면 거래를 보류하고 자동 완료와 판매대금 지급을 차단한다.

#### 4.4.4 판매자 동의에 따른 환불

해당 주문의 판매자가 동의하면 반품 없이 전액 환불한다.

#### 4.4.5 합의하지 못한 거래의 처리

당사자가 합의하지 못하면 거래를 보류 상태로 유지하며, 운영자 판정이나 강제 종결은 구현하지 않는다. 따라서 합의되지 않은 거래를 최종 해결하는 절차는 이번 구현 범위에 포함되지 않는다.

### 4.5 발송 기한과 주문 취소

#### 4.5.1 발송 기한

판매자는 구매 확정 후 5영업일 이내에 발송 정보를 등록해야 한다. 외부 배송 시스템을 연동하지 않으므로, 서비스에 발송 정보가 등록되면 발송된 주문으로 판단한다. 초기에는 발송 기한 연장 기능을 지원하지 않는다.

#### 4.5.2 미발송 주문의 자동 취소

발송 기한이 지난 주문에 발송 정보가 등록되지 않았다면 시스템이 주문을 자동으로 취소한다. 기한이 지난 주문에는 발송 정보를 등록할 수 없다.

#### 4.5.3 구매자와 판매자의 주문 취소

발송 정보가 등록되기 전에는 해당 주문의 구매자 또는 판매자가 취소 사유를 작성하여 주문을 취소할 수 있다. 발송 정보가 등록된 이후에는 주문 취소를 허용하지 않으며, 상품 수령 후 문제는 환불 요청 절차로 처리한다.

#### 4.5.4 취소에 따른 잔액 반환

주문이 취소되면 결제 시 차감한 금액 전액을 구매자의 잔액으로 반환하고, 판매대금은 지급하지 않는다. 같은 주문의 취소 처리가 반복되어도 잔액은 한 번만 반환한다.

### 4.6 구매자 확인과 거래 완료

#### 4.6.1 상품 확인 기간

구매자의 상품 확인 기간은 배송 완료 안내 시점부터 48시간이다. 구매자는 이 기간에 정상 수령을 확인하거나 정해진 사유로 환불을 요청할 수 있다.

#### 4.6.2 구매자의 정상 수령 확인

구매자가 정상 수령을 확인하면 거래를 완료하고 판매자의 잔액에 판매대금을 지급한다. 환불 요청이 접수되어 보류 중인 거래는 정상 수령 확인으로 완료할 수 없다.

#### 4.6.3 응답이 없는 경우의 자동 완료

상품 확인 기간이 끝났을 때 구매자의 정상 수령 확인과 유효한 환불 요청이 모두 없으면 시스템이 거래를 자동으로 완료하고 판매대금을 지급한다. 기간 안에 유효한 환불 요청이 접수되었다면 기간이 지나도 거래를 완료하거나 판매대금을 지급하지 않는다.

### 4.7 상품 문의와 가격 협의

#### 4.7.1 상품별 1:1 대화

구매자는 상품 상세 화면에서 판매자에게 대화를 시작할 수 있다. 대화는 상품과 구매자·판매자를 기준으로 구분하며, 같은 구매자가 같은 상품에 다시 문의하면 기존 대화를 이어간다. 해당 대화의 구매자와 판매자만 메시지를 보내고 내역을 조회할 수 있다.

#### 4.7.2 메시지 저장과 실시간 전달

현재 기획 및 개발에서는 텍스트 메시지만 지원한다. 메시지는 저장하여 대화 내역으로 제공하고, 상대방이 접속 중이면 새로고침 없이 확인할 수 있도록 실시간으로 전달한다.

상대방이 접속하지 않았거나 연결이 끊겨도 저장된 메시지는 유지한다. 다시 접속하면 놓친 메시지를 확인할 수 있으며, 같은 메시지를 재전송하더라도 중복으로 저장하거나 표시하지 않는다.

#### 4.7.3 가격 제안과 응답

구매자는 대화 화면에서 상품의 등록 가격보다 낮은 금액을 제안할 수 있다. 제안 금액은 0보다 커야 하며, 판매자는 제안을 수락하거나 거절할 수 있다.

한 대화에서는 한 번에 하나의 가격 제안만 응답을 기다릴 수 있다. 거절된 경우 구매자는 다시 제안할 수 있다. 초기에는 판매자의 역제안과 수락 후 가격 재협상은 지원하지 않는다.

#### 4.7.4 합의한 가격으로 구매

판매자가 수락한 가격은 해당 상품과 구매자에게만 적용한다. 다른 구매자에게 표시되는 상품 가격은 변경하지 않는다.

가격 제안을 수락해도 해당 구매자를 위해 상품의 구매 수량을 미리 확보하거나 구매를 확정하지 않는다. 이번 구현에서는 상품 하나당 판매 수량을 1개로 두며, 가격에 합의했더라도 결제를 완료하기 전까지 다른 사용자도 그 상품을 구매할 수 있다.

구매자는 채팅창의 가격 제안 기능에서 합의한 금액을 직접 입력하여 판매자에게 확인을 요청한다. 판매자가 수락하면 해당 상품·구매자·금액을 서버에 합의 내역으로 저장한다. 채팅 메시지에 금액을 적거나 구매자가 확인을 요청한 것만으로는 합의 가격을 확정하지 않는다.

구매자는 자신의 계정으로 다시 접속한 뒤에도 결제 화면에서 저장된 합의 가격을 선택할 수 있다. 해당 가격으로 결제를 요청하면 서버는 상품이 아직 구매 가능한 상태인지, 선택한 합의 내역이 해당 상품과 구매자의 것이며 판매자가 수락한 것인지 확인한다. 확인을 통과하면 저장된 합의 금액을 결제 금액으로 적용한다.

수락된 제안이 있으면 선택한 합의 가격으로, 없거나 선택하지 않으면 등록 가격으로 결제한다. 이미 판매된 상품에는 새 가격 제안이나 제안 수락, 구매를 허용하지 않는다.

#### 4.7.5 채팅에 표시할 거래 정보

가격 제안과 수락·거절 결과는 일반 메시지와 구분하여 대화 화면에 표시한다. 상품이 판매되면 대화 화면에서도 판매 상태를 확인할 수 있도록 한다.

연결이 끊겨 변경 내용을 즉시 전달받지 못한 경우에는 재접속 후 저장된 최신 상태를 확인한다.

## 6. 이번 구현 범위

### 6.1 포함할 범위

#### 6.1.1 상품 범위와 카테고리

특정 품목에 한정하지 않고 개인 간 중고 물품 거래를 지원한다. 상품은 의류·잡화, 생활용품, 전자기기, 도서·취미, 기타의 다섯 가지 대분류로 구분하며, 초기에는 하위 카테고리를 두지 않는다. 카테고리는 상품 등록과 조회에 사용하고, 구매·배송·상품 문제 접수·환불에는 카테고리와 관계없이 공통 규칙을 적용한다.

#### 6.1.2 기본 거래 기능

초기 구현은 하나의 상품을 한 명의 구매자가 구매하는 거래를 기준으로 제안한다. 상품 등록·조회, 테스트 잔액 충전과 내역 조회, 잔액 결제, 발송과 배송 확인, 거래 완료에 따른 판매대금 지급을 기본 기능으로 구성한다. 발송 전 주문 취소와 발송 기한이 지난 미발송 주문의 자동 취소도 구현한다.

#### 6.1.3 환불 처리 범위

환불은 ‘상품 설명과 실제 상태가 다름’에 대한 요청, 거래 보류, 판매자 동의, 반품 없는 전액 환불까지 구현한다. 실제 자금 이동과 외부 연동은 제외하므로, 대금 지급과 환불은 회원 잔액의 증감과 관련 내역 기록, 거래 상태 변경으로 처리한다. (개인 프로젝트의 구현 범위를 제한하기 위해 상품 훼손 등 상품 자체의 결함에 대한 별도 환불 사유와 처리 절차는 구현하지 않는다.)

#### 6.1.4 동시 요청·권한·실패 상황 검증

여러 사용자가 같은 상품에 동시에 구매를 요청할 때 중복 판매가 발생하지 않는지 검증한다. 한 회원이 여러 상품을 동시에 결제할 때 보유 잔액을 초과하여 사용하지 않는지도 검증한다.

배송 완료 안내 후 48시간이 지나고 유효한 환불 요청이 없으면 시스템이 거래를 자동으로 완료하고 판매대금을 지급한다. 이 처리와 구매자의 환불 요청이 동시에 진행되더라도, 기간 안에 유효한 환불 요청이 접수된 거래를 완료하거나 판매대금을 지급하지 않는지 검증한다.

같은 주문의 결제 요청이 반복되어도 구매자의 잔액은 한 번만 차감되는지 검증한다. 같은 거래의 완료 처리나 환불 처리가 반복되어도 판매대금 지급이나 구매자에게 환불 금액을 돌려주는 처리가 한 번만 이루어지는지 확인한다.

해당 주문의 구매자만 환불을 요청할 수 있고, 해당 주문의 판매자만 그 요청을 승인할 수 있는지 검증한다. 거래 당사자가 아닌 다른 사용자의 환불 요청이나 승인은 거절되어야 한다.

처리 도중 실패하더라도 잔액과 결제·거래·환불 기록이 일치하는지 검증한다.

#### 6.1.5 구현과 개선 방식

먼저 거래 과정에서 지켜야 할 규칙을 정한다. 대표적인 규칙은 다음과 같다.

- 여러 구매자가 같은 상품에 동시에 결제를 요청해도 한 명만 구매할 수 있어야 한다.
- 구매자의 잔액 차감과 결제 내역 기록, 구매 확정은 모두 함께 반영되어야 한다.

구체적인 DB transaction 범위와 동시성 제어 방식은 구현·테스트 단계에서 결정한다. 외부 연동을 제외한 이번 범위에서는 내부 기록과 상태 변경을 검증하며, 실제 결제사와의 데이터 불일치 복구는 검증 범위에 포함하지 않는다.

#### 6.1.6 실시간 채팅과 가격 협의

상품별 1:1 텍스트 채팅, 대화 내역 조회, 접속 중 메시지의 실시간 전달, 재접속 후 놓친 메시지 확인을 구현한다. 구매자의 가격 제안과 판매자의 수락·거절, 합의 가격의 저장과 결제 시 선택도 포함한다.

메시지 재전송에 따른 중복 처리와 대화 참여자의 접근 권한을 검증한다. 가격 제안 수락과 다른 구매자의 결제가 동시에 진행되더라도 이미 판매된 상품을 구매하거나 유효하지 않은 가격으로 결제하지 않는지 확인한다. 재접속 후에도 해당 구매자의 합의 가격을 조회하고 선택할 수 있는지 확인한다.
