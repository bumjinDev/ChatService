# C2C Marketplace 구현 판단 기록

C2C Marketplace 기본 기능(F-001~F-019)을 구현하면서 문서 사이의 충돌이나 판단이 필요한 누락을 발견했을 때 내린 결정을 기록한다.

- 기준 문서: `docs/4. 프로젝트고도화/` 의 「1. C2C_Marketplace_프로젝트_기획서.md」(이하 기획서), 「2. C2C_Marketplace_요구사항_명세서.md」(이하 요구사항 명세서), 「3. C2C_Marketplace_설계_명세서.md」(이하 설계 명세서)
- 우선순위: 문서 사이에 내용이 다르면 설계 명세서 → 요구사항 명세서 → 기획서 순으로 따른다. 환불 정책은 요구사항 명세서 변경 이력 CH-001 을 따른다.
- 판단 개수: 30개

---

## 1. 구현 순서를 정할 부속 문서가 없음

- **내용:** 설계 명세서는 구현 순서를 부속 문서 「C2C_Marketplace_설계_결정_기록.md」로 옮겼다고 적고 있지만 저장소에 그 파일이 없다.
- **관련 문서:** 설계 명세서 문서 머리 표(부속 문서), 10.1절, 10.2절 1.2판 변경 이력
- **결정:** 실행 기반과 데이터 모델을 먼저 하나의 커밋으로 만들고, 이어서 F-001 부터 F-019 까지 번호 순서로 기능마다 구현·테스트·커밋했다. 대화 화면은 마지막에 별도 커밋으로 추가했다.
- **근거:** 요구사항 명세서 3장 기능 목록의 "의존 기능" 열을 보면 번호가 작은 기능이 항상 먼저 필요하다(F-010 은 F-001, F-003, F-009 에 의존하고 F-015 는 F-014 에 의존하는 식). 번호 순서로 진행하면 각 기능을 구현할 때 의존 기능이 이미 있다.

## 2. DDL 과 엔티티를 기능별 커밋이 아니라 기반 커밋에 한꺼번에 작성함

- **내용:** "한 커밋에 여러 기능을 섞지 않는다"는 작업 지시와, 테이블 9개가 여러 기능에 걸쳐 쓰이고 서로 외래 키로 묶여 있다는 점이 충돌한다. 예를 들어 `BALANCE_TRANSACTION` 은 F-003(충전)에 먼저 필요하지만 F-010 에서 생기는 `PURCHASE_ORDER` 를 외래 키로 참조한다.
- **관련 문서:** 설계 명세서 4.1절, 4.2절, 8.2절(DDL 실행 순서)
- **결정:** `ddl_marketplace.sql` 전체와 JPA 엔티티·저장소를 첫 기반 커밋에 넣었다. 서비스, 컨트롤러, 테스트는 기능별 커밋으로 나눴다.
- **근거:** 설계 명세서는 데이터 모델과 상태 모델을 기능 설계(6장)와 별도의 설계 대상(4장)으로 둔다. 테이블을 기능별로 쪼개 만들면 외래 키를 나중에 `ALTER TABLE` 로 덧붙여야 해서 최종 DDL 이 설계 명세서 8.2절의 "부모 테이블부터 만드는 단일 스크립트"와 달라진다.

## 3. 상품 설명 컬럼 형식(CLOB 과 VARCHAR2(4000) 중 선택)

- **내용:** 설계 명세서가 `PRODUCT.DESCRIPTION` 형식을 "확인 필요. 구현 시 정한다"로 남겼다.
- **관련 문서:** 설계 명세서 4.2절 PRODUCT 표, 요구사항 명세서 F-001 1.2
- **결정:** `CLOB` 으로 만들고 엔티티에 `@Lob` 을 붙였다. 입력 검증은 "1자 이상(공백만 불가)"만 한다.
- **근거:** 요구사항과 설계 모두 설명의 길이 상한을 정하지 않았다. `VARCHAR2(4000)` 은 바이트 기준 한도라 AL32UTF8 에서 한글이 약 1,333자로 제한되므로 문서에 없는 상한을 새로 만드는 결과가 된다. 설명은 정렬이나 검색 조건에 쓰지 않으므로 CLOB 의 제약이 문제가 되지 않는다.

## 4. Instant 와 Oracle TIMESTAMP 매핑

- **내용:** 설계 명세서는 `Instant` 를 `TIMESTAMP(6)` 컬럼에 저장하고 `hibernate.jdbc.time_zone=UTC` 를 추가하라고 하면서 매핑이 의도대로 동작하는지는 구현 시작 시 확인하라고 했다.
- **관련 문서:** 설계 명세서 4.3절(시각 저장), 8.1절(시간 규칙의 한계와 전제), 8.2절
- **결정:** `hibernate.jdbc.time_zone: UTC` 와 함께 `hibernate.type.preferred_instant_jdbc_type: TIMESTAMP` 를 설정했다. 기반 테스트(`FoundationIntegrationTest`)에서 `2026-09-28T01:02:03.123456Z` 를 저장한 뒤 DB 값이 `2026-09-28 01:02:03.123456`(UTC 시각)으로 들어가고 같은 `Instant` 로 다시 읽히는 것을 확인했다.
- **근거:** Hibernate 6 은 기본적으로 `Instant` 를 시간대가 있는 타입(TIMESTAMP_UTC)으로 바인딩한다. 컬럼은 시간대가 없는 `TIMESTAMP(6)` 이므로 바인딩 타입을 명시해야 JVM 과 DB 세션 시간대에 결과가 좌우되지 않는다.

## 5. 금액 필드에 소수가 들어올 때

- **내용:** 설계 명세서는 소수 금액을 400 으로 거절하라고 하지만, Spring Boot 기본 Jackson 설정은 정수 필드에 들어온 `1000.5` 를 `1000` 으로 잘라 받아들인다.
- **관련 문서:** 설계 명세서 4.3절(금액), 9장 F-001-AC-02, 요구사항 명세서 F-001-AC-02
- **결정:** `spring.jackson.deserialization.accept-float-as-int: false` 를 설정하고, 본문을 읽지 못한 오류를 `VALIDATION_ERROR`(400)와 해당 필드의 `fieldErrors` 로 바꿨다.
- **근거:** 잘라서 받아들이면 사용자가 입력하지 않은 금액으로 등록·충전·제안이 처리된다. 테스트로 가격·충전·제안 금액의 소수 입력이 400 으로 거절되고 데이터가 만들어지지 않는 것을 확인했다.

## 6. DB 접속 정보를 환경변수로만 받도록 변경

- **내용:** 기존 `application.yml` 에 DB URL 과 계정(`jdbc:oracle:thin:@127.0.0.1:1521:xe`, `TOYCHAT`)이 직접 적혀 있었다. 작업 지시는 DB 접속 정보와 비밀값을 환경변수로만 받으라고 한다.
- **관련 문서:** 설계 명세서 8.2절(비밀값), 작업 지시(실행·테스트 환경)
- **결정:** `spring.datasource.url` 과 `username` 을 `${ORACLE_URL}`, `${ORACLE_USERNAME}`(기본값 없음)으로 바꿨다. 비밀번호는 기존과 같은 `${ORACLE_PASSWORD}` 다. Redis 는 `${REDIS_HOST:127.0.0.1}`, `${REDIS_PORT:6379}` 로 바꾸고 비밀번호는 기존 `${REDIS_PASSWORD}` 를 유지했다.
- **근거:** DB 접속 정보는 지시대로 환경변수만 쓴다. Redis 호스트와 포트는 비밀값이 아니고 기존 배포가 로컬 Redis 를 쓰므로 기존 값을 기본값으로 남겼다. 이 변경으로 배포 서버의 systemd 유닛에 `ORACLE_URL`, `ORACLE_USERNAME` 을 추가해야 한다(README 와 남은 작업에 적었다).

## 7. 기존 회원 예외 핸들러 대체와 회원 기능 오류 코드

- **내용:** 설계 명세서는 두 회원 예외 핸들러를 새 `ApiExceptionHandler` 로 대체하라고 하지만, 6.20절 오류 코드 목록에는 회원 기능(아이디·닉네임 중복, 회원 없음)과 처리하지 못한 예외에 쓸 코드가 없다. 또 "com.chatservice 아래의 REST 컨트롤러 대상"을 `@RestControllerAdvice(basePackages=…, annotations=…)` 로 함께 지정하면 두 조건이 OR 로 묶여 `@Controller` 까지 대상이 된다.
- **관련 문서:** 설계 명세서 2.2.2절(MemberAPIControllerExceptionHandler, MemberViewControllerExceptionHandler), 5.1절(오류 응답), 6.20절
- **결정:**
  - 두 클래스를 삭제(git rm)했다. 사용 중단 대상이 아니라 "변경" 대상이며, `basePackages` 가 다른 프로젝트 패키지를 가리켜 원래 적용되지 않던 코드다.
  - `ApiExceptionHandler` 는 `@RestControllerAdvice(annotations = RestController.class)` 로 모든 REST 컨트롤러에 적용했다(모든 컨트롤러가 `com.chatservice` 아래에 있다).
  - `ErrorCode` 에 `USER_ID_ALREADY_EXISTS`(409), `NICKNAME_ALREADY_EXISTS`(409), `MEMBER_NOT_FOUND`(404), `ACCESS_DENIED`(403, 보안 체인의 접근 거부), `INTERNAL_ERROR`(500)를 더했다. `JwtKeyNotFoundException` 은 `UNAUTHENTICATED`(401)로 바꾼다.
- **근거:** 기존에는 두 핸들러가 적용되지 않아 회원 예외가 예외 클래스의 `@ResponseStatus` 상태 코드(409, 404, 401)와 Spring 기본 오류 본문으로 응답했고, 가입 입력 검증 실패도 기본 400 본문이었다. 새 코드의 상태 코드는 기존 `@ResponseStatus` 값과 같게 맞췄다. 응답 형식 `{code, status, message}` 를 한 곳에서 통제한다는 6.20절의 취지에 맞춰 회원 기능도 같은 형식으로 돌려준다. 재사용 대상인 `join.js` 는 수정하지 않았으므로, 가입 오류 알림 문구는 응답 객체의 값을 이어 붙인 형태로 바뀐다.

## 8. 컴포넌트 스캔 제외 방법과 레거시 JPA 저장소

- **내용:** 설계 명세서는 `@ComponentScan` 제외 필터를 추가하라고만 정했다. `@SpringBootApplication` 이 이미 `@ComponentScan` 을 포함하고, 레거시 패키지에는 Spring Data 저장소 인터페이스(`createroom.dao.RoomQueueJpa`, `scheduler.RoomQueueEntityJpa`)도 있다.
- **관련 문서:** 설계 명세서 2.2.3절, 8.2절(ChatServiceApplication)
- **결정:** `ChatServiceApplication` 에 `@ComponentScan` 을 직접 선언하고 Spring Boot 기본 필터(`TypeExcludeFilter`, `AutoConfigurationExcludeFilter`)와 레거시 패키지 정규식 필터를 함께 넣었다. 레거시 패키지 파일은 수정하지 않았다. 두 레거시 JPA 저장소는 Spring Data 저장소 스캔으로 빈이 계속 만들어지지만 호출하는 곳이 없어 그대로 두었다.
- **근거:** 기본 필터를 빼면 테스트 설정 클래스 같은 빈이 의도치 않게 스캔될 수 있다. 저장소 빈을 막으려면 `@EnableJpaRepositories` 범위를 바꿔야 하는데, 설계 명세서 2.2.3절은 `RoomQueueEntity` 가 엔티티 스캔에 남아도 `ddl-auto: none` 이라 영향이 없다고 보고 있어 같은 취지로 판단했다. 레거시 컨트롤러·서비스 빈이 없다는 것과 `/rooms` 가 404 인 것은 테스트로 확인했다.

## 9. /ws/** 보안 체인의 실패 응답 형식

- **내용:** 설계 명세서는 `/ws/**` 체인을 "기존 `chatWebSocketFilterChain` 과 같은 구성"으로 만들라고 하지만, 기존 체인의 실패 핸들러는 HTML `<script>alert()</script>` 를 응답하고 쿠키를 지운다. 같은 절은 그 HTML 응답을 API 에 쓰지 않는다고 한다.
- **관련 문서:** 설계 명세서 5.1절(보안 체인 추가), 5.3절(오류 결과 401)
- **결정:** 경로 매처, 인증 필요, CSRF·세션 설정, `JwtAuthProcessorFilter` 는 기존 체인과 같게 두고 인증 실패·접근 거부 핸들러만 `/api/**` 와 같은 JSON 핸들러(`ApiAuthenticationEntryPoint`, `ApiAccessDeniedHandler`)를 썼다.
- **근거:** WebSocket 핸드셰이크 실패는 브라우저 화면에 그려지지 않으므로 HTML 스크립트 응답이 의미가 없고, 5.3절이 요구하는 결과는 401 상태 코드다.

## 10. WebSocket 핸드셰이크에서 대화가 없을 때의 응답

- **내용:** 설계 명세서 5.3절은 핸드셰이크 오류로 401, 403, 400 만 정했고, 없는 대화 ID 로 연결할 때의 결과가 없다.
- **관련 문서:** 설계 명세서 5.1절("존재하지 않는 자원은 404"), 5.3절
- **결정:** 404 로 응답하고 핸드셰이크를 거부한다.
- **근거:** 5.1절 공통 규약의 "존재하지 않는 자원은 404"를 따랐다. 참여자 검사(403)는 대화가 있어야 할 수 있다.

## 11. WebSocket 허용 Origin

- **내용:** 기존 `WebSocketConfig` 는 `setAllowedOrigins("*")` 로 모든 출처를 허용한다. 설계 명세서는 새 설정을 "기존 WebSocketConfig 와 같은 구조"로 만들라고 한다.
- **관련 문서:** 설계 명세서 7.2절(ConversationWebSocketConfig), NFR-003
- **결정:** 경로와 핸들러·인터셉터 등록 구조는 같게 하고 허용 Origin 은 지정하지 않아 Spring 기본값(같은 출처만 허용)을 쓴다.
- **근거:** 인증이 쿠키로 이루어지므로 모든 출처를 허용하면 다른 사이트의 페이지가 사용자의 쿠키로 연결해 대화 이벤트를 받을 수 있다. 대화 화면은 같은 출처(`/ChatService/conversations/{id}`)에서 열리므로 기능에 영향이 없다.

## 12. 실시간 이벤트를 보내는 시점과 세션 전송 직렬화

- **내용:** 설계 명세서는 "저장이 끝난 뒤 한 번 전달"이라고만 정했다. 서비스 메서드 안에서 바로 보내면 트랜잭션이 커밋되기 전에 이벤트가 나가 롤백된 내용이 전달되거나, 이벤트를 받은 상대가 바로 조회했을 때 아직 저장되지 않은 상태를 볼 수 있다. 또 한 `WebSocketSession` 에 여러 요청 스레드가 동시에 보내면 전송 예외가 난다.
- **관련 문서:** 설계 명세서 3.3절(메시지 전송 순서), 5.3절(전달 규칙), 6.6절 처리 순서 5, 7.2절(RealtimePublisher)
- **결정:** `RealtimePublisher` 는 트랜잭션 안에서 호출되면 `TransactionSynchronization.afterCommit` 에서 보낸다. 이벤트 내용(JSON)은 호출 시점에 만든다. 세션별 전송은 `synchronized (session)` 으로 직렬화한다. 전송 실패는 로그만 남긴다.
- **근거:** "저장이 끝난 뒤"를 커밋 이후로 해석해야 저장 실패를 전송 성공으로 다루지 않는다는 F-006 규칙과 맞는다. 세션 단위 직렬화는 동시 요청 제어(후속 과제)가 아니라 WebSocket API 의 사용 조건을 지키는 처리다.

## 13. 응답 형식 때문에 앞선 기능 커밋에 들어간 조립 코드

- **내용:** F-005(채팅 시작)의 응답은 F-007 의 대화 상세(5.2.8) 형식이고, F-010(결제)의 응답은 F-019 의 주문 상세(5.2.15) 형식이다. 번호 순서로 구현하면 응답을 만드는 코드가 조회 기능보다 먼저 필요하다.
- **관련 문서:** 설계 명세서 5.2.6절, 5.2.8절, 5.2.13절, 5.2.15절, 6.6절
- **결정:** F-005 커밋에 쓰기 가능 판단(`ConversationStateEvaluator`, 6.6절 규칙)과 대화 상세 조립(`ConversationAssembler`)을 넣고, F-010 커밋에 주문 상세 조립(`OrderDetailAssembler`)을 넣었다. 조회 API 자체(GET)는 각각 F-007, F-019 커밋에서 추가했다.
- **근거:** 응답 형식은 해당 기능 API 의 일부다. 조회 기능 커밋에서는 이미 있는 조립 코드를 엔드포인트에 연결하고 조회 검증을 추가했다.

## 14. 판매 종료 상품인데 주문이 없을 때의 쓰기 가능 판단

- **내용:** 6.6절 쓰기 가능 판단 규칙은 판매 종료 상품에 주문이 하나 있다고 전제한다. 주문 없이 판매 종료인 경우의 결과가 정해져 있지 않다.
- **관련 문서:** 설계 명세서 6.6절 규칙 3, 4.2절 PURCHASE_ORDER
- **결정:** 읽기 전용(`PRODUCT_SOLD_TO_OTHER`)으로 판단한다.
- **근거:** 정상 흐름에서는 결제와 판매 종료가 한 트랜잭션으로 반영되어 생기지 않는 상태다. 이 대화의 구매 희망자가 결제했다는 사실을 확인할 수 없으므로 BR-007 의 "실제 구매자·판매자의 기존 대화만 쓰기 유지"에 따라 쓰기를 허용하지 않는 쪽을 택했다.

## 15. 자동 처리의 트랜잭션 단위와 한 건 실패 시 동작

- **내용:** 작업 지시는 "함께 반영할 변경"을 한 트랜잭션으로 반영하라고 하고, 설계 명세서는 자동 처리를 "주문 한 건씩" 실행하되 한 건에서 예외가 났을 때 다음 건을 계속 처리할지는 후속 과제로 남겼다.
- **관련 문서:** 설계 명세서 6.13~6.18절, 7.1절(재실행과 실패 처리의 범위)
- **결정:** 자동 처리 메서드(`cancelExpiredUnshipped`, `completeDueDeliveries`, `completeExpiredInspections`, `autoApproveExpired`)는 대상 ID 를 조회한 뒤 한 건마다 `TransactionTemplate`(기본 전파·격리)으로 트랜잭션을 연다. 트랜잭션 안에서 엔티티를 다시 읽어 대상 조건(상태, 기한, 발송·환불 요청 유무)을 재확인한 뒤 처리한다. 한 건에서 예외가 나면 그 메서드는 거기서 멈추고, `TradeScheduler` 는 작업별로 예외를 로그로 남긴 뒤 다음 작업을 실행한다.
- **근거:** 설계 명세서가 정한 "함께 반영할 변경"의 단위가 주문 한 건이다. 실패한 건을 건너뛸지, 재시도할지, 일부 반영을 어떻게 복구할지는 후속 과제이므로 별도 정책을 넣지 않았다. 처리 직전 재확인은 6.13절(발송 정보 재확인)과 6.16절(환불 요청 재확인)의 지시를 네 작업에 같은 방식으로 적용한 것이다.

## 16. 스케줄러 사용 여부 설정 추가

- **내용:** 설계 명세서는 `marketplace.scheduler.fixed-delay` 와 `marketplace.mock-delivery.duration` 만 정했다. 테스트는 스케줄러를 기다리지 않고 서비스 메서드를 직접 호출하라고 하는데, 스케줄러가 테스트 중에도 돌면 고정·이동하는 `MutableClock` 시각으로 자동 처리가 끼어들어 결과가 달라진다.
- **관련 문서:** 설계 명세서 7.1절(실행 설정), 9장(검증 방법)
- **결정:** `marketplace.scheduler.enabled`(기본 `true`)를 추가하고 `TradeScheduler` 에 `@ConditionalOnProperty` 를 붙였다. 테스트 프로필(`application-test.yml`)에서 `false` 로 둔다. 스케줄러 자체는 같은 서비스 빈으로 직접 만들어 실행하는 테스트로 검증했다.
- **근거:** 운영 동작은 바뀌지 않고, 9장의 "직접 호출" 검증 방법을 결정적으로 실행할 수 있다.

## 17. 스케줄러 간격과 모의 배송 기간 기본값

- **내용:** 설계 명세서와 요구사항 명세서(TBD-005)는 폴링 간격과 모의 배송 기간을 구현·테스트 단계에서 정하라고 했다.
- **관련 문서:** 설계 명세서 7.1절, 요구사항 명세서 6장 TBD-005
- **결정:** `marketplace.scheduler.fixed-delay: PT30S`, `marketplace.mock-delivery.duration: PT2M` 로 정했다.
- **근거:** 설계 명세서가 모의 배송 기간 예로 `PT2M` 을 들었다. 30초 간격이면 2분 모의 배송이 늦어도 30초 안에 반영되고, 대상 조회가 조건 조회 몇 번이라 DB 부하가 작다. 운영 성능 목표가 아니며(7.1절), 환경변수로 바꿀 수 있다. 실제 실행에서 `PT5S`/`PT10S` 로 바꿔 스케줄러가 배송 완료를 반영하는 것을 확인했다.

## 18. 결제 시 판매 종료 이벤트의 전달 대상

- **내용:** 5.3절은 "사건을 일으킨 회원의 세션을 뺀다"고 하고, 6.10절은 결제 후 "그 상품의 모든 대화에 `CONVERSATION_STATE` 를 보낸다"고 한다. 결제한 구매자는 자기 대화 외에는 참여자가 아니므로 어느 세션을 빼는지 해석이 필요하다.
- **관련 문서:** 설계 명세서 5.3절(전달 규칙), 6.10절 처리 순서 6, 7.2절(publishToProductConversations)
- **결정:** 상품의 모든 대화에 대해 결제한 구매자의 세션을 빼고 보낸다. 판매자와 다른 구매 희망자의 세션은 받는다. 수령 확인·취소·환불 판단도 같은 방식으로 요청한 회원을 빼고, 자동 처리는 두 참여자 모두에게 보낸다.
- **근거:** 결제한 구매자는 REST 응답으로 결과를 받는다는 5.3절 규칙과 같다. 다른 구매 희망자의 대화는 읽기 전용으로 바뀌므로 그 참여자들(다른 구매 희망자, 판매자)이 알아야 한다.

## 19. 대화 화면 경로

- **내용:** 설계 명세서는 대화 화면(`conversation.jsp`, `conversation.js`)을 만들라고 하면서 화면 경로를 정하지 않았다. 5.1절은 "새 기능은 전부 `/api/**` 와 `/ws/**` 아래에 둔다"고 한다.
- **관련 문서:** 설계 명세서 5.1절, 8.2절(대화 화면)
- **결정:** `GET /conversations/{conversationId}` 를 처리하는 `ConversationViewController` 를 추가했다. 이 경로는 어느 보안 체인에도 속하지 않으며, 화면에는 대화 ID 만 넘긴다. 대화 내용, 참여자, 제안, 쓰기 가능 여부는 `conversation.js` 가 인증이 필요한 `/api/**` 와 `/ws/**` 로 조회한다. 인증이 없으면 API 가 401 을 돌려주고 화면은 로그인 페이지로 이동한다.
- **근거:** 화면 경로 자체는 데이터를 담지 않으므로 인증 없이 열려도 정보가 노출되지 않는다. JSP 를 `/api/**` 아래에 두면 API 체인의 JSON 401 처리와 섞이고, 새 보안 체인을 추가하는 것은 설계 명세서의 SecurityConfig 변경 범위를 넘는다. 실제 실행(Playwright)에서 두 참여자 화면의 실시간 수신, 제안 수락, 읽기 전용 전환을 확인했다.

## 20. 대화 화면을 기능 커밋과 분리

- **내용:** 대화 화면은 F-005~F-010 의 여러 API 를 함께 쓰므로 "기능 하나당 커밋 하나" 지시에 맞는 단일 기능이 없다.
- **관련 문서:** 설계 명세서 8.2절(대화 화면), 작업 지시(작업 방식 4)
- **결정:** F-001~F-019 커밋을 마친 뒤 `feat(ui)` 커밋 하나로 화면을 추가했다.
- **근거:** 기능 커밋에 화면 일부를 섞으면 한 커밋에 여러 기능이 들어간다. 기존 git log 에 `feat(ui)` 접두어가 있다.

## 21. 재사용하는 메인 화면(index.jsp)의 방 집계 표시와 시작 버튼

- **내용:** `index.jsp` 는 "재사용(파일 변경 없음)" 대상이지만 방 개수·인원 값(`totalRoom`, `totalUser`)을 표시하고, 로그인 사용자용 "실시간 채팅 시작하기" 버튼은 `indexUser.js` 에서 사용을 중단한 `/rooms` 로 이동한다. 설계 명세서는 `MainPageController` 가 집계 없이 화면을 그린다고만 정했다.
- **관련 문서:** 설계 명세서 2.2.1절(index.jsp 재사용), 2.2.2절(메인 화면 컨트롤러), 5.1절(`/rooms*` 는 404 예상), 8.2절(화면 범위)
- **결정:** `index.jsp`, `indexUser.js` 를 수정하지 않았다. `MainPageController` 는 `userName` 만 넘기므로 두 집계 값은 빈칸으로 보이고, 시작 버튼은 404 페이지로 이동한다.
- **근거:** 재사용 대상은 파일을 바꾸지 않는 것이 설계 명세서의 정의이고, 화면 작업 범위는 대화 화면뿐이다. 메인 화면 개편은 남은 작업에 적었다.

## 22. gradlew 실행 권한

- **내용:** 저장소의 `gradlew` 파일 모드가 `100644` 라 `./gradlew build` 를 그대로 실행할 수 없다(Jenkinsfile 은 `chmod +x` 로 우회한다).
- **관련 문서:** 작업 지시(검증: `./gradlew build` 통과)
- **결정:** 기반 커밋에서 `gradlew` 모드를 `100755` 로 바꿨다.
- **근거:** 지시된 검증 명령을 그대로 실행하기 위해서다. Jenkins 파이프라인의 `chmod +x` 는 그대로 동작한다.

## 23. Java toolchain 명시

- **내용:** 설계 명세서는 Java 21 을 `java.toolchain` 으로 명시하는 것을 "잠정. 구현 시작 시 확인"으로 두었다.
- **관련 문서:** 설계 명세서 2.1절, 8.2절(언어)
- **결정:** `build.gradle` 에 `java { toolchain { languageVersion = JavaLanguageVersion.of(21) } }` 를 추가했다.

## 24. 테스트 DB 구성과 테스트 데이터 정리

- **내용:** 설계 명세서는 Oracle 테스트 스키마 구성을 구현 시작 시 정하라고 했다. 작업 지시는 Docker 로 Oracle XE 를 실행해 그 위에서 통합 테스트를 실행하라고 했다.
- **관련 문서:** 설계 명세서 8.2절(테스트), 9장, 작업 지시(실행·테스트 환경)
- **결정:**
  - Docker 이미지 `gvenzl/oracle-xe:21-slim-faststart` 로 `XEPDB1` 에 `TOYCHAT` 계정을 만들어 썼다. 접속 정보는 환경변수로만 넘겼다.
  - 테스트 시작 시 테이블이 없으면 `ddl_toychat.sql`, `ddl_marketplace.sql` 을 적용한다. 두 파일은 Gradle `processTestResources` 가 테스트 클래스패스 `db/` 로 복사한다.
  - 테스트마다 마켓플레이스 테이블 9개의 모든 행과 ID 가 `it_` 로 시작하는 회원을 지우고 `MutableClock` 을 기준 시각(2026-09-28 월요일 10:00 KST)으로 되돌린다.
  - 인증 쿠키는 `LoginFilter` 와 같은 방식(JWTUtil 로 서명키·토큰 생성, Redis 에 저장)으로 발급한다.
  - 커넥션 풀이 `auto-commit: false` 이므로 테스트의 준비 데이터 변경은 `TransactionTemplate` 안에서 커밋한다.
  - Spring 컨텍스트를 한 번만 띄우도록 모든 통합 테스트가 같은 설정(`RANDOM_PORT`, `MockMvc`, `test` 프로필)을 쓴다.
- **근거:** 실제 Oracle 에서 DDL, 제약 조건, 시각 매핑을 함께 검증할 수 있다. 행 삭제 방식은 운영 스키마에서 실행하면 데이터를 지우므로 README 에 테스트 전용 스키마로만 실행하라고 적었다.

## 25. Gradle 실행 로케일

- **내용:** DDL 이 있는 문서 경로(`docs/1. 프로젝트개발/2. db`)에 한글이 있어, 로케일이 POSIX 인 Linux 환경에서는 Gradle 과 테스트 JVM 이 경로를 읽지 못했다(`InvalidPathException`, `Could not stat file`).
- **관련 문서:** 작업 지시(DDL 위치 `docs/1. 프로젝트개발/2. db/ddl_marketplace.sql`)
- **결정:** 경로는 지시대로 두고 Gradle 을 `LC_ALL=C.UTF-8` 로 실행했다. README 테스트 실행 절에 같은 내용을 적었다.
- **근거:** 실행 환경 설정 문제이며, Windows·macOS 처럼 UTF-8 경로를 기본으로 다루는 환경에서는 추가 설정이 필요 없다.

## 26. 상품명·수령인·주소 등에서 공백만 있는 입력

- **내용:** 설계 명세서는 상품명을 "1~100자", 수령인·주소·택배사명·운송장 번호·사유를 "공백 불가" 또는 길이로 정했다. 상품명과 설명은 공백만으로 된 값을 허용하는지 명시하지 않았다.
- **관련 문서:** 설계 명세서 4.2절(PRODUCT, PURCHASE_ORDER, SHIPMENT, REFUND_REQUEST), 6.1절, 요구사항 명세서 F-001 1.2("누락 불가")
- **결정:** 문자열 필수 입력에는 모두 `@NotBlank` 와 최대 길이 `@Size(max=…)` 를 적용해 공백만 있는 값을 400 으로 거절한다.
- **근거:** 요구사항 명세서는 상품명·설명을 "누락 불가"로 정했고, 공백만 있는 값은 실질적으로 누락이다. 다른 필드와 같은 규칙을 적용해 입력 검증을 일관되게 했다.

## 27. 메시지 전송 응답과 잔액 내역 조회의 세부 필드

- **내용:** 메시지 전송 응답(5.2.10)의 필드 목록에는 `senderNickname` 이 없지만 메시지 내역 조회(5.2.9)와 `MESSAGE` 이벤트에는 있다. 내역 조회(`GET /api/wallet/transactions`)가 지갑을 만드는지도 6.4절과 5.2.5절의 표현이 조금 다르다.
- **관련 문서:** 설계 명세서 5.2.5절, 5.2.9절, 5.2.10절, 6.4절
- **결정:** 메시지 전송 응답은 내역 조회와 같은 형식(`senderNickname` 포함)으로 돌려준다. 잔액 조회와 내역 조회 모두 지갑이 없으면 잔액 0 인 지갑을 만든다.
- **근거:** 필드를 더하는 것은 문서가 정한 필드를 빠뜨리지 않으며, 화면이 전송 결과와 조회 결과를 같은 방식으로 그릴 수 있다. 5.2.5절의 "재호출 처리"가 두 조회를 한 표로 묶어 "지갑 행이 아직 없을 때만 잔액 0 인 행을 만든다"고 정했다.

## 28. 환불 합의 실패 처리(기획서와 요구사항 명세서의 충돌)

- **내용:** 기획서는 판매자와 합의하지 못한 환불 거래를 보류 상태로 무기한 유지하고 강제 종결을 구현하지 않는다고 한다. 요구사항 명세서의 변경 이력 CH-001 은 판매자 거절 시 정상 완료와 판매대금 지급, 접수 후 48시간 무응답 시 자동 승인과 전액 환불로 바꿨다.
- **관련 문서:** 기획서 4장 6항, 4.4.5절, 6.3절(합의 실패 거래의 강제 종결 제외), 요구사항 명세서 1.1절, 1.2절, 7.2절 CH-001, 설계 명세서 5.2.20절, 6.18절
- **결정:** CH-001 을 따랐다. 판매자 동의는 반품 없는 전액 환불(`REFUNDED`), 판매자 거절은 정상 완료(`COMPLETED`, `REFUND_REJECTED`)와 판매대금 지급, 접수 후 정확히 48시간부터는 판매자 응답을 거절하고 자동 승인(`AUTO_APPROVED`)과 전액 환불을 한다.
- **근거:** 작업 지시가 환불 정책은 CH-001 을 따르라고 했고, 문서 우선순위(설계 명세서 → 요구사항 명세서 → 기획서)도 같은 결과다.

## 29. 기획서·요구사항 명세서의 동시성·중복 방지 요구와 이번 구현 범위

- **내용:** 기획서(4.2.3, 4.2.4, 4.7.2, 6.1.4절)와 요구사항 명세서(BR-004, F-003-AC-01, F-005-AC-01, F-006-AC-02, F-010-AC-01·02·04 등)는 동시 결제 제어, 같은 요청의 중복 반영 방지, 처리 도중 실패 시 일부 반영 금지를 요구한다. 설계 명세서는 이를 기본 기능 구현 이후의 후속 과제로 정했다.
- **관련 문서:** 설계 명세서 1.1절, 2.3절(후속 단계에서 구현·검증할 항목), 9장(후속 과제로 표시된 검증 행), 작업 지시(구현 범위)
- **결정:** 락, 격리 수준 조정, 낙관적 잠금, UNIQUE 제약, `requestId` 기반 중복 판단, 실패 복구, 스케줄러 중복 실행 방지는 구현하지 않았다. `requestId` 는 저장만 한다. 순차 요청에서의 중복 방지는 현재 상태 검사(409)와 자동 처리의 대상 조회 조건으로만 지킨다. 해당 수용 기준(F-003-AC-01, F-005-AC-01, F-006-AC-02, F-010-AC-01·02·04)은 테스트하지 않았다.
- **근거:** 문서 우선순위와 작업 지시가 같은 범위를 정했다. 순차 요청에서 반복 요청이 409 로 거절되고 금전 처리가 반복되지 않는 것은 각 기능 테스트(F-012-AC-03, F-015 반복, F-017-AC-03, F-018-AC-03·04 등)로 확인했다.

## 30. 실시간 전달이 실패한 클라이언트의 복구 방식(화면)

- **내용:** 설계 명세서는 놓친 내용을 대화 상세와 `afterId` 메시지 조회로 다시 가져온다고 정했지만, 화면이 언제 다시 연결하고 다시 조회하는지는 정하지 않았다. 기존 `chat.js` 는 연결이 끊기면 대기방으로 이동한다.
- **관련 문서:** 설계 명세서 5.3절(재호출 처리), 7.2절, 8.1절(연결 단절 후 복구), NFR-002
- **결정:** `conversation.js` 는 종료 코드 3000 이 아닌 이유로 연결이 끊기면 3초 뒤 대화 상세와 `afterId=마지막 messageId` 메시지를 다시 조회하고 다시 연결한다. 종료 코드 3000 이면 "다른 탭에서 접속"을 안내하고 다시 연결하지 않는다. 받은 메시지와 제안은 `messageId`, `offerId` 로 중복을 거른다.
- **근거:** NFR-002 와 8.1절의 "클라이언트가 마지막 messageId 를 기억해야 놓친 메시지만 받는다"를 화면에서 구현한 것이다. 3000 처리 방식은 5.3절이 정한 대로 기존 `chat.js` 와 같다.
