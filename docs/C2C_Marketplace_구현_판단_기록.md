## J-01 Oracle XE 컨테이너를 쓸 수 없음

- **충돌·누락:** 작업 지시는 Docker 를 쓸 수 있으면 Oracle XE 컨테이너에 테스트 스키마를 만들어 서비스 통합 테스트를 실행하라고 한다. 작업 환경에는 Docker CLI 만 있고 Docker 데몬이 실행되고 있지 않았다(`/var/run/docker.sock` 없음). 데몬을 직접 기동하려는 시도는 실행 환경의 보안 정책에 의해 차단되어 기동한 프로세스를 즉시 종료했다. 로컬 Oracle 설치도 없다.
- **관련:** 작업 지시 "실행·테스트 환경", 설계 9장.
- **결정:** Oracle 대상 통합 테스트는 실행하지 않은 항목으로 기록한다. Oracle 결과를 다른 DB 결과로 대신하지 않는다(J-02).
- **근거·영향:** Oracle 에서의 DDL 적용, `Instant`↔`TIMESTAMP(6)` 매핑(설계 4.3 "확인 필요"), IDENTITY 채번, CLOB 매핑은 이 환경에서 확인하지 못했다. README 에 Oracle 준비·실행 절차를 적어 사용자가 직접 실행할 수 있게 했다. 이후 DDL 적용은 사용자가 로컬 Oracle XE 에서 확인했다(J-30). 나머지 항목과 Oracle 통합 테스트는 여전히 확인하지 않았다.
- **상태:** 확정(환경 제약)

## J-02 H2(Oracle 호환 모드) 보조 실행 추가

- **충돌·누락:** Oracle 을 쓸 수 없을 때 "가능한 검증을 계속"하라는 지시와 "다른 DB 결과를 Oracle 검증 결과로 대체하지 않는다"는 지시가 함께 있다.
- **관련:** 작업 지시 "실행·테스트 환경", 설계 9장.
- **결정:** 통합 테스트는 DB 설정만 바꿔 같은 코드로 실행되도록 만들고, `-PintegrationDb=h2` 를 주면 테스트 런타임 전용 H2(Oracle 호환 모드)로 실행하는 보조 경로를 둔다. H2 실행 시에도 저장소의 `ddl_toychat.sql`, `ddl_marketplace.sql` 을 그대로 읽어 적용한다. H2 결과는 "H2 보조 실행"으로만 보고하고 Oracle 검증으로 보고하지 않는다.
- **근거·영향:** `testRuntimeOnly` 의존성 하나만 추가하며 운영 코드와 운영 설정은 H2 를 모른다. H2 는 Oracle 의 시간대 처리, 잠금, 오류 코드, CLOB 처리와 동일하지 않으므로 J-01 의 미확인 항목은 그대로 남는다.
- **상태:** 확정(사용자 확인: 유지). 지울 때는 의존성과 `application-integration-h2.yml`, `H2IntegrationDataSourceConfig` 를 함께 지운다.

## J-03 테스트 태스크 분리

- **충돌·누락:** `./gradlew build` 를 실행하라는 지시가 있고, 서비스 통합 테스트는 Oracle·Redis 가 필요하다. 외부 DB 없이 `build` 가 항상 실패하면 코드 문제와 환경 문제를 구분할 수 없다.
- **관련:** 작업 지시 "검증", 설계 9장.
- **결정:** `test`(build 에 포함)는 외부 자원이 필요 없는 단위 테스트만 실행한다. DB·Redis 가 필요한 테스트는 `@Tag("integration")` 으로 표시하고 `integrationTest` 태스크로 따로 실행한다. 통합 테스트를 비활성화하거나 조건을 낮춘 것이 아니며, 실행 여부와 결과를 따로 보고한다.
- **근거·영향:** `integrationTest` 는 JVM 기본 시간대를 `Asia/Seoul` 로 두어 시각 저장이 JVM 시간대에 좌우되지 않는지도 함께 본다. 한글 DDL 경로를 읽기 위해 리눅스 POSIX 로케일에서는 테스트 JVM 에 `LC_ALL=C.UTF-8` 을 준다.
- **상태:** 확정(업무 동작과 무관한 구성 선택)

## J-05 컴포넌트 스캔 제외 방식

- **충돌·누락:** 설계 8.2 는 `@ComponentScan` 제외 필터 추가를 정한다. `@SpringBootApplication` 에 `@ComponentScan` 을 덧붙이면 메타 어노테이션의 스캔과 함께 처리될 수 있다.
- **관련:** 설계 2.2.3, 8.2.
- **결정:** `ChatServiceApplication` 의 `@SpringBootApplication` 을 `@SpringBootConfiguration`·`@EnableAutoConfiguration`·`@ComponentScan(기존 기본 필터 + 제외 패키지 정규식)` 으로 풀어 쓴다. 제외 패키지는 `createroom`, `joinroom`, `concurrency`, `scheduler`, `roomlist`, `web`, `websocketcore`, `redis.controller`, `redis.service` 이며 파일은 수정·삭제하지 않았다.
- **근거·영향:** 제외 패키지 안의 Spring Data 저장소 인터페이스(`RoomQueueJpa`, `RoomQueueEntityJpa`)는 JPA 저장소 스캔 대상이라 빈으로 남지만 호출하는 곳이 없다. `/rooms`, `/api/v1/redis/singleData/*` 가 404 인 것을 통합 테스트로 확인했다.
- **상태:** 확정

## J-06 기존 회원 예외 핸들러 대체

- **충돌·누락:** 설계 2.2.2 는 `MemberAPIControllerExceptionHandler`, `MemberViewControllerExceptionHandler` 를 새 `ApiExceptionHandler` 로 대체한다고 정한다. 두 클래스는 다른 프로젝트 패키지를 가리켜 실제로 적용되지 않았다. 회원 도메인 예외(닉네임 중복, 회원 없음, JWT 키 없음)의 새 오류 코드는 설계 6.20 에 없다.
- **관련:** 설계 2.2.2, 5.1, 6.20.
- **결정:** 두 파일을 삭제하고 `ApiExceptionHandler` 를 `@RestController` 대상으로 둔다. `/members/join` 의 `@Valid` 실패는 새 형식(`VALIDATION_ERROR`, `fieldErrors`)으로 응답한다. 회원 도메인 예외는 새 코드를 만들지 않는다. 이 예외들은 클래스에 붙은 `@ResponseStatus` 대로(아이디·닉네임 중복 409, 회원 없음 404, JWT 키 없음 401) Spring Boot 기본 오류 응답으로 나간다. JSP 를 돌려주는 `@Controller` 는 이 핸들러의 대상이 아니다.
- **정정:** 처음 기록에는 회원 도메인 예외가 500 이 된다고 적었다. 화면 확인(J-27) 중 중복 가입이 409 로 오는 것을 보고 코드를 다시 확인해 바로잡았다. 동작은 바뀌지 않았다.
- **근거·영향:** 필드 메시지는 `message` 에도 이어 담아 `fieldErrors` 를 읽지 않는 클라이언트도 원인을 보여 줄 수 있게 했다. 화면 재작성(J-23)에서 `join.js` 를 다시 써서 `fieldErrors` 를 입력 칸별로 보여 주고, 409 는 "이미 사용 중인 아이디 또는 닉네임"으로 안내한다(기본 오류 응답에는 어느 값이 중복인지 없다).
- **상태:** 가정

## J-07 보안 체인 수준 403 의 오류 코드

- **충돌·누락:** 설계 5.1 은 `/api/**` 체인에 JSON 403 을 돌려주는 `ApiAccessDeniedHandler` 를 두라고 하지만, 6.20 목록에는 보안 체인 수준 거부에 대한 코드가 없다.
- **관련:** 설계 5.1, 6.20.

- **상태:** 가정

## J-08 소수·범위 초과 입력의 거절

- **충돌·누락:** 요구사항 2.3 은 저장·연산 범위를 넘는 값을 자르거나 반올림하지 않고 거절하라고 한다. Jackson 기본 설정은 정수 필드에 들어온 소수를 잘라서 받는다.
- **관련:** 요구사항 2.3, BR-003, F-001-AC-02·04, F-010-AC-07, 설계 4.3.
- **결정:** `spring.jackson.deserialization.accept-float-as-int=false` 로 소수를 400 `VALIDATION_ERROR` 로 거절한다. 금액 입력은 `NUMBER(15)` 범위(최대 999,999,999,999,999), 수량 입력은 `NUMBER(10)` 범위(최대 9,999,999,999)를 Bean Validation 으로 검사한다. 단가×수량, 충전·반환·지급 후 잔액이 범위를 넘으면 수동 요청은 변경 전에 400 으로 거절하고, 자동 처리는 그 건을 바꾸지 않고 오류 로그를 남긴다.
- **근거·영향:** 업무상 충전·보유 상한을 새로 둔 것이 아니다(설계 4.3). 회원 API DTO 에는 숫자 필드가 없어 영향이 없다.
- **상태:** 확정

## J-09 시각 매핑 설정

- **충돌·누락:** 설계 4.3 은 `Instant`(UTC) 저장과 `hibernate.jdbc.time_zone=UTC` 를 정하고 Oracle 매핑 동작은 구현 시작 시 확인하라고 한다. Hibernate 6 는 `Instant` 를 기본적으로 시간대 포함 타입으로 바인딩하는데 컬럼은 `TIMESTAMP(6)`(시간대 없음)이다.
- **관련:** 설계 4.3, 8.1 "시간 규칙", 8.2.
- **결정:** `hibernate.type.preferred_instant_jdbc_type=TIMESTAMP` 를 함께 설정해 `Instant` 를 UTC 달력으로 `TIMESTAMP` 에 쓰고 읽게 한다. 서비스는 `TimeRules.now()` 로 현재 시각을 마이크로초 단위로 잘라 쓴다(컬럼 정밀도 6자리와 맞추기 위해서다).
- **근거·영향:** 통합 테스트는 JVM 시간대를 `Asia/Seoul` 로 두고 저장 후 다시 읽은 시각이 같은지 확인한다. Oracle·ojdbc8 에서의 동작은 J-01 에 따라 확인하지 못했다.
- **상태:** 가정(Oracle 확인 필요)

- **상태:** 확정(설계가 위임한 선택)

## J-11 DDL 의 UNIQUE·CHECK 범위

- **충돌·누락:** 설계 4.2 는 `SHIPMENT.ORDER_ID`, `REFUND_REQUEST.ORDER_ID` 를 "주문당 하나"라고 설명하지만 제약 열에는 FK 만 적고, 4.1 은 동시 요청을 막을 목적의 제약을 이번 범위에서 정하지 않는다고 한다.
- **관련:** 설계 4.1, 4.2, 작업 지시 "구현 범위"(동시 요청 제어 제외).
- **결정:** UNIQUE 와 성능 목적 인덱스를 두지 않는다. "주문당 하나"는 순차 요청에서 서비스의 현재 상태 검사로 지킨다. 값 범위·열거값·`PAID_AMOUNT = UNIT_PRICE * QUANTITY`·`BALANCE >= 0` 은 CHECK 로 둔다. 시각 사이 관계(기한 = 기준 + 48시간 등)는 애플리케이션이 계산해 저장하고 CHECK 로 두지 않는다.
- **근거·영향:** 동시에 같은 주문에 발송·환불 요청이 들어오는 경우의 중복 방지는 후속 과제로 남는다.
- **상태:** 확정

## J-12 잔액 변동 내역 조회 시 지갑 행 생성

- **충돌·누락:** 설계 5.2.5 의 재호출 처리는 "지갑 행이 아직 없을 때만 잔액 0인 행을 만든다"고 하며 `/api/wallet` 과 `/api/wallet/transactions` 를 함께 다룬다. 내역 조회만 하는 경우에도 행을 만들지는 명시하지 않았다.
- **관련:** 설계 4.2 WALLET, 5.2.5, 6.4.
- **결정:** 두 조회 모두 지갑 행이 없으면 잔액 0 으로 만든다. 잔액과 내역 값은 바꾸지 않는다.
- **근거·영향:** 6.4 가 두 조회를 한 처리 순서로 적었다. 반환되는 데이터에는 차이가 없다.
- **상태:** 확정

## J-13 대화 WebSocket 의 허용 Origin

- **충돌·누락:** 설계 7.2 는 `ConversationWebSocketConfig` 를 기존 `WebSocketConfig` 와 같은 구조로 만들라고 한다. 기존 설정은 `setAllowedOrigins("*")` 로 모든 출처를 허용한다. 허용 출처는 설계에 정해져 있지 않다.
- **관련:** 설계 5.3, 7.2, NFR-003.
- **결정:** 등록 구조는 같게 두고 허용 출처는 지정하지 않아 Spring 기본값(같은 출처만 허용)을 쓴다.
- **근거·영향:** 이 연결은 쿠키로 인증하므로 모든 출처를 허용하면 다른 사이트의 페이지가 로그인한 사용자의 쿠키로 대화 이벤트를 받을 수 있다. 같은 출처에서 여는 `conversation.jsp` 와 Origin 헤더를 보내지 않는 테스트 클라이언트는 영향이 없다. 다른 출처의 클라이언트가 필요하면 허용 목록을 정해야 한다.
- **상태:** 확정(사용자 확인: 유지). 다른 출처 허용은 사용자가 후속 개선으로 진행한다.

## J-15 실시간 전달 시점과 전송 실패

- **충돌·누락:** 설계 7.2 는 "저장이 끝난 뒤 한 번 시도한다"고 정한다. 서비스 메서드에 트랜잭션을 적용하면 메서드 안에서 보낸 이벤트가 커밋 전에 도착할 수 있다.
- **관련:** 설계 3.3, 5.3, 7.2, NFR-001.
- **결정:** `RealtimePublisher` 는 트랜잭션이 진행 중이면 커밋 직후(`afterCommit`)에 보낸다. 이벤트 본문(쓰기 가능 여부·남은 수량 등)은 트랜잭션 안에서 계산해 두고 전송만 미룬다. 전송 실패는 로그만 남기며 다시 보내지 않는다. 같은 세션에 여러 스레드가 동시에 보내는 경우의 직렬화는 하지 않았다.
- **근거·영향:** 롤백된 메시지·제안·주문이 상대방 화면에 먼저 나타나지 않는다. 동시 전송 충돌로 일부 이벤트가 전달되지 않을 수 있으며, 클라이언트는 재접속 후 대화 상세·메시지 조회로 확인한다. 전달 보장 개선은 후속 과제다.
- **상태:** 확정(전달 시점), 한계 기록(동시 전송)

## J-17 자동 처리의 트랜잭션 단위와 한 건 실패 시 동작

- **충돌·누락:** 설계 7.1 은 자동 처리 4종을 "주문 한 건씩" 처리한다고 하면서, 한 건에서 예외가 나면 다음 건을 계속 처리할지와 일부만 반영된 상태의 복구는 후속 단계에서 정한다고 한다. 6장 머리 6번은 자동 처리에서 금액 범위를 넘으면 해당 건의 변경 전에 오류를 기록하라고 한다. 기본 구현에서도 어느 한 동작은 정해야 한다.
- **관련:** 설계 4.4.3, 6장 머리, 6.13, 6.14, 6.16, 6.18, 7.1, 작업 지시 "구현 범위"(일반적인 Spring 트랜잭션 적용).
- **결정:** 대상 주문 ID 를 먼저 조회한 뒤 주문 한 건씩 별도 트랜잭션(`TransactionTemplate`, 기본 전파·격리)으로 처리한다. 트랜잭션 안에서 주문을 다시 읽어 조건(상태·기한·발송/환불 요청 존재)을 다시 확인한다. 한 건에서 예외가 나면 그 건은 롤백되고 오류 로그를 남긴 뒤 다음 건을 처리한다. 처리 결과로 이번 실행의 처리 건수를 돌려준다.
- **근거·영향:** 4.4.3 이 주문의 최종 상태 변경·잔액 변동·내역 기록을 한 묶음으로 정했으므로 묶음 단위를 주문 한 건으로 했다. 실패한 건은 상태가 바뀌지 않아 다음 폴링에서 다시 대상이 된다. 이는 별도의 재시도 장치가 아니라 대상 조회 조건의 결과이며, 실패 원인이 남아 있으면 계속 실패한다. 재시도 정책·복구·스케줄러 중복 실행 방지는 구현하지 않았다.
- **상태:** 확정(사용자 확인: 유지)

## J-25 화면이 보여 주는 요청 버튼과 서버 판정, 요청 식별자

- **충돌·누락:** 설계는 각 API 의 허용 조건만 정하고, 화면이 어떤 요청을 언제 보여 줄지는 정하지 않았다.
- **관련:** 설계 5.2, 6.10~6.18, F-019 추가 규칙, J-16.
- **결정:**
  - 주문 상세는 거래 상태·배송 상태·내 역할·기한을 보고 지금 할 수 있는 요청(발송 등록, 취소, 구매 확정, 환불 요청, 환불 승인·거절)만 보여 준다. 브라우저 시계로 기한이 지났으면 버튼 대신 자동 처리를 기다린다는 안내를 보여 준다. 허용 여부와 기한 판정은 서버가 하고, 거절되면 서버 메시지를 그대로 보여 준다.
  - 요청을 보내는 동안 누른 버튼을 잠근다. 화면 동작일 뿐이며 서버의 중복 요청 판단(후속 과제)을 대신하지 않는다.
  - 충전·결제·발송 등록·환불 요청·가격 제안에는 화면에서 만든 `requestId`(UUID)를 넣는다. 결과를 알 수 없는 실패(연결 실패, 5xx)에서는 같은 값을 유지하고, 성공하거나 서버가 거절(4xx)하면 새 값을 만든다. 서버는 이 값을 저장만 한다(J-16). 메시지 전송에는 넣지 않았다.
  - 결제 결과를 알 수 없으면 다시 결제하기 전에 구매 내역에서 주문이 만들어졌는지 확인하라고 안내한다.
  - 상대방의 처리나 자동 처리로 상태가 바뀌어 주문 요청이 409 로 거절되면, 거절 사유를 알리고 주문을 다시 읽어 지금 상태의 안내와 버튼으로 다시 그린다. 결제가 재고 부족(409 `INSUFFICIENT_STOCK`)으로 거절되면 입력한 수령인·주소·가격 선택은 그대로 두고 남은 수량만 다시 읽는다.
  - 판매가 끝난 상품은 공개 상세가 404 이다(F-002, 설계 5.2.3). 화면은 이를 "판매가 끝났거나 없는 상품"으로 안내하고, 대화 화면은 판매 중일 때만 상품 화면으로 연결한다. 주문 상세는 상품 화면 대신 주문에 담긴 상품 정보(설명 포함)를 보여 준다.
  - 판매가 끝난 뒤 남은 대기 제안은 서버 상태가 그대로 `PENDING` 이지만 "판매 종료로 응답 불가"로 표시한다(F-009 추가 규칙). 발송 기한 경과 자동 취소의 고정 사유 코드(`SHIPMENT_DEADLINE_EXPIRED`)는 한국어 안내로 바꿔 보여 준다.
  - 메인 화면의 로그인 여부는 닉네임과 따로 받는다(`data-logged-in`). 처음에는 기존 화면처럼 닉네임 자리의 `"none"` 으로 비로그인을 나타냈으나, 닉네임이 `none` 인 회원이 비로그인으로 보이는 문제를 리뷰에서 확인해 바꿨다.
- **상태:** 가정

## J-26 지갑 첫 조회의 동시 요청 실패

- **발견:** 브라우저 확인(J-27, H2 보조 실행) 중 지갑 행이 없는 회원이 지갑 화면을 처음 열자, 머리글의 잔액 조회(`GET /api/wallet`)와 화면의 내역 조회(`GET /api/wallet/transactions`)가 함께 지갑 행을 만들려다 한쪽이 기본키 위반으로 500 을 받았다.
- **관련:** 설계 6.4(조회 시 지갑 행이 없으면 만든다), J-12, 작업 지시 "동시성 제어는 후속 과제".
- **결정:** 서버는 바꾸지 않았다. 화면은 진행 중인 잔액 조회가 있으면 그 결과를 함께 쓰고, 지갑 화면은 잔액 조회가 끝난 뒤 내역을 조회한다. 그래서 한 화면 안에서는 두 요청이 겹치지 않는다.
- **근거·영향:** 다른 탭이나 다른 클라이언트에서 첫 조회가 동시에 들어오거나, 첫 조회와 판매대금 지급·환불 반환이 겹치면 같은 실패가 남는다. 동시 요청 제어 과제에서 함께 다뤄야 한다.
- **상태:** 확정(한계 기록)

## J-27 화면 확인 방법과 범위

- **결정:** 화면 동작은 Playwright(Chromium)로 직접 확인했다. 통합 테스트 설정(H2 보조 실행, 테스트 Redis)으로 서버를 띄우는 임시 테스트와 브라우저 스크립트를 썼고, 둘 다 저장소에 넣지 않았다. 모의 배송 완료는 테스트 Clock 을 3분 옮긴 뒤 서비스 메서드를 직접 호출했다.
- **확인한 흐름:**
  - 비로그인 목록과 로그인 안내, 상품 등록(빈 입력의 칸별 오류 포함), 충전, 목록 → 상세 → 문의
  - 두 브라우저 사이의 실시간 메시지, 가격 제안·수락과 합의 가격 자동 선택, 제안 거절 뒤 다시 제안
  - 합의 가격으로 2개 결제, 발송 등록(빈 입력 오류 포함), 배송 완료 뒤 환불 요청, 판매자 거절과 판매대금 지급
  - 등록 가격 결제 뒤 구매자 취소와 전액 반환, 판매자 취소, 환불 승인과 전액 반환, 잔액 내역
  - 재고보다 많은 수량 입력 시 입력값 유지, 상대방이 취소한 주문에 발송 등록 시 409 뒤 최신 상태로 다시 그림
  - 판매 종료 뒤 대화 읽기 전용, 판매 종료 상품 상세 안내, 주문 상세의 상품 정보
  - 실시간 연결을 강제로 끊은 동안 상대방이 보낸 메시지가 재연결 뒤 나타남(J-29). 같은 확인을 수정 전 대화 화면 코드로 돌리면 이 단계에서 실패하는 것도 확인했다.
  - 회원 가입 오류·성공·중복, 가입한 계정(닉네임 `none`)의 로그인 폼과 로그인 표시, 390px 폭 화면(가로 넘침 없음)
- **화면 코드 리뷰:** 보안·API 계약·정책 문구·화면 로직의 네 관점으로 리뷰하고, 지적마다 다른 검토자가 반박을 시도해 확인했다. 확인된 지적 14건(같은 내용 1건 포함)을 모두 고쳤다. 보안 관점의 지적은 없었다. 고친 부분만 다시 리뷰해 나온 회귀 지적 5건(오류 칸 초점 순서, 확인 창의 첫 초점, 오른쪽 열의 그림자 잘림, 상태 충돌 뒤 안내 순서, 대화 영역 이름 중복)도 고쳤다. 확인 창은 모두 되돌릴 수 없는 요청을 묻으므로 처음 초점을 항상 취소 버튼에 둔다.
- **확인하지 않은 것:** 무응답 자동 환불, 확인 기간 만료 자동 완료, 발송 기한 자동 취소의 화면 표시(서버 동작은 통합 테스트로 확인했다). 화면 읽기 프로그램으로 직접 들어 보는 확인. Chromium 외 브라우저. Oracle 환경.
- **상태:** 확정(검증 기록)

## J-28 회원 정보 수정 화면을 연결하지 않음

- **충돌·누락:** 기존 `modify.jsp` 의 수정 버튼에는 스크립트가 붙어 있지 않아 동작하지 않는다. 수정 API(`POST /members/edit`)는 JWT 로 인증하지만 수정 대상은 요청 본문의 `id` 로 정한다(`MemberService.editMember`). 수정 화면(`GET /members/edit?editid=`)은 인증 없이 열리며, 설계 8.1 "접근 통제"의 한계와 전제는 이 문제를 이번 범위 밖으로 둔다.
- **관련:** 설계 2.2.1(회원 화면 재사용), 8.1.
- **결정:** 새 머리글에 회원 정보 수정 링크를 두지 않았고 `modify.jsp` 에 스크립트를 붙이지 않았다.
- **근거·영향:** 화면을 연결하면 본문의 `id` 로 다른 회원의 정보를 바꿀 수 있는 기존 API 를 화면에서 쓰게 된다. 회원 기능을 고치는 일은 이번 요구사항 범위 밖이므로 따로 다뤄야 한다.
- **상태:** 가정

## J-29 대화 화면의 놓친 내용 따라잡기

- **충돌·누락:** 설계 5.3·7.2 는 이벤트를 저장 뒤 한 번만 보내고, 놓친 내용은 재접속 후 조회로 확인한다고 한다(J-15). 언제 무엇을 기준으로 다시 조회할지는 정하지 않았다.
- **관련:** 설계 5.2.9(`afterId`), 5.3, 7.2, J-15.
- **결정:**
  - 실시간 연결이 열릴 때마다(첫 연결 포함) 따라잡기 기준 이후의 메시지와 대화 상세를 다시 조회한다. 첫 조회와 연결 사이에 저장된 내용도 이벤트로 오지 않기 때문이다.
  - 따라잡기 기준은 메시지 조회(REST) 결과로만 올린다. 내가 보낸 메시지나 받은 이벤트로 올리면, 끊긴 동안 저장됐거나 전달에 실패한 앞선 메시지를 건너뛴다. 다시 받은 메시지는 `messageId` 로 거른다.
  - 처음 구현은 재연결 때만 따라잡고 마지막으로 화면에 들어온 메시지 ID 를 기준으로 썼다. 리뷰에서 첫 연결 전 메시지가 빠지는 경우와, 끊긴 동안 내가 보낸 메시지가 기준을 넘기는 경우를 확인해 바꿨다(J-27 의 강제 끊김 확인).
- **근거·영향:** 연결된 채로 이벤트 하나가 전달에 실패하면 다음 재연결이나 새로고침 때 채워진다. 그 전까지는 화면에 빠져 있다. 전달 보장은 J-15 대로 후속 과제다.
- **상태:** 가정

## J-30 로컬 Oracle 의 MEMBERTBL 에 기본키가 없음

- **발견:** 사용자가 로컬 Oracle XE 의 `TOYCHAT` 스키마에 `ddl_marketplace.sql` 을 실행하자(2026-10-06), 회원을 참조하는 `PRODUCT`·`WALLET`·`BALANCE_TRANSACTION` 이 `ORA-02270`(참조할 기본키·고유 키 없음)으로 실패했다. 나머지 6개는 먼저 만들어져야 할 테이블이 없어 `ORA-00942` 로 함께 실패해, 테이블은 하나도 만들어지지 않았다. 실제 `MEMBERTBL` 에는 NOT NULL 제약(`C`)만 있고 기본키가 없었다.
- **관련:** `ddl_toychat.sql`(저장소의 정의에는 `PK_MEMBERTBL` 이 있다), 설계 4.1·4.2(회원 FK), J-01, J-02.
- **결정:** 새 테이블의 회원 FK 는 설계대로 둔다. 사용자가 `ID` 중복·NULL 이 없는 것을 확인한 뒤 `ALTER TABLE MEMBERTBL ADD CONSTRAINT PK_MEMBERTBL PRIMARY KEY (ID)` 로 기본키를 추가했고, 스크립트를 다시 실행해 새 테이블이 만들어졌다. `ddl_marketplace.sql` 머리말의 선행 조건과 README 의 DDL 적용 절에 이 확인 절차를 적었다.
- **근거·영향:** 저장소의 `ddl_toychat.sql` 과 엔티티(`@Id`)가 전제하던 상태로 실제 DB 를 맞춘 것이며 회원 데이터는 바꾸지 않았다. H2 보조 실행은 저장소 DDL 로 테이블을 만들기 때문에 이 차이를 드러내지 못했다. 실제 DB 와 저장소 DDL 의 다른 차이는 확인하지 않았다.
- **상태:** 확정(환경 사실)
